# PTES 渗透测试执行标准：七个阶段

> 来源：<http://www.pentest-standard.org/index.php/Main_Page>（通过 Web Archive 快照读取，读取日期 2026-09-15）。
> 该站点当前直接访问不稳定；若主站不可达，改用 <https://web.archive.org/> 检索快照。

## 1. PTES 是什么，解决什么问题

PTES（Penetration Testing Execution Standard，渗透测试执行标准）是一份社区维护的**渗透测试流程规范**。它覆盖"一次渗透测试相关的全部事情"——从最初的沟通，到情报收集、威胁建模、漏洞研究、利用与后渗透，直到报告。

它和本模块其他标准的区别：

| 标准 | 回答的问题 | 定位 |
| --- | --- | --- |
| **PTES** | **一次渗透测试应该按什么步骤做？每步的输入输出是什么？** | 流程（Process） |
| [MITRE ATT&CK](../mitre-attack/README.md) | 对手用什么战术技术？ | 对手行为知识库 |
| [OWASP / WSTG](../owasp/README.md) | Web 应用该测哪些项、怎么测？ | 技术测试方法 |
| [Exploit-DB](../exploit-db/README.md) | 有哪些现成的 EXP？ | 武器库 |
| [CWE](../cwe/README.md) | 这个缺陷属于哪类弱点？ | 弱点分类 |
| [NIST SP 800-115](../nist/800-115.md) | 安全测试与评估的规范方法是什么？验收标准是什么？ | 规范与评估 |

一句话：**PTES 管"怎么走流程"，其余标准往流程的各个格子里填空。**

PTES 还配套一份 **Technical Guidelines（技术指南）**，把流程各阶段的技术细节展开；本页只讲流程骨架，技术细节请查官方 Technical Guidelines。

## 2. 七个阶段总览

| # | 阶段英文名 | 中文名 | 一句话目标 | 主要产出 |
| --- | --- | --- | --- | --- |
| 1 | Pre-engagement Interactions | 前期交互 | 把"要测什么、不能碰什么、出事怎么办"谈清楚并书面化 | 授权书、范围表、规则约定 |
| 2 | Intelligence Gathering | 情报收集 | 尽可能多地拿到目标的技术与业务信息 | 资产清单、技术栈、账号线索、组织信息 |
| 3 | Threat Modeling | 威胁建模 | 决定"哪些路径最值得打"，把无限的可能性收敛成有限的目标 | 攻击路径优先级、场景清单 |
| 4 | Vulnerability Analysis | 漏洞分析 | 找出候选弱点并验证其真实可利用性 | 已验证漏洞清单（含证据） |
| 5 | Exploitation | 利用 | 在授权范围内真正突破，验证影响 | 利用记录、权限获取证据 |
| 6 | Post Exploitation | 后渗透 | 评估"拿到之后能造成多大影响" | 影响范围、横向路径、数据可达性证据 |
| 7 | Reporting | 报告 | 把技术发现翻译成决策者能用的信息 | 报告、修复建议、复现步骤 |

**阶段顺序不是单纯线性的。**实战中 2↔3↔4 会反复循环（新情报修正威胁模型，新漏洞改变情报需求），5→6 之间也可能回到 4。PTES 的结构是"检查有没有漏掉该做的事"，不是"必须严格串行"。

## 3. 阶段一：前期交互（Pre-engagement Interactions）

**目标**：在动手之前，把所有会导致"法律风险 / 业务中断 / 甲乙双方预期不符"的事谈清楚。

**输入**：客户的测试诉求、合规要求（如等保、PCI DSS、SOC 2）、预算与时间窗。

**关键动作**

1. **确定测试意图**：是为了合规取证、上线前把关，还是为了验证某个具体防护？意图决定强度。
2. **划定范围（Scope）**：明确到具体域名、IP 段、应用、账号、时间窗。**范围必须同时写"包含什么"和"不包含什么"**。第三方托管系统、CDN、云服务商的基础设施通常需要额外书面许可。
3. **规则约定（Rules of Engagement, RoE）**：
   - 允许的攻击强度（是否允许 DoS 类测试、是否允许社会工程、是否允许物理入侵）；
   - 测试窗口（可测时段、禁测时段，如月末结算期）；
   - 应急联系人（技术联系人 + 业务决策人 + 法务），含**非工作时间联系方式**；
   - 发现严重问题时的**即时通报机制**（例如：一旦拿到域管权限，立刻停手并电话通报）；
   - 数据处理规则（测试中取得的凭据、数据如何存储、何时销毁）。
4. **取得书面授权**：授权书必须由**有权授权的人**签署（通常是 CTO / CISO / 法定代表），而不是对接的技术经理。授权范围要与范围表一字不差。
5. **确认法律与合规要素**：测试数据是否涉及个人信息；是否触发客户所在行业的监管报告义务；保险公司是否要求事前报备。

**输出**：签署的授权书 / SOW、范围表、RoE 文档、联系人清单。

**常见失误**

| 失误 | 后果 |
| --- | --- |
| 只口头确认范围 | 事后纠纷时无法举证，测试人员独自承担法律风险 |
| 授权书由对接人签署，但其无授权权限 | 授权无效，测试行为可能构成未授权访问 |
| 范围里没排除第三方托管系统 | 打到云服务商基础设施，触发对方法务 |
| 没约定"拿到域管后怎么办" | 测试人员继续深入，客户完全不知情，产生信任危机 |
| 没约定数据销毁 | 测试中导出的客户数据长期滞留在测试方，成为新的合规风险 |
| 应急联系人只有工作时间电话 | 周末测出严重问题，无人响应 |

## 4. 阶段二：情报收集（Intelligence Gathering）

**目标**：在与目标交互（被动）或最小交互（主动）的前提下，尽量还原目标的资产、技术、人员面貌。

**输入**：范围表、合规约束（哪些信息采集手法被允许）。

**关键动作**

1. **被动情报（Passive / OSINT）**——不与目标直接交互：
   - 域名与子域名枚举、DNS 历史记录、证书透明度日志（CT Log）；
   - 公开代码仓库中的凭据与内网信息泄露；
   - 招聘信息反推技术栈与内部系统名称；
   - 组织架构与人员（用于评估是否要做社会工程）；
   - 搜索引擎与公开数据泄露情报。
2. **半被动情报**——查 WHOIS、ASN 归属、云资产指纹，不直接触碰目标服务。
3. **主动情报（Active）**——**必须在授权范围内**：
   - 端口与服务扫描、服务版本识别；
   - Web 指纹（框架、中间件、WAF）；
   - 目录与接口发现。
4. **信息整理**：把收集到的内容结构化为「资产 ↔ 服务 ↔ 版本 ↔ 归属人 ↔ 业务重要性」。

**输出**：资产与服务清单、技术栈清单、人员与组织信息、可疑暴露面列表。

**常见失误**

- **被动与主动混为一谈**：把主动扫端口当"情报收集"却没在授权范围里写明，性质就变了。
- **只收集技术信息，忽略业务信息**：不知道哪个系统承载核心业务，就无法做威胁建模排序。
- **不做资产归属确认**：把客户租用的云服务商 IP 当客户资产测，越界。
- **信息不沉淀**：情报散在几个人脑子里，后渗透阶段想用却找不到。

## 5. 阶段三：威胁建模（Threat Modeling）

**目标**：把"可能性无限"的攻击面收敛成"值得投入时间"的有限路径集合。**这是 PTES 里最被忽视、但决定测试质量的一步。**

**输入**：阶段二的资产与业务信息。

**关键动作**

1. **确定有价值的资产**：哪些系统一旦失陷会造成真实业务影响（客户数据、资金通道、核心生产系统）。
2. **识别威胁主体**：客户更怕哪类攻击者（机会型犯罪团伙、内部人员、定向 APT）？不同主体动机与手法差别巨大。
3. **枚举攻击路径**：从外部到核心资产的路径。每条路径标注需要的前置条件。
4. **排序与选优**：对路径按「可行性 × 影响」排序，选出本轮要打的若干条。
5. **与客户对齐**：把排序结果给客户确认——客户往往会指出"这条路径对应的业务系统下周就要下线了"，能节省大量时间。

**可借助的工具**：用 [MITRE ATT&CK](../mitre-attack/mapping-guide.md) 把每条路径上的行为映射到技术编号，做覆盖度和可行性评估；这正是 ATT&CK 与 PTES 的结合点。

**输出**：排好序的攻击路径清单、每条路径的假设与前置条件。

**常见失误**

- **跳过威胁建模直接扫**：工具扫描结果是"有什么洞"，不是"哪里值得打"。这是纯扫描式测试和真渗透测试的分水岭。
- **只从技术角度排序**：忽略业务影响，导致把时间花在边缘系统上。
- **没有让客户参与**：排序脱离业务现实。

## 6. 阶段四：漏洞分析（Vulnerability Analysis）

**目标**：找出候选弱点，并**验证其真实可利用性**——未经确认的扫描结果不是漏洞，是"可能性"。

**输入**：排好序的攻击路径、资产清单。

**关键动作**

1. **自动化扫描**：作为**发现线索**的手段，不作为结论。扫描器的输出需要人工去伪。
2. **人工验证**：对每个候选弱点，构造最小验证动作，确认：
   - 目标版本/配置确实存在该弱点；
   - 在**当前环境约束**下（WAF、补丁、编译选项、权限模型）确实可利用；
   - 利用的**前置条件**是否满足。
3. **去伪（误报排除）**：详见 [CWE 审计指南](../cwe/audit-guide.md) 里每种弱点的"误报排除"思路。
4. **关联 EXP 与弱点分类**：用 [Exploit-DB](../exploit-db/README.md) 找现成利用代码，用 [CWE](../cwe/README.md) 归类弱点类型，用 CVE 定位具体实例。
5. **记录证据**：每个确认的漏洞都要有**可复现的最小步骤 + 截图/输出**。没有证据的发现不能进报告。

**输出**：已验证漏洞清单（含严重度、证据、前置条件、影响）。

**常见失误**

| 失误 | 后果 |
| --- | --- |
| 直接拿扫描器报告当交付 | 大量误报，报告可信度崩塌 |
| 把"版本号在受影响范围"当成"漏洞存在" | 实际打了补丁或配置不可达，属于假阳性 |
| 复现步骤不完整 | 客户安全团队无法复核，修复方也不知道怎么验证修好了 |
| 破坏性验证 | 用 `DROP TABLE` 之类手法验证 SQLi，造成真实数据损失 |
| 只记"有漏洞"，不记前置条件 | 修复排序时无法判断真实风险 |

## 7. 阶段五：利用（Exploitation）

**目标**：在授权范围内真正突破，用**实际影响**替代**理论风险**。

**输入**：已验证漏洞清单、攻击路径。

**关键动作**

1. 按攻击路径组织利用，而不是按漏洞列表逐个打。
2. 优先使用**影响最小、可回退**的利用方式。能在只读验证就不改数据。
3. 每次利用记录：时间戳、源 IP、目标、手法、使用的 EXP 编号或工具版本、结果。
4. **严格遵守 RoE**：触及约定的停手条件（如获得域管）立即停止并通报。
5. 保留完整证据链：为后续报告和客户复核服务。

**输出**：利用记录、获取的权限清单、突破路径图。

**常见失误**

- **利用强度失控**：为了"打通路径"用了可能引起服务重启的手法，影响业务。
- **越界**：利用过程中落到范围外的第三方系统。
- **记录不完整**：无法向客户说明"我们到底改了/看了什么"，客户无法评估污染范围。
- **不停手**：RoE 明确要求拿到域管即通报，测试人员继续深入，客户端完全失去可见性。

## 8. 阶段六：后渗透（Post Exploitation）

**目标**：回答客户最关心的问题——**"如果我被这样打进来，会损失什么？"**

**输入**：已获取的访问权限、资产与业务重要性信息。

**关键动作**

1. **确定权限价值**：当前权限能访问哪些资产？能改什么？能读什么？
2. **识别高价值目标**：定位核心数据（客户信息、财务数据、源代码、密钥、备份）。
3. **评估横向移动可能性**：还有多少主机可用同一凭据/同一弱点拿下。
4. **评估持久化与隐蔽性**：攻击者能否长期驻留而不被发现（**只做评估，是否实际落持久化必须严格按 RoE 决定**）。
5. **清理与恢复**：按 RoE 要求移除测试期间引入的账号、文件、配置变更，并**逐项列出清理清单**供客户核对。
6. **数据最小化**：只取证明影响所需的最少量数据样本；按约定销毁。

**输出**：影响范围说明、数据可达性证据、横向路径、清理清单。

**常见失误**

| 失误 | 后果 |
| --- | --- |
| 未与客户约定是否允许落持久化 | 留下后门，成为长期的真实安全隐患 |
| 不留清理清单 | 测试引入的账号/文件长期存在，无人清除 |
| 大量导出真实数据 | 测试方成为数据泄露源，触发合规问题 |
| 只报"拿到了域管"，不评估业务影响 | 客户无法做风险决策 |
| 后渗透无节制扩大范围 | 影响生产业务 |

---

## 9. 阶段七：报告（Reporting）

**目标**：把技术发现翻译成**能让不同角色各自做出决策**的信息。

**输入**：前六阶段的全部记录。

**关键动作**

1. **面向不同读者分层写**：
   - 给管理层：执行摘要（业务影响、风险等级、优先修复顺序）；
   - 给技术团队：发现详情（复现步骤、证据、修复建议）；
   - 给合规/审计：方法论、范围、时间、工具、限制说明。
2. **风险评级要有依据**：用 CVSS 等公开量表，并说明环境因素如何调整了分数。
3. **修复建议要可执行**：写"升级到 X 版本并把 Y 参数改为 Z"，而不是"加强安全意识"。
4. **写清限制**：时间窗、范围外系统、未验证的假设、可能存在的遗漏。
5. **附上证据**：截图、命令输出、时间线。
6. **提供复核方式**：让客户能自己验证修复是否有效。

详细的报告结构与模板见 [templates.md](./templates.md)。

**常见失误**

- **只有技术细节，没有执行摘要**：管理层看不懂，报告被搁置，问题不修复。
- **风险评级虚高**：所有漏洞都是"严重"，客户无法排优先级，等于没排。
- **修复建议不可执行**："加固服务器"不是建议。
- **不写限制**：客户误以为"报告里没有的就是安全的"。
- **不提供复核方法**：修复后无法验证。

## 10. 与 NIST SP 800-115 的关系

[NIST SP 800-115](../nist/800-115.md) 是美国 NIST 发布的技术指南，和 PTES 是互补的：

| 维度 | PTES | NIST SP 800-115 |
| --- | --- | --- |
| 性质 | 社区标准，流程规范 | 政府机构技术指南 |
| 侧重 | 渗透测试的完整流程与商务/法律交互 | 技术测试与审查的方法、四种技术分类、评估规划 |
| 阶段划分 | 7 个阶段 | 技术分 4 类（Review / Target Identification / Target Vulnerability Validation / Planning），流程分测试前、中、后 |
| 独有内容 | Pre-engagement 的商务与法律细节、Threat Modeling | 评估政策制定、评估优先级与排期、规则约定模板、数据处理的四个环节 |
| 使用方式 | 拿来做项目流程骨架 | 拿来做方法学依据与验收标准 |

**实践建议**：用 PTES 的 7 阶段组织项目流程，用 SP 800-115 的技术分类检查"我们有没有漏掉某类技术手法"，用 SP 800-115 附录的规则约定模板补强 RoE。对比细节见 [../nist/800-115.md](../nist/800-115.md)。
