# PTES 交付物模板集

本页所有模板都是**可直接复制使用**的。方括号 `[ ]` 内的内容是占位符。

- 阅读前置：[README.md](./README.md)（七个阶段）
- CVSS 字段说明依据：<https://www.first.org/cvss/v4.0/specification-document>、<https://www.first.org/cvss/>（读取日期 2026-09-15）

## 1. 项目授权书（SOW）要点清单

授权书（Statement of Work / 渗透测试授权书）是本项目**法律效力的来源**。缺少任一项都可能让测试行为性质改变。

### 1.1 必备条款

| # | 条款 | 必须写清的内容 | 常见错误 |
| --- | --- | --- | --- |
| 1 | 委托方与受托方全称 | 法定名称、统一社会信用代码/注册号、地址 | 用品牌名代替法定名称 |
| 2 | **签署人及其授权依据** | 签署人姓名、职务、证明其有权授权的依据（如董事会授权、法定代表人授权书） | 由对接的技术经理签署，无授权依据 |
| 3 | 服务范围（In-Scope） | 逐条列出域名、IP/网段、URL、应用名、API、账号、设备；**含时间窗口** | 只写"公司全部系统"，边界模糊 |
| 4 | **排除范围（Out-of-Scope）** | 明确列出不测的系统，特别是：第三方托管系统、生产数据库主库、灾备中心、云服务商基础设施、员工个人设备 | 只写包含不写排除 |
| 5 | 测试类型与强度 | 黑盒/灰盒/白盒；是否允许 DoS、社会工程、物理入侵、无线、供应链 | 未写明是否允许社会工程，测试人员真的去钓了 |
| 6 | 规则约定（RoE）摘要 | 测试窗口、禁测时段、允许的破坏性上限、停手条件 | 未约定停手条件 |
| 7 | 应急联系人与升级路径 | 技术联系人、业务决策人、法务；含**非工作时间**联系方式；约定响应时限 | 只有工作时间电话 |
| 8 | 即时通报义务 | 触发哪些条件必须立即停手并通报（例如获得最高权限、发现真实入侵痕迹、发现数据已泄露） | 无此条款 |
| 9 | 数据处理与销毁 | 测试中取得的凭据/数据的存储方式、访问控制、销毁时限与销毁证明 | 无销毁条款 |
| 10 | 保密义务 | 保密范围、保密期限、例外情形 | 无 |
| 11 | 知识产权与报告归属 | 报告的归属与使用限制 | 无 |
| 12 | 责任限制与免责 | 明确"在授权范围内依约行事造成的影响由委托方承担" | 责任条款缺失，测试方承担全部风险 |
| 13 | 费用与付款 | 金额、付款节点、变更范围时的计费方式 | 无变更计费条款 |
| 14 | 变更程序 | 任何范围变更必须以**书面补充协议**确认 | 靠微信/口头扩大范围 |
| 15 | 争议解决与适用法律 | 管辖地、适用法律 | 无 |

### 1.3 签署前核对（每一项不通过就不开工）

- [ ] 签署人确实有权授权（有书面依据）
- [ ] 范围表里每一行都写到了 IP/域名/应用 粒度
- [ ] 排除范围逐条写明
- [ ] 授权书、范围表、RoE 三者的范围描述**完全一致**
- [ ] 应急联系人含非工作时间联系方式，且**已实际拨通验证过**
- [ ] 第三方系统已有书面同意
- [ ] 数据处理与销毁条款已约定
- [ ] 变更程序已约定

## 2. 测试范围表（附件一）

| 序号 | 资产名称 | 类型 | 标识（域名/IP:端口/URL/应用） | 归属方 | 是否在范围 | 业务重要性 | 允许的测试强度 | 备注 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 1 | 官网门户 | Web | `https://www.example.com` | 甲方 | ✅ | 高 | 只读验证，禁止写入 | |
| 2 | 客户 API | API | `https://api.example.com/v2` | 甲方 | ✅ | 极高 | 允许写入测试账号数据 | 仅限测试账号 `pentest01` |
| 3 | 办公 VPN | 网络 | `vpn.example.com:443` | 甲方 | ✅ | 高 | 禁止暴力破解（可能锁号） | 锁定策略：5 次 |
| 4 | CRM 系统 | SaaS | `https://acme.crm-vendor.com` | **第三方** | ❌ | 高 | — | 供应商未授权，严禁测试 |
| 5 | CDN 边缘节点 | 基础设施 | `*.cdn-vendor.net` | **第三方** | ❌ | — | — | 属于 CDN 服务商 |
| 6 | 生产数据库主库 | DB | `10.20.30.40:5432` | 甲方 | ❌ | 极高 | — | 禁止直连，仅允许经应用层间接验证 |
| 7 | 员工个人手机 | 终端 | — | 个人 | ❌ | — | — | 含 BYOD 设备 |

**填表要点**

- `归属方` 是关键列：一旦这一列不是甲方，就必须有第三方书面同意，否则直接排除。
- `允许的测试强度` 必须具体到"禁止什么"，而不是"注意安全"。
- `业务重要性` 用客户的语言（营收、客户量、合规义务），不要用技术术语。

**填写纪律**

- **所有时间戳用同一时区**，并在第一天记下时区。

## 5. 漏洞记录表（Vulnerability Register）

### 5.1 表结构

| 字段 | 说明 | 示例 |
| --- | --- | --- |
| 漏洞编号 | 自定义，建议 `V-001` 递增 | `V-003` |
| 标题 | 一句话说清"在哪、什么问题" | `客户 API /v2/users 存在水平越权` |
| 发现日期 | `YYYY-MM-DD` | `2026-09-15` |
| 发现阶段 | PTES 阶段 | `漏洞分析` |
| 受影响资产 | 对应范围表编号 | `范围表 #2` |
| 受影响端点 | URL / IP:端口 / 组件 | `GET https://api.example.com/v2/users/{id}` |
| 漏洞类型（CWE） | CWE 编号 + 名称 | `CWE-639 Authorization Bypass Through User-Controlled Key` |
| CVE 编号 | 有则填，无则写"不适用" | `不适用（业务逻辑缺陷）` |
| ATT&CK 技术 | 映射到的技术编号 | `T1190 Exploit Public-Facing Application` |
| 利用代码来源 | EDB-ID 或"自研" | `自研 PoC` |
| **CVSS 版本** | 统一版本 | `CVSS v4.0` |
| **CVSS 向量** | 完整向量字符串 | `CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N` |
| **CVSS 基础分** | 由向量算得 | `7.1` |
| **严重度** | None/Low/Medium/High/Critical | `High` |
| 前置条件 | 利用需要什么 | `需任一有效低权限账号` |
| 复现步骤 | 编号步骤，可直接执行 | 见 5.3 |
| 证据 | 截图/输出文件编号 | `EV-003-01` |
| 影响说明 | 业务语言 | `任一注册用户可读取全部其他用户的姓名与手机号` |
| 修复建议 | 可执行 | `在服务端按会话主体校验资源归属，禁止直接信任路径参数 id` |
| 修复优先级 | P0/P1/P2 | `P0` |
| 状态 | 待修复/修复中/已修复待验证/已验证关闭 | `已修复待验证` |
| 复测方法与结果 | | `重放原 PoC，返回 403` |

### 5.2 CVSS 字段填写规范

**CVSS v4.0（当前版本）**——Base 组共 11 个必填指标：

| 组 | 指标 | 缩写 | 取值 |
| --- | --- | --- | --- |
| 可利用性 | Attack Vector 攻击途径 | `AV` | `N` 网络 / `A` 相邻 / `L` 本地 / `P` 物理 |
| 可利用性 | Attack Complexity 攻击复杂度 | `AC` | `L` 低 / `H` 高 |
| 可利用性 | Attack Requirements 攻击前置条件 | `AT` | `N` 无 / `P` 存在 |
| 可利用性 | Privileges Required 所需权限 | `PR` | `N` 无 / `L` 低 / `H` 高 |
| 可利用性 | User Interaction 用户交互 | `UI` | `N` 无 / `P` 被动 / `A` 主动 |
| 受影响系统影响 | Vulnerable System Confidentiality | `VC` | `H` / `L` / `N` |
| 受影响系统影响 | Vulnerable System Integrity | `VI` | `H` / `L` / `N` |
| 受影响系统影响 | Vulnerable System Availability | `VA` | `H` / `L` / `N` |
| 后续系统影响 | Subsequent System Confidentiality | `SC` | `H` / `L` / `N` |
| 后续系统影响 | Subsequent System Integrity | `SI` | `H` / `L` / `N` |
| 后续系统影响 | Subsequent System Availability | `SA` | `H` / `L` / `N` |

向量字符串中 Base 指标必须**按固定顺序**出现：

```
CVSS:4.0/AV:_/AC:_/AT:_/PR:_/UI:_/VC:_/VI:_/VA:_/SC:_/SI:_/SA:_
```

严重度分级（适用于所有 CVSS 计分形式）：

| 等级 | 分数区间 |
| --- | --- |
| None 无 | `0.0` |
| Low 低 | `0.1 – 3.9` |
| Medium 中 | `4.0 – 6.9` |
| High 高 | `7.0 – 8.9` |
| Critical 严重 | `9.0 – 10.0` |

**CVSS v3.1（归档但仍常用）**——Base 组 8 个指标：`AV` / `AC` / `PR` / `UI` / `S`（Scope，范围） / `C` / `I` / `A`。向量格式：`CVSS:3.1/AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:H`。

**填表纪律**

- **一份报告内只用一种 CVSS 版本**，并在方法学章节声明；混用会让分数不可比。
- 标 CVSS **基础分（Base）**时说明是否叠加了威胁指标（Threat）和环境指标（Environmental）。CVSS v4.0 支持 `CVSS-B` / `CVSS-BE` / `CVSS-BT` / `CVSS-BTE` 多种计分形式，写明用的是哪种。
- 客户环境因素（补偿性控制）体现在 Environmental 指标里，并在"影响说明"里用文字解释为什么最终风险等级与基础分不一致。
- 官方计算器：<https://www.first.org/cvss/calculator/4.0>（v3.1 为 <https://www.first.org/cvss/calculator/3.1>）

### 5.3 单条漏洞记录格式（可直接复制）

```
============================================================
V-003  客户 API /v2/users 存在水平越权（IDOR）
============================================================
发现日期   : 2026-09-15
发现阶段   : 漏洞分析（PTES 阶段四）
受影响资产 : 范围表 #2 客户 API
受影响端点 : GET https://api.example.com/v2/users/{id}
弱点分类   : CWE-639 Authorization Bypass Through User-Controlled Key
CVE        : 不适用（业务逻辑缺陷，无对应 CVE）
ATT&CK     : T1190 Exploit Public-Facing Application
利用来源   : 自研 PoC（未使用 Exploit-DB 条目）

风险评级
  CVSS 版本 : v4.0
  向量      : CVSS:4.0/AV:N/AC:L/AT:N/PR:L/UI:N/VC:H/VI:N/VA:N/SC:N/SI:N/SA:N
  基础分    : 7.1
  严重度    : High
  评级说明  : 需持有任一有效低权限账号（PR:L），无需用户交互（UI:N）；
              可读取他人个人信息（VC:H）；不影响数据完整性（VI:N）。
              客户在内网侧部署了 API 网关做速率限制，但不影响本漏洞可利用性，
              故未下调环境分数。

前置条件
  1. 拥有任一有效低权限账号（测试使用客户提供的 pentest01）
  2. 目标账号 id 可枚举

复现步骤
  1. 以 pentest01 登录，取得会话 Cookie：
     curl -s -c jar.txt -X POST https://api.example.com/v2/login \
       -d '{"u":"pentest01","p":"***"}'
  2. 请求自己 uid=1001 的资源，确认返回本人信息：
     curl -s -b jar.txt https://api.example.com/v2/users/1001
  3. 将路径参数改为他人 uid=1002：
     curl -s -b jar.txt https://api.example.com/v2/users/1002
  4. 观察响应：返回 uid=1002 用户的姓名、手机号。
     ⚠️ 本条为只读验证，未修改任何数据，也未批量遍历。

证据
  EV-003-01  步骤 2 的响应截图（本人数据）
  EV-003-02  步骤 3 的响应截图（他人数据，手机号已打码）
  EV-003-03  Burp 请求/响应原始记录

影响说明（业务语言）
  任一注册用户可读取全部其他用户的姓名与手机号。以现有注册量 [N] 估算，
  单次批量遍历即可获取全量用户个人信息，构成个人信息泄露事件，
  可能触发《个人信息保护法》下的告知与报告义务。

修复建议（可执行）
  1. [立即] 在服务端以会话主体为基准校验资源归属，禁止直接信任路径参数 id：
     查询语句必须带 owner_id = session.user_id 条件。
  2. [短期] 为 /v2/users/* 增加服务端访问控制单测，覆盖"跨用户读取"用例。
  3. [长期] 引入统一的资源授权中间件，避免各接口重复实现。

  ❌ 不接受的建议形式："加强权限校验"、"注意越权问题"

修复优先级 : P0（有个人信息泄露风险，且有合规报告义务）
状态       : 已修复待验证
复测方法   : 重放步骤 3，预期返回 403 或 404
复测结果   : [修复后填写]
关闭时间   : [ ]
============================================================
```

## 6. 最终报告结构

```
封面
  报告名称 / 客户名称 / 测试类型 / 测试时间窗 / 报告版本 / 密级 / 编制与审核

修订记录
  版本 / 日期 / 修订人 / 修订内容 / 审批

目录

一、执行摘要（Executive Summary）
    1.1 测试背景与目标
    1.2 测试范围与时间
    1.3 总体结论（2～3 句话，业务语言）
        例："本次测试在授权范围内成功从公网突破至可访问客户个人信息，
             共发现 12 个漏洞，其中 3 个为高危。核心风险集中在 API 层的
             访问控制缺失。"
    1.4 风险概览（按严重度的数量表 + 一张热力图）
    1.5 Top 5 关键风险与建议行动（含责任团队与建议完成时间）
    1.6 与上次测试的对比（如有）

二、方法论（Methodology）
    2.1 遵循的标准与框架
        - 流程：PTES 七阶段
        - 技术分类：NIST SP 800-115
        - 行为建模：MITRE ATT&CK v[版本]
        - 弱点分类：CWE Top 25（[年份]）
        - 风险评级：CVSS v[3.1/4.0]，说明计分形式（CVSS-B / BE / BT / BTE）
    2.2 各阶段实际执行内容与对应时间
    2.3 使用的工具与版本
    2.4 测试限制与假设（见第五节）

三、测试范围（Scope）
    3.1 在范围资产（引用范围表）
    3.2 排除范围资产
    3.3 范围变更记录

四、发现（Findings）
    4.1 发现汇总表（编号 / 标题 / 严重度 / CVSS / CWE / ATT&CK / 状态）
    4.2 按严重度排序的详细发现（每条用 [5.3 单条漏洞记录格式](#53-单条漏洞记录格式可直接复制)）
    4.3 攻击路径还原（从入口到影响的完整链路，附图与时间线）
    4.4 未验证的可疑点（明确标注"未确认"，不要混进正式发现）

五、风险评级标准（Risk Rating）
    5.1 CVSS 版本与指标说明
    5.2 严重度分级表（None / Low / Medium / High / Critical 及分数区间）
    5.3 环境因素如何调整了评级（补偿性控制、业务重要性）
    5.4 优先级定义（P0/P1/P2 的判定规则）

六、修复建议（Recommendations）
    6.1 即时措施（可在数日内完成，降低当前风险）
    6.2 短期措施（数周内，修正设计与实现缺陷）
    6.3 长期措施（制度、流程、架构层面）
    6.4 建议的复核方式与时间点
    6.5 建议纳入安全需求的条目（引用 CWE 编号，便于写入开发规范）

七、附录（Appendix）
    附录 A  漏洞记录表全量
    附录 B  测试时间线（含每日日志摘要）
    附录 C  原始证据清单（截图编号、命令输出）
    附录 D  测试期间对系统的影响记录与清理清单
    附录 E  使用的 Exploit-DB 条目（EDB-ID 与 URL）
    附录 F  术语表（中文（English）对照）
    附录 G  数据销毁确认函
```
