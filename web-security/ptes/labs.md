# PTES 实验：为一个假想目标写完整测试计划与授权书

本实验的目标是**产出一套完整、可交付、能通过现实审查的前期交互文档**。这是 PTES 七阶段里最容易被跳过、却最影响项目成败的一步。

- 前置阅读：[README.md](./README.md)（七阶段） ｜ [templates.md](./templates.md)（模板）
- 产出：一份授权书 + 一份范围表 + 一份测试计划 + 一份 RoE

> 本实验全部使用**虚构目标**。任何情况下，对真实系统实施渗透测试都必须先取得书面授权。

---

## 1. 实验场景

**委托方**：星海医疗器械股份有限公司（虚构）

**背景**：公司自研的"病案管理系统"（Medical Records Management System，MRMS）计划在 2026 年 12 月上线，服务于 12 家三级医院。系统处理患者身份信息、诊断记录与影像索引，属于敏感个人信息。

**要求**：上线前完成一次灰色盒渗透测试，用于（a）上线前风险把关，（b）满足客户医院的采购安全要求。

**已提供的信息**

| 项 | 内容 |
| --- | --- |
| 公网入口 | 门户 `https://portal.xinghai-med.example`；API `https://api.xinghai-med.example/v1` |
| 部署 | 某公有云，华东区；负载均衡 + WAF（云厂商托管） |
| 应用 | 前端 Vue 3 SPA；后端 Spring Boot 微服务 4 个；MySQL 8.0；Redis 6 |
| 身份 | 自建 OAuth2，对接医院侧 LDAP |
| 测试账号 | 三个角色：`doctor`（医生）、`nurse`（护士）、`admin`（院方管理员），均为测试环境账号 |
| 环境 | 有一套独立的测试环境 `https://test-api.xinghai-med.example`，数据为脱敏数据 |
| 约束 | ① 生产环境数据为真实患者数据，**严禁写入与导出**；② 医院侧 LDAP 为第三方系统，未获授权；③ 云厂商 WAF/CDN 基础设施不可测 |
| 上线日期 | 2026-12-01 |

## 2. 任务一：写测试范围表

参照 [templates.md 第 2 节](./templates.md#2-测试范围表附件一) 的表格，为星海医疗填写范围表。**至少 10 行**，必须包含下列信息，并把每一项判定依据写清：

1. 两个公网入口（门户、API）——在范围。
2. 测试环境的同两个入口——在范围，且**优先在测试环境验证**。
3. 医院侧 LDAP 身份源——**不在范围**，写出理由与替代验证方式。
4. 云厂商 WAF 与 CDN 基础设施——**不在范围**，写出理由。
5. 生产 MySQL 主库——判定：不在"直接测试"范围，说明允许的间接验证方式。
6. WAF 封禁策略——说明是否需要提前报备与加白。
7. 三个测试账号——在范围，并标注各角色允许的测试强度。
8. 至少 2 个你自己识别出的、容易遗漏的范围判定项（提示：备份系统、日志平台、运维跳板机、对象存储、第三方短信/支付、企业微信/钉钉通知机器人、CI/CD 流水线）。

**验收标准**

- [ ] 每一行都有 `归属方` 列，非委托方的资产一律标 ❌ 并说明是否已有第三方书面同意
- [ ] 每一行的 `允许的测试强度` 写的是**禁止什么**，不是"注意安全"
- [ ] 至少识别出 2 个容易被漏掉的范围外系统

## 3. 任务二：写授权书

参照 [templates.md 第 1.2 节](./templates.md#12-授权书正文骨架) 的骨架，写一份完整授权书。

**本场景下必须特别处理的 5 个点**

1. **签署人授权**：本次授权应包含"处理敏感个人信息"相关的内容，说明签署人为何有权授权（例如董事会决议编号、法定代表人授权书编号）。
2. **第三方系统声明**：医院侧 LDAP 与云厂商基础设施，必须在"甲方声明与保证"里明确由甲方负责取得同意，或明确排除。**两者不能都不写。**
3. **停手条件**：至少写 4 条，必须包含：
   - 触及授权范围外系统；
   - 发现真实患者数据被访问到（而非脱敏数据）——**这是本场景最重要的停手条件**；
   - 发现系统已被第三方入侵的真实痕迹；
   - 测试动作导致或可能导致医院侧业务中断（医疗系统中断可能危及患者安全）。
4. **数据处理与销毁**：因为涉及敏感个人信息，必须写明：
   - 测试中若意外取到真实患者数据的处置动作（立即停止、不存储、不复制、即时通报、留存证据仅限最小必要）；
   - 数据的加密存储方式与访问控制；
   - 销毁时限（例如项目结束后 15 日内）与书面销毁确认。
5. **责任条款**：明确"甲方保证其有权授权测试"以及"乙方在授权范围内依约行事"的边界。

**验收标准**

- [ ] 15 项必备条款全部出现（对照 [templates.md 1.1](./templates.md#11-必备条款)）
- [ ] 4 条停手条件至少包含上述 4 条
- [ ] 授权书、范围表、RoE 三者的范围描述**逐字一致**
- [ ] 有"第三方系统"的明确处理方式（排除 + 甲方声明两条都要）

## 4. 任务三：写规则约定（RoE）

RoE 是授权书的附件三，比授权书更具体。至少覆盖：

| 条款 | 本场景需要写成什么样 |
| --- | --- |
| 测试窗口 | 具体到日期与时段，例如 `2026-10-08 ～ 2026-11-07`，每日 `09:30–18:00`；**避开医院门诊高峰**（例如 08:00–10:00 禁测） |
| 禁测日期 | 医院方可能有的特殊日期（如集中采购、系统割接、监督检查期） |
| 允许的测试类型 | 手工渗透 ✅、自动化扫描 ✅（限定速率）、社会工程 ❌、DoS/压力测试 ❌、物理入侵 ❌、无线 ❌ |
| 允许的破坏性上限 | 仅允许在**测试环境**写入和修改数据；生产环境**只读** |
| 扫描速率约束 | 明确并发数与每秒请求上限，例如 `≤ 5 req/s`，避免影响业务 |
| 停手条件 | 与授权书一致，另加"WAF 反复封禁导致无法判断是否影响业务时暂停" |
| 即时通报 | 触发条件、通报对象（技术 + 业务 + 法务）、通报时限（例如 30 分钟内电话） |
| 应急联系人 | 双方技术联系人、业务决策人、法务；**含非工作时间联系方式**；并注明"已实际拨通验证" |
| 数据处置 | 取证截图中的患者信息必须打码；不得落地任何真实患者数据 |
| 日志与证据保存 | 保存位置、加密、留存期限 |
| 清理义务 | 测试期间在测试环境创建的全部账号/文件/配置，项目结束前全部清理并出具清单 |
| 变更程序 | 任何范围变更须书面补充协议 |

**验收标准**

- [ ] 有明确的速率上限数字
- [ ] 有 30 分钟内通报的时限要求
- [ ] 应急联系人含非工作时间方式
- [ ] 有"截图打码"和"不得落地真实患者数据"两条

## 5. 任务四：写测试计划

参照 [templates.md 第 3 节](./templates.md#3-测试计划test-plan) 的骨架，为星海医疗写一份完整测试计划。要求：

### 5.1 七个阶段都要有排期

| 阶段 | 起止 | 交付物 | 备注 |
| --- | --- | --- | --- |
| Pre-engagement Interactions | 2026-09-22 ～ 2026-10-07 | 授权书、范围表、RoE、本计划 | 含三方（医院）沟通时间 |
| Intelligence Gathering | 2026-10-08 ～ 2026-10-12 | 资产与服务清单、技术栈清单 | 先被动后主动 |
| Threat Modeling | 2026-10-13 ～ 2026-10-15 | 攻击路径优先级清单（附 ATT&CK 映射） | |
| Vulnerability Analysis | 2026-10-16 ～ 2026-10-27 | 已验证漏洞清单（含证据） | **优先在测试环境** |
| Exploitation | 2026-10-28 ～ 2026-11-02 | 利用记录、时间线 | 生产环境仅只读验证 |
| Post Exploitation | 2026-11-03 ～ 2026-11-05 | 影响范围说明、清理清单 | |
| Reporting | 2026-11-06 ～ 2026-11-13 | 正式报告 | 留出客户复核与原稿反馈时间 |

### 5.2 威胁建模阶段必须做 ATTCK 映射

在威胁建模阶段，用 [MITRE ATT&CK](../mitre-attack/README.md) 做两件事：

1. **选对手**：病案管理系统属于医疗行业，结合你掌握的情报选一个相关的攻击组织（`G` 编号），用 Navigator 的 Threat Groups 选中其全部技术，生成"基线层"。方法见 [ATT&CK 实验 2](../mitre-attack/labs.md#实验-2模拟-apt-的-ttp-覆盖度分析)。
2. **列出本系统最可能的 5 条攻击路径**，每条路径映射到 ATT&CK 技术编号，并注明可借助的技术资源（CWE 与 Exploit-DB）。示例格式：

   | # | 攻击路径 | ATT&CK 技术 | 相关 CWE | 可利用资源 |
   | --- | --- | --- | --- | --- |
   | 1 | 从公网门户的越权接口读取其他医院的患者索引 | T1190 Exploit Public-Facing Application | CWE-639、CWE-862 | 自研 PoC |
   | 2 | 通过文件上传接口落 Web Shell 获得服务器权限 | T1505.003 Web Shell | CWE-434 | 查 Exploit-DB |
   | 3 | 从 API 响应中获取内部服务地址，尝试 SSRF 打通内网 | T1190 | CWE-918 | — |
   | 4 | 利用弱口令登录运维跳板机 | T1078 Valid Accounts | CWE-521 | — |
   | 5 | 通过 CI/CD 流水线配置泄露获得部署凭据 | T1552.004 Unsecured Credentials: Private Keys | CWE-798 | — |

   （表内编号请自己打开 ATT&CK 官网核对定义与所在战术，方法见 [mapping-guide.md](../mitre-attack/mapping-guide.md)。）

### 5.3 风险与应对必须包含

- 测试导致医院侧业务中断 → 应对方式要先写清
- 意外取到真实患者数据 → 应对流程
- WAF 封禁导致测试中断 → 应对
- 三方（医院）不配合导致 LDAP 侧无法验证 → 替代方案

### 5.4 数据管理章节

因为涉及敏感个人信息，本章节必须比一般项目更细：

- 存储位置（本地加密卷 / 客户指定环境）
- 加密方式与密钥管理
- 访问控制（谁能访问）
- 销毁时限（项目结束后 15 日内）
- 销毁确认方式（书面确认函）
- **意外获取真实患者数据的处置流程**

**验收标准**

- [ ] 七阶段都有排期与交付物
- [ ] 威胁建模阶段有 ATT&CK 基线层产出要求
- [ ] 5 条攻击路径都映射到 ATT&CK 编号
- [ ] 风险清单覆盖上述 4 项
- [ ] 数据管理章节有"意外获取真实患者数据"的处置流程

## 6. 任务五：写第一天的每日进度记录

用 [templates.md 第 4 节](./templates.md#4-每日进度记录daily-log) 的格式，虚构 2026-10-08（情报收集第一天）的记录。要求：

**验收标准**

- [ ] 时间戳时区统一
- [ ] "对客户系统的影响"有内容（哪怕只读也要写）
- [ ] "清理记录"写了"无"而不是留空

## 7. 任务六（进阶）：写一条完整漏洞记录

用 [templates.md 5.3 节](./templates.md#53-单条漏洞记录格式可直接复制) 的格式，为下面这个虚构发现写一条完整记录：

> 2026-10-21，在测试环境 `https://test-api.xinghai-med.example/v1/records/{recordId}` 发现水平越权。以 `nurse` 角色账号登录后，将 `recordId` 改为其他医院患者的记录 ID，可成功返回该患者的姓名、性别、出生日期与诊断摘要。共验证 1 条，未批量遍历。仅读取，未修改。

**必须包含**

- [ ] 完整 CVSS v4.0 向量（11 个指标齐全，顺序正确）与基础分
- [ ] CWE 编号（提示：参看 [CWE Top 25](../cwe/README.md) 中与授权相关的条目）
- [ ] ATT&CK 技术编号
- [ ] 前置条件
- [ ] 可执行、可复现的复现步骤（含完整 curl 命令）
- [ ] 影响说明用**业务语言**，并指出合规影响
- [ ] 修复建议可执行（禁止出现"加强权限校验"这类表述）
- [ ] 附证据编号

**自评本题的三个陷阱**

1. 你是否因为"涉及个人信息"就把 `VC` 标成 `H`，但又忘记说明数据量只有 1 条？（CVSS 的 Confidentiality 衡量的是**影响范围**而非数据条数，但报告文字里要说明实际验证范围。）
2. 你是否重复计算了风险——CVSS 分数和风险等级是一回事，不要既给 High 又在正文写"极高危"。
3. 复现步骤里是否出现了真实患者数据？（**不可以**，必须脱敏或用占位符。）

## 10. 常见扣分点与纠正

| 扣分点 | 为什么是问题 | 纠正 |
| --- | --- | --- |
| 范围只写"星海医疗的所有系统" | 边界模糊，测试人员无法判断越界 | 逐条到 IP/URL，并列出排除项 |
| 授权书由项目经理签署 | 可能无授权权限，授权无效 | 要求有授权依据的签署人签署 |
| RoE 写"注意不要影响业务" | 不可执行、不可仲裁 | 写具体数字：速率上限、禁测时段、停手条件 |
| 排除范围只写"第三方系统" | 医院 LDAP 与云基础设施性质不同，得分列 | 逐条列名并说明处置 |
| 应急联系人只有一个人的手机号 | 单点失效 | 至少 3 人（技术/业务/法务）+ 备选 |
| 数据条款只写"保密" | 缺少销毁时限与确认方式 | 补：15 日内销毁 + 书面确认函 |
| 承诺"保证测试不造成任何影响" | 无法保证，反而埋下纠纷 | 改为"尽力避免 + 明确影响记录与通报义务" |
| 测试计划里没有客户复核时间 | 报告发出即结束，客户无反馈机会 | 排期里留出客户看原稿的时间 |
| 日志里"影响"栏留空 | 事后无法举证 | "无影响"也要写"无" |
