# NIST SP 800-115 实验：为内部系统设计一次安全评估方案

本实验的产出是一份**完整的、按 SP 800-115 结构组织的安全评估方案**。它不是"渗透测试计划"的翻版——SP 800-115 覆盖的范围比渗透测试更广（含非侵入性的检查类手法）。

- 前置阅读：[README.md](./README.md) ｜ [800-115.md](./800-115.md)（章节号、表格编号与原文引用均在该页核实过）
- 交叉参考：[PTES 七阶段](../ptes/README.md)、[PTES 交付物模板](../ptes/templates.md)、[ATT&CK 映射指南](../mitre-attack/mapping-guide.md)
- 产出：一份评估方案文档（含完整的第 6.5 节"必答五问"、三类技术覆盖度矩阵、数据处理四环节）

> 本实验的评估对象是**虚构的内部系统**。所有手法描述仅用于方案设计，**不对任何真实系统执行**。

---

## 1. 场景：虚构的内部系统

**组织**：云帆物流有限公司（虚构）

**待评估系统**：**"运单结算平台"（WBP, Waybill Billing Platform）**

| 项 | 内容 |
| --- | --- |
| 系统用途 | 内部员工录入运单、自动计算运费、生成对账单、对接银行代付接口 |
| 用户规模 | 内部员工 480 人（财务 60 人、调度 300 人、管理 120 人）；外部承运商只读查询账号 1,200 个 |
| 部署 | 自建机房（非公有云）；Nginx + Java Spring Boot 3 个微服务 + MySQL 8 + Redis |
| 网络位置 | **仅内网可达**（无公网入口）；员工通过 VPN 或办公网访问 |
| 对接系统 | ① 银行代付接口（第三方，走专线）② 身份源为集团 LDAP（**第三方管理**）③ 短信通知网关（第三方 SaaS） |
| 数据敏感度 | 含员工个人信息、承运商结算金额、银行账号；**不含**客户个人身份信息 |
| 合规要求 | 集团内部《信息系统安全管理办法》要求：核心系统每 12 个月至少一次安全评估；涉及资金系统需额外做渗透测试 |
| 上次评估 | 2024-11，发现 3 个中危问题，已于 2025-01 关闭 |
| 业务约束 | 结算平台在**每月最后 3 个工作日**必须可用（月度结算期），期间**禁止任何可能影响可用性的测试** |

**已知的组织级现状**（这些会影响方案设计）

- 组织**有**《信息系统安全管理办法》，但**没有**专门的安全评估政策（即 SP 800-115 第 6.1 节说的那份政策）——这是方案要指出并建议补齐的。
- 组织**有**变更管理流程与配置基线文档。
- 组织**有**集中日志平台（保留 90 天），但**从未**做过日志审查。
- 团队**没有**专职安全人员，安全评估外包给第三方。

## 2. 任务一：补齐"评估政策"这一层（第 6.1 节）

SP 800-115 第 6.1 节要求组织先有**信息安全评估政策**。云帆物流目前没有，而它的《信息系统安全管理办法》是更高层的制度。**任务**：写出这份评估政策的最小内容。

按官方要求的五项要素填写：

| 要素 | 云帆物流应该怎么写 |
| --- | --- |
| 组织要求（合规来源） | 集团《信息系统安全管理办法》第 X 条：核心系统每 12 个月至少评估一次；涉及资金系统额外做渗透测试； |
| 角色与职责（至少含批准与执行） | 信息中心主任 = 批准人；安全主管 = 评估管理人；外部第三方 = 执行人；系统负责人 = 配合人 |
| 遵循既定方法学 | 明确写"采用 NIST SP 800-115 的分阶段方法学（Planning / Execution / Post-Execution）"，并保留可替换为其他方法学的条款 |
| 评估频率 | 核心系统 ≤ 12 个月一次；涉及资金系统 ≤ 12 个月一次渗透测试；**重大变更后追加一次**； |
| 文档要求 | 评估计划、评估结果、整改台账三类文档的模板、归档位置与保留期限 |

**官方额外要求，别漏**

- [ ] 政策经批准后**分发给** CIO / CISO / CTO 层面的人员
- [ ] 领导层把政策**传达给将执行评估的第三方**
- [ ] 政策**至少每年审查一次**，并在出现新的评估相关要求时审查

**追问（必须回答）**：云帆物流既然把评估外包，为什么还需要自己的评估政策？
参考思路：**政策是"要求"，外包是"执行"。** 没有政策，外包方就没有明确的验收标准；出事时组织也无法证明自己履行了合规义务。官方在第 6.1 节明确要求组织"为评估提供方向与指导"，这项职责不能外包。

### 问题 4：敏感数据应如何处理？（第 7.4 节四环节）

**这是本场景最需要细致处理的环节**——结算平台含员工个人信息与银行账号。

```
4.1 数据收集（Data Collection）
    - 范围：仅采集证明漏洞存在所需的最小数据
    - 银行账号：**不得采集**；截图时若出现必须打码
    - 员工个人信息：不得批量导出；验证越权时最多验证 1 条并立即停止
    - 抓包：仅在必要时抓，且**必须符合法务部门提出的要求**（第 6.6 节）
      → 抓包文件不得包含认证凭据明文；如包含，须即时脱敏

4.2 数据存储（Data Storage）
    - 位置：乙方加密工作卷（非评估人员个人电脑的普通目录）
    - 加密：静态加密 + 评估人员各自口令访问
    - 访问控制：仅本项目的三名评估人员
    - 留存期限：项目结束后 15 日内销毁（见 4.4）

4.3 数据传输（Data Transmission）
    - 回传通道：仅经加密通道（VPN / SFTP）
    - 禁止经第三方网络明文传输
    - 禁止通过个人邮箱、IM、公有云盘传输任何数据

4.4 数据销毁（Data Destruction）
    - 时限：项目验收后 15 个工作日内
    - 方式：安全删除（不可恢复）+ 确认清理所有副本与备份
    - 确认：出具书面的《数据销毁确认函》交信息中心归档

4.5 意外获取真实敏感数据的处置（本场景必写）
    若意外取到真实员工个人信息或银行账号：
      (a) 立即停止该测试动作，不再扩大采集范围
      (b) 不得复制、不得保存、不得外传
      (c) 30 分钟内电话通报信息中心技术对接人
      (d) 仅在报告中以"已验证存在越权访问"的方式描述，不附实际数据
      (e) 已落在磁盘上的临时文件，在信息中心见证下当场删除并留痕
```

**自查**：
- [ ] 四个环节（收集/存储/传输/销毁）全部有内容
- [ ] 明确写出"抓包须符合法务要求"（第 6.6 节要求）
- [ ] 有"意外取到敏感数据"的处置流程，且含时限与动作
- [ ] 有书面的销毁确认方式

### 任务四：为"发现"阶段的 Review 类格子填具体手法

SP 800-115 第 3 章给出六种审查手法。针对云帆物流的现状（**有配置基线文档、有集中日志但从未做过日志审查、有变更管理流程**），逐项判断做不做、怎么做：

| 第 3 章的手法 | 做不做 | 怎么做 | 为什么 |
| --- | --- | --- | --- |
| Documentation Review 文档审查 | ✅ 做 | 对照配置基线文档逐项核对实际配置；核对变更记录与架构图是否一致 | 组织有基线文档，做这个性价比最高 |
| Log Review 日志审查 | ✅ **重点做** | 用集中日志平台的 90 天留存数据，检查攻击面相关的关键事件（登录失败、权限变更、异常访问）；对照 [ATT&CK](../mitre-attack/README.md) 的 Discovery / Credential Access 战术找检测缺口 | **从未做过，是最大的空白**；这也是 Review 类里最容易被忽略但价值很高的一项 |
| Ruleset Review 规则集审查 | ✅ 做 | 审查网络边界规则、VPN 访问控制列表、数据库账号权限 | 内网系统的横向风险主要靠这些规则约束 |
| System Configuration Review 系统配置审查 | ✅ 做 | 按配置基线逐项核查应用服务器、数据库、Redis、跳板机 | 组织已有基线，核查成本低 |
| Network Sniffing 网络嗅探 | ⚠️ 谨慎 | 仅在测试环境或经批准的镜像口执行 | **官方提醒**：嗅探需要接到 hub/TAP/SPAN 端口，**某些情况下需重新配置网络设备，可能中断业务** → 与"结算期禁测"约束冲突，须逐案批准 |
| File Integrity Checking 文件完整性检查 | ➕ 建议做 | 在评估起止各做一次基线比对，识别期间被变更的关键文件 | 可从另一个角度发现"未知的变更"，也能发现遗留的攻击工具 |

**注意**：这张表里的每一项都是 **Examination（检查）类**手法。官方在第 2.3 节说明：**检查通常对目标环境中的实际系统或网络没有影响**，除非需要访问文档、日志或规则集。**所以在"结算期"这类可用性敏感的窗口里，Review 类手法仍然可以做**——这是一个非常实用的裁剪结论，值得写进方案。

## 5. 任务五：设计"分批执行"的裁剪方案

云帆物流的约束是：**系统无公网入口 + 结算期禁测 + 团队无专职安全人员 + 只有 4 周窗口**。

SP 800-115 没有直接教你怎么裁剪，但给了两块依据：**Examination vs Testing 的影响差异**（第 2.3 节）与 **Testing Viewpoints**（第 2.4 节）。请据此设计分批方案：

```
批次 1（影响最小，可在任何时段执行）
  手法：全部 Review 类（第 3 章六种中的五项，Network Sniffing 除外）+ 应用安全审查
  依据：Examination 通常对目标系统无影响（第 2.3 节）
  产出：配置偏差清单、日志检测缺口清单、规则集问题清单
  → 这一步做完，往往已经能给出报告中大部分"加固类"建议

批次 2（轻量测试，避开业务高峰）
  手法：端口与服务识别、漏洞扫描、口令强度抽样
  约束：速率 ≤ 20 req/s；限 11:00-17:00；结算期全时段禁测
  依据：第 5.2.1 节——扫描只查"漏洞是否存在"，不利用
  产出：候选漏洞清单（**此时全部是"疑似"，不能进正式发现**）

批次 3（侵入性验证，需逐项获批）
  手法：渗透测试（含权限提升、横向移动）、应用安全测试
  约束：只读验证优先；写操作仅在测试环境；触及停手条件立即停止
  依据：第 5.2.1 节——攻击阶段"利用漏洞来确认其存在"
  产出：已验证漏洞清单 + 证据

批次 4（报告与整改）
  手法：Post-Testing Activities（第 8 章）
  产出：报告（描述漏洞 + 风险评级 + 缓解指导）、整改台账、
        数据销毁确认函、评估账号禁用/删除记录
```

**必须回答的三个裁剪问题**

1. **如果只有 2 周而不是 4 周，砍哪一批？**
   参考思路：优先保批次 1（Review 类），因为影响最小、性价比最高，且能覆盖最多的加固类问题；批次 3 若必须砍，则报告里**必须**明确"未执行目标漏洞验证，发现均为疑似"，不能把扫描结果直接当结论。
2. **批次 1 里为什么把 Network Sniffing 排除？**
   参考思路：官方脚注 5 明确其可能影响网络（需连接 hub/TAP/SPAN，有时需改网络设备配置）；在"结算期禁测 + 可用性敏感"的约束下，风险收益比不划算。
3. **三类技术里有哪一类在本次方案中覆盖度最低？为什么？**
   参考思路：**非技术手法覆盖度为零**（物理安全测试、人工资产识别都不在范围）。这不是疏漏，而是本系统无公网入口、且范围限定在信息系统层；但**必须在报告的限制章节声明**，否则客户会误以为物理层面的风险也被评估过了。

## 6. 任务六：写报告的差异说明

SP 800-115 第 8 章对报告的要求比 PTES 简（描述漏洞、风险评级、缓解指导）。但本方案要面对一个现实：**云帆物流没有专门的安全评估政策**。

**任务**：写出报告中必须包含的"限制与说明"章节（对应 [PTES 报告结构](../ptes/templates.md#6-最终报告结构) 的第五节）。

至少覆盖：

```
一、方法与依据
    本次评估采用 NIST SP 800-115 的分阶段方法学（Planning / Execution / Post-Execution）。
    技术手法覆盖 Review / Target Identification and Analysis / Target Vulnerability Validation 三类。

二、未覆盖的范围（逐条说明原因）
    1. 非技术手法：物理安全测试、人工资产识别**未纳入**本方案（第 2.2 节明确此类内容不在 SP 800-115 范围内）
    2. 外部视角：目标系统无公网入口，未执行 External 视角测试
    3. 第三方系统：银行代付接口、集团 LDAP、短信网关均在授权范围外，未做任何测试
    4. 基础设施层：承载虚机的宿主机与存储设备未纳入本轮
    5. 未执行 Network Sniffing（原因：与结算期可用性约束冲突）

三、评估的固有限制
    1. 评估只提供某一时间点的安全快照（第 6.2 节官方表述），不代表持续状态
    2. 团队无专职安全人员，配合与响应能力有限，可能影响部分场景的测试深度
    3. 报告未列出的问题不代表不存在

四、组织层面的建议（超出本次技术评估范围，但必须提出）
    1. 建议制定信息安全评估政策（第 6.1 节五项要素），明确批准人、执行人、频率与文档要求
    2. 建议建立评估频率的书面依据（当前依赖集团办法的第 X 条，缺少技术性排期依据）
    3. 建议为评估人员建立独立的临时账号管理流程（第 6.4.2 节）
    4. 建议补齐日志审查的常态化机制（本次是首次审查）

五、数据处理确认
    1. 采集的数据类型与量级
    2. 存储位置与加密方式
    3. 已执行的销毁动作（附《数据销毁确认函》）
    4. 评估专用账号的禁用/删除记录
```

**为什么要写"四、组织层面的建议"？**
参考思路：SP 800-115 第 6.1 节要求组织有评估政策、第 6.2 节要求有排期依据、第 6.4.2 节要求有账号管理。这些是**组织能力**而非**技术漏洞**，但恰恰是"团队无专职安全人员、评估全靠外包"的组织最容易缺失的。把它们写进报告，是从"交一份漏洞清单"升级为"交一份可持续的评估能力建设建议"。

## 8. 总验收清单

**按 SP 800-115 的官方结构逐项核对**

- [ ] 任务一：评估政策覆盖了第 6.1 节的**五项要素**（组织要求、角色职责、方法学、频率、文档要求）
- [ ] 任务一：写了"政策需分发、需传达给第三方、至少每年审查"三条额外要求
- [ ] 任务二问题 1：范围**到了 IP 粒度**，且逐条列出了排除的第三方系统
- [ ] 任务二问题 1：明确了测试视角（External/Internal、Overt/Covert），并解释了某视角不做的原因
- [ ] 任务二问题 2：每个评估人员有**独立账号**，且写明结束后禁用/删除
- [ ] 任务二问题 2：明确了物理访问级别（无限制/陪同）
- [ ] 任务二问题 2：做了技能基线自评（对照 Table 3-2 / 4-2 / 5-2）
- [ ] 任务二问题 3：说明了评估位置的**权衡**（场内便利 vs 无法从对手视角评估）
- [ ] 任务二问题 3：有明确的扫描速率上限数字
- [ ] 任务二问题 4：**四个环节**（收集/存储/传输/销毁）全部有内容
- [ ] 任务二问题 4：写明"抓包须符合法务要求"
- [ ] 任务二问题 4：有"意外取到敏感数据"的处置流程，含**时限**
- [ ] 任务二问题 5：停手条件 ≥ 4 条，含"第三方系统"与"敏感数据"两条
- [ ] 任务二问题 5：通报有**时限**，且有非工作时间联系方式**并已拨通验证**
- [ ] 任务三：覆盖度矩阵的每一行都有内容，或对空项给出了原因
- [ ] 任务四：Review 类六项手法都有"做/不做 + 怎么做 + 为什么"
- [ ] 任务四：识别出"Examination 通常不影响系统，所以结算期也能做 Review 类"这一裁剪结论
- [ ] 任务五：四个批次划分合理，且回答了三个裁剪问题
- [ ] 任务五：识别出"非技术手法覆盖度为零"这一事实
- [ ] 任务六：限制章节覆盖了未覆盖范围、固有限制、组织层面建议、数据处理确认
- [ ] 全文：没有任何一处把**未验证的扫描结果**当成正式发现

**如果以上任何一项没做到**，回到 [800-115.md](./800-115.md) 对应章节重读——本实验的每一项要求都对应了该专篇中的官方内容。

## 9. 进阶：做一次跨标准的对齐

本实验的方案只用了 SP 800-115。现实中一份好的方案往往要**同时对齐多套标准**。做以下对齐练习：

| 本方案中的内容 | 对齐到哪套标准的哪个部分 |
| --- | --- |
| "三类技术覆盖度矩阵" | [OWASP / WSTG](../owasp/README.md)：Web 应用层面的测试项是否覆盖了 Review / Identification / Validation 三类？ |
| "Discovery 阶段的候选目标排序" | [MITRE ATT&CK](../mitre-attack/README.md)：把候选目标与攻击路径映射到技术编号，做优先级排序 |
| "报告的发现分类" | [CWE](../cwe/README.md)：把每个发现归到一个 CWE 编号，同类合并成一条修复项 |
| "攻击阶段使用的 exploit" | [Exploit-DB](../exploit-db/README.md)：记录 EDB-ID 与 URL，说明做了哪些修改 |
| "整改建议的补丁类条目" | [NIST SP 800-40 Rev. 4](./README.md#34-sp-800-40-rev-4--guide-to-enterprise-patch-management-planning-preventive-maintenance-for-technology)：按"识别—排优先级—获取—安装—验证"五步写，并给出排序依据 |
| "发现到控制项的映射" | [NIST SP 800-53 Rev. 5](./README.md#32-sp-800-53-rev-5--security-and-privacy-controls-for-information-systems-and-organizations)：把发现映射到控制族编号 |
| "报告的风险评级" | CVSS（见 [PTES 模板的 CVSS 填写规范](../ptes/templates.md#52-cvss-字段填写规范)） |
| "测试后的事件响应建议" | [NIST SP 800-61 Rev. 3](./README.md#33-sp-800-61-rev-3--incident-response-recommendations-and-considerations-for-cybersecurity-risk-management) |

**练习**：从云帆物流的评估范围里任选 3 个系统，为每个系统列出"至少 3 个必须检查的 Web 应用测试项"，并说明每个测试项属于三类技术中的哪一类、对应哪一类 CWE。
