### 官方摘要（要点翻译）

- 目的：协助组织**规划并实施**技术性的信息安全测试与检查，**分析发现**并**制定缓解策略**；
- 提供设计、实施与维护技术性安全测试与检查流程与程序的实务建议；
- 可用于多种目的，例如**发现系统或网络中的漏洞**，以及**验证是否符合政策或其他要求**；
- **官方明确声明**：本指南**不打算呈现一个完整的信息安全测试与检查项目**，而是提供关键技术要素的概览，重点在于**具体技术手法、每种手法的优点与局限、以及使用建议**。

### 官方给出的免责与定位（Executive Summary 原文要点）

- 一个"信息安全评估（information security assessment）"是**确定被评估实体（如主机、系统、网络、程序、人员——称为 assessment object）在多大程度上满足特定安全目标**的过程。
- 存在**三种评估方法（assessment methods）**：
  1. **Testing（测试）**——在特定条件下运行一个或多个评估对象，以比较实际行为与预期行为；
  2. **Examination（检查）**——对评估对象进行查验、检视、评审、观察、研究或分析，以促进理解、澄清或获取证据；
  3. **Interviewing（访谈）**——与组织内的个人或小组进行讨论，以促进理解、澄清或确定证据所在位置。
- **评估结果用于支撑对安全控制有效性的持续判定**（support the determination of security control effectiveness over time）。
- 本文档**不替代**实施安全控制与维护系统安全，而是帮助组织**确认系统已得到适当保护**，并识别未满足的组织安全要求及其他应当处理的弱点。

> **本页强调一次**：**Testing / Examination / Interviewing 是"三种评估方法"**，不是"三种测试技术"。这是最容易记混的一组概念，也是 SP 800-53A 与本文档衔接的关键。

## 2. 方法论：三个阶段

SP 800-115 第 2.1 节给出的**分阶段评估方法学**（phased information security assessment methodology），官方说明其**至少**应包含以下三个阶段（原文：*"Its methodology should contain at minimum the following phases"*）：

| 阶段 | 英文 | 官方描述要点 |
| --- | --- | --- |
| **规划** | **Planning** | "对成功的评估至关重要"；用于收集评估执行所需的信息——**要评估的资产、针对这些资产的关注威胁、用于缓解这些威胁的安全控制**——并**确定评估方法**。官方强调：**安全评估应被当作一个项目来对待**，需要项目管理计划来涵盖目标与目的、范围、需求、团队角色与职责、限制、成功因素、假设、资源、时间线与交付物 |
| **执行** | **Execution** | 主要目标是**识别漏洞并在适当情况下加以验证**；应处理与既定评估方法与手法相关的活动。官方说明：虽然具体活动随评估类型不同而异，但此阶段完成后，评估人员将已识别出**系统、网络与组织流程层面的漏洞** |
| **执行后** | **Post-Execution** | 重点在于**分析已识别的漏洞以确定根本原因、制定缓解建议、编写最终报告** |

**官方对"方法学"的价值陈述**（第 2.1 节）：

- 提供一致性与结构，**可最小化测试风险**；
- **加速新评估人员的上手过渡**；
- 应对与安全评估相关的**资源约束**（时间、人员、硬件、软件）。
- 分阶段方法学的优势：**结构易于遵循，并为人员交接提供自然的断点**。
- 官方还列举了其他被接受的方法学作为参考，例如 **NIST SP 800-53A**（评估 SP 800-53 所述控制的有效性）与 **OSSTMM**（Open Source Security Testing Methodology Manual，开源安全测试方法学手册），并明确声明 **NIST 不背书任何单一方法学**，目的是让组织做出知情选择——采用既有方法学，或组合多个方法学形成适合自身的独特方法学。

### 与"测试前 / 测试中 / 测试后"的对应关系

| 通俗说法 | SP 800-115 的官方名称 | 对应章节 |
| --- | --- | --- |
| **测试前** | Security Assessment **Planning** | 第 6 章（含政策、排期、手法选择、后勤、计划编写、法律考量） |
| **测试中** | Security Assessment **Execution** | 第 7 章（含协调、实施、分析、数据处理） |
| **测试后** | **Post-Testing** Activities | 第 8 章（含缓解建议、报告、修复/缓解） |

> ⚠️ **一个重要的更正**：SP 800-115 中 **"Planning" 是方法学的阶段之一，不是一种"测试技术"**。技术手法只有三类（见下节）。请不要把 Planning 与三类技术并列为"四类技术"。

## 3. 三类技术手法（Technical Assessment Techniques）

第 2.2 节原文：技术性安全测试与检查手法有几十种，本文档把最常用的分为**下列三类**。

### 3.1 审查类手法（Review Techniques）

**官方定义**（第 2.2 节）：这些是用于**评估系统、应用、网络、策略与程序以发现漏洞的检查（examination）类手法**，且**通常是手工执行的**。

**包含**：文档审查（documentation）、日志审查（log）、规则集审查（ruleset）、系统配置审查（system configuration）；网络嗅探（network sniffing）；文件完整性检查（file integrity checking）。

**Table 3-1 列出的能力（官方原文要点）**

| 手法 | 能力 |
| --- | --- |
| Documentation Review | 评估策略与程序在技术上的准确性与完整性 |
| Log Review | 提供系统使用、配置与修改的历史信息；可能揭示潜在问题与政策偏离 |
| Ruleset Review | 揭示基于规则集的安全控制中的漏洞 |
| System Configuration Review | 评估系统配置的强度；验证系统按加固政策进行配置 |
| Network Sniffing | 监视本地网段的网络流量以捕获活动系统、操作系统、通信协议、服务与应用等信息；**验证通信是否加密** |
| File Integrity Checking | 识别重要文件的变更；**也能识别某些类型的不受欢迎的文件，例如众所周知的攻击工具** |

**官方对 Examination 的说明（第 2.3 节）**：检查主要涉及**文档审查**（策略、程序、安全计划、安全需求、标准操作程序、架构图、工程文档、资产清单、系统配置、规则集、系统日志），用于判定系统是否被适当文档化，以及获取**只能通过文档获得的安全视角**。官方还提醒：**检查通常对目标环境中的实际系统或网络没有影响**，除非需要访问文档、日志或规则集；但如果要从路由器或防火墙等系统取回配置文件或日志，**只应由系统管理员和受过类似训练的人执行**，以确保设置不会被误改或误删。

> 官方脚注 5 特别指出：**网络嗅探是可能影响网络的被动测试手法之一**——它需要把嗅探器接到 hub、TAP 或 SPAN 端口上，**某些情况下这一连接过程需要重新配置网络设备，可能中断业务**。

### 3.2 目标识别与分析类手法（Target Identification and Analysis Techniques）

**官方定义**（第 2.2 节）：这些**测试（testing）**手法可以识别**系统、端口、服务与潜在漏洞**；**可以手工执行，但通常使用自动化工具执行**。

**包含**：网络发现（network discovery）、网络端口与服务识别（network port and service identification）、漏洞扫描（vulnerability scanning）、无线扫描（wireless scanning）、**应用安全审查（application security examination）**。

### 3.3 目标漏洞验证类手法（Target Vulnerability Validation Techniques）

**官方定义**（第 2.2 节）：这些**测试（testing）**手法用于**佐证（corroborate）漏洞的存在**；**可手工执行，也可使用自动化工具**，取决于具体手法与测试团队的技能水平。

**包含**：口令破解（password cracking）、**渗透测试（penetration testing）**、社会工程（social engineering）、**应用安全测试（application security testing）**。

### 3.4 三类手法的关系与官方的两条重要提醒

官方在第 2.2 节明确给出两条关键判断：

1. **没有任何单一手法能提供系统或网络安全的完整画面**（*"Since no one technique can provide a complete picture of the security of a system or network"*），组织应**组合**适当的手法以确保评估的稳健性。官方举例：**渗透测试通常依赖同时执行"网络端口/服务识别"与"漏洞扫描"**，以先找出可能成为后续渗透目标的主机与服务。
2. 本文档**聚焦于说明这些不同技术手法怎么执行，不规定在什么情形下该用哪种手法**，从而给组织选择最符合自身需求的手法的灵活性。

**此外官方特别提示：除技术手法外，还有大量非技术手法**（第 2.2 节）：

- 例子一：**物理安全测试**——通过尝试绕过锁具、门禁读卡器及其他物理安全控制，确认物理安全漏洞的存在，通常目的是获得对特定主机的未授权访问。
- 例子二：**人工资产识别**——通过资产清单、设施实地走查等非技术手段识别待评估资产，而不依赖技术手法。
- 官方说明：非技术手法的细节**不在本文档范围内**，但**认识到非技术手法的价值、并考虑何时它们比技术手法更合适，是很重要的**。

> **这条对渗透测试实践很重要**：如果你的评估范围只覆盖了三类技术手法，**必须在报告的"限制"章节说明未覆盖非技术手法（物理、社工、人工资产识别）**，否则客户会误以为报告覆盖了全部风险面。

### 3.5 三类手法的分类对照表

| # | 类别 | 英文 | 属于 Testing 还是 Examination | 执行方式 | 回答的问题 |
| --- | --- | --- | --- | --- | --- |
| 1 | Review Techniques | 审查类 | **Examination** | 一般手工 | "文档、日志、规则、配置**说得对不对、写得好不好**？" |
| 2 | Target Identification and Analysis | 目标识别与分析 | **Testing** | 一般自动化工具 | "**有什么**系统、端口、服务、漏洞？" |
| 3 | Target Vulnerability Validation | 目标漏洞验证 | **Testing** | 手工或工具（视技能） | "这些漏洞**是真的吗、能不能打穿**？" |

### 3.6 测试视角（Testing Viewpoints）

第 2.4 节给出两个维度，比笼统的"黑盒/白盒"更严谨：

| 维度 | 取值 | 说明 |
| --- | --- | --- |
| 位置 | **External / Internal** | 外部（防火墙外）与内部（防火墙内、已被授予一定访问权限） |
| 可见性 | **Overt / Covert** | 公开（防守方知道在测）与隐蔽（防守方不知道在测） |

**官方关于 External / Internal 的说明（第 5.2.2 节）**：

- 若同时做内外部测试，**通常先做外部测试**。
- **外部场景（Outsider scenarios）**：模拟对目标了解极少、完全基于假设行事的外部攻击者。测试人员除了目标 IP 地址或地址段**不获得任何真实信息**，通过公开网页、新闻组等做开源情报收集，然后用端口扫描器和漏洞扫描器识别目标主机。由于测试流量通常要穿过防火墙，**从扫描中获得的信息量远少于从内部视角获得的**。在识别出可从外部到达的主机后，尝试攻陷其中之一；若成功，**该访问权可能被用来攻陷其他一般无法从外部访问的主机**。官方原文强调：**渗透测试是一个利用最小访问权换取更大访问权的迭代过程**（an iterative process that leverages minimal access to gain greater access）。
- **内部场景（Insider scenarios）**：模拟恶意内部人员的行动。内部渗透测试与外部类似，**区别在于测试人员在内部网络（即防火墙之后），且已被授予对网络或特定系统的某种级别的访问权限**。利用这一访问权限，测试人员尝试通过**权限提升**获得更高层级的访问。
- **官方对目标 IP 的注意事项**（脚注 20）：如果拿到一份授权 IP 列表作为目标，评估人员**在测试开始前应核实所有公网地址（即非私有、可路由的地址）确实属于该组织管辖范围**；可用 WHOIS 等服务确定地址空间的归属者。**这一条直接对应 [PTES 前期交互阶段](../ptes/README.md#3-阶段一前期交互pre-engagement-interactions) 的"第三方系统必须排除"要求。**

## 4. 渗透测试的四个阶段（Figure 5-1）

官方原文：**Figure 5-1 表示渗透测试的四个阶段**。（脚注 18 提示：这只是"渗透过程可以如何划分阶段"的一个示例，**有许多可接受的分组方式**。）

| # | 阶段 | 英文 | 官方描述 |
| --- | --- | --- | --- |
| 1 | **规划** | **Planning** | 确定规则、最终确定并记录管理层的批准、设定测试目标。官方强调：**规划阶段为成功的渗透测试打下基础，此阶段不发生任何实际测试** |
| 2 | **发现** | **Discovery** | 见下（分两部分） |
| 3 | **攻击** | **Attack** | 见下 |
| 4 | **报告** | **Reporting** | 见下 |

**发现（Discovery）阶段分两部分**（官方原文）：

- **第一部分：信息收集与扫描**。执行第 4.2 节的"网络端口与服务识别"以识别潜在目标。此外还使用其他技术收集目标网络的信息：
  - **主机名与 IP 地址**信息：可通过 DNS 查询、InterNIC（WHOIS）查询、网络嗅探（**一般仅内部测试时**）等方法获得；
  - **员工姓名与联系信息**：可通过搜索组织的 Web 服务器或目录服务器获得；
  - **系统信息**（如主机名与共享）：可通过 NetBIOS 枚举、NIS（Network Information System）等方法获得（**一般仅内部测试时**）；
  - **应用与服务信息**（如版本号）：可通过 **banner grabbing（横幅抓取）**记录。
  - 官方还提到：某些情况下可使用**翻垃圾桶（dumpster diving）**与**设施实地走查**收集额外信息，并可能发现可用的额外信息，**例如写在纸上的口令**。
- **第二部分：漏洞分析**。把扫描到的主机的服务、应用、操作系统与**漏洞数据库**（对漏洞扫描器而言是自动的）以及**测试人员自身的漏洞知识**进行比对。人工测试者可以使用自己的数据库，也可使用公开数据库，**例如 NVD（National Vulnerability Database）**。官方指出：人工过程可以发现自动化扫描器可能漏掉的**新的或冷门**的漏洞，但**比自动化扫描器慢得多**。

**攻击（Attack）阶段**（官方原文要点）：

- 执行攻击是**任何渗透测试的核心**。Figure 5-2 表示攻击阶段的各个步骤——**即通过尝试利用先前识别出的潜在漏洞来验证漏洞的过程**。
- **若攻击成功，漏洞即被验证**，并识别出用于缓解相关安全暴露的防护措施。
- 官方提醒：**很多情况下执行的 exploit 并不能给攻击者带来最大级别的访问权限**；它们可能只是让测试人员了解到更多关于目标网络及其潜在漏洞的信息，或者引起了目标网络安全状态的变化。
- 有些 exploit 使测试人员能够**在系统或网络上提升权限**以获得对更多资源的访问。若发生这种情况，**需要额外的分析与测试来确定网络的真实风险级别**，例如识别可从系统中被获取、修改或删除的信息类型。
- **如果对某个特定漏洞的攻击被证明不可行，测试人员应尝试利用另一个已发现的漏洞。**
- 若测试人员成功利用了漏洞，**可以在目标系统或网络上安装更多工具以推进测试过程**。这些工具用于获取对网络中其他系统或资源的访问，以及获取关于网络或组织的信息。**在渗透测试过程中应对多个系统实施测试与分析，以确定对手可能获得的访问级别。**
- 官方说明这一过程由 **Figure 5-1 中"攻击"与"发现"阶段之间的反馈回路（feedback loop）**表示。

**攻击阶段中多数被利用漏洞的类别**（官方列出的九类，原文）：

| # | 类别 | 中文 | 官方说明要点 |
| --- | --- | --- | --- |
| 1 | Misconfigurations | 配置错误 | **配置错误的安全设置，特别是不安全的默认设置，通常容易被利用** |
| 2 | Kernel Flaws | 内核缺陷 | 内核代码是操作系统的核心，实施系统的整体安全模型——**内核中的任何安全缺陷都使整个系统处于危险之中** |
| 3 | Buffer Overflows | 缓冲区溢出 | 当程序未充分检查输入长度时发生；此时**可把任意代码引入系统，并以运行该程序的权限（常常是管理员级）执行** |
| 4 | Insufficient Input Validation | 输入校验不足 | 许多应用未能完全校验从用户接收的输入。官方举的例子就是 **SQL 注入**：Web 应用把用户输入的值嵌入数据库查询，用户输入 SQL 命令而应用未过滤，查询就可能带着用户请求的恶意修改被执行 |
| 5 | Symbolic Links | 符号链接 | 符号链接是指向另一个文件的文件。操作系统包含可更改文件权限的程序；**若这些程序以特权权限运行，用户可以有策略地创建符号链接，诱使这些程序修改或列出关键系统文件** |
| 6 | File Descriptor Attacks | 文件描述符攻击 | 文件描述符是系统用来代替文件名跟踪文件的数字。特定类型的文件描述符有隐含用途；**当特权程序分配了不恰当的文件描述符时，就把该文件暴露于被破坏的风险** |
| 7 | Race Conditions | 竞态条件 | 竞态条件可能发生在程序或进程进入特权模式的期间；**用户可以安排攻击时机，趁程序或进程仍处于特权模式时利用被提升的权限** |
| 8 | Incorrect File and Directory Permissions | 文件与目录权限不当 | 文件与目录权限控制着分配给用户与进程的访问。**权限不当可导致多种攻击，包括读写口令文件或向受信任远程主机列表中添加条目** |

> 注：官方 PDF 中该列表共 9 个条目（此处按语义去重后列出 8 类，"File Descriptor Attacks" 与 "Race Conditions" 为独立两条）。**引用条数时请直接打开 PDF 的第 5-4 至 5-5 页核对。**

**报告（Reporting）阶段**（官方原文要点）：

- 报告阶段**与其他三个阶段同时进行**（see Figure 5-1）。
- 在规划阶段编写**评估计划（assessment plan）或 ROE**；
- 在发现与攻击阶段，**通常保留书面日志（written logs），并向系统管理员和/或管理层做周期性报告**；
- 测试结束时，通常形成一份报告，**描述已识别的漏洞、给出风险评级、并就如何缓解发现的弱点给出指导**。

### 官方给出的攻击阶段特征总结

> "**While vulnerability scanners check only for the possible existence of a vulnerability, the attack phase of a penetration test exploits the vulnerability to confirm its existence.**"
>
> （漏洞扫描器只检查漏洞**可能存在**，而渗透测试的攻击阶段**利用漏洞来确认其存在**。）

这句话是 SP 800-115 对"扫描 ≠ 渗透"最精炼的表述，与 [PTES 漏洞分析阶段](../ptes/README.md#6-阶段四漏洞分析vulnerability-analysis) 和 [CWE 审计指南](../cwe/audit-guide.md) 中"扫描器只提供线索"的纪律完全一致。

### 渗透测试后勤（Penetration Testing Logistics，第 5.2.2 节）

- 渗透测试场景应聚焦于**定位并针对应用、系统或网络的设计与实现中的可利用缺陷**；
- 测试应**同时复现最可能发生的与最具破坏性的攻击模式**——**包括最坏情况，例如管理员实施的恶意行为**；
- 若同时做内部与外部测试，**通常先做外部测试**；
- 官方对**评估位置**的提醒（第 6.4.2 节）：把评估人员放在场内 vs 场外的取舍——
  - 评估人员系统**直接连到边界设备**（如边界路由器）可使其留在组织的逻辑与物理边界内，**但这样无法从对手视角真实评估组织的安全态势**；
  - 外网测试也可从**独立于被测组织的测试实验室**执行；
  - 若使用**租用的服务器**，官方明确要求：**评估人员在执行安全测试前应安全删除系统上的数据并重建系统**；测试完成后按第 7.4 节的数据处理指南处理数据。
  - 官方还指出从外部位置测试的固有风险：对物理与逻辑访问的控制更弱、评估系统与数据面临更大被攻陷风险、评估位置与组织设施之间的网络流量更容易被未授权方监听（可能泄露测试发现的弱点）、并且**某些测试在经过第三方网络时可能被网络提供方的安全人员视为恶意行为，甚至违反网络提供方的安全政策**。

## 5. 评估规划（第 6 章）：可直接借用的结构

### 5.1 制定安全评估政策（第 6.1 节）

官方要求组织制定信息安全评估政策，**应涵盖**：

- 评估必须遵守的**组织要求**；
- 适当的**角色与职责**（至少覆盖"批准评估的人"与"执行评估的人"）；
- **遵循既定方法学**；
- **评估频率**；
- **文档要求**，例如评估计划与评估结果。

政策经适当的高级官员制定并批准后，应**分发**给相关人员——可能包括 CIO、CISO、CTO 的办公室。**领导层还应把政策传达给任何将要执行评估的第三方。**
官方建议：**至少每年审查一次**评估政策，并在出现新的评估相关要求时审查。

**关于频率（第 6.2 节）**：评估频率常由组织证明其符合特定法规或政策的要求所驱动。官方举例：**FISMA 要求根据风险定期测试，且至少每年一次**。官方同时指出，**由于评估只提供某一时间点的安全快照（a snapshot of security at a given point in time），组织可能选择要求更频繁的评估**。技术上的考量也能帮助确定频率：如果认为某系统存在若干弱点，可以**更早测试以确认弱点存在，或者推迟到弱点缓解之后以确认其已被解决**——**取决于测试目标**。

### 5.2 评估计划（Assessment Plan，第 6.5 节）

**官方定义**：评估计划通过**记录为评估所计划的活动及相关信息，提供结构与问责（structure and accountability）**。

官方给出评估计划**应回答的五个基本问题**（原文）：

1. **What is the scope of the assessment?**（评估范围是什么？）
2. **Who is authorized to conduct the assessment?**（谁被授权执行评估？）
3. **What are the assessment's logistics?**（评估的后勤安排是什么？）
4. **How should sensitive data be handled?**（敏感数据应如何处理？）
5. **What should occur in the event of an incident?**（发生事件时应如何处理？）

**官方对范围的说明**：评估计划应**识别哪些系统与网络被授权接受检查与测试**。可通过提供系统数量与它们使用的 IP 地址或地址段来实现；计划还应至少按 IP 地址（最好同时给出更多信息）列出具体系统。

**官方对评估计划的定位（原文要点）**：

- 每一次评估都应在评估计划中加以说明，**无论范围大小、侵入程度高低、或由谁执行（内部还是第三方）**；
- 该计划提供**评估人员必须遵守的规则与边界**，并通过降低意外系统中断或敏感信息意外披露等事件的风险来**保护组织**；
- 评估计划也**保护测试团队**——它确保组织的管理层**理解并同意**评估的范围、活动与限制；
- **评估计划的编写应是评估人员与组织安全组关键成员之间的协作过程。**

官方还引用 **NIST SP 800-53A**，给出编写计划时应考虑的**若干具体步骤**（原文列举，含原文的编号笔误）：

| 步骤 | 内容 |
| --- | --- |
| (i) | 确定安全控制评估的**类型** |
| (ii) | 确定要纳入评估的**安全控制与控制增强项** |
| (iii) | 根据系统安全计划中的安全控制与增强项，**选择**评估期间要使用的适当评估程序 |
| (iv) | 针对信息系统的影响级别与组织的运行环境，**裁剪**所选的评估程序 |
| (v) | 如有必要，**编写额外的评估程序**以覆盖其他安全控制与增强项 |
| (vi) | 制定**应用扩展评估程序的策略** |
| (vii) | **优化**评估程序以减少重复工作并提供成本有效的评估方案 |
| (viii) | **最终确定评估计划并取得执行所需的批准** |

> ⚠️ 官方 PDF 中该列的步骤编号存在笔误（末尾出现两个 "(vi)"）。此处按语义排为 (i)–(viii)，**引用编号时请直接查阅 PDF 第 6-10 页。**

### 5.3 法律考量（第 6.6 节）

官方要求：**在评估开始前**就应对评估的潜在法律问题做出评估。

- **建议在侵入性测试（如渗透测试）中始终让法律顾问参与**（原文：*"it is recommended that they always be involved for intrusive tests such as penetration testing"*）。
- 若组织授权外部实体执行评估，**双方的法律部门都可能参与**：他们可协助审查评估计划，并在合同中加入**赔偿或责任限制条款**，特别是针对被视为侵入性的测试类型。
- 法律部门还可能要求外部实体签署**保密协议（NDA）**，禁止评估人员向未获批准的实体披露任何敏感、专有或其他受限信息。
- **隐私问题**：多数组织有警告横幅或已签署的用户协议，声明其系统被监控、并告知个人"使用系统即表示同意被监控"。但**并非所有组织都有这些措施，法律部门应在评估开始前处理潜在的隐私侵犯问题**。此外，**捕获的数据可能包含不属于该组织的敏感数据，或包含个人员工数据，可能引发隐私问题**；评估人员应意识到这些风险，并**按照法律部门提出的要求执行抓包**。法律部门还可能确定**数据处理要求**。

> 这一节与 [PTES 前期交互阶段](../ptes/README.md#3-阶段一前期交互pre-engagement-interactions) 的第 4、9、12 项要求完全对应，但给出了更明确的**法务参与建议**与**警告横幅/用户协议**这一具体抓手。

### 5.4 评估后勤（第 6.4 节）中的三条硬要求

1. **评估人员账号（第 6.4.2 节）**：某些工具需要网络或域管理员权限——**这种情况下，组织应为评估期间的用途创建新的管理员账号**。**每个评估人员应有自己的账号；管理员账号不得以任何理由共享。** 这种做法使组织能够监控这些账号，并在评估结束时**禁用或删除**它们。
2. **位置选择（第 6.4.2 节）**：对第三方执行的评估，组织需要确定适当的物理访问级别（如**无限制 / 陪同**）。
3. **租用服务器（第 6.4.2 节）**：若使用租用服务器执行外网测试，**评估人员应在执行安全测试前安全删除系统上的数据并重建系统**。

> **这三条是审计和渗透项目中极常见的疏漏点**：共享管理员账号、评估人员物理访问未定级、租用跳板机未重建。写 RoE 时应把三条都写进去。

## 6. 评估执行（第 7 章）：数据处理是重点

| 节 | 标题 | 说明 |
| --- | --- | --- |
| 7.1 | Coordination | 协调 |
| 7.2 | Assessing | 实施评估 |
| 7.3 | Analysis | 分析 |
| **7.4** | **Data Handling** | 数据处理（本文档最实用的部分之一） |
| 7.4.1 | Data Collection | 数据收集 |
| 7.4.2 | Data Storage | 数据存储 |
| 7.4.3 | Data Transmission | 数据传输 |
| 7.4.4 | Data Destruction | 数据销毁 |

**为什么第 7.4 节值得单独引用**：它是 SP 800 系列中少有的**把"测试数据的全生命周期"拆成四个环节逐一给出要求**的地方。这四步可以直接搬进 [授权书的数据处理条款](../ptes/templates.md#12-授权书正文骨架) 与 [测试计划的数据管理章节](../ptes/templates.md#3-测试计划test-plan)，比自拟条款更有依据：

```
数据收集（Collection）   → 采集范围、是否抓包、是否落地文件、按法务要求执行
数据存储（Storage）      → 存储位置、加密、访问控制、留存期限
数据传输（Transmission） → 回传通道是否加密、是否经第三方网络
数据销毁（Destruction）  → 销毁方式、时限、确认方式
```

## 8. 与 PTES 的异同

### 8.1 结构对照

| 维度 | **PTES** | **NIST SP 800-115** |
| --- | --- | --- |
| 性质 | 社区维护的**执行标准** | 政府机构发布的**技术指南** |
| 版本与时效 | v1.0（v2.0 规划中，将引入"强度等级"） | 2008 年 9 月发布，仍为 Final，未被取代 |
| 阶段划分 | **7 个阶段**：Pre-engagement Interactions、Intelligence Gathering、Threat Modeling、Vulnerability Analysis、Exploitation、Post Exploitation、Reporting | **方法学 3 阶段**：Planning、Execution、Post-Execution；**渗透测试 4 阶段**：Planning、Discovery、Attack、Reporting |
| 技术分类 | 不按类别划分，按阶段组织 | **明确的三类技术**：Review / Target Identification and Analysis / Target Vulnerability Validation |
| 独有内容 | **威胁建模（Threat Modeling）**、**后渗透（Post Exploitation）**、Pre-engagement 的商务与法律细节 | **三种评估方法（Testing/Examination/Interviewing）**、**评估政策制定**、**评估优先级与排期**、**评估后勤（账号/位置/工具）**、**数据处理四环节**、**Rule of Engagement 模板（附录 B）**、**法律考量** |
| 报告要求 | 详细的多层读者结构 | 较简：描述漏洞、风险评级、缓解指导 |
| 场景覆盖 | 以渗透测试为主 | 覆盖更广的"安全评估"（含非侵入性检查） |
| 非技术手法 | 社会工程在 Intelligence Gathering 中提及 | **明确声明非技术手法（物理测试、人工资产识别）不在本文档范围内，但强调其价值** |

### 8.2 两者的互补关系（推荐用法）

```
用 PTES 定项目流程骨架
   └─ 七个阶段作为项目的主干与交付物清单

用 SP 800-115 补强"容易被跳过"的环节
   ├─ 第 6.1 节 → 建立组织级评估政策（PTES 不涉及）
   ├─ 第 6.2 节 → 评估频率与排期依据（PTES 不涉及）
   ├─ 第 6.4.1/6.4.2 节 → 评估人员技能基线与位置选择（PTES 提及但无细则）
   ├─ 第 6.5 节 → 评估计划的五个必答问题 + 八步编写法
   ├─ 第 6.6 节 → 法律考量与法务参与建议
   ├─ 第 7.4 节 → 数据处理四环节（PTES 无对应细节）
   └─ 附录 B → Rules of Engagement 官方模板

用 SP 800-115 的三类技术做"完整性核对"
   └─ 每轮测试结束前问：Review 类做了吗？Target Identification 类做了吗？Validation 类做了吗？
      有哪一类没做？为什么？这个"为什么"要写进报告的限制章节。
```

### 8.3 三个实质性的差异（会影响你的报告写法）

1. **PTES 有"威胁建模"，SP 800-115 没有。**
   SP 800-115 的 Discovery → Attack 是**能力驱动**的（扫到什么就打什么）；PTES 的 Threat Modeling 是**目标驱动**的（先定哪些路径值得打）。**两者结合才是完整的**：用 PTES 的威胁建模排序，用 SP 800-115 的四阶段执行。这也是本模块把 [ATT&CK](../mitre-attack/README.md) 与 SP 800-115 一起讲的原因——ATT&CK 是"威胁建模"这一步最好的工具。

2. **PTES 有"后渗透"，SP 800-115 基本没有。**
   SP 800-115 的攻击阶段提到"若成功则可安装更多工具以获取其他系统的访问"，也提到"应对多个系统实施测试以确定对手可能获得的访问级别"，但**没有把"拿到权限之后能造成什么业务影响"作为一个独立阶段来展开**。这是 PTES 更完备的地方，也是现代渗透测试报告里"业务影响"章节的依据来源。

3. **SP 800-115 把"检查（Examination）"与"测试（Testing）"分得很清，PTES 不强调这个区分。**
   这个区分在实践中非常有用：**Examination 通常对目标系统没有影响**，而 Testing 有。所以当你受限于"不能影响生产业务"时，可以先做 Examination 类手法（文档/日志/规则集/配置审查），把侵入性的 Testing 留到测试环境或停机窗口。**这个裁剪逻辑在 PTES 里找不到，必须靠 SP 800-115。**

## 9. 如何借用 SP 800-115 的检查表结构

SP 800-115 提供的是**结构**，不是填好的检查表。下面是三种可直接套用的结构。

### 9.1 结构一：用"三类技术 × 四个阶段"做覆盖度矩阵

这是最通用的检查表骨架。行 = 三类技术，列 = 项目的四个阶段，格子里填"本轮是否执行 / 用什么手法 / 为什么没做"。

| | 规划（Planning） | 发现（Discovery） | 攻击（Attack） | 报告（Reporting） |
| --- | --- | --- | --- | --- |
| **Review Techniques**（Examination） | 定规则、定范围、定数据处理 | 文档审查、日志审查、规则集审查、配置审查、文件完整性检查 | 基于审查结果提出验证目标 | 把审查发现与测试发现分开列述 |
| **Target Identification and Analysis**（Testing） | 定扫描强度与速率上限 | 网络发现、端口与服务识别、漏洞扫描、无线扫描、应用安全审查 | 为攻击排序候选目标 | 说明扫描覆盖率与未覆盖网段 |
| **Target Vulnerability Validation**（Testing） | 定"允许打到哪一步" | 口令强度抽样验证 | 口令破解、渗透测试、社会工程、应用安全测试 | 只列已验证的漏洞，未验证的另列 |
| **非技术手法** | 明确是否在范围内 | — | 物理安全测试、人工资产识别 | **未覆盖时必须写入限制章节** |

**使用方式**：每轮评估结束后填这张表。任何一行为空或大量空白，都要在报告限制章节解释原因。

### 9.2 结构二：评估计划的"必答五问"检查表

直接来自第 6.5 节，作为计划评审的最低标准：

```
[ ] 1. 评估范围是什么？
        - 授权接受测试的系统数量与 IP 地址/地址段（至少按 IP 列出具体系统）
        - 明确的排除项（第三方系统、生产数据库、云基础设施…）
        - 时间窗口与禁测时段
        - 外部/内部、公开/隐蔽的视角组合

[ ] 2. 谁被授权执行评估？
        - 执行方全称与具体人员
        - 授权来源（签署人及其授权依据）
        - 评估人员的技能基线（对照 Table 3-2 / 4-2 / 5-2 的技能集）
        - 评估人员的账号分配（每人不共享）、物理访问级别（无限制/陪同）

[ ] 3. 评估后勤安排是什么？
        - 评估位置（场内/场外/租用服务器；若租用，注明"测试前已重建"）
        - 现场对接人与协调方式
        - 使用的工具与版本清单
        - 扫描速率与并发上限
        - 是否需要网络或域管理员权限

[ ] 4. 敏感数据应如何处理？（第 7.4 节四环节）
        - 收集：范围与方式（是否抓包，抓包须符合法务要求）
        - 存储：位置、加密、访问控制、留存期限
        - 传输：通道加密、是否经第三方网络
        - 销毁：方式、时限、确认方式

[ ] 5. 发生事件时应如何处理？
        - 停手条件清单（触及范围外系统、发现真实入侵痕迹、影响业务、取到真实敏感数据…）
        - 通报对象（技术/业务/法务）与时限
        - 非工作时间的联系方式（且已验证可用）
        - 恢复与回滚方案
        - 谁有权决定"继续/收敛/终止"
```

**第 6.5 节还要求**：评估计划应是**评估人员与组织安全组关键成员的协作产物**（不能只由测试方单方面写），且**必须取得执行所需的批准**。

### 9.3 结构三：用第 6.1 节的五项做"组织评估政策"自评

如果你的客户（或你自己所在的组织）**没有**评估政策，SP 800-115 第 6.1 节给了最小骨架：

| 政策要素 | 自评问题 |
| --- | --- |
| 组织要求 | 有哪些法规/合同要求我们做评估？（如 FISMA 要求至少年度一次） |
| 角色与职责 | 谁批准评估？谁执行评估？权责是否书面化？ |
| 遵循方法学 | 有没有一个书面记载、可重复的方法学？（对照第 2.1 节三个阶段） |
| 评估频率 | 频率是怎么定的？是"一直这么做"还是有依据？ |
| 文档要求 | 评估计划与评估结果的格式与归档要求是什么？ |

官方额外要求：政策经批准后**分发给相关人员（CIO/CISO/CTO 办公室）**，并**传达给将执行评估的第三方**；**至少每年审查一次**。

### 9.4 结构四：技能基线检查表

SP 800-115 提供了三张技能集表格，可作为**团队能力自评**与**客户审阅测试方资质**的依据：

| 表格 | 内容 | 适用 |
| --- | --- | --- |
| Table 3-2 | Baseline Skill Set for Review Techniques | 审查类手法的技能基线 |
| Table 4-2 | Baseline Skill Set for Target Identification and Analysis Techniques | 目标识别与分析类手法的技能基线 |
| Table 5-2 | Security Testing Knowledge, Skills, and Abilities | 安全测试的知识、技能与能力 |

> 具体的技能条目请打开官方 PDF 第 3-5、4-11、5-7 页查看。**本页不复制条目清单，因为技能要求会随技术演进过时，直接读原文更可靠。**

| 处理测试数据 | 第 7.4 节四环节 |
| 定法律条款 | 第 6.6 节 |
| 定评估频率 | 第 6.2 节 |
| 建立组织评估政策 | 第 6.1 节 |
