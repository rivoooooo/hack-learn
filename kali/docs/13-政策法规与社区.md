## 核心知识

### Kali 的六条「设计政策」（它们决定了你看到的行为）

**① User Policy（用户权限策略）**

Kali 用两种方式提权：

- **`pkexec`**：GUI 与 CLI 都能用（涉及桌面环境时）；
- **`sudo`**：CLI。

官方特别提醒：**部分工具在无超级用户权限时行为会不同**。官方举的例子就是 **nmap**：

> 「默认情况下，Nmap 执行 SYN 扫描；但如果用户没有发送原始包的合适权限（Unix 上需要 root），它会改用 connect 扫描。」

- **SYN 扫描（`-sS`）**：root 的默认，发一个 SYN 包即可，快，但需要特殊能力（root）。
- **Connect 扫描（`-sT`）**：非 root 的默认，要走完整三次握手，**更慢、包更多**。

如果想恢复 Kali 旧的（全 root）行为：

```bash
sudo apt update
sudo apt install -y kali-grant-root
```

> 该策略自 **Kali 2020.1** 起生效。

**② Penetration Testing Tools Policy（工具收录政策）**

Kali 团队用下列问题判断一个工具该不该进 Kali（官方原文）：

- 这个工具在渗透测试环境中**有用/可用**吗？
- 它与其他已有工具**功能重叠**吗？
- 它的**许可证允许自由再分发**吗？
- 它需要**多少资源**？能在「标准」环境里跑吗？

**关键条款**：**专门针对 DoS、DDoS 或匿名的工具「很少用于合法授权项目」，因此默认不安装**。

新工具请求要走 <https://bugs.kali.org/>，且官方明确要求：**不要只发一行字的请求**，要把理由讲清楚。

**③ Network Service Policy（网络服务策略）——最容易被误解的一条**

Kali 是渗透测试工具集，可能被用在「敌对」环境里，所以它**对网络服务的处理和普通发行版非常不同**：

> **Kali 默认不启用任何对外监听的服务**，目标是把默认状态下的暴露面降到最低。

具体机制：

- **默认禁止服务跨重启持久化**。例如安装 `apt-cacher-ng` 时，会看到：

  ```text
  update-rc.d: We have no instructions for the apt-cacher-ng init script.
  update-rc.d: It looks like a network service, we disable it.
  ```

- **要覆盖默认策略**，显式启用：

  ```bash
  sudo systemctl enable apt-cacher-ng
  ```

- **白名单/黑名单在 `/usr/sbin/update-rc.d` 文件末尾的 `__DATA__` 段**里：

  ```bash
  tail -95 /usr/sbin/update-rc.d | more
  ```

  ```text
  __DATA__
  #
  # List of blocklisted init scripts
  #
  apache2 disabled
  avahi-daemon disabled
  bluetooth disabled
  cups disabled
  dictd disabled
  ssh disabled
  [...]

  #
  # List of allowlisted init scripts
  #
  acpid enabled
  acpi-fakekey enabled
  acpi-support enabled
  alsa-utils enabled
  anacron enabled
  [...]
  ```

  **含义**：`ssh`、`apache2`、`cups`、`bluetooth` 等**默认都是禁用的**——你装完 SSH 服务不会自动开机启动，**这是设计，不是 bug**。

**④ Open Source Policy（开源政策）**

- Kali 是**聚合了数千个自由软件包的发行版**。
- 作为 Debian 派生版，**主区（main）所有核心软件都符合 Debian 自由软件指南（DFSG）**。
- **例外**：`non-free` 区里有一些**非开源工具**，是 OffSec 通过与厂商签订的默认或专项许可协议获得再分发权的。
- **如果你要做 Kali 的衍生版**：必须**逐个检查 Kali 特有的 non-free 包的许可证**；但**从 Debian 导入的 non-free 包可以安全再分发**。
- **Kali 自己的基础设施与集成工作在 GNU GPL v3 下**（<https://www.kali.org/docs/LICENSE>）。
- 查某个包的许可：源码包里看 `debian/copyright`；已安装的包看 `/usr/share/doc/<包名>/copyright`。

**⑤ Kali 与 Debian 的关系**

- Kali **基于 Debian Testing**。
- **绝大多数 Kali 包是从 Debian 仓库原样导入的**。
- 少数情况下会从 **Debian Unstable 或 Experimental** 摘取更新版本（为了更好的体验或关键 bug 修复）。
- **fork 的包**保持在最低限度：优先推动上游集成该特性，或在上游加上必要的 hooks，从而不必长期改上游代码。每个 fork 的包在 <https://gitlab.com/kalilinux> 有一个 Git 仓库，带 `debian` 分支，因此更新 fork 只需在其 master 分支里 `git merge debian`。
- **额外包**：大量渗透测试/安全审计领域的包。多数符合 DFSG。**Kali 有意把这些包回馈给 Debian，并直接在 Debian 里维护它们**，为此 Kali 的打包**尽量符合 Debian Policy 并遵循 Debian 的最佳实践**。

**⑥ Update Policies（更新/安全更新政策）**

- **绝大多数包**（即原样导入的那一批）**安全更新的到达时间与 Debian 主发行版基本相同**。
- 其他包由 Kali 开发团队**尽力而为（best-effort）**地支持。

### ⚠️ 法律边界：未经授权测试他人系统的后果

> **免责声明**：以下内容是面向中文读者的**一般性风险提示，不构成法律意见**。具体条文号、构成要件与量刑以**现行法律及司法解释**为准。做任何测试前请咨询专业法律人士并取得**书面授权**。

**技术能力强 ≠ 有权去做。** Kali 官方本身把这些工具定位为**渗透测试**用途，而渗透测试在业界的基本前提就是**授权**：有合同、有范围（scope）、有时间窗、有联系人。

**为什么 Kali 会默认关掉所有网络服务？** 官方给的理由是「可能被用在敌对环境中」——这是**降低被滥用时的默认暴露面**，而不是许可证意义上的授权。

**中国的相关规定（方向性表述）**：

- **《中华人民共和国刑法》**中与计算机犯罪相关的条款（常被引用的如第 **285** 条、第 **286** 条）覆盖**非法侵入计算机信息系统**、**非法获取计算机信息系统数据**、**非法控制计算机信息系统**、**破坏计算机信息系统**等行为。**具体条文号与司法解释请以现行文本为准**。
- **《中华人民共和国网络安全法》**确立网络运营者与使用者的安全义务，并对相关违法行为规定了行政处罚。
- **《中华人民共和国数据安全法》**与**《中华人民共和国个人信息保护法》**对数据的收集、处理、跨境传输与个人信息处理设定了义务。渗透测试中若接触到个人信息，可能同时触发这些义务。

**常见认知误区（必须避免）**：

| 误区 | 现实 |
|------|------|
| 「我只是扫了一下端口，没造成损失」 | 未授权扫描本身在多个司法辖区就可能构成违法/侵权，**不要求实际损失** |
| 「我用的是自己的云主机」 | 云主机有公网 IP，**扫描的是别人的系统**就一样违法；云商还会记录全部流量 |
| 「目标是公开的网站，随便测」 | 公开可访问 ≠ 授权测试 |
| 「我已经拿到授权」 | 授权**有范围**：域名/IP 段、时间窗、允许的技术手段。**超出范围的部分仍然违法** |
| 「我改一下 MAC/IP 就查不到我」 | 网络取证依赖日志、时间线、流量特征、账号与支付记录，**隐匿手段不是免责手段** |

**境外的相关规定（方向性表述）**：美国有 **CFAA（Computer Fraud and Abuse Act）**，英国有 **Computer Misuse Act**，欧盟有 **NIS2 / GDPR** 等。各国对「未授权访问」的界定与处罚差异很大，跨境测试**风险叠加**。

**合规的最小操作清单**：

1. **书面授权书 / SOW（Statement of Work）**，明确范围、时间、手段、免责与紧急联系人；
2. **只测授权范围内的目标**，逐条对照 IP / 域名清单；
3. **隔离测试环境**优先：自建靶场、CTF、本地 VM；
4. **数据最小化**：碰到真实个人信息立即停止并报告，不复制、不外传；
5. **测试前通知**（如适用）IT/安全/法务，避免触发误判的应急响应；
6. **保留证据链**：授权文件、测试时间线、操作日志；
7. **不要**在云主机上对互联网做扫描/爆破，见 [09-WSL与云环境](09-WSL与云环境.md)。

**小结（一句话）**：**Kali 里有很多工具，但没有一个工具自带授权。** 授权来自目标所有者的书面同意，而不是来自工具的易得性。

### 商标政策（做教程、写博客、做视频要注意）

- **`Linux®`** 是注册商标，通过 **Linux Foundation** 的再许可使用（Linus Torvalds 是全球权利人，Linux Foundation 是独占被许可方）。
- **Kali Linux 与 OffSec** 要推广自家商标的认知度，但前提是**避免公众误以为在与你打交道而实际上不是**——这在「可信的渗透测试发行版」领域尤其重要。
- **不要修改商标**：举例包括**缩写名称、给商标加 logo、把商标与其他词组合**。官方建议**完全按官方形式使用**，样式资源在 press-pack：
  - <https://gitlab.com/kalilinux/documentation/press-pack/-/tree/main/Kali>
  - <https://gitlab.com/kalilinux/documentation/press-pack/-/tree/main/Kali_NetHunter>
  - <https://gitlab.com/kalilinux/documentation/press-pack/-/tree/main/Kali_NetHunter_Pro>
- **首次提及时要带符号**：注册商标用 `®`，未注册商标用 `™`；**不确定时用 `™`**。
- **要与周围文字区分**（大写、斜体、加粗或下划线）。
- **要加归属声明**，例如：`KALI LINUX ™ is a trademark of OffSec.`（可放正文、脚注或尾注）。
- **❌ 禁止把 OffSec 商标用在域名里**（会造成用户混淆）。
- **周边**：可以做 T 恤、壁纸等**只给自己和朋友**（不收任何有价值回报的人）；**任何商业化用途（无论是否盈利）都必须事先获得书面许可**。
- 超出政策范围的用法，**必须获得 OffSec 的书面许可**。

### EULA / 隐私 / Cookie

- **EULA**：Kali 的最终用户许可协议正文是一个独立文件：<https://www.kali.org/docs/policy/eula/EULA.txt>。
- **Privacy Policy**：只在**你自愿提交**时收集可识别个人信息（姓名、地址、邮箱等），且**只用于完成你的具体请求**（除非你另行授权，例如加入邮件列表）。站点可能使用 Cookie/追踪技术（浏览器类型、操作系统、访客数、使用方式），**个人信息本身不能通过 Cookie 收集**，但**如果你此前提供过个人信息，Cookie 可能与之关联**；**聚合的 Cookie 与追踪信息可能与第三方共享**。
- **信息分发**：可能向**政府机构**或协助**反欺诈/调查**的公司共享，条件是①法律允许或要求；②防范实际或潜在欺诈与未授权交易；③调查已发生的欺诈。**不会为营销目的提供给这些公司**。
- **数据安全**：可识别个人信息保存在安全环境中，只有授权员工可访问；所有邮件与简报**允许退订**。
- **Cookie Policy**：区分第一方/第三方 Cookie、持久/会话 Cookie，并说明如何管理 Cookie。

## 关键文档精读

### Kali Linux User Policy

- **解决什么问题**：为什么 Kali 里 `sudo` 和 `pkexec` 并存，以及非 root 下工具为什么「变慢/变弱」。
- **操作步骤**：
  ```bash
  # 恢复旧的「全 root」行为（可选）
  sudo apt update
  sudo apt install -y kali-grant-root
  ```
- **验证方式**：
  ```bash
  id                              # 看自己是否在 sudo 组
  nmap -v <目标> | grep -i scan   # 非 root 下应是 connect 扫描
  sudo nmap -sS <目标>            # 显式用 root 拿 SYN 扫描
  ```
- **坑**：`kali-grant-root` 会**削弱权限隔离**，等于回到旧模型。官方链接把它标为「旧 root 策略」。

### Penetration Testing Tools Policy

- **解决什么问题**：理解「为什么 Kali 里没有某类工具」，以及如何申请收录。
- **要点**：四大判断标准 + **DoS/DDoS/匿名类工具默认不装**。
- **操作步骤**：新工具请求走 <https://bugs.kali.org/>，写清楚理由（**一行字的请求会被无视**）。
- **坑**：「默认不装」不等于「完全没有」——有些可以在仓库里找到，但**这不改变使用它们的法律风险**。

### Kali Linux Network Service Policy

- **解决什么问题**：装完服务为什么不自启。
- **操作步骤**：
  ```bash
  tail -95 /usr/sbin/update-rc.d | more     # 看黑/白名单
  sudo systemctl enable <服务>               # 显式覆盖默认禁止策略
  ```
- **验证方式**：
  ```bash
  systemctl is-enabled ssh
  ss -tlnp                                   # 看有没有对外监听
  ```
- **坑**：**这是安全设计**。把它当 bug 去「修」（比如批量 `systemctl enable` 所有服务）会把机器暴露在敌对网络上。

### Kali's Relationship With Debian

- **解决什么问题**：搞清楚 Kali 包的来龙去脉（打包必读，见 [12-开发与打包](12-开发与打包.md)）。
- **验证方式**：
  ```bash
  apt policy <包名>       # 看包来自 kali-rolling 还是 Debian
  ```
- **坑**：写文档/做衍生版时，**别把 Kali 描述成「完全独立于 Debian 的发行版」**——官方明确说是 Debian Testing 的派生。

### Kali Linux Trademark Policy

- **解决什么问题**：写教程、做视频、印周边时的合规用法。
- **要点**：见上文。**核心是「不要造成混淆」**。
- **坑**：**别把 "Kali" 放进产品/服务域名**；商业用途必须书面授权。

### Where and How to Contribute to Kali

- **解决什么问题**：想给 Kali 做贡献，从哪下手。
- **五大官方社区平台（官方原文列举顺序）**：
  1. **GitLab** <https://gitlab.com/kalilinux> —— 所有包、docs、tools、build-scripts 都在这。知道要改什么就发 **merge request**；不知道就发 **issue**。
  2. **论坛** <https://forums.kali.org/> —— 求助、分享工具、反馈。官方强调的优点是**永久可检索**（不像 Discord 里的信息容易丢）。
  3. **Discord** <https://discord.kali.org/> —— 实时聊天（**不是官方支持服务器**，但常有人帮忙）。
  4. **IRC** —— OFTC 上的 `#kali-linux`，见下。
  5. **Bug Tracker** <https://bugs.kali.org/> —— 报 bug 或帮人修 bug。
- **文档贡献**：所有 Kali 文档**用 Markdown 写成且开源**。
  - `kali-docs`：<https://gitlab.com/kalilinux/documentation/kali-docs>（语法、命令改进，甚至新页面）
  - `kali-tools`：<https://gitlab.com/kalilinux/documentation/kali-tools>
- **技术贡献路径**：
  - **Kali Packages**：打包是核心。绝大多数工具用 **Python、C/C++、Perl、Ruby、Go 或 Rust** 写。
  - **上游包更新**：处理 <https://pkg.kali.org/derivative/kali-roll/#newer_version> 里「有更新上游版本」的包；不会打包的话可以**报 bug**。
  - **打包新工具**：有现成的待办列表（bug tracker 的 `Queued Tool Addition` 分类）。
  - **Autopkgtests（debci）**：给包写运行时测试。
- **用硬件帮忙**：
  - **QA 测试**：团队会在 Discord/论坛上征召特定设备测试（留意通知）。
  - **托管镜像**：见 <https://www.kali.org/docs/community/setting-up-a-kali-linux-mirror/>。
  - **移植到新平台**：ARM 走 [kali-arm](https://gitlab.com/kalilinux/build-scripts/kali-arm)，云走 [kali-cloud](https://gitlab.com/kalilinux/build-scripts/kali-cloud)，VM 走 [kali-vm](https://gitlab.com/kalilinux/build-scripts/kali-vm)，NetHunter 走 <https://gitlab.com/kalilinux/nethunter/build-scripts>。
  - **做种 Kali torrent**：保留 `.torrent` 文件并保持连接，帮忙上传；可用 <https://www.kali.org/torrents.xml>（RSS）自动化。
- **社交与评价**：关注官方社交账号；在**你确实使用过的**第三方平台留评价。

### Submitting Bugs for Kali Linux

- **解决什么问题**：写一份**能被复现**的 bug 报告。
- **核心心态（官方原文要点）**：Kali 是「出于热爱」的项目，开发者是**有本职工作的志愿者**。目标是**让开发者能亲自复现失败**。
- **提交语言**：**官方明确说最好用英文提交**。
- **操作步骤**：

  **① 先浏览，无需账号**
  > 「任何人都可以不登录阅读已有报告。」从主页用 **View Issues**（或直接访问 `bugs.kali.org/view_all_bug_page.php`）按分类/状态/关键字筛选。

  **② 确认不是重复报告**
  - **非硬件问题**：**不要**重复提交，**也不要**发「Me Too」「+1」这类无新信息的评论。
  - **硬件问题**：**即使看起来相似也要提交新报告**——你的硬件很可能与别人不完全相同。**别因为型号相同就假设问题是同一个**。

  **③ 注册账号**：点 **Signup for new account**，填用户名、邮箱、过 CAPTCHA，**点邮件里的链接激活**。

  **④ 创建报告**：登录后点 **Report Issue**。
  **必填字段**：`Category`、`Summary`、`Description`。
  **强烈建议填写**：`Reproducibility`、`Select Profile`、`Steps to Reproduce`、`Additional Information`、`Upload File`（错误日志/截图）。

  **分类一共 8 个（官方列举）**：`Feature Requests`、`General Bug`、`Kali Package Bug`、`Kali Package Improvement`、`Kali Websites & Docs`、`New Tool Requests`、`Queued Tool Addition`、`Tool Upgrade`。
  > ⚠️ **不要在 bug tracker 里寻求支持或提问**——支持渠道是 Docs、论坛、IRC。

  **Summary 要好**：
  - 好：`Chromium Package installed from repo will not run as root user`
  - 差：`Chromium doesn't work`

  **Description 要包含（官方清单）**：
  - 错误信息的**完整原文**（屏幕输出或日志）
  - **你确切输入了什么 / 做了什么操作**
  - 如果你有**修复方案、绕过方法或补丁**，一并给出
  - 出问题包的版本，以及相关依赖包信息
  - **内核版本、共享 C 库版本**等
  - `uname -a` 的输出
  - `dpkg -s libc6 | grep ^Version` 的输出
  - 适用时给软件版本（如 `python -V`）
  - **硬件详情**；如果是驱动问题，**装上 `lshw` 并把整机硬件信息都给出**
  - **别担心报告太长**——只要信息相关，就写进去

  **⑤ Reproducibility 必须准确**：新工具请求或工具升级选 `N/A`。
  > 官方警告：**如果你标了「always」而实际只是偶发，开发者测不出来，报告可能被过早关闭。**

  **⑥ Steps to Reproduce 只放复现步骤**：看起来冗余的步骤也要写——**缺失的那一步可能正是关键**。

  **⑦ 报告里的行为准则（官方原文要点）**：
  - 给足信息；不确定时「**宁可多也不要少**」
  - **保持客观**，只讲事实
  - **分清楚哪些是事实（要有日志、回滚记录等佐证）、哪些是你的推测**
  - **不要引用 Wikipedia 等非一手来源当作「事实」**——「出问题的是你系统上的现象，不是 Wikipedia 声称的东西」
  - **不要把多个问题塞进一份报告**：**一个人，一份报告，一个 bug，一种硬件组合**
  - 开发者要求补充信息时请配合，**不懂就问，别发「Me too」**
  - **不要抱怨修得慢**——开发者是志愿者

- **验证方式**：报告发出后能在 `View Issues` 里检索到；有人能按你的步骤复现。

### Kali Linux Community Forums / IRC

- **论坛**：官方社区论坛在 <https://forums.kali.org/>，有明确的 **Forum Rules**，目标是让每个人都感到被欢迎。
- **IRC**：官方频道是 **`#kali-linux`，位于 OFTC 网络**。规则要点（官方列举的栏目）：注册昵称、如何对待其他用户、如何争论、语言、保持话题相关。
- **坑**：Discord/IRC 上的答案**不保证准确**，且**不永久**；有长期价值的问题优先发论坛。

### Official Kali Linux Mirrors

- **两大官方仓库（都用 mirrorlist 重定向）**：
  - **`http.kali.org`**：**主软件包仓库**（`apt` 用的那个）；
  - **`cdimage.kali.org`**：**预构建镜像仓库**（ISO 那些）。
- **验证方式**：
  ```bash
  curl -I http://http.kali.org/kali/         # 看 302 重定向到哪个镜像
  curl -i https://cdimage.kali.org/kali-2026.2/kali-linux-2026.2-installer-amd64.iso
  ```
  （原理与测速方法见 [11-故障排查](11-故障排查.md) 的下载速度一节。）
- **坑**：这两个域名**不是文件服务器**，是**重定向器**。把它们当作下载源或缓存代理后端会出问题（官方在 approx 配置里专门警告过）。

### Official Kali Linux Sites

- **它解决什么问题**：**辨别真假官网**，避免下载到被篡改的镜像。
- **要点**：Kali 项目使用 `kali.org` 的多个子域，每个有特定用途。官方明确：**这些站点是唯一的官方 Kali Linux 站点**。
- **官方站点分类**：Public Websites、Documentation、Community、Mirrors、Development、Infrastructure、External、Social Media Networks、Marketplaces and Stores。
- **验证方式**：镜像**永远从 <https://www.kali.org/get-kali/> 进入**，并**必须校验 SHA256**（<https://www.kali.org/docs/introduction/download-images-securely/>）。
- **坑**：第三方站点分发的「Kali 镜像」可能被植入后门。**只从官方渠道下载 + 校验校验和**是唯一的防线。

### How And Where To Get Help

- **它解决什么问题**：不知道该去哪求助。
- **官方建议**：如果你不想看长篇解释，先读 [11-故障排查](11-故障排查.md) 对应的 Basics of Troubleshooting；如果你觉得问题更复杂，用本篇。
- **渠道**：本地文档 → 在线文档 → 故障排查文档 → 报告（bug tracker）。
- **坑**：**「先搜索再提问」**是社区礼仪的底线；重复提问会被无视。

### Setting Up a Kali Linux Mirror

- **它解决什么问题**：自建**公开**或**私有** Kali 镜像。
- **公开镜像的主要步骤（官方 Outline）**：了解要求 → 建镜像用户 → 建目录 → 配置 `rsync` → 配置你的镜像 → 设置 SSH 密钥 → 联系官方以公开 → 首次同步 → 防火墙规则 → 配 cron 手动镜像 ISO → 加入 mirror redirector。
- **私有镜像**：同样的骨架，但只给自己用。
- **排错**：手动跑 `ftpsync`、清理**陈旧的 `.~tmp~` 目录**。
- **验证方式**：
  ```bash
  rsync --version
  du -sh /path/to/mirror
  ```
- **坑**：**磁盘与带宽消耗巨大**；公开镜像需要满足官方的**同步频率与在线时间要求**，具体以官方页面为准：<https://www.kali.org/docs/community/setting-up-a-kali-linux-mirror/>

## 实操清单

### 政策合规

- [ ] 读一遍 User Policy，理解非 root 下的行为差异（nmap 扫描类型）
- [ ] 理解 Network Service Policy：装完服务不自动启动是**设计**
- [ ] 检查自己机器上有没有被手工 enable 的对外服务：`ss -tlnp`、`systemctl list-unit-files --state=enabled`
- [ ] 做衍生版/二次分发前，逐个检查 Kali 特有 **non-free** 包的许可证
- [ ] 写教程/视频/周边时按商标规范使用 `Kali Linux ™`，首次出现带符号
- [ ] **不要**在产品或服务域名里使用 Kali/OffSec 商标
- [ ] 商业用途前先取得 OffSec 书面许可

### 授权与法务（做任何测试之前）

- [ ] **书面授权书 / SOW** 到位，写清范围、时间窗、技术手段、联系人
- [ ] 目标清单逐条核对（IP / 域名 / 应用）
- [ ] 明确「碰到真实个人信息怎么办」的应急流程
- [ ] 确认云服务商条款是否允许渗透测试（很多云商要求**提前申请**）
- [ ] 自建靶场/CTF/本地 VM 优先，**云主机不对互联网扫描**

### 社区

- [ ] 加 GitLab 账号，SSH key 配好（见 [12-开发与打包](12-开发与打包.md)）
- [ ] 注册论坛账号，先搜索再提问
- [ ] 需要实时交流再进 Discord / IRC（`#kali-linux` on OFTC）
- [ ] 注册 bug tracker 账号并**激活邮件**
- [ ] 报 bug 前先 `View Issues` 搜索是否重复
- [ ] 报 bug 时带上 `uname -a`、`dpkg -s libc6 | grep ^Version`、硬件信息（驱动问题装 `lshw`）
- [ ] 有带宽就做种 Torrent；有条件就托管镜像

## 排错

| 现象 | 原因 | 解决 |
|------|------|------|
| 装了 SSH/Apache 但重启后不自启 | **Network Service Policy 默认禁止服务持久化** | 显式 `sudo systemctl enable <服务>` |
| 非 root 下 nmap 扫描很慢 | 降级为 connect 扫描 | 用 `sudo nmap -sS`，或接受 `-sT` |
| 想让所有工具都像以前一样以 root 跑 | Kali 2020.1 起改为非 root | `sudo apt install -y kali-grant-root`（会削弱隔离） |
| 某个包在 Kali 主区找不到 | 可能在 `contrib`/`non-free`，或未收录 | 检查源里的 Components；新工具请求走 bugs.kali.org |
| 想做的事被官方拒绝收录 | DoS/DDoS/匿名类工具官方默认不装 | 这是政策；不要试图绕过，评估法律风险 |
| 下载到的「Kali 镜像」可疑 | 可能是第三方假冒站点 | 只从 <https://www.kali.org/get-kali/> 下载并校验 SHA256 |
| `curl -I http://http.kali.org/kali/` 返回 302 | 正常：它是重定向器 | 不要当作文件服务器或缓存代理后端 |
| 自己做的教程被指误导 | 商标被修改/缩写/加 logo | 按 press-pack 原样使用，首次出现带 ® / ™ 并加归属声明 |
| Bug 报告被要求补充信息 / 被关闭 | 无法复现，或缺关键信息 | 按官方清单补 `uname -a`、C 库版本、硬件信息、复现步骤 |
| Bug 报告被标记重复 | 提交前没搜索 | 先 `View Issues` 检索；**硬件问题例外，仍应单独提交** |
| 论坛/IRC 提问没人理 | 没搜索就提问，或问了文档里已有的内容 | 先读 Docs 与 [11-故障排查](11-故障排查.md)，再带足信息提问 |
