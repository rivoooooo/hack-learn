# Dradis（协作式渗透测试报告平台）

> **一句话**：一个 Web 版「渗透项目工作台」——多人协作维护一份**节点树 + 问题库 + 证据**，把 nmap/Nessus/Burp 等工具的输出直接导入，最后**按模板一键出报告**。
> **分类**：报告与协作（Reporting）｜ **Kali 包**：`dradis`（命令 `dradis-start`、`dradis-stop`；`dradis` 已被 Kali 标记为废弃）｜ **官方文档**：<https://dradis.com/ce/> ｜ 项目：<https://github.com/dradis/dradis-ce>

---

## 1. 它解决什么问题

一个人做小项目，用 [`cherrytree.md`](cherrytree.md) 就够了。但只要涉及**团队**和**正式交付**，立刻会出现新问题：

| 团队报告的真实痛点 | Dradis 的答案 |
|--------------------|---------------|
| 3 个人同时测试，笔记互相覆盖 | **Web 应用 + 团队账号**，多人实时协作（有修订历史） |
| 每个人记录格式不一样 | **统一的数据模型**（节点/问题/证据），格式天然一致 |
| 扫描器输出要手工抄进报告 | **导入插件**：nmap XML、Nessus、Burp、OpenVAS… 直接进 |
| 同一个漏洞在 10 台主机上出现，要写 10 遍 | **Issue（漏洞库）+ Evidence（每台主机的实例）** 复用 |
| 报告格式每次都不一样 | **报告模板**（HTML/Word 等）+ 内容块复用 |
| 客户要 Word/Excel/PDF | **导出插件**生成对应格式 |
| 测试完不记得"这步是谁做的" | 修订历史 + 活动记录 |

**核心设计思想**：**「一次评估」= 一棵节点树（资产）+ 一个漏洞库（知识）+ 两者之间的证据关联。**

对比同类：

| 工具 | 定位 | 差异 |
|------|------|------|
| **Dradis** | 协作报告平台 | Web、多用户、**导入/导出插件生态**、按模板出报告 |
| **`cherrytree`** | 个人层级笔记 | 单机、离线、上手快；适合过程记录与草稿；见 [`cherrytree.md`](cherrytree.md) |
| **Faraday** | 同类平台 | Kali 工具清单中**没有** `faraday`（本仓库数据未收录），故本教程不展开 |
| **Serpico / PlexTrac（商业）** | 报告平台 | 商业产品，功能更全 |

**推荐组合**：**CherryTree 记过程 → Dradis 汇总出报告**（或直接用 Dradis 全程记录）。

## 2. 工作原理

```
┌──────────────── Kali（Web 应用，Rails）────────────────┐
│ dradis-start → http://127.0.0.1:3000                  │
│                                                        │
│  ┌──────────── 数据模型 ────────────┐                   │
│  │ Team（团队成员与权限）             │                   │
│  │  └─ Project（一次评估）            │                   │
│  │       ├─ Node（节点树：资产/主机/服务）│               │
│  │       │    └─ Evidence（某问题在该节点上的证据）│      │
│  │       ├─ Issue（问题库：漏洞定义/修复建议）│           │
│  │       ├─ Content Block（可复用文本块）  │             │
│  │       ├─ Note（自由笔记）              │             │
│  │       └─ Attachment（附件，如截图/PCAP）│             │
│  └───────────────────────────────────┘                  │
│                                                        │
│  导入插件（Import）        导出插件（Export）            │
│   · Nmap XML               · HTML Report               │
│   · Nessus / OpenVAS       · Word / Excel（视插件）     │
│   · Burp Suite XML         · 自定义模板                 │
│   · Qualys / Acunetix …                                 │
└────────────────────────────────────────────────────────┘
        ▲                                  │
        │ 浏览器（多人同时访问）              ▼
   测试人员 A/B/C …                    交付给客户
```

### 关键概念（**理解这四个，就会用 Dradis**）

| 概念 | 含义 | 类比 |
|------|------|------|
| **Node（节点）** | 资产节点，**树形结构**（如 `192.168.56.0/24` → `192.168.56.102` → `21/tcp vsftpd`） | 报告里的"资产清单" |
| **Issue（问题）** | **漏洞定义**：标题、描述、影响、修复建议（可复用的"知识"） | 报告里的"漏洞章节模板" |
| **Evidence（证据）** | **某个 Issue 在某台主机上的实例**：命令、输出、截图 | 报告里的"复现记录" |
| **Content Block（内容块）** | 可复用的文本片段（如"免责声明""测试范围"） | 报告里的"固定段落" |

**为什么这样设计**：**同一个漏洞出现在 10 台主机上时，你只写一次 Issue，然后创建 10 条 Evidence** —— 报告导出时自动合并成"该漏洞影响 10 台主机"。**这是 Dradis 相对纯文档工具最大的效率优势。**

### 导入/导出插件机制

- **导入**：解析工具输出（XML/JSON），**自动创建 Nodes 并填充 Evidence**（例如 nmap XML 会生成 `IP → 端口/服务` 的节点树）。
- **导出**：按**模板**（HTML/Word/Excel）渲染报告。模板可自定义（Rails 视图/`dradis-reports-*` 插件），**这是"报告格式统一"的关键**。

## 3. 安装与快速上手

```bash
sudo apt update
sudo apt install dradis
command -v dradis-start dradis-stop
```

启动：

```bash
sudo dradis-start
```

```console
[*] Web UI: http://127.0.0.1:3000
[i] You might need to refresh your browser once it opens
```

```bash
# 确认在监听
ss -lntp | grep 3000
```

浏览器打开 `http://127.0.0.1:3000`：

```
首次访问 → 进入初始化/登录流程
  · 若引导创建账号：设置管理员账号与口令（务必用强口令）
  · 之后用该账号登录
```

停止：

```bash
sudo dradis-stop
```

> **注意**：Dradis 是 Rails 应用，**首次启动较慢**（要初始化数据库/资产编译）。启动后等几十秒再访问。日志可用 `journalctl -u dradis -n 50` 查看。

## 4. 核心参数详解

Dradis 是 Web 应用，没有命令行参数。下面给**界面核心操作**与**配置要点**。

### 4.1 界面核心操作

| 目的 | 位置 | 说明 |
|------|------|------|
| 创建项目 | `Projects → New Project` | 一次评估一个项目 |
| 建/导入节点 | `Nodes`（左侧树）→ 右键 → `Add child` / `Import` | 也可用插件批量导入 |
| 添加问题 | `Issues`（或节点上的 `Add issue`） | Issue 是"漏洞定义"，可复用 |
| 为节点添加证据 | 选中节点 → `Add evidence` | 绑定某个 Issue，填命令/输出 |
| 复用已有 Issue | 添加证据时选择"已有 Issue" | **这是效率关键** |
| 内容块 | `Content Blocks` | 固定段落（免责声明、范围、方法） |
| 附件 | 节点/证据里上传 | 截图、日志、抓包 |
| 修订历史 | 各对象的历史记录 | 谁改了什么（**协作审计**） |
| 导入工具输出 | `Import`（或节点右键 → `Import`） | 选插件（Nmap/Nessus/Burp…），上传文件 |
| 导出报告 | `Export → Reports`（或项目 → `Report`) | 选模板（HTML/Word…） |
| 团队与权限 | 管理员区 | 多人协作的账号与角色 |
| 方法论（若有） | `Methodologies` 插件 | 按 PTES/OWASP 组织 checklist |

### 4.2 数据字段与写法建议

| 对象 | 关键字段 | 写法建议 |
|------|----------|----------|
| **Node** | `Label`（名称）、`Type`（Host/Service/...）、`Parent` | **用 IP/域名作为 Label**；服务节点写 `PORT/PROTO SERVICE` |
| **Issue** | `Title`、`Description`、`Solution`、`References`、`CVSS`/`Severity` | **一次写清、反复复用**；标题含漏洞类型 |
| **Evidence** | `Content`（正文）、绑定的 Issue、附件 | **命令与输出用代码块**；**必须脱敏** |
| **Content Block** | `Label`、`Content` | 放免责声明、范围、方法、术语表 |
| **Tags** | 自定义标签 | 按风险等级/整改状态打标，便于筛选 |

### 4.3 导入插件（**最省时间的功能**）

| 插件 | 输入 | 生成什么 |
|------|------|----------|
| **Nmap** | `-oX` 的 XML | 主机/端口/服务节点 + 证据 |
| **Nessus** | `.nessus` / `.nessus2` | 漏洞证据（严重级别来自扫描器） |
| **OpenVAS/Greenbone** | XML | 漏洞证据 |
| **Burp Suite** | XML 导出 | Web 漏洞证据 |
| **Qualys / Acunetix / Nexpose / Nikto** | 各自报告 | 对应证据 |
| **CSV / Word / MediaWiki** | 通用格式 | 批量导入（可自定义映射） |

### 4.4 导出与模板

| 目标 | 做法 |
|------|------|
| HTML 报告 | `Export → Reports → HTML` |
| Word/Excel | 需要相应导出插件（视 Kali 打包与社区插件） |
| 自定义模板 | **修模板文件/插件**（Rails 视图），实现公司统一格式 |
| 内容复用 | 把固定段落做成 Content Block，模板里引用 |

## 5. 实战演练

> **环境声明**：以下使用**自建靶场**（自建虚拟机、TryHackMe、HTB、VulnHub）产出的扫描与利用记录。
> **笔记/报告内容含客户敏感信息**，请按第 9 节的合规要求管理；**记录时就脱敏**。

### 场景 1：从零建一个项目并导入扫描结果

**Step 1：启动并登录**

```bash
sudo dradis-start
```

```console
[*] Web UI: http://127.0.0.1:3000
```

```bash
# 首次启动可能需要等一会儿（Rails 初始化）
sleep 20; curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3000
```

```console
200
```

浏览器打开 `http://127.0.0.1:3000` → 完成初始化（创建管理员账号）→ 登录。

**Step 2：创建项目**

```
Projects → New Project
  Name: 2026-001 · 内部演练（自建靶场）
  → Create Project
```

**Step 3：用 Nmap 插件导入扫描结果（**这一步最能体现价值**）**

```bash
# 先产生 XML 输出
nmap -sV -sC -oX /tmp/nmap_2026-001.xml 192.168.56.0/24
ls -lh /tmp/nmap_2026-001.xml
```

```
Dradis：Import → Nmap → Choose File 选 /tmp/nmap_2026-001.xml → Upload
```

```console
Imported:
  Nodes created: 6
  Evidence: 41
```

**解读**：**几十条证据自动进库**。对比手工抄写，这是数量级的效率差异。

**Step 4：检查并整理节点树**

```
左侧 Nodes 树（导入后自动生成）：
  192.168.56.102
    ├─ 21/tcp  vsftpd 2.3.4
    ├─ 22/tcp  OpenSSH 4.7p1
    ├─ 80/tcp  Apache httpd 2.2.8
    └─ …
  192.168.56.103
    └─ …
```

**整理建议**：

| 动作 | 原因 |
|------|------|
| 重命名节点为**有意义的名称**（如 `WEB01 (192.168.56.102)`） | 报告可读性 |
| 把主机节点按分组/网段归类 | 报告结构 |
| 删除无关噪音节点（如只开放 22 且无发现的主机） | 报告精简 |
| 给有漏洞的节点打 Tag（如 `高危`、`待修复`） | 便于筛选与统计 |

### 场景 2：写一条可复用的 Issue + 多条 Evidence（**Dradis 的核心优势**）

**Step 1：定义 Issue（漏洞库）**

```
Issues → New Issue
  Title:       vsftpd 2.3.4 后门导致远程命令执行
  Severity:    Critical
  CVSS:        9.8
  Description: vsftpd 2.3.4 发行包被植入后门：用户名以 ":)" 结尾时，
               服务在 6200 端口以 root 权限开 shell。
  Solution:    1) 升级到 3.0.3+ 或发行版修复版本
               2) 无 FTP 需求则卸载并关闭 21/6200
               3) 防火墙限制来源
               4) 排查是否已被植入其他后门
  References:  CVE-2011-2523; EDB-17491
  → Save
```

**Step 2：为该 Issue 在具体主机上添加 Evidence（复现记录）**

```
Nodes → 选 192.168.56.102 → Add Evidence
  Issue:   选择刚建的 "vsftpd 2.3.4 后门…"
  Content: （命令与输出，注意脱敏）
```

```
【复现】
$ ftp 192.168.56.102
Name: user:)

$ nc 192.168.56.102 6200
# id
uid=0(root) gid=0(root)

【证据】
（上传终端截图附件：evidence_vsftpd_root.png）

【时间】2026-03-02 10:14 (CST)
```

**Step 3：如果同一漏洞影响多台主机 —— 再建一条 Evidence 即可**

```
Nodes → 选 192.168.56.110 → Add Evidence → 选同一个 Issue → 填该主机的复现
```

**解读**：导出报告时，这个 Issue 会自动合并显示「影响 2 台主机」。**这就是「Issue 复用 + Evidence 实例化」的威力**：写一次定义，N 台主机各自补证据。

**Step 4：用 Content Block 管好"固定段落"**

```
Content Blocks → New Content Block
  Label:   范围声明
  Content: 本次评估范围为 192.168.56.0/24，测试时间窗为
           2026-03-01 09:00 至 2026-03-05 18:00（CST）。
           测试依据授权编号 AUTH-2026-001。
```

同样为「免责声明」「测试方法」「术语表」「风险评级标准」各建一个内容块 → 报告模板里引用，**每次报告都不用重写**。

### 场景 3：团队协作、导出报告与自定义模板

**3a. 多人协作**

```
管理员区 → 创建团队成员账号（按角色分权限）
  · 测试人员 A 负责 192.168.56.10x 网段
  · 测试人员 B 负责 Web 应用
  · 项目负责人 审核与导出
```

**协作纪律（重要）**：

| 规则 | 原因 |
|------|------|
| **按资产划分负责范围** | 避免同一条证据被两人重复写 |
| **写完就走"审核"流程**（状态标记/Tag） | 保证报告质量 |
| **每条 Evidence 记录操作人与时间** | 修订历史可追溯 |
| **不把未经确认的发现直接标成"已确认"** | 报告中"误报"是专业事故 |

**3b. 导出报告**

```
选择项目 → Export → Reports
  → 选模板（如 HTML Report）
  → 选要包含的节点/问题（可按 Tag 过滤）
  → Generate / Download
```

```bash
# 下载到本地后检查
ls -lh ~/Downloads/
```

**检查清单（交付前必做）**：

| 检查项 | 说明 |
|--------|------|
| **脱敏** | 口令/hash/姓名/无关个人数据是否已处理 |
| **风险等级一致** | Issue 的严重级别与 Evidence 的描述是否矛盾 |
| **修复建议可执行** | 不是"加强安全"这种空话，而是具体操作 |
| **范围与时间** | 报告里是否写明授权范围与测试时间窗 |
| **误报清理** | 未验证的扫描器结果是否已标注为"未确认" |
| **附件与图片** | 是否完整、是否脱敏 |

**3c. 自定义报告模板（实现"公司统一格式"）**

```bash
# 模板通常位于 Dradis 安装目录的模板/插件目录中（Rails 视图）
sudo find / -path '*dradis*' -iname '*.html*' 2>/dev/null | grep -i -E 'template|report' | head
```

```console
/usr/share/dradis/.../templates/reports/...
```

**解读**：模板是 Rails 视图（HTML/ERB），可以改成公司样式（Logo、页眉页脚、章节顺序、风险评级表）。**这是"报告格式统一"的根治办法**——比每次导出再手工排版可靠得多。若是团队常规需求，建议把模板纳入版本管理。

**3d. 与 CherryTree 的分工（实战常用组合）**

```
过程中（动手时）：
  CherryTree：随手记命令、输出、截图、想法（离线、快、无网络依赖）
      │
      └─► 把整理好的结论搬到 Dradis（Issue + Evidence）
                │
交付时：
  Dradis：统一模板导出正式报告（团队审核、格式一致）
```

见 [`cherrytree.md`](cherrytree.md)。

## 6. 输出解读

### 6.1 报告应包含的章节（Dradis 的数据模型天然对应）

| 报告章节 | 对应 Dradis 对象 |
|----------|------------------|
| 封面 / 免责声明 / 范围与时间窗 | Content Block + 项目信息 |
| 执行摘要（管理层视角） | 手工撰写（结合统计） |
| 风险统计（各等级数量） | Issue 的 Severity 汇总 |
| 资产清单 | Nodes 树 |
| 漏洞详情（描述/复现/影响/修复） | Issue + Evidence |
| 附录（命令输出、截图、工具版本） | Evidence 附件 + Content Block |

### 6.2 质量判断

| 信号 | 含义 | 动作 |
|------|------|------|
| 一条 Issue 挂了 20 条 Evidence | 该漏洞影响面大 | 在报告摘要里突出 |
| 大量 Evidence 来自扫描器**未验证** | 可能存在误报 | **逐条验证**或明确标注"未确认" |
| Issue 缺少 `Solution` | 报告不完整（客户最需要这个） | 补齐修复建议 |
| 节点树里有孤立/无证据节点 | 可能是扫描噪音 | 清理 |
| 修订历史显示"多人反复改同一段" | 协作冲突 | 明确分工 |
| 导出的报告里出现真实口令 | **严重合规事故** | 重新脱敏后重新导出 |

## 7. 与其他工具配合

```
① 扫描与利用（产出结果）
   nmap -oX  /  Nessus  /  Burp  /  OpenVAS  /  Nikto / sqlmap
        │
        ├─► Dradis 导入插件（自动建节点 + 证据）      ← 本文
        └─► CherryTree（手工记录过程与草稿）          ← cherrytree.md
                │
② 汇总与协作
   Dradis：Issue 库 + Evidence + Content Block + 团队账号
        │
        ├─► 导出 HTML/Word/Excel（按模板）
        └─► 自定义模板 → 公司统一格式
                │
③ 交付与归档
   报告（脱敏）→ 客户；原始证据 → 加密归档（按合同期限销毁）
```

**典型流水线**：

```bash
nmap -sV -oX scan.xml 192.168.56.0/24      # 扫描
# → Dradis Import: Nmap
nikto -h http://192.168.56.102 -o nikto.txt
# → Dradis：手工/CSV 导入
burpsuite                                  # Burp XML → Dradis Import: Burp
# → 人工验证 + 写 Issue/Evidence
# → Export Reports（HTML/Word）
```

## 8. 常见坑与排错

| 报错/现象 | 原因 | 解决 |
|-----------|------|------|
| `dradis` 提示已废弃 | Kali 改用新命令 | 用 `sudo dradis-start` / `dradis-stop` |
| 3000 端口打不开 | 服务未起/Rails 初始化中 | 等 20–60 秒；`journalctl -u dradis -n 50`；`ss -lntp \| grep 3000` |
| 启动很慢/内存占用高 | Rails 应用特性 | 耐心等；给虚拟机足够内存 |
| 忘记管理员口令 | 初始化时设置 | 查 Kali/官方文档的密码重置流程；或重建数据库（**会丢数据**） |
| 导入 Nmap XML 失败 | XML 版本/格式不符 | 用 `nmap -oX`（不是 `-oN`）；检查是否被截断 |
| 导入后节点树很乱 | 扫描范围太大 | 先整理/过滤再导入；分次导入 |
| 报告里出现真实凭据 | **未脱敏** | **重新检查所有 Evidence**；建立"记录时脱敏"的纪律（见 [`cherrytree.md`](cherrytree.md) 场景 3） |
| 导出 Word/Excel 不可用 | 缺对应导出插件 | 用 HTML 导出；或按官方文档安装报告插件 |
| 多人同时编辑冲突 | 未分工/无审核流程 | 按资产划分责任人；用 Tag 标记状态 |
| 附件很大导致慢 | 上传了巨大 PCAP/镜像 | 附件只放必要证据；大文件另行归档 |
| 数据备份 | Rails + 数据库 | 定期备份数据库与附件目录；**迁移前先备份** |
| 想用 API 自动化 | CE 的 API 能力有限 | 查看当前版本的 API 支持情况；或用导入插件做批量 |

## 9. 防御视角（蓝队 / 项目管理）

Dradis 承载的是**整个项目的敏感信息聚合体**：资产清单、漏洞细节、证据（含命令输出与截图）。**它一旦泄露，等于客户的安全报告全量泄露。**

| 风险 | 后果 | 应对 |
|------|------|------|
| Dradis 暴露到公网 | 攻击者直接读到所有资产与漏洞 | **只监听内网**（默认 `127.0.0.1:3000`，不要改到 `0.0.0.0` 后放公网）；前面加认证与 TLS |
| 弱口令/共享账号 | 无法追溯"谁做了什么" | **每人独立账号 + 强口令**；用修订历史追责 |
| 证据含真实凭据 | 合规事故 + 二次泄露风险 | **记录时脱敏**（口令/hash/姓名） |
| 项目数据长期留存 | 超出合同约定的数据保留 | 按合同**到期销毁**；保留销毁记录 |
| 无备份 | 项目数据丢失 → 无法交付 | 定期备份数据库与附件；**备份也要加密** |
| 模板里嵌入了敏感示例 | 每个新报告都重复泄露 | 模板里用**脱敏示例**；模板本身纳入版本管理与审核 |
| 报告未经审核就交付 | 误报/口径不一致/信息泄露 | 建立**双人审核**流程（Dradis 的协作能力正好支持） |

**给安全团队的三条建议**：

1. **把 Dradis 部署在内网隔离环境**，配上 TLS 与独立账号（**永不暴露公网**）；
2. **把"记录即脱敏"写进 SOP**，并在导出前做一次**脱敏检查清单**；
3. **把报告模板纳入版本管理**（统一格式 + 统一脱敏措辞 + 统一风险评级标准）。

## ⚠️ 法律与伦理

Dradis 本身是**正当的报告协作工具**，风险来自**它聚合的内容**与**它的部署方式**：

- **未授权测试的记录**：项目数据会成为违法行为的完整证据链（目标、时间、工具、命令）—— 可能触犯《刑法》第 285/286 条；
- **客户数据与个人信息**：证据中的凭据、员工信息、内部拓扑属敏感数据；泄露或超范围使用会触发《个人信息保护法》《数据安全法》责任，并违反 NDA；
- **部署安全**：Dradis 集中承载全部敏感信息，**暴露到公网等于把客户的安全报告公开**。这不仅是技术问题，也可能构成对客户的**违约与侵权**。

**操作要求**：

1. **只记录有授权的测试内容**，并在报告中写明授权范围与时间窗；
2. **只在内网部署**，每人独立账号、强口令、启用 TLS；
3. **记录时就脱敏**（口令、hash、姓名、无关个人数据）；
4. **导出前做脱敏检查**，并保留审核记录（双人复核）；
5. **按合同期限保存与销毁数据**，销毁要有记录；
6. **备份加密**，且备份与生产数据同等级管理；
7. **不要用共享账号**——否则出问题时无法自证清白。
