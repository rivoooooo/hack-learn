## 1. 权威书籍

### 1.1 第一梯队：按阶段选

| 书名 | 作者 | 适合阶段 | 说明 |
| --- | --- | --- | --- |
| 《Linux Kernel Development》第 3 版（中译《Linux 内核设计与实现》） | Robert Love | **入门到中级** | 最好的第一本书。讲「为什么这么设计」，代码量少，语言易读。缺点：内容停留在 2.6 时代，需要配合现代源码看 |
| 《Understanding the Linux Kernel》第 3 版（中译《深入理解 Linux 内核》） | Daniel P. Bovet、Marco Cesati | **中级到高级** | O'Reilly 的经典「动物书」。逐子系统深入，讲进程/内存/VFS/信号很细。同样停留在 2.6 时代，且比 Love 的书难 |
| 《Linux Device Drivers》第 3 版（LDD3，中译《Linux 设备驱动程序》） | Jonathan Corbet、Alessandro Rubini、Greg Kroah-Hartman | **驱动入门** | 驱动开发的入门标准。**官方提供免费 PDF**：<https://lwn.net/Kernel/LDD3/>（已实测确认，含 18 章 PDF）。⚠️ 该书对应内核 2.6.10，API 变化很大 —— 把它当作「概念地图」而不是代码参考 |
| 《Professional Linux Kernel Architecture》 | Wolfgang Mauerer | **中级到高级** | 比 Bovet 稍新（2.6.24 时代），结构清晰，图表丰富 |
| 《Understanding the Linux Virtual Memory Manager》 | Mel Gorman | **专项：内存管理** | 内存管理最系统的一本。免费在线版在作者的站点可查。同样偏老，但伙伴系统/SLAB/页回收的概念至今未变 |
| 《Linux Kernel Programming: A Comprehensive Guide to Kernel Internals, Writing Kernel Modules, and Kernel Synchronization》 | Kaiwan N Billimoria | **驱动/模块实战** | 相对新（5.x 时代），从模块到同步到内存管理，实验导向。配套第二册讲调试与性能 |
| 《Linux Kernel Debugging》 | Kaiwan N Billimoria | **调试专项** | 专门讲内核调试工具链：printk、ftrace、kprobes、GDB、crash、KASAN 等 |

### 1.2 中文原创

| 书名 | 作者 | 适合阶段 | 说明 |
| --- | --- | --- | --- |
| 《Linux 内核源代码情景分析》 | 毛德操、胡希明 | **高级** | 按「情景」（一次系统调用的完整流程）展开，读法非常契合本文档 [02](02-源码结构与阅读方法.md#63-调用链实证一次-write-从用户态到设备) 提倡的「跟一条链走到底」。代码基于 2.4，极老，方法论仍有效 |
| 《Linux 内核完全剖析》 | 赵炯 | **了解演进** | 逐行分析 0.11 版内核（约 2 万行）。适合理解「内核最原始长什么样」，但与现代内核差距巨大 |

### 1.3 工具与性能（与内核强相关）

| 书名 | 作者 | 说明 |
| --- | --- | --- |
| 《Systems Performance: Enterprise and the Cloud》第 2 版（中译《性能之巅》） | Brendan Gregg | 系统性能分析的方法论 + Linux 工具链。第 6、7 章讲观测工具时大量涉及内核机制 |
| 《BPF Performance Tools》 | Brendan Gregg | eBPF/bpftrace 的百科。数百个可直接用的脚本，每个都对应一个内核子系统 |
| 《The Linux Programming Interface》 | Michael Kerrisk | **用户态**视角，但是理解系统调用语义最权威的一本（man-pages 的维护者写的）。读内核代码时拿它对照「这个 syscall 承诺什么行为」非常有价值 |

### 1.4 阅读建议

老书的价值在于「概念」，不在「API」。推荐这台组合：

```
Robert Love（为什么）
        +
本地源码树（怎么样，永远最新）
        +
docs.kernel.org（权威细节）
        +
[02-源码结构与阅读方法](02-源码结构与阅读方法.md) 的调用链实证
```

**不要**试图把一本老书的代码示例编译到 7.x 上。看到 `foo->count++` 之类就把它当成「那个年代的写法」读思路即可。

## 3. 源码树里的文档（别忽略）

联网查文档有时不如直接 `grep` 本地源码。实测本地 `Documentation/` 有 75 个子目录，与在线文档同源。

```bash
export KSRC=$(pwd)/kernel/src/linux
cd "$KSRC"

# 按关键词找文档
grep -rln "use-after-free" Documentation/ | head
grep -rln "workqueue" Documentation/core-api/

# 最该先读的几个文件
ls Documentation/process/            # 开发流程（development-process.rst, submitting-patches.rst, submit-checklist.rst, coding-style.rst, 4.Coding.rst, security-bugs.rst, ...）
ls Documentation/kbuild/             # 构建系统（kbuild.rst, makefiles.rst, kconfig.rst, modules.rst, kconfig-language.rst）

ls Documentation/dev-tools/          # 调试工具（kasan.rst, kcsan.rst, kfence.rst, kmsan.rst, ubsan.rst, kmemleak.rst, kcov.rst, kselftest.rst, kunit/, checkpatch.rst, sparse.rst, coccinelle.rst, ...）
ls Documentation/admin-guide/        # 管理员视角（kernel-parameters.txt, sysctl/, kdump/, LSM/, bug-hunting.rst, reporting-issues.rst, ...）
ls Documentation/trace/              # ftrace / tracepoint / kprobe（ftrace.rst, ftrace-design.rst, kprobes.rst, kprobetrace.rst, events.rst, histogram.rst, ...）
ls Documentation/bpf/                # eBPF（bpf_design_QA.rst, btf.rst, kfuncs.rst, libbpf/, map_*.rst, ...）

## 4. 邮件列表与社区

### 4.1 该发到哪个列表

**永远先查 `MAINTAINERS`**：

```bash
cd "$KSRC"
./scripts/get_maintainer.pl mm/page_alloc.c
./scripts/get_maintainer.pl -f fs/ext4/inode.c
./scripts/get_maintainer.pl --no-git-fallback --roles=maintainer,reviewer drivers/char/misc.c
```

输出会给出：维护者（`M:`）、评审者（`R:`）、邮件列表（`L:`）、状态（`S:`）。**只发给维护者与对应列表，不要广撒网。**

| 列表 | 用途 |
| --- | --- |
| `linux-kernel@vger.kernel.org` | 总列表。流量极大（每天数千封）。除非没有更具体的列表，否则**不要**只发这里 |
| `linux-mm@kvack.org` | 内存管理 |
| `linux-fsdevel@vger.kernel.org` | VFS 与文件系统开发 |
| `netdev@vger.kernel.org` | 网络 |
| `linux-security-module@vger.kernel.org` | LSM |
| `bpf@vger.kernel.org` | eBPF |
| `kvm@vger.kernel.org` | KVM |
| `linux-arch@vger.kernel.org` | 跨架构话题 |
| `linux-doc@vger.kernel.org` | 文档 |
| `stable@vger.kernel.org` | stable 分支的补丁 |
| `security@kernel.org` | ⚠️ **安全漏洞专用**，私有列表，见 [04 §6.3](04-内核安全与攻防.md#63-上游报告流程) |

### 4.2 提问与提交的礼仪（这是硬性规则，不是建议）

**纯文本邮件。** 内核社区明确拒绝 HTML 邮件。手机客户端、网页邮箱默认发 HTML —— 必须手动切成纯文本。

| 规则 | 原因 |
| --- | --- |
| 纯文本，行宽 ~72 列 | 内核代码风格就是 80 列；超宽行在多种客户端里会错乱 |
| **底部回复 / 交错回复**（inline reply），不要顶部回复 | 讨论上下文必须可读 |
| 只引用相关的几行，不要整封回引 | 动辄几百行的引用会让维护者直接跳过 |
| 不要附件发 patch，patch 直接内联在邮件正文 | 维护者用 `git am` 直接吃正文 |
| 不要发截图 | 别人无法搜索、无法引用 |
| Subject 要能独立读懂 | `[PATCH] mm: fix off-by-one in foo_alloc` 而不是 `[PATCH] fix bug` |
| 回复时保留原 Subject 与 `Message-ID` 线索（用 `git send-email` / 邮件客户端的"回复"） | 否则讨论被拆成多个线程 |
| 不要催 | 维护者是志愿者 |
| 一次只做一件事 | 一个补丁混合了重构 + 修 bug 会被要求拆分 |
| 用 `git send-email` 而不是复制粘贴 | 自动处理编码、行宽、`In-Reply-To` |

### 4.3 提问模板（问「为什么这段代码这样写」）

```
Subject: Question about <函数名>() in <文件路径>

Hello,

I'm reading <文件路径>:<行号>, specifically <函数名>():

    <粘贴 10-30 行相关代码>

I understand that it <你理解的部分>, but I don't understand why
<具体的困惑点>.

Specifically:
1. <问题 1>
2. <问题 2>

I've already looked at:
- <你已经读过的文件/文档>
- <你已经查过的提交>

Thanks,
<你的名字>
```

关键点：**表明你已经做过功课**。问「这个函数做什么」不会得到回复；问「这里为什么用 `rcu_dereference()` 而不是直接读，我看注释说……但我不理解 X」会。

### 4.4 提交第一个补丁的推荐路径

1. 读 `Documentation/process/development-process.rst`（实测存在）+ 它的 9 个子文件。
2. 读 `Documentation/process/coding-style.rst` 与 `Documentation/process/4.Coding.rst`。
3. 读 `Documentation/process/submitting-patches.rst` 与 `Documentation/process/submit-checklist.rst`。
4. 从 `drivers/staging/` 或 `Documentation/` 的拼写/示例修正开始（社区明确欢迎新人从这类补丁入手）。
5. 用 `scripts/checkpatch.pl` 自检，用 `scripts/get_maintainer.pl` 找人。
6. `git format-patch` + `git send-email`。
7. 接受 review。第一次被要求改 3 遍是正常的。

> ⚠️ 不要把测试补丁发到真实的 LKML。自测时用 `<你的名字>.invalid@example.com` 之类的假地址，或者只用 `--dry-run`：
> ```bash
> git send-email --dry-run --to=yourself@example.com *.patch
> ```

## 5. 如何提问与报告问题

### 5.1 提问前的自检清单

- [ ] 我已经在 `Documentation/` 里搜索过关键词（`grep -rin "<关键词>" Documentation/`）
- [ ] 我已经在代码里搜索过（`grep -rn`，用 [02](02-源码结构与阅读方法.md#71-三种跳转方式的取舍) 的方法）
- [ ] 我确认了我的内核版本（`uname -r` / `make -s kernelversion`）
- [ ] 问题在最新版本上仍然存在（`linux-next` 或最新 mainline）
- [ ] 我读过相关的 `git log`（`git log -p --follow <文件>` 或 `git blame`）
- [ ] 我在 Lore 上搜过这个问题是否讨论过
- [ ] 我能给出最小复现（而不是"我的服务挂了"）

### 5.2 Bug 报告模板

```
Subject: <子系统>: <简短现象描述>

# 1. 概要
一句话说清问题。

# 2. 环境
- 内核版本: <make -s kernelversion 或 uname -r 的完整输出>
- 发行版/架构: <...>
- 相关配置: <grep 出相关 CONFIG_ 行粘贴>
- 硬件/虚拟机: <...>

# 3. 复现步骤
1. ...
2. ...
（如果能让别人复制粘贴就最好）

# 4. 实际结果
完整的内核日志（不要截断，不要截图）：
<粘贴 dmesg 或串口输出，包含完整的 Oops/KASAN/WARNING 报告>

### 6.2 三种分支类型的区别

| 类型 | 何时用 | 谁维护 | 是否可提交补丁 |
| --- | --- | --- | --- |
| **mainline**（主线，`torvalds/linux`） | 跟踪最新开发、做上游工作、验证你的补丁 | Linus Torvalds | 是（先经过子系统树） |
| **stable**（`linux-x.y.z`） | 生产环境需要新特性但不想用 `-rc` | Greg Kroah-Hartman + Sasha Levin | 只接受「上游已有对应修复」的 backport，或明确标注 `Cc: stable@vger.kernel.org` |
| **longterm / LTS** | 生产环境，需要长期安全更新 | Greg Kroah-Hartman | 同上 |
| **linux-next** | 提前发现跨子系统冲突 | Stephen Rothwell | 不直接提交，只是整合测试 |
| **子系统树**（`*-next`，如 `net-next`） | 特定子系统的开发前沿 | 各子系统维护者 | 是（这才是你的补丁该去的第一个地方） |

### 6.3 版本号的含义

```
       7  .  3  .  0  -  rc3
       │     │     │     │
       │     │     │     └─ 候选发布的序号（Release Candidate）
       │     │     └─────── SUBLEVEL：稳定补丁号
       │     └───────────── PATCHLEVEL：特性版本
       └─────────────────── VERSION：主版本
```

对应源码树 `Makefile` 顶部的变量（实测）：

```makefile
VERSION = 7
PATCHLEVEL = 3
SUBLEVEL = 0
EXTRAVERSION = -rc3
NAME = Baby Opossum Posse
```

| 字段 | 含义 | 什么时候变 |
| --- | --- | --- |
| `VERSION` | 主版本号 | 极少变（…5 → 6 → 7） |
| `PATCHLEVEL` | 特性版本 | 每个 merge window 结束 +1 |
| `SUBLEVEL` | 稳定补丁号 | 每次 stable 发版 +1（只含修复） |
| `EXTRAVERSION` | 额外后缀 | `-rc1`…`-rc8`（开发期）或 `-next` 等 |
| `NAME` | 代号 | 每个特性版本一个，Linus 起名 |
| `LOCALVERSION` | 自定义后缀 | **配置文件里的 `CONFIG_LOCALVERSION`**，会拼在 `uname -r` 里 |

`make -s kernelversion` 的输出规则：

| 情形 | 输出 |
| --- | --- |
| `SUBLEVEL = 0` 且无 `EXTRAVERSION` | `7.3` |
| `SUBLEVEL = 0` 且有 `EXTRAVERSION = -rc3` | `7.3.0-rc3` ← 本仓库的情况 |
| `SUBLEVEL = 6`，无 `EXTRAVERSION` | `7.2.6` |
| 有 `LOCALVERSION = "-learn"` | `uname -r` 会多出 `-learn`，但 `make kernelversion` 不含它 |

验证：

```bash
cd "$KSRC"
make -s kernelversion          # 7.3.0-rc3
grep -E '^(VERSION|PATCHLEVEL|SUBLEVEL|EXTRAVERSION|NAME)' Makefile
grep CONFIG_LOCALVERSION .config 2>/dev/null || true
```

### 6.4 `uname -r` 输出解读

`uname -r` 打印 `UTS_RELEASE`，由 `Makefile` 的版本变量 + `CONFIG_LOCALVERSION` + `CONFIG_LOCALVERSION_AUTO` 拼接而成。

```bash
uname -r          # 例如：7.2.3-arch1-3
uname -a
cat /proc/version
```

拆解一个复杂的例子：

```
6.12.110-1-amd64-lxc
│  │   │ │  │     └── 打包者的额外标记（如 LXC 优化）
│  │   │ │  └──────── 架构标记（Debian 的 kernel flavour）
│  │   │ └─────────── 发行版修订号（-1 = 第几次打包修订）
│  │   └───────────── CONFIG_LOCALVERSION（约 6.12.y 的 stable 号）
│  └───────────────── PATCHLEVEL
└──────────────────── VERSION
```

| 位置 | 来源 | 说明 |
| --- | --- | --- |
| 前两段 | `VERSION.PATCHLEVEL` | 内核特性版本 |
| 第三段 | `SUBLEVEL` | stable 补丁号；分发版常把 stable 号放这里 |
| 后面的 `-xxx` | `CONFIG_LOCALVERSION` + 发行版自定义 | **不是内核版本的一部分** |
| 末尾的架构词 | 发行版的 `kernel flavour` | 如 Debian 的 `-amd64`、`-rt-amd64`、`-cloud-amd64` |

查看某台机器的完整信息：

```bash
uname -r
uname -v                      # 编译时间（可能含发行版补丁提示）
uname -m                      # 机器架构
cat /proc/version             # 含编译器版本
cat /proc/sys/kernel/version  # 编译日期
# 从 bzImage 里提取编译时用的 .config（需要有 ikconfig 支持）
"$KSRC/scripts/extract-ikconfig" /boot/vmlinuz-$(uname -r) | head -50
# 发行版内核的配置（Debian/Ubuntu）
grep -E 'CONFIG_(LOCALVERSION|HZ|PREEMPT)' /boot/config-$(uname -r)
```

**为什么 `uname -r` 这么重要**：它是 `/lib/modules/$(uname -r)/` 的目录名，也是模块 `vermagic` 的第一项。你自己编译的内核如果没设 `CONFIG_LOCALVERSION`，`uname -r` 可能与发行版内核完全相同，导致 `/lib/modules/` 目录被覆盖 —— 这就是为什么本文推荐设 `LOCALVERSION="-learn"`。

### 6.5 为什么版本号在 6.x / 7.x 之间跳跃很快

不要把主版本号当作「重大变化」的信号。实际上是：

- **`VERSION.PATCHLEVEL` 的增长与时间绑定**，与"重大程度"无关。
- 一个「特性版本」（如 6.12 → 6.13）大约每 9~10 周发布一次，由 **merge window** 驱动：2 周合并窗口 + 6~8 周 `-rc` 稳定期。
- merge window 期间 `PATCHLEVEL` 已经 +1 但 `EXTRAVERSION = -rc1`，所以你看到的是 `7.3-rc1`。
- `SUBLEVEL` 的增长完全是缺陷修复的累积，与特性无关。

关于版本号历史的说明可在 <https://www.kernel.org/category/releases.html> 找到。

### 6.6 选哪个版本做实验

| 你的目的 | 推荐版本 | 理由 |
| --- | --- | --- |
| 学习源码结构、写模块 | **最新的 stable**（当前 `7.2.6`）或 **mainline `-rc`** | 代码最新，社区文档与讨论对得上 |
| 对齐生产环境 | 与你服务器相同的 LTS（`6.12.y` / `6.6.y` / `6.1.y`） | 行为一致，补丁可复用 |
| 做模糊测试找 bug | **mainline 或 linux-next** | 新代码 bug 多，也才有价值 |
| 做内核安全研究 | **最新 stable + 最新 LTS** 两条都看 | 现代缓解机制 vs 广泛部署版本 |
| 本仓库当前状态 | `7.3.0-rc3` | 已克隆，文档已对齐 |

切换分支（浅克隆下需要重新拉取）：

```bash
# 拉取 stable 分支
export KERNEL_MIRROR=https://git.kernel.org/pub/scm/linux/kernel/git/stable/linux.git
bash scripts/fetch_linux_kernel.sh --stable   # 切换到 linux-6.12.y

# 或手动指定任意标签（需要完整或足够深的历史）
cd "$KSRC"
git fetch --depth 1 origin tag v7.2.6
git checkout v7.2.6
make -s kernelversion     # 7.2.6
```

⚠️ 切换版本后，本文档里的**行号与部分目录清单会失效**。目录结构、模块 ABI、`vermagic` 都会变，必须重新 `ls` / `grep` 验证。这是 [02-源码结构与阅读方法](02-源码结构与阅读方法.md) 反复强调「不要凭记忆写」的原因。
