# 02 - 源码结构与阅读方法

本文所有目录清单、文件名、函数名、行号均来自本仓库本地源码树 `kernel/src/linux`（下文简称 `$KSRC`）的实测结果。源码版本：**7.3.0-rc3**。

```bash
# 在仓库根目录执行
export KSRC=$(pwd)/kernel/src/linux
cd "$KSRC" && make -s kernelversion && ls
```

相关文档：[README](../README.md) · [01-内核构建与调试](01-内核构建与调试.md) · [03-内核模块开发](03-内核模块开发.md)

> **行号会随版本漂移**。本文给出的行号用于帮你快速定位「这一段大概在哪」，不是永久坐标。始终用 `grep -n` 重新确认。

## 1. 读内核代码的正确姿势

内核代码规模（实测，不含 `tools/`）：

| 指标 | 数量 |
| --- | --- |
| 顶层目录 | 24 个（+ 15 个顶层文件） |
| `*.c` 文件 | 约 33 584 |
| `Kconfig*` 文件 | 1 927 |
| 磁盘占用（工作树 + `.git`） | 约 2.1 GB |

一次性读完是不可能的。可行的策略是**沿着一条具体的数据流走到底**，再横向扩展。本文 §6 就提供了这样一条完整链路。

三条硬性建议：

1. **只读一个函数，不要读一个文件。** 用 `grep -n` 定位到函数，读它的参数、返回值、错误分支，然后跳到**调用者**和**被调用者**。
2. **随时回答三个问题**：这个函数运行在什么上下文（进程/中断/软中断）？可以睡眠吗？谁持有锁？
3. **不要相信记忆中的 API。** 上一版内核的函数名这一版可能已经改了（例如 `do_filp_open()` 在 7.3 中已被 `do_file_open()` 取代，见 §6.3）。永远 `grep` 验证。

## 3. `kernel/` 子目录的关键文件

`kernel/` 是「内核核心」而非「整个内核」。实测文件清单中的重点：

### 3.1 进程与调度

| 文件 | 关键函数 / 内容 |
| --- | --- |
| `kernel/fork.c` | `kernel_clone()`、`copy_process()`、`dup_mm()`、`copy_thread()` —— `fork()`/`clone()`/`vfork()` 的实现 |
| `kernel/exit.c` | `do_exit()`、`do_group_exit()`、`wait4()` 的 `kernel_wait4()`、`release_task()` |
| `kernel/exec_domain.c` | 历史遗留，已基本空壳 |
| `kernel/sched/core.c` | 调度器主逻辑：`__schedule()`、`schedule()`、`try_to_wake_up()`、`set_user_nice()` |
| `kernel/sched/fair.c` | CFS（完全公平调度器）主体；`sched_slice()`、`task_tick_fair()` |
| `kernel/sched/rt.c` | 实时调度策略 `SCHED_FIFO` / `SCHED_RR` |
| `kernel/sched/deadline.c` | `SCHED_DEADLINE`（EDF 调度） |
| `kernel/sched/syscalls.c` | `sched_setscheduler()` 等与用户态打交道的调度接口 |
| `kernel/sched/psi.c` | PSI（Pressure Stall Information，资源压力指标），`/proc/pressure/*` 的来源 |
| `kernel/sched/ext/` | `sched_ext`（`SCX`）可编程调度器 |
| `kernel/sched/build_policy.c` / `build_utility.c` | 纯集合式编译单元（把多个 `.c` `#include` 进来以缩短构建时间），**不是逻辑文件** |

### 3.2 系统调用杂项与信号

| 文件 | 内容 |
| --- | --- |
| `kernel/sys.c` | 一大批「没地方放」的系统调用：`sys_getpid`→`__do_sys_getpid`、`sys_newuname`、`sys_setrlimit`、`sys_reboot` |
| `kernel/signal.c` | 信号投递与处理：`send_signal()`、`get_signal()`、`do_signal()` |
| `kernel/seccomp.c` | seccomp BPF 过滤器（`Documentation/userspace-api/seccomp_filter.rst`） |
| `kernel/capability.c` | `capable()`、`ns_capable()` 的能力检查 |
| `kernel/cred.c` | `struct cred` 的生命周期与复制 |
| `kernel/pid.c` | PID 分配：`alloc_pid()`、`find_task_by_vpid()` |
| `kernel/nsproxy.c` | namespace 代理（mnt/uts/ipc/pid/net/cgroup/time） |
| `kernel/user_namespace.c` | 用户命名空间，**容器安全的关键** |
| `kernel/ptrace.c` | `ptrace` 系统调用 —— 调试器与反调试的战场 |
| `kernel/umh.c` | `call_usermodehelper()`，内核请求用户态程序（热点 udev/`modprobe` 路径） |

### 3.6 其他值得知道的

`kernel/cgroup/`（cgroup v2）、`kernel/audit*.c`（审计）、`kernel/livepatch/`（热补丁）、`kernel/watchdog.c`（硬/软 lockup 检测）、`kernel/hung_task.c`（D 状态卡死检测）、`kernel/kcsan/`、`kernel/futex/`、`kernel/power/`（挂起/休眠）、`kernel/printk/`、`kernel/entry/`（通用入口 `common.c`）。

## 6. 系统调用全景与调用链实证

### 6.1 `SYSCALL_DEFINE` 宏与 syscall 表

内核里定义系统调用不用手写汇编，而是用 `SYSCALL_DEFINE<n>` 宏：

```c
SYSCALL_DEFINE3(write, unsigned int, fd, const char __user *, buf,
		size_t, count)
{
	return ksys_write(fd, buf, count);
}
```

规则：宏名里的数字 = 参数个数；宏的第一个参数是 syscall 名；随后是「类型, 形参名」的交替列表。这些宏定义在 `include/linux/syscalls.h`，通过 `__SYSCALL_DEFINE` 展开后生成一个接受 `struct pt_regs *` 的函数 `__x64_sys_write()`，再从寄存器里取出实参。

实测规模：

| 指标 | 数值 |
| --- | --- |
| 全树 `SYSCALL_DEFINE*` 出现次数 | 799 |
| `arch/x86/entry/syscalls/syscall_64.tbl` 中的条目（不含 x32） | 422 |
| 表中最大系统调用号 | 472 |

表文件格式（实测 `syscall_64.tbl` 头部注释原文）：

```
# The format is:
# <number> <abi> <name> <entry point> [<compat entry point> [noreturn]]]
# The abi is "common", "64" or "x32" for this file.
```

`write` 的行（`:13`）：

```
1	common	write			sys_write
```

编号 | ABI | 名字（用户态用） | 内核入口符号

### 6.2 从 syscall 号到 C 函数的 4 跳

```
用户态: syscall(1, fd, buf, count)  或  glibc write()
   |
   | x86-64 的 SYSCALL 指令，号放 rax
   v
[1] arch/x86/entry/entry_64.S:87   SYM_CODE_START(entry_SYSCALL_64)
        ... 换栈、保存 pt_regs ...
    arch/x86/entry/entry_64.S:121  call do_syscall_64
   |
   v
[2] arch/x86/entry/syscall_64.c:79   do_syscall_64(struct pt_regs *regs, long nr)
        -> syscall_enter_from_user_mode_randomize_stack()  (让 nr 被验证)
        -> do_syscall_x64()
             nr = array_index_nospec(nr, NR_syscalls);   /* 防 Spectre 的边界钳制 */
   |
   v
[3] arch/x86/entry/syscall_64.c:36   x64_sys_call(regs, nr)
        switch (nr) { ... case 1: return __x64_sys_write(regs); ... }
        /* __x64_sys_* 由 asm/syscalls_64.h 生成，从 pt_regs 取参 */
   |
   v
[4] fs/read_write.c:747   SYSCALL_DEFINE3(write, unsigned int, fd,
                                          const char __user *, buf, size_t, count)
        -> ksys_write(fd, buf, count)
```

值得注意的细节（都能在源码里看到，不是传说）：

- `sys_call_table[]`（`arch/x86/entry/syscall_64.c:29`）**已经不再用于分发系统调用**，源码注释明确写着它只是留给 `kernel/trace/trace_syscalls.c` 查地址用。真实分发走 `x64_sys_call()` 里的 `switch`，因为 `switch` 生成的代码更利于缓解 Spectre。
- `do_syscall_x64()` 里的 `array_index_nospec(nr, NR_syscalls)` 是在做**边界钳制**，让 CPU 的推测执行无法越过数组边界 —— 这是「如何防投机侧信道」的教科书例子。
- 入口处 `do_syscall_64()` 是 `noinstr` 标记的：它不能有任何插桩（ftrace/kprobe/编译器插桩），因为它跑在 `regs` 还没完全可信的阶段。

### 6.4 7.x 的新写法：`CLASS()` 自动清理

`ksys_write()`（`fs/read_write.c:728`）里这一行值得单独说：

```c
CLASS(fd_pos, f)(fd);
```

这是基于 `include/linux/cleanup.h` 的作用域自动清理（scope-based cleanup）。它的定义在 `include/linux/file.h`：

```c
include/linux/file.h:83   DEFINE_CLASS(fd,     struct fd, fdput(_T),     fdget(fd),     int fd)
include/linux/file.h:84   DEFINE_CLASS(fd_raw, struct fd, fdput(_T),     fdget_raw(fd), int fd)
include/linux/file.h:85   DEFINE_CLASS(fd_pos, struct fd, fdput_pos(_T), fdget_pos(fd), int fd)
```

`CLASS(fd_pos, f)(fd)` 展开后会：
1. 通过 `fdget_pos()` 获取 `struct fd`；
2. 在函数返回（含提前 `return`、`goto`）时自动调用 `fdput_pos()`。

好处是可以彻底杜绝「忘记 `fdput()` 导致引用计数泄漏」这类 bug。读到这类代码不要慌，把它当作「声明 + 自动析构」即可。

## 7. 阅读方法：工具与技巧

### 7.1 三种「跳转」方式的取舍

| 方式 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- |
| `grep -rn` / `rg` | 零配置、结果可信、能搜字符串与宏 | 需要手写正则；同名函数多时会噪音大 | **默认首选** |
| `cscope` + `vim`/`emacs` | 定义/调用/引用分类清晰，能反向查「谁调用了它」 | 建库较慢，对大目录需设 `-q` | 大规模阅读 |
| `clangd` / LSP | 真正语义级跳转（能区分同名函数、展开宏） | 需要 `compile_commands.json`，内核构建生成较慢 | 长时段深入某个子系统 |

生成 cscope 数据库（只索引不想索引 `drivers/` 时排除掉，可大幅加速）：

```bash
cd "$KSRC"
find . -name '*.c' -o -name '*.h' -o -name '*.S' \
  | grep -v '^./drivers/' | grep -v '^./tools/' > /tmp/cscope.files
cscope -bq -i /tmp/cscope.files -f /tmp/cscope.out
cscope -d -f /tmp/cscope.out      # 打开交互界面
# 常用：0 查找符号  1 查找定义  2 查找被调用  3 查找调用者  4 查找文本
```

生成 `compile_commands.json` 供 clangd 使用：

```bash
cd "$KSRC"
make O=/tmp/kbuild-learn defconfig
scripts/clang-tools/gen_compile_commands.py -d /tmp/kbuild-learn -o /tmp/kbuild-learn/compile_commands.json
# 然后在编辑器里把 clangd 的编译数据库路径指过去
```

> 另一种轻量方案：`coccinelle`（`scripts/coccinelle/`）用于批量语义搜索与重构，`sparse`（`make C=1`）用于静态分析。

### 7.2 从一个 syscall 顺藤摸瓜的标准流程

以「`io_uring` 的 `IORING_OP_OPENAT` 是怎么实现的」为例：

```bash
cd "$KSRC"
# 1. 找到 opcode 常量
grep -rn "IORING_OP_OPENAT" include/uapi/linux/io_uring.h

# 2. 找到 opcode 分发表
grep -rn "io_uring_opcode_supported\|struct io_issue_def io_issue_defs\|io_issue_defs\[" io_uring/*.c io_uring/*.h | head
sed -n '1,80p' io_uring/opdef.c

# 3. 找到具体实现文件
grep -rn "io_openat\b" io_uring/*.c | head
ls io_uring/            # 注意 7.x 里每个 opcode 一个文件：openclose.c, rw.c, fs.c ...

# 4. 从实现里看参数校验与对象生命周期
sed -n '1,80p' io_uring/openclose.c

# 5. 追它的注册/析构路径（UAF 通常在这里）
grep -rn "io_openat_prep\|io_openat_issue\|io_openat_cleanup\|io_clean_op" io_uring/openclose.c
```

四步通用化：

1. **查用户态 ABI**：`include/uapi/` 找常量、结构体、ioctl 号。
2. **查分发表**：`switch`、函数指针数组、`struct xxx_ops`。
3. **查实现**：具体 `.c`。
4. **查生命周期**：谁分配、谁释放、有没有引用计数（`kref`、`refcount_t`）、清理路径在哪。

第 4 步最容易漏，也最容易被攻击者利用。

### 7.3 如何从 Kconfig / Makefile 找到「这个文件到底会不会被编译」

内核里大量代码是条件编译的。读一个文件前，先确认它在你的配置下**是否真的被编译**：

```bash
cd "$KSRC"

# 1) 看这个目录的 Makefile（最关键）
cat mm/Makefile | head -30
#    形如：obj-$(CONFIG_SWAP) += swapfile.o

# 2) 看该配置项的定义与类型
grep -rn "^config SWAP$" -A 12 mm/Kconfig

# 3) 看你的 .config 里它是什么值
grep -n "CONFIG_SWAP" .config
#    =y 编进内核； =m 编成模块； 未出现 = 依赖不满足或用了默认

# 4) 或者直接看构建产物中是否存在对应 .o（构建后）
find /tmp/kbuild-learn -name 'swapfile.o'
```

阅读 Kbuild 语法的速查（完整规则见 `Documentation/kbuild/makefiles.rst`）：

| 写法 | 含义 |
| --- | --- |
| `obj-y += foo.o` | 无条件编进内核 |
| `obj-$(CONFIG_FOO) += foo.o` | `=y` 时编进内核，`=m` 时编成 `foo.ko` |
| `foo-y := a.o b.o` / `foo-$(CONFIG_X) += c.o` | 把多个 `.o` 链接成 `foo.o` |
| `ccflags-y += -DXYZ` | 只对当前目录的编译加标志 |
| `CFLAGS_foo.o += -Wno-...` | 只对单个文件生效 |
| `obj-$(CONFIG_A) += dir/` | 递归进入子目录 |

判断某个函数是否可达，最稳的方法是**同时看 Makefile 和 `.config`**，而不是靠猜：

```bash
# 一条命令：找出某个文件所属的目录、需要的配置项
grep -rn "read_write.o\|open.o" fs/Makefile
grep -n "CONFIG_.*=" .config | grep -i "fs" | head
```

### 7.4 三个高频陷阱

1. **`#ifdef` 迷宫**：同一个函数可能有多种实现（`CONFIG_SMP` / `!CONFIG_SMP`、`CONFIG_PREEMPT_RT` / `!CONFIG_PREEMPT_RT`）。读之前先看 `.config`。
2. **集合式编译单元**：`kernel/sched/build_policy.c`、`kernel/sched/build_utility.c` 里只有一堆 `#include "fair.c"` 之类。看到别慌，实际逻辑在同目录其他文件里。
3. **同名函数**：`foo_read()` 这类名字在树里可能有几十个。`grep -rn` 后一定要用文件路径与 `static` 关键字判断你找到的是哪一个。

### 8.1 `file` / `inode` / `dentry` 的关系（最常见的困惑）

```
用户态 fd (整数)
   |
   |  进程的 fd 表: struct files_struct -> fdtable -> struct file *
   v
struct file            一个"打开实例"。mkdir 两次打开同一文件 = 两个 struct file
   |   f_path (struct path)
   |     ├── .dentry ----+
   |     └── .mnt        |
   v                     v
                     struct dentry       路径中的一个"名字"。(/etc, /etc/passwd)
                         |  d_inode
                         v
                     struct inode        "文件实体"。硬链接共享同一个 inode
                         |  i_mapping
                         v
                     struct address_space  <- 页缓存
                         |  a_ops
                         v
                     struct address_space_operations  读/写页的具体实现
```

关键点：

- **`fd` → `file` 是「一对一」的一部分**：同一进程里 `dup()` 出的两个 fd 指向同一个 `struct file`（因此共享 `f_pos`）。
- **`file` → `inode` 是「多对一」**：同一文件的两次 `open()` 产生两个 `file`，共享一个 `inode`。
- **`inode` → `dentry` 是「一对多」**：硬链接的多个 dentry 指向同一 inode。
- **`inode` 才有页缓存**（`i_mapping`），`file` 没有。
- 引用计数：`file` 用 `f_count`（配合 `get_file()` / `fput()`）；`dentry` 用 `d_lockref`/`d_count`（`dget()` / `dput()`）；`inode` 用 `i_count`（`igrab()` / `iput()`）。**这三者的引用计数错配是最经典的内核漏洞来源之一。**

### 8.2 定位数据结构的命令

```bash
cd "$KSRC"
for s in task_struct mm_struct vm_area_struct file inode dentry page folio sk_buff file_operations; do
  printf '%-18s ' "$s"
  grep -rn "^struct $s {" --include=*.h include/ | head -1
done
```

看一个结构体的真实字段（避免被 `#ifdef` 迷惑时，可用 `pahole` 从调试信息里 dump 实际布局）：

