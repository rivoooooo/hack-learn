**目标**：把 README 里的目录清单与本地源码树一一对应，并确认版本号。

**前置**：`kernel/src/linux` 已克隆完成。

**步骤**

```bash
export KSRC=$(pwd)/kernel/src/linux
```

## 实验 02 🟢 编译一个最小内核

**目标**：从 `defconfig` 走到可引导的 `bzImage`，理解 Kbuild 的产物。

**前置**：装好 `build-essential bc bison flex libssl-dev libelf-dev libncurses-dev dwarves`（见 [README §4.1](../README.md#41-编译与调试工具debian--kali--ubuntu)）。

**步骤**

```bash
export KSRC=$(pwd)/kernel/src/linux
export OUT=/tmp/kbuild-learn

cd "$KSRC"
rm -rf "$OUT"

# 1) 配置：默认 + KVM 客户机片段
make O="$OUT" defconfig kvm_guest.config

# 2) 打开关键调试项（用命令行改配置）
"$KSRC/scripts/config" --file "$OUT/.config" \
  --enable DEBUG_INFO --enable KALLSYMS_ALL \
  --set-str LOCALVERSION "-learn"
make O="$OUT" olddefconfig

# 3) 编译（按内存调整 -j；16G 内存建议 8）
make O="$OUT" -j"$(nproc)" 2>&1 | tail -20

# 4) 检查产物
ls -lh "$OUT/vmlinux" "$OUT/arch/x86/boot/bzImage" "$OUT/System.map"
file "$OUT/vmlinux" "$OUT/arch/x86/boot/bzImage"
"$OUT/scripts/extract-ikconfig" "$OUT/arch/x86/boot/bzImage" | grep -E "CONFIG_LOCALVERSION|CONFIG_DEBUG_INFO"
```

**验证标准**

- `bzImage` 存在且 `file` 识别为 x86 boot sector
- `vmlinux` 是 ELF 且带调试信息（`file` 输出含 `not stripped`）
- `grep -c . "$OUT/System.map"` 大于 5 万
- 编译日志最后一行是 `Kernel: arch/x86/boot/bzImage is ready`

**延伸思考**

- `vmlinux` 和 `bzImage` 的体积差多少？为什么？
- `O=` 外部构建相比原地构建有什么好处？`.config` 在哪个目录？
- 为什么 `DEFCONFIG` 之后还要 `olddefconfig`？

## 实验 03 🟢 用 QEMU 启动自己的内核

**目标**：让自编译内核在 QEMU 里跑到用户态 shell。

**前置**：实验 02 成功；装了 `qemu-system-x86`、`busybox`（静态）、`cpio`。

**步骤**

```bash
export KSRC=$(pwd)/kernel/src/linux
export OUT=/tmp/kbuild-learn

# 1) 制作最小 initramfs（完整说明见 01 文档 §4.3）
rm -rf /tmp/initramfs && mkdir -p /tmp/initramfs/{bin,dev,proc,sys,tmp}
cp "$(command -v busybox)" /tmp/initramfs/bin/busybox
cd /tmp/initramfs && ./bin/busybox --install -s bin
cat > init <<'EOF'
#!/bin/busybox sh
/bin/busybox --install -s /bin
mount -t proc     none /proc
mount -t sysfs    none /sys
mount -t devtmpfs none /dev 2>/dev/null
echo "=== BOOTED ==="
uname -a
cat /proc/version
exec /bin/sh
EOF
chmod +x init
find . -print0 | cpio --null -ov --format=newc 2>/dev/null | gzip -9 > /tmp/initramfs.cpio.gz

# 2) 启动
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel "$OUT/arch/x86/boot/bzImage" \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init loglevel=7 panic=1" \
  -nographic -no-reboot
# 退出：Ctrl-a 然后按 x
```

**验证标准**

- 串口输出完整的启动日志，出现内核版本 `7.3.0-rc3-learn`（或你设置的 `LOCALVERSION`）
- 出现 `=== BOOTED ===` 与 BusyBox `sh` 提示符
- 在虚拟机里执行 `cat /proc/cmdline` 能看到你传的 `console=ttyS0 rdinit=/init ...`
- `ls /proc`、`ls /sys/kernel` 有内容（说明 procfs/sysfs 挂载成功）

**延伸思考**

- 如果不加 `console=ttyS0` 会看到什么？为什么？
- `rdinit=` 和 `init=` 有什么区别？（提示：`init/main.c` 的 `kernel_init()` 里读 `ramdisk_execute_command`）
- 为什么 `-nographic` 需要串口控制台？

## 实验 05 🟡 GDB 单步跟进一次 `write` 系统调用

**目标**：在 QEMU+GDB 下把用户态 `write` 一路断点跟到 `vfs_write`，验证 [02](02-源码结构与阅读方法.md#63-调用链实证一次-write-从用户态到设备) 的调用链。

**前置**：实验 03/04 成功；内核已 `make scripts_gdb`；装了 `gdb`。

**步骤**

```bash
export KSRC=$(pwd)/kernel/src/linux
export OUT=/tmp/kbuild-learn
cd "$KSRC" && make O="$OUT" scripts_gdb

# 终端 1：带 gdbstub 启动，CPU 冻结
qemu-system-x86_64 -m 2G -smp 2 \
  -kernel "$OUT/arch/x86/boot/bzImage" \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init" \
  -nographic -no-reboot -s -S
```

```bash
# 终端 2
cd "$KSRC"
gdb "$OUT/vmlinux"
```

在 GDB 里逐条执行：

```gdb
# 当前目录即内核源码树（$KSRC）
add-auto-load-safe-path .
set confirm off
target remote :1234
lx-symbols

break start_kernel
continue                    # 让内核跑到 C 入口

# 在 __x64_sys_write 上下断点（注意符号名带 __x64_ 前缀）
break __x64_sys_write
continue                    # 让内核启动完成，到 shell

# 回到 QEMU 终端，执行：echo hello > /tmp/x
# 这里应该命中 __x64_sys_write
bt                          # 看调用栈
info registers rax rdi rsi rdx   # 分别是 syscall 号、fd、buf、count
break ksys_write
continue
break vfs_write
continue
break new_sync_write
continue
bt
p *(struct file *)0            # 别乱试，用下面的
p file->f_op->write_iter
finish
```

若想验证用户态参数：在 `__x64_sys_write` 命中时，`p/x ((struct pt_regs *)$rdi)->di` 之类需要看 `x64_sys_call` 的传参约定；更简单的是在 `ksys_write` 里 `p fd`、`p count`。

**验证标准**

- `bt` 输出里能看到 `__x64_sys_write` → `ksys_write` → `vfs_write` → `new_sync_write` 这条链
- 能读到 `file->f_op->write_iter` 的函数指针值，并用 `p file->f_op->write_iter` 或 `info symbol` 解析出是哪个函数
- `lx-dmesg` 能打印内核日志（不依赖串口）

**延伸思考**

- 为什么 `__x64_sys_write` 这个符号带 `__x64_` 前缀？它在哪个文件里被生成？
- 断在 `vfs_write` 时，`p current->comm` 输出什么？`p current->pid` 呢？
- 对 `/dev/null` 和普通文件各做一次，哪一跳开始分叉？

## 实验 06 🟢 用 ftrace 跟踪一次 `open` 调用

**目标**：不写代码、不用 GDB，用 ftrace 拿到一次 `openat` 的完整内核函数调用图。

**前置**：实验 03 的内核启动成功；内核有 `CONFIG_FUNCTION_TRACER`（`defconfig` 默认有）。

**步骤**

在 QEMU 虚拟机里：

```sh
mount -t tracefs nodev /sys/kernel/tracing
T=/sys/kernel/tracing
cd $T

# 1) 看有什么跟踪器
cat available_tracers
wc -l available_filter_functions

# 2) 函数图跟踪：以 sys_openat 为根
echo nop > current_tracer
echo > trace
echo function_graph > current_tracer
echo __x64_sys_openat > set_graph_function
echo 1 > tracing_on
cat /etc/hostname        # 触发一次 open
echo 0 > tracing_on
cat trace | head -60

# 3) 事件跟踪：只看 syscall 边界，开销更小
echo nop > current_tracer
echo > trace
echo 1 > events/syscalls/sys_enter_openat/enable
echo 1 > tracing_on
ls / > /dev/null
echo 0 > tracing_on
grep -c openat trace
head -5 trace

# 4) 统计型：用 function profiler 数调用次数
echo 0 > tracing_on
echo > trace
echo 1 > function_profile_enabled
ls /etc > /dev/null
echo 0 > function_profile_enabled
head -20 trace_stat/function0
```

**验证标准**

- `function_graph` 输出里能看到从 `__x64_sys_openat` 往下若干层的缩进调用树，且带每个函数的耗时
- `events/syscalls/sys_enter_openat` 的输出里有你刚执行的 `ls` 的进程名与参数
- `trace_stat/function0` 里能看到被调用次数排序的函数表

**延伸思考**

- `function_graph` 与 `function` 跟踪器的开销差多少？为什么？
- 为什么 `trace` 文件读到一半可能不完整？（提示：它是环形缓冲区）
- `set_ftrace_filter='vfs_*'` 试试，看能过滤出多少函数。过滤能降低多少开销？

## 实验 07 🟡 用 bpftrace 统计 syscall 耗时分布

**目标**：用 eBPF 做一次真实性能观测。

**前置**：内核有 `CONFIG_BPF_SYSCALL=y`、`CONFIG_BPF_JIT=y`、`CONFIG_KPROBES=y`、`CONFIG_DEBUG_INFO_BTF=y`（`defconfig` + `kvm_guest.config` 未必全有，需要确认并补）；装了 `bpftrace`。

**步骤**

QEMU 里没有 bpftrace 的话，可以在宿主机的**当前内核**上先做（这是只读观测，风险低），但要清楚你观测的不是自编译内核。

```bash
# 0) 确认内核支持
grep -E 'CONFIG_(BPF_SYSCALL|BPF_JIT|KPROBES|DEBUG_INFO_BTF|FTRACE_SYSCALLS)' /boot/config-$(uname -r)
sudo bpftrace --info | head -20

# 1) 统计各进程的 openat 次数
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }' &
sleep 5; sudo kill %1

# 2) write 耗时直方图
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_write { @start[tid] = nsecs; }
tracepoint:syscalls:sys_exit_write  /@start[tid]/ {
    @ns = hist(nsecs - @start[tid]);
    delete(@start[tid]);
}'
# 在另一个终端制造负载：dd if=/dev/zero of=/tmp/x bs=4k count=10000

# 3) 按进程统计 syscall 次数
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_enter { @[comm] = count(); }'

# 4) 谁在调 sched_switch（看上下文切换大户）
sudo bpftrace -e 'tracepoint:sched:sched_switch { @[comm] = count(); }'

# 5) 抓一次耗时超过 1ms 的 read，并打印调用栈
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_read { @s[tid] = nsecs; }
tracepoint:syscalls:sys_exit_read /@s[tid] && nsecs - @s[tid] > 1000000/ {
    printf("%s pid=%d took %d us\n", comm, pid, (nsecs - @s[tid]) / 1000);
    print(kstack());
    delete(@s[tid]);
}'
```

**验证标准**

- `bpftrace --info` 的 `Kernel features` 里 eager 相关项为 yes
- 第 1 个脚本输出形如 `@[bash]: 123`、`@[ls]: 45` 的计数表
- 第 2 个脚本输出一个带 `[n, m)` 区间的直方图，且在 `dd` 负载下分布右移
- 第 5 个脚本能打印出内核调用栈

**延伸思考**

- `tracepoint:` 与 `kprobe:` 的稳定性差异是什么？为什么生产环境优先用 tracepoint？
- `@start[tid]` 用 `tid` 作键，如果同一个 tid 在 `sys_enter` 与 `sys_exit` 之间被复用会怎样？
- 为什么 Linux 5.8+ 要求 `CAP_BPF`+`CAP_PERFMON` 而不是直接 `CAP_SYS_ADMIN`？新能力拆分解决了什么问题？

## 实验 08 🟡 用 KASAN 触发并读懂一次越界报告

**目标**：故意写一个有越界 bug 的模块，用 KASAN 抓出它，并学会读报告定位到源码行。

**前置**：编译一个带 KASAN 的内核（见下）；[03](03-内核模块开发.md) 的模块能正常编译加载。

**步骤**

```bash
export KSRC=$(pwd)/kernel/src/linux
export OUT=/tmp/kbuild-kasan

# 1) 编译 KASAN 内核
cd "$KSRC"
rm -rf "$OUT"
make O="$OUT" defconfig kvm_guest.config
"$KSRC/scripts/config" --file "$OUT/.config" \
  --enable KASAN --enable KASAN_GENERIC --enable KASAN_INLINE \
  --enable DEBUG_INFO --enable KALLSYMS_ALL \
  --set-str LOCALVERSION "-kasan"
make O="$OUT" olddefconfig
make O="$OUT" -j"$(nproc)"

# 2) 写一个有 bug 的模块
mkdir -p $LAB/kasan-demo && cd $LAB/kasan-demo
cat > kasan-demo.c <<'EOF'
// SPDX-License-Identifier: GPL-2.0
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kernel.h>
#include <linux/init.h>
#include <linux/slab.h>

#define N 16

static char *buf;

static int __init bad_init(void)
{
	int i;

	buf = kmalloc(N, GFP_KERNEL);
	if (!buf)
		return -ENOMEM;

	/* BUG：写入下标 0..N（应为 0..N-1），最后一次越界 1 字节 */
	for (i = 0; i <= N; i++)      /* 注意 <= */
		buf[i] = 'A' + (i % 26);

	pr_info("wrote N+1 bytes into a %d-byte buffer\n", N);
	return 0;
}

static void __exit bad_exit(void)
{
	kfree(buf);
}
module_init(bad_init);
module_exit(bad_exit);
MODULE_LICENSE("GPL");
EOF
cat > Makefile <<'EOF'
obj-m := kasan-demo.o
# KSRC 指向内核源码树（见文档开头的 export KSRC）
KDIR ?= $(KSRC)
PWD  := $(shell pwd)
all:
	$(MAKE) -C $(KDIR) O=/tmp/kbuild-kasan M=$(PWD) modules
clean:
	$(MAKE) -C $(KDIR) O=/tmp/kbuild-kasan M=$(PWD) clean
EOF
make

# 3) 用 KASAN 内核启动 QEMU（加 9p 以便在虚拟机里取模块）
qemu-system-x86_64 -m 2G -smp 2 \
  -kernel "$OUT/arch/x86/boot/bzImage" \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init kasan.fault=report kasan_multi_shot" \
  -nographic -no-reboot \
  -virtfs local,path=$HOME,id=host0,security_model=none,mount_tag=host0
```

虚拟机里：

```sh
mkdir -p /mnt/host
mount -t 9p -o trans=virtio,version=9p2000.L host0 /mnt/host
insmod /mnt/host/kmod-lab/kasan-demo/kasan-demo.ko
dmesg | tail -60
```

**验证标准**

- `dmesg` 里出现 `BUG: KASAN: slab-out-of-bounds in bad_init` 类似的报告
- 报告里有 `Write of size 1 at addr ...` 与 `Allocated by task` 段
- 能按下面的方法把报告位置换算回源码行

```bash
# 在宿主机上
cd $LAB/kasan-demo
objdump -dS kasan-demo.ko | grep -A 60 '<bad_init>:'
# 找到报告里 RIP 的偏移对应的指令
addr2line -e kasan-demo.ko -f -i <偏移地址>
# 或
gdb kasan-demo.ko -batch -ex 'list *(bad_init+0xXX)'
```

**延伸思考**

- 报告里 `Allocated by task` 的调用栈告诉了你什么？如果这是 UAF，你需要哪一段信息？
- `kasan.fault=panic` 与 `kasan.fault=report` 各适合什么场景？
- KASAN 的内存开销（约 1/8 内存）与性能开销（约 3 倍减速）能接受吗？生产环境用什么替代？（提示：KFENCE）
- 如果 bug 是 UAF 而不是越界，报告会变成什么形状？把 `kfree(buf)` 提到写之前试试。

```c
// SPDX-License-Identifier: GPL-2.0
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/module.h>
#include <linux/kthread.h>
#include <linux/mutex.h>
#include <linux/delay.h>
#include <linux/init.h>

static DEFINE_MUTEX(lock_a);
static DEFINE_MUTEX(lock_b);
static struct task_struct *t1, *t2;

static int worker1(void *arg)
{
	while (!kthread_should_stop()) {
		mutex_lock(&lock_a);      /* A -> B */
		msleep(1);
		mutex_lock(&lock_b);
		mutex_unlock(&lock_b);
		mutex_unlock(&lock_a);
	}
	return 0;
}

static int worker2(void *arg)
{
	while (!kthread_should_stop()) {
		mutex_lock(&lock_b);      /* B -> A  <-- 与 worker1 相反 */
		msleep(1);
		mutex_lock(&lock_a);
		mutex_unlock(&lock_a);
		mutex_unlock(&lock_b);
	}
	return 0;
}

static int __init dl_init(void)
{
	t1 = kthread_run(worker1, NULL, "dl_worker1");
	t2 = kthread_run(worker2, NULL, "dl_worker2");
	if (IS_ERR(t1) || IS_ERR(t2)) {
		if (!IS_ERR(t1)) kthread_stop(t1);
		if (!IS_ERR(t2)) kthread_stop(t2);
		return -ENOMEM;
	}
	return 0;
}

static void __exit dl_exit(void)
{
	kthread_stop(t1);
	kthread_stop(t2);
}
module_init(dl_init);
module_exit(dl_exit);
MODULE_LICENSE("GPL");
```

**验证标准**

- 加载后不久 `dmesg` 出现 `possible circular locking dependency detected`

```bash
# ./FlameGraph/stackcollapse-perf.pl /tmp/out.perf | ./FlameGraph/flamegraph.pl > /tmp/fg.svg

# 看某进程的系统调用开销
sudo perf stat -e 'syscalls:sys_enter_*' -a -- sleep 1 2>&1 | head

# 内核 vs 用户态占比
sudo perf stat -a -- sleep 3
```

**验证标准**

- `perf report` 里能看到内核符号（不是一列 `[unknown]`），说明符号解析正常
- 能指出 top 3 的 CPU 消耗函数，并说出它们属于哪个子系统
- `perf stat` 输出的 `cpu-clock` 里 `sys`/`user` 占比可解释

**延伸思考**

- `perf record` 的 `-g` 会产生多大开销？采样频率 `-F` 怎么选？

## 实验 18 🔴 用 GDB 调试一个死机的内核

**目标**：让内核真的死锁/panic，然后用 GDB 连上去找出原因。

**前置**：实验 05 完成。

**步骤**

```bash
export OUT=/tmp/kbuild-learn
# 终端 1
qemu-system-x86_64 -m 2G -smp 2 \
  -kernel "$OUT/arch/x86/boot/bzImage" \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init" \
  -nographic -no-reboot -s -S
# 注意：不加 panic=1，让内核保持在死锁状态便于连 GDB
```

```bash
# 终端 2
cd "$KSRC"
gdb "$OUT/vmlinux"
```

```gdb
# 当前目录即内核源码树（$KSRC）
add-auto-load-safe-path .
set confirm off
target remote :1234
lx-symbols
continue
```

虚拟机里制造死锁（加载实验 15 的模块，假设它是未修复版本）：

```sh
insmod /mnt/host/kmod-lab/lockdep-demo/dl-demo.ko
# 系统逐渐失去响应
```

回到 GDB，中断执行（`Ctrl-C`）：

```gdb
interrupt
info threads                       # QEMU gdbstub 下通常只有一个"线程"（vCPU）
# 每个 vCPU 是独立的 gdb thread，用下面命令切换
thread apply all bt                # 打印所有 vCPU 的调用栈

# 更实用的：用 scripts/gdb 的 lx-ps 看进程状态
lx-ps

# 看某个卡住的线程
p *(struct task_struct *)<地址>
p <地址>->comm
p <地址>->__state
p <地址>->stack
```

也可以在内核里主动触发信息输出（**不用 GDB 的更简单办法**）：

```sh
echo w > /proc/sysrq-trigger      # 打印所有 D 状态进程的栈
echo l > /proc/sysrq-trigger      # 打印所有 CPU 的栈
echo t > /proc/sysrq-trigger      # 打印所有进程的栈
```

**验证标准**

- `thread apply all bt` 或 `echo w > /proc/sysrq-trigger` 输出里，能看到两个 kthread 分别卡在 `__mutex_lock` 上，且各自已经持有对方需要的锁
- 能说出「A 持有 lock_a 等 lock_b，B 持有 lock_b 等 lock_a」
- 能从栈帧里定位到是模块代码（`[dl_demo]`）而不是内核自身

**延伸思考**

- gdbstub 的 `thread` 与内核里的 `task_struct` 不是一回事，为什么？
- `lx-ps` 是怎么从内核内存里遍历出进程列表的？（读 `scripts/gdb/linux/tasks.py`）
- 如果内核已经完全无响应，串口也没输出，还能做什么？（提示：NMI watchdog、硬件调试器、QEMU monitor 的 `info registers`）

```bash
export KSRC=$(pwd)/kernel/src/linux
```

## 实验 20 🔴 用 syzkaller 跑一个有 bug 的驱动

**目标**：搭起覆盖率引导的模糊测试环境，并让它抓到你自己埋的 bug。

**前置**：装好 Go 1.23+、`debootstrap`；能编译带 KCOV+KASAN 的内核；磁盘空间 ≥ 40 GB。**在隔离的虚拟机/独立机器上做**（见 [04 §6.1](04-内核安全与攻防.md#61-搭建研究环境隔离优先)）。

**步骤**

```bash
# ---------- 1) 准备带 KCOV + KASAN 的内核 ----------
export KSRC=$(pwd)/kernel/src/linux
export OUT=/tmp/kbuild-syz
cd "$KSRC"
rm -rf "$OUT"
make O="$OUT" defconfig kvm_guest.config

"$KSRC/scripts/config" --file "$OUT/.config" \
  --enable KCOV --enable KCOV_INSTRUMENT_ALL --enable KCOV_ENABLE_COMPARISONS \
  --enable KASAN --enable KASAN_INLINE \
  --enable DEBUG_INFO --enable DEBUG_INFO_DWARF_TOOLCHAIN_DEFAULT \
  --enable KALLSYMS --enable KALLSYMS_ALL \
  --enable DEBUG_FS --enable CONFIGFS_FS --enable SECURITYFS \
  --enable PROVE_LOCKING --enable DEBUG_ATOMIC_SLEEP --enable DEBUG_VM \
  --enable HARDENED_USERCOPY --enable FORTIFY_SOURCE \
  --enable FAULT_INJECTION --enable FAULT_INJECTION_DEBUG_FS \
  --enable FAILSLAB --enable FAIL_PAGE_ALLOC \
  --disable RANDOMIZE_BASE
make O="$OUT" olddefconfig
make O="$OUT" -j"$(nproc)"

# 确认关键项
grep -E 'CONFIG_(KCOV|KASAN|DEBUG_INFO|RANDOMIZE_BASE)' "$OUT/.config"

# ---------- 2) 准备 syzkaller ----------
# 用官方建议的 Go 版本（以 syzkaller 仓库当前 README 为准）
git clone https://github.com/google/syzkaller
cd syzkaller
make -j"$(nproc)"
ls bin/

# ---------- 3) 造镜像 ----------
sudo apt install -y debootstrap
./tools/create-image.sh --arch amd64 --distribution bookworm
ls -lh bullseye.img 2>/dev/null || ls -lh *.img

# ---------- 4) 埋一个可被模糊测试触达的 bug ----------
#    做法：写一个字符设备模块，暴露 ioctl，
#    在 ioctl 里对用户提供的长度不做上界检查（越界读）。
#    参考 03 文档 §5 的 mychardev.c，加一个:
#      case 0x1234: {
#          struct { u32 len; char *buf; } req;
#          copy_from_user(&req, (void __user *)arg, sizeof(req));
#          char tmp[64];
#          /* BUG: 未检查 req.len <= sizeof(tmp) */
#          copy_from_user(tmp, req.buf, req.len);
#          ...
#      }
#    然后写 sys/linux/dev_mychardev.txt 描述这个 ioctl，
#    并在 manager 配置里用 enable_syscalls 限定只跑它。

# ---------- 5) 启动 syz-manager ----------
mkdir -p /tmp/syz-workdir
cat > /tmp/syz.cfg <<'EOF'
{
  "target": "linux/amd64",
  "http": "127.0.0.1:56741",
  "workdir": "/tmp/syz-workdir",
  "kernel_obj": "/tmp/kbuild-syz",
  "image": "/home/rivo/syzkaller/bullseye.img",
  "sshkey": "/home/rivo/syzkaller/bullseye.id_rsa",
  "syzkaller": "/home/rivo/syzkaller",
  "procs": 2,
  "type": "qemu",
  "vm": {
    "count": 1,
    "kernel": "/tmp/kbuild-syz/arch/x86/boot/bzImage",
    "cpu": 2,
    "mem": 2048,
    "qemu_args": "-enable-kvm"
  }
}
EOF
./bin/syz-manager -config /tmp/syz.cfg
# 浏览器打开 http://127.0.0.1:56741
```

**验证标准**

- `syz-manager` 启动后，Web UI 的 coverage 曲线持续上升（说明 KCOV 生效）
- VM 能被拉起（`syz-manager` 日志无 SSH 报错）
- 在你的 ioctl 被触达后，Web UI 出现 `KASAN: slab-out-of-bounds` 类崩溃，且能下载到 `.syz` 复现程序与完整报告
- 用 `syz-execprog` 手工重放该 `.syz` 文件，能稳定复现：

```bash
./bin/syz-execprog -executor ./bin/syz-executor -repeat=3 -procs=1 -cover=1 \
  /tmp/crash-xxxx.syz
```

**延伸思考**

- 为什么必须关掉 `CONFIG_RANDOMIZE_BASE`？（KASLR 会让符号地址在每次启动时不同，崩溃无法归并）
- `sandbox=none` / `sandbox=namespace` / `sandbox=setuid` 的区别与安全影响是什么？
- 覆盖率引导与纯随机的差别有多大？（可以试试临时把 KCOV 关掉对比 crash 发现速度）
- syzkaller 的描述文件（`sys/linux/*.txt`）为什么要手写？它相比「随机 ioctl 号」有什么优势？
- 如果一个崩溃无法复现，可能的原因有哪些？（时序、状态依赖、需要特定的初始化序列）
- 如果你在**别人的系统**上发现了可提权的崩溃，正确做法是什么？（见 [04 §6.3](04-内核安全与攻防.md#63-上游报告流程)）
