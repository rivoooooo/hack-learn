## 1. 为什么内核是最高价值目标

用户态的安全边界（进程隔离、文件权限、容器、SELinux/AppArmor、seccomp）**全部由内核强制执行**。一旦在内核里获得任意代码执行，这些机制全部失效：

| 用户态防线 | 被内核提权后为什么失效 |
| --- | --- |
| 进程地址空间隔离 | 内核可以任意读写任何进程的内存（`ptrace` 做不到的它也能做） |
| 文件权限 / UID 模型 | 直接改 `current->cred`（`struct cred` 在 `include/linux/cred.h`），或改 inode 的 mode |
| 容器（namespace + cgroup） | 从宿主机内核视角看 namespace 只是一组指针；改 `task_struct->nsproxy` 即逃逸 |
| seccomp 过滤器 | 过滤器在 `kernel/seccomp.c` 里判断，改掉 `task_struct->seccomp` 或直接走未过滤的路径 |
| SELinux / AppArmor | LSM 钩子的返回值由内核决定；`task_struct->security` 直接可改 |
| 内核模块签名 / lockdown | 已经在内核里了，可以直接改 `module_sig_check()` 的判断 |
| 磁盘加密 / kTLS | 密钥在内存里，且解密点在内核内 |

另外两个让内核特别「值钱」的性质：

1. **ring0 是全系统的单点。** 一个内核 bug 影响同物理机上的所有容器、所有用户、所有虚拟机（除非有独立的 hypervisor 边界）。
2. **内核是唯一直接解析「不可信输入」且运行在最高特权级的组件。** 文件系统镜像、网络包、USB 描述符、`ioctl` 参数、`io_uring` SQE —— 这些都由不可信的一方构造，却由内核解析。

反向看：这也是为什么内核的防御机制设计得如此激进 —— 攻击面太大了。

## 2. 攻击面分类

攻击面 = 「不可信方可以控制的数据进入内核的入口」。逐类列出并给出真实入口位置。

### 2.1 系统调用接口（最大的一类）

约 422 个 x86-64 系统调用（实测 `arch/x86/entry/syscalls/syscall_64.tbl` 中除 x32 外 422 条，最大号 472），全树有 799 处 `SYSCALL_DEFINE*` 定义。

| 子类 | 典型入口 | 危险点 |
| --- | --- | --- |
| 内存管理 | `mmap`、`mprotect`、`mremap`、`madvise`、`process_vm_readv/writev`、`userfaultfd` | 权限位（W^X）检查、VMA 边界、`userfaultfd` 带来的竞态窗口 |
| 进程/线程 | `clone`、`clone3`、`ptrace`、`execve`、`pidfd_*` | 参数结构体解析、标志组合校验、`ptrace` 的 PTRACE_MODE 检查 |
| 文件系统 | `openat2`、`renameat2`、`linkat`、`mount`、`fsopen`/`fsconfig`、`io_uring` 全部 opcode | 路径解析竞态、`O_PATH` 语义、mount 命名空间 |
| 网络 | `socket`、`setsockopt`、`sendmsg`/`recvmsg`、`bpf`、`ioctl(SIOC*)` | 协议栈解析不可信报文、`msghdr` 的 `iovec` 数组 |
| IPC | `shmget`、`msgrcv`、`semctl`、`memfd_create` | 共享内存的权限与生命周期 |
| 时间 | `timer_create`、`clock_settime`、`timerfd_*` | 结构体拷贝与标志校验 |
| 信号 | `rt_sigaction`、`sigaltstack`、`rt_sigtimedwait` | 老架构的 sigreturn 相关处理 |
| 设备 | `ioctl`（数量极多） | 见 §2.2 |
| 安全/审计 | `keyctl`、`add_key`、`seccomp`、`perf_event_open`、`bpf` | 高权限特性的检查遗漏 |
| 虚拟化 | `kvm_*` ioctl、`/dev/vhost-*` | 见 §2.2 |

**子系统聚合入口**（参数空间巨大、历史上 bug 密度高）：`io_uring/`、`bpf`（`kernel/bpf/syscall.c`）、`netlink`（`net/netfilter/nf_tables_api.c`、`net/ethtool/`、`net/sched/`）、`perf`（`kernel/events/core.c`）、`kvm`。

### 2.2 ioctl 与设备文件

`ioctl` 是「一个 syscall，实现无数子命令」的机制。每个驱动的 `unlocked_ioctl` 自己解析 `cmd` 与 `arg`。

```
用户态 ioctl(fd, cmd, arg)
  fs/ioctl.c          SYSCALL_DEFINE3(ioctl) -> vfs_ioctl() -> file->f_op->unlocked_ioctl()
  每个驱动的实现       自己 switch(cmd)，用 copy_from_user 取结构体
```

危险点：

- `arg` 是**用户态地址**。直接解引用 = 内核读任意地址；`copy_from_user` 没检查长度 = 栈溢出。
- `cmd` 的编码（`_IO`/`_IOR`/`_IOW`）里的**大小字段不可信**。必须在代码里校验「大小字段 == 结构体实际大小」。
- 老式 `.ioctl`（不带 `unlocked_`）与 `.compat_ioctl` 是历史上的重灾区；现代驱动应只用 `.unlocked_ioctl` 并正确处理复合对齐。
- 结构体里有**长度 + 指针**的组合时，长度与指针指向的实际区域必须一致，且**读取期间要固定住用户内存**（否则 `userfaultfd` 可以中途替换内容）。

设备文件子系统（每个都是独立的攻击面）：`/dev/dri/*`（GPU 驱动）、`/dev/kvm`、`/dev/vhost-net`、`/dev/vfio/*`、`/dev/fuse`、`/dev/input/event*`、`/dev/tty*`、`/dev/nvme*`、`/dev/loop*`、`/dev/net/tun`、`/proc/*`、`/sys/*`、`/dev/snd/*`。

### 2.3 文件系统解析器

内核要解析不可信的磁盘映像（U 盘、ISO、容器镜像、挂载的远程共享）：

| 解析器 | 位置 |
| --- | --- |
| ELF | `fs/binfmt_elf.c` |
| Squashfs | `fs/squashfs/` |
| ext4 | `fs/ext4/`（尤其 `super.c`、`extents.c`） |
| XFS | `fs/xfs/` |
| Btrfs | `fs/btrfs/` |
| FAT/exFAT/NTFS | `fs/fat/`、`fs/exfat/`、`fs/smb/` |
| ISO9660 | `fs/isofs/` |
| UDF | `fs/udf/` |
| f2fs / erofs | `fs/f2fs/`、`fs/erofs/` |
| 网络文件系统 | `fs/nfs/`、`fs/ceph/`、`fs/cifs`→`fs/smb/` |
| FUSE | `fs/fuse/`（用户态文件系统，直接暴露给非特权用户） |
| 内核内自解压 | `lib/decompress*.c`、`fs/squashfs/decompressor*.c` |

结构性危险点：**元数据声明的长度/深度/数量与实际数据不符**（越界读、整数溢出）、递归深度不受限（栈溢出）、自引用结构（无限循环）、跨区域指针（指向未映射区域）。

### 2.4 网络协议栈

外部可完全控制数据包内容。入口自下而上：

```
网卡驱动 -> NAPI -> netif_receive_skb()  (net/core/dev.c)
```

### 2.5 eBPF

eBPF 的特殊性在于：**它允许非特权（或仅需 `CAP_BPF`）用户把一门图灵完备的受限语言加载到内核里执行**。这等于在运行时可编程地扩展内核，验证器（`kernel/bpf/verifier.c`）成了唯一的安全边界。

入口与子系统：

| 位置 | 说明 |
| --- | --- |
| `kernel/bpf/syscall.c` | `bpf()` 系统调用：`BPF_PROG_LOAD`、`BPF_MAP_CREATE` 等 |
| `kernel/bpf/verifier.c` | 验证器。**这是 eBPF 安全的核心，也是 bug 最集中的地方** |
| `kernel/bpf/*map*.c` | 各种 map 类型（hash、array、ringbuf、bloom、arena…） |
| `kernel/bpf/btf.c` | BTF 解析（类型信息本身也是不可信输入） |
| `arch/x86/net/bpf_jit_comp.c` | JIT 编译器（把 eBPF 字节码翻译成 x86 机器码） |
| `net/core/filter.c` | 网络相关 helper |
| `kernel/trace/bpf_trace.c` | 跟踪类程序 |

结构性危险点：验证器的状态跟踪不完备（漏掉某条路径）、JIT 的立即数/偏移编码、map 生命周期与程序引用（未清理的 map 引用）、`bpf_probe_read_*` 系列的边界、speculative execution 相关的 map 索引。

相关文档：`Documentation/bpf/`（`bpf_design_QA.rst`、`kfuncs.rst`、`btf.rst`、`libbpf/`）。

## 3. 经典漏洞类型

本节只做**结构性**说明与代码模式识别训练，不给出可用于攻击具体系统的完整利用步骤。所有示例都是**故意写错的模式**，用来训练你在真实代码里认出它们。

> 阅读建议：打开 [02-源码结构与阅读方法](02-源码结构与阅读方法.md) 里的调用链，按下面的模式去 `grep` 真实代码。看到熟悉的形状就去核对边界条件。

### 3.1 越界读写（OOB read / write）

**结构**：计算出来的访问范围超出了实际分配的对象。

常见成因：

```c
/* 模式 A：用户提供的长度未校验 */
struct req {
    u32 len;
    char data[];
};
struct req *r = kmalloc(sizeof(*r) + len, GFP_KERNEL);
copy_from_user(r, uarg, sizeof(*r) + len);
/* 若 uarg->len > len，则 r->data 之外的读越界；
   若后续用 r->len 去遍历 r->data，则越界读。修复：以实际拷贝量为准。 */

/* 模式 B：索引来自用户且未做上界检查 */
u32 idx;
get_user(idx, &uarg->idx);
return table[idx].value;          /* idx 可达 0xffffffff -> 越界 */

/* 模式 C：整数溢出导致分配过小 */
u32 count, size;
/* 校验写成乘法形式，溢出后 count*size 变小 */
buf = kmalloc(count * size, GFP_KERNEL);   /* 应改为 kcalloc() 或 check_mul_overflow() */
```

识别信号：

| 信号 | 说明 |
| --- | --- |
| `kmalloc(a * b)` / `kmalloc(a + b)` | 乘法/加法溢出。正确写法是 `kcalloc()`、`kmalloc_array()`、`struct_size()`、`check_*_overflow()` |
| `copy_from_user(dst, src, user_len)` 后直接用 `user_len` 遍历 | 长度未经上界校验 |
| 数组下标来自用户态字段，附近没有 `if (idx >= n) return -EINVAL;` | 缺边界检查 |
| 循环的终止条件用了用户提供的字段 | 可能死循环或越界 |
| 长度字段与缓冲区指针来自不同来源 | 两者可能不匹配 |

**内核侧的防御**：`CONFIG_HARDENED_USERCOPY`（`security/Kconfig.hardening:221`）在 `copy_*_user` 时用 `check_object_size()` 检查对象边界（实现 `mm/usercopy.c`）；`CONFIG_FORTIFY_SOURCE`（`:214`）在编译期插入 `__builtin_object_size()` 检查；KASAN 在运行期抓。三层叠起来能在很多情况下把「静默越界」变成「明确报错」。

### 3.2 释放后使用（UAF, use-after-free）

**结构**：对象被释放后，仍有指针可以访问它。

最常见的三种形状：

```c
/* 形状 1：错误路径漏掉引用计数 / 提前释放 */
obj = lookup(id);           /* 返回带引用的对象 */
if (!obj)
    return -ENOENT;
kfree(obj);                 /* 提前释放 */
use(obj->field);            /* UAF */

/* 形状 2：文件描述符 / 句柄的生命周期与底层对象错配 */
static long my_ioctl(struct file *f, unsigned int cmd, unsigned long arg)
{
    struct ctx *c = f->private_data;
    if (cmd == MY_DESTROY)
        kfree(c);                    /* 释放了，但 f->private_data 仍指向它 */
    return c->something;             /* 同一 fd 再次 ioctl -> UAF */
}
/* 正确：要么在 destroy 时同时失效 fd，要么靠引用计数由 release 统一释放 */

/* 形状 3：并发下的检查-使用间隙（TOCTOU） */
if (refcount_read(&obj->refs) == 1) {
    /* 另一个 CPU 在这里 refcount_dec_and_test -> kfree(obj) */
    obj->field = 1;              /* UAF */
}
/* 正确：拿锁，或用 refcount_inc_not_zero() 原子地"抢引用" */
```

识别信号：

| 信号 | 说明 |
| --- | --- |
| `kfree()` / `free_x()` 之后函数没立即返回 | 危险 |
| `kfree()` 了但结构体里的指针没置 NULL，也没 `list_del()` | 悬空指针 + 悬空链表节点 |
| 手工管理 `atomic_t` 引用计数 | 应改 `refcount_t`（能检测下溢） |
| 同一对象有两套所有权（fd 表 + 全局链表） | 双重释放 / UAF 的高发形状 |
| 异步回调（workqueue / timer / tasklet / RCU callback）持有对象指针，但对象可能已被释放 | 必须在取消回调后再释放，或用 `refcount` |
| `release()` 里先释放资源再 `kfree()` 容器 | 顺序错 |
| 一个 `ioctl` 的 `cmd` 里既有「创建」又有「销毁」 | 状态机容易不一致 |

**内核侧的防御**：KASAN 的 quarantine（被释放的对象不立即复用，延后一段时间）；`CONFIG_SLAB_FREELIST_HARDENED`（`mm/Kconfig:208`）；`CONFIG_INIT_ON_FREE_DEFAULT_ON`（`security/Kconfig.hardening:172`，释放时清零）；`CONFIG_DEBUG_OBJECTS`（`Documentation/core-api/debug-objects.rst`）；`refcount_t`。

### 3.3 类型混淆（type confusion）

**结构**：把 A 类型的对象当成 B 类型来访问。

```c
/* 模式 A：union / 泛型容器里没有区分类型标签 */
struct node {
    enum kind kind;
    union {
        struct file  *f;
        struct inode *i;
    };
};
/* 若读取路径没校验 kind 就用 u.i，而实际存的是 f，就是类型混淆 */

/* 模式 B：void * / 无类型句柄 */
void *handle = lookup(id);       /* 可能返回两种不同的结构体 */
((struct type_a *)handle)->field_a;   /* 没判断到底是哪种 */

/* 模式 C：结构体大小不同但复用了同一个分配与释放路径 */
```

识别信号：

| 信号 | 说明 |
| --- | --- |
| `(struct foo *)` 强制转换附近没有类型/tag 校验 | 危险 |
| `union` 的成员访问前没有 `switch (kind)` | 危险 |
| `void *private_data` 在多个 `file_operations` 回调里被转成不同结构体 | 必须保证所有路径都用同一种 |
| 一个 id 空间可以指向多种对象（如 `io_uring` 的注册表） | 需要显式类型字段 |

**内核侧的防御**：`CONFIG_RANDSTRUCT`（`security/Kconfig.hardening:336`，随机化结构体字段顺序，让「按固定偏移当成另一种类型」失败）；`CONFIG_CFI_CLANG`（`arch/Kconfig:970`，控制流完整性，让「跳到类型不匹配的函数」失败）；`CONFIG_X86_KERNEL_IBT`（`arch/x86/Kconfig:1746`，CET 间接分支跟踪）。

### 3.4 整数溢出与符号问题

**结构**：算术结果超出类型范围，或在有符号/无符号之间意外转换。

```c
/* 无符号回绕 */
u32 total = count * sizeof(struct item);   /* count = 0x40000001 -> total 变小 */
buf = kmalloc(total, GFP_KERNEL);          /* 分配了远小于需要的空间 */

u32 len = user_len + sizeof(struct hdr);   /* user_len = 0xfffffff0 -> len = 0x10 */
if (len > MAX) return -EINVAL;             /* 检查通过，但实际需要 4GB+ */

/* 有符号/无符号混用 */
int n;
get_user(n, &uarg->count);
if (n < 0) return -EINVAL;
size_t sz = n;                             /* 这里没问题 */
/* 但若写成：if (n > MAX) ... 后再赋值给 unsigned，n 为负时会变成巨大值 */

/* 截断 */
long big = ...;        /* 可能 > 4GB */
u32 small = big;       /* 静默截断 */
```

识别信号：

| 信号 | 说明 |
| --- | --- |
| 分配大小由一个或多个用户可控值经过算术得出 | 必须用溢出安全的 API |
| 检查在算术之后做 | 应改为「先检查，再算术」或用 `check_add_overflow()` / `check_mul_overflow()`（`include/linux/overflow.h`） |
| `int` ↔ `unsigned` ↔ `size_t` 之间来回赋值 | 检查每个转换点 |
| 用 `-1` 等负值作为「特殊值」 | 转成无符号后语义完全不同 |

安全写法对照：

```c
/* 不安全 */                          /* 安全 */
kmalloc(n * m, GFP_KERNEL);           kmalloc_array(n, m, GFP_KERNEL);
kmalloc(sizeof(*p) + n, GFP_KERNEL);  kmalloc(struct_size(p, member, n), GFP_KERNEL);
kmalloc(n * sizeof(*p), GFP_KERNEL);  kmalloc_array(n, sizeof(*p), GFP_KERNEL);
if (a + b > LIMIT) ...                if (check_add_overflow(a, b, &r) || r > LIMIT) ...
```

### 3.5 竞态条件（race condition / TOCTOU）

**结构**：两个执行者之间的时间窗口里，共享状态被改变。

内核里竞态的后果不只是数据不一致，常见的是**把上面四类漏洞「放大」**：竞态导致的 UAF、竞态导致的越界。

```c
/* 形状 1：检查与使用之间存在窗口（TOCTOU） */
if (access_ok(buf, len)) {          /* 检查 */
    /* ... 攻击者用 userfaultfd 在缺页处挂住，另一个线程修改映射 ... */
    copy_from_user(dst, buf, len);  /* 使用 */
}
/* 正确：copy_from_user 内部会重新做访问检查，不要依赖外层 access_ok */

/* 形状 2：符号检查与解引用分离 */
if (dir->type == DIR_ENTRY) {
    /* 另一个线程 mprotect/unlink/改名 */
    read(dir->special_ptr);          /* 类型已被改 */
}

/* 形状 3：引用计数「先看再抢」 */
if (obj->refcount == 1) {            /* 非原子读 */
    use(obj);                        /* 已被另一 CPU 释放 */
}
/* 正确：refcount_inc_not_zero() / 拿锁 / RCU */

/* 形状 4：fd 表操作与其他线程的 close 竞赛 */
fd = ...;
/* 另一线程 close(fd) 并复用同一个编号 */
syscall_using_fd(fd);                /* 操作了错误的文件 */
/* 正确：用 fdget() 一次性拿到文件引用（vfs 层已经这么做） */

/* 形状 5：只在部分路径加锁 */
static int update(...)
{
    mutex_lock(&l);
    obj->a = 1;
    mutex_unlock(&l);
    obj->b = 2;      /* 这里没锁 —— 与读者竞态 */
}
```

识别信号：

| 信号 | 说明 |
| --- | --- |
| 全局/静态可变变量在多个函数里被读写，但没看到锁 | 需要确认是否真的只有单线程路径 |
| 检查用的值和后续使用的值来自两次独立读取 | 中间可能被改 |
| 锁的获取在某个 `if` 分支里，释放却无条件执行（或反之） | 必然的锁不平衡 |
| 函数名里有 `_try`、`_nowait`、`_async` | 很可能存在无法立即完成的状态 |
| 中断处理函数也在访问同一数据，但进程上下文侧只用 `spin_lock()` | 必须用 `spin_lock_irqsave()` |
| `userfaultfd`、`FUSE`、`/proc/self/mem` 出现在触达路径上 | 攻击者能精确控制时序窗口 |
| 用 `schedule_work()` / `timer` / `irq_work` 做「延迟处理」 | 对象生命周期必须用引用计数保护 |

**内核侧的防御**：KCSAN（`Documentation/dev-tools/kcsan.rst`，主动检测数据竞争）；lockdep（`kernel/locking/lockdep.c`，锁序与上下文违规）；`CONFIG_DEBUG_ATOMIC_SLEEP`（在原子上下文睡眠时报警）；`CONFIG_PROVE_RCU`。

### 3.6 其他值得认识的结构性问题

| 类型 | 结构 |
| --- | --- |
| 未初始化内存读取 | `kmalloc()` 不置零 + 只初始化了部分字段 + 整个结构体被 `copy_to_user()` 出去（可能泄露内核指针或旧数据）。防御：`CONFIG_INIT_ON_ALLOC_DEFAULT_ON`（`security/Kconfig.hardening:159`） |
| 栈溢出 | 把用户提供的长度用于栈上数组；或无限递归。防御：`CONFIG_VMAP_STACK`、`CONFIG_SCHED_STACK_END_CHECK`、`CONFIG_RANDOMIZE_KSTACK_OFFSET` |
| 空指针解引用 | 通常来自错误的错误处理路径（`if (IS_ERR(p))` 写成 `if (!p)`） |
| 双重释放 | 所有权不唯一。防御：`CONFIG_DEBUG_OBJECTS`、KASAN |
| 资源泄漏 | 错误路径漏了释放；反复触发后耗尽内存/fd/pid。可用 kmemleak + 反复触发来发现 |
| 权限检查遗漏 | `capable()` / `ns_capable()` / `file_permission()` 写错或漏写。**这类 bug 不需要内存破坏就能提权** |

## 4. 防御机制

理解防御有双重价值：知道加固怎么做，也知道哪些防线在什么条件下会失效。

### 4.1 硬件提供的隔离

| 机制 | 作用 | 在本源码树中的状态 |
| --- | --- | --- |
| **ring0 / ring3 特权级** | 内核代码在 CPL=0，用户代码 CPL=3 | 基础 |
| **SMEP**（Supervisor Mode Execution Prevention，管理模式执行保护） | ring0 不能**执行**用户页。挡住「跳到用户态 shellcode」 | 现代内核中**已无 `CONFIG_X86_SMEP` 开关**：CPU 支持则强制开启。实测 `arch/x86/kernel/cpu/common.c:371` 的 `setup_smep()` 无条件 `cr4_set_bits(X86_CR4_SMEP)`；特性位定义在 `arch/x86/include/asm/cpufeatures.h:250` |
| **SMAP**（Supervisor Mode Access Prevention，管理模式访问保护） | ring0 不能**读写**用户页，除非显式 `stac`/`clac`。这让「伪造内核结构体在用户空间」失效 | 同上，无 `CONFIG_X86_SMAP`，`setup_smap()` 强制开启；特性位 `cpufeatures.h:263` |
| **NX / W^X** | 页表 NX 位禁止执行数据页 | `CONFIG_STRICT_KERNEL_RWX`、`CONFIG_STRICT_MODULE_RWX`；用 `CONFIG_DEBUG_WX` 启动时校验；模块的 `kernel/module/strict_rwx.c` |
| **CET IBT**（间接分支跟踪） | 间接跳转目标必须以 `endbr64` 开头 | `CONFIG_X86_KERNEL_IBT`（`arch/x86/Kconfig:1746`），见 `arch/x86/kernel/cet.c` |
| **CET Shadow Stack**（影子栈） | 返回地址另存一份，ROP 失效 | 用户态：`CONFIG_X86_USER_SHADOW_STACK`（`arch/x86/Kconfig:1848`）。实测 `arch/x86/configs/hardening.config` 里就开启了它 |
| **IOMMU** | 设备 DMA 不能写到任意物理内存 | `CONFIG_INTEL_IOMMU_DEFAULT_ON`、`CONFIG_AMD_IOMMU`（同见 `hardening.config`） |

> SMEP/SMAP 的实战意义：即使攻击者能把内核的某个函数指针改成用户空间地址，跳过去也会立刻 #PF。所以现代利用必须转向 **ROP/JOP 到内核自身的代码**（或数据导向攻击，如改 `cred` 结构体内容）—— 这就引出了 KPTI、KASLR、CFI 的必要性。

### 4.2 地址空间隔离

| 机制 | 配置项 | 作用 |
| --- | --- | --- |
| **KPTI**（Kernel Page Table Isolation，内核页表隔离） | `CONFIG_MITIGATION_PAGE_TABLE_ISOLATION`（`arch/x86/Kconfig:2420`） | 用户态运行时，内核页不映射在用户页表里。缓解 Meltdown 类攻击 |
| **KASLR**（Kernel Address Space Layout Randomization） | `CONFIG_RANDOMIZE_BASE`（`arch/x86/Kconfig:2054`） | 内核基址随机化。仅当攻击者无法获取任何内核地址时有效 —— 一个泄露的内核指针就能算出基址 |
| 内核栈随机化 | `CONFIG_RANDOMIZE_KSTACK_OFFSET` | 每次 syscall 随机偏移内核栈起始位置 |
| 模块加载地址随机化 | 模块加载时在模块区随机分配虚拟地址 | 抬高「在模块里找 gadget」的成本 |
| vmalloc 随机化 | 随 `RANDOMIZE_BASE` | — |

**KASLR 的现实强度**：它是一种「提高门槛」机制而不是边界。一旦有任何信息泄露（`/proc` 输出、日志、侧信道、某个未初始化的结构体字段），它就被绕过。所以内核同时做了这些事：

| 限制 | 位置 |
| --- | --- |
| `kptr_restrict` | `kernel/printk/sysctl.c:70`（0=不限制、1=需要 `CAP_SYSLOG`、2=总是打 0） |
| `dmesg_restrict` | `kernel/printk/sysctl.c:61` |
| `%pK` 格式 | `kernel/ksyms_common.c` 中根据 `kptr_restrict` 与 `CAP_SYSLOG` 决定是否输出真实地址 |
| `kallsyms_show_value()` | `kernel/ksyms_common.c:30` |

检查你的系统：

```bash
sysctl kernel.kptr_restrict kernel.dmesg_restrict
# 期望：kptr_restrict = 2（或至少 1）、dmesg_restrict = 1
```

### 4.3 控制流完整性

| 机制 | 配置项 | 作用 |
| --- | --- | --- |
| 栈保护（stack protector） | `CONFIG_STACKPROTECTOR` / `CONFIG_STACKPROTECTOR_STRONG`（`arch/Kconfig:718` / `:742`） | 函数序言写入 canary，返回前校验，检测栈溢出覆盖返回地址 |
| **CFI**（Control Flow Integrity，控制流完整性） | `CONFIG_CFI_CLANG`（`arch/Kconfig:970`） | 编译期在间接调用前插入类型检查。能阻止大量「改函数指针」利用。`CONFIG_CFI_PERMISSIVE`（`:1006`）只警告不阻止 |
| 返回地址保护 | `CONFIG_X86_KERNEL_IBT`、`CONFIG_X86_USER_SHADOW_STACK` | 见 §4.1 |
| `CONFIG_SHADOW_CALL_STACK` | `arch/Kconfig:771` | 影子调用栈（主要 arm64） |
| 栈擦除 | `CONFIG_KSTACK_ERASE`（`security/Kconfig.hardening:88`，原 `GCC_PLUGIN_STACKLEAK`） | 函数返回时擦除栈上残留数据，防止信息泄露 |
| 清零调用者未使用的寄存器 | `CONFIG_ZERO_CALL_USED_REGS`（`:194`） | 防止寄存器里的内核指针泄露到用户态 |

### 4.4 内存与对象加固

| 机制 | 配置项 | 作用 |
| --- | --- | --- |
| 分配时清零 | `CONFIG_INIT_ON_ALLOC_DEFAULT_ON`（`security/Kconfig.hardening:159`） | 所有页分配与 slab 分配返回前清零，消除未初始化内存泄露 |
| 释放时清零 | `CONFIG_INIT_ON_FREE_DEFAULT_ON`（`:172`） | 消除 UAF 的「读旧内容」路径，但代价明显 |
| 变量自动初始化 | `CONFIG_INIT_STACK_ALL_ZERO` / `INIT_STACK_ALL_PATTERN`（`:46`、`:66`） | 栈变量清零/填模式 |
| **HARDENED_USERCOPY** | `CONFIG_HARDENED_USERCOPY`（`:221`） | `copy_*_user` 时校验源/目标是否落在合法对象边界内 |
| **FORTIFY_SOURCE** | `CONFIG_FORTIFY_SOURCE`（`:214`） | 编译期 + 运行期的 `memcpy`/`strcpy` 系列越界检查 |
| LIST_HARDENED | `CONFIG_LIST_HARDENED`（`:245`） | 检查链表操作的指针完整性，抓链表投毒 |
| BUG_ON_DATA_CORRUPTION | `CONFIG_BUG_ON_DATA_CORRUPTION`（`:264`） | 检测到数据结构损坏时直接 BUG 而不是静默继续 |
| SLAB_FREELIST_HARDENED | `mm/Kconfig:208` | 空闲链表指针编码，抓「覆写 freelist」式利用 |
| SLAB_FREELIST_RANDOM | `mm/Kconfig:200` | 随机化空闲对象顺序，让堆风水变难 |
| RANDOM_KMALLOC_CACHES | `mm/Kconfig:311` | 按调用点拆分 kmalloc 缓存，减少跨类型的对象混用 |
| RANDSTRUCT | `CONFIG_RANDSTRUCT`（`security/Kconfig.hardening:336`） | 随机化结构体字段顺序，破坏依赖固定偏移的利用。需要插件或 Clang |
| 页表检查 | `CONFIG_PAGE_TABLE_CHECK`、`mm/page_table_check.c` | 检测页表被非法修改 |
| **KASAN / KMSAN / KFENCE / UBSAN** | 见 [01](01-内核构建与调试.md#54-kasan--kcsan--kfence) | 运行期错误检测。开发/测试内核必开 |
| kmemleak | `CONFIG_DEBUG_KMEMLEAK` | 内存泄漏检测 |
| KCOV | `CONFIG_KCOV`（`lib/Kconfig.debug:2170`）、`KCOV_INSTRUMENT_ALL`（`:2193`）、`KCOV_ENABLE_COMPARISONS`（`:2183`） | 覆盖率反馈，模糊测试的基础设施 |

关于 `refcount_t`：早期内核有 `CONFIG_REFCOUNT_FULL` 开关来选择严格检查；**该配置项在 7.3 源码树中已不存在** —— 引用计数的溢出/下溢检测现在是 `refcount_t` 的常态行为（见 `include/linux/refcount.h` 与 `Documentation/core-api/refcount-vs-atomic.rst`）。

### 4.5 系统调用与特权限制

| 机制 | 配置项 / sysctl | 作用 |
| --- | --- | --- |
| **seccomp** | `CONFIG_SECCOMP`（`arch/Kconfig:664`）、`CONFIG_SECCOMP_FILTER`（`:681`） | 用 BPF 程序过滤系统调用。过滤器一旦安装（无 `TSYNC` 时）不可撤销 |

| lockdown 状态 | `/sys/kernel/security/lockdown` | 查看/设置 |

| 用户命名空间 | `CONFIG_USER_NS`、`sysctl user.max_user_namespaces`（`kernel/ucount.c:77`） | 非特权用户命名空间极大扩展攻击面；容器场景需要，桌面/服务器可考虑关闭 |

## 5. 内核加固自查清单

按「先做成本低、影响小的，再做侵入性大的」排序。

### 5.1 运行时配置（不改内核，立即可做）

- [ ] `kernel.kptr_restrict = 2`（或 1）
- [ ] `kernel.dmesg_restrict = 1`
- [ ] `kernel.perf_event_paranoid = 3`（默认通常是 2 或 4）
- [ ] `kernel.unprivileged_bpf_disabled = 1`（若不需要非特权 eBPF）
- [ ] `vm.unprivileged_userfaultfd = 0`
- [ ] `kernel.randomize_va_space = 2`
- [ ] `kernel.kexec_load_disabled = 1`（不需要 kdump 时）
- [ ] `kernel.modules_disabled = 1`（⚠️ **不可逆**，只在静态内核的生产机器上，且必须先加载完所有需要的模块）
- [ ] `user.max_user_namespaces = 0`（不需要非特权用户命名空间的服务器）
- [ ] `kernel.yama.ptrace_scope >= 1`
- [ ] `/dev/mem`、`/dev/kmem`、`/dev/port` 权限收紧或不存在
- [ ] `fs.protected_hardlinks = 1`、`fs.protected_symlinks = 1`
- [ ] `/proc/sys/fs/suid_dumpable = 0`
- [ ] 检查是否有不必要的 `CAP_*` 通过文件 capability 授予（`getcap -r / 2>/dev/null`）

### 5.2 启动参数

```
# 常见加固启动参数的思路（具体名称见
# Documentation/admin-guide/kernel-parameters.rst）
init_on_alloc=1
init_on_free=1
slab_nomerge
page_alloc.shuffle=1
pti=on
randomize_kstack_offset=on
oops=panic               # 配合 kdump 收集现场
panic_on_warn=1          # 只在测试环境用，生产会频繁重启
slub_debug=FZPU          # 只在测试环境用，性能代价大
```

⚠️ `oops=panic` + `panic_on_warn=1` 会让任何一次 WARN 都导致重启。生产环境请先在测试机上评估。

### 5.3 编译期内核配置（`CONFIG_`）

## 6. 合法研究路径

### 6.1 搭建研究环境（隔离优先）

```
+-----------------------------------------------------------+
|  宿主机（你的日常系统，不要在上面跑有 bug 的内核）              |
|                                                           |
|   +---------------------------------------------------+   |
|   |  专用虚拟机 / 独立物理机                            |   |
|   |  - 只做内核模糊测试，不存放任何真实数据               |   |
|   |  - 无外网（或只允许到你的内网镜像）                   |   |
|   |  - 快照可随时回滚                                   |   |
|   |                                                   |   |
|   |   +-------------------------------------------+   |   |
|   |   |  QEMU VM：带 KASAN/KCOV 的测试内核           |   |   |
|   |   |  - 每次 fuzz 用全新快照启动                  |   |   |
|   |   |  - 不挂载宿主机目录（除只读的案例目录）       |   |   |
|   |   +-------------------------------------------+   |   |
|   +---------------------------------------------------+   |
+-----------------------------------------------------------+
```

**硬性规则**：

1. 模糊测试虚拟机**不要**挂载宿主机的可写目录。有 bug 的内核可以写穿一切权限检查。
2. 不要在带真实数据、密钥、凭据的机器上运行 fuzzer。
3. 不要在生产网络里跑 fuzzer（网络协议栈 fuzz 会发出畸形报文）。
4. 所有发现的 crash 一律先在**你自己的**环境里复现和最小化，不要拿别人系统验证。

### 6.2 syzkaller —— 覆盖率引导的内核模糊测试

syzkaller 是 Google 维护的无监督、覆盖率引导的内核 fuzzer（https://github.com/google/syzkaller）。它的工作方式：向内核注入大量「系统调用序列」，用 KCOV 收集覆盖率反馈，用编写的描述文件（`sys/linux/*.txt`）描述参数空间与依赖关系。

#### 6.2.1 需要的内核配置

syzkaller 官方推荐的配置（已核对本源码树中的配置项名称）：

```
# 覆盖率（syzkaller 的立身之本）
CONFIG_KCOV=y
CONFIG_KCOV_INSTRUMENT_ALL=y
CONFIG_KCOV_ENABLE_COMPARISONS=y
CONFIG_DEBUG_FS=y

# 崩溃检测
CONFIG_KASAN=y
CONFIG_KASAN_INLINE=y
CONFIG_UBSAN=y
CONFIG_DEBUG_KMEMLEAK=y

# 符号与代码覆盖可视化
CONFIG_KALLSYMS=y
CONFIG_KALLSYMS_ALL=y
CONFIG_DEBUG_INFO=y
CONFIG_DEBUG_INFO_DWARF_TOOLCHAIN_DEFAULT=y

# 沙箱（限制 fuzzer 自身的权限，减少误伤）
CONFIG_NAMESPACES=y
CONFIG_UTS_NS=y
CONFIG_IPC_NS=y
CONFIG_PID_NS=y
CONFIG_NET_NS=y
CONFIG_USER_NS=y
CONFIG_CGROUP_PIDS=y
CONFIG_MEMCG=y

# 在 QEMU 里跑
CONFIG_VIRTIO=y
CONFIG_VIRTIO_PCI=y
CONFIG_VIRTIO_NET=y
CONFIG_VIRTIO_BLK=y
CONFIG_SERIAL_8250=y
CONFIG_SERIAL_8250_CONSOLE=y
CONFIG_CONFIGFS_FS=y
CONFIG_SECURITYFS=y

# 故障注入（让 syzkaller 能注入分配失败，暴露错误路径 bug）
CONFIG_FAULT_INJECTION=y
CONFIG_FAULT_INJECTION_DEBUG_FS=y
CONFIG_FAULT_INJECTION_USERCOPY=y
CONFIG_FAILSLAB=y
CONFIG_FAIL_PAGE_ALLOC=y
CONFIG_FAIL_MAKE_REQUEST=y
CONFIG_FAIL_IO_TIMEOUT=y

# 各类调试检查（官方建议"越多越好"）
CONFIG_LOCKDEP=y
CONFIG_PROVE_LOCKING=y
CONFIG_DEBUG_ATOMIC_SLEEP=y
CONFIG_PROVE_RCU=y
CONFIG_DEBUG_VM=y
CONFIG_FORTIFY_SOURCE=y
CONFIG_HARDENED_USERCOPY=y
CONFIG_LOCKUP_DETECTOR=y
```

⚠️ **不要**在 fuzz 内核里开启 `CONFIG_RANDOMIZE_BASE`（KASLR）：syzkaller 需要能解析符号地址来归并崩溃。官方明确指出在旧内核上建议关闭。用：

```
# CONFIG_RANDOMIZE_BASE is not set
```

⚠️ 实测本源码树中 `CONFIG_REFCOUNT_FULL` **已不存在**（旧版 syzkaller 文档里还在提它）。synth 配置时如果 `scripts/config` 报"未知选项"就是这个原因。

#### 6.2.2 一个可用的起步流程

```bash
# ---------- 1) 准备内核（宿主机） ----------
export KSRC=/home/rivo/Documents/hack-learn/kernel/src/linux
cd "$KSRC"
make O=/tmp/kbuild-syz defconfig kvm_guest.config
scripts/config --file /tmp/kbuild-syz/.config \
  --enable KCOV --enable KCOV_INSTRUMENT_ALL --enable KCOV_ENABLE_COMPARISONS \
  --enable KASAN --enable KASAN_INLINE \
  --enable DEBUG_INFO --enable DEBUG_INFO_DWARF_TOOLCHAIN_DEFAULT \
  --enable KALLSYMS --enable KALLSYMS_ALL \
  --enable DEBUG_FS --enable CONFIGFS_FS --enable SECURITYFS \
  --enable PROVE_LOCKING --enable DEBUG_ATOMIC_SLEEP --enable DEBUG_VM \
  --enable HARDENED_USERCOPY --enable FORTIFY_SOURCE \
  --disable RANDOMIZE_BASE
make O=/tmp/kbuild-syz olddefconfig
make O=/tmp/kbuild-syz -j"$(nproc)"

# ---------- 2) 准备 Go 与 syzkaller（宿主机） ----------
# 官方要求 Go 1.23+（以 syzkaller 仓库当时的 README 为准）
git clone https://github.com/google/syzkaller
cd syzkaller
make                 # 产物在 bin/
ls bin/              # syz-manager  syz-execprog  syz-prog2c  ...

# ---------- 3) 制作 VM 镜像 ----------
# 官方脚本 tools/create-image.sh（需要 debootstrap 等）
sudo apt install -y debootstrap
./tools/create-image.sh --arch amd64 --distribution bookworm
# 产物：bullseye.img / bullseye.id_rsa / bullseye.key

# ---------- 4) 写 manager 配置 ----------
cat > /tmp/syz.cfg <<'EOF'
{
  "target": "linux/amd64",
  "http": "127.0.0.1:56741",
  "workdir": "/tmp/syz-workdir",
  "kernel_obj": "/tmp/kbuild-syz",
  "image": "/path/to/bullseye.img",
  "sshkey": "/path/to/bullseye.id_rsa",
  "syzkaller": "/path/to/syzkaller",
  "procs": 4,
  "type": "qemu",
  "vm": {
    "count": 2,
    "kernel": "/tmp/kbuild-syz/arch/x86/boot/bzImage",
    "cpu": 2,
    "mem": 2048,
    "qemu_args": "-enable-kvm"
  }
}
EOF

# ---------- 5) 跑起来 ----------
mkdir -p /tmp/syz-workdir
./bin/syz-manager -config /tmp/syz.cfg
# 打开 http://127.0.0.1:56741 查看覆盖率与崩溃
```

**注意事项**：

| 现象 | 原因 / 解决 |
| --- | --- |
| `QEMU requires root for -enable-kvm` | `sudo usermod -a -G kvm $USER` 后重新登录 |
| QEMU 报 `failed to set MSR ...` 或类似 KVM 错误 | 去掉 `-cpu host,migratable=off`，`qemu_args` 只留 `-enable-kvm` |
| VM 起不来 / SSH 不通 | 镜像里必须有 SSH 服务且允许 root 免密（`create-image.sh` 已处理）；确认 `sshkey` 路径正确 |
| 覆盖率一直是 0 | 内核没开 `CONFIG_KCOV`；或 VM 里没挂 `debugfs` 到 `/sys/kernel/debug` |
| 崩溃无法归并 / 全是随机符号 | 忘了关 `CONFIG_RANDOMIZE_BASE` |
| 一堆 hung task 误报 | 调大 `CONFIG_DEFAULT_HUNG_TASK_TIMEOUT`（官方建议 140）与 `CONFIG_RCU_CPU_STALL_TIMEOUT`（建议 100） |

#### 6.2.3 只 fuzz 你关心的子系统

全量 fuzz 覆盖面太大，收敛慢。可以：

```bash
# 1) 用 syz-execprog 手工跑一个程序，看这个子系统能不能被触达
./bin/syz-execprog -executor ./bin/syz-executor -repeat=10 -procs=1 \
  -cover=1 -sandbox=none /tmp/myprog.txt

# 2) 在 sys/linux/ 下写自己的 syscall 描述文件（.txt），
#    只保留目标子系统需要的类型定义，能显著提高触达率。
#    参考 sys/linux/README.md 与已有的 .txt 写法。

# 3) manager 配置里用 "enable_syscalls" / "disabled_syscalls"
#    正则来限制调用面（见 docs/configuration.md）
```

一个只针对某驱动（比如一个字符设备）的思路：
1. 写一个 `syz_mount_image` 风格的伪 syscall 描述，或在 `sys/linux/dev_*.txt` 里补充该设备的 ioctl 定义；
2. 用 `enable_syscalls` 只放行你写的伪 syscall + `openat`/`ioctl`/`read`/`write`/`close`；
3. 让它跑几个小时，看覆盖率增长曲线是否收敛。

### 6.3 上游报告流程

发现崩溃后，正确的做法不是发博客，而是**上游报告**。syzkaller 发现的崩溃通常会被自动转发到 syzbot（https://syzkaller.appspot.com/），但如果你是自己搭的环境，流程是：

1. **最小化复现**：syzkaller 会自动做，但你要人工复核一遍。一份「3 行 C 程序」比「1 MB 的 syz 程序」有用得多。
2. **确认可复现**：在干净的内核上重跑，至少 3 次。
3. **判断是不是已修复**：在 `linux-next` 或最新 mainline 上试。已修复的直接跳过。
4. **定位子系统**：读 `MAINTAINERS`（`grep -n "<子系统名>" MAINTAINERS`），找到维护者与邮件列表。这是必须看的一步 —— 发错列表会被无视。
5. **`git bisect` 找引入点**（有完整克隆时）：
   ```bash
   git bisect start
   git bisect bad v7.3
   git bisect good v7.2
   # 每次 bisect 后重编译并运行你的复现程序，报告 good/bad
   ```
   准确的 bisect 结果能极大加快修复。
6. **按规范发邮件**：读 `Documentation/process/submitting-patches.rst`、`Documentation/admin-guide/reporting-issues.rst`、`Documentation/admin-guide/bug-hunting.rst`、`Documentation/process/submit-checklist.rst`，用 `git send-email` 或纯文本邮件。**不要发 HTML 邮件，不要粘贴截图**。
7. **报告应包含**：内核版本与 `.config`、复现步骤（最小程序）、实际输出（完整 Oops/KASAN 报告原文）、预期行为、你的分析（如果定位到了具体函数，指出来）、是否可用 `git bisect`。
8. **如果是安全漏洞**（可被利用的提权/沙箱逃逸）：**不要**直接发到公开列表。按 `Documentation/process/security-bugs.rst` 的流程私下报告给 `security@kernel.org`。这一点非常关键 —— 公开发布未修复的提权漏洞会伤害所有用户。

### 6.4 其他学习路径

| 方式 | 说明 |
| --- | --- |
| 复现已修复的历史漏洞 | 找一个已被修复且有公开分析的内核漏洞，checkout 到修复前的 commit，自己写 PoC，再读修复 patch 理解根因。**只在你自己的虚拟机里做。** |
| 参加内核 CTF | 一些 CTF 有 kernel pwn 题目（提供 `vmlinux`、`bzImage`、`initramfs`、`run.sh`）。这是最安全的练习场 |
| 读内核加固项目的设计文档 | `security/Kconfig.hardening` 的 help 文本、`Documentation/` 下的 `dev-tools/` 与 `admin-guide/LSM/` |
| 参与上游 | 从 `Documentation/` 的拼写/示例修正开始，熟悉流程后再做代码 |
| 订阅漏洞披露 | `linux-distros@vs.openwall.org`（发行版协调）、oss-security 列表 |

## 7. 一页总结

```
攻击面（不可信输入进入内核的入口）
  syscall / ioctl / 设备文件 / 文件系统解析器 / 网络协议栈 / eBPF / 硬件输入

漏洞类型（结构性的"形状"，不是具体案例）
  越界读写   <- 长度未校验、索引未设界、整数溢出
  UAF        <- 引用计数错配、错误路径提前释放、异步回调持有已释放对象
  类型混淆   <- union/void* 无 tag、句柄可指向多种类型
  整数问题   <- 回绕、符号转换、截断
  竞态       <- TOCTOU、非原子"检查再使用"、部分路径加锁、fd 复用
  权限检查遗漏 <- 不需要内存破坏就能提权

防御（每一层都在提高"从 bug 到提权"的成本）
  硬件     ring0/ring3、SMEP/SMAP（现为强制）、NX、CET IBT、CET Shadow Stack、IOMMU
  隔离     KPTI、KASLR、栈随机化、vsyscall 移除
  控制流   STACKPROTECTOR、CFI_CLANG、ZERO_CALL_USED_REGS、KSTACK_ERASE
  内存     INIT_ON_ALLOC/FREE、HARDENED_USERCOPY、FORTIFY_SOURCE、LIST_HARDENED、
           SLAB_FREELIST_HARDENED/RANDOM、RANDOM_KMALLOC_CACHES、RANDSTRUCT、PAGE_TABLE_CHECK
  检测     KASAN/KMSAN/KFENCE/KCSAN/UBSAN/kmemleak/KCOV、lockdep、DEBUG_ATOMIC_SLEEP
  特权     seccomp、LSM（selinux/apparmor/landlock/yama/…）、lockdown、MODULE_SIG、
           非特权 BPF/userfaultfd/用户命名空间限制、kptr_restrict/dmesg_restrict
  流程     模糊测试（syzkaller）、代码审查、私下报告 security@kernel.org

实操路径
  1. QEMU + KASAN 内核 + initramfs（01 文档）—— 一遍就搭好隔离环境
  2. 写一个带 bug 的模块，用 KASAN/lockdep 抓出来（03 文档 + 05 实验）
  3. 上游报告流程走一遍（本节 6.3）
```
