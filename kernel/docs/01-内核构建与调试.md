## 1. 从 defconfig 到启动的完整流程

Kbuild（内核构建系统）的核心思路：**先由 Kconfig 生成 `.config`，再由 Makefile 体系按 `.config` 决定编译哪些文件**。

```
Kconfig 文件树 (Kconfig, arch/x86/Kconfig, drivers/*/Kconfig ...)
        |  make menuconfig / defconfig / olddefconfig
        v
     .config          <- 你的配置（约 1 万行）
        |
        |  make (Kbuild 递归遍历 Makefile)
        v
  obj-y / obj-m 展开 -> 编译 -> vmlinux (ELF, 带符号)
        |
        |  objcopy / 压缩
        v
  arch/x86/boot/bzImage  <- 可被 bootloader / QEMU 直接加载
        |
        |  make modules_install (可选)
        v
  /lib/modules/$(uname -r)/kernel/...  +  modules.dep（由 depmod 生成）
```

### 1.1 `make defconfig` —— 生成默认配置

```bash
cd "$KSRC"
make defconfig
```

在 x86_64 上，`defconfig` 会使用 `arch/x86/configs/x86_64_defconfig`（实测该文件存在，同目录还有 `i386_defconfig`、`tiny.config`、`xen.config`、`hardening.config`）。它只保证「能编译、能启动」，大量驱动是 `=n`。

其他常用配置生成方式：

| 命令 | 作用 | 适用场景 |
| --- | --- | --- |
| `make defconfig` | 架构默认配置 | 第一次编译 |
| `make tinyconfig` | 极小配置（基于 `kernel/configs/tiny-base.config`） | 学习启动流程、最小化实验 |
| `make localmodconfig` | 以当前机器已加载模块为基准裁剪 | 只为当前机器编译，大幅缩短编译时间 |
| `make olddefconfig` | 保留旧 `.config`，新增选项取默认值 | 升级内核版本后复用配置 |
| `make savedefconfig` | 把当前 `.config` 精简为最小差异，写入 `defconfig` | 准备提交一个自定义配置 |
| `make randconfig` | 随机配置 | 模糊测试「配置组合是否能编译」 |
| `make help` | 列出全部可用目标 | — |

### 1.2 配置片段合并（很实用）

Kbuild 支持把一个 `.config` 片段叠在基础配置之上。片段文件的搜索路径由 `scripts/kconfig/Makefile` 定义，实际为：

```
kernel/configs/<name>  或  arch/<arch>/configs/<name>
```

实测存在的片段（`ls arch/x86/configs/ kernel/configs/`）：

| 片段 | 内容 |
| --- | --- |
| `kernel/configs/kvm_guest.config` | 让内核可作为 KVM/QEMU 客户机启动：`CONFIG_VIRTIO_*`、`CONFIG_SERIAL_8250_CONSOLE`、`CONFIG_9P_FS`、`CONFIG_NET_9P_VIRTIO`、`CONFIG_DEBUG_KERNEL` 等 |
| `kernel/configs/x86_debug.config`、`debug.config` | 开启各类调试选项 |
| `arch/x86/configs/hardening.config` | 硬化选项：`CONFIG_X86_KERNEL_IBT`、`CONFIG_X86_USER_SHADOW_STACK`、IOMMU 等 |

**推荐做法**（既能在 QEMU 里跑，又带调试能力）：

```bash
cd "$KSRC"
make defconfig kvm_guest.config
make -j"$(nproc)"
```

### 1.3 `make menuconfig` 用法

```bash
cd "$KSRC"
make menuconfig
```

需要 `libncurses-dev`（Debian）或 `ncurses`（Arch），否则报 `Unable to find the ncurses library`。

| 按键 | 作用 |
| --- | --- |
| `↑` `↓` | 移动 |
| `Enter` | 进入子菜单 / 切换选项 |
| `y` / `m` / `n` | 编译进内核 / 编译为模块 / 不编译 |
| `/` | **搜索**：输入符号名（如 `KASAN`）或字符串，跳到对应项 |
| `?` | 查看该项的 `help` 文本与依赖条件 |
| `Esc` `Esc` | 返回上级 / 退出 |
| `+` `-` | 展开/折叠 |

常用启动参数（实测 `Documentation/kbuild/kconfig.rst` 中有记载）：

```bash
make MENUCONFIG_COLOR=mono menuconfig      # 单色，适合某些终端
make MENUCONFIG_MODE=single_menu menuconfig
make nconfig                               # 另一种 TUI，搜索体验更好
make xconfig                               # Qt 图形界面
```

### 1.4 `.config` 关键项解读

下表是新手最需要看懂的项，`?` 帮助文本里都有原文说明：

| 配置项 | 含义 | 建议值（学习用） |
| --- | --- | --- |
| `CONFIG_LOCALVERSION` | 追加到版本号后的自定义字符串，影响 `uname -r` 与模块 `vermagic` | `"-learn"` 便于区分 |
| `CONFIG_MODULES` | 是否支持可加载模块。关闭后 `insmod` 完全不可用 | `=y` |
| `CONFIG_MODULE_UNLOAD` | 是否允许卸载模块。关闭后 `rmmod` 失败 | `=y` |
| `CONFIG_MODVERSIONS` | 模块符号 CRC 校验。改动内核结构体后旧模块会被拒绝加载 | 学习期建议 `=n`，便于反复改源码 |
| `CONFIG_DEBUG_INFO` | 生成 DWARF 调试信息。GDB、`crash` 依赖它 | `=y` |
| `CONFIG_DEBUG_INFO_DWARF5` / `DWARF4` | DWARF 版本 | 跟随默认 |
| `CONFIG_DEBUG_INFO_BTF` | 由 `pahole` 生成 BTF。bpftrace/CO-RE 依赖它 | `=y`（需装 `dwarves`） |
| `CONFIG_KALLSYMS` | 把符号表打进内核，Oops 里才能看到函数名而非裸地址 | `=y` |
| `CONFIG_KALLSYMS_ALL` | 连数据符号也打进 | `=y`（学习期） |
| `CONFIG_FRAME_POINTER` | 使用帧指针，栈回溯更可靠 | `=y` |
| `CONFIG_PREEMPT` / `CONFIG_PREEMPT_DYNAMIC` | 抢占模型。`PREEMPT_DYNAMIC` 允许启动时切换 | `PREEMPT_DYNAMIC` |
| `CONFIG_HZ` | 内核时钟节拍 | 1000 |
| `CONFIG_CMDLINE` | 编译进内核的默认命令行（`-append` 会追加/覆盖） | 留空或用 `-append` |
| `CONFIG_INITRAMFS_SOURCE` | 把 initramfs 直接编译进内核 | 见 §4.4 |
| `CONFIG_SMP` | 多核支持 | `=y` |
| `CONFIG_MAGIC_SYSRQ` | 支持 SysRq 魔法键（`Alt+SysRq`，串口上 `echo t > /proc/sysrq-trigger`） | `=y` |

查看已生效的关键项：

```bash
grep -E '^(CONFIG_LOCALVERSION|CONFIG_MODULES|CONFIG_DEBUG_INFO|CONFIG_KALLSYMS|CONFIG_KASAN|CONFIG_PREEMPT)' "$KSRC/.config"
```

### 1.5 配置的隐藏来源：`CONFIG_` 与自动生成的符号

`.config` 里没有出现的项 = 用了默认值或依赖不满足。想查某个符号到底为什么被禁用：

```bash
make menuconfig
# 按 / 输入符号名，帮助文本里的 "Depends on:" 会说明依赖链
```

自动生成的配置头文件在构建目录：

```bash
cat "$KSRC/include/generated/autoconf.h" | head
grep -n "CONFIG_KASAN" "$KSRC/include/config/auto.conf"   # 构建后才有
```

## 2. 编译内核与模块

### 2.1 编译

```bash
cd "$KSRC"
make -j"$(nproc)"
```

产物：

| 文件 | 说明 |
| --- | --- |
| `vmlinux` | 未压缩的 ELF 内核，**带调试符号** —— GDB 调试的输入 |
| `arch/x86/boot/bzImage` | 压缩后的可引导内核，QEMU `-kernel` 的输入 |
| `System.map` | 符号地址表，分析 Oops 计算地址时用 |
| `.config` | 当前配置 |
| `*.ko` | 编译为 `=m` 的模块，散落在各子目录 |

> 生成 `System.map` 与 `vmlinux` 的前提是 `CONFIG_KALLSYMS=y` / `CONFIG_DEBUG_INFO=y`。
> 单独重新生成 `System.map`：`make -s vmlinux && nm -n vmlinux | sort > System.map`（内核构建通常已自动完成）。

### 2.2 **不要**在源码树里构建（推荐 `O=`）

源码树里构建会把 `.o`、`.cmd`、`include/generated/` 混进源码，污染目录树，也让「源码结构 vs 构建产物的区别」这一学习点变得模糊。推荐外部构建：

```bash
cd "$KSRC"
make O=/tmp/kbuild-learn x86_64_defconfig
make O=/tmp/kbuild-learn -j"$(nproc)"
ls /tmp/kbuild-learn/vmlinux /tmp/kbuild-learn/arch/x86/boot/bzImage
```

本文后续命令若使用 `O=/tmp/kbuild-learn`，只是示例；你可以选择原地构建，只是要记得 `make mrproper` 才能彻底清理。

清理相关目标：

| 命令 | 删除内容 |
| --- | --- |
| `make clean` | 大部分构建产物，保留 `.config` |
| `make mrproper` | 构建产物 **+ `.config` + 各类备份** |
| `make distclean` | `mrproper` + 编辑器备份、补丁残留 |

### 2.3 安装模块

```bash
sudo make modules_install
# 或指定构建目录
sudo make O=/tmp/kbuild-learn modules_install
```

结果写入 `/lib/modules/<版本号>/kernel/`，并调用 `depmod` 生成 `modules.dep`。只安装到临时目录（不想污染系统时）：

```bash
make INSTALL_MOD_PATH=/tmp/modstage modules_install
ls /tmp/modstage/lib/modules/
```

### 2.4 `make install`（⚠️ 会改动 bootloader）

```bash
sudo make install
```

该目标执行 `arch/x86/boot/install.sh`：把 `bzImage`、`System.map`、`.config` 复制到 `/boot`，然后尝试调用 `update-grub`（Debian 系）或直接调 `grubby`/`installkernel`。**风险与回滚见 §7。**

只想把文件放到 `/boot` 而不动 bootloader：

```bash
sudo install -m 644 arch/x86/boot/bzImage /boot/vmlinuz-7.3.0-rc3-learn
sudo install -m 644 System.map          /boot/System.map-7.3.0-rc3-learn
sudo install -m 644 .config             /boot/config-7.3.0-rc3-learn
```

## 3. 编译耗时与并行度

- `make -j$(nproc)` 并非越大越好：每个 `gcc` 进程可占 1~1.5 GB 内存。16 GB 内存建议 `-j8`。
- 观察真实瓶颈：

```bash
/usr/bin/time -v make -j8 2>&1 | tail -20
```

- 只重编一个目录（增量构建）：

```bash
make M=fs   # ❌ 错误用法

# 正确做法：直接给目标
make fs/read_write.o
```

- 只想编译某个模块：

```bash
make -j"$(nproc)" drivers/char/mem.ko
```

## 4. 用 QEMU 跑自己编译的内核

这是**最安全的实验方式**：内核跑在虚拟机里，崩溃只影响 QEMU 进程。

### 4.1 先装 QEMU

```bash
sudo apt install -y qemu-system-x86 qemu-utils     # Debian / Kali
sudo pacman -S --needed qemu-full                  # Arch / Omarchy
```

确认 KVM 可用（能显著提速）：

```bash
ls -l /dev/kvm && kvm-ok 2>/dev/null || true
```

### 4.2 最小启动（无根文件系统，会 panic）

```bash
cd "$KSRC"
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel arch/x86/boot/bzImage \
  -append "console=ttyS0" \
  -nographic
```

预期看到 `Kernel panic - not syncing: VFS: Unable to mount root fs on unknown-block(0,0)`。这证明**内核本身已经跑起来了**，只是缺根文件系统。这是很好的第一步验证。

`-nographic` 会把串口重定向到当前终端；因此 `console=ttyS0` 必须有，否则你看不到任何输出。退出 QEMU：`Ctrl-a` 然后按 `x`。

### 4.3 制作最小 initramfs（初始内存文件系统）

思路：内核启动最后会执行根文件系统上的 `/init`（可用 `rdinit=` 覆盖）。我们把一个静态链接的 BusyBox 和一个 `init` 脚本打包成 cpio 归档，让内核直接当作根文件系统。

```bash
sudo apt install -y busybox-static cpio     # Debian / Kali
sudo pacman -S --needed busybox cpio        # Arch / Omarchy

# 1) 准备目录骨架
rm -rf /tmp/initramfs && mkdir -p /tmp/initramfs/{bin,dev,proc,sys,etc,tmp,root}
cd /tmp/initramfs

# 2) 放入静态 BusyBox。Debian 是 /bin/busybox，Arch 是 /usr/bin/busybox
BB=$(command -v busybox || echo /bin/busybox)
cp "$BB" bin/busybox
chmod +x bin/busybox

# 3) 用 BusyBox 自带的多合一功能创建全部工具软链接（ls, sh, mount, cat ...）
./bin/busybox --install -s bin

# 4) 写 init 脚本
cat > init <<'EOF'
#!/bin/busybox sh
/bin/busybox --install -s /bin

mount -t proc     none /proc
mount -t sysfs    none /sys
mount -t devtmpfs none /dev 2>/dev/null

echo "=== 自编译内核已启动 ==="
uname -a
cat /proc/version
echo "=== 进入 shell，输入 exit 结束 ==="

exec /bin/sh
EOF
chmod +x init

# 5) 打包成 newc 格式 cpio 再 gzip
find . -print0 | cpio --null -ov --format=newc 2>/dev/null | gzip -9 > /tmp/initramfs.cpio.gz
ls -lh /tmp/initramfs.cpio.gz
```

### 4.4 完整可执行的启动命令

```bash
cd "$KSRC"
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel arch/x86/boot/bzImage \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init loglevel=7 panic=1" \
  -nographic \
  -no-reboot
```

| 参数 | 作用 |
| --- | --- |
| `-kernel arch/x86/boot/bzImage` | 直接加载内核，不走 bootloader |
| `-initrd /tmp/initramfs.cpio.gz` | 提供初始根文件系统 |
| `-append "console=ttyS0 ..."` | 传给内核的命令行（等价于 GRUB 的 `linux` 行） |
| `console=ttyS0` | 内核日志输出到第一个串口，配合 `-nographic` 才能在终端看到 |
| `rdinit=/init` | 指定 initramfs 中要执行的程序（默认就是 `/init`） |
| `loglevel=7` | 打印全部等级日志（0=只打印紧急，7=全部），见 §5.1 |
| `panic=1` | panic 后 1 秒自动重启，避免挂死 |
| `-nographic` | 串口重定向到终端，不弹窗口 |
| `-no-reboot` | panic 后直接退出而不是无限重启（配合 `panic=1` 便于脚本化） |
| `-enable-kvm` | 有 `/dev/kvm` 时加上，速度提升一个数量级 |
| `-no-reboot -s -S` | 见 §5.3 的 GDB 调试 |

**更省事的做法：把 initramfs 编进内核**（QEMU 就不需要 `-initrd`）：

```bash
cd "$KSRC"
mkdir -p /tmp/initramfs/etc
make menuconfig     # General setup -> Initial RAM filesystem and RAM disk -> 
                   # (1234) Initramfs source file(s) 填 /tmp/initramfs
make -j"$(nproc)"
qemu-system-x86_64 -m 2G -smp 2 -kernel arch/x86/boot/bzImage \
  -append "console=ttyS0" -nographic
```

对应配置项是 `CONFIG_INITRAMFS_SOURCE="/tmp/initramfs"`。

### 4.5 让 QEMU 里的内核看到宿主机目录（9p）

调试驱动时很有用，可以在宿主机编辑源码、在虚拟机里查看效果：

```bash
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel arch/x86/boot/bzImage \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init" \
  -nographic \
  -virtfs local,path=$(git rev-parse --show-toplevel),mount_tag=host0,security_model=none
  # 共享仓库根目录；在仓库内任意位置执行都能解析
```

虚拟机内：

```sh
mkdir -p /mnt/host
mount -t 9p -o trans=virtio,version=9p2000.L host0 /mnt/host
ls /mnt/host
```

前提：内核启用了 `CONFIG_NET_9P`、`CONFIG_9P_FS`、`CONFIG_9P_FS_POSIX_ACL`、`CONFIG_NET_9P_VIRTIO` —— 这些正好都在 `kernel/configs/kvm_guest.config` 里（实测）。

### 4.6 常用 QEMU 选项速查

| 选项 | 用途 |
| --- | --- |
| `-m 2G` | 内存大小 |
| `-smp 2` | 2 个 vCPU；测竞态时建议 `-smp 4` |
| `-cpu host` | 直通宿主机 CPU 特性（需 `-enable-kvm`）；测 SMEP/SMAP/IBT 需要 |
| `-s -S` | `-s` 开 gdbstub（1234 端口），`-S` 启动时冻结 CPU |
| `-serial mon:stdio` | 串口与 QEMU 监视器共用标准输入 |
| `-drive file=disk.img,format=raw,if=virtio` | 挂一块 virtio 磁盘 |
| `-trace events=...` | QEMU 自身的事件跟踪（与内核无关） |
| `-d int,cpu_reset` | 打印中断/异常，排查早期启动问题 |

## 5. 调试手段

### 5.1 printk 与日志等级

`printk()` 的格式是 `printk(等级字符串 "格式", 参数...)`。等级定义在 `include/linux/kern_levels.h`：

| 等级 | 宏 | 数值 |
| --- | --- | --- |
| 紧急 | `KERN_EMERG` | 0 |
| 报警 | `KERN_ALERT` | 1 |
| 严重 | `KERN_CRIT` | 2 |
| 错误 | `KERN_ERR` | 3 |
| 警告 | `KERN_WARNING` | 4 |
| 通知 | `KERN_NOTICE` | 5 |
| 信息 | `KERN_INFO` | 6 |
| 调试 | `KERN_DEBUG` | 7 |

```c
printk(KERN_INFO "hello: value=%d\n", v);
printk(KERN_ERR  "hello: failed ret=%d\n", ret);
```

现代写法（推荐，会自动带上 `pr_fmt` 前缀与设备信息）：

```c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/printk.h>

pr_info("value=%d\n", v);
pr_err("failed ret=%d\n", ret);
pr_debug("只在开启 DEBUG 或 dynamic_debug 时输出\n");   /* 对应 KERN_DEBUG */
dev_info(dev, "device-specific message\n");
dev_dbg(dev, "device debug\n");
```

**注意**：`pr_info` 缺少换行 `\n` 会导致相邻日志粘连，这是最常见的低级错误。

查看与调节：

```bash
dmesg | tail -30
dmesg -w                     # 持续跟踪（相当于 tail -f）
dmesg -T                     # 把时间戳转成人类可读时间
dmesg -l err,warn            # 只看错误与警告
dmesg --clear                # 清空环形缓冲区

cat /proc/sys/kernel/printk       # 输出 "当前 默认 最小 最大"，例如 4 4 1 7
echo 7 > /proc/sys/kernel/printk  # 打印所有等级（临时）
dmesg -n 8                        # 同上，用 dmesg 命令设置
```

`/proc/sys/kernel/printk` 的四个数字含义（`Documentation/admin-guide/sysctl/kernel.rst`）：

| 位置 | 含义 |
| --- | --- |
| 第 1 个 | 当前 `console_loglevel`：等级数值 **小于** 它的消息才会打印到控制台 |
| 第 2 个 | 未指定等级时的默认等级 |
| 第 3 个 | 最小允许值 |
| 第 4 个 | 启动时的默认值 |

内核日志是**环形缓冲区**（`kernel/printk/`），大小由 `CONFIG_LOG_BUF_SHIFT` 决定，约 2^(shift) 字节。日志刷得太快时早期日志会被覆盖 —— 提高该值或加 `log_buf_len=4M` 启动参数。

### 5.2 dynamic_debug —— 生产级按需打开调试日志

`pr_debug()` / `dev_dbg()` 默认被编译掉。打开 `CONFIG_DYNAMIC_DEBUG=y` 后，它们变成运行时可单独开关的调用点，开销接近零。

```bash
# 1) 确认已挂载 debugfs（内核 7.x 中 dynamic_debug 入口在 debugfs 下）
mount | grep debugfs || sudo mount -t debugfs none /sys/kernel/debug
ls /sys/kernel/debug/dynamic_debug/control

# 2) 打开某个文件里的全部调试输出
echo -n 'file read_write.c +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

# 3) 打开整个模块
echo -n 'module nvme +p' | sudo tee /sys/kernel/debug/dynamic_debug/control

# 4) 关闭
echo -n 'module nvme -p' | sudo tee /sys/kernel/debug/dynamic_debug/control

# 5) 查看当前生效的调用点（带 =p 的才是开启的）
sudo grep -c '=p' /sys/kernel/debug/dynamic_debug/control
```

启动参数写法（等价于内核命令行追加）：

```
dyndbg="file read_write.c +p"
dyndbg="module nvme +p; module xhci_hcd +p"
```

代码里也可以声明：

```c
#define pr_fmt(fmt) KBUILD_MODNAME ": " fmt
#include <linux/printk.h>
#include <linux/dynamic_debug.h>

static int dbg;
module_param(dbg, int, 0644);
dynamic_debug_init...   /* 一般不需要手写；用 module_param + DEFINE_DYNAMIC_DEBUG_METADATA */
```

最简做法是用 `module_param` 配合 `pr_debug`，或在模块中用：

```c
DEFINE_DYNAMIC_DEBUG_METADATA(my_dbg, "my message");
if (DYNAMIC_DEBUG_BRANCH(my_dbg))
    __dynamic_pr_debug(&my_dbg, "val=%d\n", val);
```

### 5.3 QEMU + GDB 源码级单步

关键点：**调试符号在 `vmlinux`（ELF）里，不在 `bzImage` 里**。所以必须先 `make` 出 `vmlinux`，并确保 `CONFIG_DEBUG_INFO=y`。

```bash
# 1) 生成 GDB 辅助脚本（提供 lx-symbols、lx-dmesg、lx-ps 等命令）
cd "$KSRC"
make scripts_gdb

# 2) 带 gdbstub 启动 QEMU；-S 让 CPU 在第一条指令前冻结
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel arch/x86/boot/bzImage \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init" \
  -nographic -no-reboot \
  -s -S
```

另开一个终端：

```bash
cd "$KSRC"
gdb vmlinux
```

在 GDB 里：

```gdb
# 允许自动加载脚本（首次需要）
# 当前目录即内核源码树（$KSRC）
add-auto-load-safe-path .
set confirm off

target remote :1234          # 连上 QEMU 的 gdbstub
lx-symbols                   # 加载内核符号与已加载模块的符号（来自 scripts/gdb）

break start_kernel           # 在 C 入口下断点
continue                     # 继续执行，命中后停在 start_kernel
list                         # 查看源码
next                         # 单步（不进入函数）
step                         # 单步（进入函数）
bt                           # 回溯调用栈
p init_task                  # 打印全局变量
p $lx_current()              # 打印当前 task_struct（scripts/gdb 提供）

# 跟踪一次系统调用
break __x64_sys_write
continue
bt
finish
```

`scripts/gdb/`（实测存在）提供的常用命令：

| 命令 | 作用 |
| --- | --- |
| `lx-symbols` | 加载/刷新内核与模块符号 |
| `lx-dmesg` | 直接读内核 log 缓冲区（即使串口没输出） |
| `lx-ps` | 列出进程 |
| `lx-lsmod` | 列出模块 |
| `lx-list` | 遍历 `list_head` 链表 |
| `lx-device-list-bus` / `lx-device-list-class` | 遍历设备树 |

调试内核模块的细节见 [03-内核模块开发](03-内核模块开发.md#8-调试与-oops-阅读)。

### 5.4 KASAN / KCSAN / KFENCE

三者都用于「在开发阶段主动暴露内存/并发错误」，是内核安全研究的基础设施。

| 工具 | 检测目标 | 配置项 | 文档 |
| --- | --- | --- | --- |
| KASAN | 越界访问、UAF（use-after-free，释放后使用） | `CONFIG_KASAN=y` + `CONFIG_KASAN_GENERIC=y` | `Documentation/dev-tools/kasan.rst` |
| KCSAN | 数据竞争（data race） | `CONFIG_KCSAN=y` | `Documentation/dev-tools/kcsan.rst` |
| KFENCE | 极低开销的采样内存错误检测，适合常开 | `CONFIG_KFENCE=y` | `Documentation/dev-tools/kfence.rst` |
| KMSAN | 未初始化内存使用 | `CONFIG_KMSAN=y`（x86_64 支持） | `Documentation/dev-tools/kmsan.rst` |
| UBSAN | 未定义行为（除零、移位越界等） | `CONFIG_UBSAN=y` | `Documentation/dev-tools/ubsan.rst` |
| kmemleak | 内存泄漏 | `CONFIG_DEBUG_KMEMLEAK=y` | `Documentation/dev-tools/kmemleak.rst` |

实测 `lib/Kconfig.kasan` 中 KASAN 的三种模式：`CONFIG_KASAN_GENERIC`（多架构，类同用户态 ASan）、`CONFIG_KASAN_SW_TAGS`（arm64）、`CONFIG_KASAN_HW_TAGS`（arm64 MTE）。x86_64 用 `KASAN_GENERIC`。

KASAN 的开销（来自 `lib/Kconfig.kasan` 的 help 原文）：启动时消耗约 1/8 可用内存，动态分配有约 50% 额外开销，整体性能下降约 3 倍。

KASAN 报告格式示例（真实结构）：

```
BUG: KASAN: slab-use-after-free in mydriver_read+0x1a3/0x2c0 [mydriver]
Read of size 8 at addr ffff88810a3b4c00 by task cat/1234

CPU: 1 PID: 1234 Comm: cat Not tainted 7.3.0-rc3-learn #1
Call Trace:
 <TASK>
 dump_stack_lvl+0x5a/0x80
 print_report+0x...
 kasan_report+0x...
 mydriver_read+0x1a3/0x2c0 [mydriver]
 vfs_read+0x...
 ...
Allocated by task 1201:
 kasan_save_stack+0x...
 kmalloc_trace+0x...
 mydriver_open+0x...
Freed by task 1205:
 kfree+0x...
 mydriver_release+0x...
```

阅读要点：**第一行 `BUG: KASAN: <类型> in <函数>`** 是结论；`Allocated by` / `Freed by` 告诉你对象生命周期，UAF 的修复方向通常在里面。

有用的 KASAN 启动参数（实测 `Documentation/dev-tools/kasan.rst`）：

| 参数 | 作用 |
| --- | --- |
| `kasan.fault=report` / `=panic` / `=panic_on_write` | 报告后是继续还是直接 panic。`panic` 适合配合 GDB 抓现场 |
| `kasan_multi_shot` | 每次都报告，而不是只报第一次 |
| `kasan.stacktrace=off` / `=on` | 是否打印分配/释放栈 |
| `kasan.vmalloc=off` | 关闭 vmalloc 区域的标记 |
| `kasan.page_alloc.sample=N` | 只对每 N 次页分配打标签，降低开销 |

在 QEMU 中的建议启动行（`kasan_multi_shot` 是**不带值的裸参数**）：

```bash
# 每次越界都报告，便于连续观察
-append "console=ttyS0 rdinit=/init kasan.fault=report kasan_multi_shot"

# 或：一遇错就 panic，配合 QEMU -s -S 用 GDB 抓第一现场
-append "console=ttyS0 rdinit=/init kasan.fault=panic"
```

> KCSAN 报告形如 `BUG: KCSAN: data-race in func_a / func_b`，随后会打印两个访问点各自的调用栈 —— 修复时两边都要加锁或改用 `READ_ONCE()`/`WRITE_ONCE()`。
> 注意：KASAN 与 KCSAN 不能同时使用。

### 5.5 ftrace —— 内核自带函数跟踪

tracefs 挂载点：现代内核默认可用 `/sys/kernel/tracing`（也可挂到 `/sys/kernel/debug/tracing`）。

```bash
# 1) 挂载
mount -t tracefs nodev /sys/kernel/tracing     # 或
sudo mount -t debugfs none /sys/kernel/debug
T=/sys/kernel/tracing
ls $T

# 2) 函数图跟踪：看某次 open 的完整调用链
cd $T
echo function_graph > current_tracer
echo do_sys_openat2 > set_graph_function
echo 1 > tracing_on
cat /tmp/whatever          # 触发一次 open
echo 0 > tracing_on
cat trace | head -60
```

常用控制文件：

| 文件 | 作用 |
| --- | --- |
| `available_tracers` | 可用跟踪器列表（`function`、`function_graph`、`nop`、`hwlat`、`osnoise` 等） |
| `current_tracer` | 当前跟踪器 |
| `set_ftrace_filter` | 只跟踪指定函数（支持通配符 `vfs_*`） |
| `set_ftrace_notrace` | 排除指定函数 |
| `set_graph_function` | `function_graph` 模式的根函数 |
| `available_filter_functions` | 所有可被跟踪的函数（需 `CONFIG_FUNCTION_TRACER`） |
| `trace` | 读取跟踪结果（快照） |
| `trace_pipe` | 流式读取，读到即消费 |
| `tracing_on` | 0/1 开关 |
| `trace_options` | 各种开关（`funcgraph-proc`、`sym-userobj` 等） |

事件跟踪（tracepoint，编译期静态插桩点）：

```bash
cd $T
echo 0 > tracing_on
echo > trace
echo 1 > events/syscalls/sys_enter_openat/enable
echo 1 > tracing_on
ls /tmp > /dev/null
echo 0 > tracing_on
cat trace
```

用 `trace-cmd` 更省事：

```bash
sudo apt install -y trace-cmd
sudo trace-cmd record -p function_graph -g do_sys_openat2 ls
sudo trace-cmd report | head -40
```

**注意**：ftrace 有全局唯一性，同一时刻只能有一个跟踪器生效；多用户共享的系统上会互相干扰。

### 5.6 perf —— 采样剖析

```bash
sudo apt install -y linux-perf        # Debian：包名也可能是 linux-tools-$(uname -r)
sudo pacman -S --needed perf          # Arch

# 采样 5 秒，记录调用栈
sudo perf record -a -g -- sleep 5
sudo perf report                      # 交互式浏览，方向键选择

# 实时 Top
sudo perf top

# 跟踪系统调用（类似 strace 但开销更低）
sudo perf trace -a -- sleep 3
sudo perf trace -e openat,openat2 -- ls /tmp

# 统计某进程的硬件事件
sudo perf stat -p <pid> -- sleep 5
```

内核侧需要 `CONFIG_PERF_EVENTS=y`（默认开启）和符号信息（`CONFIG_KALLSYMS=y`）。

### 5.7 eBPF / bpftrace —— 可编程的内核观测

bpftrace 用一行脚本就能统计 syscall 耗时（eBPF 程序由内核 JIT 执行，无需改内核、无需重编译模块）：

```bash
sudo apt install -y bpftrace          # Debian / Kali
sudo pacman -S --needed bpftrace      # Arch

# 1) 统计各进程发起的 openat 次数
sudo bpftrace -e 'tracepoint:syscalls:sys_enter_openat { @[comm] = count(); }'

# 2) 统计一次 write 的耗时分布（纳秒 -> 直方图）
sudo bpftrace -e '
tracepoint:syscalls:sys_enter_write { @start[tid] = nsecs; }
tracepoint:syscalls:sys_exit_write  /@start[tid]/ {
    @ns = hist(nsecs - @start[tid]);
    delete(@start[tid]);
}'

# 3) 按进程统计 syscall 总耗时
sudo bpftrace -e 'tracepoint:raw_syscalls:sys_exit { @[comm] = sum(args->id); }'
```

| 探针类型 | 语法 | 说明 |
| --- | --- | --- |
| `tracepoint:` | `tracepoint:syscalls:sys_enter_openat` | 稳定 ABI，推荐优先使用 |
| `kprobe:` | `kprobe:vfs_read` | 任意内核函数入口（`CONFIG_KPROBES`） |
| `kretprobe:` | `kretprobe:vfs_read` | 函数返回处 |
| `uprobe:` | `uprobe:/bin/bash:readline` | 用户态函数 |
| `profile:` | `profile:hz:99` | 周期性采样 |
| `software:` / `hardware:` | `software:faults:1` | perf 事件 |
| `BEGIN` / `END` | — | bpftrace 脚本的开始/结束 |

前置条件：`CONFIG_BPF=y`、`CONFIG_BPF_SYSCALL=y`、`CONFIG_BPF_JIT=y`、`CONFIG_KPROBES=y`、`CONFIG_DEBUG_INFO_BTF=y`（CO-RE 需要）。

更多：`Documentation/bpf/`（实测存在 `bpf_design_QA.rst`、`kfuncs.rst`、`btf.rst`、`libbpf/` 等）。

### 5.8 kdump / crash —— 事后分析

`printk` 只能看到日志；要看 panic 时刻的完整内存，需要**崩溃转储**（crash dump）。

| 组件 | 配置 / 工具 | 说明 |
| --- | --- | --- |
| kexec | `CONFIG_KEXEC=y`、`CONFIG_KEXEC_CORE=y` | 允许从一个内核直接跳入另一个内核，无需经过 BIOS |
| kdump | `CONFIG_CRASH_DUMP=y`、`CONFIG_PROC_VMCORE=y` | 崩溃时由 kexec 启动「捕获内核」，把内存写成 `/proc/vmcore` |
| 用户态工具 | `kdump-tools`、`makedumpfile` | 配置与压缩 vmcore |
| 分析器 | `crash` | `crash vmlinux vmcore` |
| GDB 宏 | `Documentation/admin-guide/kdump/gdbmacros.txt` | 在无 `crash` 时用 GDB 分析 vmcore |

```bash
sudo apt install -y kdump-tools crash
# 配置 /etc/default/kdump-tools，然后
sudo systemctl enable --now kdump-tools
cat /proc/cmdline        # 应包含 crashkernel=...，否则捕获内核无法预留内存

# 崩溃后
sudo ls /var/crash/
sudo crash /usr/lib/debug/boot/vmlinux-$(uname -r) /var/crash/<时间戳>/vmcore
crash> bt          # 回溯
crash> log         # 内核日志
crash> ps          # 进程列表
crash> struct task_struct <地址>
```

在 QEMU 里做实验时，更简单的替代方案是：`kasan.fault=panic` + `-s -S`，panic 后直接用 GDB 连上去看现场。或者用 QEMU 的 `-d int` 与 QEMU monitor 的 `info registers`。

## 6. 常见构建错误与解决

| 错误信息 | 原因 | 解决 |
| --- | --- | --- |
| `*** Unable to find the ncurses library` | 缺 `libncurses-dev` | `sudo apt install libncurses-dev` |
| `fatal error: openssl/bio.h: No such file or directory` | 缺 `libssl-dev` | `sudo apt install libssl-dev` |
| `fatal error: gelf.h: No such file or directory` | 缺 `libelf-dev` | `sudo apt install libelf-dev` |
| `*** No rule to make target 'debian/certs/debian-uefi-certs.pem'` | 发行版配置里指定了签名证书文件但不存在 | 关掉 `CONFIG_SYSTEM_TRUSTED_KEYS` / `CONFIG_SYSTEM_REVOCATION_KEYS`（设为空字符串），或 `scripts/config --disable SYSTEM_TRUSTED_KEYS` |
| `BTF: .tmp_vmlinux.btf: pahole (pahole) is not available` | 缺 `pahole`（`CONFIG_DEBUG_INFO_BTF=y`） | `sudo apt install dwarves`；或 `scripts/config --disable DEBUG_INFO_BTF` |
| `error: code model kernel does not support PIC mode` | 编译器/架构不匹配 | 确认 `ARCH=x86_64` 且 `CROSS_COMPILE` 为空 |
| `flex: command not found` / `bison: command not found` | 缺词法/语法分析器 | `sudo apt install flex bison` |
| `No space left on device` | 磁盘不足（构建峰值 10~20 GB） | 用 `O=` 指向大分区；或 `CONFIG_DEBUG_INFO=n` 减小产物 |
| `BTF ids were not found in vmlinux` | 增量构建残留 | `make clean && make` |
| `modpost: ... undefined!` | 模块引用了未导出的内核符号 | 见 [03-内核模块开发](03-内核模块开发.md#7-常见错误与排查) |
| `Killed`（无其他信息） | OOM：并行度过高 | 降低 `-j`，例如 `make -j4` |
| `make[1]: *** wait: No child processes. Stop.` | 目录名含空格或特殊字符 | 把源码移到无空格路径 |
| 编译成功但启动后 `Kernel panic - not syncing: VFS: Unable to mount root fs` | 没提供根文件系统 | 见 §4.3 制作 initramfs |
| 启动后无任何输出 | 少了 `console=ttyS0` 或没加 `-nographic` | 补上 |
| `WARNING: modpost: module uses symbol X from namespace Y, but does not import it` | 符号命名空间（`MODULE_IMPORT_NS`）缺失 | 加 `MODULE_IMPORT_NS("Y")` |

排查任何构建问题，先看**第一个**错误（而非最后一个）：

```bash
make -j8 2>&1 | tee /tmp/build.log
grep -n -m1 -E "^make.*Error|error:" /tmp/build.log
```

## 7. 把自编译内核装到本机（⚠️ 危险）

⚠️ **风险**：改错 bootloader 配置或新内核无法启动，可能导致系统无法引导。请务必：

1. 先备份：`sudo cp -a /boot /boot.bak.$(date +%F)` 与 `sudo cp /etc/default/grub /etc/default/grub.bak`
2. 保留旧内核条目（不要 `apt autoremove` 掉当前内核）
3. 准备好 live USB 或另一台机器查资料
4. 优先在 QEMU 里验证新内核能启动，再装到本机

```bash
cd "$KSRC"
sudo make modules_install
sudo make install
sudo update-grub              # Debian / Ubuntu / Kali
# Arch：内核放 /boot 后用
#   sudo grub-mkconfig -o /boot/grub/grub.cfg
#   或（systemd-boot）直接用 mkinitcpio -P
```

**回滚**：

```bash
# GRUB：重启进入 "Advanced options for ..." 选择旧内核
sudo grep -n "" /boot/grub/grub.cfg | grep -i menuentry    # 确认旧条目还在

# 彻底撤销
sudo rm -f /boot/vmlinuz-7.3.0-rc3-learn \
           /boot/System.map-7.3.0-rc3-learn \
           /boot/config-7.3.0-rc3-learn \
           /boot/initrd.img-7.3.0-rc3-learn
sudo rm -rf /lib/modules/7.3.0-rc3-learn
sudo update-grub
```

`Arch` 上还要注意 `/etc/mkinitcpio.conf` 的 `MODULES` 与 `HOOKS`，以及 `CONFIG_LOCALVERSION` 生成的版本目录名。

## 8. 一条命令串起全流程（复制即用）

```bash
set -e
KSRC=$(pwd)/kernel/src/linux   # 在仓库根目录执行
OUT=/tmp/kbuild-learn

cd "$KSRC"
make -s kernelversion

# 1) 配置：默认 + KVM 客户机片段（便于 QEMU 启动）
make O="$OUT" defconfig kvm_guest.config

# 2) 打开几个关键调试项
KCONFIG_CONFIG="$OUT/.config" "$KSRC/scripts/config" \
  --file "$OUT/.config" \
  --enable DEBUG_INFO --enable KALLSYMS_ALL \
  --set-str LOCALVERSION "-learn"
make O="$OUT" olddefconfig

# 3) 编译
make O="$OUT" -j"$(nproc)"

# 4) 制作 initramfs
rm -rf /tmp/initramfs && mkdir -p /tmp/initramfs/{bin,dev,proc,sys,tmp}
cp "$(command -v busybox)" /tmp/initramfs/bin/busybox
cd /tmp/initramfs && ./bin/busybox --install -s bin
printf '#!/bin/busybox sh\n/bin/busybox --install -s /bin\nmount -t proc none /proc\nmount -t sysfs none /sys\nmount -t devtmpfs none /dev 2>/dev/null\necho "=== booted ==="\nuname -a\nexec /bin/sh\n' > init
chmod +x init
find . -print0 | cpio --null -ov --format=newc 2>/dev/null | gzip -9 > /tmp/initramfs.cpio.gz

# 5) 启动
qemu-system-x86_64 \
  -m 2G -smp 2 \
  -kernel "$OUT/arch/x86/boot/bzImage" \
  -initrd /tmp/initramfs.cpio.gz \
  -append "console=ttyS0 rdinit=/init loglevel=7 panic=1" \
  -nographic -no-reboot
```

验证标准：串口出现内核启动日志，最后进入 `=== booted ===` 与 BusyBox shell 提示符。做到这一步，就可以进入 [02-源码结构与阅读方法](02-源码结构与阅读方法.md) 与 [03-内核模块开发](03-内核模块开发.md)。
