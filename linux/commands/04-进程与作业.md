### ps — 进程快照

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：⚠️ **BSD 风格与 UNIX 风格选项混用会被 ps 拒绝**，两套不能混

#### 语法
```bash
ps [选项]
```

#### 三种风格
| 风格 | 示例 | 特点 |
|------|------|------|
| UNIX | `ps -ef` | 带 `-`，字段名固定 |
| BSD | `ps aux` | 不带 `-` |
| GNU 长选项 | `ps --sort=-%cpu` | 可与其他混用 |

#### 高频选项
| 选项 | 含义 |
|------|------|
| `aux` | 所有用户的所有进程（BSD 风格） ⭐ |
| `-ef` | 所有进程完整格式（UNIX 风格） ⭐ |
| `-e` | 所有进程 |
| `-f` | 完整格式（含 PPID、UID、STIME） |
| `-o 字段,...` | 自定义输出列 ⭐ |
| `--sort=-%cpu` | 按 CPU 降序（`-` 表示降序） ⭐ |
| `-u 用户` | 只看某用户 |
| `-p PID` | 指定 PID |
| `-C 命令名` | 按命令名 |
| `-t TTY` | 按终端 |
| `-H` | 显示线程 |
| `-L` | 显示线程与 LWP |
| `-forest` / `--forest` | 树状缩进 ⭐ |
| `--no-headers` | 不显示表头（脚本用） |
| `-ww` | 不截断命令行宽度 |

#### 常用输出字段
| 字段 | 含义 |
|------|------|
| `pid` | 进程 ID |
| `ppid` | 父进程 ID ⭐ |
| `comm` | 可执行文件名（截断到 15 字符） |
| `args` / `cmd` | 完整命令行 |
| `stat` | 状态码 |
| `rss` | 常驻内存（KiB） |
| `vsz` | 虚拟内存 |
| `%cpu` / `%mem` | CPU / 内存占比 |
| `etime` | 已运行时长 |
| `lstart` | 启动时刻 |
| `ni` | nice 值 |
| `psr` | 运行在哪个 CPU |
| `wchan` | 内核等待通道 ⭐ |
| `lwp` | 线程 ID |
| `nlwp` | 线程数 |

#### 实战示例
```bash
# 场景：找 CPU 占用最高的 10 个进程 ⭐
$ ps -eo pid,ppid,user,pcpu,pmem,etime,cmd --sort=-pcpu | head -11

# 场景：找内存占用最高的
$ ps -eo pid,ppid,user,pmem,rss,cmd --sort=-rss | head -6

# 场景：看进程树（父子关系）
$ ps -ef --forest | head -30

# 场景：只看某用户的进程
$ ps -u alice -o pid,ppid,stat,etime,cmd

# 场景：🧪 查看某进程在等什么内核资源
$ ps -o pid,stat,wchan,cmd -p 1234
    PID STAT WCHAN  CMD
   1234 S    wait    /usr/bin/app
#            ↑ 卡在 wait，可能是等网络或磁盘

# 场景：查看线程
$ ps -T -p 1234
$ ps -eLf | grep 1234 | head

# 场景：查某进程的启动时间与运行时长
$ ps -o pid,lstart,etime,cmd -p 1234

# 场景：找僵尸进程 ⭐
$ ps -eo pid,ppid,stat,cmd | awk '$3 ~ /^Z/'

# 场景：脚本里判断进程是否存在
$ ps -p 1234 -o comm= >/dev/null && echo running

# 场景：🔐 找可疑进程（可执行文件被删、在 /tmp 运行）
$ ps -eo pid,user,cmd | grep -E '/tmp/|/dev/shm/|\./'
$ sudo ls -l /proc/*/exe 2>/dev/null | grep -E 'deleted|/tmp'
```

#### 输出解读
`STAT` 列字符：

| 字符 | 含义 | 字符 | 含义 |
|------|------|------|------|
| `R` | 运行/就绪 | `S` | 可中断睡眠 |
| `D` | 不可中断睡眠（I/O） | `T` | 已停止（`Ctrl+Z`） |
| `t` | 调试停止 | `Z` | 僵尸 |
| `I` | 内核空闲线程 | `<` | 高优先级 |
| `N` | 低优先级 | `L` | 页面被锁定 |
| `s` | 会话首进程 | `l` | 多线程 |
| `+` | 前台进程组 | | |

`ps aux` 的表头：

| 列 | 含义 |
|----|------|
| `USER` | 有效用户名 |
| `PID` / `%CPU` / `%MEM` | — |
| `VSZ` | 虚拟内存大小（KiB） |
| `RSS` | 常驻内存（KiB） |
| `TTY` | 终端（`?` = 无终端，即守护进程） ⭐ |
| `STAT` | 状态 |
| `START` | 启动时间 |
| `TIME` | 累计 CPU 时间 |
| `COMMAND` | 命令行 |

#### 常见坑
- ⚠️ **不能混用 BSD 与 UNIX 风格**：`ps aux -f` 会报 `error: conflicting format options`。要么 `ps aux`，要么 `ps -ef`。
- **`ps aux | grep X` 会匹配到 `grep X` 自身**。用 `pgrep`，或 `grep -v grep`，或 `grep '[X]'` 技巧。
- **`%CPU` 是「进程生命周期内的平均 CPU 占比」**，不是瞬时值。刚启动的进程数值可能极高（如 100%×短时间）。
- **`VSZ` 不代表真实内存占用**，它包含未使用的映射（如 mmap 的大文件、预留堆）。看 `RSS`。
- **`COMMAND` 默认被截断到终端宽度**（非管道时），脚本里要用 `-ww` 或指定 `-o args=`。
- **`ps` 读的是 `/proc/<pid>/*`**，有极短的竞态窗口：进程可能在你看到的瞬间已经消失，导致字段显示为 `-`。
- **`ps` 不显示内核线程**（`-e` 也看不到部分），要 `ps -eLf` 或 `ps ax` 配合。

#### 相关命令
`top` · `pgrep` · `pstree` · `lsof` · `/proc`

### top — 实时进程监视

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：`procps` 与 `busybox` 的 top 选项差异很大

```bash
top [选项]
```

| 选项 | 含义 |
|------|------|
| `-d N` | 刷新间隔秒（默认 3） ⭐ |
| `-n N` | 刷新 N 次后退出 ⭐ |
| `-b` | 批处理模式（适合重定向/脚本） ⭐ |
| `-p PID,...` | 只看指定 PID |
| `-u 用户` | 只看某用户 |
| `-o 字段` | 排序字段（如 `-o %MEM`） |
| `-H` | 显示线程 |
| `-c` | 显示完整命令行 |
| `-w N` | 输出宽度（`-w 512`） |
| `-1` | 显示每个 CPU 核心 |

#### 关键交互键
| 键 | 作用 |
|----|------|
| `1` | 展开每个 CPU 核心 |
| `H` | 切换线程显示 |
| `c` | 切换完整命令行 |
| `M` | 按内存排序 ⭐ |
| `P` | 按 CPU 排序 ⭐ |
| `T` | 按运行时间排序 |
| `k` | 杀进程（输入 PID 和信号） |
| `r` | renice |
| `u` | 过滤用户 |
| `f` | 选择显示字段 |
| `z` | 彩色显示 |
| `V` | 树状显示 |
| `W` | 保存当前配置为默认 |
| `q` | 退出 |

#### 实战示例
```bash
# 场景：只看某进程，1 秒刷新
$ top -d 1 -p 1234

# 场景：批处理快照（重定向、脚本、日志）
$ top -bn1 | head -20
top - 09:30:00 up 11:28,  3 users,  load average: 0.52, 0.61, 0.58
Tasks: 312 total,   1 running, 310 sleeping,   0 stopped,   1 zombie
%Cpu(s):  3.2 us,  1.1 sy,  0.0 ni, 95.4 id,  0.3 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :  15872.0 total,   2144.3 free,   8123.5 used,   5604.2 buff/cache
MiB Swap:   8192.0 total,   8192.0 free,      0.0 used.   6512.1 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1234 alice     20   0 2456789 512345  12345 S   12.3   3.2  10:23.45 app

# 场景：按内存排序的前 5 行
$ top -bn1 -o %MEM | head -12 | tail -5

# 场景：监控整个 CPU（用于压测观察）
$ top -d 1 -b | grep --line-buffered '^%Cpu' | head -20

# 场景：找出所有线程的 CPU 占用（-H 加批处理）
$ top -bH -n1 -o %CPU | head -15
```

#### 输出解读

**第一行（负载）**：
```
top - 09:30:00 up 11:28,  3 users,  load average: 0.52, 0.61, 0.58
```
`load average` 是 1/5/15 分钟的平均「可运行 + 不可中断」进程数。**与 CPU 核数比较**：8 核机器上 load 8 表示饱和，load 16 表示严重过载。

**第二行（任务）**：`Tasks` 总数、运行、睡眠、停止、**僵尸**数。

**第三行（CPU）**：

| 字段 | 含义 |
|------|------|
| `us` | 用户态时间 |
| `sy` | 内核态时间 |
| `ni` | nice 调整过的用户态时间 |
| `id` | 空闲 |
| `wa` | **等 I/O**（>10% 说明磁盘是瓶颈） ⭐ |
| `hi` | 硬中断 |
| `si` | 软中断（网络中断多时会高） |
| `st` | **被 hypervisor 偷走的时间**（虚拟机特有，>5% 说明宿主争抢） ⭐ |

**第四/五行（内存）**：
```
MiB Mem :  15872.0 total,   2144.3 free,   8123.5 used,   5604.2 buff/cache
MiB Swap:   8192.0 total,   8192.0 free,      0.0 used.   6512.1 avail Mem
```
`avail Mem` 是「新程序可用的大致内存」（含可回收的缓存），比 `free` 更有参考价值。

**进程行**：

| 列 | 含义 |
|----|------|
| `PR` | 优先级（`rt` = 实时） |
| `NI` | nice 值（-20 ~ 19） |
| `VIRT` | 虚拟内存（含映射与预留） |
| `RES` | 常驻物理内存 ⭐ |
| `SHR` | 共享内存（库、tmpfs） |
| `S` | 状态（同 `ps` 的 STAT） |
| `TIME+` | 累计 CPU 时间（百分之一秒精度） |

#### 常见坑
- ⚠️ **`top` 的 `%CPU` 刷新值在批处理模式（`-b`）下是「自上次刷新以来的增量」**，单次 `-bn1` 的 CPU% 是从进程启动算起的平均值（不可靠）。要准确测 CPU 用 `pidstat` 或 `top -d 1 -b -n 3`。
- **`VIRT` 迷惑性极强**：Java/Python 进程的 VIRT 常达几十 GB（预留），实际用 `RES`。
- **`load average` 包含 `D` 状态进程**，所以纯 I/O 瓶颈也会让 load 很高而 CPU 空闲。
- **`top` 按 `q` 退出前会写 `~/.toprc`**（按 `W` 时），可能影响下次启动的显示。
- **`top -b | head` 会因 SIGPIPE 让 top 报错退出**，用 `-n1` 限制次数更干净。
- `top` 的字段宽度固定，`COMMAND` 会被截断，用 `-c -w 512` 展开。
- 容器里 `top` 看到的可能是宿主的全部进程（取决于 `pid` namespace 与 `/proc` 挂载）。用 `top` 前先确认 `/proc` 的可见性。

#### 相关命令
`htop` · `atop` · `glances` · `pidstat` · `vmstat`

### htop — 交互式进程监视

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，需安装

```bash
htop [选项]
```

| 选项 | 含义 |
|------|------|
| `-d N` | 刷新间隔（十分之一秒） |
| `-u 用户` | 只看某用户 |
| `-p PID,...` | 只看指定 PID |
| `-t` | 树状模式 |
| `-s 字段` | 初始排序字段 |
| `-C` | 单色 |
| `--no-color` | 无色 |

#### 关键交互键
| 键 | 作用 |
|----|------|
| `F1` `h` | 帮助 |
| `F2` `S` | Setup（配置显示字段） |
| `F3` `/` | 搜索 |
| `F4` `\` | 过滤（只显示匹配） |
| `F5` `t` | 树状视图 ⭐ |
| `F6` `>` | 选择排序字段 |
| `F7` `]` | 提高 nice |
| `F8` `[` | 降低 nice |
| `F9` `k` | 杀进程（选信号） ⭐ |
| `F10` `q` | 退出 |
| `u` | 过滤用户 |
| `l` | 显示该进程打开的文件（`lsof`） |
| `s` | 用 strace 跟踪该进程 ⭐ |
| `e` | 显示环境变量 ⭐ |
| `H` | 切换线程显示 |
| `M` | 按内存排序 ⭐ |
| `P` | 按 CPU 排序 ⭐ |
| `T` | 按时间排序 |
| `a` | 设置 CPU 亲和性 |
| `c` | 显示完整命令行 + 可执行路径 |

```bash
$ htop
$ htop -u alice
$ htop -t -p 1234
$ htop --tree -d 5
```

#### 输出解读
顶部的彩色条：

| 颜色 | 含义 |
|------|------|
| 绿（CPU） | 用户态 |
| 蓝 | 低优先级（nice） |
| 红 | 内核态 |
| 橙/黄 | 软/硬中断 |
| 灰 | I/O 等待 |

底部 `F1`–`F10` 菜单是操作提示。

#### 常见坑
- **`htop` 的 CPU% 是相对于「全部核心」的百分比**，可能显示 >100%（多线程进程）。`top` 默认同理。想看到「单核百分比」要在 htop 里用 Setup 改成 `Irix mode` 关闭。
- **在 `-p` 指定 PID 时不能删除进程列表**，只能退出重开。
- **`e` 显示环境变量可能泄露密钥**，共享屏幕（录屏、会议）时要小心 🔐。
- **htop 不是 POSIX**，最小化系统里没有，脚本里别用。
- 容器里 `htop` 需要挂载宿主的 `/proc` 才能看到全部进程；默认只看容器内。

#### 相关命令
`top` · `atop` · `glances` · `btop`

### pstree — 树状显示进程关系

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
pstree [选项] [PID或用户]
```

| 选项 | 含义 |
|------|------|
| `-p` | 显示 PID ⭐ |
| `-u` | 显示用户切换（UID 变化时标注） |
| `-a` | 显示命令行参数 |
| `-n` | 按 PID 排序（默认按名字） |
| `-h` | 高亮当前进程及其祖先 ⭐ |
| `-l` | 不截断长行 |
| `-A` / `-U` / `-G` | ASCII / UTF-8 / VT100 画线 |
| `-s PID` | 显示指定进程的祖先链 ⭐ |
| `-c` | 不折叠相同的子树 |
| `-t` | 显示线程 |

```bash
# 场景：看整体进程树
$ pstree -p | head -20
systemd(1)─┬─NetworkManager(623)─┬─{NetworkManager}(645)
           │                     └─{NetworkManager}(646)
           ├─sshd(892)───sshd(12345)───bash(12346)───pstree(12360)

# 场景：看某进程的祖先（它是谁拉起来的）⭐
$ pstree -sp 1234
systemd(1)───sshd(892)───sshd(12345)───bash(12346)───app(1234)

# 场景：高亮当前 shell 的位置
$ pstree -h

# 场景：显示用户切换（发现 su/sudo 的踪迹）⭐
$ pstree -up | head -30

# 场景：🔐 找可疑的进程链（Web 服务 → shell）
$ pstree -ap | grep -E 'nginx|apache|php|python.*bash|sh -c'

# 场景：显示线程
$ pstree -pt -p 1234

# 场景：ASCII 输出（便于复制到文档）
$ pstree -A -p
```

#### 输出解读
- 相同名字与参数的分支会被**折叠**成 `N*[name]`。
- `{name}` 花括号是**线程**。
- `-u` 时，若有效用户变化会显示 `(uid)`。

#### 常见坑
- **`pstree` 默认按名字排序**，不是 PID。要看「最近启动的顺序」用 `-n`。
- **默认会折叠相同的子树**，看起来「少了进程」。要完整展开用 `-c`。
- **`pstree` 只显示有父子的进程**，孤立的进程（PPID=1 且无子进程）会直接挂在 `systemd` 下，不显眼。
- **进程树在系统繁忙时会「跳变」**（进程创建/退出快），可能看到不完整的关系。
- 容器里进程树的根是容器内的 PID 1，看不到宿主。
- `-s PID` 的 `-s` 是「show parents」，输出从根到该进程，**方向是自上而下**（不是从该进程往上）。

#### 相关命令
`ps --forest` · `top -V`（树状）· `systemd-cgls`

### pgrep — 按条件查找进程 PID

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
pgrep [选项] 模式
```

| 选项 | 含义 |
|------|------|
| （默认） | 匹配**进程名**（15 字符以内） |
| `-f` | 匹配**完整命令行** ⭐ |
| `-a` | 同时显示命令行（`pgrep -a`） ⭐ |
| `-l` | 显示进程名 |
| `-u 用户` | 按用户 |
| `-U UID` | 按真实 UID |
| `-P PPID` | 按父进程 |
| `-t TTY` | 按终端 |
| `-n` | 只输出最新的一个 |
| `-o` | 只输出最老的一个 |
| `-c` | 只输出数量 ⭐ |
| `-x` | 精确匹配整个名字（不匹配其子串） ⭐ |
| `-i` | 忽略大小写 |
| `-v` | 反选 |
| `-d 分隔符` | 输出分隔符（默认换行） |
| `-g 组` | 按进程组 |
| `-s 会话` | 按会话 |

```bash
# 场景：查 PID
$ pgrep nginx
892
1234

# 场景：带命令行，确认要杀的是谁 ⭐
$ pgrep -a nginx
892 nginx: master process /usr/bin/nginx
1234 nginx: worker process

# 场景：按完整命令行匹配（能匹配参数）⭐
$ pgrep -af 'python.*worker'
5678 python3 /opt/app/worker.py --queue=default

# 场景：精确匹配（避免匹配到 nginx_exporter）
$ pgrep -x nginx
$ pgrep -x nginx_exporter

# 场景：计数
$ pgrep -c nginx
3

# 场景：按用户
$ pgrep -u alice -a

# 场景：找某进程的子进程
$ pgrep -P 1234 -a

# 场景：最新/最老的实例
$ pgrep -n nginx
$ pgrep -o nginx

# 场景：判断进程是否存在（脚本）
$ pgrep -x myservice >/dev/null && echo running || echo stopped

# 场景：⚠️ 先看再杀（避免误杀）
$ pgrep -af nginx
$ pkill -x nginx

# 场景：🔐 找异常进程
$ pgrep -af 'nc |ncat|socat|/tmp/'
$ pgrep -af 'curl|wget' | grep -v 'apt|pacman'
```

#### 输出解读
- 默认只输出 PID（每行一个）。
- `-a` 输出 `PID 命令行`。
- `-c` 只输出数字。
- 无匹配时**无输出且退出码 1**（脚本判断用）。

#### 常见坑
- ⚠️ **默认只匹配进程名的前 15 字符**（`comm` 字段的限制）。匹配长名字或带参数的必须 `-f`。
- ⚠️ **`-f` 是子串匹配，非常容易误伤**：`pgrep -f ssh` 会命中 `sshd`、`ssh-agent`、`vim ~/.ssh/config`。**必须先用 `-a` 确认**。
- **`pgrep -f` 也会匹配到 `pgrep` 自己**（在某些实现里）。用 `-x` 或排除自身 PID（`$$`）。
- **`-x` 与 `-f` 一起用时是「精确匹配整个命令行」**，不是精确匹配名字。
- **`pgrep` 看不到内核线程**（`kthreadd` 的子进程不可见，因为 `/proc` 里它们的 `comm` 是内核线程名但权限受限）。
- 进程名被修改过（`prctl(PR_SET_NAME)`）的进程，`pgrep`（非 `-f`）会匹配新名字。
- 在容器里 `pgrep` 只能看到命名空间内的进程。

#### 相关命令
`pkill` · `pidof` · `ps` · `kill`

### pkill — 按条件发送信号

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
pkill [选项] 模式
```

选项与 `pgrep` **完全相同**（`-f` `-u` `-x` `-n` `-o` `-P` `-t` 等），另有：

| 选项 | 含义 |
|------|------|
| `-信号` | 指定信号（如 `-9` `-TERM`），默认 SIGTERM |
| `-e` | 显示被杀进程的名字（`echo`） ⭐ |
| `--signal 信号` | 等价写法 |

```bash
# 场景：优雅终止（先看后杀）⭐
$ pgrep -a nginx
$ pkill -TERM -x nginx

# 场景：模糊匹配 + 显示结果
$ pkill -e -f 'python.*worker'
python killed (pid 5678)

# 场景：按用户杀（清理某用户所有进程）⭐
$ pkill -u alice
$ pkill -9 -u alice

# 场景：杀某进程的所有子进程
$ pkill -P 1234

# 场景：只杀最新的一个实例
$ pkill -n -f 'myapp'

# 场景：🧪 测试匹配范围（不真杀）——用 pgrep 代替
$ pgrep -af 'pattern'

# 场景：杀会话（登出用户的全部进程）
$ pkill -t pts/3
```

#### 输出解读
- 成功杀到至少一个进程返回 0；没有匹配返回 1。
- `-e` 会输出 `名字 killed (pid N)`。

#### ⚠️ 危险用法
```bash
$ pkill -f ssh          # ⚠️ 可能杀掉自己的 SSH 会话！因为 SSH 客户端命令行含 "ssh"
$ pkill -9 -f python    # ⚠️ 杀掉所有 python，包括系统关键服务
$ pkill -u root         # ⚠️ 可能杀掉系统关键进程（如果用 root 执行）
$ pkill -f '.*'         # ⚠️ 匹配所有进程 = 系统崩溃
```

**安全流程**：
```bash
# 1. 先列出
$ pgrep -af 'pattern'
# 2. 确认名单无误
# 3. 再杀（用 -x 精确名或 -f + 精确正则）
$ pkill -x 'exact_name'
```

#### 常见坑
- ⚠️ **`pkill -f ssh` 会杀掉你自己**（你的 SSH 客户端进程命令行含 `ssh`）。远程操作时先 `pgrep -af` 检查。
- **`pkill` 的模式是 ERE 正则**（不是 glob）。`pkill 'nginx*'` 里的 `*` 是「前一个字符重复零次或多次」，会匹配 `nginx`、`nginxx`、`ngin`，但**不会**匹配 `nginx-worker`。要匹配任意后缀用 `pkill 'nginx.*'`。
- **`pkill` 默认 SIGTERM**，程序可以忽略。要强杀加 `-9`。
- **`pkill` 发送 SIGKILL 后进程变成僵尸**（如果父进程不回收），需要父进程也处理。
- 杀进程后**立即判断是否还在**（有些程序收到 TERM 后要几十秒才退出）：
  ```bash
  $ pkill -TERM -x app; for i in {1..10}; do pgrep -x app >/dev/null || break; sleep 1; done
  ```
- 在 systemd 管理的服务上**不要用 pkill**，用 `systemctl stop`（否则 systemd 会因为进程意外退出而重启它，或状态不一致）。

#### 相关命令
`pgrep` · `kill` · `killall` · `systemctl stop`

### kill — 向进程发送信号

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：`-l` 输出格式略有差异；`kill` 是 shell 内建与外部命令并存

```bash
kill [-信号] PID...
kill -l [信号]
kill -s 信号 PID
```

| 写法 | 含义 |
|------|------|
| `kill PID` | 发送 SIGTERM(15) |
| `kill -9 PID` | 发送 SIGKILL |
| `kill -TERM PID` | 用名字（**推荐**，跨架构安全） |
| `kill -s TERM PID` | 另一种写法 |
| `kill -l` | 列出所有信号 |
| `kill -l 9` | 数字转名字 |
| `kill -l TERM` | 名字转数字 |
| `kill -0 PID` | 不发送，只检查进程是否存在 ⭐ |
| `kill -- -PGID` | 发送给整个进程组 ⭐ |
| `kill %1` | 按作业号（shell 内建功能） |

```bash
# 场景：优雅终止
$ kill 1234
$ kill -TERM 1234

# 场景：强杀（最后手段）
$ kill -9 1234

# 场景：多个 PID
$ kill -TERM 1234 5678 9012

# 场景：重载配置（守护进程的惯例）
$ sudo kill -HUP 1234
$ sudo systemctl reload nginx         # 更推荐

# 场景：用户自定义信号（很多服务用它做日志轮转）
$ sudo kill -USR1 1234

# 场景：检查进程是否存在（不发信号）⭐
$ kill -0 1234 && echo "存在" || echo "不存在"
$ kill -0 1234 2>/dev/null

# 场景：暂停/继续
$ kill -STOP 1234
$ kill -CONT 1234

# 场景：杀掉整个进程组（含所有子孙）⭐
$ ps -o pgid= -p 1234
  1234
$ kill -TERM -- -1234        # 注意 -- 与负号

# 场景：列出所有信号名
$ kill -l | tr ' ' '\n' | head -20

# 场景：信号号转名字
$ kill -l 15
TERM
$ kill -l 137
# 137 不是标准信号，>128 表示被信号 (137-128)=9 杀死
```

#### 常用信号速查
| 号 | 名 | 默认动作 | 可捕获 | 用途 |
|----|----|----------|--------|------|
| 1 | HUP | 终止 | ✅ | 重载配置 / 终端断开 |
| 2 | INT | 终止 | ✅ | `Ctrl+C` |
| 3 | QUIT | 终止+core | ✅ | `Ctrl+\` |
| 6 | ABRT | 终止+core | ✅ | `abort()` |
| 9 | **KILL** | 终止 | ❌ | 强杀，不可捕获 |
| 10 | USR1 | 终止 | ✅ | 自定义（日志轮转） |
| 12 | USR2 | 终止 | ✅ | 自定义 |
| 15 | **TERM** | 终止 | ✅ | 优雅退出（默认） |
| 18 | CONT | 继续 | ✅ | 恢复 |
| 19 | **STOP** | 暂停 | ❌ | 不可捕获 |
| 20 | TSTP | 暂停 | ✅ | `Ctrl+Z` |

#### ⚠️ 退出码与信号
```bash
$ kill -9 1234 ; echo $?
$ wait 1234 ; echo $?
137          # 128 + 9
```
判断脚本里被信号杀死的常见模式：
```bash
$ cmd; rc=$?
if [ "$rc" -gt 128 ]; then
  sig=$((rc - 128))
  echo "被信号 $sig ($(kill -l $sig)) 终止"
fi
```

#### 常见坑
- ⚠️ **`kill -9` 不给进程清理机会**：不 flush 缓冲、不删临时文件、不释放锁、不通知子进程。**数据库、写入类进程可能数据损坏**。
- ⚠️ **`kill -9` 之后进程仍可能显示为僵尸**（如果父进程不回收），需要处理父进程。
- ⚠️ **`kill -- -1234` 杀整个进程组**，若 PGID 搞错可能杀掉不该杀的（包括自己的 shell）。
- **信号名跨架构不同**：`SIGUSR1` 在 x86 是 10，MIPS 是 16。**脚本里永远用名字**。
- **`kill` 可以是 shell 内建或外部命令**，行为略有差异（内建支持 `%1` 作业号）。
- **`kill -0` 对僵尸进程返回 0（存在）**，但僵尸已经不能做任何事。
- **权限限制**：只能给同 UID 的进程或自己的子进程发信号，除非是 root（或有 CAP_KILL）。
- **`kill` 成功后进程不一定立即消失**，要轮询确认。

#### 相关命令
`pkill` · `killall` · `signal(7)` · `trap`

### killall — 按名字发送信号

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：⚠️ **psmisc 版与 Solaris 版语义完全不同**（Solaris 的 `killall` 是杀所有进程）

```bash
killall [选项] 名字...
```

| 选项 | 含义 |
|------|------|
| `-信号` | 指定信号 |
| `-i` | 每个都询问 |
| `-e` / `-v` | 报告结果 |
| `-q` | 没匹配到时安静退出 |
| `-u 用户` | 只杀该用户的 |
| `-r` | 名字按正则解释 |
| `-w` | 等待进程真的退出（用于脚本） ⭐ |
| `-n` / `-o` | 最新 / 最老的实例 |
| `-Z 上下文` | 按 SELinux 上下文 |

```bash
# 场景：杀所有同名进程
$ killall nginx
$ killall -TERM firefox

# 场景：交互确认
$ killall -i -e firefox
Kill firefox(1234) ? (y/N)

# 场景：等进程真正退出（脚本里很有用）⭐
$ killall -w -TERM myservice && echo "已停止"

# 场景：只杀某用户的
$ killall -u alice chrome

# 场景：正则匹配
$ killall -r 'python.*'
```

#### 输出解读
- 名字必须**精确匹配进程名**（`comm`，15 字符以内）。`killall firefox` 不会匹配 `firefox-esr`。
- `-e` 输出 `name killed / no process found`。

#### 常见坑
- ⚠️ **Solaris/部分 Unix 的 `killall` 是「杀掉所有进程」（等同 `kill -9 -1`）**。跨平台脚本里绝不能用 `killall` 做危险操作。
- **名字长度限制 15 字符**（`comm` 的限制）。长名字用 `pkill -x` 或 `pkill -f`。
- **`-w` 在某些实现上可能无限等待**，配合 `timeout` 使用。
- **不带 `-q` 时没匹配到会返回非零退出码**，脚本里 `set -e` 会中断。
- 与 `pkill` 相比功能少（不能匹配命令行），**现代脚本更推荐 `pkill`**。

#### 相关命令
`pkill` · `kill` · `pgrep`

### pidof — 按程序名查 PID

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，`sysvinit-utils` 提供

```bash
pidof [选项] 程序名
```

| 选项 | 含义 |
|------|------|
| `-s` | 只输出一个（默认输出全部） |
| `-o PID` | 排除指定 PID（避免匹配自己） |
| `-x 脚本` | 也匹配 shell 脚本 |
| `-c` | 只匹配同一 root 目录的 |
| `-S` / `-t` | 见 man | 

```bash
# 场景：查 PID
$ pidof nginx
1234 892

# 场景：只输出一个
$ pidof -s nginx
1234

# 场景：排除某 PID（避免把自己算进去）
$ pidof -o $$ myscript

# 场景：服务脚本里判断是否运行
$ pidof myservice >/dev/null && echo running

# 场景：杀之前确认
$ kill -TERM $(pidof nginx)
```

#### 输出解读
- 多个 PID 在同一行，空格分隔，**从大到小**（最新的在前）。
- 一个都没有时**无输出，退出码 1**。

#### 常见坑
- **`pidof` 匹配的是可执行文件的路径**（更准确地说，是 `/proc/PID/exe` 与 `/proc/PID/cmdline[0]` 的 basename），比 `pgrep` 的 `comm` 更严格。
- **脚本默认不匹配**（因为脚本的 `exe` 是解释器）。要匹配脚本用 `-x script.sh`。
- **在容器里看不到宿主进程**。
- **服务有多进程时返回多个**，直接 `kill $(pidof X)` 会全部杀掉。
- systemd 环境下推荐 `systemctl status` 与 `systemctl show -p MainPID`。

```bash
# systemd 服务的 PID 更可靠的取法
$ systemctl show -p MainPID --value nginx
$ systemctl show -p MainPID --value 'ssh.service'
```

#### 相关命令
`pgrep` · `pkill` · `systemctl show -p MainPID`

### jobs — 列出 shell 作业

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无（shell 内建）

```bash
jobs [选项] [作业号...]
```

| 选项 | 含义 |
|------|------|
| `-l` | 同时显示 PID 与 PGID ⭐ |
| `-p` | 只显示 PID |
| `-r` | 只显示运行中的 |
| `-s` | 只显示已停止的 |
| `-n` | 只显示状态变化的 |

**作业号标记**：

| 标记 | 含义 |
|------|------|
| `%1` `%2` | 第 N 个作业 |
| `%%` 或 `%+` | 当前作业（最近一次放到后台的） |
| `%-` | 前一个作业 |
| `%name` | 以 name 开头的作业 |
| `%?str` | 命令行含 str 的作业 |

```bash
# 场景：列出作业
$ sleep 300 & sleep 600 &
[1] 12345
[2] 12346
$ jobs -l
[1]- 12345 Running                 sleep 300 &
[2]+ 12346 Running                 sleep 600 &

# 场景：只看已停止的
$ jobs -s

# 场景：用作业号操作
$ kill %1
$ fg %2
$ bg %1
```

#### 输出解读
```
[1]- 12345 Running                 sleep 300 &
 │  │   │    │                     └─ 命令行
 │  │   │    └─ 状态：Running / Stopped / Done
 │  │   └─ PID
 │  └─ - 表示「前一个作业」，+ 表示「当前作业」
 └─ 作业号
```

#### 常见坑
- ⚠️ **作业控制只在交互式 shell 可用**。脚本（非交互）里 `jobs` 通常是空的，`%1` 也不可用。
- ⚠️ **作业号是 shell 局部概念**，换一个终端/新 shell 就没有了。
- ⚠️ **shell 退出时，作业会收到 SIGHUP**（除非 `nohup`/`disown`/`setsid`）。
- **`Done` 状态的作业会在下次执行命令时被 shell 清理**，你可能来不及看到。
- **子 shell 里启动的作业不会出现在父 shell 的 `jobs` 里**。
- `set -m`（monitor mode）在脚本里关闭，作业控制不可用。

#### 相关命令
`bg` · `fg` · `disown` · `nohup` · `wait`

### bg / fg — 作业前后台切换

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无（shell 内建）

```bash
bg [作业号...]
fg [作业号]
```

```bash
# 场景：暂停后转后台
$ ./long_build
^Z                        # Ctrl+Z 发送 SIGTSTP
[1]+  Stopped             ./long_build
$ bg
[1]+ ./long_build &
$ jobs
[1]+ Running              ./long_build &

# 场景：把后台作业拉回前台
$ fg
./long_build
# 或指定作业号
$ fg %2

# 场景：启动时直接后台
$ ./server &
[1] 12345

# 场景：暂停 → 后台 → 之后再拉回
$ vim /etc/nginx/nginx.conf
^Z
[1]+ Stopped    vim /etc/nginx/nginx.conf
$ bg %1
$ # 干别的事
$ fg %1
```

#### 输出解读
`fg` 会把作业恢复到**前台**并接收 SIGCONT；`bg` 恢复到**后台**。

#### 常见坑
- ⚠️ **`bg` 只对已停止的作业有意义**。对已经在跑的作业 `bg` 会失败（`no current job`）。
- ⚠️ **`Ctrl+Z` 只是暂停（SIGTSTP），不是终止**。被暂停的进程仍占内存和 PID，可能持有锁。
- **`Ctrl+Z` 对不响应 SIGTSTP 的程序无效**（如某些自定义信号处理的程序）。
- **后台作业仍与终端关联**，读写终端会收到 SIGTTIN/SIGTTOU 被暂停。所以后台程序要重定向 stdin。
- **前台作业只能有一个**，`fg` 到新作业不会自动暂停旧的（会报错或抢占）。
- 在 `tmux`/`screen` 里 `Ctrl+Z` 会先被 tmux 处理（取决于配置）。

#### 相关命令
`jobs` · `disown` · `nohup` · `setsid`

### disown — 从作业表移除

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：Bash / zsh 特有，POSIX 无

```bash
disown [-h] [-a] [作业号...]
```

| 选项 | 含义 |
|------|------|
| `-h` | 保留在作业表，但**不接收 SIGHUP** ⭐ |
| `-a` | 处理所有作业 |
| `-r` | 只处理运行中的 |

```bash
# 场景：让后台作业在 shell 退出后继续 ⭐
$ ./server &
$ disown
$ exit            # server 继续运行

# 场景：保留作业表但屏蔽 HUP
$ ./server &
$ disown -h %1
$ jobs
[1]+ Running    ./server &
$ exit            # 不会向 server 发 HUP

# 场景：启动时忘记 nohup 的补救 ⭐
$ ./longjob
^Z
$ bg
$ disown -h
```

#### 常见坑
- ⚠️ **`disown` 与 `nohup` 解决的问题不完全相同**：
  - `nohup` 让进程**忽略** SIGHUP（进程级）
  - `disown -h` 让 shell **不发送** SIGHUP（shell 级）
  - 前者更强（无论谁发 HUP 都无效），后者只防自己的 shell
- ⚠️ **`disown` 后作业无法再用 `fg`/`bg`/`%1` 操作**（已从作业表移除）。用 PID 操作。
- **`disown` 不带作业号默认作用于「当前作业」**（`%+`），容易搞错，建议显式指定。
- **进程仍与终端关联**，终端关闭时若进程尝试读终端会收到 SIGHUP/SIGTTIN。彻底脱离要用 `setsid` 或重定向 stdin。
- **不是 POSIX**。`sh`/`dash` 没有这个内建。

#### 相关命令
`nohup` · `setsid` · `jobs` · `tmux`

### nohup — 忽略挂断信号运行

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无

```bash
nohup 命令 [参数...]
```

```bash
# 场景：SSH 断开后继续运行 ⭐
$ nohup ./server > server.log 2>&1 &
[1] 12345
nohup: ignoring input and appending output to 'nohup.out'
$ exit                    # server 继续运行

# 场景：完整写法（重定向 stdin，避免占用终端）⭐
$ nohup ./server </dev/null >/var/log/server.log 2>&1 &

# 场景：不指定输出时，会写到 nohup.out
$ nohup ./task
$ ls nohup.out

# 场景：配合 nice 降优先级跑批
$ nohup nice -n 19 ionice -c3 ./backup.sh </dev/null >/tmp/backup.log 2>&1 &
$ echo $! > /tmp/backup.pid        # ⭐ 记录 PID 便于管理
```

#### 输出解读
- `nohup: ignoring input and appending output to 'nohup.out'` — 因为没有重定向输出。
- `nohup.out` 默认写在**当前目录**；若不可写则写 `$HOME/nohup.out`。
- `nohup` 会把进程对 SIGHUP 的处理设为 `SIG_IGN`。

#### 常见坑
- ⚠️ **`nohup` 只处理 SIGHUP**，不处理终端关闭导致的其他问题（如 stdout 关闭后的 SIGPIPE、读 stdin 的 SIGTTIN）。**必须重定向 stdin/stdout/stderr**。
- ⚠️ **`nohup` 后忘记 `&` 会占住终端**（前台运行），此时 `Ctrl+C` 仍能杀死它（SIGINT 不受 nohup 保护）。
- ⚠️ **`nohup.out` 会无限增长**，长期运行的服务必须显式重定向到有 logrotate 的日志。
- **`nohup` 不改变进程的工作目录**（仍继承当前目录）。若目录被卸载/删除，进程会异常。守护进程应 `cd /`。
- **`nohup` 不脱离终端（不是 setsid）**，进程仍属于原会话。用 `ps -o sid=` 能看到。
- **现代推荐用 `systemd-run` 或 `systemd` service** 而不是 `nohup`（有日志、有重启、有资源限制）：
  ```bash
  $ systemd-run --user --unit=mytask /usr/local/bin/longjob
  $ systemctl --user status mytask
  ```

#### 相关命令
`setsid` · `disown` · `screen` · `tmux` · `systemd-run`

### setsid — 在新会话中运行

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：POSIX

```bash
setsid [选项] 命令 [参数...]
```

| 选项 | 含义 |
|------|------|
| `-w` / `--wait` | 等待命令结束并返回其退出码（util-linux 2.24+） |
| `-f` / `--fork` | 强制 fork（即使调用者不是进程组首进程） |
| `-c` / `--ctty` | 设置控制终端 |

```bash
# 场景：完全脱离终端运行 ⭐
$ setsid ./server </dev/null >/var/log/server.log 2>&1 &
$ ps -o pid,sid,tty,cmd -p $!
    PID     SID TTY      CMD
  12345   12345 ?        ./server
#            ↑ 新会话 ID = PID，TTY 为 ? （无终端）

# 场景：与 nohup 的对比
$ nohup ./a </dev/null >/dev/null 2>&1 &
$ ps -o pid,sid,tty,cmd -p $!
    PID     SID TTY      CMD
  12346    8920 pts/1    ./a
#            ↑ 仍在原会话，仍关联 pts/1
$ setsid ./b </dev/null >/dev/null 2>&1 &
$ ps -o pid,sid,tty,cmd -p $!
    PID     SID TTY      CMD
  12347   12347 ?        ./b
#            ↑ 新会话，无终端

# 场景：等待并获取退出码
$ setsid -w ./task && echo OK

# 场景：创建守护进程的标准姿势
$ setsid -f --fork /usr/local/bin/mydaemon
```

#### 输出解读
`ps -o sid=` 显示会话 ID。新会话的首进程的 SID = 自己的 PID，且 `TTY` 为 `?`。

#### 常见坑
- **`setsid` 会创建新会话，进程与终端完全脱离**，所以它不会收到终端的 SIGHUP/SIGTTIN/SIGTTOU。
- **若 `setsid` 的调用者已经是进程组首进程，会直接执行而不 fork**（POSIX 规定）。用 `-f` 强制 fork。
- **`setsid` 不重定向文件描述符**。stdout 仍可能指向已关闭的终端，写入会得到 `EIO` 或 SIGPIPE 被杀。**仍要重定向**。
- **`setsid -w` 的退出码是子命令的退出码**，而不带 `-w` 时立即返回 0。
- **`setsid` 不改变工作目录**，仍需自己 `cd /`。
- 🔐 **`setsid` 是创建「不可见」进程的常见手法**（脱离终端、`TTY` 显示 `?`），排查时关注 `ps -o pid,tty,cmd` 里 `TTY` 为 `?` 的非系统进程：
  ```bash
  $ ps -eo pid,ppid,tty,cmd | awk '$3=="?" && $1>1000'
  ```

#### 相关命令
`nohup` · `disown` · `daemon(3)` · `systemd` 服务

### nice — 以指定优先级启动

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无

```bash
nice [-n 调整值] 命令 [参数...]
```

| 选项 | 含义 |
|------|------|
| `-n N` | nice 值增加 N（`-20`~`19`） |
| `--adjustment=N` | 长选项 |

```bash
# 场景：低优先级跑批处理（不抢线上服务）⭐
$ nice -n 19 ./backup.sh

# 场景：查看调整后的 nice 值
$ nice -n 10 sleep 100 &
$ ps -o pid,ni,cmd -p $!
    PID  NI CMD
  12345  10 sleep 100

# 场景：默认增量是 10
$ nice sleep 100 &        # nice 值变成 10
$ ps -o ni= -p $!
10

# 场景：组合 I/O 优先级（更彻底的不打扰）
$ nice -n 19 ionice -c3 ./indexer

# 场景：提优先级需要 root（普通用户只能降）
$ nice -n -5 ./latency_critical
nice: cannot set niceness: Permission denied
$ sudo nice -n -5 ./latency_critical

# 场景：查看当前 shell 的 nice（通常 0）
$ nice
0
```

#### 输出解读
nice 值范围 `-20`（最高优先）到 `19`（最低优先），默认 `0`。**数值越大优先级越低**。

#### 常见坑
- ⚠️ **普通用户只能提高 nice 值（降低优先级）**，不能降低（提高优先级）。要 `sudo`。
- ⚠️ **`nice` 的效果有限**：它只影响 CFS 的权重，不限制 CPU 使用量。要硬限制用 `cpulimit`、cgroup 的 `CPUQuota` 或 `systemd-run -p CPUQuota=`。
- **`nice -n 19` 不会让任务「完全让出」CPU**，它只是权重最低。极端情况下低优先级任务仍会占用 CPU。
- **`nice` 只影响 CPU 调度，不影响 I/O**。磁盘密集任务要用 `ionice`。
- **nice 不是 NI 列的唯一来源**：`autogroup`（桌面环境的默认开启）会做额外的调度分组。

#### 相关命令
`renice` · `ionice` · `chrt` · `cpulimit` · `systemd-run`

### renice — 调整运行中进程优先级

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无

```bash
renice [-n] 优先级 [-p PID] [-u 用户] [-g PGID]
```

| 选项 | 含义 |
|------|------|
| `-n N` | 新的 nice 值（绝对值，不是增量） ⚠️ |
| `-p PID` | 指定进程（默认） |
| `-u 用户` | 该用户的所有进程 |
| `-g PGID` | 整个进程组 |

```bash
# 场景：把进程降到最低优先级
$ sudo renice -n 19 -p 1234
1234 (process ID) old priority 0, new priority 19

# 场景：提高优先级（需 root）
$ sudo renice -n -10 -p 1234

# 场景：调整某用户的所有进程
$ sudo renice -n 10 -u alice
alice (user ID 1000) old priority 0, new priority 10

# 场景：查看结果
$ ps -o pid,ni,cmd -p 1234

# 场景：降优先级跑大编译（编译前先降自己）
$ sudo renice -n 19 -p $$
$ make -j8

# 场景：容器内调整（需要相应 capability）
$ sudo renice -n 5 -p 1234
```

#### 输出解读
```
1234 (process ID) old priority 0, new priority 19
```

#### 常见坑
- ⚠️ **`renice` 的 `-n` 是新的绝对值，不是增量**（与 `nice` 相反）。`nice -n 10` 是「+10」，`renice -n 10` 是「设为 10」。这是最常见的混淆。
- ⚠️ **普通用户不能提高优先级**（降低 nice 值），只能调高。
- **`renice` 会更新进程的 ctime**（`/proc/PID` 的元数据），不影响文件。
- **`renice` 对已经在跑的进程的 `autogroup` 行为可能有意外**。
- **调整 PID 1 或内核线程可能失败或无效**（内核线程的 nice 调整有特殊规则）。
- **`renice -u` 对遗留的 zombie 进程会报错但不影响其他进程**。

#### 相关命令
`nice` · `ionice` · `chrt` · `top -r`

### ionice — 设置 I/O 优先级

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：Linux 特有，来自 `util-linux`

```bash
ionice [-c 类别] [-n 级别] [-p PID] [命令...]
```

| 选项 | 含义 |
|------|------|
| `-c 类别` | 0=无 1=实时 2=best-effort(默认) 3=idle ⭐ |
| `-n 级别` | 类别内的优先级 0–7（越小越优先，对 best-effort） |
| `-p PID` | 调整已运行的进程 |
| `-t` | 忽略失败（不报错） |
| `-u` | 显示当前进程的 I/O 优先级 |

```bash
# 场景：让备份任务占用最低 I/O 优先级 ⭐
$ ionice -c3 -p $$ && ./backup.sh
$ ionice -c3 ./backup.sh
$ nice -n 19 ionice -c3 ./backup.sh        # 组合最温和

# 场景：查看当前 I/O 优先级
$ ionice -p $$
none: prio 4

# 场景：调整已运行的进程
$ ionice -c2 -n7 -p 1234

# 场景：实时类别（⚠️ 可能饿死其他进程）
$ sudo ionice -c1 -n0 -p 1234

# 场景：在脚本里包住整批任务
$ ionice -c3 -n7 tar czf /backup/data.tgz /data
```

#### I/O 类别
| 类别 | 值 | 行为 |
|------|----|------|
| `none` | 0 | 不改（继承） |
| `realtime` | 1 | 最高，始终优先访问磁盘 ⚠️ |
| `best-effort` | 2 | 默认，按优先级 0–7 排队 |
| `idle` | 3 | **只在没有其他进程用磁盘时才允许访问** ⭐ |

#### 常见坑
- ⚠️ **`ionice` 只在「CFQ/BFQ I/O 调度器」下生效**。现代内核默认的 `none`/`mq-deadline`/`kyber`（尤其 NVMe）调度器**忽略 I/O 优先级**。检查：
  ```bash
  $ cat /sys/block/nvme0n1/queue/scheduler
  [none] mq-deadline kyber bfq
  $ echo bfq | sudo tee /sys/block/nvme0n1/queue/scheduler   # 切到 bfq 后才有效
  ```
  所以 `ionice` 在 SSD/NVMe 上常常「设了也没用」。
- ⚠️ **`-c1`（realtime）可能导致其他进程的 I/O 完全饿死**，包括内核回写，可能引发系统卡顿。
- **只有 `ionice` 的 `-c3`（idle）是相对可靠的**（即使调度器不完整支持，它也会降低优先级标记）。
- **普通用户可以对**自己的**进程设置 ionice**，但调高类别（如 realtime）需要 root。
- 容器里的 `ionice` 可能无效（取决于 cgroup 的 io 控制器配置）。

#### 相关命令
`nice` · `renice` · `chrt` · `cgroup io.max`

### chrt — 设置调度策略

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：Linux 特有

```bash
chrt [选项] [优先级] 命令 [参数...]
chrt -p [优先级] PID
```

| 选项 | 含义 |
|------|------|
| `-f` | SCHED_FIFO（实时，先到先服务） |
| `-r` | SCHED_RR（实时，时间片轮转） |
| `-o` | SCHED_OTHER（普通分时，默认） |
| `-b` | SCHED_BATCH（批处理） |
| `-i` | SCHED_IDLE（最低优先） |
| `-d` | SCHED_DEADLINE（需 `--sched-runtime` 等） |
| `-p` | 操作已存在的 PID |
| `-m` | 显示最小/最大优先级范围 |
| `-v` | 显示策略名而不只是数字 |
| `-a` | 作用于所有线程 |

实时优先级范围：**1–99**（数字越大越优先）。

```bash
# 场景：查看当前进程的调度策略
$ chrt -p $$
pid 12345's current scheduling policy: SCHED_OTHER
pid 12345's current scheduling priority: 0

# 场景：查看支持的策略与优先级范围
$ chrt -m
SCHED_OTHER min/max priority    : 0/0
SCHED_FIFO min/max priority     : 1/99
SCHED_RR min/max priority       : 1/99
SCHED_BATCH min/max priority    : 0/0
SCHED_IDLE min/max priority     : 0/0

# 场景：以实时优先级运行（需 root 或 CAP_SYS_NICE）
$ sudo chrt -f 50 ./realtime_audio

# 场景：调整已运行的进程
$ sudo chrt -p -f 50 1234

# 场景：把批处理任务设为最低
$ chrt -i 0 ./background_task

# 场景：给整个线程组设置
$ sudo chrt -a -f 10 -p 1234
```

#### 输出解读
| 策略 | 含义 |
|------|------|
| `SCHED_OTHER` | 普通 CFS，nice 值生效 |
| `SCHED_BATCH` | 批处理，不抢占交互任务 |
| `SCHED_IDLE` | 只在 CPU 空闲时运行 |
| `SCHED_FIFO` | 实时，一旦运行直到主动让出或被更高优先级抢占 |
| `SCHED_RR` | 实时，同优先级轮转 |
| `SCHED_DEADLINE` | 基于 deadline 的调度 |

#### 常见坑
- ⚠️ **`SCHED_FIFO`/`SCHED_RR` 的进程会抢占所有普通进程**（包括内核线程如回写、网络处理）。一个死循环的实时进程可以**挂死整个系统**。
- ⚠️ **实时进程运行时，普通进程（包括你的 SSH）可能完全没机会运行**。远程操作时有把自己锁在外面的风险。
- **需要 root 或 `CAP_SYS_NICE`**。容器默认没有该能力。
- **内核有 `sched_rt_runtime_us` 限制**（默认 950000/1000000，即实时进程最多占 95% CPU），防止完全挂死。可以调但风险更高。
- **`SCHED_DEADLINE` 需要额外参数**（`--sched-runtime` `--sched-deadline` `--sched-period`），配置错误会直接失败。
- **`chrt -p` 只影响指定 PID，不递归子进程**。要递归用 `-a`（线程）或遍历 `/proc`。

#### 相关命令
`nice` · `renice` · `ionice` · `taskset`

### time — 测量命令耗时

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：⚠️ **bash 内建 `time` 与 `/usr/bin/time` 输出格式与选项完全不同**

```bash
time 命令 [参数...]                 # shell 保留字
/usr/bin/time [-v] 命令             # 外部命令，功能更多
```

**bash 内建 `time`**：

```bash
$ time sleep 1
real    0m1.003s
user    0m0.001s
sys     0m0.002s
```

| 字段 | 含义 |
|------|------|
| `real` | 墙上时钟（用户感知的时间） |
| `user` | 用户态 CPU 时间 |
| `sys` | 内核态 CPU 时间 |

**外部 `/usr/bin/time`**：

| 选项 | 含义 |
|------|------|
| `-v` | 详细报告（内存、页错误、上下文切换） ⭐ |
| `-p` | POSIX 格式（可解析） |
| `-o 文件` | 输出到文件（不混入 stdout） ⭐ |
| `-a` | 追加 |
| `-f 格式` | 自定义格式 |
| `--quiet` | 不报告错误 |

常用格式符：`%e` 耗时、`%U` 用户、`%S` 系统、`%M` 峰值内存(KiB)、`%P` CPU 占比、`%x` 退出码、`%I` 文件系统输入、`%O` 输出。

```bash
# 场景：比较两种实现的性能 ⭐
$ time sort -n big.txt > /dev/null
real    0m2.341s
user    0m2.280s
sys     0m0.060s

# 场景：判断瓶颈是 CPU 还是 I/O ⭐
# real 远大于 user+sys → I/O 密集或等待
$ time cat bigfile > /dev/null
real    0m5.120s
user    0m0.010s
sys     0m1.230s      # 大量时间在等待 I/O

# 场景：详细报告（峰值内存、页错误）
$ /usr/bin/time -v ./benchmark
	Command being timed: "./benchmark"
	User time (seconds): 12.34
	System time (seconds): 1.23
	Percent of CPU this job got: 99%
	Elapsed (wall clock) time: 0:13.68
	Maximum resident set size (kbytes): 512340
	Minor (reclaiming a frame) page faults: 125678
	Major (requiring I/O) page faults: 12
	Voluntary context switches: 890
	Involuntary context switches: 45
	Exit status: 0

# 场景：输出到文件（不污染 stdout）
$ /usr/bin/time -o /tmp/bench.txt -f '%e %M %P' ./run

# 场景：脚本里取耗时
$ t=$( { /usr/bin/time -f '%e' ./task; } 2>&1 )
$ echo "耗时 ${t}s"

# 场景：多核并行的效率
$ time make -j1 && time make -j8
```

#### 常见坑
- ⚠️ **bash 内建的 `time` 是保留字，`/usr/bin/time` 是程序**。`time -v` 会被 bash 解释成错误，必须写 `/usr/bin/time -v` 或 `\time -v`。
- ⚠️ **内建 `time` 的输出走 stderr**，重定向 stdout 时计时信息仍会显示在终端。要捕获：`{ time cmd; } 2>&1`。
- **`real` 可能大于 `user + sys`**（等待 I/O、睡眠、锁），也可能**小于**（多线程并行，`user` 是所有 CPU 时间之和）。
- **`%P` 是 CPU 利用率**（`(user+sys)/real`）。多核上可超过 100%。
- **`-v` 的 `Maximum resident set size` 是峰值 RSS**，这是找内存泄漏的好指标。
- **`time` 对管道只计时最后一段**：`time a | b` 计时的是 `b`（bash 内建实际会覆盖整个管道，行为依实现而异，要小心）。稳妥写法 `time (a | b)`。
- **第 3 方工具 `hyperfine` 更适合基准测试**（自动多次运行、统计、预热）。

#### 相关命令
`hyperfine` · `perf stat` · `date +%s%N` · `strace -c`

### timeout — 超时终止命令

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：GNU coreutils（`util-linux` 无）

```bash
timeout [选项] 时长 命令 [参数...]
```

| 选项 | 含义 |
|------|------|
| `-s 信号` / `--signal` | 超时后发送的信号（默认 TERM） ⭐ |
| `-k 时长` | 若 TERM 后仍未退出，再等多久发 KILL ⭐ |
| `-p` | 无 `-k` 时也保留（默认行为） |
| `--foreground` | 让命令在前台进程组运行（能收 Ctrl+C） |
| `--preserve-status` | 返回命令的退出码而非 124 |
| `-v` | 详细诊断 |

**时长格式**：`10`（秒）、`10s`、`5m`、`1h`、`1d`、`0.5s`。

```bash
# 场景：防止命令卡死 ⭐
$ timeout 5 ping 8.8.8.8
$ timeout 30 curl -s https://example.com

# 场景：TERM 无效则 KILL（更彻底）⭐
$ timeout -k 5 30 ./runaway_process

# 场景：判断是否超时（退出码 124）
$ timeout 5 slow_cmd
$ echo $?
124

# 场景：脚本里超时后走降级逻辑 ⭐
$ if timeout 10 curl -sf https://api.example.com/health >/dev/null; then
>   echo healthy
> else
>   rc=$?
>   [ "$rc" -eq 124 ] && echo "健康检查超时" || echo "健康检查失败 rc=$rc"
> fi

# 场景：能接收 Ctrl+C（--foreground）
$ timeout --foreground 60 ./interactive_tool

# 场景：测试端口连通性（替代 nc）
$ timeout 2 bash -c '</dev/tcp/10.0.0.1/22' && echo OPEN || echo CLOSED

# 场景：限制 SSH 连接时间
$ timeout 10 ssh -o BatchMode=yes user@host true && echo ok

# 场景：组合 tar 的 I/O 操作超时
$ timeout -k 10 300 tar czf /backup/full.tgz /data || echo "备份失败或超时"
```

#### 输出解读
| 退出码 | 含义 |
|--------|------|
| `124` | 命令超时被杀 ⭐ |
| `125` | `timeout` 自身出错 |
| `126` | 命令找到但无法执行 |
| `127` | 命令未找到 |
| 其他 | 命令自身的退出码（若用了 `--preserve-status` 则原样传递） |

#### 常见坑
- ⚠️ **默认只发 SIGTERM**，不响应 TERM 的进程不会被杀死（`timeout` 会一直等）。**生产脚本一律加 `-k`**。
- ⚠️ **`timeout` 只杀直接子进程，不杀其子孙进程**（除非它们在同一进程组且 `timeout` 用了进程组信号）。孤儿进程可能继续运行：
  ```bash
  $ timeout 5 bash -c 'sleep 100 & wait'
  # sleep 100 可能仍然存在
  ```
  要彻底清理用 `setsid` + `kill -- -PGID` 或 `systemd-run` 的 scope。
- **`124` 与「命令自己返回 124」无法区分**。用 `--preserve-status` 会混淆更多，通常不用。
- **`timeout 0 cmd` 表示不限时**（不是立即超时）。
- **管道的位置很重要**：`timeout 5 a | b` 只限制 `a`。要限制整个管道：`timeout 5 sh -c 'a | b'`。
- **在非交互环境（cron、systemd）下 `--foreground` 可能有意外**。

#### 相关命令
`sleep` · `wait` · `at` · `systemd-run --on-active`

### watch — 周期性重复执行命令

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，`procps`

```bash
watch [选项] 命令
```

| 选项 | 含义 |
|------|------|
| `-n N` | 间隔秒（默认 2，最小 0.1） ⭐ |
| `-d` | 高亮变化的部分 ⭐ |
| `-g` | 输出变化时退出（用于等待） |
| `-t` | 不显示头部 |
| `-e` | 出错时停止刷新 |
| `-b` | 命令非零退出时蜂鸣 |
| `-c` | 保留 ANSI 颜色 |
| `-x` | 把命令交给 `sh -c`（可带管道） |

```bash
# 场景：观察磁盘空间变化
$ watch -n 5 -d 'df -h /'

# 场景：观察目录内容变化
$ watch -n 1 -d 'ls -l /tmp'

# 场景：观察网络连接
$ watch -n 2 'ss -tunap | grep -c ESTAB'

# 场景：观察进程数
$ watch -n 1 -d 'pgrep -c nginx'

# 场景：带管道（需要 -x 或引号）
$ watch -n 2 'ss -tn | awk "NR>1{print \$1}" | sort | uniq -c'

# 场景：等某条件成立就退出 ⭐
$ watch -g -n 2 'test -f /tmp/done && echo READY'

# 场景：观察内存变化
$ watch -n 1 -d 'free -m'

# 场景：监控文件大小增长（日志暴涨排查）
$ watch -n 5 'ls -lh /var/log/app.log'
```

#### 输出解读
顶部显示：
```
Every 2.0s: df -h /                          hostname: Tue Sep 15 09:30:00 2026
```
`-d` 模式下，**变化的部分会高亮**（这是排查动态变化最有用的功能）。

#### 常见坑
- ⚠️ **`watch` 的默认 `sh -c` 行为**：带管道或重定向的命令需要引号包裹。`watch ls | wc` 会把 `| wc` 交给外层 shell，结果不对。用 `watch 'ls | wc'`。
- **`watch` 会屏蔽颜色**，除非加 `-c`。
- **`watch` 的终端尺寸影响输出**，窗口太小会截断（不是换行）。
- **`-g` 在命令输出变化时退出**，但「变化」的判断是**逐字节比较整个输出**，包含时间戳等易变内容会让你立即退出。
- **`watch` 在非交互环境（重定向、cron）下无效**，因为没有 TTY 刷新。
- **`-n` 最小间隔受实现限制**，某些系统上小于 0.1 会被设成 0.1。
- **`watch` 反复执行命令**，对「有副作用」的命令（如 `rm`、`kill`、`systemctl restart`）**绝对不要用**。

#### 相关命令
`top` · `vmstat 1` · `while true; do cmd; sleep 1; done` · `entr`

### sleep — 延时

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：GNU 支持小数与多单位（`1m30s`），POSIX 只支持整数秒（或某些实现支持小数）

```bash
sleep 时长[后缀]...
```

**后缀**：`s` 秒、`m` 分、`h` 时、`d` 天。可叠加：`1m30s`。

```bash
$ sleep 5
$ sleep 0.5
$ sleep 2m
$ sleep 1h30m
$ sleep 1d

# 场景：重试循环（指数退避）⭐
$ for i in 1 2 3 4 5; do
>   curl -sf https://api/health && break
>   sleep $((2**i))
> done

# 场景：等进程启动
$ ./server & sleep 0.5
$ curl -s localhost:8080/health

# 场景：等待某条件（轮询）⭐
$ while ! pgrep -x myservice >/dev/null; do sleep 1; done

# 场景：可用 Ctrl+C 中断的等待
$ sleep 3600
^C

# 场景：不用 sleep，用 read 做「按任意键继续」
$ read -n1 -r -p '按任意键继续...' key

# 场景：在脚本里做简单限速
$ for f in *.log; do process "$f"; sleep 0.2; done
```

#### 常见坑
- ⚠️ **`sleep 1m30s` 是 GNU 扩展**，POSIX 的 `sleep` 只接受整数秒。跨平台脚本用 `sleep $((90))`。
- ⚠️ **`sleep` 的精度有限**（通常 10ms 级）。不要用它做精确计时。
- ⚠️ **`sleep` 期间可以被信号中断**（SIGTERM 会终止它，返回码 143）。所以 `sleep 60` 不等价于「保证等 60 秒」。
- ⚠️ **不要在 `set -e` 的脚本里用 `sleep` 挂太久**，被 Ctrl+C 打断会中断整个脚本。
- **等待服务的正确姿势**不是 `sleep 5` 然后赌它起来了，而是**轮询健康检查**。固定 sleep 在慢机器上会失败，在快机器上浪费时间。
- **`sleep` 与 `usleep`/`sleep(3)`** 不同：shell 的 `sleep` 是外部命令（或内建），C 的 `sleep(3)` 是秒级的库函数。

#### 相关命令
`timeout` · `wait` · `at` · `usleep`

### wait — 等待子进程

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：无（shell 内建）

```bash
wait [PID或作业号...]
wait -n [PID...]        # bash 4.3+
```

| 写法 | 含义 |
|------|------|
| `wait` | 等**所有**后台子进程 |
| `wait PID` | 等指定进程 |
| `wait %1` | 等指定作业 |
| `wait -n` | 等任意一个结束（收一个就返回） ⭐ |
| `wait -f` | 等所有（含已停止的，bash 5.1+） |
| `wait -p 变量` | 把结束的 PID 存入变量（bash 5.1+） |

```bash
# 场景：等所有后台任务完成 ⭐
$ for f in *.csv; do process "$f" & done
$ wait
$ echo "全部完成"

# 场景：并行 + 收集退出码
$ for i in 1 2 3; do
>   ./job.sh "$i" &
>   pids+=($!)
> done
$ fail=0
$ for p in "${pids[@]}"; do wait "$p" || fail=1; done
$ [ "$fail" -eq 0 ] && echo "全部成功" || echo "有失败"

# 场景：控制并发数（保持最多 4 个并行）⭐
$ max=4
$ for f in *; do
>   ./process.sh "$f" &
>   while [ "$(jobs -rp | wc -l)" -ge "$max" ]; do wait -n; done
> done
$ wait

# 场景：等某进程退出
$ ./server & pid=$!
$ sleep 5
$ kill "$pid"
$ wait "$pid"; echo "退出码 $?"

# 场景：给 wait 加超时（wait 本身不支持超时）⭐
$ ./longjob &
$ pid=$!
$ ( sleep 10; kill "$pid" 2>/dev/null ) &
$ watcher=$!
$ wait "$pid"; rc=$?
$ kill "$watcher" 2>/dev/null
```

#### 输出解读
- `wait PID` 的退出码是该 PID 的退出码。
- `wait`（无参数）返回 0（除非有作业失败且启用了 `set -e` 相关行为）。

#### 常见坑
- ⚠️ **`wait` 只能等「自己 shell 的子进程」**。等别的进程用轮询 `kill -0`。
- ⚠️ **`wait` 对已经结束的进程返回其退出码**（前提是 shell 还没回收）。但被 shell 回收后（处理过 SIGCHLD）会报 `not a child of this shell`。
- ⚠️ **`wait -n` 需要 bash 4.3+**，`wait -p` 需要 bash 5.1+。
- **`set -e` 下 `wait` 的失败会中断脚本**，要注意。
- **后台进程在循环里覆盖 `$!`**：`for ...; do cmd & done` 后 `$!` 只是最后一个的 PID，前面的 PID 已经丢失。要收集到数组。
- **`wait` 不阻止 shell 退出**：`set -e` 时若某个子进程失败，脚本可能在 `wait` 前就退了。

#### 相关命令
`jobs` · `xargs -P` · `parallel` · `flock`

### lsof — 列出打开的文件与连接

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，需安装

```bash
lsof [选项] [文件...]
```

#### 高频选项
| 选项 | 含义 |
|------|------|
| `-i` | 网络文件（可加筛选） ⭐ |
| `-i :80` | 端口 80 |
| `-i @10.0.0.5` | 远程地址 |
| `-i tcp` / `-i udp` | 协议 |
| `-p PID` | 指定进程 ⭐ |
| `-u 用户` | 指定用户 |
| `-c 名字` | 命令名（支持前缀与 `^`） |
| `-d fd` | 文件描述符（`cwd`、`txt`、`0-9`） |
| `+D 目录` | 递归该目录下所有打开的文件（**极慢**） |
| `+d 目录` | 非递归 |
| `-n` | 不做主机名解析（**必加，否则极慢**） ⭐ |
| `-P` | 不做端口名解析（**必加**） ⭐ |
| `-a` | 各条件取 AND（默认 OR） ⭐ |
| `-r N` | 每 N 秒重复 |
| `+L1` | 显示 link count < 1 的文件（**已删除但仍被打开**） ⭐ |
| `-w` | 抑制警告 |
| `-s` | 显示文件大小 |
| `-F 字符` | 机器可解析输出 |

```bash
# 场景：谁占用了 8080 端口 ⭐
$ sudo lsof -i :8080
COMMAND   PID  USER   FD   TYPE DEVICE SIZE/OFF NODE NAME
java    12345  app    45u  IPv6  67890      0t0  TCP *:8080 (LISTEN)

# 场景：某进程打开了哪些文件
$ sudo lsof -p 1234 | head -20
COMMAND  PID USER   FD      TYPE DEVICE SIZE/OFF   NODE NAME
nginx   1234 root  cwd       DIR  253,0     4096  ... /etc/nginx
nginx   1234 root  txt       REG  253,0   123456  ... /usr/bin/nginx
nginx   1234 root  mem       REG  253,0   987654  ... /lib/x86_64-linux-gnu/libc.so.6
nginx   1234 root    0r      CHR    1,3      0t0  10335 /dev/null
nginx   1234 root    4u     IPv4  45678      0t0    TCP *:80 (LISTEN)

# 场景：某用户的所有网络连接
$ sudo lsof -a -u alice -i -nP

# 场景：🔐 找「已删除但仍被打开」的文件（释放空间 / 取证）⭐
$ sudo lsof +L1 | head
COMMAND   PID USER  FD   TYPE DEVICE SIZE/OFF NLINK  NODE NAME
app      1234 root  3w   REG  253,0 1073741824     0 12345 /var/log/app.log (deleted)
# ⭐ 这是「df 显示满但 du 找不到」的经典原因

# 场景：🔐 排查异常外连
$ sudo lsof -i -nP | grep ESTABLISHED

# 场景：某目录下被打开的文件
$ sudo lsof +D /var/log -nP | head

# 场景：找出监听端口与进程的对应
$ sudo lsof -i -sTCP:LISTEN -nP

# 场景：监控某进程的文件变化（每 2 秒）
$ sudo lsof -r 2 -p 1234

# 场景：脚本友好的输出
$ sudo lsof -F pc -i :80
p12345
cjava
```

#### 输出解读
| 列 | 含义 |
|----|------|
| `COMMAND` | 进程名 |
| `PID` / `USER` | — |
| `FD` | 文件描述符 + 模式：`cwd` 当前目录、`txt` 可执行文件、`mem` 内存映射、`rtd` 根目录、数字 + 模式 |
| `TYPE` | `REG` 普通文件、`DIR` 目录、`CHR` 字符设备、`IPv4`/`IPv6`、`unix`、`FIFO` |
| `DEVICE` | 设备号 |
| `SIZE/OFF` | 大小或偏移（网络连接是 `0t0`） |
| `NODE` | inode 号（网络是协议号） |
| `NAME` | 路径或连接信息 |

FD 的模式字符：`r` 读、`w` 写、`u` 读写、（空）未知。

#### 常见坑
- ⚠️ **不加 `-n -P` 会做 DNS 与端口名解析，可能慢到分钟级**。生产排查**一律加 `-nP`**。
- ⚠️ **多个条件是 OR 关系**，`lsof -i -u alice` 是「网络文件 **或** alice 的文件」。要 AND 必须加 `-a`。这是最常见的误用。
- ⚠️ **`+D` 会遍历整个目录，在大目录上可能跑几分钟**。用 `+d` 或直接 `-p`。
- **普通用户只能看到自己的进程**，看别人的要 `sudo`。
- **`lsof` 是 `+L1` 才是「已删除」**，不是 `-L`。`NLINK` 为 0 表示已删除。
- **`lsof` 有内核的 `/proc` 权限限制**（`hidepid` 挂载选项会屏蔽他人的进程）。
- **网络连接会显示 `(ESTABLISHED)` `(LISTEN)` `(CLOSE_WAIT)`** 等，与 `ss` 的状态一致。
- **`lsof -p` 的输出很长**（每个 mmap 的库都是一行），用 `lsof -p PID | grep -v 'mem'` 精简。
- 容器里 `lsof` 只能看到容器内进程的 `/proc`。

#### 相关命令
`fuser` · `ss` · `/proc/PID/fd` · `strace`

### fuser — 查看并终止占用文件的进程

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，`psmisc`

```bash
fuser [选项] 文件或端口...
```

| 选项 | 含义 |
|------|------|
| （默认） | 显示占用文件的 PID（到 stderr） |
| `-v` | 详细（表格形式，含用户、PID、访问类型） ⭐ |
| `-k` | **杀掉**占用者 ⚠️ |
| `-i` | 杀之前询问 |
| `-信号` | 配合 `-k` 指定信号 |
| `-m 挂载点` | 指定文件系统（用于卸载前检查） ⭐ |
| `-n 类型` | 命名空间：`file`（默认）、`tcp`、`udp` |
| `-u` | 显示用户名 |
| `-a` | 显示所有（含未占用的） |
| `-s` | 静默（脚本用，只看退出码） |

```bash
# 场景：谁占用了某端口 ⭐
$ sudo fuser -v 8080/tcp
                     USER        PID ACCESS COMMAND
8080/tcp:            app       12345 F.... java

$ sudo fuser -n tcp 8080
8080/tcp:            12345

# 场景：谁在使用某文件/挂载点 ⭐
$ sudo fuser -vm /mnt/data

# 场景：卸载前检查并终止占用者（NFS 卡死常用）⭐
$ sudo umount /mnt/nfs
umount: /mnt/nfs: target is busy.
$ sudo fuser -vm /mnt/nfs
$ sudo fuser -km /mnt/nfs       # ⚠️ 杀掉所有占用者
$ sudo umount /mnt/nfs

# 场景：端口是否被占用（脚本判断）⭐
$ fuser -s 8080/tcp && echo "被占用" || echo "空闲"

# 场景：交互式杀（先看后确认）
$ sudo fuser -ik 8080/tcp

# 场景：删文件前看谁在用
$ sudo fuser -v /var/log/app.log
```

#### 输出解读
`-v` 的 `ACCESS` 列：

| 字符 | 含义 |
|------|------|
| `c` | 当前目录 |
| `e` | 正在执行的程序 |
| `f` | 打开的文件 |
| `F` | 打开并正在写 |
| `r` | 根目录 |
| `m` | mmap 的文件 |

#### 常见坑
- ⚠️ **默认输出到 stderr**，脚本里重定向要注意：`fuser 8080/tcp 2>/dev/null`。
- ⚠️ **`-k` 不带 `-i` 会直接杀**，没有任何提示。可能杀掉关键服务。
- ⚠️ **`-km /` 会杀掉几乎所有进程**（因为几乎所有进程都有文件在 `/` 上）——这是灾难级操作。
- **默认只查 `file` 命名空间**，查端口必须 `-n tcp` 或写 `PORT/tcp`。
- **退出码**：0 = 找到占用者；1 = 没找到；其他 = 出错。所以 `fuser -s X` 可直接用于判断。
- **`fuser` 不解析主机名/端口名**（比 `lsof` 快），但也因此输出是纯数字。
- **`fuser` 对网络连接只显示本地端**，看不到对端地址，这点不如 `lsof`/`ss`。

#### 相关命令
`lsof` · `ss` · `umount` · `kill`

### strace — 跟踪系统调用

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：Linux 特有

```bash
strace [选项] [命令 [参数...]]
strace -p PID [选项]
```

#### 高频选项
| 选项 | 含义 |
|------|------|
| `-p PID` | 附加到运行中的进程 ⭐ |
| `-f` | 跟踪子进程与线程 ⭐ |
| `-c` | 汇总统计（不输出每条） ⭐ |
| `-e trace=集合` | 只用指定调用（`open,read,write` / `file` / `network` / `%file`） ⭐ |
| `-e signal=集合` | 显示信号 |
| `-o 文件` | 输出到文件 ⭐ |
| `-t` / `-tt` / `-ttt` | 时间戳（秒 / 微秒 / 微秒 epoch） |
| `-T` | 显示每个调用耗时 ⭐ |
| `-r` | 显示调用间隔 |
| `-s N` | 字符串最大长度（默认 32） ⭐ |
| `-x` | 十六进制显示非 ASCII |
| `-y` | 显示文件描述符对应的路径 ⭐ |
| `-yy` | 还显示 socket 细节 |
| `-k` | 显示调用栈（需 `libunwind`） |
| `-d` | 显示 strace 自身调试信息 |
| `-q` | 不显示退出信息 |
| `-z` | 只显示成功的调用 |
| `-Z` | 只显示失败的调用 ⭐ |

**trace 集合速记**：
| 集合 | 包含 |
|------|------|
| `file` / `%file` | 文件相关（`open`、`stat`、`read`、`write`…） |
| `network` / `%net` | 网络（`socket`、`connect`、`sendto`…） |
| `process` / `%process` | 进程（`fork`、`execve`、`exit`…） |
| `signal` / `%signal` | 信号 |
| `ipc` | 进程间通信 |
| `desc` | 文件描述符操作 |

#### 实战示例
```bash
# 场景：看程序到底读了哪些文件 ⭐
$ strace -f -e trace=file -o /tmp/strace.log ./app
$ grep -E 'openat.*ENOENT' /tmp/strace.log | head
# 找「找不到的配置文件」——启动失败最常见原因

# 场景：卡住的进程在等什么 ⭐
$ sudo strace -p 1234 -f -tt -T
# Ctrl+C 退出，看最后几个调用

# 场景：汇总统计（找热点）⭐
$ sudo strace -c -p 1234
# 运行几秒后 Ctrl+C
% time     seconds  usecs/call     calls    errors syscall
------ ----------- ----------- --------- --------- ----------------
 85.23    1.234567        1234      1000           read
 10.11    0.146789         147       998           write
  3.02    0.043789          43      1021           openat
------ ----------- ----------- --------- --------- ----------------
100.00    1.425145                  3019         5 total

# 场景：看网络调用
$ strace -f -e trace=network ./client
socket(AF_INET, SOCK_STREAM, IPPROTO_TCP) = 3
connect(3, {sa_family=AF_INET, sin_port=htons(80), sin_addr=inet_addr("93.184.216.34")}, 16) = 0

# 场景：只看失败的调用（权限/文件不存在）
$ strace -f -Z ./app 2>&1 | head -20

# 场景：显示 fd 对应的路径（排查 fd 泄漏）
$ strace -f -y -e trace=openat,close ./app 2>&1 | head -30

# 场景：跟踪权限检查失败的进程（排查 EPERM）
$ sudo strace -p 1234 -e trace=%file -Z 2>&1 | head

# 场景：🔐 观察恶意程序的文件/网络行为
$ strace -f -e trace=file,network -s 256 -o /tmp/trace.log ./suspicious
```

#### 输出解读
```
openat(AT_FDCWD, "/etc/app.conf", O_RDONLY) = -1 ENOENT (No such file or directory)
│      │            │                │        │  └─ 错误描述
│      │            │                │        └─ 错误码
│      │            │                └─ 返回 -1 表示失败
│      │            └─ 文件路径
│      └─ 相对于当前目录
└─ 系统调用名
```

常见错误码：

| 错误 | 含义 |
|------|------|
| `ENOENT` | 文件不存在 |
| `EACCES` | 权限不足 |
| `EPERM` | 操作不允许（capability/SELinux） |
| `EAGAIN` | 资源暂时不可用（非阻塞 I/O 正常情况） |
| `ECONNREFUSED` | 连接被拒绝（端口没开） |
| `ETIMEDOUT` | 超时 |
| `ENOSPC` | 磁盘满 |

#### 常见坑
- ⚠️ **`strace` 会显著拖慢目标进程**（每次系统调用都陷入），**不要在生产高负载服务上用**。要低开销用 `perf trace` 或 eBPF（`bpftrace`）。
- ⚠️ **`-s 32` 默认截断字符串**，看完整内容要 `-s 256` 或更大。
- ⚠️ **不加 `-f` 看不到多线程/子进程**，现代程序几乎都是多线程的。
- **输出量巨大**，务必配 `-e trace=` 和 `-o 文件`。
- **不是所有系统调用都能跟踪**（`vDSO` 里的调用不产生系统调用，如 `gettimeofday`、`clock_gettime` 的快速路径）。
- **`strace` 需要 `ptrace` 权限**：默认只能跟踪自己的进程；跟踪别人的要 root，且容器里的 `CAP_SYS_PTRACE` 常被移除。
- 🔐 **`strace` 附加到进程可以看到它读的敏感文件、收到的网络数据**，是取证和逆向的利器。
- **被跟踪的进程收到 SIGKILL 时 strace 会显示 `+++ killed by SIGKILL +++`**，这是判断「谁杀了这个进程」的关键线索。
- **替代方案**：`ltrace`（库调用）、`perf trace`（更低开销）、`bpftrace`（生产可用）。

#### 相关命令
`ltrace` · `perf trace` · `bpftrace` · `gdb` · `auditd`

### ltrace — 跟踪库函数调用

**常用度**：★★★☆☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：Linux 特有

```bash
ltrace [选项] [命令]
ltrace -p PID
```

| 选项 | 含义 |
|------|------|
| `-p PID` | 附加到进程 |
| `-c` | 汇总统计 |
| `-e 表达式` | 跟踪指定库函数（`strcmp`、`malloc`、`+printf` 表示前缀匹配） |
| `-l 模式` | 只跟踪名字匹配的库 |
| `-x 模式` | 跟踪符号匹配的（前缀 `@` 表示库函数，默认） |
| `-n N` | 缩进 N 层 |
| `-s N` | 字符串最大长度 |
| `-S` | 也显示系统调用 |
| `-f` | 跟踪子进程 |
| `-T` | 显示调用耗时 |
| `-o 文件` | 输出文件 |

```bash
# 场景：看程序调用了哪些库函数
$ ltrace ./app
__libc_start_main(0x4005b6, 1, 0x7ffd..., 0x400650 <unfinished ...>
malloc(64)                                        = 0x55a1b2c3d400
strcpy(0x55a1b2c3d400, "hello")                   = 0x55a1b2c3d400
printf("result: %s\n", "hello")                   = 13
+++ exited (status 0) +++

# 场景：跟踪字符串比较（找口令校验）🔐 ⭐
$ ltrace -e 'strcmp' ./crackme
strcmp("test", "secret")                          = -1
strcmp("admin", "secret")                         = 1

# 场景：跟踪内存分配（找泄漏）
$ ltrace -e 'malloc+free' ./app

# 场景：跟踪加密库调用
$ ltrace -e 'AES_*' ./encrypt_tool

# 场景：汇总
$ ltrace -c ./app | head -20
% time     seconds  usecs/call     calls      function
------ ----------- ----------- --------- --------------------
 45.12    0.001234          12       100 printf
 30.21    0.000826          82        10 malloc

# 场景：🔐 找程序读取的敏感路径（配合 -S 看 stat/open）
$ ltrace -S -e 'strstr+strcmp+fopen' ./login_tool
```

#### 输出解读
```
函数名(参数...) = 返回值
```
- `<unfinished ...>` 表示调用还没返回（`-f` 时常见）。
- `+++ exited (status N) +++` 是进程退出。

#### 常见坑
- ⚠️ **现代程序大量使用 PLT/GOT 优化，且很多函数被内联**，`ltrace` 可能看不到预期调用（尤其是编译器内联的 `strcmp`、`strlen`）。用 `-O0` 编译的程序更容易跟踪。
- ⚠️ **静态链接的程序 `ltrace` 基本无效**（没有动态符号表）。改为 `strace` 或 `gdb`。
- ⚠️ **Go / Rust 的程序大量绕过 libc**（直接系统调用），`ltrace` 看不到关键逻辑。
- **比 `strace` 更慢**，因为要在每次库调用处断点。
- **需要动态链接与符号表**；`strip` 过的二进制看不到符号名。
- **`ltrace` 需要 `libc6-dbg` 之类的调试符号**才能完整显示。
- 🔐 **`ltrace -e strcmp` 是逆向 crackme 的常用手法**，可以直接看到比较的字符串（很多 crackme 的解法）。

#### 相关命令
`strace` · `gdb` · `objdump -T` · `LD_PRELOAD`

### ulimit — 查看与设置资源限制

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：`ulimit` 是 shell 内建；`prlimit` / `getrlimit` 是外部工具

```bash
ulimit [选项] [值]
ulimit -a                # 显示全部
```

| 选项 | 资源 | 常见问题 |
|------|------|----------|
| `-a` | 全部 ⭐ | — |
| `-c` | core 文件大小 | — |
| `-d` | 数据段大小 | — |
| `-f` | 单个文件大小 ⭐ | 大文件写入失败 (`File size limit exceeded`) |
| `-l` | 可锁定内存 | 数据库调优 |
| `-m` | 常驻内存 | 少用 |
| `-n` | **打开文件描述符数** ⭐⭐ | `Too many open files` 的头号原因 |
| `-s` | 栈大小 | 递归爆栈 |
| `-t` | CPU 时间（秒） | — |
| `-u` | 进程数 ⭐ | fork bomb 防护 |
| `-v` | 虚拟内存 | JVM/Go 大堆 |
| `-p` | 管道缓冲区 | — |
| `-S` | 软限制（可提高） | — |
| `-H` | 硬限制（只能降） | — |

```bash
# 场景：查看所有限制 ⭐
$ ulimit -a
real-time non-blocking time  (microseconds, -R) unlimited
core file size              (blocks, -c) unlimited
data seg size               (kbytes, -d) unlimited
scheduling priority                 (-e) 0
file size                   (blocks, -f) unlimited
pending signals                     (-i) 128426
max locked memory           (kbytes, -l) 8192
max memory size             (kbytes, -m) unlimited
open files                          (-n) 1024
pipe size                (512 bytes, -p) 8
POSIX message queues         (bytes, -q) 819200
real-time priority                  (-r) 95
stack size                  (kbytes, -s) 8192
cpu time                   (seconds, -t) unlimited
max user processes                  (-u) 128426
virtual memory              (kbytes, -v) unlimited
file locks                          (-x) unlimited

# 场景：临时提高 fd 限制（只对当前 shell 及子进程有效）⭐
$ ulimit -n
1024
$ ulimit -n 65535
$ ulimit -n
65535
$ ./service        # 继承 65535

# 场景：查看硬限制（软限制不能超过它）
$ ulimit -Hn
1048576
$ ulimit -Sn
1024

# 场景：永久修改（写入 limits.conf）
$ sudo tee /etc/security/limits.d/99-nofile.conf <<'EOF'
*    soft    nofile    65535
*    hard    nofile    65535
root soft    nofile    65535
root hard    nofile    65535
EOF
# ⚠️ 需要重新登录才生效

# 场景：systemd 服务用 unit 文件限制（不看 limits.conf！）⭐
# [Service]
# LimitNOFILE=65535
# LimitNPROC=4096
$ sudo systemctl edit myservice

# 场景：查看运行中进程的实际限制
$ cat /proc/1234/limits
Limit                     Soft Limit           Hard Limit           Units
Max open files            65535                65535                files
$ prlimit -p 1234                     # 更可读
$ prlimit --pid 1234 --nofile=65535:65535   # 动态修改（⚠️ 需权限）

# 场景：防止 fork bomb（当前 shell）
$ ulimit -u 100

# 场景：让崩溃产生 core dump
$ ulimit -c unlimited
$ sudo sysctl -w kernel.core_pattern=/tmp/core.%e.%p
```

#### 输出解读
```
open files                          (-n) 1024
│                                    │    └─ 当前值（软限制）
│                                    └─ 选项字母
└─ 资源名
```

**软限制 vs 硬限制**：软限制是当前生效值，可以在不超过硬限制的范围内调整（普通用户**只能降硬限制**，不能升）。提高硬限制需要 root 或 `CAP_SYS_RESOURCE`。

#### 常见坑
- ⚠️ **`ulimit` 是 shell 内建，只影响当前 shell 及其子进程**。改完不会影响已经运行的进程，也不会影响其他终端。
- ⚠️ **systemd 服务不读 `/etc/security/limits.conf`**（除 `pam_limits` 在某些路径下生效）。systemd 用自己的 `LimitNOFILE=` 等指令，默认继承 systemd 的默认（通常 `1024:524288`）。这是「明明改了 limits.conf 但服务还是 1024」的头号原因。
- ⚠️ **`ulimit -n` 提高后，如果 `ulimit -Hn` 不够也会失败**。先看硬限制。
- **`nofile` 的实际上限受 `/proc/sys/fs/nr_open` 限制**（内核级）。
- **`ulimit -n` 在容器里受容器创建时的 `--ulimit` 限制**，且硬限制可能在容器启动时锁定。
- **`ulimit -v`（虚拟内存）会影响 mmap**，对 JVM/Go 等预留大量地址空间的程序有灾难性影响，可能导致 `Cannot allocate memory`。
- **`ulimit -f`（文件大小）会以 SIGXFSZ 杀死进程**，日志里会看到 `File size limit exceeded (core dumped)`。这是磁盘写满排查的一个隐藏原因。
- **`ulimit -u` 限制的是「用户的进程数」不是「当前 shell 的」**（Linux 上按真实 UID 计），所以对 fork bomb 的防护有限；更好的手段是 cgroup 的 `pids.max`。
- **`prlimit` 可以动态修改运行中进程的限制**（需权限），比 `ulimit` 强大，且可用于脚本。

#### 相关命令
`prlimit` · `limits.conf` · `systemd LimitNOFILE` · `sysctl fs.nr_open` · `cgroup pids.max`

### tmux — 终端复用器

**常用度**：★★★★★ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
tmux [选项] [命令]
```

#### 命令行常用
| 命令 | 作用 |
|------|------|
| `tmux` | 新建会话 |
| `tmux new -s 名字` | 新建命名会话 ⭐ |
| `tmux new -d -s 名字 '命令'` | 后台新建并运行命令 ⭐ |
| `tmux ls` | 列出会话 |
| `tmux a` / `tmux attach -t 名字` | 附加到会话 ⭐ |
| `tmux a -d -t 名字` | 附加并踢掉其他连接 |
| `tmux kill-session -t 名字` | 杀掉会话 |
| `tmux kill-server` | 杀掉所有会话 |
| `tmux ls -F '#{session_name} #{session_windows}'` | 自定义格式 |
| `tmux source-file ~/.tmux.conf` | 重载配置 |

#### 快捷键（默认前缀 `Ctrl+b`）
| 键 | 作用 |
|----|------|
| `Ctrl+b` `d` | 脱离会话（detach） ⭐ |
| `Ctrl+b` `c` | 新建窗口 |
| `Ctrl+b` `,` | 重命名窗口 |
| `Ctrl+b` `n` / `p` | 下/上一个窗口 |
| `Ctrl+b` `0-9` | 跳到指定窗口 |
| `Ctrl+b` `w` | 窗口列表 |
| `Ctrl+b` `%` | 垂直分屏 |
| `Ctrl+b` `"` | 水平分屏 |
| `Ctrl+b` `方向键` | 切换 pane |
| `Ctrl+b` `z` | 当前 pane 最大化/还原 ⭐ |
| `Ctrl+b` `[` | 进入复制模式（可滚动） ⭐ |
| `Ctrl+b` `]` | 粘贴 |
| `Ctrl+b` `x` | 关闭当前 pane |
| `Ctrl+b` `&` | 关闭当前窗口 |
| `Ctrl+b` `t` | 显示时钟 |
| `Ctrl+b` `:` | 命令模式 |
| `Ctrl+b` `?` | 帮助 |
| `Ctrl+b` `空格` | 切换 pane 布局 |

```bash
# 场景：SSH 断开后任务继续运行 ⭐⭐
$ ssh server
$ tmux new -s work
$ ./long_running_task
# 网络断了也没关系
# 重新连接后
$ ssh server
$ tmux attach -t work

# 场景：后台跑任务并分离 ⭐
$ tmux new -d -s backup 'rsync -avz /data/ /backup/'
$ tmux ls
backup: 1 windows (created Tue Sep 15 09:30:00 2026)
$ tmux attach -t backup

# 场景：一次看多个日志（分屏）⭐
$ tmux new -s logs
# Ctrl+b % 垂直分屏
# Ctrl+b " 水平分屏
# 在每个 pane 里 tail -f 不同日志

# 场景：脚本里向 tmux 会话发送命令
$ tmux send-keys -t work 'echo hello' Enter
$ tmux capture-pane -t work -p | tail -5     # 抓取 pane 内容 ⭐

# 场景：查看会话里正在跑什么
$ tmux ls
$ tmux list-panes -t work -F '#{pane_current_command} #{pane_current_path}'
```

#### 输出解读
`tmux ls` 输出：`会话名: N windows (created 时间) (attached 状态)`

#### 🔐 安全要点
- **`tmux` 会话对同一用户的所有终端可见**。多人共享同一账号时（如运维跳板机），任何人都能 `tmux attach` 看别人在干什么。
  ```bash
  $ tmux ls
  $ tmux attach -t 别人的会话     # 不需要密码！
  ```
- **`tmux` 的 socket 在 `/tmp/tmux-<uid>/default`**，权限是 `700`，所以只有同 UID 能访问。**跨账号是安全的**，同账号不是。
- **会话长期运行会累积敏感输出**（密码、token），危害等同于未清理的 shell 历史。
- 攻击者常检查 `tmux ls` / `screen -ls` 找遗留的活跃会话（可能包含未锁定的 root shell）。

#### 常见坑
- ⚠️ **`tmux a` 默认附加到最后一个会话**，如果你有多个会话会搞错。**始终用 `-t 名字`**。
- ⚠️ **在 tmux 里跑 GUI 或需要 `$DISPLAY` 的程序会失败**（环境变量问题）。
- **`Ctrl+b` 前缀与某些终端/程序冲突**（如 emacs 的某些绑定），可以在 `~/.tmux.conf` 改前缀。
- **退出 tmux 会话里的最后一个 shell 会关闭该 pane/窗口**，如果只有一个 pane 则整个会话结束。要保留用 `Ctrl+b d` 脱离而不是 `exit`。
- **`tmux kill-server` 会杀掉所有会话**，包括别人的（同 UID 下）。
- **嵌套 tmux** 时会不认识前缀，用 `Ctrl+b Ctrl+b` 或 `send-prefix`。
- **容器/最小化环境可能没有 tmux**，`screen` 更常见。用 `command -v tmux || command -v screen` 检测。

#### 相关命令
`screen` · `abduco`/`dtach` · `nohup` · `systemd-run --pty`

### screen — 终端复用器

**常用度**：★★★★☆ ｜ **所属**：进程与作业 ｜ **POSIX/GNU 差异**：非 POSIX，比 tmux 更老、更常见于老系统

```bash
screen [选项] [命令]
```

#### 命令行常用
| 命令 | 作用 |
|------|------|
| `screen` | 新建 |
| `screen -S 名字` | 新建命名会话 ⭐ |
| `screen -dmS 名字 命令` | 后台新建并运行 ⭐ |
| `screen -ls` | 列出会话 ⭐ |
| `screen -r 名字` | 恢复会话 ⭐ |
| `screen -x` | 多人共享同一会话 |
| `screen -S 名字 -X quit` | 杀掉会话 |
| `screen -wipe` | 清理死会话 |

#### 快捷键（默认前缀 `Ctrl+a`）
| 键 | 作用 |
|----|------|
| `Ctrl+a` `d` | 脱离（detach） ⭐ |
| `Ctrl+a` `c` | 新建窗口 |
| `Ctrl+a` `A` | 重命名窗口 |
| `Ctrl+a` `n` / `p` | 下/上一个窗口 |
| `Ctrl+a` `0-9` | 跳到窗口 |
| `Ctrl+a` `"` | 窗口列表 |
| `Ctrl+a` `|` | 垂直分屏 |
| `Ctrl+a` `S` | 水平分屏 |
| `Ctrl+a` `Tab` | 切换分屏 |
| `Ctrl+a` `[` | 复制/回滚模式 ⭐ |
| `Ctrl+a` `]` | 粘贴 |
| `Ctrl+a` `X` | 关闭当前区域 |
| `Ctrl+a` `k` | 关闭当前窗口 |
| `Ctrl+a` `?` | 帮助 |
| `Ctrl+a` `Esc` | 进入回滚模式（用方向键/PageUp 浏览） |

```bash
# 场景：SSH 断开后任务继续 ⭐
$ screen -S work
$ ./long_task
# Ctrl+a d 脱离
$ screen -ls
There is a screen on:
	12345.work	(Detached)
$ screen -r work

# 场景：后台跑并分离 ⭐
$ screen -dmS backup rsync -avz /data/ /backup/

# 场景：多人共享同一终端（结对排查）⭐
$ screen -S debug
# 另一个人：
$ screen -x debug          # 双方看到同样的内容

# 场景：进入回滚模式查看历史输出（相当于滚动）⭐
# Ctrl+a Esc，然后用 PageUp/PageDown，q 退出

# 场景：杀掉会话
$ screen -S work -X quit
$ screen -wipe
```

#### 输出解读
`screen -ls` 输出：
```
There is a screen on:
	12345.work	(Detached)
1 Socket in /run/screen/S-alice.
```
`(Detached)` = 已脱离，`(Attached)` = 有人连着。

#### 🔐 安全要点
- **`screen -x` 可以让同 UID 的任何人接入你的会话**，比 tmux 更「开放」（tmux 也能 attach 但需要显式 `-t`）。
- **socket 目录 `/run/screen/S-<user>/` 权限 700**，同 UID 可见。
- 会话里的历史输出可用 `Ctrl+a [` 回滚查看，**包括之前显示的密码**。

#### 常见坑
- ⚠️ **`Ctrl+a` 前缀与 bash 的「行首」快捷键冲突**（在 emacs 模式下 `Ctrl+a` 是行首）。习惯后无问题，但新手常按错。
- ⚠️ **`screen -r` 在会话已被他人 attach 时会失败**（`Attached` 状态）。用 `-x` 共享或 `-d -r` 夺回。
- **`screen` 的配置是 `~/.screenrc`**，与 tmux 的语法完全不同。
- **`screen` 的回滚缓冲区默认只有 100 行**，要调大在 `.screenrc` 里设 `defscrollback 10000`。
- **多层嵌套 screen** 时前缀要重发（`Ctrl+a a`）。
- **`screen -wipe` 会清理「dead」状态的会话**，不影响活跃的。
- **`screen` 在容器里可能没有 SUID/`/run` 权限**，导致无法创建 socket。用 `tmux` 或 `-D`/`-m` 参数绕过。

#### 相关命令
`tmux` · `abduco` · `dtach` · `nohup`
