### apt — Debian 系高层包管理

**常用度**：★★★★★ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian/Ubuntu/Kali/Mint 专有

#### 语法
```bash
apt [选项] 子命令 [包...]
```

#### 高频子命令
| 子命令 | 作用 |
|--------|------|
| `update` | 更新本地包索引（**不升级任何软件**） ⭐ |
| `upgrade` | 升级（不删包、不加新包） ⭐ |
| `full-upgrade` | 升级（允许为解决依赖而删/加包） ⭐ |
| `install` | 安装 ⭐ |
| `remove` | 删除（**保留配置**） |
| `purge` | 删除（**连配置一起删**） ⭐ |
| `autoremove` | 删除不再需要的自动依赖 ⭐ |
| `autoclean` / `clean` | 清理过期的 / 全部下载缓存 |
| `search` | 搜索 ⭐ |
| `show` | 显示包详情 ⭐ |
| `list` | 列出（`--installed` / `--upgradable`） ⭐ |
| `download` | 只下载不安装 ⭐ |
| `edit-sources` | 编辑软件源 |
| `satisfy` | 按依赖表达式安装 |

#### 高频选项
| 选项 | 含义 |
|------|------|
| `-y` | 自动确认 ⭐ |
| `--no-install-recommends` | 不装推荐包（**让系统更精简**） ⭐ |
| `-s` / `--simulate` | 模拟，不真做 ⭐⭐ |
| `--dry-run` | 同 `-s` |
| `-f` / `--fix-broken` | 修复损坏的依赖 ⭐ |
| `--reinstall` | 重装 |
| `-o Dpkg::Options::="--force-confdef"` | 保留旧配置（自动化） |
| `--only-upgrade` | 只升级不安装 |
| `-V` | 显示版本号 |
| `--allow-downgrades` | 允许降级 ⚠️ |
| `-qq` | 极安静（脚本用） |

#### 实战示例
```bash
# 场景：标准流程 ⭐
$ sudo apt update
$ sudo apt -y upgrade
$ sudo apt -y install nginx curl jq

# 场景：先模拟（看会装/删什么）⭐⭐
$ sudo apt -s install nginx
$ sudo apt -s full-upgrade
# 极其重要的习惯：升级前先 -s 看会不会删掉关键包

# 场景：安装本地 .deb（自动处理依赖）⭐
$ sudo apt install ./package.deb

# 场景：卸载（保留 / 连配置一起删）⭐
$ sudo apt remove nginx
$ sudo apt purge nginx
$ sudo apt -y autoremove --purge

# 场景：查看已安装与可升级 ⭐
$ apt list --installed | wc -l
$ apt list --upgradable
$ apt list --installed 'nginx*'

# 场景：搜索与详情 ⭐
$ apt search '^nginx'
$ apt show nginx
$ apt show -a nginx              # 所有版本

# 场景：查看某文件来自哪个包 ⭐
$ apt-file search /usr/bin/nc    # 需 apt install apt-file && apt-file update

# 场景：只看下载不安装（离线部署/分析）⭐
$ apt download nginx
$ apt download nginx -o Dir::Cache::archives=/tmp

# 场景：指定版本安装 ⭐
$ apt list -a nginx
$ sudo apt install nginx=1.24.0-1

# 场景：修复损坏的依赖（`dpkg -i` 之后）⭐⭐
$ sudo apt -f install

# 场景：不装推荐包（精简系统）⭐
$ sudo apt install --no-install-recommends nginx

# 场景：🧪 查看某包会安装哪些文件（不真装）
$ sudo apt -s install nginx 2>&1 | grep -E '^Inst|^Conf' | head

# 场景：脚本里做幂等安装 ⭐
$ dpkg -s nginx >/dev/null 2>&1 || sudo apt-get install -y nginx

# 场景：🔐 检查是否有可升级的安全更新（Debian 系）
$ sudo apt update && apt list --upgradable 2>/dev/null | grep -i security

# 场景：🔐 列出所有已安装包的版本（做基线）⭐
$ dpkg-query -W -f='${Package}\t${Version}\n' | sort > /root/pkg-baseline-$(date +%F).txt
$ # 之后对比：
$ diff <(dpkg-query -W -f='${Package}\t${Version}\n' | sort) /root/pkg-baseline-*.txt
```

#### 输出解读
`apt list --upgradable` 的输出格式：
```
nginx/stable-updates 1.24.0-1 amd64 [upgradable from: 1.22.1-9]
│     │               │          │      └─ 当前版本
│     │               │          └─ 架构
│     │               └─ 可用版本
│     └─ 来源仓库
└─ 包名
```

`apt -s` 的模拟输出关键词：

| 关键词 | 含义 |
|--------|------|
| `Inst` | 将要安装 |
| `Conf` | 将要配置 |
| `Remv` | 将要删除 ⭐ |
| `Upgr` | 将要升级 |

⚠️ **`Remv` 出现在升级模拟里要特别当心**（可能是为了解依赖而删关键包）⭐⭐。

#### 常见坑
- ⚠️ **`apt` 与 `apt-get` 的输出格式不同**（`apt` 有进度条与颜色，**不适合脚本**）。脚本用 `apt-get` 或 `apt -qq` ⭐。
- ⚠️ **`apt upgrade` 不会删除包**，遇到需要删包的依赖冲突会保留旧版本（可能留下安全漏洞）。要真升级用 `full-upgrade`，**但先 `-s` 确认**。
- ⚠️ **`apt` 的锁**：另一进程在用包管理时会报 `Could not get lock /var/lib/dpkg/lock-frontend`。**不要直接删锁文件**，先确认没有 apt/dpkg 在跑：
  ```bash
  $ sudo fuser -v /var/lib/dpkg/lock-frontend
  $ ps aux | grep -E 'apt|dpkg'
  # 确认没有后（谨慎）：
  $ sudo rm /var/lib/dpkg/lock-frontend /var/lib/dpkg/lock /var/cache/apt/archives/lock
  $ sudo dpkg --configure -a
  ```
- ⚠️ **`apt update` 必须在 `install`/`upgrade` 前执行**，否则会用过期索引（装到旧版本或找不到包）。
- ⚠️ **`apt install ./local.deb` 的 `./` 不能省**（否则会被当成包名去仓库找）。
- **`--no-install-recommends` 会少装一些功能**（如 `nginx` 的某些模块），需要时手动补。
- **`autoremove` 可能删掉你以为还需要的东西**（如果它是作为依赖装的）。先 `-s`。
- **`apt` 的下载缓存在 `/var/cache/apt/archives/`**，占空间可用 `apt clean` 清理。
- **`/etc/apt/sources.list.d/*.list` 与 `*.sources`（deb822 格式）都会被读**。

#### 相关命令
`apt-get` · `apt-cache` · `dpkg` · `apt-mark` · `sources.list`

### apt-get — 脚本友好的 apt

**常用度**：★★★★☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian 系

```bash
apt-get [选项] 子命令 [包...]
```

子命令与 `apt` 基本相同，但**输出稳定、无进度条**，适合脚本。

| 与 apt 的差异 | 说明 |
|---------------|------|
| 输出 | **稳定、可解析** ⭐ |
| 进度条 | 无（用 `Dpkg::Progress-Fancy` 控制） |
| `dist-upgrade` | 存在（`apt` 里叫 `full-upgrade`） |
| `--assume-yes` | 等同 `-y` |

```bash
# 场景：脚本里的标准写法 ⭐⭐
$ export DEBIAN_FRONTEND=noninteractive
$ sudo apt-get update -qq
$ sudo apt-get install -y -qq --no-install-recommends nginx
$ sudo apt-get -y -qq autoremove --purge

# 场景：非交互安装（避免卡在配置界面）⭐⭐
$ sudo DEBIAN_FRONTEND=noninteractive apt-get install -y -o Dpkg::Options::="--force-confdef" \
>   -o Dpkg::Options::="--force-confold" nginx

# 场景：只下载不安装（离线仓库制作）⭐
$ apt-get download nginx
$ apt-get install --download-only nginx

# 场景：显示将要做什么但不执行（脚本里做前置校验）⭐⭐
$ apt-get -s install nginx
$ if apt-get -s install nginx | grep -q '^Remv'; then
>   echo "⚠️ 会删除包，需要人工确认"; exit 1
> fi

# 场景：修复损坏的安装（幂等脚本常用）
$ sudo dpkg --configure -a
$ sudo apt-get -f install -y

# 场景：只升级安全更新（unattended-upgrades 风格）
$ sudo apt-get install -y unattended-upgrades
$ sudo dpkg-reconfigure -plow unattended-upgrades

# 场景：🧪 完整的最小化 Dockerfile 做法 ⭐
$ cat /tmp/Dockerfile
FROM debian:stable-slim
RUN apt-get update \
 && apt-get install -y --no-install-recommends ca-certificates curl \
 && rm -rf /var/lib/apt/lists/*
```

#### 常见坑
- ⚠️ **`DEBIAN_FRONTEND=noninteractive` 必须在同一命令的环境里**（`sudo DEBIAN_FRONTEND=... cmd`），或 `export` 后在**同一个 sudo 会话**里。`sudo export ...` 无效。
- ⚠️ **`--force-confold` 保留旧配置文件，`--force-confnew` 用新版本**。自动化里要明确选一个，否则会卡在交互提示 ⭐。
- **`apt-get -qq` 会隐藏 `-y` 之外的很多输出**，出错时的诊断信息也会少。调试时去掉 `-qq`。
- **`apt-key` 已废弃**（Debian 12+/Ubuntu 22.04+），第三方源的密钥应放到 `/etc/apt/keyrings/` 并用 `signed-by=` 引用。

#### 相关命令
`apt` · `dpkg` · `apt-cache` · `unattended-upgrades`

### apt-cache — 查询包元数据

**常用度**：★★★★☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian 系（部分功能已由 `apt show`/`apt list` 取代）

```bash
apt-cache 子命令 [包...]
```

| 子命令 | 作用 |
|--------|------|
| `show 包` | 包详情 ⭐ |
| `showpkg 包` | 依赖与反向依赖（更完整） ⭐ |
| `depends 包` | 依赖 ⭐ |
| `rdepends 包` | **反向依赖（谁依赖它）** ⭐ |
| `pkgnames` | 所有包名 |
| `policy 包` | **版本与来源优先级** ⭐⭐ |
| `madison 包` | 所有可用版本 ⭐ |
| `search 正则` | 搜索 |
| `dump` | 完整索引（很大） |
| `stats` | 索引统计 |
| `unmet` | 未满足的依赖 |

```bash
# 场景：包详情 ⭐
$ apt-cache show nginx | head -20
Package: nginx
Version: 1.24.0-1
Architecture: amd64
Maintainer: Debian Nginx Maintainers <pkg-nginx-maintainers@lists.alioth.debian.org>
Installed-Size: 2500
Depends: nginx-core (= 1.24.0-1)
Priority: optional
Section: httpd
Homepage: https://nginx.org
Description: small, powerful, scalable web/proxy server

# 场景：为什么装的是这个版本？看优先级 ⭐⭐
$ apt-cache policy nginx
nginx:
  Installed: 1.24.0-1
  Candidate: 1.24.0-1                 # ⭐ 将被安装的版本
  Version table:
     1.24.0-1 500
        500 http://deb.debian.org/debian stable/main amd64 Packages
        100 /var/lib/dpkg/status
#    ↑ 优先级数字越大越优先被选为 Candidate

# 场景：所有可用版本 ⭐
$ apt-cache madison nginx
nginx | 1.24.0-1 | http://deb.debian.org/debian stable/main amd64 Packages
nginx | 1.22.1-9 | http://deb.debian.org/debian oldstable/main amd64 Packages

# 场景：依赖与反向依赖（评估升级影响）⭐⭐
$ apt-cache depends nginx
nginx
  Depends: nginx-core
  Depends: nginx-full
$ apt-cache rdepends nginx | head
nginx
Reverse Depends:
  nginx-extras
  nginx-doc

# 场景：🔐 找出「谁在用它」（决定能否安全卸载）⭐
$ apt-cache rdepends --installed libssl3 | tail -n +3 | wc -l

# 场景：搜索（支持正则）⭐
$ apt-cache search '^nginx' | head
$ apt-cache search --names-only 'web server'

# 场景：包名列表（模糊匹配）
$ apt-cache pkgnames | grep -E '^python3-' | wc -l

# 场景：未满足的依赖（排查系统损坏）
$ apt-cache unmet | head
```

#### 输出解读
`apt-cache policy` 的 `Version table`：

| 优先级 | 含义 |
|--------|------|
| `1000` | 手动安装的（`dpkg -i`）或 `/var/lib/dpkg/status` 对应的已装版本 ⭐ |
| `990` | 目标发行版（`stable`）的包 |
| `500` | 非目标发行版的包 |
| `100` | 已安装版本的记录 |
| `-10` | 被 pin 排除 |

⚠️ **优先级（`-t` 与 `/etc/apt/preferences.d/`）决定 `Candidate` 是哪个版本**。这是「为什么装的是旧版本」的答案 ⭐。

#### 常见坑
- ⚠️ **`apt-cache search` 只在索引里搜**，必须先 `apt update`。索引过期会搜不到新包 ⭐。
- ⚠️ **`apt-cache policy` 显示的是「当前索引下的状态」**，与 `apt show -a` 的输出可能不一致（后者展示所有版本详情）。
- **`apt-cache rdepends` 默认包含源码级依赖**，`--installed` 才只列已安装的 ⭐。
- **`apt-cache dumpavail` 与 `apt-cache dump` 输出量极大**，不要在生产上随手跑。
- **`apt-cache` 不检查依赖是否真的能安装**（只读元数据）。真正的依赖解析是 `apt-get` 的活。

#### 相关命令
`apt` · `apt-get` · `apt-mark` · `aptitude`

### apt-mark — 锁定与标记包

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian 系

```bash
apt-mark 子命令 [包...]
```

| 子命令 | 作用 |
|--------|------|
| `hold 包` | **锁定，禁止升级** ⭐ |
| `unhold 包` | 解除锁定 |
| `showhold` | 显示所有锁定的包 ⭐ |
| `auto 包` | 标记为「自动安装」（可被 autoremove） |
| `manual 包` | 标记为「手动安装」（**不会被 autoremove**） ⭐ |
| `showauto` | 显示所有自动安装的包 |
| `showmanual` | 显示所有手动安装的包 ⭐ |
| `minimize` | 自动把不必要的包标记为 auto |

```bash
# 场景：锁定关键包版本（防止意外升级）⭐⭐
$ sudo apt-mark hold nginx linux-image-amd64
$ apt-mark showhold
nginx
linux-image-amd64

# 场景：解除锁定 ⭐
$ sudo apt-mark unhold nginx

# 场景：把某包从 autoremove 列表里保护出来 ⭐
$ sudo apt-mark manual libssl3
$ sudo apt-mark showmanual | wc -l

# 场景：看哪些包是自动装的（autoremove 的候选）
$ apt-mark showauto | wc -l
$ apt-mark showauto | head

# 场景：批量锁定内核相关包（避免内核升级导致的兼容问题）⭐⭐
$ sudo apt-mark hold linux-image-$(uname -r) linux-headers-$(uname -r)

# 场景：🧪 用 preferences 做更精细的 pin（比 hold 更强）⭐⭐
$ sudo tee /etc/apt/preferences.d/nginx-pin <<'EOF'
Package: nginx
Pin: version 1.24.*
Pin-Priority: 1001
EOF
$ apt-cache policy nginx

$ # 或按来源 pin（只用 stable 的包）
$ sudo tee /etc/apt/preferences.d/stable-only <<'EOF'
Package: *
Pin: release a=stable
Pin-Priority: 900
EOF

# 场景：缩减 autoremove 范围
$ sudo apt-mark minimize
```

#### 输出解读
- `apt-mark showhold` 输出锁定的包名（每行一个）。
- `apt-mark showmanual` 的行数通常远小于 `showauto`（大部分包是依赖装进来的）。

#### 常见坑
- ⚠️ **`apt-mark hold` 只阻止升级，不阻止卸载**。要把包彻底固定用 pin（`/etc/apt/preferences.d/`） ⭐。
- ⚠️ **`hold` 的包在 `full-upgrade` 时可能造成依赖冲突**（其他包需要新版本），此时升级会失败或被跳过。
- ⚠️ **`apt-mark auto` 会让包进入 autoremove 候选**（可能被删）。
- **被 `hold` 的包在 `apt` 的输出里会显示「已锁定」**，容易被误认为可用版本不存在。
- **`hold` 状态存在 `/var/lib/apt/extended_states`**，不是 `/etc/`，所以不会被配置备份覆盖 ⭐。
- **pin 的优先级数字**：`> 1000` 表示「即使降级也装这个版本」；`990` 默认；`< 0` 表示「永不安装」。

#### 相关命令
`apt` · `apt-cache policy` · `/etc/apt/preferences.d/`

### dpkg — Debian 系低层包管理

**常用度**：★★★★★ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian 系

```bash
dpkg [选项] 动作
```

| 选项 | 含义 |
|------|------|
| `-i 文件.deb` | 安装（**不解决依赖**） ⚠️ |
| `-r 包` | 卸载（保留配置） |
| `-P 包` | 彻底卸载（连配置） ⭐ |
| `-l [模式]` | 列出已安装包 ⭐ |
| `-L 包` | 列出包的文件清单 ⭐ |
| `-S 路径` | **反查文件属于哪个包** ⭐⭐ |
| `-s 包` | 包状态详情 ⭐ |
| `-c 文件.deb` | 列出 .deb 的内容（不安装） ⭐ |
| `-I 文件.deb` | .deb 的元信息 ⭐ |
| `-x 文件.deb 目录` | 解包 .deb 到目录 ⭐ |
| `-V [包]` | **校验文件完整性（检测篡改）** 🔐 ⭐⭐ |
| `--configure -a` | 配置所有未完成的包 ⭐ |
| `--audit` | 检查半安装的包 ⭐ |
| `--unpack 文件.deb` | 只解包不配置 |
| `-G` | 已有更新版本时不安装 |
| `-E` | 同版本已安装时不安装 |

```bash
# 场景：安装本地 .deb（要自己处理依赖）⚠️
$ sudo dpkg -i package.deb
$ sudo apt -f install          # ⭐ 修依赖，必须跟上
```

#### 输出解读
`dpkg -l` 的两字母状态码（**第一个字母 = 期望状态，第二个 = 当前状态**）：

| 码 | 含义 |
|----|------|
| `ii` | **正确安装**（最常见，正常） ⭐ |
| `rc` | 已删除但保留配置文件（正常，出现在 `purge` 前） |
| `iU` | 解包了但未配置（**半安装，需 `--configure -a`**） |
| `iF` | 配置失败 |
| `iH` | 半安装 |
| `un` | 未知 |
| `pn` | 已清除 |
| `hr` | 期望保持（hold）但已删 |

`dpkg -V` 的输出格式：9 个字符的标记 + 路径，每个字符对应一种校验：

```
??5??????   /usr/bin/ls
│││││││││
││││││││└─ 第 9 位
...
│└──────── 第 2 位
└───────── 第 1 位
```
标记含义（简化）：`5` = md5 不匹配、`S` = 大小不匹配、`T` = mtime 不匹配、`?` = 该项未检查。**任何非 `?` 的标记都值得追查** 🔐。

#### 常见坑
- ⚠️ **`dpkg -i` 不解决依赖**。装完必须 `apt -f install`，否则系统会处于依赖断裂状态 ⭐。
- ⚠️ **`dpkg -i` 的 `./` 不能省**（`dpkg -i package.deb` 会找不到文件，要 `./package.deb` 或完整路径）。
- ⚠️ **`dpkg -V` 的基准是 `/var/lib/dpkg/info/*.md5sums`**。**如果攻击者同时改了二进制和这个文件，校验会通过**。对抗方式：
  - 用**离线保存的基线**（把 `dpkg -V` 输出、`md5sums` 存在只读介质）
  - 用 `debsums -c`（依赖同样的本地数据，同样可被绕过）
  - 用独立的完整性监控（AIDE / Tripwire / IMA）
- ⚠️ **`dpkg --force-all` 会破坏包数据库的一致性**，只在极度无奈时用。
- ⚠️ **包管理器的锁**：`dpkg` 与 `apt` 共用锁，不能同时运行。
- **`dpkg -S` 只查已安装包的文件清单**，未安装包的文件要用 `apt-file search` ⭐。
- **`dpkg -S` 对路径有软链接时不解析**（要写包记录里的原始路径，通常是 `/usr/bin/...` 而非 `/bin/...`）。
- **`dpkg -l '模式'` 支持通配符**（如 `dpkg -l 'nginx*'`）。

#### 相关命令
`apt` · `apt-get` · `dpkg-deb` · `apt-file` · `debsums` · `apt-cache`

### dpkg-deb — 操作 .deb 文件

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian 系

```bash
dpkg-deb [选项] 动作
```

| 动作 | 作用 |
|------|------|
| `-b 目录 [输出.deb]` | **打包**（从目录构建 .deb） ⭐ |
| `-c 文件.deb` | 列出内容（同 `dpkg -c`） ⭐ |
| `-I 文件.deb` | 显示控制信息 ⭐ |
| `-f 文件.deb 字段` | 显示某控制字段 ⭐ |
| `-e 文件.deb 目录` | **解出控制信息（含安装脚本）** 🔐 ⭐⭐ |
| `-x 文件.deb 目录` | 解出文件内容 ⭐ |
| `-W 文件.deb 字段` | 同 `-f`（旧写法） |
| `-R 文件.deb 目录` | 解出所有（内容 + 控制） |

| 选项 | 含义 |
|------|------|
| `-Z 压缩` | 压缩算法（`gzip`/`xz`/`zstd`/`none`） ⭐ |
| `-z 级别` | 压缩级别 |
| `--root-owner-group` | 所有文件归 root:root（**普通用户构建时用**） ⭐ |
| `-D` | 不压缩控制文件 |

```bash
# 场景：🔐 审查第三方 .deb（安装前必做）⭐⭐
$ dpkg-deb -I package.deb

-rw-r--r-- root/root      1234 2026-09-01 10:00 ./etc/myapp/config.yml

$ # 🔐⭐ 看安装脚本（这是最需要审查的部分）
$ mkdir -p /tmp/debctl && dpkg-deb -e package.deb /tmp/debctl
$ ls -la /tmp/debctl/

-rw-r--r-- 1 user user 512 ... control
-rw-r--r-- 1 user user   3 ... md5sums

-rwxr-xr-x 1 user user 123 ... preinst      # ⭐ 安装前执行

# ⭐ 审查这里：有没有 curl|bash、反连、改 crontab、加用户…

# 场景：🔐 看有没有 SUID 文件
$ dpkg-deb -c package.deb | grep -E '^.{3}s|^-rws'

# 场景：只取一个字段（脚本用）⭐
$ dpkg-deb -f package.deb Version
1.2.3
$ dpkg-deb -f package.deb Depends

# 场景：安全解包（不安装）⭐
$ dpkg-deb -x package.deb /tmp/unpacked

# 场景：自己打包（从文件树构建）⭐
$ tree /tmp/myapp-pkg

$ dpkg-deb --root-owner-group -Zzstd -b /tmp/myapp-pkg /tmp/myapp_1.0.0_amd64.deb

# 场景：对比两个版本的包内容 ⭐
```

#### 输出解读
`.deb` 是 **ar 归档**，内部含两个 tar：
- `control.tar.*`：元信息 + 安装脚本
- `data.tar.*`：实际文件

```
$ ar t package.deb
debian-binary
control.tar.zst
data.tar.zst
```

维护者脚本的执行时机：

| 脚本 | 时机 | 权限 |
|------|------|------|
| `preinst` | 解包**前** | root ⚠️ |
| `postinst` | 配置**后**（安装完成） | root ⚠️ |
| `prerm` | 卸载**前** | root |
| `postrm` | 卸载**后** | root |

⚠️ **这四个脚本都以 root 执行**。审查第三方 `.deb` 时它们是最需要看的地方 🔐。

#### 常见坑
- ⚠️ **不用 root 也能 `-c`/`-I`/`-x`/`-e` 解包检查**（这是安全审查的正确姿势）。**安装才需要 root** ⭐。
- ⚠️ **`-e` 不会解出 `data.tar`**（那是 `-x` 的活）。两者要一起用才能看全 ⭐。
- ⚠️ **`dpkg-deb -b` 打包时若不指定 `--root-owner-group`**，文件属主会是你的 UID，安装后会有奇怪的属主。
- ⚠️ **压缩算法选错会导致旧版 dpkg 无法安装**（`zstd` 需要 dpkg 1.21.18+）⭐。
- **`dpkg-deb -R` 会解出到同一目录**，可能与已有文件冲突。
- **`dpkg-deb` 是 `dpkg` 的子命令**，很多操作 `dpkg` 也能做（`-c`/`-I`/`-x`/`-e`）。
- **`data.tar` 的路径以 `./` 开头**，`-c` 输出里的第 6 列才是路径（`awk '{print $6}'`）。

#### 相关命令
`dpkg` · `ar` · `tar` · `fpm` · `lintian`

### add-apt-repository — 添加软件源

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Debian/Ubuntu 专有（`software-properties-common` 包）

```bash
add-apt-repository [选项] 源
```

| 选项 | 含义 |
|------|------|
| `-r` | 删除源 ⭐ |
| `-y` | 自动确认 |
| `-u` | 添加后立即 `apt update` ⭐ |
| `-n` | 不更新（默认已不更新） |
| `-P` | 只打印要添加的源 |
| `-s` | 同时加源码源 |
| `-c 组件` | 指定组件 |

```bash
# 场景：添加 PPA（Ubuntu）⭐
$ sudo add-apt-repository -y ppa:ondrej/php
$ sudo apt update

# 场景：添加后立即更新 ⭐
$ sudo add-apt-repository -yu ppa:deadsnakes/ppa

# 场景：删除源 ⭐
$ sudo add-apt-repository -r ppa:ondrej/php
$ sudo apt update

# 场景：只打印要加什么（先审查）⭐⭐
$ add-apt-repository -P ppa:ondrej/php
deb https://ppa.launchpadcontent.net/ondrej/php/ubuntu noble main
# deb-src https://ppa.launchpadcontent.net/ondrej/php/ubuntu noble main
$ # ⭐ 看到内容后再真加

# 场景：添加普通仓库（非 PPA）
$ sudo add-apt-repository "deb [arch=amd64 signed-by=/etc/apt/keyrings/foo.gpg] https://repo.example.com/apt stable main"

# 场景：🔐 手工管理（更可控，推荐生产使用）⭐⭐
# 1. 下载并验证 GPG 公钥
$ curl -fsSL https://repo.example.com/key.gpg | sudo gpg --dearmor -o /etc/apt/keyrings/example.gpg
$ ls -l /etc/apt/keyrings/example.gpg
-rw-r--r-- 1 root root 1234 ... example.gpg
# 2. 写源（用 signed-by 绑定到该密钥）
$ echo 'deb [signed-by=/etc/apt/keyrings/example.gpg] https://repo.example.com/apt stable main' \
>   | sudo tee /etc/apt/sources.list.d/example.list
$ sudo chmod 644 /etc/apt/sources.list.d/example.list
# 3. 更新
$ sudo apt update

# 场景：看当前有哪些源 ⭐
$ grep -rhE '^[^#]' /etc/apt/sources.list /etc/apt/sources.list.d/ | head
$ apt-cache policy | grep -A1 'origin' | head -20

# 场景：deb822 格式（Debian 12+ 推荐）⭐
$ cat /etc/apt/sources.list.d/example.sources
Types: deb
URIs: https://repo.example.com/apt
Suites: stable
Components: main
Signed-By: /etc/apt/keyrings/example.gpg
```

#### 输出解读
现代格式的源行：

```
deb [arch=amd64 signed-by=/path/key.gpg] https://repo/apt stable main
│   │                │                          │      │      └─ 组件
│   │                │                          │      └─ 发行版代号
│   │                │                          └─ 仓库地址
│   │                └─ 用哪个密钥验签 ⭐
│   └─ 架构限制
└─ 二进制源（deb-src 是源码源）
```

#### 🔐 安全要点
| 风险 | 说明 |
|------|------|
| 第三方源 = 把 root 权限交给对方 | 该源里的包会以 root 安装 |
| 密钥不绑定 | 用 `signed-by=` 绑定到具体密钥，**不要用全局 `apt-key`** ⭐ |
| 源被劫持 | 用 HTTPS + 校验指纹 |
| PPAs 不经过 Debian/Ubuntu 审核 | 只看 PPA 所有者 |

```bash
# 查看系统里所有受信任的密钥（哪些源有签名权）🔐
$ ls /etc/apt/trusted.gpg.d/ /etc/apt/keyrings/ 2>/dev/null
$ apt-key list 2>/dev/null || echo "apt-key 已废弃（好）"
$ gpg --show-keys /etc/apt/keyrings/*.gpg 2>/dev/null | grep -E 'uid|^pub'
```

#### 常见坑
- ⚠️ **`add-apt-repository` 会自动获取并导入 GPG 密钥到全局钥匙环**（旧行为），**等价于给该密钥签任何源的权利** ⭐。生产环境应手工用 `signed-by=`。
- ⚠️ **`apt-key` 已废弃**（Debian 12 / Ubuntu 22.04+），用 `signed-by` + `/etc/apt/keyrings/`。
- ⚠️ **加源后必须 `apt update`**，否则 `apt install` 找不到新包。
- ⚠️ **PPA 的 URL 里含发行版代号**（`noble`、`jammy`），系统升级后旧源会 404，要更新或删除。
- **`add-apt-repository` 需要 `software-properties-common`**，最小化系统可能没装。
- **源的优先级可以用 pin 调整**（见 `apt-mark`）。
- **`/etc/apt/sources.list` 与 `/etc/apt/sources.list.d/*.list` 是同级的**，都会读。deb822 的 `.sources` 文件优先级更高。

#### 相关命令
`apt` · `apt-key` · `/etc/apt/sources.list.d/` · `gpg --dearmor`

#### 输出解读
`dnf history` 的 `Altered` 列：

| 后缀 | 含义 |
|------|------|
| `E` | 包含 **Erase（卸载）** ⭐ |
| `I` | 包含 Install |
| `U` | 包含 Upgrade |
| `D` | 包含 Downgrade |
| `EE` | 卸载了多个包（**可能是破坏性操作**） ⭐ |

`dnf check-update` 的退出码：

| 码 | 含义 |
|----|------|
| `0` | 无更新 |
| `100` | **有可用更新** ⭐ |
| `1` | 出错 |

#### 常见坑
- ⚠️ **`dnf upgrade` 会升级内核**（需重启生效），与 `apt` 的行为不同。要跳过内核用 `--exclude=kernel*` ⭐。
- ⚠️ **`dnf history undo` 依赖缓存中的旧 RPM 包**。`dnf clean all` 之后可能无法回滚 ⭐。
- ⚠️ **`--nogpgcheck` 会跳过签名校验**，禁止用于生产。
- ⚠️ **`dnf remove` 会连带删除依赖它的包**（可能删除关键组件）。先 `--assumeno` 或看输出里的删除列表 ⭐。
- **`dnf` 比 `yum` 快得多**（基于 libsolv），但元数据刷新仍慢。用 `--refresh` 强制，或调 `/etc/dnf/dnf.conf` 的 `metadata_expire`。
- **`dnf` 与 `rpm` 共用数据库**，但 `rpm -i` 装的包**不会出现在 `dnf history` 里**（🔐 攻击者常用 `rpm -i` 绕过历史记录）⭐。
- **`module` 是 RHEL 8+ 的概念**（AppStream 中的不同版本流），`dnf module enable php:8.2` 切换版本。
- **`weak deps`（Recommends）默认会装**，用 `--setopt=install_weak_deps=False` 精简 ⭐。

#### 相关命令
`yum` · `rpm` · `dnf-automatic` · `dnf history` · `reposync` · `createrepo_c`

### yum — dnf 的旧名

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：RHEL 7 及更早；RHEL 8+ 上 `yum` 是 `dnf` 的符号链接

```bash
yum [选项] 子命令 [包...]
```

```bash
# 场景：RHEL 7 / CentOS 7 上的标准用法（与 dnf 基本相同）
$ sudo yum check-update
$ sudo yum -y update
$ sudo yum -y install nginx

# 场景：查询
$ yum search nginx
$ yum info nginx
$ yum list installed | head
$ yum provides '*/bin/nc'

# 场景：历史（yum 也有，但功能比 dnf 弱）
$ sudo yum history
$ sudo yum history info 42
$ sudo yum history undo 42

# 场景：仓库
$ yum repolist
$ sudo yum-config-manager --add-repo https://example.com/repo.repo
$ sudo yum-config-manager --enable epel
$ sudo yum-config-manager --disable epel

# 场景：清理
$ sudo yum clean all
$ sudo yum makecache

# 场景：包组
$ yum grouplist
$ sudo yum groupinstall -y 'Development Tools'

# 场景：确认本机是 yum 还是 dnf ⭐
$ command -v yum; readlink -f "$(command -v yum)"
/usr/bin/dnf            # ⭐ 指向 dnf 说明是 RHEL 8+
$ dnf --version

# 场景：🧪 yum 与 dnf 的差异要点 ⭐
$ # dnf 的改进：
$ #   依赖解析用 libsolv（快得多）
$ #   支持模块（AppStream）
$ #   支持事务回滚（history undo 更可靠）
$ #   默认不装 Recommends（可配）
$ #   API 更稳定（Python 3）
```

#### 常见坑
- ⚠️ **在 RHEL 8+ 上 `yum` 就是 `dnf`**（符号链接或 wrapper），所以 `yum` 的文档与 `dnf` 相通 ⭐。
- ⚠️ **RHEL 7 的 `yum` 依赖解析非常慢**（尤其包多时），这是它被 dnf 取代的主因。
- ⚠️ **`yum -y update` 在 RHEL 7 上会升级内核**，需重启。
- **`yum` 与 `dnf` 的缓存目录不同**（`/var/cache/yum/` vs `/var/cache/dnf/`）。
- **`yum history undo` 在 RHEL 7 上成功率较低**（dnf 的改进之一）。

#### 相关命令
`dnf` · `rpm` · `yum-config-manager`

### rpm — RPM 低层包管理

**常用度**：★★★★☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：RPM 系专有

```bash
rpm [选项] [包|文件]
```

| 选项 | 含义 |
|------|------|
| `-qa` | 列出所有已安装包 ⭐ |
| `-qi 包` | 包信息 ⭐ |
| `-ql 包` | 文件清单 ⭐ |
| `-qf 路径` | **反查文件归属** ⭐⭐ |
| `-qc 包` / `-qd 包` | 只看配置文件 / 文档 ⭐ |
| `-qp 文件.rpm` | 查询未安装的 .rpm ⭐ |
| `-qpl 文件.rpm` | 列出 .rpm 内容 ⭐ |
| `-qp --scripts 文件.rpm` | 看安装脚本 🔐 ⭐⭐ |
| `-qp --requires` / `--provides` | 依赖 / 提供 ⭐ |
| `-V 包` | **校验文件完整性（检测篡改）** 🔐 ⭐⭐ |
| `-Va` | 校验所有包 ⭐ |
| `-K 文件.rpm` | 校验签名 🔐 ⭐ |
| `-i 文件.rpm` | 安装（**不解决依赖**） ⚠️ |
| `-U 文件.rpm` | 升级或安装 ⚠️ |
| `-e 包` | 卸载 ⚠️ |
| `-e --nodeps 包` | ⚠️⚠️ 强制卸载（不检查依赖） |
| `--last` | 按安装时间排序 ⭐ |
| `--import 密钥` | 导入 GPG 公钥 |

```bash
# 场景：列出已安装包 ⭐
$ rpm -qa | wc -l
$ rpm -qa | grep -i nginx

# 场景：🔐 按安装时间排序（找最近装的，追查后门）⭐⭐
$ rpm -qa --last | head -20
nginx-1.24.0-1.el9.x86_64            Tue 15 Sep 2026 09:00:00 AM CST
...
$ rpm -qa --qf '%{INSTALLTIME:date}\t%{NAME}-%{VERSION}\n' | sort -r | head

# 场景：包信息与文件清单 ⭐
$ rpm -qi nginx
Name        : nginx
Version     : 1.24.0
Release     : 1.el9
Architecture: x86_64
Install Date: Tue 15 Sep 2026 09:00:00 AM CST
Group       : Unspecified
Size        : 1234567
License     : BSD
Signature   : RSA/SHA256, ...
Source RPM  : nginx-1.24.0-1.el9.src.rpm
Build Date  : Mon 01 Sep 2026
Vendor      : Rocky
URL         : https://nginx.org
Summary     : A high performance web server
Description : ...

$ rpm -ql nginx | head
/etc/nginx/nginx.conf
/usr/sbin/nginx
...

$ rpm -qc nginx                # 只看配置文件 ⭐

# 场景：🔐 反查文件属于哪个包（应急响应第一命令）⭐⭐
$ rpm -qf /usr/bin/passwd
passwd-0.80-1.el9.x86_64
$ rpm -qf /tmp/suspicious
error: file /tmp/suspicious: No package owns /tmp/suspicious
# ⭐ 无归属 = 可疑！

# 场景：🔐🔐 校验包文件（检测二进制被替换）⭐⭐
$ rpm -V passwd
# 无输出 = 一致
# 有输出格式：SM5DLUGTP  c /path
$ rpm -V coreutils
$ sudo rpm -Va                       # 校验所有包（很慢）

# 🔐 只显示「内容类」差异（排除 mtime 与权限变化）
$ sudo rpm -Va | grep -vE '^\.{9}|^..5' | head
$ # 首列字符含义见下文

# 场景：🔐 检查 .rpm 签名与脚本（安装第三方 rpm 前必做）⭐⭐
$ rpm -K package.rpm
package.rpm: digests signatures OK
$ rpm -Kv package.rpm               # 详细（含签名者）

$ rpm -qp --scripts package.rpm
preinstall scriptlet (using /bin/sh):
...
postinstall scriptlet (using /bin/sh):
#!/bin/sh
# ⭐ 审查：curl|bash、反连、cron、加用户…
...

$ rpm -qpl package.rpm | grep -E '^/etc/(cron|systemd|sudoers|passwd)'
$ rpm -qpl package.rpm | head

$ rpm -qp --requires package.rpm
$ rpm -qp --provides package.rpm
$ rpm -qp --changelog package.rpm | head

# 场景：⚠️ 安装本地 rpm（不解决依赖）
$ sudo rpm -ivh package.rpm
$ sudo rpm -Uvh package.rpm         # 升级或安装
$ sudo dnf -y install ./package.rpm  # ⭐ 更推荐（自动解决依赖）

# 场景：⚠️ 强制卸载（破坏依赖，慎用）
$ sudo rpm -e --nodeps package
$ sudo rpm -e --allmatches --justdb package    # 只改数据库不删文件

# 场景：🔐 导入 GPG 公钥 ⭐
$ sudo rpm --import https://example.com/RPM-GPG-KEY
$ rpm -qa gpg-pubkey --qf '%{NAME}-%{VERSION}-%{RELEASE} %{SUMMARY}\n'

# 场景：查哪个包提供了某能力
$ rpm -q --whatprovides 'libcrypto.so.3()(64bit)'
$ rpm -q --whatrequires 'libcrypto.so.3()(64bit)'

# 场景：提取 rpm 内容不安装（安全审查）⭐
$ rpm2cpio package.rpm | cpio -idmv -D /tmp/unpacked
$ find /tmp/unpacked -type f -perm -4000 -ls    # 🔐 看 SUID
```

#### 输出解读
`rpm -V` 的输出格式：**9 个字符的标记 + 属性字符 + 路径**

```
SM5DLUGTP  c /etc/nginx/nginx.conf
│││││││││  │ └─ 路径
│││││││││  └─ 属性（c = config，d = doc，l = license，r = readme）
││││││││└─ 9. T = mtime 不同
│││││││└─ 8. P = capabilities 不同
││││││└─ 7. G = 属组不同
│││││└─ 6. U = 属主不同
││││└─ 5. L = 符号链接目标不同
│││└─ 4. D = 设备号不同
││└─ 3. 5 = md5（内容）不同 ⭐⭐
│└─ 2. M = 权限不同
└─ 1. S = 大小不同
```

⚠️ **首字母 `S` 或第 3 位的 `5` 是最需要关注的**（大小或内容变了 = 二进制被替换）🔐。
`.` 表示一致，`?` 表示未能检查。

#### 常见坑
- ⚠️ **`rpm -i` / `rpm -U` 不解决依赖**，装完必须 `dnf -f` 之类的修复（`dnf` 会处理）。**优先用 `dnf install ./pkg.rpm`** ⭐。
- ⚠️ **`rpm -e --nodeps` 会留下依赖断裂**，可能让系统无法更新。只在明确后果时用。
- ⚠️ **`rpm -Va` 会报告大量「正常」的差异**（mtime、权限、配置文件被合法修改）。要过滤：
  ```bash
  # 只看内容变化（第 3 位是 5）
  $ sudo rpm -Va | awk 'substr($0,3,1)=="5"'
  ```
- ⚠️ **`rpm -V` 的基准是本地 RPM 数据库**。**攻击者改二进制后同步更新数据库即可绕过**。要用离线基线 ⭐。
- ⚠️ **`rpm --import` 会永久信任该密钥**（对所有仓库）。只在确认来源后导入 ⭐。
- ⚠️ **`rpm -i` 装包不会写 `dnf history`**（🔐 攻击者绕过审计的手法）⭐。
- **`rpm -qf` 只查已安装包**；未安装的用 `dnf provides`。
- **`rpm -qa --last` 的时间可能受系统时钟影响**，取证时与 `journalctl` 交叉验证。
- **`rpm2cpio | cpio` 可提取内容而不安装**（安全审查的正确姿势）⭐。
- **`rpm` 的数据库在 `/var/lib/rpm/`**，损坏时可用 `rpm --rebuilddb` 重建（⚠️ 先备份）。

#### 相关命令
`dnf` · `yum` · `rpm2cpio` · `cpio` · `rpmdevtools`

### zypper — openSUSE 包管理

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：openSUSE / SLES 专有

```bash
zypper [选项] 命令 [包...]
```

| 命令 | 作用 |
|------|------|
| `refresh` / `ref` | 刷新仓库（`apt update` 的对应） ⭐ |
| `update` / `up` | 升级已安装包 ⭐ |
| `dup` | 发行版整体升级（`dist-upgrade` 对应） ⭐ |
| `patch` | 应用补丁（**安全更新用这个**） ⭐ |
| `install` / `in` | 安装 ⭐ |
| `remove` / `rm` | 卸载 ⭐ |
| `search` / `se` | 搜索 ⭐ |
| `info` | 详情 ⭐ |
| `list-updates` / `lu` | 列出可用更新 ⭐ |
| `list-patches` / `lp` | 列出可用补丁 ⭐ |
| `repos` / `lr` | 列出仓库 ⭐ |
| `addrepo` / `ar` | 添加仓库 |
| `removerepo` / `rr` | 移除仓库 |
| `modifyrepo` / `mr` | 修改仓库 |
| `packages --orphaned` | 孤立包 ⭐ |
| `verify` | 校验已安装包 ⭐ |
| `clean` | 清理缓存 |
| `ar-to` / `dist-upgrade` | — |

| 选项 | 含义 |
|------|------|
| `-y` / `--no-confirm` | 自动确认 ⭐ |
| `--dry-run` | 模拟 ⭐⭐ |
| `-f` | 强制 |
| `--no-recommends` | 不装推荐包 ⭐ |
| `-t 类型` | 类型（`package`/`patch`/`pattern`） ⭐ |
| `-C` | 用缓存（不刷新） |
| `-n` | 只做（不交互） |
| `--details` | 详细 |

```bash
# 场景：标准流程 ⭐
$ sudo zypper refresh
$ zypper list-updates
$ sudo zypper --no-confirm update

# 场景：先模拟（看会删什么）⭐⭐
$ sudo zypper --dry-run update
$ sudo zypper --dry-run install nginx

# 场景：安装（按类型）⭐
$ sudo zypper install nginx
$ sudo zypper install -t pattern devel_basis       # pattern（成套软件）
$ sudo zypper install -t patch openSUSE-2026-123   # 补丁

# 场景：安全补丁（推荐的安全更新方式）⭐⭐
$ zypper list-patches --category security
$ sudo zypper --no-confirm patch --category security
$ zypper lp -a --bugzilla

# 场景：搜索与详情 ⭐
$ zypper search nginx
$ zypper search --installed-only
$ zypper info nginx
$ zypper info --requires nginx
$ zypper info --recommends nginx

# 场景：仓库管理 ⭐
$ zypper repos
$ zypper repos --uri
$ sudo zypper addrepo -f https://example.com/repo openSUSE_Example
$ sudo zypper modifyrepo --disable openSUSE_Example
$ sudo zypper remove-repo openSUSE_Example

# 场景：🔐 校验已安装包（检测篡改）⭐
$ sudo zypper verify
$ sudo zypper verify --details

# 场景：找孤立包（不再被任何仓库需要的）
$ zypper packages --orphaned
$ sudo zypper remove --clean-deps <包名>

# 场景：脚本幂等安装 ⭐
$ rpm -q nginx >/dev/null 2>&1 || sudo zypper --no-confirm install nginx

# 场景：清理缓存
$ sudo zypper clean --all

# 场景：发行版升级（跨版本）⭐⭐
$ sudo zypper refresh
$ sudo zypper --no-confirm dup
$ # 或指定目标版本
$ sudo zypper dup --releasever 16.0
```

#### 输出解读
`zypper list-updates` 的表头：`S | Repository | Name | Current Version | Available Version | Arch`。

`S` 列的含义：`v` = 可更新、`-` = 其他状态。

`zypper patches` 的分类：

| 类别 | 含义 |
|------|------|
| `security` | **安全补丁（优先）** ⭐ |
| `recommended` | 推荐补丁 |
| `optional` | 可选 |
| `feature` | 新功能 |

#### 常见坑
- ⚠️ **`zypper update` 不会升级到新的发行版**（只更新包），跨版本要 `zypper dup` ⭐。
- ⚠️ **`zypper dup` 是破坏性操作**（可能降级、删包、改大量配置），必须 `--dry-run` 先看，且要在维护窗口执行 ⭐。
- ⚠️ **`zypper` 的仓库优先级默认都相同**，冲突时可能从任意仓库选版本。要显式设优先级：`zypper mr -p 90 repo`（数字小优先） ⭐。
- ⚠️ **`refresh` 是必需的**（`apt update` 的对应），否则 `list-updates` 是过期的。
- **openSUSE Tumbleweed 是滚动发行版**，`dup` 是**标准更新方式**（每天/每周），不是「升级」。
- **`--no-recommends` 能精简系统**（openSUSE 默认会装推荐包，可能导致依赖膨胀）⭐。
- **`zypper` 有 `--non-interactive` 模式**，会默认选择保守方案（不删包）。脚本里配合 `-y` 用 ⭐。
- **`zypper` 的缓存清理要 `clean --all`**（单独 `clean` 只清部分）。

#### 相关命令
`rpm` · `zypper dup` · `SUSEConnect` · `yast`

### pacman — Arch 系包管理

**常用度**：★★★★★ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Arch / Manjaro / EndeavourOS / Omarchy / CachyOS 专有

> ⚠️ **Arch 是滚动发行版。永远用 `pacman -Syu` 整体升级，绝不要「部分升级」（partial upgrade）。**

#### 语法
```bash
pacman [选项] [包...]
```

#### 操作（首字母）
| 操作 | 含义 |
|------|------|
| `-S` | 同步（从仓库安装/更新） ⭐ |
| `-R` | 移除 ⭐ |
| `-Q` | 查询本地数据库 ⭐ |
| `-U` | 安装本地包文件 ⭐ |
| `-F` | 查询文件数据库（反查归属） ⭐ |
| `-D` | 修改数据库 |
| `-T` | 检查依赖 |
| `-V` | 版本 |

#### 常用组合
| 组合 | 作用 |
|------|------|
| `-Syu` | ⭐⭐ **整体升级（唯一正确的升级方式）** |
| `-Ss 关键词` | 搜索仓库 ⭐ |
| `-Si 包` | 仓库中的包信息 ⭐ |
| `-Sc` / `-Scc` | 清理包缓存 ⭐ |
| `-Rns 包` | 卸载 + 依赖 + 配置（最彻底） ⭐ |
| `-Q` | 已安装列表 ⭐ |
| `-Qe` | 显式安装的（非依赖） ⭐ |
| `-Qm` | **外来包（AUR / 手动装的）** ⭐ |
| `-Ql 包` | 文件清单 ⭐ |
| `-Qo 路径` | **反查文件归属** ⭐⭐ |
| `-Qk 包` / `-Qkk 包` | **校验文件（-Qkk 更详细）** 🔐 ⭐⭐ |
| `-Qdt` | 孤立依赖（可清理） ⭐ |
| `-U 文件` | 安装本地包 ⭐ |

| 选项 | 含义 |
|------|------|
| `--noconfirm` | 自动确认 ⭐ |
| `--needed` | 已是最新则跳过（幂等） ⭐ |
| `--overwrite '模式'` | 覆盖冲突文件 |
| `--ignore=包` | 跳过某包 ⭐ |
| `--print` | 只打印不执行（dry run） ⭐ |
| `--print-format '%n %v'` | 格式化打印 ⭐ |
| `--dbonly` | 只改数据库 |
| `--noscriptlet` | 不执行安装脚本 ⭐ |
| `--downloadonly` | 只下载 |

#### 实战示例
```bash
# 场景：⭐⭐ 整体升级（唯一正确的升级方式）
$ sudo pacman -Syu
:: Synchronizing package databases...
:: Starting full system upgrade...
# ⚠️ 绝不要 pacman -Sy 然后单独装包（= 部分升级 = 系统损坏）

# 场景：搜索与安装 ⭐
$ pacman -Ss nginx
$ sudo pacman -S nginx
$ sudo pacman -S --needed base-devel git      # ⭐ --needed 幂等

# 场景：查看仓库中的包信息 ⭐
$ pacman -Si nginx

Name            : nginx
Version         : 1.24.0-1
Description     : Lightweight HTTP server and IMAP/POP3 proxy
Architecture    : x86_64

Installed Size  : 4.5 MiB
Depends On      : pcre2 openssl zlib

# 场景：卸载（三种彻底程度）⭐
$ sudo pacman -R nginx            # 只删包

$ sudo pacman -Rns nginx          # ⭐ 连配置一起删（最彻底）

$ pacman -F 文件或命令          # 查未安装包的归属（需先 pacman -Fy）
$ sudo pacman -Fy                # 更新文件数据库
$ pacman -F pacman.conf

# 场景：已安装列表与分类 ⭐
$ pacman -Q | wc -l
$ pacman -Qe                     # 显式安装（你主动装的）
$ pacman -Qq                      # 只要名字（脚本友好）
$ pacman -Qm                     # 🔐 外来包（AUR / 手动装的）
$ pacman -Qdt                    # 孤立依赖（可清理）
$ sudo pacman -Rns $(pacman -Qdtq)   # ⚠️ 先确认列表

# 场景：文件清单 ⭐
$ pacman -Ql nginx | head
nginx /etc/nginx/

nginx /usr/bin/nginx
$ pacman -Ql nginx | grep -v '/$' | wc -l

$ sudo pacman -Qkk 2>&1 | grep -vE '0 altered files' | head

# 场景：清理（包缓存会占很大空间）⭐
$ du -sh /var/cache/pacman/pkg
$ sudo pacman -Sc                # 清理已卸载包的缓存
$ sudo pacman -Scc               # ⚠️ 清空全部缓存（之后无法降级）
$ sudo paccache -r               # 保留最近 3 个版本（pacman-contrib）

# 场景：降级（用缓存里的旧版本）⭐

$ sudo pacman -U /var/cache/pacman/pkg/nginx-1.22.0-1-x86_64.pkg.tar.zst
# ⚠️ 降级单个包可能造成部分升级！要一并处理依赖

# 场景：安装本地包（AUR 构建产物）
$ sudo pacman -U ./package-1.0.0-1-x86_64.pkg.tar.zst
$ sudo pacman -U --noconfirm ./package.tar.zst

# 场景：只下载不安装（离线仓库）⭐
$ sudo pacman -Sw nginx
$ sudo pacman -Syw --cachedir /tmp/pkgs nginx

# 场景：dry run（看会做什么）⭐⭐
$ sudo pacman -S --print nginx
$ sudo pacman -Syu --print | head -20
$ sudo pacman -S --print-format '%n %v' nginx

# 场景：跳过一次升级（临时）⭐
$ sudo pacman -Syu --ignore=linux,linux-headers
$ # 持久化：在 /etc/pacman.conf 里写 IgnorePkg = linux linux-headers

# 场景：检查损坏的包数据库或依赖
$ sudo pacman -Dk
$ sudo pacman -T                          # 检查未满足的依赖
$ sudo pacman -Qkk | grep -v '0 altered'

# 场景：🔐 审计外来包（AUR 风险）⭐
$ pacman -Qm
$ for p in $(pacman -Qmq); do
>   echo "== $p"
>   pacman -Qi "$p" | grep -E 'Packager|Install Date|Description'
> done
```

#### 输出解读
`pacman -Rns` 的参数含义：

| 字母 | 含义 |
|------|------|
| `-R` | 移除 |
| `-s` | 递归（含不再被需要的依赖） ⭐ |
| `-n` | 不保留配置文件（`nosave`） ⭐ |
| `-c` | 级联（含依赖它的包） ⚠️ |
| `-d` | 跳过依赖检查 ⚠️ |

`pacman -Qkk` 的输出：

| 输出 | 含义 |
|------|------|
| `0 missing files` | 无文件丢失 |
| `0 altered files` | 无文件被改动 ⭐ |
| `N altered files` | **有文件被改动，需追查** 🔐 |
| `N missing files` | 文件丢失（可能被删） |

#### ⚠️ 危险操作
| 命令 | 后果 |
|------|------|
| `pacman -Sy && pacman -S pkg` | **部分升级**，可能导致库与二进制不匹配 → 系统损坏 ⚠️⚠️ |
| `pacman -Scc` | 清空全部缓存，**失去降级能力** ⚠️ |
| `pacman -Rdd pkg` | 跳过依赖检查卸载，可能导致其他程序崩溃 ⚠️ |
| `pacman -Syu --overwrite '*'` | 无差别覆盖文件，可能破坏配置 ⚠️ |

#### 常见坑
- ⚠️⚠️ **Arch 不支持部分升级**。`pacman -Sy`（只更新索引）+ 单独 `pacman -S pkg` 会让库与二进制版本不匹配，**可能导致系统无法启动** ⭐⭐。**永远 `-Syu`**。
- ⚠️ **`-Syu` 输出很长时先看「会移除哪些包」**（`-Rns` 级的删除）。Arch 升级偶尔会需要删包，要人工判断。
- ⚠️ **升级前读 Arch 官网的 News**（https://archlinux.org/news/），重大变更会提前公告（需手动干预）⭐。
- ⚠️ **`pacman -Qkk` 检测的是 `/var/lib/pacman/local/` 里的 mtree 数据库**。攻击者若同时改数据库可绕过 ⭐。
- ⚠️ **`-Qo` 对符号链接不解析**（写包记录里的原始路径）。
- **`pacman -Sy` 并非无用**：它用于「只更新索引后立刻 `-Su`」，或在同一个事务里 `-Syu`。
- **`pacman` 的缓存默认不清理**（占几十 GB 很常见），要配 `paccache.timer` 定期清 ⭐。
- **`/etc/pacman.conf` 的 `IgnorePkg` 会持久忽略**，排查「包升不上去」时先看它 ⭐。
- **`pacman` 的锁** `/var/lib/pacman/db.lck`：进程崩溃后可能残留，确认无进程后再删。
- **`-Qm`（外来包）是 AUR 风险审计的起点**，这些包不受官方仓库审核 ⭐。

#### 相关命令
`yay` · `paru` · `makepkg` · `paccache` · `checkupdates` · `reflector`

### makepkg — 从 PKGBUILD 构建包

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：Arch 专有（`pacman` 包）

```bash
makepkg [选项]
```

| 选项 | 含义 |
|------|------|
| `-s` / `--syncdeps` | 自动安装依赖 ⭐ |
| `-i` / `--install` | 构建后安装 ⭐ |
| `-r` / `--rmdeps` | 构建后删除依赖 ⭐ |
| `-c` / `--clean` | 构建后清理 `src/` 与 `pkg/` |
| `-f` / `--force` | 强制重建 |
| `--noconfirm` | 不询问 ⭐ |
| `--needed` | 已最新则跳过 |
| `--noextract` | 不解包源码 |
| `-p PKGBUILD` | 指定 PKGBUILD 路径 |
| `-o` / `--nobuild` | 只下载并解包源码（不构建） ⭐ |
| `-e` | 不重新解包源码 |
| `--skipchecksums` | ⚠️ 跳过校验和！ |
| `--skipinteg` | ⚠️ 跳过全部完整性校验 |
| `--holdver` | 保留版本号 |
| `--packagelist` | 只列出会生成哪些包 |
| `-V` | 版本 |

```bash
# 场景：🧪 手工构建 AUR 包（先审查 PKGBUILD！）⭐⭐
$ git clone https://aur.archlinux.org/example.git
$ cd example
$ cat PKGBUILD
# ⭐⭐ 必须审查：
#   source= 里有没有可疑 URL（非官方域名）
#   prepare()/build()/package() 里有没有 curl|bash / 反连 / 改系统文件
#   sha256sums 是否齐全（不足说明上游可能被篡改）
$ less PKGBUILD
$ makepkg -si --noconfirm

# 场景：只下载源码并解包（不构建，便于深度审查）⭐⭐
$ makepkg -o
$ ls src/
$ # 审查源码后再构建
$ makepkg -e

# 场景：构建但不安装（产物留在当前目录）⭐
$ makepkg -s
$ ls *.pkg.tar.zst
$ sudo pacman -U example-1.0.0-1-x86_64.pkg.tar.zst

# 场景：构建后清理构建目录
$ makepkg -sric

# 场景：只列出会生成什么包
$ makepkg --packagelist

# 场景：🔐 校验 AUR 包的提交历史（判断是否被劫持）⭐
$ git log --oneline -10
$ git log -p -1                                  # 看最近一次改了什么
$ git log --format='%H %an %ae %ad %s' -5
$ git diff HEAD~1 HEAD -- PKGBUILD

# 场景：🧪 自己写一个最简 PKGBUILD ⭐
$ cat /tmp/mypkg/PKGBUILD
pkgname=hello-arch
pkgver=1.0.0
pkgrel=1
pkgdesc="A minimal test package"
arch=('any')
url="https://example.com"
license=('MIT')
depends=('glibc')
source=("$pkgname-$pkgver.tar.gz::https://example.com/hello-$pkgver.tar.gz")
sha256sums=('SKIP')

package() {
  install -Dm755 "$srcdir/hello" "$pkgdir/usr/bin/hello"
  install -Dm644 "$srcdir/README.md" "$pkgdir/usr/share/doc/$pkgname/README.md"
}

$ cd /tmp/mypkg && makepkg -f
$ ls *.pkg.tar.zst

# 场景：检查 PKGBUILD 合法性（静态检查）⭐
$ namcap PKGBUILD
$ namcap example-1.0.0-1-x86_64.pkg.tar.zst
$ # namcap 会提示缺失依赖、不规范的路径等

# 场景：查看包内容（构建后审查）⭐
$ bsdtar -tf example-1.0.0-1-x86_64.pkg.tar.zst | head
$ bsdtar -xOf example-1.0.0-1-x86_64.pkg.tar.zst .PKGINFO
$ bsdtar -xOf example-1.0.0-1-x86_64.pkg.tar.zst .INSTALL   # 🔐 看安装脚本
```

#### 输出解读
`PKGBUILD` 的关键字段：

| 字段 | 含义 |
|------|------|
| `pkgname` / `pkgver` / `pkgrel` | 包名、版本、发行号 |
| `depends` / `makedepends` | 运行 / 构建依赖 |
| `source` | 源码来源（URL 或本地文件） 🔐 |
| `sha256sums` / `b2sums` | 校验和（`SKIP` 表示不校验） 🔐 |
| `md5sums` | 已废弃（不安全） |
| `build()` / `package()` | 构建 / 打包函数（**这是执行任意代码的地方**） 🔐⚠️ |

`.PKGINFO`（包元数据）与 `.INSTALL`（安装脚本）是两个特殊的点号开头文件。

#### 🔐 AUR 安全审计清单
```
1. source= 里的 URL 域名是否可信？（GitHub 官方仓库 vs 陌生域名）
2. 校验和是否齐全？（缺 sha256sums 说明可被中间人替换）
3. prepare()/build()/package() 里是否有：
   - curl ... | bash
   - wget ... | sh
   - nc/socat 反连
   - 修改 /etc/passwd /etc/sudoers /etc/cron*
   - systemctl enable 未知服务
   - 访问浏览器 profile（2025 年曾出现此类 AUR 恶意包）
4. git log 最近的提交者是否是熟人？（AUR 账号可能被劫持）
5. 上游源码仓库是否在你预期的组织下？
```

```bash
# 快速审计脚本 ⭐
$ grep -nE 'curl.*\|.*(bash|sh)|wget.*\|.*(bash|sh)|nc -e|socat.*EXEC|/etc/(passwd|sudoers|cron)|\.ssh/|\.config/(google-chrome|chromium|firefox)' PKGBUILD
$ grep -n 'sha256sums' PKGBUILD
```

#### 常见坑
- ⚠️⚠️ **`makepkg` 以你的普通用户身份执行 `PKGBUILD` 里的代码**，且 `package()` 里的 `$pkgdir` 会被 `pacman -U` 以 root 安装。**AUR 包可能完全控制你的账号** ⭐。
- ⚠️ **不要用 root 运行 `makepkg`**（它会拒绝），但也**不要以为普通用户就安全**（能读你的 SSH 私钥、浏览器数据、代码仓库）⭐。
- ⚠️ **`--skipchecksums` / `--skipinteg` 会让你跳过完整性校验**，等于接受任意内容 ⚠️。
- ⚠️ **`makepkg` 生成的包不做签名**，除非配了 `makepkg.conf` 的 `GPGKEY`。用 `pacman -U` 安装时 `SigLevel` 会放行本地包。
- **`makepkg` 需要 `base-devel` 组**（`gcc`、`make`、`fakeroot` 等）。
- **构建目录是当前目录**（`src/`、`pkg/`），`-c` 会清理它们。
- **`sha256sums=('SKIP')` 在 VCS 包（`-git` 后缀）里是正常的**（源码随时变），但它意味着构建结果不可复现 ⭐。
- **`namcap` 是静态检查工具**，能发现依赖缺失与路径问题，但**不检查恶意代码** 🔐。

#### 相关命令
`pacman` · `yay` · `paru` · `namcap` · `bsdtar` · `devtools`

### yay — Arch AUR 助手

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：第三方工具（非官方仓库）

```bash
yay [选项] [包...]
```

| 选项 | 含义 |
|------|------|
| `-S` | 安装（含 AUR） ⭐ |
| `-Ss` | 搜索（AUR + 仓库） ⭐ |
| `-Si` | 信息 |
| `-Rns` | 卸载（同 pacman） |
| `-Syu` | 整体升级（含 AUR 包） ⭐ |
| `-Y` | yay 自身操作 |
| `-Yc` | 清理未使用的 AUR 依赖 ⭐ |
| `-Yclean` | 清理构建缓存 ⭐ |
| `-G 包` | **只下载 PKGBUILD 到当前目录（审查用）** ⭐⭐ |
| `-V` | 版本 |
| `--noconfirm` | 自动确认 ⭐ |
| `--needed` | 已最新则跳过 |
| `--devel` | 检查 `-git` 包的上游更新 ⭐ |
| `--answerclean` / `--answerdiff` | 自动回答清理/差异确认 ⭐ |
| `--editmenu` | 编辑 PKGBUILD 与 .install 再构建 ⭐ |

```bash
# 场景：搜索与安装 AUR 包 ⭐
$ yay -Ss google-chrome
$ yay -S google-chrome
$ yay -S --noconfirm --needed brave-bin

# 场景：🔐🔐 只下载 PKGBUILD 审查（不构建）⭐⭐
$ cd /tmp && yay -G suspicious-package
$ ls suspicious-package/
PKGBUILD
$ less suspicious-package/PKGBUILD
$ grep -nE 'curl.*\|.*(bash|sh)|nc -e' suspicious-package/PKGBUILD
$ # 审查通过后再构建
$ cd suspicious-package && makepkg -si

# 场景：🔐 强制在构建前查看 PKGBUILD 与 diff ⭐
$ yay -S --editmenu package
# 或在 /etc/yay.conf 里设：
$ grep -E 'EditMenu|DiffMenu|CleanMenu' /etc/yay.conf 2>/dev/null
# ⭐ 建议：EditMenuOnDiff 保持开启，DiffMenu 设为 Always，CleanMenu 设为 All

# 场景：整体升级（仓库 + AUR）⭐
$ yay -Syu
$ yay -Syu --devel                # 也检查 -git 包的更新

# 场景：清理 AUR 构建残留 ⭐
$ yay -Yc                         # 清理不需要的依赖
$ yay -Yclean                     # 清理构建缓存（可能很大）
$ du -sh ~/.cache/yay

# 场景：查看 AUR 包的投票数与维护状态（判断可信度）⭐
$ yay -Si package
# 输出含 Votes、Popularity、Maintainer、OutOfDate
# ⭐ Maintainer 为空 = 无人维护（风险高）；OutOfDate 非空 = 上游已失效

# 场景：只查 AUR（不查官方仓库）
$ yay -Ss --aur package
$ yay -Ss --repo package

# 场景：查看哪些已装包来自 AUR ⭐
$ pacman -Qm | wc -l
$ yay -Qm

# 场景：降级 AUR 包
$ yay -S package --noconfirm
$ ls ~/.cache/yay/package/
$ sudo pacman -U ~/.cache/yay/package/package-1.0.0-1-x86_64.pkg.tar.zst
```

#### 输出解读
`yay -Si` 的 AUR 信息会包含（与 `pacman -Si` 不同）：

| 字段 | 含义 |
|------|------|
| `Votes` | 社区投票数（**越高越可信**） ⭐ |
| `Popularity` | 流行度 |
| `Maintainer` | 维护者（**为空 = 无人维护，风险高**） ⭐ |
| `OutOfDate` | 是否被标记为过时 |
| `First Submitted` / `Last Updated` | 首次提交 / 最后更新 ⭐ |
| `URL` / `AUR URL` | 上游与 AUR 页面 |
| `Keywords` | 关键词 |

#### 🔐 AUR 的风险与防护
| 风险 | 防护 |
|------|------|
| PKGBUILD 里有恶意代码 | **构建前审查 `PKGBUILD` 与 `.install`** ⭐⭐ |
| 校验和缺失 | 检查 `sha256sums` 是否完整 |
| 上游仓库被劫持 | 检查 `source=` 的域名与组织 |
| AUR 账号被盗后投毒 | 看提交历史与维护者变化 |
| 无人维护的包 | 优先选 `Votes` 高的（2025 年曾出现恶意 AUR 包窃取浏览器数据） |

**配置建议**（`/etc/yay.conf` 或 `~/.config/yay/config.json`）：
```
DiffMenu = Always        # ⭐ 总是显示 PKGBUILD 差异
EditMenu = Always        # ⭐ 总是允许编辑 PKGBUILD
CleanMenu = All          # ⭐ 总是清理构建文件
BatchInstall = false
```

#### 常见坑
- ⚠️⚠️ **`yay -S` 会在你不知情的情况下执行 AUR 的 PKGBUILD**，代码以你的用户身份运行，安装时以 root 执行脚本 ⭐。
- ⚠️ **`--noconfirm` 会跳过所有确认，包括 PKGBUILD 差异确认**。批量安装时很方便，但**会跳过审查机会** ⭐。
- ⚠️ **`--editmenu` 只在你显式指定时生效**，默认行为取决于配置。**生产/长期维护的机器应把 `DiffMenu` 设为 `Always`**。
- ⚠️ **`yay` 不是官方工具**，它自身也是 AUR 包（鸡生蛋问题：第一次安装要手工构建）⭐。
- **`yay -Yclean` 会清掉构建缓存**，之后 AUR 包无法从缓存降级。
- **`yay -Syu` 与 `pacman -Syu` 的差异**：前者会额外检查 AUR 包的更新，可能引入 AUR 侧的破坏性变更 ⭐。
- **`--devel` 会检查 `-git`/`-svn` 类包的上游**，可能导致频繁重编译（Rolling AUR 包的不稳定性）⭐。
- **`paru` 是 yay 的流行替代**（Rust 实现，行为更接近 pacman），选项类似。

`paru` · `pacman` · `makepkg` · `namcap`

#### 🔐 Flatpak 的安全模型
- 应用**默认在沙箱里**（bubblewrap + user namespace + seccomp）。
- 沙箱边界由**权限声明**决定。`filesystems=host` 或 `devices=all` 会大幅削弱隔离 ⭐。
- **用户可以用 `override` 收紧权限**，应用无法绕过（除非有 `--nofilesystem` 等例外）。
- `--unshare=network` 会给应用一个**独立的网络命名空间**（完全无网络）⭐。
- `flatpak info --show-permissions` 应作为安装第三方应用前的必查项 ⭐。

#### 常见坑
- ⚠️ **Flatpak 应用默认能访问 X11 socket**，而 X11 本身不安全（可截屏、模拟按键）。要真正隔离需要 Wayland ⭐。
- ⚠️ **`filesystems=host` 或 `home` 让沙箱形同虚设**（可读写你的全部文件）。安装前检查 ⭐。
- ⚠️ **`--user` 与系统级安装是独立的**，同一个应用可能装两份，`flatpak list` 都会显示。
- ⚠️ **`flatpak uninstall` 默认保留应用数据**（配置、缓存），要 `--delete-data` 才删 ⭐。
- **运行时（runtime）会占大量空间**（`--unused` 清理常能省几 GB）⭐。
- **Flatpak 应用更新独立于系统**，不受发行版影响（这也是它的卖点）。
- **`flatpak override --user` 只影响当前用户**；系统级 override 需要 root。
- **`flatpak enter` 需要 root 或 `CAP_SYS_ADMIN`**（要进入沙箱命名空间）⭐。
- **Flatpak 应用可能自带旧的运行时**（安全更新滞后于系统库），这是它的一个劣势。

- ⚠️ **`--classic` 让沙箱失效**。安装时要用 `--classic` 的应用（VS Code、Docker）**没有 snap 的安全优势** ⭐。

- **snapd 在非 Ubuntu 发行版上需要额外安装**（Arch 等可能需要 `snapd` + AppArmor 配置）。
- **snap 的启动比原生应用慢**（squashfs 挂载 + 沙箱初始化），这是它的主要缺点。
- **`snap revert` 依赖本地保留的旧 revision**，超出保留数就无法回滚 ⭐。
- **`snap connections` 的 `Notes` 列**：`-` 表示默认连接状态，`manual` 表示手动连接/断开。
- **snap 的应用数据在 `~/snap/<name>/`**，卸载时要手动清理（`snap remove --purge` 会删）。

#### ⚠️ 为什么不要 `sudo pip install`
| 风险 | 说明 |
|------|------|
| 覆盖系统包 | 发行版管理的 Python 包（如 `apt` 的依赖）被替换 ⭐ |
| 破坏包管理器 | `apt`/`dnf` 自己用 Python，升级时崩溃 ⭐ |
| 文件归属混乱 | 文件不属于任何系统包，`dpkg -S` 查不到 🔐 |
| 版本冲突 | 两个应用需要不同版本，无法共存 |
| PEP 668 保护 | 现代发行版会直接拒绝（应遵守，不要绕过） ⭐ |

**替代方案**：`venv`（项目隔离）、`pipx`（CLI 工具）、`conda`/`uv`（环境管理）、发行版包（`python3-xxx`）。

#### 常见坑
- ⚠️ **`externally-managed-environment` 错误是保护机制**，不要用 `--break-system-packages` 绕过。用 venv 或 pipx ⭐。
- ⚠️ **`pip install --user` 会装到 `~/.local/lib/python3.x/site-packages`**，与 venv 混用会混乱（venv 里的 pip 仍可能看到用户的包）。要 `python3 -m venv --system-site-packages` 控制。
- ⚠️ **`pip install -r req.txt` 不锁定传递依赖**（除非文件里写死了）。生产要用 `pip-compile --generate-hashes` 或 `poetry.lock` ⭐。
- ⚠️ **PyPI 上有抢注包（typosquatting）**：`reqeusts`、`urlib3`、`crypto`（正确是 `pycryptodome`）等 🔐。安装前核对拼写。
- ⚠️ **`setup.py` / `pyproject.toml` 在安装时会执行代码**（构建后端），`pip install` 一个恶意包等于执行任意代码 🔐。
- **`pip freeze` 包含所有已安装包**（含你不直接依赖的），不如 `pip-compile` 的结果干净。
- **虚拟环境的 `python`/`pip` 要与 `python3 -m pip` 一致**，避免用错解释器（`which pip` 检查）⭐。
- **`uv` 是 pip 的现代替代**（Rust 实现，快 10–100 倍），值得关注 ⭐。
- **`pip download --platform` 交叉下载需要指定 `--only-binary=:all:`**，否则会尝试构建。

- **`package-lock.json` 必须提交到版本库**（否则 CI 无法复现）⭐。
- **`.npmrc` 里的 token 不要提交到仓库**（会被 `npm install` 泄露）🔐。

| 优点 | 说明 |

#### 常见坑

- **`cargo` 需要 `rustup` 或系统包管理的 rust 工具链**。
- **`Cargo.lock` 对二进制项目应提交**，对库项目过去不建议（现在也建议提交）⭐。
- **`cargo vendor` 后要检查 `.cargo/config.toml`** 的替换配置是否正确。
- **`cargo install` 的二进制名可能与 crate 名不同**（要 `cargo install --list` 确认）。
- **私有仓库需要配 `~/.cargo/config.toml` 的 `[registries]`**。

#### 相关命令
`rustup` · `rustc` · `cargo-audit` · `cargo-deny` · `cargo-outdated`

#### 🔐 Go 的供应链安全（相对最好）
| 机制 | 作用 |
|------|------|
| **`go.sum`** | 依赖的密码学哈希，防篡改 ⭐⭐ |

#### 常见坑
- ⚠️ **`go get` 在 Go 1.17+ 不再安装二进制**，装二进制要用 `go install` ⭐。
- ⚠️ **`go install 路径@版本` 的 `@版本` 现在几乎必需**（否则会报错或行为不定）⭐。
- ⚠️ **`go install` 的产物在 `$GOPATH/bin`（默认 `~/go/bin`）**，**默认不在 PATH 里**，要自己加 ⭐。
- ⚠️ **`GOFLAGS=-mod=mod` 会让 `go` 忽略 `-mod=readonly` 保护并自动改 go.mod**，可能引入意外依赖 ⭐。
- ⚠️ **`GONOSUMDB` / `GONOSUMCHECK` / `GOFLAGS=-insecure` 会削弱校验**，生产环境不要设 🔐。
- **`go mod tidy` 会删除「未使用」的依赖**（按静态分析），可能在运行时才发现需要（反射、插件） ⭐。
- **`go.sum` 必须提交到版本库**（否则 CI 无法校验依赖）⭐。
- **`go build` 产出的二进制默认包含调试信息**（很大），用 `-ldflags '-s -w'` 减体积 ⭐。
- **`vendor/` 目录会显著增大仓库**，但对离线构建与确定性很有价值 ⭐。

### make — 构建工具

**常用度**：★★★★★ ｜ **所属**：包管理（构建） ｜ **POSIX/GNU 差异**：GNU make 有大量扩展（`ifeq`、`$(shell ...)`、`.PHONY` 语义等）

> 🔐 **`make` 会执行 Makefile 里的任意 shell 命令。从源码安装前必须读 Makefile。**

```bash
make [选项] [目标...]
```

| 选项 | 含义 |
|------|------|
| （无参） | 执行第一个目标（通常是 `all`） |
| `-f 文件` | 指定 Makefile ⭐ |
| `-j N` | **并行 N 个任务** ⭐⭐ |
| `-j` | 不限制并行（**可能 OOM**） ⚠️ |
| `-k` | 出错后继续（尽量多做事） |
| `-n` | ⭐⭐ **只打印会执行的命令，不执行（dry run）** |
| `-s` | 不打印命令（安静） |
| `-B` | 无条件重建所有目标 ⭐ |
| `-C 目录` | 先切目录再执行 ⭐ |
| `-e` | 环境变量覆盖 Makefile 里的变量 |
| `-i` | 忽略所有错误 |
| `-p` | 打印数据库（变量与规则） ⭐ |
| `-d` | 调试输出 ⭐ |
| `--dry-run` | 同 `-n` |
| `-t` | 只 touch 目标不执行 ⚠️ |
| `VAR=值` | 覆盖 Makefile 里的变量 ⭐ |
| `--version` / `-v` | 版本 |

```bash
# 场景：⭐⭐ `make -n` 是在跑 Makefile 前最重要的一步
$ make -n install
install -Dm755 build/app /usr/local/bin/app
install -Dm644 config/default.yml /etc/app/default.yml
rm -rf /var/lib/app/*
# ⭐ 看到「rm -rf」就知道要当心

# 场景：标准三步（Autotools）⭐⭐
$ ./configure --prefix=/usr/local
$ make -j"$(nproc)"
$ sudo make install

# 场景：🧪 先装到临时前缀（便于卸载）⭐⭐
$ ./configure --prefix=/opt/myapp-1.0.0
$ make -j"$(nproc)"
$ sudo make install
$ # 卸载 = sudo rm -rf /opt/myapp-1.0.0

# 场景：查看有哪些目标 ⭐
$ make help                        # 很多项目会实现 help
$ grep -E '^[a-zA-Z0-9_-]+:' Makefile | head -20
$ make -p | grep -E '^[a-zA-Z0-9_-]+:' | head        # 更全（含隐含规则）

# 场景：并行构建（不要用无参数的 -j）⭐⭐
$ make -j"$(nproc)"
$ make -j"$(( $(nproc) + 1 ))"
$ make -j"$(( $(nproc) / 2 ))"        # 内存小时减半

# 场景：覆盖变量（不改 Makefile）⭐
$ make PREFIX=/usr DESTDIR=/tmp/stage install
$ make CC=clang CFLAGS='-O2 -g' -j8
$ make V=1                             # 很多项目用它显示详细命令 ⭐

# 场景：分段安装到 staging 目录（打包用）⭐⭐
$ make DESTDIR=/tmp/stage install
$ find /tmp/stage -type f | head
$ # ⭐ 之后可以用 fpm/checkinstall 打成本地包

# 场景：调试 Makefile ⭐
$ make -n -d 2>&1 | head -40
$ make -p 2>/dev/null | grep -A5 '^CFLAGS'
$ make --warn-undefined-variables
$ make -n 2>&1 | grep -E 'rm -rf|curl|wget|chmod 777|/etc/(passwd|sudoers)'

# 场景：🔐 安全审查 Makefile（装源码前必做）⭐⭐
$ grep -nE 'curl.*\|.*(bash|sh)|wget.*\|.*(bash|sh)|nc -e|/etc/(passwd|sudoers|cron)|base64 -d|eval' Makefile
$ grep -nE '^install:|^[[:space:]]+.*rm -rf' Makefile
$ less Makefile
$ # 尤其看 install 目标与 post-install 之类的自定义目标

# 场景：只构建不安装（先看产物）⭐
$ make
$ ls -la build/ 2>/dev/null || ls -la | head

# 场景：CMake 项目里的 make（通过生成的 Makefile）⭐
$ cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DCMAKE_INSTALL_PREFIX=/usr/local
$ cmake --build build -j"$(nproc)"          # 或 cmake --build build --parallel 8
$ sudo cmake --install build
$ # 现代写法（不依赖 make）：
$ cmake -S . -B build -G Ninja && ninja -C build

# 场景：Meson 项目 ⭐
$ meson setup build --prefix=/usr/local
$ ninja -C build
$ sudo ninja -C build install

# 场景：清理
$ make clean                        # 删中间产物
$ make distclean                    # 同时也删 configure 产物
$ make uninstall                    # ⚠️ 不是所有项目都支持

# 场景：🧪 时间统计（看哪一步慢）
$ time make -j"$(nproc)"
$ # 更细的：每步耗时
$ make -j1 2>&1 | ts '[%H:%M:%S]'    # 需 moreutils 的 ts
```

#### 输出解读
`make` 的执行逻辑：
1. 找到默认目标（Makefile 里第一个非 `.` 开头的目标）
2. 对每个目标检查**依赖是否比目标新**（按 mtime）
3. 需要更新则执行该目标的命令

常见目标名（约定）：

| 目标 | 含义 |
|------|------|
| `all` | 构建全部（默认） ⭐ |
| `install` | 安装 ⭐ |
| `uninstall` | 卸载（**很多项目没有**） |
| `clean` | 清理中间产物 ⭐ |
| `distclean` / `mrproper` | 清理全部生成物 |
| `test` / `check` | 运行测试 ⭐ |
| `dist` / `package` | 制作发布包 |
| `help` | 显示帮助（非标准，但常见） |

常用变量：

| 变量 | 含义 |
|------|------|
| `PREFIX` | 安装前缀（`/usr/local`） ⭐ |
| `DESTDIR` | **临时安装根**（打包用，不改 PREFIX） ⭐⭐ |
| `CC` / `CXX` | 编译器 |
| `CFLAGS` / `CXXFLAGS` | 编译选项 |
| `LDFLAGS` | 链接选项 |
| `V` | 详细模式（很多项目支持） ⭐ |
| `VERBOSE` | 同 `V`（视项目） |

⚠️ **`DESTDIR` 与 `PREFIX` 的区别是打包的关键**：
```
make PREFIX=/usr DESTDIR=/tmp/stage install
→ 文件实际装到 /tmp/stage/usr/...
→ 包管理器安装时会剥离 DESTDIR 前缀
```

#### 🔐 安全要点
| 风险 | 说明 |
|------|------|
| **Makefile 是任意代码** | `make` 直接执行其中的 shell 命令 ⚠️⭐ |
| **`install` 目标以 sudo 执行** | 若下载的源码被篡改，可直接 root |
| **`curl \| bash` 形式的 bootstrap** | 项目常提供但**跳过验证** ⚠️ |
| **`$(shell ...)` 在解析时执行** | 即使只想用 `-n` 查看也可能执行部分代码 ⚠️ |

```bash
# 🔐 安全流程
$ # 1. 校验下载包的哈希/签名
$ sha256sum -c sha256sums.txt 2>/dev/null || sha256sum package.tar.gz
$ gpg --verify package.tar.gz.asc package.tar.gz
$ # 2. 读 Makefile 的 install 目标与自定义目标
$ grep -nE '^install:|^[a-zA-Z_-]+:' Makefile | head -20
$ less Makefile
$ # 3. 用 -n 预演
$ make -n install | less
$ # 4. 装到临时前缀（不要直接 /usr）
$ ./configure --prefix=/opt/app-1.0.0 && make -j"$(nproc)" && sudo make install
```

#### 常见坑
- ⚠️ **`make -j` 不带参数会无限并行**（直到资源耗尽），**可能 OOM 或卡死** ⭐。
- ⚠️ **`make install` 通常需要 root，且会写到 `/usr/local`**（污染不受包管理器管理）⭐。**优先用 `DESTDIR` + `fpm`/`checkinstall` 打包**。
- ⚠️ **`make` 的依赖判断基于 mtime**，系统时钟错乱或 `cp -p` 会破坏增量构建（用 `-B` 强制重建）⭐。
- ⚠️ **`make -t`（touch）会更新目标文件的时间戳但不执行命令**，可能让后续构建跳过必要的步骤。极少用。
- **`make -n` 并非完全安全**：`$(shell ...)` 与 `$(wildcard ...)` 在解析阶段就会执行 ⭐。
- **`-e` 会让环境变量覆盖 Makefile 变量**，行为可能与预期相反。
- **`make uninstall` 不是标准目标**，很多项目没实现，要手工删（记录 `make install` 的输出来清理）⭐。
- **BSD make 与 GNU make 语法差异很大**（BSD 的 bmake 用 `.include`，GNU 用 `include`）。跨平台项目常要求 gmake ⭐。
- **`make` 在长命令里用 Tab 缩进（不是空格）**，修改 Makefile 时极易出错（报 `missing separator`）⭐。

#### 相关命令
`cmake` · `meson` · `ninja` · `autoconf` · `pkg-config` · `checkinstall` · `fpm`

### ldconfig — 共享库缓存管理

**常用度**：★★★★☆ ｜ **所属**：包管理（运行时） ｜ **POSIX/GNU 差异**：Linux 特有（glibc）

> 🔐 **`ldconfig` 与 `/etc/ld.so.conf` 是 Linux 动态库劫持（提权）的经典入口。**

```bash
ldconfig [选项] [目录...]
```

| 选项 | 含义 |
|------|------|
| （无参） | 更新缓存（读 `/etc/ld.so.conf` 与默认路径） ⭐ |
| `-p` | **打印当前缓存内容（不修改）** ⭐⭐ |
| `-n 目录` | 只处理该目录（不读配置文件） ⭐ |
| `-v` | 详细（显示创建的链接） ⭐ |
| `-N` | 不重建符号链接 |
| `-X` | 不创建符号链接 |
| `-l` | 进入库模式（内部用） |
| `-r 根目录` | chroot |
| `-f 配置` | 用指定配置文件 |
| `-C 缓存` | 用指定缓存文件 |

**相关文件**：

| 路径 | 用途 |
|------|------|
| `/etc/ld.so.conf` | 库搜索路径配置 ⭐ |
| `/etc/ld.so.conf.d/*.conf` | 分片段配置（推荐） ⭐ |
| `/etc/ld.so.cache` | **生成的缓存（二进制，ld.so 实际读的）** ⭐ |
| `/lib`、`/usr/lib` | 默认搜索路径 |
| `/etc/ld.so.preload` | **强制预加载的库列表** 🔐⚠️ |

```bash
# 场景：打印缓存内容（看某库在不在缓存里）⭐⭐
$ ldconfig -p | grep libssl
	libssl.so.3 (libc6,x86-64) => /usr/lib/libssl.so.3

# 场景：🔐🔐 审核库搜索路径（提权排查）⭐⭐
$ cat /etc/ld.so.conf

# 场景：🧪 用 LD_PRELOAD 观察库劫持（授权环境）⭐
$ cat > /tmp/hook.c <<'EOF'
#define _GNU_SOURCE
#include <stdio.h>
#include <dlfcn.h>
ssize_t write(int fd, const void *buf, size_t n) {
    static ssize_t (*real)(int, const void *, size_t) = NULL;
    if (!real) real = dlsym(RTLD_NEXT, "write");
    fprintf(stderr, "[hook] write(%d, %zu bytes)\n", fd, n);
    return real(fd, buf, n);
}
EOF
$ gcc -shared -fPIC -o /tmp/hook.so /tmp/hook.c -ldl
$ LD_PRELOAD=/tmp/hook.so ls /tmp >/dev/null
[hook] write(1, 34 bytes)

$ # ⚠️ 若目标是 SUID 程序，hook 会被忽略：
$ LD_PRELOAD=/tmp/hook.so /usr/bin/passwd --help >/dev/null   # 无 hook 输出
$ rm -f /tmp/hook.so /tmp/hook.c

$ ldd --version
$ /lib/x86_64-linux-gnu/libc.so.6 | head -1
$ # 用 LD_LIBRARY_PATH 指向新版 glibc 会破坏系统（glibc 不能这样替换） ⚠️⚠️
```

#### 输出解读
`ldconfig -p` 的输出：

```
	libssl.so.3 (libc6,x86-64) => /usr/lib/libssl.so.3
	│           │              └─ 实际文件路径
	│           └─ ABI 标签（架构与 libc 类型）
	└─ 库的 SONAME（版本化的名字） ⭐
```

**库文件名规则（SONAME 机制）**：

| 文件 | 用途 |
|------|------|
| `libfoo.so.1.2.3` | **实际的库文件**（含真实版本号） |
| `libfoo.so.1` | **SONAME 链接**（运行时用，`.so.主版本`） ⭐ |
| `libfoo.so` | **开发链接**（编译时用，需 `-dev`/`-devel` 包） ⭐ |

⚠️ 运行时只找 `.so.主版本`，编译时只找 `.so`。缺 `-dev` 包时编译报 `cannot find -lfoo`；缺运行库时报 `error while loading shared libraries` ⭐。

#### 🔐 动态库劫持：Linux 提权经典路径
| 手法 | 条件 | 防护 |
|------|------|------|
| **`LD_PRELOAD`** | 目标程序的启动环境可被控制 | SUID 程序会忽略（除 `ld.so.preload`） ⭐ |
| **`LD_LIBRARY_PATH`** | 同上 | 同上 |
| **`/etc/ld.so.preload`** | **SUID 程序也会加载！** 🔐⚠️⚠️ | 监控该文件的存在与内容 ⭐⭐ |
| **`ld.so.conf.d/` 里可写目录** | 目录权限配置错误 | 目录必须 root 拥有且非全局可写 |
| **SUID 程序调用外部命令且 PATH 可劫持** | PATH 未清理 | `secure_path`、绝对路径调用 |

```bash
# 🔐 排查检查清单
$ ls -l /etc/ld.so.preload 2>/dev/null || echo "OK: 不存在"
$ cat /etc/ld.so.conf.d/*.conf | grep -v '^#'
$ for d in /lib /usr/lib /usr/local/lib; do ls -ld "$d"; done
$ find / -xdev -name '*.so*' -newer /etc/hostname -ls 2>/dev/null | head    # 最近新增的库 ⭐
$ find / -xdev -perm -0002 -type d \( -name 'lib*' -o -name '*lib' \) 2>/dev/null
```

#### 常见坑
- ⚠️ **`ldconfig` 需要 root**（要写 `/etc/ld.so.cache`）。
- ⚠️ **装库后必须 `ldconfig`**，否则运行时找不到（`error while loading shared libraries`）⭐。包管理器会自动调用，手工 `cp` 则要自己跑。
- ⚠️ **`LD_LIBRARY_PATH` 优先级高于 `ld.so.cache`**（除 SUID 程序）——这是提权风险点 ⭐。
- ⚠️ **`/etc/ld.so.preload` 的文件格式是「每行一个库路径」**，写错会导致**所有程序无法启动**（包括 `ls`、`bash`）。修不了就可能要救援模式 ⭐⚠️。
- **`ldconfig` 只处理 `.so` 与 `.so.N` 形式的文件**，其他名字会被忽略。
- **`ldconfig -p` 只读缓存，不反映当前目录状态**（新装的库刷缓存后才出现）⭐。
- **`ldd` 的执行是「运行加载器」，对不信任的二进制有代码执行风险**（老 `ldd` 的经典漏洞）🔐：
  ```bash
  # 更安全的替代（不执行目标）
  $ objdump -p /path/to/binary | grep NEEDED
  $ readelf -d /path/to/binary | grep NEEDED
  ```
- **容器里的 `ld.so.conf` 与宿主的独立**，但镜像里的库路径改动也会被继承 ⭐。
- **glibc 不能通过 `LD_LIBRARY_PATH` 替换**（会导致段错误与系统崩溃）⚠️⚠️。

#### 相关命令
`ldd` · `ld.so` · `LD_PRELOAD` · `objdump -p` · `patchelf` · `ldconfig -p`

### checkinstall — 把 make install 打包

**常用度**：★★★☆☆ ｜ **所属**：包管理 ｜ **POSIX/GNU 差异**：第三方工具，需安装；部分发行版已停止维护

```bash
checkinstall [选项]
```

| 选项 | 含义 |
|------|------|
| `-y` | 自动回答 yes ⭐ |
| `-D` | 让用户修改包描述（交互） |
| `--install=yes/no` | 是否安装生成的包 ⭐ |
| `--fstrans=yes/no` | 用文件系统事务（更安全） ⭐ |
| `--pkgname=名字` | 包名 |
| `--pkgversion=版本` | 版本（**必须是数字开头**） ⭐ |
| `--pkgrelease=发布号` | 发布号（如 `1`） |
| `--pkgarch=架构` | 架构（`amd64`） |
| `--pkggroup=组` | 组 |
| `--maintainer=邮箱` | 维护者 |
| `--provides=列表` | 提供的能力 |
| `--requires=列表` | 依赖 |
| `--nodoc` | 不打包 `-doc` 部分 |
| `--strip=yes/no` | 是否 strip 二进制 |
| `--backup=yes/no` | 是否备份被覆盖的文件 ⭐ |
| `--exclude=模式` | 排除文件 |
| `--include=模式` | 包含文件 |
| `-A` | 同 `--install=no --fstrans=no` |
| `--spec` | 生成 RPM spec |

```bash
# 场景：🧪 从源码构建本机包（Debian 系）⭐⭐
$ tar xzf app-1.0.0.tar.gz && cd app-1.0.0
$ ./configure --prefix=/usr/local
$ make -j"$(nproc)"
$ sudo checkinstall -D -y \
>   --pkgname=myapp \
>   --pkgversion=1.0.0 \
>   --pkgrelease=1 \
>   --pkgarch=amd64 \
>   --maintainer=me@example.com \
>   --requires=libc6 \
>   --backup=yes \
>   --install=yes

checkinstall 1.6.2, Copyright 2009 Felipe Eduardo Sanchez Diaz Duran
...
**********************************************************************
 Done. The new package has been installed (via "make install").
**********************************************************************

$ # 产物
$ ls *.deb
myapp_1.0.0-1_amd64.deb
$ # 之后可以用包管理器管理
$ dpkg -L myapp
$ sudo apt purge myapp
$ sudo apt install ./myapp_1.0.0-1_amd64.deb

# 场景：RPM 系上生成 .rpm ⭐
$ sudo checkinstall -y --pkgname=myapp --pkgversion=1.0.0 --pkgrelease=1 --pkgarch=x86_64
$ ls *.rpm
$ sudo rpm -ql myapp

# 场景：先不安装，只生成包（便于审查与分发）⭐
$ sudo checkinstall --install=no -y --pkgname=myapp --pkgversion=1.0.0
$ ls *.deb
$ dpkg-deb -c myapp_1.0.0-1_amd64.deb | head     # 审查内容

# 场景：只生成，然后用文件系统事务（更安全）
$ sudo checkinstall --fstrans=yes --install=no -y --pkgname=myapp --pkgversion=1.0.0

# 场景：⚠️ checkinstall 不可用时的手工方案 ⭐⭐
# 1. 用 DESTDIR 装到临时目录
$ ./configure --prefix=/usr
$ make -j"$(nproc)"
$ make DESTDIR=/tmp/stage install
$ # 2. 用 fpm 打包（更现代、更可控）
$ sudo apt install ruby ruby-dev build-essential
$ sudo gem install fpm
$ fpm -s dir -t deb -n myapp -v 1.0.0 \
>   --prefix / \
>   --maintainer me@example.com \
>   --description "My application" \
>   -C /tmp/stage \
>   --deb-no-default-config-files \
>   .
$ ls *.deb

# 场景：fpm 的更多用法 ⭐
$ fpm -s dir -t rpm -n myapp -v 1.0.0 -C /tmp/stage .        # 打 RPM
$ fpm -s dir -t deb -n myapp -v 1.0.0 \
>   --deb-depends 'libc6 (>= 2.31), libssl3' \
>   --deb-recommends 'ca-certificates' \
>   -C /tmp/stage .
$ fpm -s dir -t deb -n myapp -v 1.0.0 \
>   --exclude '*.log' --exclude 'usr/share/doc/*' \
>   -C /tmp/stage .

# 场景：🔐 审查生成的包
$ dpkg-deb -c myapp_1.0.0-1_amd64.deb                      # 文件清单
$ dpkg-deb -e myapp_1.0.0-1_amd64.deb /tmp/ctl && cat /tmp/ctl/postinst
$ dpkg-deb -c myapp_1.0.0-1_amd64.deb | grep -E '^-rws|^...s'

# 场景：Arch 上的等价做法（写 PKGBUILD）⭐
$ makepkg -si
$ ls *.pkg.tar.zst

# 场景：卸载手工安装的软件（没有包管理器时的正确方式）⭐⭐
$ # 1. 安装前记录文件清单
$ make DESTDIR=/tmp/stage install
$ find /tmp/stage -type f > /tmp/myapp.files
$ sudo cp -a /tmp/stage/. /
$ # 2. 卸载
$ sudo xargs -a /tmp/myapp.files -d '\n' rm -f
$ sudo find /tmp/stage -type d -empty
```

#### 输出解读
`checkinstall` 的工作流程：

```
1. 拦截 make install 写文件的行为（通过 LD_PRELOAD 或 DESTDIR 或备份机制）
2. 记录所有被创建/修改的文件
3. 生成包元数据（包裹控制文件）
4. 调用 dpkg-deb / rpmbuild 生成包
5. （可选）用包管理器安装该包
```

生成的包与原文件的关系：

| 方式 | 效果 |
|------|------|
| `--install=yes` | 生成包并立即用包管理器安装（**推荐**，文件归属正确） ⭐ |
| `--install=no` | 只生成包，你手动 `dpkg -i` |

#### 常见坑
- ⚠️ **`checkinstall` 需要 `make install` 的产物已构建**（先 `make` 再 `checkinstall`）⭐。
- ⚠️ **`--pkgversion` 必须以数字开头**（dpkg 的要求），`v1.0` 会失败 ⭐。
- ⚠️ **`checkinstall` 的备份机制在安装时会覆盖系统文件**，且**并行安装时可能记录错误**。用 `--fstrans=yes` 更安全，或改用 `DESTDIR` + `fpm` ⭐⭐。
- ⚠️ **很多发行版已不再维护 `checkinstall`**（Arch 上需要 AUR；Debian 上版本较老）。**推荐 `DESTDIR` + `fpm` 或写 `PKGBUILD`** ⭐。
- ⚠️ **生成的包不含依赖信息**（除非手写 `--requires`），安装时不会拉依赖，可能运行时才发现缺库 ⭐。
- **`checkinstall` 对**静态链接**的程序更可靠**（动态依赖不容易被正确推断）。
- **它会调用 `make install`**，所以 `Makefile` 的 `install` 目标里的恶意代码仍会执行 🔐。
- **`--backup=yes` 会在覆盖前备份原文件到 `/var/tmp/`**，占空间且不易清理。
- **`--strip=yes` 会 strip 二进制**（减小体积），但会破坏调试符号。
- **升级/卸载时如果文件被其他包修改过，包管理器会报冲突**。

#### 相关命令
`fpm` · `dpkg-deb` · `rpmbuild` · `makepkg` · `DESTDIR`
