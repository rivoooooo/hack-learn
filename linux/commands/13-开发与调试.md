### gcc / clang — C 编译器

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：`cc` 是 POSIX 约定的名字（通常链接到 gcc 或 clang）

```bash
gcc [选项] 源文件...
g++ / clang / clang++ [选项] 源文件...
```

| 选项 | 含义 |
|------|------|
| `-o 文件` | 输出文件名 ⭐ |
| `-c` | 只编译不链接（生成 `.o`） ⭐ |
| `-S` / `-E` | 生成汇编 / 只预处理 ⭐ |
| `-I 目录` / `-L 目录` / `-l 库` | 头文件 / 库 / 链接库 ⭐⭐ |
| `-D 宏[=值]` | 定义宏 ⭐ |
| `-g` / `-g3` | **生成调试信息** ⭐⭐ |
| `-O0`/`-O1`/`-O2`/`-O3`/`-Os`/`-Og` | 优化级别（**调试用 `-Og`**） ⭐⭐ |
| `-Wall -Wextra` | **开启警告** ⭐⭐ |
| `-Werror` | 警告视为错误 ⭐ |
| `-Wl,选项` | 传给链接器（`-Wl,-rpath,...`） ⭐⭐ |
| `-fPIC -shared` | 位置无关代码 / 共享库 ⭐ |
| `-static` | 静态链接 ⭐ |
| `-fsanitize=address` | **ASan 内存错误检测** ⭐⭐ |
| `-fsanitize=undefined` | UBSan 未定义行为 ⭐ |
| `-fsanitize=thread` | TSan 竞态检测 ⭐ |
| `-fstack-protector-strong` | 栈保护 ⭐ |
| `-D_FORTIFY_SOURCE=2` | 编译期加固 ⭐ |
| `-fPIE -pie` | 位置无关可执行文件 ⭐ |
| `-Wl,-z,relro,-z,now` | Full RELRO ⭐ |
| `-MMD -MP` | 生成依赖文件 ⭐ |
| `-###` | 只显示会执行的命令（dry run） ⭐ |
| `-print-search-dirs` | 显示搜索路径 ⭐ |

```bash
# 场景：⭐ 编译
$ gcc -Wall -Wextra -O2 -o hello hello.c
$ gcc -g -Og -Wall -o hello_dbg hello.c          # ⭐ 调试用
$ gcc -c -o hello.o hello.c && gcc -o hello hello.o

# 场景：⭐ 多文件 + 头文件/库路径
$ gcc -Wall -I./include -o app main.c util.c net.c -L./lib -lmylib

# 场景：⭐ 动态库与静态库
$ gcc -fPIC -shared -Wl,-soname,libmylib.so.1 -o libmylib.so.1.0.0 mylib.c
$ gcc -c mylib.c -o mylib.o && ar rcs libmylib.a mylib.o
$ gcc -o app main.c -L. -lmylib -Wl,-rpath,'$ORIGIN'    # ⭐ $ORIGIN = 自身目录

# 场景：🔐⭐⭐ ASan 检测内存错误（开发期必备）
$ cat > /tmp/bug.c <<'EOF'
#include <stdlib.h>
#include <string.h>
#include <stdio.h>
int main(void) {
    char *p = malloc(8);
    strcpy(p, "this is way too long");   /* 堆溢出 */
    printf("%s\n", p);
    free(p);
    printf("%c\n", p[0]);                /* use-after-free */
    return 0;
}
EOF
$ gcc -g -fsanitize=address -o /tmp/bug /tmp/bug.c
$ /tmp/bug 2>&1 | head -20
ERROR: AddressSanitizer: heap-buffer-overflow on address ...
# ⭐ ASan 直接给出「溢出位置 + 栈回溯」，比 gdb 快得多

$ gcc -g -fsanitize=undefined -o /tmp/ub -x c - <<'EOF'
#include <stdio.h>
int main(void) { int x = 2147483647; printf("%d\n", x + 1); return 0; }
EOF
$ /tmp/ub 2>&1 | head -5
$ rm -f /tmp/bug /tmp/bug.c /tmp/ub

# 场景：🔐 生产二进制加固（完整标志）
$ gcc -O2 -Wall -Wextra \
>   -fstack-protector-strong -D_FORTIFY_SOURCE=2 \
>   -fPIE -pie -Wl,-z,relro,-z,now -Wl,-z,noexecstack \
>   -o hardened app.c
$ # ⭐ 验证
$ readelf -h hardened | grep Type                     # DYN + PIE
$ readelf -d hardened | grep -E 'BIND_NOW|FLAGS_1'    # NOW PIE
$ readelf -lW hardened | awk '/GNU_STACK/{print $7}'  # RW（不是 RWE）
$ checksec --file=hardened 2>/dev/null | head -10

# 场景：⭐ 查看编译过程与搜索路径
$ gcc -### -o hello hello.c 2>&1 | head -20
$ gcc -print-search-dirs
$ echo | gcc -dM -E - | grep -iE 'fortify|stack_protector'
$ dpkg-buildflags 2>/dev/null || rpm --eval '%{optflags}'

# 场景：⭐ clang 特色
$ clang -Wall -Wextra -O2 -o hello hello.c
$ clang -fsanitize=address,undefined -g -o /tmp/x hello.c
$ clang --analyze hello.c                  # ⭐ 静态分析器
$ clang -Weverything hello.c 2>&1 | head   # ⭐ 打开所有警告

# 场景：⚠️ 交叉编译
$ aarch64-linux-gnu-gcc -o app-arm64 app.c   # 需工具链
$ gcc -m32 -o app32 app.c                    # 需 gcc-multilib
$ gcc -march=native -o app app.c             # ⚠️ 不可移植到其他 CPU
```

#### 输出解读
错误信息阅读顺序 ⭐：

```
file.c:12:25: error: 'x' undeclared (first use in this function)
│       │  │    └─ 描述
│       │  └─ 列
│       └─ 行
└─ 文件
```
⚠️ **从第一个错误开始修**（后面的常是连带错误）。

| 错误 | 原因 |
|------|------|
| `undefined reference to 'foo'` | 缺库（`-lfoo`）或**链接顺序错** ⭐⭐ |
| `fatal error: foo.h: No such file` | 缺开发包或缺 `-I` ⭐ |
| `relocation R_X86_64_32 against ...` | 编译共享库时忘了 `-fPIC` ⭐ |
| `cannot find -lfoo` | 缺库文件或 `-L` 路径 ⭐ |
| `exec format error` | 架构不匹配 ⭐ |

**链接顺序很重要** ⭐⭐：`gcc main.o -lfoo` 中，**被依赖的库要放在后面**。`gcc -lfoo main.o` 常失败。

#### 常见坑
- ⚠️⚠️ **不加 `-g` 就没法用 gdb 定位行号**（只有地址）⭐⭐。
- ⚠️⚠️ **`-O2`/`-O3` 会让调试困难**（变量被优化掉、行号错位）。**调试用 `-Og` 或 `-O0`** ⭐⭐。
- ⚠️⚠️ **链接顺序（库在后）** 是最常见的 `undefined reference` 原因 ⭐⭐。
- ⚠️ **`-static` 编出的二进制不能真正跨发行版**（glibc 仍有依赖），要可移植用 musl ⭐。
- ⚠️ **`-march=native` 在别的 CPU 上可能 `Illegal instruction`** ⚠️。
- **`-D_FORTIFY_SOURCE` 需 `-O1` 以上才生效** ⭐。
- **`-pie` 与 `-fPIE` 要一起给** ⭐。
- **`cc` 通常是 gcc 或 clang 的链接** ⭐：
  ```bash
  $ readlink -f "$(command -v cc)"
  /usr/bin/gcc
  ```

#### 相关命令
`make` · `ldd` · `objdump` · `readelf` · `gdb` · `pkg-config` · `ccache`

### make / cmake / meson — 构建系统

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：GNU make 与 BSD make 语法不兼容

> `make` 的完整说明见 [`08-包管理.md`](08-包管理.md#make--构建工具)。

```bash
make [选项] [目标]                  # 读 Makefile
cmake -S 源目录 -B 构建目录 [选项]   # 生成构建文件
cmake --build 构建目录 [-j N]
meson setup 构建目录 && ninja -C 构建目录
```

| cmake 选项 | 含义 |
|------------|------|
| `-S 目录` / `-B 目录` | 源目录 / 构建目录（**out-of-source**） ⭐⭐ |
| `-D 变量=值` | `CMAKE_BUILD_TYPE`、`CMAKE_INSTALL_PREFIX` ⭐⭐ |
| `-G 生成器` | `Ninja` / `Unix Makefiles` ⭐ |
| `--build` / `--install` / `--target` | 构建 / 安装 / 目标 ⭐ |
| `-L` / `-LA` | 列出可设置变量 ⭐ |
| `-DCMAKE_EXPORT_COMPILE_COMMANDS=ON` | 生成 `compile_commands.json` ⭐⭐ |

| meson 命令 | 含义 |
|------------|------|
| `meson setup build --buildtype=release` | 配置 ⭐ |
| `meson compile -C build` / `ninja -C build` | 构建 ⭐ |
| `meson test -C build` | 测试 ⭐ |
| `meson install -C build` | 安装 ⭐ |
| `meson configure build` | 查看/修改配置 ⭐ |

```bash
# 场景：⭐⭐ Makefile 最小可用模板
$ cat > /tmp/Makefile <<'EOF'
CC      ?= gcc
CFLAGS  ?= -Wall -Wextra -O2 -g -MMD -MP
LDLIBS  ?= -lm
TARGET  := app
SRCS    := $(wildcard *.c)
OBJS    := $(SRCS:.c=.o)
DEPS    := $(OBJS:.o=.d)

.PHONY: all clean install test
all: $(TARGET)
$(TARGET): $(OBJS)
	$(CC) $(LDFLAGS) -o $@ $^ $(LDLIBS)
%.o: %.c
	$(CC) $(CFLAGS) -c -o $@ $<
-include $(DEPS)
install: $(TARGET)
	install -Dm755 $(TARGET) $(DESTDIR)/usr/local/bin/$(TARGET)
test: $(TARGET)
	./$(TARGET) --selftest
clean:
	rm -f $(TARGET) $(OBJS) $(DEPS)
EOF
$ make -n                                # ⭐ 先看会执行什么
$ make -j"$(nproc)"                      # ⭐ 并行
$ make DESTDIR=/tmp/stage install         # ⭐ 装到临时前缀（便于打包）
$ make clean all -j8
$ grep -E '^[a-zA-Z0-9_-]+:' /tmp/Makefile   # ⭐ 看有哪些目标

# 场景：⭐⭐ CMake 标准工作流
$ cmake -S . -B build -G Ninja \
>   -DCMAKE_BUILD_TYPE=Release \
>   -DCMAKE_INSTALL_PREFIX=/usr/local \
>   -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
$ cmake --build build -j"$(nproc)"
$ sudo cmake --install build
$ ctest --test-dir build --output-on-failure     # ⭐ 跑测试
$ ls build/compile_commands.json                 # ⭐ 编辑器用

$ cmake -S . -B build -L                          # ⭐ 列出可设置变量
$ cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug -DCMAKE_C_FLAGS='-fsanitize=address'
$ cmake --build build-debug
$ cmake --build build --target help 2>/dev/null | head   # ⭐ 可用目标

# 场景：⭐⭐ Meson + Ninja（最快）
$ meson setup builddir --buildtype=release --prefix=/usr/local
$ meson compile -C builddir -j"$(nproc)"
$ meson test -C builddir --print-errorlogs
$ sudo meson install -C builddir
$ meson configure builddir -Dbuildtype=debug
$ ninja -C builddir -t targets | head              # ⭐ 目标列表
$ ninja -C builddir -t commands | head             # ⭐ 实际命令

# 场景：⭐ 干净重建
$ rm -rf build && cmake -S . -B build && cmake --build build -j"$(nproc)"

# 场景：🔐 构建时审查（装源码前必做）
$ cat > /tmp/build-audit.sh <<'SH'
#!/bin/bash
echo "=== 1. 构建脚本里的可疑命令 ==="
grep -nE 'curl.*\|.*(bash|sh)|wget.*\|.*(bash|sh)|nc -e|/dev/tcp|base64 -d|eval' \
  Makefile CMakeLists.txt meson.build configure config.status 2>/dev/null | head -20
echo "=== 2. install 目标会写到哪（⚠️ 关注 /etc、systemctl、useradd）==="
make -n install 2>/dev/null | grep -E '/etc/|/usr/bin|/usr/sbin|/lib/|systemctl|useradd|crontab' | head -20
echo "=== 3. CMake 的自定义命令（可能下载/执行）==="
grep -nE 'execute_process|add_custom_command|add_custom_target|ExternalProject|FetchContent' \
  CMakeLists.txt 2>/dev/null | head -20
SH
$ bash /tmp/build-audit.sh

# 场景：🔐 用 strace 观察构建（发现隐蔽的网络访问）
$ sudo strace -f -e trace=network -o /tmp/build.trace make -j1 2>/dev/null
$ grep -E 'connect\(.*AF_INET' /tmp/build.trace | head -10

# 场景：🧪 用容器隔离构建（推荐）
$ docker run --rm -v "$PWD":/src -w /src -u "$(id -u):$(id -g)" \
>   gcc:14 bash -c 'make -j4 && make test'
```

#### 输出解读
三种构建系统的关系 ⭐：

```
手写 Makefile         → make
Autotools(configure)  → make（configure 生成 Makefile）
CMake                 → 生成 Makefile 或 build.ninja → make / ninja ⭐
Meson                 → 生成 build.ninja → ninja ⭐
```

**Ninja vs Make**：Ninja **更快**（专为速度设计），CMake/Meson 都推荐 Ninja 作为后端 ⭐。

#### 常见坑
- ⚠️⚠️ **`make -j` 不带数字会无限并行**，可能 OOM ⭐⭐。
- ⚠️⚠️ **`make install` 通常需 root 且写到 `/usr/local`**（污染包管理器之外）。**用 `DESTDIR` + 打包工具** ⭐⭐。
- ⚠️⚠️ **CMake 的 in-source build（`cmake .`）会污染源码树**，难清理。**永远用 `-S . -B build`** ⭐⭐。
- ⚠️ **改了 `CMakeLists.txt` 要重新 `cmake -S . -B build`**（不重新配置不生效）⭐。
- ⚠️ **`make` 的依赖判断基于 mtime**，`cp -p` 或时钟错乱会破坏增量构建 ⭐。
- ⚠️ **`meson` 不支持 in-source build** ⭐。
- **`pkg-config` 是很多构建系统找依赖的方式**（缺 `-dev` 包会报 `Package X not found`）⭐。
- **`compile_commands.json` 对 IDE/clangd 很重要** ⭐⭐。
- 🔐 **构建过程本身能执行任意代码**（`Makefile`/`CMakeLists.txt`/`configure` 里的命令）🔐⭐⭐。

#### 相关命令
`gcc` · `pkg-config` · `ninja` · `autoconf` · `ccache` · `distcc`

### pkg-config — 查询编译与链接参数

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
pkg-config [选项] 包名...
```

| 选项 | 含义 |
|------|------|
| `--cflags` | **编译选项（`-I`）** ⭐⭐ |
| `--libs` | **链接选项（`-l`、`-L`）** ⭐⭐ |
| `--modversion` | 版本 ⭐ |
| `--list-all` | **列出所有已知包** ⭐⭐ |
| `--exists` / `--atleast-version=` | 存在性/版本检查（看退出码） ⭐ |
| `--print-errors` | 显示错误原因 ⭐ |
| `--static` | 静态链接所需选项 ⭐ |
| `--variable=变量` | 读变量（`prefix`/`includedir`/`pcfiledir`） ⭐ |
| `--print-variables` | 列出所有变量 ⭐ |
| `--validate` | 校验 `.pc` 文件语法 ⭐ |

```bash
# 场景：⭐⭐ 查询与使用
$ pkg-config --cflags --libs openssl
-I/usr/include -lssl -lcrypto
$ gcc -o app app.c $(pkg-config --cflags --libs libcurl)
$ pkg-config --modversion openssl
3.3.1
$ pkg-config --variable=prefix zlib
/usr

# 场景：⭐⭐ 列出所有已知包（找依赖名）
$ pkg-config --list-all | head -20
$ pkg-config --list-all | grep -iE 'ssl|crypto|curl|sqlite|xml|zlib'
$ pkg-config --list-all | awk '{print $1}' | sort > /tmp/pkgs.txt

# 场景：⭐ 版本检查（构建脚本里用）
$ pkg-config --exists 'openssl >= 3.0' && echo "满足要求" || echo "版本太低"
$ pkg-config --atleast-version=3.0 openssl && echo ">= 3.0"
$ pkg-config --print-errors --exists 'libcurl >= 8.0' ; echo "rc=$?"
Package libcurl was not found in the pkg-config search path.
Perhaps you should add the directory containing `libcurl.pc'
to the PKG_CONFIG_PATH environment variable

# 场景：⭐⭐ 排查「找不到包」
$ pkg-config --exists libfoo; echo "rc=$?"
$ # 1. .pc 文件在哪
$ find / -name '*.pc' 2>/dev/null | head -20
$ ls /usr/lib/pkgconfig/ /usr/lib/x86_64-linux-gnu/pkgconfig/ /usr/share/pkgconfig/ 2>/dev/null | head
$ # 2. 是不是缺开发包？（Debian: lib<name>-dev，RPM: <name>-devel）⭐
$ dpkg -S 'libcurl.pc' 2>/dev/null || rpm -qf /usr/lib*/pkgconfig/libcurl.pc 2>/dev/null
$ # 3. 非标准前缀安装的库要设 PKG_CONFIG_PATH ⭐
$ export PKG_CONFIG_PATH=/usr/local/lib/pkgconfig:$PKG_CONFIG_PATH
$ pkg-config --libs libfoo

# 场景：⭐ 查看 .pc 内容
$ cat "$(pkg-config --variable=pcfiledir zlib)/zlib.pc"
prefix=/usr
exec_prefix=${prefix}
libdir=${exec_prefix}/lib
includedir=${prefix}/include
Name: zlib
Description: zlib compression library
Version: 1.3.1
Libs: -L${libdir} -lz
Cflags: -I${includedir}

# 场景：🔐 交叉编译（避免误用宿主的 .pc）⭐⭐
$ export PKG_CONFIG_LIBDIR=/path/to/sysroot/usr/lib/pkgconfig   # ⭐ 替换默认路径
$ export PKG_CONFIG_SYSROOT_DIR=/path/to/sysroot
$ pkg-config --cflags --libs libfoo

# 场景：⭐ 手写自己的 .pc（非标准前缀）
$ mkdir -p /usr/local/lib/pkgconfig
$ cat > /usr/local/lib/pkgconfig/mylib.pc <<'EOF'
prefix=/opt/mylib
exec_prefix=${prefix}
libdir=${exec_prefix}/lib
includedir=${prefix}/include
Name: mylib
Description: My custom library
Version: 1.0.0
Libs: -L${libdir} -lmylib
Cflags: -I${includedir}
EOF
$ pkg-config --cflags --libs mylib
$ pkg-config --validate /usr/local/lib/pkgconfig/mylib.pc && echo OK

# 场景：🧪 批量检查项目的依赖是否齐备
$ for p in openssl zlib libcurl sqlite3 libxml-2.0; do
>   printf '%-16s %-12s %s\n' "$p" \
>     "$(pkg-config --modversion "$p" 2>/dev/null || echo '缺失')" \
>     "$(pkg-config --exists "$p" && echo OK || echo FAIL)"
> done
```

#### 输出解读
`.pc` 文件的字段：

| 字段 | 含义 |
|------|------|
| `prefix` / `libdir` / `includedir` | 路径 ⭐ |
| `Name` / `Description` / `Version` | 名称/描述/版本 ⭐ |
| `Requires` / `Requires.private` | 依赖（后者仅静态链接需要） ⭐ |
| `Libs` / `Libs.private` | 链接参数 ⭐ |
| `Cflags` | 编译参数 ⭐ |
| `Conflicts` | 冲突的包 ⭐ |

**搜索路径**：`/usr/lib/pkgconfig/`、`/usr/lib/<triplet>/pkgconfig/`、`/usr/share/pkgconfig/`、`/usr/local/lib/pkgconfig/`、`$PKG_CONFIG_PATH` ⭐

#### 常见坑
- ⚠️⚠️ **`pkg-config` 只说「找不到」，不说「装哪个包」**：Debian 是 `lib<name>-dev`，RPM 是 `<name>-devel` ⭐⭐。
- ⚠️⚠️ **`--cflags` 与 `--libs` 要分别给对位置**（编译用前者，链接用后者）⭐。
- ⚠️⚠️ **静态链接要加 `--static`**（否则缺 `Requires.private` 的库）⭐⭐。
- ⚠️ **`PKG_CONFIG_PATH` 是追加，`PKG_CONFIG_LIBDIR` 是替换**（交叉编译用后者）⭐⭐。
- ⚠️ **交叉编译时宿主的 `.pc` 会被误用**（链接到错误架构）⭐⭐。
- **`pkgconf` 是现代替代**（兼容实现）⭐：
  ```bash
  $ readlink -f "$(command -v pkg-config)"
  /usr/bin/pkgconf
  ```
- **`pkg-config` 与 CMake 的 `find_package` 是两套机制** ⭐。

#### 相关命令
`gcc` · `make` · `cmake` · `ldconfig` · `ldd`

### ldd — 查看动态链接依赖

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：非 POSIX

> 🔐⚠️ **`ldd` 的实现是「运行加载器」，对不可信二进制可能执行其代码**。分析外来二进制用 `objdump -p` / `readelf -d` 代替。

```bash
ldd [选项] 文件...
```

| 选项 | 含义 |
|------|------|
| （无参） | 完整依赖树 ⭐ |
| `-u` | 显示未使用的直接依赖 ⭐ |
| `-r` | 报告缺失依赖与重定位错误 ⭐ |
| `-v` | 显示版本要求 ⭐ |

```bash
# 场景：⭐⭐ 查看依赖
$ ldd /usr/bin/ls
	linux-vdso.so.1 (0x00007ffe...)
	libselinux.so.1 => /lib/x86_64-linux-gnu/libselinux.so.1 (0x00007f...)
	libc.so.6 => /lib/x86_64-linux-gnu/libc.so.6 (0x00007f...)
	/lib64/ld-linux-x86-64.so.2 (0x00007f...)
$ # 格式：<SONAME> => <实际路径> (<加载地址>)

# 场景：⭐⭐ 找缺失依赖（服务起不来的经典原因）⭐
$ ldd /path/to/app | grep 'not found'
	libfoobar.so.1 => not found
$ ldd -r /path/to/app 2>&1 | grep -iE 'not found|undefined'
$ # ⭐ 修复：装对应的「运行库」（不是 -dev 包）
$ apt-file search libfoobar.so.1 2>/dev/null || dnf provides '*/libfoobar.so.1'

# 场景：⭐⭐ 排查自定义库找不到
$ sudo install -Dm755 libmylib.so.1.0.0 /usr/local/lib/libmylib.so.1.0.0
$ sudo ln -sf libmylib.so.1.0.0 /usr/local/lib/libmylib.so.1
$ echo '/usr/local/lib' | sudo tee /etc/ld.so.conf.d/local.conf
$ sudo ldconfig
$ ldd /usr/local/bin/myapp | grep mylib
$ # ⭐ 还找不到就查 RPATH / LD_LIBRARY_PATH / ld.so.conf
$ readelf -d /usr/local/bin/myapp | grep -E 'RPATH|RUNPATH'

# 场景：⭐ 未使用依赖与版本要求
$ ldd -u /usr/bin/app

	libpthread.so.0
$ ldd -v /usr/bin/ls | grep -A5 'Version information' | head -15

# 场景：🔐⭐⭐ 安全用法（分析不可信二进制）
$ cat > /tmp/safe-ldd.sh <<'SH'
#!/bin/bash

echo "--- 解释器 ---"

SH
$ bash /tmp/safe-ldd.sh ./suspicious_binary

# 场景：🔐 判断动态还是静态
$ file /tmp/static_app

$ ldd /tmp/static_app

  [ -f "$f" ] && [ -x "$f" ] || continue

    *'/tmp'*|*'/home'*|*'/dev/shm'*|*'/var/tmp'*) echo "⚠️ $f: $rp" ;;

echo "=== 环境中的 LD_* ==="; env | grep -E '^LD_' || echo "(无)"
echo "=== ld.so.preload ==="; cat /etc/ld.so.preload 2>/dev/null || echo "(不存在)"

$ strace -f -e trace=openat /usr/bin/ls 2>&1 | grep '\.so' | head -10

```

```
│                └─ `=>`（`not found` = 缺失）⭐
└─ SONAME ⭐
```

| 输出 | 含义 |
|------|------|
| `linux-vdso.so.1` | **内核提供的虚拟库**（无实体文件，正常）⭐ |
| `/lib64/ld-linux-x86-64.so.2` | **动态加载器本身** ⭐ |
| `X => not found` | **缺失，程序无法启动** ⭐⭐ |
| `not a dynamic executable` | 静态链接 ⭐ |

**库搜索顺序** ⭐⭐：
```
1. DT_RPATH（若没有 DT_RUNPATH）
2. LD_LIBRARY_PATH
3. DT_RUNPATH                    ← 现代做法
4. /etc/ld.so.cache（ldconfig）
5. /lib、/usr/lib
```
⚠️ **SUID 程序会忽略 `LD_LIBRARY_PATH`**（安全设计）⭐。

#### 🔐 `ldd` 的安全风险
`ldd` 会**把目标程序交给加载器执行**（设置 `LD_TRACE_LOADED_OBJECTS`），所以**对恶意二进制有代码执行风险** ⚠️⭐⭐。

**安全替代** ⭐⭐：
```bash
$ readelf -d 文件 | grep NEEDED
$ objdump -p 文件 | grep NEEDED
```

#### 常见坑
- ⚠️⚠️ **`ldd` 对不可信二进制有代码执行风险** ⭐⭐。
- ⚠️⚠️ **`not found` 说明缺运行库**（不是缺 `-dev`）⭐⭐。
- ⚠️⚠️ **`ldd` 的输出不反映运行时真实情况**（`LD_LIBRARY_PATH`/cwd 不同则加载不同）⭐⭐：
  ```bash
  $ ldd ./app && LD_LIBRARY_PATH=. ldd ./app
  ```
- ⚠️ **静态程序报 `not a dynamic executable` 不是错误** ⭐。
- ⚠️ **容器里只能看到容器内的库** ⭐。
- **`ldd -r` 比只看 `not found` 更严格**（会报未解析符号）⭐。
- **`LD_DEBUG=libs` 是排查库加载的最强工具** ⭐⭐。

#### 相关命令
`readelf -d` · `objdump -p` · `ldconfig` · `LD_DEBUG` · `patchelf`

### objdump — 反汇编与 ELF 检查

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：GNU binutils

```bash
objdump [选项] 文件...
```

| 选项 | 含义 |
|------|------|
| `-d` | **反汇编（只含代码的节）** ⭐⭐ |
| `-D` | 反汇编所有节 ⭐ |
| `-S` | 反汇编混排源码（需 `-g`） ⭐⭐ |
| `-M intel` | **Intel 语法（默认是 AT&T）** ⭐⭐ |
| `-t` / `-T` | 符号表 / **动态符号表** ⭐⭐ |
| `-h` / `-x` | 节头 / 所有头部 ⭐ |
| `-p` | **私有头（NEEDED/RPATH）** ⭐⭐ |
| `-r` / `-R` | 重定位 / 动态重定位 ⭐ |
| `-s -j 节名` | 显示某节内容（hex） ⭐ |
| `--disassemble=函数` | **只反汇编某函数** ⭐⭐ |
| `--start-address=` / `--stop-address=` | 地址范围 ⭐⭐ |
| `-C` | C++ 符号还原 ⭐⭐ |
| `-l` | 显示行号（需 `-g`） ⭐ |
| `--dwarf=info` | DWARF 调试信息 ⭐ |

```bash
# 场景：⭐⭐ 反汇编
$ objdump -d /usr/bin/ls | head -20
0000000000005b90 <main>:
    5b90:	f3 0f 1e fa          	endbr64
    5b94:	48 83 ec 08          	sub    $0x8,%rsp
$ objdump -d -M intel /usr/bin/ls | head -10           # ⭐ Intel 语法
$ objdump -d -S -M intel /tmp/demo | sed -n '/<main>:/,/ret/p' | head -40

# 场景：⭐⭐ 只反汇编某个函数（大二进制定位）
$ objdump -d -M intel --disassemble=main /usr/bin/ls | head -20
$ objdump -d -M intel --start-address=0x1149 --stop-address=0x11a0 /tmp/demo

# 场景：⭐⭐ 看依赖与 RPATH（不执行目标，比 ldd 安全）
$ objdump -p /usr/bin/ls | grep -E 'NEEDED|RPATH|RUNPATH|SONAME|INTERP'
$ objdump -p /usr/local/bin/myapp | grep -E 'RPATH|RUNPATH'

# 场景：⭐ 符号与节
$ objdump -t /tmp/demo | grep -E 'F .text' | head -10
$ objdump -T /usr/bin/ls | grep -E 'UND|GLIBC' | head -10
$ objdump -h /usr/bin/ls | grep -E '\.text|\.data|\.bss|\.rodata'
$ objdump -h /tmp/demo | head -10

# 场景：🔐⭐⭐ 手工 checksec（加固检查）
$ cat > /tmp/checksec-manual.sh <<'SH'
#!/bin/bash
f=$1
echo "=== $f ==="
type=$(readelf -h "$f" | awk '/Type:/{print $2}')
flags1=$(readelf -d "$f" 2>/dev/null | grep FLAGS_1)
stack=$(readelf -lW "$f" 2>/dev/null | awk '/GNU_STACK/{print $7}')
relro=$(readelf -lW "$f" 2>/dev/null | grep -c GNU_RELRO)
bindnow=$(readelf -d "$f" 2>/dev/null | grep -cE 'BIND_NOW|NOW')

case "$type$flags1" in *PIE*) echo "PIE: ✅" ;; *) echo "PIE: ❌" ;; esac
case "$stack" in *E*) echo "NX: ❌ 栈可执行" ;; *) echo "NX: ✅" ;; esac
if [ "$relro" -gt 0 ] && [ "$bindnow" -gt 0 ]; then echo "RELRO: ✅ Full"
elif [ "$relro" -gt 0 ]; then echo "RELRO: ⚠️ Partial"; else echo "RELRO: ❌"; fi
strings -a "$f" 2>/dev/null | grep -q __stack_chk_fail && echo "Canary: ✅" || echo "Canary: ❓"
readelf --dyn-syms -W "$f" 2>/dev/null | grep -q '_chk@' && echo "FORTIFY: ✅" || echo "FORTIFY: ❓"
readelf -d "$f" 2>/dev/null | grep -q TEXTREL && echo "⚠️ TEXTREL（需可写代码段）" || echo "TEXTREL: 无"
objdump -T "$f" 2>/dev/null | grep -oE '\b(strcpy|strcat|sprintf|gets|system|popen|memcpy|alloca)\b' | sort -u | tr '\n' ' '
echo
SH
$ bash /tmp/checksec-manual.sh /usr/bin/ls
$ checksec --file=/usr/bin/ls 2>/dev/null || pwn checksec /usr/bin/ls 2>/dev/null | head

$ strings -a /tmp/demo | grep -iE 'password|token|/etc/|http' | head -10

# 场景：🔐 查调试信息泄露（源码路径、用户名）⭐
$ objdump --dwarf=info /tmp/demo 2>/dev/null | grep -E 'DW_AT_(name|comp_dir|producer)' | head -10
$ readelf --string-dump=.comment /tmp/demo | head -5

# 场景：🧪 对比不同优化级别的产物

```

#### 输出解读
```

    5b94:	48 83 ec 08          	sub    rsp,0x8
    │       │                     └─ 汇编指令
    │       └─ 机器码
    └─ 地址
```

**加固项检查速查** ⭐⭐：

| 加固项 | 检查 | 期望 |
|--------|------|------|
| PIE | `readelf -h` 的 `Type: DYN` + `FLAGS_1: PIE` | 启用 ⭐⭐ |
| NX | `readelf -lW \| awk '/GNU_STACK/{print $7}'` | `RW`（非 `RWE`） ⭐⭐ |
| RELRO | `GNU_RELRO` + `BIND_NOW` | Full ⭐ |
| Canary | `objdump -d \| grep stack_chk_fail` | 有 ⭐ |
| FORTIFY | `objdump -T \| grep '_chk'` | 有 ⭐ |
| TEXTREL | `readelf -d \| grep TEXTREL` | 无 ⚠️ |

#### 常见坑
- ⚠️ **默认是 AT&T 语法**（`mov %rax,%rbx` 顺序与 Intel 相反）。**加 `-M intel`** ⭐⭐。
- ⚠️ **`-d` 只反汇编代码节**；`-D` 会包含数据（大量无意义输出）⭐。
- ⚠️ **`-S` 需要 `-g` 编译** ⭐。
- ⚠️ **stripped 二进制只有地址没有函数名** ⭐。
- ⚠️ **`-T`（动态符号，含 `GLIBC_*` 版本）与 `-t`（普通符号表）不同** ⭐。
- ⚠️ **大二进制的 `objdump -d` 输出可能几百万行**，务必用 `--disassemble=` 限制 ⭐⭐。
- **`objdump -p` 是安全的看依赖方式**（不执行目标）⭐⭐。
- 🔐 **`.rodata` 与 `.comment` 可能泄露硬编码凭据与工具链版本** ⭐⭐。

#### 相关命令
`readelf` · `nm` · `strings` · `gdb` · `rizin` · `checksec` · `patchelf`

```bash
  case "$stack" in *E*) printf 'NX❌ ' ;; *) printf 'NX✅ ' ;; esac
  if [ "$relro" -gt 0 ] && [ "$bindnow" -gt 0 ]; then printf 'RELRO=Full✅ '
  elif [ "$relro" -gt 0 ]; then printf 'RELRO=Partial⚠️ '; else printf 'RELRO❌ '; fi
  strings -a "$f" 2>/dev/null | grep -q __stack_chk_fail && printf 'Canary✅ ' || printf 'Canary❌ '
  readelf --dyn-syms -W "$f" 2>/dev/null | grep -q '_chk@' && printf 'FORTIFY✅' || printf 'FORTIFY❌'
  echo
done
SH
```

**ELF 头的 `Type`** ⭐⭐：

| 值 | 含义 |
|----|------|
| `EXEC` | 固定地址可执行（**无 PIE**，ASLR 保护弱）⚠️ |
| `DYN` | 共享对象或 **PIE 可执行**（配合 `FLAGS_1: PIE`）⭐⭐ |
| `REL` | 可重定位目标（`.o`） |
| `CORE` | core dump ⭐ |

**程序头必看的三个** ⭐⭐：

| 段 | 检查 |
|----|------|
| `INTERP` | 动态加载器路径（无 = 静态链接）⭐ |
| `GNU_STACK` | `RW`（NX 启用）vs `RWE`（**栈可执行，危险**）⭐⭐ |
| `GNU_RELRO` | 有 = 部分/完整 RELRO ⭐ |

**动态节的加固标志** ⭐⭐：`BIND_NOW`/`NOW`（Full RELRO 的一半）、`PIE`、`RUNPATH`（审计是否指向可写目录）、`TEXTREL`（⚠️ 削弱 W^X）。

#### 常见坑
- ⚠️ **`readelf -a` 输出极长**，用具体选项 ⭐。
- ⚠️ **`-W` 避免输出被截断**（长节名必需）⭐⭐。
- ⚠️ **`Type: DYN` 不一定是 PIE**（也可能只是共享库），要看 `FLAGS_1` ⭐。
- ⚠️⚠️ **`GNU_STACK` 为 `RWE` 说明栈可执行**（重要弱点）⭐⭐。
- ⚠️ **`.comment` 泄露编译器版本**（生产可 strip）🔐⭐。
- ⚠️ **stripped 二进制没有 `.symtab` 但仍有 `.dynsym`** ⭐。
- **`readelf -d` 比 `ldd` 安全**（不执行目标）⭐⭐。
- **build-id 是关联调试符号与识别来源的关键** ⭐。

### nm — 符号表

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：POSIX 定义了 `nm`；选项集 GNU 更丰富

```bash
nm [选项] 文件...
```

| 选项 | 含义 |
|------|------|
| （无参） | 符号表（地址、类型、名字） ⭐ |
| `-D` | **动态符号表**（stripped 二进制唯一可看的） ⭐⭐ |
| `-C` | **C++ 符号还原** ⭐⭐ |
| `-u` | **只看未定义符号**（依赖什么） ⭐⭐ |
| `-U` | 只看已定义 ⭐ |
| `-g` | 只看外部符号 ⭐ |
| `-l` | 显示源文件与行号（需 `-g`） ⭐ |
| `-n` | 按地址排序 ⭐ |
| `-S` + `--size-sort` | 显示符号大小并按大小排序 ⭐ |
| `-A` | 显示所属文件（`.a` 里有用） ⭐ |

**符号类型字符** ⭐⭐：

| 字符 | 含义 |
|------|------|
| `T` / `t` | **代码段**：大写=全局（导出），小写=局部（static） ⭐⭐ |
| `D` / `d` | 已初始化数据 ⭐ |
| `B` / `b` | 未初始化数据（`.bss`） ⭐ |
| `R` / `r` | 只读数据 ⭐ |
| `U` | **未定义（外部引用）** ⭐⭐ |
| `W` / `w` | 弱符号 |
| `A` | 绝对地址 |

### size / strip / strings — 大小、剥离与字符串

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：`strings` 的 `-t` 格式有差异

```bash
size [选项] 文件...          # 段大小
strip [选项] 文件...         # 剥离符号
strings [选项] 文件...       # 提取可打印字符串
```

| size | 含义 |
|------|------|
| （无参） | text/data/bss/dec/hex ⭐ |
| `-A` | 按节显示大小 ⭐ |
| `-t` | 加总计 ⭐ |

| strip | 含义 |
|-------|------|
| （无参） | 剥离所有符号 ⭐ |
| `-g` / `--strip-debug` | 只剥离调试信息（保留符号名） ⭐ |
| `--strip-unneeded` | 剥离不需要的（**共享库要用这个**） ⭐⭐ |
| `-o 文件` | 输出到新文件（**不覆盖原文件**） ⭐⭐ |
| `-K 符号` | 保留指定符号 ⭐ |
| `-R 节` / `--remove-section=` | 移除某节 ⭐ |

| strings | 含义 |
|---------|------|
| `-a` | **扫描整个文件（不只已加载段）** ⭐⭐ |
| `-n N` | 最短长度（默认 4） ⭐ |
| `-t 进制` | 显示偏移（`d`/`o`/`x`） ⭐ |
| `-e 编码` | `s`/`S`/`b`/`l`/`B`/`L` ⭐ |

#### 🔐 strip 的安全意义
| 好处 | 说明 |
|------|------|
| 减小体积 | 符号表可能占 30–50% ⭐ |

- ⚠️⚠️ **对共享库用 `strip --strip-all` 会破坏动态链接**。**用 `--strip-unneeded`** ⭐⭐。
- ⚠️⚠️ **`strip` 默认覆盖原文件**，用 `-o` 或先备份 ⭐⭐。
- ⚠️ **strip 掉的符号无法恢复**（除非有备份或 build-id）⭐。
- ⚠️⚠️ **`strings` 不加 `-a` 会漏掉未初始化段里的字符串**。**取证必加 `-a`** ⭐⭐。
- ⚠️ **`strings` 对压缩/加密数据无效** ⭐。
- ⚠️ **`strings` 不做编码转换**，UTF-8 中文可能被截断 ⭐。
- **`size` 的 `bss` 不计入文件大小** ⭐。
- **`strings -n 4`（默认）输出海量**，先 `sort -u` ⭐。
- 🔐 **`strings` 是恶意软件分析的第一步**（零成本，收益高）⭐⭐。

#### 输出解读
**地址转换原理** ⭐：

```
文件偏移  →  addr2line 读 DWARF  →  源文件:行号
```

⚠️ **运行时地址 ≠ 文件偏移**（PIE/ASLR）⭐⭐：

| 二进制类型 | 转换 |
|------------|------|
| 非 PIE（`EXEC`）且无 ASLR | 运行时地址 = 文件地址 ⭐ |
| **PIE（`DYN` + PIE）** | **偏移 = 运行时地址 − 加载基址** ⭐⭐ |
| 共享库 | 偏移 = 运行时地址 − 库加载基址 ⭐ |

**基址从哪来** ⭐：
```bash
$ cat /proc/PID/maps | awk '/r-xp/{print $1, $NF}' | head    # r-xp 段起始
$ # 或 gdb: info proc mappings
```

**`c++filt` 支持**：GNU v3（Itanium）、Java、ObjC、Ada、Rust（较新版本）等 mangling 格式 ⭐

#### 常见坑
- ⚠️⚠️ **PIE 二进制必须减加载基址**，否则得到错误行号或 `??:0` ⭐⭐。
- ⚠️⚠️ **需要带调试信息的二进制（`-g`）**，否则只能得到函数名或 `??` ⭐⭐。
- ⚠️⚠️ **strip 过的二进制无法 `addr2line`**（除非有独立 debug 文件 + `.gnu_debuglink`）⭐⭐：
  ```bash
  $ objcopy --only-keep-debug bin bin.debug
  $ objcopy --add-gnu-debuglink=bin.debug bin.stripped
  $ addr2line -e bin.stripped 0x1149        # 自动找 bin.debug
  ```
- ⚠️ **`-i` 只对有内联信息（`-g` 且未过度优化）的二进制有效** ⭐。
- ⚠️ **C++ 符号务必 `-C`** ⭐⭐。
- **`-p` 让输出变成单行**（脚本友好）⭐：
  ```
  handle_request at /home/user/src/server.c:142
  ```
- **`-s` 只显示 basename**（避免泄露完整路径）⭐。
- 🔐 **`addr2line` 是漏洞分析的常用工具**（从崩溃地址快速定位代码）⭐⭐。


#### 常见坑
- ⚠️⚠️ **必须 `-g` 编译才能看到源码行号**，`-O2`/`-O3` 会让调试困难（用 `-Og`）⭐⭐。
- ⚠️⚠️ **`gdb -p PID` 会暂停目标进程**（附加时发送 SIGSTOP），`detach` 才能继续 ⭐⭐。
- ⚠️⚠️ **在容器里 `gdb -p` 需要 `CAP_SYS_PTRACE` 与 `ptrace_scope` 允许** ⭐⭐：
  ```bash
  $ cat /proc/sys/kernel/yama/ptrace_scope
  1     # 1 = 只能调试自己的子进程；0 = 允许任意
  $ sudo sysctl -w kernel.yama.ptrace_scope=0    # ⚠️ 会降低安全性
  ```
- ⚠️ **看别人的进程要 root** ⭐。
- ⚠️ **`gdb` 对大 core（几 GB）加载很慢** ⭐。
- ⚠️ **多线程调试时默认会切换线程**（`set scheduler-locking on` 可锁定）⭐。
- ⚠️ **`gdb` 无法调试被 strip 的二进制**（除汇编级）⭐。
- **`set pagination off` 在脚本里必须设**（否则会卡在 `--More--`）⭐⭐。
- **`-batch` 模式遇到错误会退出**，可用 `-ex '命令'` 顺序执行 ⭐。
- 🔐 **`gdb` 能读进程内存与环境**（含凭据），本身也是攻击者的工具 ⭐⭐。

#### 相关命令
`coredumpctl` · `strace` · `ltrace` · `objdump` · `addr2line` · `rr`（录制回放调试）

### perf — 性能分析

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：Linux 特有（`perf_event_open`）

```bash
perf [子命令] [选项]
```

| 子命令 | 作用 |
|--------|------|
| `stat` | **统计特定事件（计数器）** ⭐⭐ |
| `record` | **采样并记录** ⭐⭐ |
| `report` | 分析 record 的数据 ⭐⭐ |
| `top` | 实时热点函数（类 top） ⭐⭐⭐ |
| `trace` | **跟踪系统调用（strace 的低开销版）** ⭐⭐ |
| `sched` | 调度器分析（延迟、迁移） ⭐⭐ |
| `lock` | 锁竞争分析 ⭐⭐ |
| `mem` | 内存访问分析 ⭐ |
| `list` | 列出可用事件 ⭐⭐ |
| `annotate` | 源码/汇编级热点注释 ⭐⭐ |
| `diff` | 对比两次 record |
| `script` | 解析 record 数据（脚本） ⭐ |
| `kmem` | 内核内存分析 |
| `c2c` | 缓存行竞争分析 ⭐ |
| `probe` | 动态添加探针 ⭐ |

| stat 选项 | 含义 |
|-----------|------|
| `-e 事件` | 指定事件（可多个） ⭐⭐ |
| `-a` | 全部 CPU |
| `-C N` | 指定 CPU |
| `-p PID` | 指定进程 ⭐ |
| `-d` / `-dd` / `-ddd` | 详细事件集 ⭐ |
| `-r N` | 重复 N 次取平均 ⭐ |
| `-I 毫秒` | 周期性输出 ⭐ |
| `--per-core` / `--per-thread` | 按核 / 按线程 ⭐ |
| `-G` | 只统计该 cgroup |

| record 选项 | 含义 |
|-------------|------|
| `-g` | **记录调用图（call graph）** ⭐⭐ |
| `--call-graph dwarf` | 用 DWARF 展开栈（更准但更慢） ⭐ |
| `-F N` | 采样频率（Hz） ⭐ |
| `-e 事件` | 采样事件（`cycles`、`cache-misses`） ⭐ |
| `-p PID` / `-a` | 进程 / 全部 CPU ⭐ |
| `-o 文件` | 输出文件 ⭐ |

```bash

$ perf --version
$ cat /proc/sys/kernel/perf_event_paranoid
2     # ⭐ 2 = 只允许用户空间采样；-1 = 全部允许
$ sudo sysctl -w kernel.perf_event_paranoid=-1     # ⚠️ 降低安全性（临时）
$ ls /sys/kernel/debug/tracing/ 2>/dev/null | head -3

# 场景：⭐⭐ 统计整体性能计数器
$ perf stat ./app

      1234.56 msec task-clock                #    0.998 CPUs utilized
            12      context-switches          #   ......
             2      cpu-migrations
           456      page-faults
    3,456,789,012      cycles
    1,234,567,890      instructions              #    0.36  insn per cycle   # ⭐ IPC
      234,567,890      branches
        1,234,567      branch-misses             #    0.53% of all branches   # ⭐ 分支预测失败率

       1.236789012 seconds time elapsed

$ # ⭐ IPC（instructions per cycle）< 1 说明 CPU 在等（可能是内存/分支问题）
$ perf stat -d ./app                       # ⭐ 更多事件
$ perf stat -dd ./app
$ perf stat -e cache-misses,cache-references,instructions,cycles ./app
$ perf stat -r 5 ./app                     # ⭐ 跑 5 次取平均
$ perf stat -I 1000 ./app                  # ⭐ 每秒输出
$ perf stat --per-core -a sleep 1
$ perf stat -p 1234 sleep 5                # ⭐ 统计运行中的进程

# 场景：⭐⭐⭐ perf top（实时热点，无需先 record）
$ sudo perf top                            # 全系统热点函数
$ sudo perf top -p 1234                    # 只盯某进程
$ sudo perf top -g                         # ⭐ 显示调用图
$ sudo perf top -e cache-misses            # ⭐ 看缓存未命中的热点
$ sudo perf top --sort=dso,symbol
$ # 交互键：h 帮助、z 缩放、E 展开、a 注释、q 退出

# 场景：⭐⭐ record + report（离线分析）
$ perf record -g -F 999 -o /tmp/perf.data ./app
$ perf report -i /tmp/perf.data            # ⭐ 交互式（TUI）
$ perf report -i /tmp/perf.data --stdio | head -40       # ⭐ 文本输出（脚本友好）
$ perf report -i /tmp/perf.data --stdio --sort=comm,dso,symbol | head -20
$ perf report -i /tmp/perf.data --stdio -g | head -40    # ⭐ 带调用图

$ # ⭐ 采样特定事件（找内存瓶颈）
$ perf record -e cache-misses -g -o /tmp/cm.data ./app
$ perf report -i /tmp/cm.data --stdio | head -20
$ perf record -e branch-misses -g -o /tmp/bm.data ./app
$ perf report -i /tmp/bm.data --stdio | head -20

# ⭐ 采样调用图（更准，但需调试信息）
$ perf record --call-graph dwarf -F 499 -o /tmp/dw.data ./app
$ perf report -i /tmp/dw.data --stdio -g | head -40

# 场景：⭐⭐⭐ perf trace（strace 的低开销版）
$ sudo perf trace ./app
$ sudo perf trace -p 1234
$ sudo perf trace -e openat,read,write ./app
$ sudo perf trace --summary ./app           # ⭐ 汇总统计
$ sudo perf trace -s ./app                  # 同 --summary
$ perf list | grep -E 'syscalls:sys_enter_(open|execve|connect)' | head

# 场景：⭐⭐ 调度器分析（找「谁把 CPU 让出去了」）
$ sudo perf sched record ./app
$ sudo perf sched latency                   # ⭐ 各任务的调度延迟
$ sudo perf sched timehist | head -30        # ⭐ 时间线

$ sudo perf sched max                        # 最大延迟

# 场景：⭐⭐ 锁竞争分析
$ sudo perf lock record ./app
$ sudo perf lock report                     # ⭐ 锁等待排行
$ sudo perf lock contention -b -a sleep 5   # ⭐ 实时锁竞争

# 场景：⭐ 内存访问分析
$ sudo perf mem record ./app
$ sudo perf mem report                      # ⭐ 内存访问热点与延迟
$ sudo perf mem report --sort=mem,symbol

# 场景：⭐ c2c（缓存行伪共享，多线程性能杀手）
$ sudo perf c2c record ./mt_app
$ sudo perf c2c report                      # ⭐ 找缓存行竞争

# 场景：⭐⭐ 源码/汇编级热点注释
$ perf record -g ./app
$ perf annotate --stdio | head -60          # ⭐ 每个函数的指令级热点
$ perf annotate --stdio -s main             # ⭐ 只看某函数
$ perf annotate --stdio --source            # ⭐ 源码级（需 -g）

# 场景：⭐ 对比两次运行（找性能回归）
$ perf record -o /tmp/before.data ./app
$ # ... 改代码 ...
$ perf record -o /tmp/after.data ./app
$ perf diff /tmp/before.data /tmp/after.data | head -30
$ perf diff --sort=delta /tmp/before.data /tmp/after.data

# 场景：🔐⭐⭐ 安全用途（异常行为检测）
$ cat > /tmp/perf-security.sh <<'SH'
#!/bin/bash
echo "=== 1. 找 CPU 占用异常的进程（可能是挖矿）==="
sudo perf top -b -e cycles 2>/dev/null | head -15

echo "=== 2. 追踪谁在频繁执行系统调用（可能是扫描/爆破）==="
sudo perf trace -a --summary sleep 5 2>/dev/null | head -20

echo "=== 3. 看某进程的系统调用分布 ==="
pid=${1:-}
[ -n "$pid" ] && sudo perf trace -p "$pid" --summary sleep 5 2>/dev/null | head -20

echo "=== 4. 观察调度延迟（异常可能有抢占或锁问题）==="
sudo perf sched record -- sleep 5 2>/dev/null && sudo perf sched latency | head -15

$ bash /tmp/perf-security.sh

# 场景：⭐ 动态探针（无需重新编译/加载内核模块）
$ sudo perf probe -x /usr/bin/myapp --add 'main'                # ⭐ 对已 strip 也行（若 has 符号）

$ sudo perf probe -x /usr/bin/myapp --add 'myfunc %s' args_s:64 # 字符串参数
$ perf probe -x /usr/bin/myapp -l | head                        # ⭐ 列出可探测点
$ sudo perf record -e probe_myapp:main -a sleep 5
$ sudo perf probe --del '*'

# 场景：⭐ 列出所有可用事件
$ perf list | head -40
$ perf list | grep -iE 'cache|branch|stall|tlb' | head -20
$ perf list sw | head -20        # 软件事件
$ perf list cache | head -20     # 缓存事件
$ perf list tracepoint | head -20   # 跟踪点
$ perf list 'sched:*' | head -20

# 场景：🧪 完整性能分析流程（推荐顺序）
$ cat > /tmp/perf-workflow.sh <<'SH'
#!/bin/bash
set -uo pipefail
cmd=$1; shift

echo "############ 性能分析流程 ############"

echo "=== 1. 整体计数器（先看宏观指标）==="
perf stat -d "$cmd" "$@" 2>&1 | tail -25
echo "⭐ 关注：IPC、cache-misses、branch-misses 的比例"

echo
echo "=== 2. 采样热点（找耗时最多的函数）==="
perf record -g -F 999 -o /tmp/p.data "$cmd" "$@" 2>/dev/null
echo "--- Top 20 热点 ---"
perf report -i /tmp/p.data --stdio --sort=symbol -g 2>/dev/null | grep -E '^\s+[0-9]+\.[0-9]+%' | head -20

echo
echo "=== 3. 指令级热点（定位到具体代码行）==="
perf annotate -i /tmp/p.data --stdio 2>/dev/null | head -40

echo
echo "=== 4. 调度延迟（看是否有等待）==="
perf sched record -o /tmp/s.data "$cmd" "$@" >/dev/null 2>&1
perf sched latency -i /tmp/s.data 2>/dev/null | head -15

rm -f /tmp/p.data /tmp/s.data
SH
$ bash /tmp/perf-workflow.sh /usr/bin/sha256sum /dev/urandom 2>/dev/null | head -60
```

#### 输出解读
`perf stat` 的关键指标 ⭐⭐：

| 指标 | 含义 | 健康值 |
|------|------|--------|
| `task-clock` | CPU 时间 | — |
| `context-switches` | 上下文切换次数 | 越少越好 ⭐ |
| `page-faults` | 缺页 | 少 ⭐ |
| `cycles` / `instructions` | 周期数 / 指令数 | — |
| **`insn per cycle`（IPC）** | **每周期指令数** | **> 1 好；< 0.5 说明 CPU 在等** ⭐⭐ |
| `branch-misses` | 分支预测失败率 | **< 1% 好** ⭐ |
| `cache-misses` | 缓存未命中率 | 越低越好 ⭐ |

`perf report` 的输出 ⭐：
```
    45.23%  app  libc.so.6   [.] memcpy
    22.11%  app  app         [.] process_data
    10.34%  app  [kernel]    [k] copy_user_enhanced_fast_string
```
⭐ **前几行就是性能瓶颈**。

#### 🔐 perf 的安全意义
| 用途 | 说明 |
|------|------|
| 找挖矿进程 | CPU 占用异常高的进程 ⭐ |
| 找异常系统调用 | `perf trace --summary` 看 syscall 分布 ⭐ |
| 无侵入式追踪 | **不需要改二进制或重启服务** ⭐⭐ |
| **本身是攻击面** | `perf_event_open` 有过多个 CVE（提权） 🔐⚠️ |
| `perf_event_paranoid` | **应设为 2 或 3**（限制非特权用户） 🔐⭐ |

#### 常见坑
- ⚠️⚠️ **`perf_event_paranoid` 默认较高时会限制采样**（`perf record` 报 `Permission denied`）⭐⭐。
- ⚠️⚠️ **采样需要 root 或降 `perf_event_paranoid`**，而这**降低了安全性**（`perf_event_open` 曾是提权途径）🔐⭐⭐。
- ⚠️ **需要内核调试符号才能显示内核函数名**（`[k]` 后的名字），否则显示地址 ⭐：
  ```bash
  $ sudo dnf debuginfo-install kernel 2>/dev/null
  $ sudo apt install linux-image-$(uname -r)-dbgsym 2>/dev/null
  ```
- ⚠️ **`--call-graph dwarf` 会显著增加开销**（几倍），生产慎用 ⭐⭐。
- ⚠️ **采样是概率性的**（`-F` 频率低会漏热点），关键路径可提高频率 ⭐。
- ⚠️ **容器里 `perf` 通常受限**（需 `CAP_PERFMON`/`CAP_SYS_ADMIN` 与 `--privileged`）⭐。
- ⚠️ **虚拟机的 PMU 可能不可用**（计数器是被虚拟化的，不准）⭐。
- **`perf top` 适合快速定位，`record`+`report` 适合深入分析** ⭐⭐。
- **`perf trace` 比 `strace` 开销低得多**（eBPF/内核内过滤）⭐⭐。
- **`perf annotate` 能直接定位到指令**（比只看函数更细）⭐⭐。

`ftrace` · `bpftrace` · `sysdig` · `valgrind --tool=callgrind` · `gprof` · `perf-tools`

### valgrind — 内存与竞态检测

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：非 POSIX

```bash
valgrind [工具选项] 程序 [程序参数]
```

| 工具 | 作用 |
|------|------|
| `memcheck`（默认） | **内存错误检测** ⭐⭐ |
| `helgrind` | **线程错误（数据竞争）** ⭐⭐ |
| `drd` | 数据竞争检测 ⭐ |
| `callgrind` | **性能剖析（调用图）** ⭐⭐ |
| `cachegrind` | 缓存与分支预测模拟 ⭐ |
| `massif` | **堆内存剖析** ⭐⭐ |
| `exp-sgcheck` | 栈/全局数组越界（已废弃） |
| `--tool=none` | 只做加载（性能基线）⭐ |

| 通用选项 | 含义 |
|----------|------|

#### 输出解读
`memcheck` 的错误类型 ⭐⭐：

| 错误 | 含义 |
|------|------|
| `Invalid write of size N` | **写越界**（堆/栈溢出） ⭐⭐ |
| `Invalid read of size N` | **读越界**（含 use-after-free） ⭐⭐ |
| `Conditional jump depends on uninitialised value` | **使用未初始化变量** ⭐⭐ |
| `Use of uninitialised value` | 同上 |
| `Invalid free()` / `double free` | 重复释放 / 释放非法指针 ⭐ |
| `Mismatched free() / delete` | C/C++ 混用 ⭐ |
| `Syscall param ... points to unaddressable byte(s)` | 传给系统调用的指针非法 ⭐ |

**泄漏类型** ⭐⭐：

| 类型 | 含义 | 严重性 |
|------|------|--------|
| `definitely lost` | **确定泄漏**（指针丢失） | 高 ⭐⭐ |
| `indirectly lost` | 间接泄漏（被泄漏的结构引用） | 高 ⭐ |
| `possibly lost` | 可能泄漏（指针在中间位置） | 中 ⭐ |
| `still reachable` | 仍可达（如全局缓存） | 低（通常可忽略）⭐ |

#### 常见坑
- ⚠️⚠️ **`valgrind` 会显著拖慢程序**（memcheck 10–50 倍，helgrind 50–200 倍）。**不要在生产用** ⭐⭐。
- ⚠️⚠️ **必须 `-g` 编译**才能看到源码行号；**`-O2` 会导致行号错位**（用 `-O0`/`-Og`）⭐⭐。
- ⚠️ **`valgrind` 不捕获所有错误**（栈上的非法访问常检测不到，因为栈内存属于进程）⭐。
- ⚠️ **第三方库会产生大量噪音**（用 `--suppressions` 过滤）⭐。
- ⚠️ **`still reachable` 通常不是 bug**（全局缓存、单例）⭐。
- ⚠️ **多线程程序的 memcheck 结果可能不稳定**（用 helgrind/drd 专门查竞态）⭐。
- ⚠️ **容器里 `valgrind` 可能因 seccomp 或缺少 `CAP_SYS_PTRACE` 而失败** ⭐。
- ⚠️ **`valgrind` 与 `-fsanitize=address` 是替代关系**——**ASan 更快（2x 开销）**，日常开发优先 ASan，valgrind 用于 ASan 无法覆盖的场景 ⭐⭐。
- **`--error-exitcode=1` 是 CI 门禁的关键参数** ⭐⭐。
- **`--track-origins=yes` 会显著变慢但能定位未初始化值的来源** ⭐⭐。

#### 相关命令
`gcc -fsanitize=address` · `gdb` · `perf` · `callgrind_annotate` · `kcachegrind` · `heaptrack`

### bpftrace / sysdig — 动态追踪

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：Linux 特有（eBPF）

> 完整的 `sysdig` 与 `auditd` 对比见 [`12-安全与审计.md`](12-安全与审计.md#sysdig--bpftrace--内核级运行时审计)。这里聚焦**开发调试**用途。

```bash
bpftrace -e '程序' [选项]
bpftrace 文件.bt
sysdig [选项] [过滤表达式]
```

| bpftrace 常用探针 | 含义 |
|-------------------|------|
| `tracepoint:syscalls:sys_enter_*` | 系统调用入口 ⭐ |
| `kprobe:函数名` / `kretprobe:函数名` | 内核函数入口/返回 ⭐ |
| `uprobe:可执行文件:函数` | 用户态函数 ⭐⭐ |
| `profile:hz:99` | 定时采样（性能剖析） ⭐ |
| `interval:s:N` | 每 N 秒 ⭐ |
| `BEGIN` / `END` | 开始/结束 ⭐ |

| bpftrace 常用函数 | 含义 |
|-------------------|------|
| `printf()` | 输出 ⭐ |
| `@map[key] = count()/sum()/hist()` | 聚合 ⭐⭐ |
| `str(args->filename)` | 读字符串参数 ⭐ |
| `strftime()` / `nsecs` | 时间 ⭐ |
| `kstack` / `ustack` | **内核/用户栈** ⭐⭐ |
| `pid` / `tid` / `comm` / `uid` | 进程信息 ⭐ |
| `ntop()` / `bswap()` | 网络地址转换 ⭐ |

```bash
# 场景：⭐⭐ 列探针与检查环境
$ sudo bpftrace -l 'tracepoint:syscalls:sys_enter_*' | head -10
$ sudo bpftrace -l 'uprobe:/bin/bash:*' | head -10
$ sudo bpftrace -l 'kprobe:tcp_*' | head
$ bpftrace --info | head -20
$ sudo bpftrace -e 'BEGIN { printf("bpftrace 可用\n"); exit(); }'

# 场景：⭐⭐ 追踪函数耗时（性能剖析）
$ sudo bpftrace -e '
tracepoint:syscalls:sys_enter_openat { @start[tid] = nsecs; }
tracepoint:syscalls:sys_exit_openat /@start[tid]/ {
  $d = (nsecs - @start[tid]) / 1000;
  if ($d > 1000) {
    printf("%s 打开 %s 耗时 %d us\n", comm, str(retval), $d);
  }
  delete(@start[tid]);
}'
```

#### 输出解读
| 元素 | 含义 |
|------|------|
| `@map[key]` | 聚合映射（`count()`/`sum()`/`hist()`/`avg()`） ⭐⭐ |
| `@start[tid]` | 按线程 ID 记录起始时间（配对 enter/exit） ⭐ |
| `kstack` / `ustack` | 内核/用户栈回溯 ⭐⭐ |
| `hist()` | 直方图（直觉看出分布） ⭐ |
| `exit()` | 结束脚本 ⭐ |
| `/条件/` | 探针过滤 ⭐ |

#### 常见坑
- ⚠️⚠️ **需要 root 与内核支持（`CONFIG_BPF`、`CONFIG_KPROBES`、`CONFIG_TRACEPOINTS`）** ⭐⭐。
- ⚠️⚠️ **`bpftrace` 语法严格**（括号、分号、类型转换），写错会报错退出 ⭐。
- ⚠️ **`unroll()` 有上限**（默认 20），遍历长参数数组要小心 ⭐。
- ⚠️ **map 会占内存**（用 `interval` 打印后 `clear()`）⭐。
- ⚠️ **`uprobe` 需要符号存在**（stripped 二进制只能按偏移探测）⭐。
- ⚠️ **内核升级后 `kprobe` 的函数名可能变了**（依赖具体内核版本）⭐。
- **`bpftrace` 不需要装内核模块**（纯 eBPF），比 `sysdig` 易部署 ⭐⭐。
- **`profile:hz:99` 是性能剖析的常用采样**（1% 开销）⭐。
- **`hist()` 输出直方图，比看平均数更能发现问题** ⭐⭐。

#### 相关命令
`sysdig` · `perf` · `strace` · `bcc` · `ftrace`

#### 常见坑
- ⚠️⚠️ **`git reset --hard` 会永久丢弃未提交的改动**（未跟踪文件不受影响但需注意）⭐⭐。
- ⚠️⚠️ **`git clean -fdx` 会删除所有未跟踪文件（含 `.env`、build 产物）** ⚠️⭐⭐：
  ```bash
  $ git clean -nd        # ⭐ 先 dry run
  $ git clean -fd        # 再执行
  ```
- ⚠️⚠️ **`git push --force` 会覆盖远端历史**（可能丢别人的提交）。**用 `--force-with-lease`** ⭐⭐：
  ```bash
  $ git push --force-with-lease        # ⭐ 若远端有新提交则拒绝
  ```
- ⚠️⚠️ **`git filter-repo`/`filter-branch` 改写历史后必须通知所有协作者重新 clone**，否则会「复活」敏感文件 ⭐⭐。
- ⚠️ **`#` 注释只在 `git commit` 的编辑器里生效**；`git log --grep` 用 `--grep='#123'` ⭐。
- ⚠️ **`git checkout -- <file>` 与 `git restore <file>` 都丢弃未暂存改动**（不可恢复）⭐⭐。

- **`git log -S` 是找「引入/删除某字符串」提交的神器** ⭐⭐。
- 🔐 **git 仓库是敏感信息泄露的重灾区**（`.env`、密钥、内部地址提交后永远留在历史里）⭐⭐。

### jq — JSON 处理

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：第三方工具（Go/C 实现）


| 选项 | 含义 |

#### 输出解读
`jq` 的退出码 ⭐：

| 码 | 含义 |
|----|------|
| `0` | 成功 |
| `1` | 上次输出为 `null`/`false`（配合 `-e`） ⭐ |
| `2` | 使用错误 |
| `3` | 编译错误 |
| `4` | 解析错误（JSON 非法） |
| `5` | `--argjson`/`--slurpfile` 的 JSON 非法 |

**`-e` 的用途**：把「过滤结果是否为空/假」变成 shell 可判断的条件 ⭐⭐：
```bash
$ git config --get user.name | jq -e 'length > 0' >/dev/null && echo "已配置"
$ curl -s api | jq -e '.status == "ok"' >/dev/null || echo "服务不健康"
```

**`//` 运算符**（替代默认值）⭐⭐：
```bash
$ echo '{"a":null,"b":0,"c":false,"d":""}' | jq -c '{a: (.a // 1), b: (.b // 1), c: (.c // 1), d: (.d // "x")}'
{"a":1,"b":0,"c":false,"d":""}
```
⚠️ **`//` 只对 `null` 与 `false` 生效**（`0` 和 `""` 是有效值）⭐。

#### 常见坑
- ⚠️⚠️ **不加 `-r` 时字符串带双引号**，直接喂给 shell 会出问题 ⭐⭐。
- ⚠️⚠️ **过滤器必须用单引号**（`'`），否则 shell 会展开 `$` 与反引号 ⭐⭐：
  ```bash
  $ jq ".name"      # ⚠️ shell 会尝试展开
  $ jq '.name'      # ✅
  ```
- ⚠️⚠️ **字符串插值用 `\(...)`**（不是 `$(...)`）⭐⭐。
- ⚠️⚠️ **`--arg` 是字符串，`--argjson` 是 JSON**。传数字用 `--argjson` 才能参与比较 ⭐⭐。
- ⚠️ **`.[]` 对 `null` 会报错**，用 `.[]?` 或先 `// []` ⭐：
  ```bash
  $ echo '{}' | jq -c '.items[]'                # 报错
  $ echo '{}' | jq -c '(.items // [])[]'        # ✅
  $ echo '{}' | jq -c '.items[]?'               # ✅
  ```
- ⚠️ **`select()` 在 `map()` 内部与外部行为不同** ⭐：
  ```bash
  $ jq -c '[.[] | select(.a>1)]'     # 过滤数组元素
  $ jq -c 'map(select(.a>1))'        # 等价
  ```
- ⚠️ **大文件用 `-s`（slurp）会全部读入内存**，用 `--stream` 或逐行处理 ⭐⭐。
- ⚠️ **`-s` 之后 `.[]` 是数组元素（不再是逐行）**，容易搞混 ⭐。
- ⚠️ **`@csv` 输出的字符串带引号**（CSV 规范），要无引号得自己拼 `"\(.a),\(.b)"` ⭐。
- ⚠️ **`jq` 的浮点精度**（IEEE 754），金额计算要小心 ⭐。
- **`jq -n` 不需要输入**（从 `null` 开始）⭐。
- **`jq 'paths'` 是探索未知 JSON 结构的好工具** ⭐⭐。

#### 常见坑
- ⚠️⚠️ **`bash -n` 只检查语法，不检查语义**（`bash -n` 通过不代表能跑）⭐⭐。
- ⚠️⚠️ **`shellcheck` 必须显式指定 shell**（否则按 `#!/bin/sh` 的 POSIX 规则检查，会产生假阳性）⭐⭐：
  ```bash
  $ shellcheck -s bash script.sh
  ```
- ⚠️⚠️ **`set -e` 有大量反直觉行为** ⭐⭐：
  - `cmd || true`、`if cmd`、`cmd && x` 中的失败**不会**触发退出
  - 管道只看最后一段（除非 `pipefail`）
  - 函数内的失败可能被「吞掉」
  - `$(...)` 里的失败不总是传播
  - **`set -e` 不是万能的错误处理**，关键步骤要显式检查
- ⚠️ **`set -u` 遇到未定义变量会报错**，包括 `${1}` 这类位置参数（用 `${1:-}`）⭐。
- ⚠️ **`IFS=$'\n\t'` 会改变分词行为**，可能让 `for x in $var` 的语义变化 ⭐。
- ⚠️ **`trap ... ERR` 在 `set -e` 下行为微妙**（子 shell 里的失败不一定触发）⭐。
- ⚠️ **`source` 与 `.` 会执行任意代码**（加载不可信的配置 = 任意代码执行）🔐⭐。
- ⚠️ **`eval` 几乎总是错的**（用数组或 `printf -v` 替代）🔐⭐。
- **`shellcheck --format=json` 便于 CI 集成** ⭐⭐。
- **In `shellcheck disable=SC2086` 注释可局部抑制** ⭐：
  ```bash
  # shellcheck disable=SC2086
  echo $intentionally_unquoted
  ```
- **`.shellcheckrc` 可配置项目级规则** ⭐。

### diff / patch — 补丁与差异

**常用度**：★★★★☆ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：`-y`、`--color`、`-r` 的组合 GNU 更丰富

> 完整说明见 [`02-文本处理.md`](02-文本处理.md#diff--比较文件差异) 与 [`02-文本处理.md`](02-文本处理.md#patch--应用补丁)。这里聚焦**开发工作流**。

```bash
diff [选项] 文件1 文件2
diff -r 目录1 目录2
patch [-p N] < 补丁文件
```

| diff 开发常用 | 含义 |
|---------------|------|
| `-u` | **统一格式（生成补丁的标准）** ⭐⭐ |
| `-r` | 递归比较目录 ⭐⭐ |
| `-N` | 缺失文件当空文件（生成「新建文件」的补丁） ⭐ |
| `-q` | 只报告是否有差异 ⭐ |
| `-w` / `-b` / `-B` | 忽略空白/空白数量/空行 ⭐ |
| `--brief` | 同 `-q` |
| `-x 模式` | 递归时排除 ⭐ |
| `--color=auto` | 着色 ⭐ |
| `-y` | 并排显示（人眼友好） ⭐ |
| `--label` | 自定义补丁里的文件名 ⭐ |

| patch 关键 | 含义 |
|------------|------|
| `-p N` | **去掉路径前 N 层** ⭐⭐ |
| `--dry-run` | **只测试能否应用** ⭐⭐ |
| `-R` | 反向应用（撤销） ⭐ |
| `-b` | 应用前备份（`.orig`） ⭐ |
| `--merge` | 冲突时合并 ⭐ |

#### 输出解读
**统一格式（`-u`）的补丁结构** ⭐⭐：
```
--- 旧文件\t时间戳
+++ 新文件\t时间戳
@@ -旧起始,旧行数 +新起始,新行数 @@
 上下文行（空格开头）
-被删除的行
+被新增的行
```

| 符号 | 含义 |
|------|------|
| `-` | 旧文件有、新文件无（删除） ⭐ |
| `+` | 新文件有、旧文件无（新增） ⭐ |
| ` `（空格） | 两边都有（上下文） ⭐ |
| `@@ -a,b +c,d @@` | 定位信息（旧文件第 a 行起 b 行 ↔ 新文件第 c 行起 d 行） ⭐⭐ |

**`-p` 层数的判断方法** ⭐⭐：
```
--- a/src/main.c        ← 去掉 1 层（a/）→ -p1
+++ b/src/main.c
--- src/main.c          ← 去掉 0 层 → -p0
+++ src/main.c
--- /home/user/proj/x.c ← 去掉 2 层 → -p2（若要相对 proj）
+++ /home/user/proj/x.c
```
⭐ **数 `---` 行里你想要保留部分之前的斜杠数**。

#### 常见坑
- ⚠️⚠️ **`diff` 默认格式（无 `-u`）不能直接给 `patch` 用**（可读性也差）。**生成补丁一律用 `-u`** ⭐⭐。
- ⚠️⚠️ **`diff` 的退出码：0 相同、1 有差异、2 出错**。`set -e` 下会因「有差异」中断，要 `|| true` ⭐⭐。
- ⚠️⚠️ **`patch` 应用失败会留下 `.rej` 与 `.orig`**，要清理 ⭐。
- ⚠️⚠️ **`-p` 层数写错是最常见的失败原因** ⭐⭐。
- ⚠️ **`patch` 默认会模糊匹配（跳过行）**，可能应用到错误位置。要严格用 `-F0` ⭐。
- ⚠️ **对含 CRLF 的文件打 UNIX 补丁会全军覆没** ⭐。
- ⚠️ **`diff -r` 对符号链接默认不跟随**（报 `Only in` 或比较链接目标）⭐。
- ⚠️ **`patch` 到已修改的文件上可能部分成功**（要检查是否有 `.rej`）⭐⭐。
- **生产环境优先用 `git apply`**（更严格、有 `--check`、支持 `--3way`）⭐⭐。
- **`diff -rN` 是生成完整目录补丁的标准组合**（`-N` 让新建文件也能工作）⭐。
- 🔐 **`diff` 是检测配置篡改与「新增后门文件」的有效手段**（配合基线）⭐⭐。

### tmux / screen — 终端复用

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：非 POSIX

> 完整说明见 [`04-进程与作业.md`](04-进程与作业.md#tmux--终端复用器) 与 [`04-进程与作业.md`](04-进程与作业.md#screen--终端复用器)。这里聚焦**开发工作流**。

```bash
tmux new -s 名字          # 新建命名会话
tmux new -d -s 名字 '命令'  # 后台新建并运行
tmux ls / tmux a -t 名字    # 列出 / 附加
tmux kill-session -t 名字
```

| tmux 快捷键（前缀 `Ctrl+b`） | 作用 |
|------------------------------|------|
| `d` | 脱离（任务继续跑） ⭐⭐ |
| `c` / `,` | 新建窗口 / 重命名 ⭐ |
| `%` / `"` | 垂直 / 水平分屏 ⭐⭐ |
| `方向键` | 切换 pane ⭐ |
| `z` | 当前 pane 最大化/还原 ⭐⭐ |
| `[` | 复制模式（可滚动/搜索） ⭐⭐ |
| `]` | 粘贴 |
| `x` | 关闭 pane |
| `&` | 关闭窗口 |
| `?` | 帮助 |
| `:` | 命令模式 ⭐ |
| `空格` | 切换布局 |

```bash
echo "=== 5. 所有用户的 tmux 会话 ==="
```

#### 输出解读
`tmux ls` 的输出 ⭐：
```
work: 3 windows (created Tue Sep 15 09:30:00 2026) (attached)
│     │         │                                   └─ 是否有人连着
│     │         └─ 创建时间
│     └─ 窗口数
└─ 会话名
```

**tmux 的三个层次** ⭐：
```
session（会话）  ← tmux ls 显示的单位
└── window（窗口）← 相当于「标签页」（Ctrl+b c 新建）
    └── pane（面板）← 分屏（Ctrl+b % 或 "）
```

**socket 位置与权限** ⭐⭐：
```bash
$ ls -ld /tmp/tmux-$(id -u)
drwx------ 2 alice alice 4096 ... /tmp/tmux-1000
```
⚠️ **权限 `700` 保证只有同 UID 能访问**（跨账号安全），但**同账号的任何终端都能 attach**（无密码）⭐⭐。

#### 🔐 安全要点
| 风险 | 说明 |
|------|------|
| **同 UID 可任意 attach** | 共享账号环境下他人可看到你的终端 ⭐⭐ |
| **会话记录敏感输出** | 密码、token、密钥会留在回滚缓冲区（`Ctrl+b [` 可翻阅）⭐⭐ |
| **遗留的活跃会话** | 攻击者 `tmux ls` 可能接管未锁定的 root shell ⭐⭐ |
| **socket 目录权限错误** | `777` 时其他 UID 也能访问 ⚠️⭐ |
| **tmux.conf 可执行命令** | `run-shell` 会在启动时执行 ⚠️⭐ |

**检查清单** ⭐⭐：
```bash
$ tmux ls                                    # 有哪些会话
$ tmux list-panes -a -F '#{session_name} #{pane_current_command}'   # 在跑什么
$ tmux capture-pane -t <session> -p | tail   # 最后输出（可能含敏感信息）
$ ls -ld /tmp/tmux-*                         # socket 权限
$ tmux lock-server                           # 锁定所有（应急）
$ cat ~/.tmux.conf                           # 有无 run-shell 🔐
```

#### 常见坑
- ⚠️⚠️ **`tmux a` 默认附加到最后一个会话**，多个会话时会搞错。**用 `-t 名字`** ⭐⭐。
- ⚠️⚠️ **同 UID 的任何人都能 attach 你的会话**（无密码）。**共享账号环境要加 `lock-session`** ⭐⭐。
- ⚠️⚠️ **在 tmux 里跑 GUI 或需要 `$DISPLAY` 的程序会失败** ⭐。
- ⚠️ **`Ctrl+b` 前缀与某些程序（emacs、readline）冲突**，可在配置里改 ⭐。
- ⚠️ **退出会话里最后一个 shell 会关闭窗口/会话**，要保留用 `Ctrl+b d` 脱离 ⭐。
- ⚠️ **`tmux kill-server` 会杀掉所有会话（含别人的，同 UID 下）** ⚠️⭐。
- ⚠️ **容器里可能没有 tmux**（用 `screen` 或 `abduco`/`dtach`）⭐。
- ⚠️ **`tmux` 在非交互 SSH 命令里（`ssh host tmux ls`）需要显式路径**（PATH 可能不含 `/usr/bin`）⭐。
- **`tmux send-keys` 后要 `sleep` 一点再 `capture-pane`**（否则抓不到输出）⭐。
- **`tmux -x N -y N` 固定尺寸让输出可复现**（自动化演示用）⭐。
- **`set -g mouse on` 让 tmux 更好用**（但要按住 Shift 才能用原生选择复制）⭐。

#### 相关命令
`screen` · `abduco`/`dtach` · `tmate` · `nohup` · `systemd-run --pty` · `zellij`

### python3 / perl — 通用脚本

**常用度**：★★★★★ ｜ **所属**：开发与调试 ｜ **POSIX/GNU 差异**：跨平台

```bash
python3 [选项] [脚本|命令] [参数...]
perl [选项] [-e '代码'] [文件] [参数...]
```

| python3 选项 | 含义 |
|--------------|------|
| `-c '代码'` | 执行一段代码 ⭐⭐ |
| `-m 模块` | 运行模块（`-m http.server`） ⭐⭐ |
| `-i` | 执行后进入交互 ⭐ |
| `-u` | **不缓冲输出（管道友好）** ⭐⭐ |
| `-W 选项` | 警告控制 |
| `-O` / `-OO` | 优化（去 docstring） |
| `-v` / `-V` | 版本 |
| `-X 选项` | 实现相关选项（`-X importtime`） ⭐ |
| `-` | 从 stdin 读脚本 ⭐ |
| `--version` | 版本 ⭐ |

#### 常见坑
- ⚠️⚠️ **Python 的 `-c` 里双引号与 shell 引号嵌套极易出错**。**用单引号包外层，内部用双引号** ⭐⭐：
  ```bash
  $ python3 -c 'print("hello")'          # ✅
  $ python3 -c "print('hello')"          # ⚠️ shell 会展开 $ 与 `
  ```

- ⚠️⚠️ **`pip install` 到系统 Python 有风险**（PEP 668 会拒绝，应遵守）⭐⭐。

  ```bash

  ```

- ⚠️ **`perl -i` 原地修改会破坏硬链接与符号链接**（`sed -i` 同理）⭐。
- ⚠️ **Python 的浮点与正则性能**不如 awk（大文件场景）⭐。
- **`python3 -m http.server` 默认监听 `0.0.0.0`**（暴露到网络）。**用 `--bind 127.0.0.1` 限制** 🔐⭐。

- **`perl` 的正则能力仍强于 Python 的内建（尤其 `\K`、递归等）** ⭐。

`ccache -s` 的关键指标 ⭐⭐：

| 指标 | 含义 |
|------|------|
| `Cacheable calls` | 可缓存的调用数 ⭐ |
| **`Hits`** | **缓存命中（直接复用，省去编译）** ⭐⭐ |
| `Direct` / `Preprocessed` | 直接命中 / 预处理后命中 ⭐ |
| `Misses` | 未命中（真正编译了） ⭐ |
| `Cache size / max` | 缓存占用 ⭐ |
| `Files in cache` | 缓存文件数 ⭐ |

⭐ **命中率 = Hits / (Hits + Misses)**。CI 上冷启动后应快速逼近高命中率。

`time` 输出的解读 ⭐⭐：

| 现象 | 结论 |
|------|------|
| `real >> user + sys` | **等 I/O、等锁、串行依赖**（如 make 依赖链） ⭐⭐ |
| `real ≈ user + sys` | CPU 密集且**并行度不足**（单线程瓶颈）⭐ |
| `user >> real` | **多线程并行有效**（用了多个核）⭐⭐ |
| `/usr/bin/time -v` 的 `Percent of CPU` | > 100% 说明多核并行 ⭐ |
| `Maximum resident set size` | 峰值内存（找内存暴涨）⭐ |

#### 常见坑
- ⚠️⚠️ **`time` 是 bash 内建保留字，`/usr/bin/time` 是程序**。`time -v` 会被 bash 解释成错误，必须 `/usr/bin/time -v` 或 `\time -v` ⭐⭐。
- ⚠️⚠️ **内建 `time` 输出走 stderr**，`time cmd > file` 时计时信息仍在终端 ⭐。
- ⚠️⚠️ **ccache 对「改了编译选项」的构建会全部 miss**（缓存键包含选项）⭐⭐：
  ```bash
  # ⭐ 关键：保持编译选项稳定；用 CCACHE_SLOPPINESS 宽松处理时间宏
  $ ls /tmp/ccache/ | head
  ```
- ⚠️ **ccache 对 `-g` 的调试信息包含路径**，路径变了会 miss（用 `hash_dir = false`）⭐。
- ⚠️ **ccache 不缓存链接阶段**（只缓存编译单元）⭐。
- ⚠️ **ccache 在 CI 上要持久化缓存目录**（否则每次都冷启动）⭐⭐：
  ```yaml
  # GitHub Actions 例子
  - uses: actions/cache@v4
    with:
      path: ~/.cache/ccache
      key: ccache-${{ hashFiles('**/*.c') }}
  ```
- ⚠️ **`ccache -C` 会清空全部缓存**（下次全量重编）⚠️。
- ⚠️ **`distcc` 会暴露源码给其他机器**（安全考虑）🔐⭐。
- **`real << user` 说明并行有效**；`real >>` 说明串行/等待 ⭐⭐。
- **`ninja` 默认比 `make` 快**，且 `-d stats` 能给构建阶段的统计 ⭐。

## 本分类自测

1. 编译一个带 `-g -Og` 的 C 程序，用 `gdb` 断在 `main` 上并打印所有局部变量。
2. 用 `-fsanitize=address` 编译一个有堆溢出的程序，读出 ASan 报告的溢出位置。
3. 用 `readelf`/`objdump` 手工判断一个二进制是否开启了 PIE、NX、Full RELRO 与 Canary。
4. 用 `nm` 与 `objdump` 找出某二进制里使用的危险函数（如 `strcpy`、`system`）。
5. 从崩溃日志里的 `+0x...` 偏移用 `addr2line` 定位到源码行（说明 PIE 时要不要减基址）。
6. 用 `valgrind --leak-check=full` 找出程序的内存泄漏点，并说明 `definitely lost` 与 `still reachable` 的区别。
7. 用 `perf stat` 与 `perf record -g` 分析一个 CPU 密集程序，指出热点函数并解释 IPC 的含义。
8. 用 `shellcheck` 找出一个脚本里的 3 个问题，并写出修复后的写法。
9. 用 `jq` 从一份 JSONL 日志里统计 Top 10 来源 IP 与平均响应字节数。
10. 用 `diff -urN` 生成两个目录的补丁，并在目标目录里用 `patch --dry-run` 验证后再应用。
