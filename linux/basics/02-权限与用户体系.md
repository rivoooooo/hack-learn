## 1. rwx 权限模型

```bash
$ ls -l /etc/passwd /etc/shadow /tmp /usr/bin/passwd
-rw-r--r-- 1 root root      2801 ... /etc/passwd
-rw-r----- 1 root shadow     1688 ... /etc/shadow
drwxrwxrwt 12 root root      4096 ... /tmp
-rwsr-xr-x 1 root root     68208 ... /usr/bin/passwd
```

第 1 列 10 个字符拆成 4 段：

```
-  rw-  r--  r--     ->  属主 rw-，属组 r--，其他人 r--
^  ^^^^^ ^^^^^ ^^^^^
|  属主   属组  其他
类型
```

### r / w / x 对「文件」和「目录」含义完全不同

| 权限 | 对文件 | 对目录 |
|------|--------|--------|
| `r` | 读取文件内容 | 列出目录内文件名（`ls`） |
| `w` | 修改文件内容 | 在目录内**创建/删除/改名**条目 |
| `x` | 执行该文件 | 进入目录、访问目录内的文件（`cd`、按路径访问） |

⚠️ **删一个文件由所在目录的 `w` 决定，与文件自身权限无关。** 所以 `/tmp` 给所有人 `w` 意味着别人能删你的临时文件——除非有 Sticky 位。

### 数字（八进制）表示

| 值 | 权限 | 值 | 权限 |
|----|------|----|------|
| 0 | `---` | 4 | `r--` |
| 1 | `--x` | 5 | `r-x` |
| 2 | `-w-` | 6 | `rw-` |
| 3 | `-wx` | 7 | `rwx` |

```bash
chmod 755 script.sh     # rwxr-xr-x
chmod 644 config.txt    # rw-r--r--
chmod 600 ~/.ssh/id_rsa # rw-------  私钥必须是 600，否则 ssh 拒绝使用
```

### 符号表示法

```bash
chmod u+x script.sh        # 属主加执行
chmod go-w file           # 属组和其他去掉写
chmod a+r file            # 所有人可读
chmod u=rw,g=r,o= file    # 精确赋值，o= 表示清空其他人权限
chmod -R g+w shared/      # 递归
chmod -R u+rwX dir/       # 大写 X：仅对目录和已有 x 位的文件加执行
```

💡 **`X` 与 `x` 的区别**：`chmod -R a+x` 会把所有普通文本文件也变成可执行的；`chmod -R a+X` 只给目录加 `x`，普通文件不动。递归授权时用 `X`。

⚠️ `chmod -R 777 /path` 是典型的错误操作：它把目录里**所有**文件变成任何人可读写执行，包含配置里的密钥、可被替换的脚本。远程服务若可触发执行，直接变成 RCE 通道。永远不要在生产里这么干。

## 2. 特殊权限位：SUID / SGID / Sticky

### 三个特殊位的含义

| 位 | 对文件 | 对目录 | 数字 |
|----|--------|--------|------|
| **SUID** (s) | 执行时**以文件属主身份**运行 | Linux 上无意义 | 4000 |
| **SGID** (s) | 执行时以文件属组身份运行 | 新建文件继承目录的属组 | 2000 |
| **Sticky** (t) | 无意义 | 目录内文件**只有属主/目录属主/root 能删** | 1000 |

### `ls -l` 里的显示规则

| 显示 | 含义 |
|------|------|
| `-rws------` | SUID 且属主有 `x` |
| `-rwS------` | SUID 但属主**没有** `x`（大写 S = 空转的标志位） |
| `drwxr-xr-t` | Sticky 且其他人有 `x` |
| `drwxr-xr-T` | Sticky 但其他人没有 `x` |

```bash
$ ls -l /usr/bin/passwd
-rwsr-xr-x 1 root root 68208 ... /usr/bin/passwd
#    ^ SUID：普通用户执行 passwd 时以 root 身份写入 /etc/shadow
```

### 🔐 安全视角：SUID 是提权第一入口

```bash
# 全盘查找 SUID 文件（取证 / 提权枚举必备）
$ find / -xdev -perm -4000 -type f 2>/dev/null

# 同时找 SUID 和 SGID
$ find / -xdev -type f \( -perm -4000 -o -perm -2000 \) 2>/dev/null -ls

# 找出属主是 root 的可写 SUID（极端危险）
$ find / -xdev -perm -4000 -type f -user root -writable 2>/dev/null
```

- `-perm -4000`：**至少**包含 4000 位（- 是「全部这些位都置位」），这里即「SUID 已置位」。
- `-perm 4000`：**恰好**等于 4000（无 `-`/`/` 前缀即精确匹配）。
- `-perm /4000`：**任意一位**匹配。

排查是否有人新增了 SUID（对比基线）：

```bash
$ find / -xdev -perm -4000 -type f -printf '%T@ %p\n' 2>/dev/null | sort -n | tail -20
```

到 [GTFOBins](https://gtfobins.github.io/) 查询某个 SUID 程序能否被滥用。经典例子：`nmap`、`find`、`vim`、`bash` 若带 SUID，基本等于直接 root。

⚠️ 即使程序本身无漏洞，**如果它加载了 LD_PRELOAD 或调用外部命令**，也可能被劫持。

### SGID 目录的实用场景

```bash
# 团队共享目录：新建文件自动继承 group
$ sudo chgrp devteam /srv/shared
$ sudo chmod 2775 /srv/shared     # 2 = SGID
$ sudo chmod g+s /srv/shared      # 等价写法
```

### Sticky 的典型场景

```bash
$ ls -ld /tmp
drwxrwxrwt 12 root root 4096 ... /tmp
#         ^ t = Sticky，因此别人不能删你的 /tmp 文件
```

## 3. 属主与属组

```bash
$ chown alice file.txt              # 改属主
$ chown alice:devteam file.txt      # 同时改属组
$ chown alice: file.txt             # 只改属主，属组跟随为 alice 的主组
$ chown :devteam file.txt           # 只改属组
$ chown -R alice:alice /home/alice  # 递归
$ chgrp devteam file.txt            # 只改属组

# ⚠️ -h 处理软链接自身而不是目标（默认跟随链接）
$ chown -h alice symlink
```

💡 符号链接的属主几乎无意义（权限判断看目标的），但 `chown` 默认会去改目标文件，可能误伤。加 `-h` 明确。

## 4. umask：新建文件的默认权限

新建文件的**默认权限**不是 `777`，而是「基准权限 & ~umask」。

| 类型 | 基准权限 |
|------|----------|
| 普通文件 | `666`（**永远不会有 x**，需要显式 `chmod +x`） |
| 目录 | `777` |

```bash
$ umask
0022                    # 默认值，常见于 root
$ umask -S
u=rwx,g=rx,o=rx

$ touch /tmp/f
$ mkdir /tmp/d
$ stat -c '%A %n' /tmp/f /tmp/d
-rw-r--r-- /tmp/f       # 666 & ~022 = 644
drwxr-xr-x /tmp/d       # 777 & ~022 = 755
```

### 更严格的 umask

```bash
$ umask 077             # 仅当前 shell 生效
$ touch /tmp/secret
$ stat -c '%A %n' /tmp/secret
-rw------- /tmp/secret
```

常被忽略的事实：**`umask` 影响的是新建文件，不会修改已存在的文件。** 排查「为什么我创建的文件别人能读」要先看 `umask`。

| umask | 新建文件 | 新建目录 | 场景 |
|-------|----------|----------|------|
| `022` | 644 | 755 | 默认 |
| `027` | 640 | 750 | 团队共享，其他用户隔离 |
| `077` | 600 | 700 | 个人机密环境 |

## 5. 用户与组

### 三个关键文件

| 文件 | 内容 | 格式 |
|------|------|------|
| `/etc/passwd` | 用户账号（**可读，无密码**） | `name:x:UID:GID:GECOS:home:shell` |
| `/etc/shadow` | 密码哈希（**仅 root 可读**） | `name:$6$salt$hash:lastchg:min:max:warn:inactive:expire` |
| `/etc/group` | 组定义 | `name:x:GID:member1,member2` |

```bash
$ getent passwd alice
alice:x:1000:1000:Alice:/home/alice:/bin/bash
#  ^用户名 ^ ^UID  ^GID  ^注释        ^家目录      ^登录 shell
```

`x` 是占位符，真实哈希在 `/etc/shadow`。第二个字段为空表示**无密码即可登录**（危险）；为 `!` 或 `*` 表示锁定。

### UID 范围约定

| 范围 | 用途 |
|------|------|
| `0` | root（**唯一**能提权到 0 的 UID；第二个 UID 为 0 的账号是后门信号） |
| `1–999` | 系统账号（服务运行用户） |
| `1000–65533` | 普通用户 |
| `65534` | `nobody`，无特权 |

🔐 **排查 UID=0 的后门账号**，这是应急响应的固定动作：

```bash
$ awk -F: '$3==0 {print $1}' /etc/passwd
root
```

🔐 **排查空密码账号**：

```bash
$ awk -F: '($2=="" || $2=="!") {print $1, $2}' /etc/shadow
```

### 用户管理命令

```bash
# 创建（-m 建家目录，-s 指定 shell，-G 附加组）
$ sudo useradd -m -s /bin/bash -G sudo,docker alice
$ sudo passwd alice                    # 交互设密码
$ echo 'alice:Str0ngP@ss' | sudo chpasswd   # 非交互

# 修改
$ sudo usermod -aG docker alice        # ⚠️ 忘了 -a = 覆盖所有附加组！
$ sudo usermod -L alice                # 锁定（shadow 前加 !）
$ sudo usermod -U alice                # 解锁
$ sudo usermod -s /usr/sbin/nologin alice  # 禁止登录 shell

# 删除（-r 同时删家目录和邮件池）
$ sudo userdel -r alice

# 组
$ sudo groupadd devteam
$ sudo gpasswd -a alice devteam        # 加入组
$ sudo gpasswd -d alice devteam        # 移出组
$ sudo groupdel devteam

# 查看
$ id alice                             # uid/gid/所有组
$ groups alice
$ getent group devteam
```

⚠️ `usermod -aG` 的 `-a`（append）漏掉会把用户从其他附加组里踢出去，可能直接导致 sudo 失效。

⚠️ `userdel` 不加 `-r` 会留下家目录和 `/var/spool/mail/alice`，UID 复用时会继承旧文件属主，是隐患。

### 查看当前身份与登录

```bash
$ whoami              # 当前有效用户名
$ id                  # 完整身份
$ who                 # 当前登录会话
$ w                   # 登录用户 + 正在执行的命令
$ last -n 10          # 登录历史（读 /var/log/wtmp）
$ lastb -n 10         # 失败登录（读 /var/log/btmp）🔐
$ lastlog             # 每个用户最后一次登录
```

## 6. su 与 sudo

### su：切换用户

```bash
$ su - alice          # ⭐ 加 - 表示「模拟完整登录」：加载目标用户环境
$ su alice            # 不加 -：只换身份，环境变量多数保持为原用户
$ su -                # 切到 root
$ sudo su -           # 常见组合，但更推荐 sudo -i
```

| 写法 | 环境变量 | 家目录 |
|------|----------|--------|
| `su alice` | 保持原用户 | 保持原目录 |
| `su - alice` | 加载 alice 的 | 切到 alice 的家目录 |

💡 只有 `su -` 才会重新走一遍 shell 启动配置（见 [`05-环境变量与Shell启动过程.md`](05-环境变量与Shell启动过程.md)），所以 PATH 差异导致的「命令找不到」通常是你忘了 `-`。

### sudo：按策略以他人身份执行

```bash
$ sudo command                   # 以 root 执行
$ sudo -u postgres psql          # 以指定用户执行
$ sudo -i                        # 启动 root 的登录 shell
$ sudo -s                        # 启动 root shell（保留当前环境）
$ sudo -l                        # 🔐 列出当前用户被允许的命令（提权枚举第一步）
$ sudo -k                        # 清除缓存的凭证
$ sudo -n command                # 非交互，若无免密则直接报错（脚本里有用）
```

Sudo 的授权规则在 `/etc/sudoers`（用 `visudo` 编辑，它会做语法检查）。

```
# 格式： 用户  主机=(可切换到的用户:组)  命令 [NOPASSWD:]
alice   ALL=(ALL:ALL) ALL
%devteam ALL=(ALL) NOPASSWD: /usr/bin/systemctl restart nginx
```

⚠️ **绝不要直接 `vim /etc/sudoers`**。语法错误会让所有 sudo 失效，可能永久锁死在系统外。用 `visudo`，它在保存前校验，出错会拒绝写入。

🔐 **`sudo -l` 输出里的三类高价值目标**：

1. `NOPASSWD: /some/binary` → 查 GTFOBins，多数可逃逸成 root。
2. 通配符如 `/usr/bin/cat /etc/*` → 可用 `../` 或参数注入绕过。
3. 可编辑被 sudo 调用的脚本 → 直接改内容，等下个用户执行。

### sudo 与 su 的日志

```bash
$ journalctl -t sudo -n 20            # sudo 调用记录
$ sudo grep -i 'sudo' /var/log/auth.log   # Debian 系
$ sudo grep -i 'sudo' /var/log/secure     # RHEL 系
$ sudo ausearch -m USER_CMD -ts recent    # auditd 视角 🔐
```

## 7. ACL：比 rwx 更细的访问控制

rwx 只能分三类主体，ACL（Access Control List，访问控制列表）可以给**单个用户/组**授权。

```bash
# 查看
$ getfacl /srv/shared
# file: srv/shared
# owner: root
# group: devteam
user::rwx
group::rwx
other::---
```

```bash
# 给单个用户加权限
$ sudo setfacl -m u:bob:rx /srv/shared
$ sudo setfacl -m u:bob:rw file.txt

# 给组加权限
$ sudo setfacl -m g:audit:r /var/log/app.log

# 递归（-R），并设置默认 ACL 让新文件继承（-d）
$ sudo setfacl -R -m u:bob:rx /srv/shared
$ sudo setfacl -R -d -m u:bob:rx /srv/shared

# 删除某条目
$ sudo setfacl -x u:bob /srv/shared

# 清空所有 ACL
$ sudo setfacl -b /srv/shared
```

设置过 ACL 的文件在 `ls -l` 权限末尾会多一个 `+`：

```bash
$ ls -l file.txt
-rw-rw-r--+ 1 root root ... file.txt
#         ^ 有扩展 ACL，必须用 getfacl 查看详情
```

💡 备份 ACL 与恢复（`-R` 递归）：

```bash
$ getfacl -R /srv/shared > /tmp/acl.bak
$ setfacl --restore=/tmp/acl.bak
```

⚠️ 用 `cp -a` 或 `rsync -A` 才能保留 ACL；普通 `cp` 会丢失。

## 8. 文件属性：chattr / lsattr

ext4/xfs 上除权限位外还有**文件属性**。

```bash
$ lsattr /etc/passwd
----------------e----- /etc/passwd

$ sudo chattr +i /etc/passwd      # i = immutable，不可修改/删除/改名
$ sudo chattr +a /var/log/app.log # a = append only，只能追加
$ sudo chattr -i /etc/passwd
```

🔐 `+i` 是防篡改的硬手段：即使 root 也必须先 `chattr -i` 才能改。恶意软件也用这招锁住自己。排查时：

```bash
$ sudo lsattr -R / 2>/dev/null | grep -E '^....i|^....a'
```

⚠️ immutable 文件连 `rm -rf` 都删不掉，且报错信息可能误导（提示 permission denied 而不是「被锁定」）。删不掉时先想 `lsattr`。

## 9. 用户登录时的身份切换链路

```
内核启动 → init/systemd 以 root 运行
  → getty / sshd 展示登录提示
  → login 程序验证 /etc/passwd + /etc/shadow
  → 取出该用户的 UID/GID 与 shell
  → 以该 UID/GID 启动 shell（真实 UID = 有效 UID = 该用户）
  → SUID 程序执行时，有效 UID 变为文件属主（真实 UID 不变）
```

| 概念 | 说明 |
|------|------|
| real UID | 你是谁 |
| effective UID | 权限判断用哪个身份（SUID 时被提升） |
| saved UID | 用于在特权与非特权间来回切 |

```bash
$ id -r    # 真实 UID
$ id -u    # 有效 UID
```

这就是 `passwd` 能改 `/etc/shadow`（只有 root 可写）的原因：它以 root 的有效 UID 运行，但真实 UID 仍是你。这也是 SUID 程序必须极端小心的原因——任何被它调用的外部程序都继承了 root 身份。
