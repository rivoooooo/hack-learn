## 1. 进程是什么

进程 = 正在运行的程序实例，内核为它维护：

| 组成 | 内容 |
|------|------|
| PID | 进程 ID，唯一 |
| PPID | 父进程 ID |
| UID/GID | 真实与有效身份（见 [`02-权限与用户体系.md`](02-权限与用户体系.md)） |
| 地址空间 | 代码段、数据段、堆、栈、共享库映射 |
| 文件描述符表 | 打开的文件、socket，见 `/proc/<pid>/fd/` |
| 状态 | R/S/D/T/Z 等 |
| 信号处理器 | 对每个信号如何响应 |

### parent / child 关系

```
PID 1 (systemd / init)
├── sshd
│   └── bash  ← 你的登录 shell
│       └── vim
└── dockerd
    └── containerd-shim → 容器内进程
```

```bash
$ pstree -p 1 | head
$ ps -o pid,ppid,user,stat,cmd -p $$
```

**孤儿进程（orphan）**：父进程先退出，子进程被 PID 1 收养（reparent）。PPID 变成 1 是正常现象。

**僵尸进程（zombie）**：子进程已退出，但父进程从未调用 `wait()` 回收它的退出状态，进程表项残留。状态显示为 `Z`，**不占内存只占 PID**。杀掉僵尸无效，必须让父进程回收（或杀掉父进程）。

```bash
$ ps aux | awk '$8 ~ /Z/ {print}'
$ ps -eo pid,ppid,stat,cmd | awk '$3=="Z"'
```

## 2. 进程状态

`ps` 的 `STAT` 列（BSD 风格）由多个字符组合而成：

| 字符 | 含义 |
|------|------|
| `R` | Running / Runnable，在运行或就绪队列中 |
| `S` | Sleeping，可中断睡眠（等事件，如等待输入） |
| `D` | Disk sleep，不可中断睡眠（等 I/O） |
| `T` | Stopped，被信号暂停（`Ctrl+Z`） |
| `t` | Tracing stop，被调试器停止 |
| `Z` | Zombie |
| `I` | Idle 内核线程 |
| `<` | 高优先级（nice 为负） |
| `N` | 低优先级（nice 为正） |
| `s` | 会话首进程（session leader） |
| `l` | 多线程（`l` 是 LWP） |
| `+` | 前台进程组 |
| `L` | 有页面被锁定到内存（用于实时/内核） |

```bash
$ ps -eo pid,ppid,stat,ni,pcpu,pmem,etime,cmd --sort=-pcpu | head
```

⚠️ **`D` 状态进程杀不掉。** `kill -9` 也无效，因为它不响应信号，只能等 I/O 完成（或硬件/网络存储恢复）。生产事故里「进程卡在 D」通常意味着 NFS / iSCSI / 磁盘故障。

### 怎么判断是 CPU 密集还是 I/O 密集

```bash
$ top -bn1 | head -5
$ iostat -xz 1 -c 3      # iostat 属于 sysstat 包
$ vmstat 1 5
```

`vmstat` 关键列：`r` 运行队列长度（> CPU 核数说明 CPU 饱和）、`b` 阻塞进程数（>0 说明 I/O 等待）、`si/so` 换页量（持续非 0 说明内存不足在换页）。

## 3. 优先级：nice 与实时调度

Linux 用 CFS（Completely Fair Scheduler，完全公平调度器）分配 CPU。优先级由两层表达：

| 层 | 范围 | 说明 |
|----|------|------|
| nice 值 | `-20`（最高）~ `19`（最低），默认 `0` | 普通用户只能**调高** nice（降低优先级） |
| 调度策略 | `SCHED_OTHER`（默认）、`SCHED_FIFO`、`SCHED_RR`、`SCHED_IDLE`、`SCHED_BATCH` | 实时策略需 CAP_SYS_NICE |

```bash
$ nice -n 10 ./long_task.sh          # 以 nice=10 启动
$ renice -n 5 -p 1234                # 改运行中进程
$ sudo renice -n -5 -p 1234          # 提优先级需 root
$ chrt -f 10 ./realtime_task         # SCHED_FIFO，优先级 10
$ ionice -c2 -n7 -p 1234             # I/O 优先级，best-effort 最低
```

💡 大文件拷贝或备份用 `nice -n 19 ionice -c3` 几乎不影响线上服务（`-c3` 是 idle 级别）。

## 4. 信号

信号是内核投递给进程的**异步通知**，本质是一个小整数。

### 必须记住的信号

| 号码 | 名称 | 默认动作 | 能否捕获 | 说明 |
|------|------|----------|----------|------|
| 1 | `SIGHUP` | 终止 | ✅ | 终端断开；常被守护进程重载配置 |
| 2 | `SIGINT` | 终止 | ✅ | `Ctrl+C` |
| 3 | `SIGQUIT` | 终止 + core dump | ✅ | `Ctrl+\` |
| 9 | `SIGKILL` | 终止 | ❌ | **不可捕获、不可忽略**，最后手段 |
| 15 | `SIGTERM` | 终止 | ✅ | `kill` 的默认信号，优雅退出首选 |
| 18 | `SIGCONT` | 继续 | ✅ | 恢复被暂停的进程 |
| 19 | `SIGSTOP` | 暂停 | ❌ | 不可捕获 |
| 20 | `SIGTSTP` | 暂停 | ✅ | `Ctrl+Z` |
| 10 | `SIGUSR1` | 终止 | ✅ | 用户自定义（很多服务用它做日志轮转） |
| 12 | `SIGUSR2` | 终止 | ✅ | 用户自定义 |
| 11 | `SIGSEGV` | 终止 + core dump | ❌ | 段错误，程序 bug |
| 6 | `SIGABRT` | 终止 + core dump | ✅ | `abort()` |

⚠️ 不同架构上 `SIGUSR1/USR2` 号码不同（x86 是 10/12，MIPS 是 16/17）。**脚本里永远用名字 `-USR1` 而不是数字。**

```bash
$ kill -l | head -20       # 列出所有信号
$ kill -l 9                # 数字转名字
$ kill TERM 1234           # 用名字（推荐）
```

### 发送信号

```bash
$ kill 1234                # 默认 SIGTERM
$ kill -9 1234             # SIGKILL
$ kill -TERM 1234 5678     # 多个 PID
$ kill %1                  # 作业号（见第 6 节）

$ pkill nginx              # 按进程名（⚠️ 模糊匹配，可能误杀）
$ pkill -f 'python.*worker' # 按完整命令行
$ pkill -u alice           # 按用户
$ killall nginx            # 按精确名字

# 先看会杀谁，再真杀（-e 显示、不加即为 dry run）
$ pkill -f -e 'pattern'
```

⚠️ `pkill -f nginx` 会匹配**命令行任意位置**含 nginx 的进程，包括 `grep nginx`、`vim /etc/nginx.conf`。先用 `pgrep -af nginx` 确认名单。

⚠️ `kill -9` 的风险：进程无法清理临时文件、无法 flush 缓冲区、无法释放锁。对数据库、文件写入类进程可能造成数据损坏。**先 `kill -TERM`，等 5–10 秒，再考虑 `-9`。**

### 常见「优雅终止」实践

```bash
# 推荐模式：TERM → 等待 → 仍在则 KILL
$ kill -TERM 1234 && sleep 5 && (kill -0 1234 2>/dev/null && kill -9 1234 || true)
```

`kill -0 PID` 不发送信号，只做存在性检查，返回 0 表示进程存在。

## 5. 守护进程与前台进程

**守护进程（daemon）**的特点：

1. 脱离控制终端（脱离 session）
2. 工作目录切到 `/`（避免占住挂载点）
3. 标准输入/输出/错误重定向到 `/dev/null` 或日志
4. 由 systemd / init 管理

```bash
# 检查进程是否关联终端（TT 列为 ? 说明无终端 = 守护进程）
$ ps -eo pid,tty,stat,cmd | awk '$2=="?"' | head
```

### 前台任务临时后台化

```bash
$ ./server
^Z                    # Ctrl+Z 暂停
[1]+  Stopped         ./server
$ bg                  # 转后台继续（收到 SIGCONT）
$ disown              # 从 shell 作业表移除，ssh 断开不受影响
```

## 6. 作业控制

| 符号 / 命令 | 作用 |
|-------------|------|
| `cmd &` | 直接后台运行 |
| `Ctrl+Z` | 暂停当前前台作业（SIGTSTP） |
| `Ctrl+C` | 终止当前前台作业（SIGINT） |
| `jobs` | 列出本 shell 的作业 |
| `jobs -l` | 带 PID |
| `fg %1` | 恢复到前台 |
| `bg %1` | 在后台继续 |
| `kill %1` | 按作业号发信号 |
| `%1` | 作业号引用（`%+` 当前作业、`%-` 上一个） |
| `disown -h %1` | 保留作业但不接收 SIGHUP |

```bash
$ sleep 300 &
[1] 45678
$ jobs -l
[1]+ 45678 Running                 sleep 300 &
$ fg %1
```

⚠️ **作业控制是 shell 内的概念**，只在**交互式 shell** 可用（脚本里默认关闭）。作业号也只在本 shell 内有效，换个终端 `jobs` 就空了。

⚠️ 用 `&` 后台运行的程序在 **shell 退出时会收到 SIGHUP 而被杀**（终端的会话结束）。要真正持久，用：

```bash
$ nohup ./server > server.log 2>&1 &
$ setsid ./server > server.log 2>&1 < /dev/null &
$ disown -a
$ screen -dmS name ./server       # 见 04-进程与作业.md
$ tmux new -d -s name './server'
```

## 7. 进程监控与定位

```bash
# 动态
$ top                    # 基础
$ htop                   # 带颜色、可鼠标（需安装）
$ top -o %MEM -u alice   # 按内存排序，只看某用户
$ top -H -p 1234         # 显示线程

# 静态快照
$ ps aux --sort=-%cpu | head
$ ps -eo pid,ppid,user,stat,%cpu,%mem,etime,cmd --sort=-%mem | head

# 该进程打开了哪些文件/socket（排查 "是谁占着 8080"）
$ sudo lsof -i :8080
$ sudo ss -tunlp | grep :8080
$ sudo fuser -v 8080/tcp

# 该进程在做哪些系统调用（卡住时用）
$ sudo strace -p 1234 -f -tt -T
$ sudo strace -c -p 1234          # 汇总统计
$ sudo timeout 5 strace -p 1234 2>&1 | tail -20

# 进程在等什么（找到对应的 file 描述符）
$ sudo cat /proc/1234/wchan; echo
$ sudo cat /proc/1234/stack 2>/dev/null
```

🔐 **排查可疑进程的固定套路**：

```bash
# 1. 找出无对应可执行文件的进程（恶意软件常删掉自己的二进制）
$ sudo ls -l /proc/*/exe 2>/dev/null | grep -i deleted

# 2. 找出可执行文件被替换/在 /tmp 运行的进程
$ sudo ls -l /proc/*/exe 2>/dev/null | grep -E '/tmp|/dev/shm'

# 3. 查看进程监听端口与已建立连接
$ sudo ss -tunlp
$ sudo ss -tunap state established

# 4. 从 /proc 恢复被删除的二进制
$ sudo cp /proc/1234/exe /tmp/evidence_binary
$ sha256sum /tmp/evidence_binary
```

## 8. cgroup 基础

**cgroup**（control group，控制组）是内核的**资源限制与统计**机制，也是容器隔离的两大支柱之一（另一个是 namespace）。

| 版本 | 挂载点 | 特点 |
|------|--------|------|
| v1 | `/sys/fs/cgroup/<controller>/` | 每个控制器独立层级，混乱 |
| v2 | `/sys/fs/cgroup/` | **统一层级**（unified hierarchy），现代发行版默认 |

### 控制器

| 控制器 | 限制什么 |
|--------|----------|
| `cpu` | CPU 带宽（`cpu.max`） |
| `cpuset` | 绑定到哪些核（`cpuset.cpus`） |
| `memory` | 内存上限（`memory.max`）、OOM 行为 |
| `io` | 块设备 I/O 带宽 |
| `pids` | 进程数上限（`pids.max`），防 fork bomb |
| `freezer` | 冻结/解冻一组进程 |

```bash
# 查看进程属于哪个 cgroup
$ cat /proc/self/cgroup
0::/user.slice/user-1000.slice/session-2.scope

# 查看 systemd 管理的资源
$ systemd-cgtop
$ systemd-cgls

# systemd 层面限制（写 unit 文件）
# [Service]
# MemoryMax=512M
# CPUQuota=50%
# TasksMax=100

# 临时给命令加限制（需 systemd-run）
$ systemd-run --user --scope -p MemoryMax=200M -p CPUQuota=30% ./heavy_task
```

🔐 **cgroup 的攻防意义**：

- `pids.max` 是防 **fork bomb** 的主要手段。传统 `ulimit -u` 只限制单用户进程数。
- 容器的隔离边界是 `namespace` + `cgroup` + `capability` + seccomp。逃逸通常来自其中之一配置不当（如 `--privileged`、挂载了 docker.sock）。
- 检查容器资源限制：`cat /sys/fs/cgroup/memory.max`。

```bash
# 查看当前 shell 的内存限制（cgroup v2）
$ cat /sys/fs/cgroup/memory.max
max            # max 表示无限制
```

## 9. OOM Killer

当系统内存耗尽，内核的 OOM Killer 会挑选一个进程杀掉以保住系统。

```bash
$ dmesg -T | grep -i 'killed process'
[Mon Sep 14 03:12:44 2026] Out of memory: Killed process 12345 (java) total-vm:8123456kB
```

谁被杀由 `oom_score` 决定（分越高越先被杀）：

```bash
$ cat /proc/1234/oom_score
$ cat /proc/1234/oom_score_adj      # 可调，-1000 表示永不被杀
$ echo -500 | sudo tee /proc/1234/oom_score_adj
```

💡 关键服务加 `OOMScoreAdjust=-500`（systemd unit 里）可以降低被杀概率，但这是缓解不是修复。根因是内存不足或内存泄漏。
