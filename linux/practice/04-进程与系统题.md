### 题 1 · ⭐ 列出系统上所有进程，并且要看**完整的命令行**（不截断）

<details><summary>答案</summary>

```bash
$ ps -ef
$ ps aux
```

两种风格的差别（**这是 `ps` 最容易踩的坑**）：

| 风格 | 写法 | 特点 |
|------|------|------|
| **UNIX 风格** | `ps -ef` | `-e` 所有进程，`-f` 完整格式 |
| **BSD 风格** | `ps aux` | `a` 所有终端上的进程，`u` 用户友好格式，`x` 包含无控制终端的进程 |

> ⚠️ **不能混用**：`ps -aux` 里那个 `-` 会让 `ps` 按 UNIX 风格解析，结果是"等于 `ps -a -u -x`"这种意外组合，GNU ps 会给警告 `Warning: bad syntax, perhaps a bogus '-'?`。要么 `ps -ef`，要么 `ps aux`。

**`ps aux` 输出字段**：

| 列 | 含义 |
|----|------|
| `USER` | 属主 |
| `PID` | 进程号 |
| `%CPU` / `%MEM` | 从进程启动至今的**平均**占用（**不是瞬时值**，看瞬时要用 `top`） |
| `VSZ` | 虚拟内存大小（含已映射但未使用的） |
| `RSS` | 常驻内存（**实际占的物理内存**，最该看的） |
| `STAT` | 状态码（见题 9） |
| `START` | 启动时间 |
| `TIME` | 累计消耗的 CPU 时间 |
| `COMMAND` | 命令（`ps aux` 会截断，见下） |

**完整命令行不截断**：`ps aux` 的 `COMMAND` 列会按终端宽度截断。想看全：

```bash
$ ps -efww                        # -ww 不限宽度
$ ps -eo pid,ppid,user,stat,args  # args 列给完整命令行
$ cat /proc/<PID>/cmdline | tr '\0' ' '; echo    # 最可靠的原始方式
```

</details>

### 题 2 · ⭐ 按 CPU 占用从高到低列出前 5 个进程

<details><summary>答案</summary>

```bash
$ ps aux --sort=-%cpu | head -6
USER       PID %CPU %MEM    VSZ   RSS TTY   STAT START   TIME COMMAND
root         1  0.1  0.0 168892 13204 ?     Ss   Sep14   1:23 /sbin/init
root       842  0.1  0.3 512340 41200 ?     Sl   Sep14   2:01 /usr/bin/containerd
...
```

`--sort=-%cpu` 里的 `-` 表示**降序**。`head -6` 是因为第一行是表头。

其它排序键：

```bash
$ ps aux --sort=-%mem | head -6      # 按内存
$ ps aux --sort=-rss  | head -6      # 按常驻内存（更准确）
$ ps aux --sort=start_time           # 按启动时间（找最近启动的）
```

> ⚠️ `ps` 的 `%CPU` 是**进程生命周期内的平均值**，不是"当前正在占多少"。一个已经跑了 3 天的进程，即使此刻 100% 占满 CPU，`%CPU` 也显示不出高值。**看瞬时 CPU 必须用 `top` / `htop`。**

用 `top` 的非交互模式取瞬时 TOP：

```bash
$ top -bn1 -o %CPU | head -12
```

`-b` 批处理模式（适合重定向到文件），`-n1` 只跑一轮。

</details>

### 题 3 · ⭐ 按内存占用从高到低列出前 5 个进程，并说明 `%MEM` 和 `RSS` 的区别

<details><summary>答案</summary>

```bash
$ ps aux --sort=-rss | head -6
USER       PID %CPU %MEM    VSZ    RSS STAT COMMAND
postgres  1024  0.0  8.4 812345 689432 Ssl  postgres: writer process
```

| 字段 | 含义 |
|------|------|
| `VSZ` | virtual set size，**虚拟内存**：进程地址空间总大小。含 malloc 但未触碰的内存、映射的文件、共享库。这个数字**通常很大但没有意义**（一个 `malloc(1GB)` 不碰的进程能显示 1GB VSZ） |
| `RSS` | resident set size，**常驻内存**：当前真的在物理内存里的页。这个才接近"这个进程占了多少内存" |
| `%MEM` | `RSS / 物理内存总量 × 100` |

**为什么两者能差很多**：

```bash
$ python3 -c 'x = bytearray(500*1024*1024); import time; time.sleep(60)' &
$ ps -o pid,vsz,rss,comm -p $!
    PID    VSZ    RSS COMMAND
  12345 523456    912 python3        # VSZ 500MB+，RSS 不到 1MB（还没写入过）
```

`bytearray(500*1024*1024)` 只是**保留了地址空间**，内核用写时复制 + 缺页机制，不写入就不分配物理页。

> ⚠️ **RSS 也有陷阱**：多个进程共享的内存（共享库、`fork` 后的 COW 页）会被**重复计算**在各自的 RSS 里。所以"所有进程 RSS 之和"通常**大于**实际物理内存使用量。想知道真实总量看 `free`/`/proc/meminfo`。

</details>

### 题 4 · ⭐ 找出所有名字里含 `nginx` 的进程的 PID

<details><summary>答案</summary>

```bash
$ pgrep -a nginx
1024 nginx: master process /usr/sbin/nginx
1090 nginx: worker process
1091 nginx: worker process

$ pgrep -x nginx           # -x 精确匹配进程名（不是整条命令行）
$ pgrep -c nginx           # 只输出数量
$ pgrep -u www-data nginx  # 只查某个用户的
```

**`pgrep` 默认只匹配"进程名"（`comm`，最多 15 字符）**，要匹配完整命令行加 `-f`：

```bash
$ pgrep -af 'nginx.*worker'
```

`pgrep` 的退出码：找到至少一个返回 `0`，一个都没找到返回 `1`。所以脚本里可以：

```bash
if pgrep -x nginx >/dev/null; then echo "在跑"; fi
```

### `pgrep` 和 `pidof` 的区别

| | `pgrep` | `pidof` |
|--|---------|---------|
| 匹配对象 | 进程名或（`-f`）命令行 | 进程名 |
| 输出 | 一行一个 PID | 一行、空格分隔 |
| 过滤能力 | 按用户、终端、父进程、时间等多种条件 | 基本没有 |
| 常用场景 | 脚本里做复杂筛选 | shell 里快速取 PID |

</details>

### 题 5 · ⭐ 以树形显示进程的父子关系

<details><summary>答案</summary>

```bash
$ pstree -p
systemd(1)─┬─NetworkManager(842)─┬─{NetworkManager}(872)
           ├─containerd(1044)───containerd-shim(2050)───nginx(2060)
           ├─sshd(1102)───sshd(3456)───bash(3460)───pstree(3500)
           └─systemd(2100)───(sd-pam)(2102)

$ ps -ef --forest            # 用 ps 实现，能同时看到完整命令行
$ pstree -p -u alice         # 只看某个用户
$ pstree -aps 3500           # 反向：只看某个进程的祖先链
```

`-p` 显示 PID。**看进程树是理解"这个进程是谁启动的"最快的办法**。

> 💡 `pstree -aps <PID>` 会打印从 PID 1 到该进程的**完整祖先链**，排查"这个服务是谁拉起来的"极有用。反过来，`ps -o ppid= -p <PID>` 只给你父 PID 一个数字。

</details>

### 题 6 · ⭐ 查看 PID 1234 的工作目录、可执行文件路径、以及它打开了哪些文件 🔐

<details><summary>答案</summary>

```bash
$ ls -l /proc/1234/cwd          # 工作目录
lrwxrwxrwx 1 root root 0 ... /proc/1234/cwd -> /var/lib/nginx

$ ls -l /proc/1234/exe          # 可执行文件
lrwxrwxrwx 1 root root 0 ... /proc/1234/exe -> /usr/sbin/nginx

$ cat /proc/1234/cmdline | tr '\0' ' '; echo
/usr/sbin/nginx -g daemon on;

$ ls -l /proc/1234/fd/          # 打开的所有文件描述符
lrwx------ 1 root root 64 ... 0 -> /dev/null
lrwx------ 1 root root 64 ... 1 -> /var/log/nginx/error.log
lrwx------ 1 root root 64 ... 3 -> socket:[23456]
lrwx------ 1 root root 64 ... 6 -> /var/lib/nginx/body/1/0 (deleted)

$ cat /proc/1234/environ | tr '\0' '\n' | grep -i pass   # 🔐 环境变量（常含机密）
DB_PASSWORD=hunter2
```

`/proc/<PID>/` 是内核暴露的"进程实时视图"，**不需要 `lsof`** 也能拿到大量信息：

| 路径 | 内容 |
|------|------|
| `cwd` | 当前工作目录（软链接） |
| `exe` | 可执行文件（软链接） |
| `root` | 进程看到的根目录（chroot 后能看到区别） |
| `cmdline` | 完整命令行，**NUL 分隔**（`tr '\0' ' '` 才可读） |
| `environ` | 环境变量，**NUL 分隔** |
| `fd/` | 打开的文件描述符 |
| `maps` | 内存映射（含加载的共享库） |
| `wchan` | 内核里阻塞在哪个函数（查 D 状态用） |
| `status` | UID/GID/内存/线程数等汇总 |
| `limits` | 该进程的 ulimit 值（**和 shell 的 `ulimit` 可能不同**） |
| `net/tcp` | 该进程所属网络命名空间里的连接 |

🔐 `(deleted)` 标记的含义很关键：文件已被删除但进程还持有 fd，**磁盘空间不会释放**，而且文件内容仍可从 `/proc/<PID>/fd/N` 读出。这是取证时的重点：

```bash
$ sudo ls -l /proc/*/fd/* 2>/dev/null | grep '(deleted)' | head
```

也可以拷出来：

```bash
$ sudo cp /proc/1234/fd/6 /tmp/recovered_file
```

🔐 **`/proc/<PID>/environ` 会泄露明文机密**（数据库密码、API token 常通过环境变量传入）。任何能读这个文件的用户（同 UID 或 root）都能拿到。这是"用环境变量传密钥"的固有风险。

</details>

### 题 7 · ⭐ `kill 1234` 和 `kill -9 1234` 有什么区别？什么时候用哪个？

<details><summary>答案</summary>

| 命令 | 信号 | 行为 |
|------|------|------|
| `kill 1234` | SIGTERM (15) | **可被捕获**。进程收到后可以保存数据、关闭连接、清理临时文件再退出。这是"请你自己退出" |
| `kill -9 1234` | SIGKILL (9) | **不可捕获、不可忽略**。内核直接终止进程，进程没有任何机会做清理 |

**推荐的处置顺序**：

```bash
$ kill 1234                      # 1. 先礼貌请它走
$ sleep 2                        # 2. 给它时间
$ kill -0 1234 2>/dev/null && kill -9 1234    # 3. 还在就强杀
```

`kill -0 PID` 是**不发送信号**的存在性检查：进程存在返回 0，不存在返回非 0。这是脚本里判断进程是否还活着的标准写法。

**`kill -9` 的代价**：

- 未写完的文件（缓冲区的数据）丢失
- 临时文件、锁文件残留，可能导致下次启动失败（比如 `pid` 文件还在、socket 文件没删）
- 数据库可能在恢复时进入"崩溃恢复"流程（虽然现代数据库都有 WAL 保护，但恢复慢）
- **网络连接会发 RST 而不是 FIN**，对端可能报错而不是正常关闭

> ⚠️ 除了极少数情况（进程完全卡死在不可中断状态、或者已经失控狂占资源），**都用 SIGTERM**。把 `kill -9` 当第一手段是运维事故的常见来源。

**用信号名而不是数字**：

```bash
$ kill -TERM 1234        # ✅ 可读，且跨平台一致
$ kill -15 1234          # ⚠️ 数字在不同架构/Unix 上可能不同（虽然常见信号大多是统一的）
```

**相关**：

```bash
$ kill -l                # 列出所有信号名与编号
$ kill -HUP 1234         # SIGHUP：很多守护进程用它做"重载配置"
$ kill -USR1 1234        # SIGUSR1：常用于"打开调试日志"或"重开日志文件"（logrotate 用）
$ kill -STOP 1234 / kill -CONT 1234    # 暂停 / 继续
$ pkill -f 'myapp.*worker'             # 按命令行模式杀
$ killall nginx                        # 按进程名杀所有匹配
```

> ⚠️ `pkill -f` 是**用模式匹配整条命令行**，非常容易误杀。典型事故：在 SSH 会话里执行 `pkill -f ssh`，结果把自己那条 `sshd` 连接也匹配上，直接掉线。**先用 `pgrep -f 模式` 看清要杀谁，再换成 `pkill`。**

</details>

### 题 8 · ⭐ 找出占用 8080 端口的进程

<details><summary>答案</summary>

**方法一：`ss`（推荐，不需要 root 就能看自己的进程）**

```bash
$ ss -tlnp 'sport = :8080'
State   Recv-Q  Send-Q  Local Address:Port  Peer Address:Port  Process
LISTEN  0       511           0.0.0.0:8080       0.0.0.0:*      users:(("java",pid=2050,fd=45))
```

`ss -tlnp` 拆开看：`t` TCP、`l` listening、`n` 数字形式（不解析服务名）、`p` 显示进程。**不加 `-p` 只看端口不看到进程。**

`-p` 需要权限：看自己的进程不用 root，看别人的要 `sudo`。

**方法二：`lsof`**

```bash
$ sudo lsof -i :8080
COMMAND  PID USER  FD   TYPE DEVICE SIZE/OFF NODE NAME
java    2050 app   45u  IPv6 123456      0t0  TCP *:8080 (LISTEN)
```

**方法三：`fuser`（最简洁）**

```bash
$ sudo fuser 8080/tcp
8080/tcp:             2050
$ sudo fuser -v 8080/tcp        # 详细信息（用户、命令）
```

**方法四：不装任何工具，直接读 `/proc`（容器/精简系统里救命）**

```bash
$ sudo find /proc/*/fd -lname 'socket:*' 2>/dev/null | head    # 太慢，只能定位到 socket inode
# 更好的办法：从 ss 拿到 inode，再去 /proc 里找
$ ss -tlnp | grep 8080
$ ls -l /proc/2050/fd | grep socket
```

**Linux 上还可以看 `/proc/net/tcp`**（**端口是十六进制**）：

```bash
$ awk 'NR>1 {print $2}' /proc/net/tcp
00000000:1F90            # 1F90 = 8080 十六进制
00000000:0016            # 0016 = 22
```

🔐 **排查监听面**（比单个端口检查更有价值）：

```bash
$ sudo ss -tunlp                              # 所有 TCP+UDP 监听
$ sudo ss -tunlp | grep -v '127.0.0.1\|::1'   # 只留"对外暴露"的
```

**关键判读**：监听地址是 `0.0.0.0` 或 `::`（**所有接口**）还是 `127.0.0.1`（**只有本机**）：

```
LISTEN  0  511  0.0.0.0:6379    0.0.0.0:*    # ⚠️ Redis 暴露在公网，经典入侵入口
LISTEN  0  128  127.0.0.1:6379  0.0.0.0:*    # ✅ 只本机可连
```

</details>

### 题 9 · ⭐ 解读 `ps` 输出里的这些 `STAT` 值：`S`、`R`、`D`、`T`、`Z`、`Ss`、`S+`、`Sl`

<details><summary>答案</summary>

| 主状态 | 含义 |
|--------|------|
| `R` | Running / Runnable —— 正在 CPU 上跑，或在运行队列里等着 |
| `S` | Sleeping —— 可中断睡眠，在等事件（IO、信号、定时器）。**绝大多数进程是这个** |
| `D` | **Disk sleep 不可中断睡眠** —— 在等 IO，**连 `kill -9` 都杀不掉** |
| `T` | Stopped —— 被作业控制暂停（Ctrl+Z）或被 `kill -STOP` |
| `t` | Tracing stop —— 被调试器（`gdb`、`strace`）停住 |
| `Z` | Zombie —— 已退出但父进程还没 `wait()` 回收 |
| `I` | Idle —— 空闲的内核线程（Linux 5.10+ 新增） |
| `X` | Dead —— 不该出现在 `ps` 里 |

**附加标志**：

| 标志 | 含义 |
|------|------|
| `s` | 是**会话领导者**（session leader） |
| `l` | 多线程（multithreaded） |
| `+` | 在**前台**进程组里 |
| `<` | 高优先级（nice 为负） |
| `N` | 低优先级（nice 为正） |

所以：

| 值 | 解读 |
|----|------|
| `Ss` | 可中断睡眠 + 会话领导者 → **典型的守护进程** |
| `S+` | 可中断睡眠 + 前台 → 你在终端里跑的前台程序 |
| `Sl` | 可中断睡眠 + 多线程 |
| `R+` | 正在前台占用 CPU |
| `Z` | 僵尸 |

> 💡 想知道一个 `S`（睡眠）状态的进程到底在等什么，看 `wchan` 或 `stack`：
> ```bash
> $ cat /proc/<PID>/wchan
> wait_woken
> $ ps -o pid,stat,wchan:32 -p <PID>
> ```
> `wchan` 会告诉你它阻塞在内核的哪个函数，这是比 `strace` 更轻量的"卡在哪"判断。

</details>

### 题 10 · ⭐ 一个进程处于 `D` 状态，`kill -9` 杀不掉，怎么办？

<details><summary>答案</summary>

**先理解为什么杀不掉**：`D` 是**不可中断睡眠**。进程发起了 IO 请求，内核为了不破坏数据结构一致性，屏蔽了这个进程的所有信号（**包括 SIGKILL**），必须等 IO 返回才能响应。所以 `kill -9` 只是把信号挂起，等 IO 结束后立刻生效。

**为什么会出现 `D`**：

| 原因 | 典型表现 |
|------|----------|
| 磁盘/NFS 挂载变成"僵死" | 网络存储断连，`ls` 该挂载点也卡住 |
| 硬件故障 | 磁盘坏道、控制器无响应 |
| 内核 bug / 驱动问题 | 特定文件系统或 RAID 驱动的死锁 |
| 设备被拔掉 | USB 存储、iSCSI 断开 |

**诊断步骤**：

```bash
# 1. 看它阻塞在内核哪里
$ sudo cat /proc/<PID>/stack
[<0>] rpc_wait_bit_killable+0x2b/0x70 [sunrpc]     # 等 NFS 的 RPC
[<0>] __nfs4_get_acl_uncached+0x1ae/0x3c0 [nfs]
[<0>] nfs3_proc_getacl+0x40/0x90 [nfs]

# 2. 看 wchan
$ ps -o pid,stat,wchan:40 -p <PID>

# 3. 看是不是某个挂载点卡了
$ cat /proc/<PID>/mountinfo | head
$ grep -E 'nfs|nfs4' /proc/mounts

# 4. 看 dmesg 里的 IO 错误
$ sudo dmesg -T | grep -iE 'error|timeout|I/O|hung' | tail -30
```

**处置**：

1. **恢复底层 IO** 是唯一真正有效的办法。NFS 卡住就恢复网络；设备掉了就插回去。
2. 实在恢复不了，**优雅的做法是重启机器**（`reboot`），而不是继续跟这个进程较劲。
3. ⚠️ 对 NFS 挂载点做 `umount -f`（force）在进程 `D` 住**在同一个挂载点上**时会失败（`device is busy`）；`umount -l`（lazy）能"逻辑卸载"，但对已经在 `D` 的进程没用。

**预防**：

```bash
# fstab 里给网络挂载加软超时，避免无限等待
server:/export  /mnt/nfs  nfs  soft,timeo=30,retrans=2,_netdev  0 0
#                            ↑ soft = 超时后让 IO 失败返回，而不是无限重试
```

> 💡 **不要**在 `D` 状态下试图 `kill -9` 后立刻 `reboot -f` 或拔电源 —— 如果 IO 是磁盘写入，强断电可能造成文件系统损坏。先看 `dmesg` 确认是哪种 IO。

</details>

### 题 11 · ⭐ 用 `nohup` 让一个命令在退出 SSH 后继续运行，并说明为什么必须重定向输出

<details><summary>答案</summary>

```bash
$ nohup ./long_task.sh > /tmp/long_task.log 2>&1 &
$ echo $!                          # 记住 PID
12345
```

**为什么必须重定向**：`nohup` 只做两件事：

1. 把 **SIGHUP 信号设为忽略**（这是"挂断"信号，SSH 断开时终端会给会话内所有进程发这个）
2. 如果 stdout/stderr 是终端，把它们**重定向到 `nohup.out`**（当前目录不可写则写 `$HOME/nohup.out`）

**但它不改变进程的"控制终端"和"会话"关系**。如果 stdout 还是指向那个已经断开的终端设备，进程一往终端写就收到 `SIGTTOU`/`SIGTTIN`，或者写失败。所以显式重定向到文件是最稳的：

```bash
$ nohup ./task.sh > /tmp/task.log 2>&1 &
                              ↑ 顺序很重要：先改 1 再让 2 跟随
```

**`nohup` 的不足与替代**：

| 方案 | 效果 | 适用 |
|------|------|------|
| `nohup cmd &` | 忽略 SIGHUP，但仍属于当前会话的进程组 | 快速场景 |
| `setsid cmd &` | **新建会话**（新 SID），完全脱离终端；不用管 SIGHUP（因为新会话的首进程不会收到终端来的 HUP） | 更彻底 |
| `disown -h %1` | 把已在后台的作业从 shell 的作业表里移除 | 已经用 `&` 起了，事后补救 |
| `systemd-run --user --unit=myjob cmd` | 交给 systemd 管理，可查状态、可重启、**关机后重启会重跑** | 长期任务（推荐） |
| `tmux` / `screen` | 在伪终端里跑，随时重连看输出 | 交互式长任务 |

```bash
# 已经用 & 起在后台了，又忘了 nohup
$ jobs -l
[1]+  12345 Running   ./task.sh
$ disown -h %1          # -h 只标记"不接收 HUP"，进程仍在作业表里；不带 -h 是彻底移除
```

**验证"确实没被杀"**：

```bash
$ ps -o pid,ppid,sid,tty,stat,cmd -p 12345
    PID    PPID     SID TT   STAT CMD
  12345       1   12345 ?    S    ./long_task.sh
```

- `TT` 是 **`?`** 表示没有控制终端（好现象）
- `PPID` 变成 **`1`** 表示被 init/systemd 收养（说明原来的 shell 已经退出并被重新父化）

> ⚠️ 用 `setsid` / `nohup` 起的进程**不受 systemd 管理**：机器重启后不会自动恢复，出问题也没有 `Restart=` 保护。**长期服务应该写成 systemd unit**（见题 18）。

</details>

### 题 12 · ⭐ 作业控制：`Ctrl+Z` 之后怎么把任务放回后台继续跑？

<details><summary>答案</summary>

```bash
$ ./task.sh                # 前台运行
^Z                         # 按 Ctrl+Z
[1]+  Stopped                 ./task.sh

$ jobs -l                  # 看作业列表
[1]+  12345 Stopped                 ./task.sh
          ↑ PID

$ bg %1                    # 放回后台**继续运行**（发 SIGCONT）
[1]+ ./task.sh &
$ fg %1                    # 再拉回前台
$ bg                       # 省略编号时操作"当前作业"（带 + 的那个）
$ jobs                     # 再查看
```

**三个快捷键的区别（极易混淆）**：

| 按键 | 信号 | 效果 |
|------|------|------|
| `Ctrl+C` | SIGINT | **终止**前台进程 |
| `Ctrl+Z` | SIGTSTP | **暂停**前台进程（挂起，不退出） |
| `Ctrl+\` | SIGQUIT | 终止 + 生成 core dump |
| `Ctrl+D` | 不是信号 | 输入结束符（EOF），交互式 shell 里退出 |

**作业号 vs PID**：

- `%1` 是 **shell 作业号**，只在当前 shell 会话内有意义，每个 shell 各自从 1 开始编号。
- PID 是系统级的。
- `kill %1` 可以按作业号杀；`kill %1` 和 `kill 12345` 效果一样但作业号更省事。

**`nohup` 和 `bg` 的区别**：

- `Ctrl+Z` + `bg`：进程还在**当前 shell 的作业表**里，shell 退出（或断线）时仍会收到 SIGHUP → **会被杀掉**。
- 想让它活下来：`bg` 之后再 `disown -h %1`，或者一开始就用 `nohup`/`setsid`。

**其它作业控制**：

```bash
$ wait %1                  # 等某个后台作业结束
$ wait                     # 等所有后台作业结束
$ kill %1 %2               # 一次杀掉多个作业
```

> 🔐 **持久化排查视角**：`jobs` 的输出是**当前 shell 的**，看不到别的会话。真正要查"机器上有哪些脱离终端的进程"要用：
> ```bash
> $ ps -eo pid,ppid,sid,tty,stat,cmd | awk '$4=="?"'
> ```

</details>

### 题 13 · ⭐ 给一个命令设定最长运行时间（超时自动杀掉）

<details><summary>答案</summary>

```bash
$ timeout 10 ./slow_task.sh
$ echo $?              # 124 表示"确实是因为超时被杀的"
124
```

`timeout` 的退出码约定：

| 退出码 | 含义 |
|--------|------|
| 命令自己的退出码 | 命令在超时前正常结束 |
| `124` | 命令被超时终止了 |
| `125` | `timeout` 自身出错 |
| `126` | 找到命令但无法执行 |
| `127` | 命令不存在 |
| `137` | 命令被 SIGKILL 杀掉（**`-s KILL` 场景**） |

**超时后先发 TERM 再强杀的写法**：

```bash
$ timeout -k 5 10 ./slow_task.sh
        ↑ 超时后再等 5 秒，然后发 SIGKILL
```

拆开看：`-k 5` 是 kill-after（宽限期），`10` 是第一阶段的超时时间。整个流程是：

1. 10 秒后发 **SIGTERM**
2. 再等 5 秒还活着 → 发 **SIGKILL**

**指定信号**：

```bash
$ timeout -s KILL 10 cmd        # 到点直接 SIGKILL，不给机会清理
$ timeout -s INT 10 cmd         # 发 SIGINT（模拟 Ctrl+C）
```

**单位的坑**：不带单位后缀默认是**秒**，也支持 `s`/`m`/`h`/`d`：

```bash
$ timeout 1.5s ./task.sh        # 支持小数
$ timeout 2m ./task.sh
```

> ⚠️ **`timeout` 只它自己启动的那个进程**，不会连带杀掉这个进程的子进程（除非用 `--foreground` + 进程组技巧）。如果被包装的脚本内部又起了后台子进程，超时后那些孙子进程可能变成孤儿继续跑：
> ```bash
> $ timeout -k 2 10 setsid ./task.sh    # 配 setsid 让整个进程组一起被带走
> ```
> 或者更彻底：`timeout --signal=TERM --kill-after=5 10 pkill -P $$`（先杀子进程）。

</details>

### 题 14 · ⭐ 🔐 一个命令执行后卡住了，怎么知道它卡在哪个系统调用？

<details><summary>答案</summary>

```bash
$ strace -p 12345
strace: Process 12345 attached
read(3,                    # ← 卡在这里，等 fd 3 的数据
```

`-p` 附加到已有进程。输出的最后一行就是它**当前阻塞的位置**。

**常用组合**：

```bash
$ sudo strace -p 12345 -T -tt                 # -T 显示每个调用的耗时，-tt 时间戳
$ sudo strace -p 12345 -e trace=network       # 只看网络相关调用
$ sudo strace -p 12345 -e trace=file          # 只看文件操作（找它在读哪个配置）
$ sudo strace -p 12345 -y -f                   # -y 把 fd 解析成具体路径！-f 跟随子线程
$ sudo strace -c -f ./cmd                      # 统计模式：每个调用的次数与耗时占比
$ sudo strace -o /tmp/trace.txt ./cmd          # 输出到文件（避免刷屏）
```

**`-y` 是最好用的选项**，不加的话你只能看到 `read(3, ...)` 而不知道 3 是什么；加了之后直接告诉你：

```bash
$ sudo strace -p 12345 -y
read(3</etc/nginx/nginx.conf>, ...
connect(7<TCP:[10.0.0.5:8080]>, ...
```

**如果 strace 不可用**（精简系统、容器里没有、`ptrace` 被禁）：

```bash
$ cat /proc/12345/wchan           # 内核函数名
$ cat /proc/12345/syscall         # 当前系统调用号与参数
$ cat /proc/12345/stack           # 内核态调用栈（需 root）
$ cat /proc/12345/status | grep -E 'State|SigBlk'
$ ls -l /proc/12345/fd/           # 看它打开了什么
$ cat /proc/12345/io              # 读写了多少字节
```

`/proc/<PID>/syscall` 的输出格式是 `系统调用号 参数1 参数2 ... 返回地址 栈指针`，配合 `ausyscall` 解码（来自 `auditd` 包）：

```bash
$ ausyscall --dump | grep -w 0     # 系统调用号 0 是什么
0	read
```

> ⚠️ **ptrace 的权限限制**（现代内核默认更严）：
> ```bash
> $ cat /proc/sys/kernel/yama/ptrace_scope
> 1
> ```
> | 值 | 含义 |
> |----|------|
> | 0 | 任何进程都能 attach 任何进程（老默认，不安全） |
> | 1 | 只能 attach **自己的子进程**，其他情况需 root（**现代发行版默认**） |
> | 2 | 只有 root 能 attach |
> | 3 | 完全禁止 attach |
>
> 所以在 `ptrace_scope=1` 下，即使 `sudo strace -p` 也可能失败在容器里（因为容器与宿主不属于同一进程树）。改为 `sudo sysctl -w kernel.yama.ptrace_scope=0` 可以放开，但**这会削弱系统安全性** 🔐。

</details>

### 题 15 · ⭐ 把一个正在跑的进程的优先级调低（让它不抢 CPU）

<details><summary>答案</summary>

```bash
$ nice -n 10 ./backup.sh &        # 启动时就设：nice 值 10（数字越大优先级越低）
$ renice 10 -p 12345              # 对已有进程改
12345 (process ID) old priority 0, new priority 10
$ renice 10 -p $(pgrep -d, -x backup.sh)   # 批量改
```

**`nice` 值的规则**：

| 范围 | 谁可以设 |
|------|----------|
| `0`（默认）到 `19` | 任何用户，把自己的进程**调低**优先级 |
| `-20` 到 `-1` | **只有 root**，提高优先级（`nice -n -10 cmd`） |

数字越小 = 优先级越高。`-20` 最高，`19` 最低。

**实际观察效果**：

```bash
$ nice -n 19 dd if=/dev/zero of=/dev/null bs=1M count=100000 &
$ ps -o pid,ni,pri,stat,cmd -p $!
    PID  NI PRI STAT CMD
  12345  19  39 R    dd if=/dev/zero ...
```

`NI` 是 nice 值，`PRI` 是内核显示的实际优先级（内核内部计算，不等于 `20 + NI`）。

**不只是 CPU**：`nice` 只影响 CPU 调度，**不影响磁盘 IO**。IO 密集的备份任务会把磁盘打满，即使 CPU nice 到 19 也一样。要控制 IO 优先级用 `ionice`：

```bash
$ sudo ionice -c3 -p 12345         # -c3 = idle 级别，只在磁盘空闲时给它 IO
$ sudo ionice -c2 -n7 -p 12345     # -c2 best-effort，级别 0（高）~7（低）
$ sudo ionice -c1 -p 12345         # -c1 realtime：**抢占所有其他进程的 IO** ⚠️
```

**整体组合成一个"温柔的后台任务"**：

```bash
$ nice -n 19 ionice -c3 ./backup.sh &
```

CPU 和 IO 都让路，对交互式使用几乎没有影响。

**更底层的实时调度**（`chrt`，用于低延迟场景，需要 root）：

```bash
$ sudo chrt -f 10 ./realtime_task       # SCHED_FIFO，优先级 10
$ sudo chrt -r 10 ./task                # SCHED_RR，带时间片的实时
$ sudo chrt -b 0 ./task                 # SCHED_IDLE，比 nice 19 还低
```

> ⚠️ 实时调度（SCHED_FIFO/SCHED_RR）里优先级高的进程会**无限期饿死**低优先级的进程，用错能让系统失去响应（连 shell 都卡住）。非必要不用。

</details>

### 题 16 · ⭐ 解读 `uptime` 的 load average，并说明"负载高"是否等于"CPU 忙"

<details><summary>答案</summary>

```bash
$ uptime
 14:32:05 up 3 days,  4:21,  3 users,  load average: 8.52, 3.11, 1.02
                                                       1min  5min  15min
```

**load average 的定义（容易误解）**：

> 过去 N 分钟内，处于**可运行（R）**和**不可中断睡眠（D）**状态的进程数平均值。

注意两点：

1. **它包含 `D` 状态**，不只是"等 CPU 的进程"。大量 IO 阻塞的进程也会推高 load，而 CPU 可能很闲。
2. **它是"数量的平均值"，不是百分比**。

**判断方法：负载要和 CPU 核数比**：

```bash
$ nproc                    # 逻辑 CPU 数（含超线程）
8
$ uptime
load average: 8.52, 3.11, 1.02
```

| load / 核数 | 含义 |
|-------------|------|
| 约等于核数 | 刚好用满，队列里没人在等 |
| 小于核数 | 有闲置能力 |
| 明显大于核数 | **有任务在排队等 CPU** |

上面这个例子：`8.52 / 8` ≈ 1.07，说明最近 1 分钟刚好打满；但 15 分钟均值才 1.02，说明**是刚起来的负载**，正在上升。

**只看 load 会误判的情况**：

| 现象 | 真实原因 | 怎么验证 |
|------|----------|----------|
| load 很高但 CPU 空闲 | 大量进程卡在 `D`（IO 慢、NFS 卡） | `vmstat 1` 看 `b` 列（blocked）；`ps -eo stat` 数 `D` 的进程 |
| load 很高，CPU 也高 | 真的 CPU 密集 | `mpstat -P ALL 1` 看每核 |
| load 很低但很卡 | 单个进程被限流、内存不足在换页 | `vmstat 1` 看 `si`/`so`；`free -h` 看 swap |

**配套的观察命令**：

```bash
$ vmstat 1
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2  0      0 812345 123456 789012    0    0    12    45  120  340  4  1 94  0  0
 ↑  ↑                                                        ↑     ↑     ↑
 运行 阻塞                                                    用户 系统  空闲
```

`b` 列（blocked）非 0 且持续 → 有进程在 `D` 状态。
`wa`（IO wait）高 → CPU 在等 IO。

```bash
$ cat /proc/loadavg                    # 原始值 + 当前运行/总进程数 + 最近创建的 PID
8.52 3.11 1.02 3/1245 12345
                          ↑ 3 个正在运行 / 共 1245 个进程
```

🔐 **负载异常也和安全有关**：挖矿木马会持续吃满 CPU，`load` 和 `%CPU` 会出现"有个陌生进程长期 100%"。见 [`../commands/04-进程与作业.md`](../commands/04-进程与作业.md) 的可疑进程排查清单。

</details>

### 题 17 · ⭐ 解释 `free -h` 输出，并说明应该看哪一列判断"内存够不够"

<details><summary>答案</summary>

```bash
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi       4.2Gi       1.1Gi       321Mi       9.9Gi        10Gi
Swap:          8.0Gi       128Mi       7.9Gi
```

| 列 | 含义 |
|----|------|
| `total` | 物理内存总量（`Swap` 行是交换空间） |
| `used` | 已用（不含 buff/cache） |
| `free` | **完全空闲**的（这个数字很小是正常的） |
| `shared` | 被 tmpfs、共享内存占用的（`/dev/shm`） |
| `buff/cache` | 被内核用作**缓存**的内存（文件缓存 + 块设备缓冲） |
| `available` | **最该看的一列**：在不使用 swap 的前提下，**估算**还能给新应用多少内存 |

**为什么 `free` 很小不用慌**：Linux 会**主动用空闲内存做文件缓存**，因为"不用的内存是浪费的内存"。这些缓存在应用需要时能被立刻回收。所以：

> **判断内存是否紧张，看 `available`，不看 `free`。**

**内存紧张的信号**：

```bash
$ vmstat 1
 si   so
 0    0        # 正常
1234 2048      # ⚠️ 正在换页：si/so（swap in/out）非 0 且持续 → 内存不够
```

```bash
$ free -h
               total        used        free      shared  buff/cache   available
Mem:            15Gi        14Gi       200Mi       321Mi       800Mi        400Mi
Swap:          8.0Gi       7.9Gi       128Mi
```

`available` 只剩 400Mi 且 swap 几乎用满 → **真的不够了**。

**看谁在占内存**：

```bash
$ ps aux --sort=-rss | head -10
$ smem -tk                    # 需要装 smem：按 PSS（按比例分摊共享内存）统计，比 RSS 准确
$ cat /proc/meminfo | head -10
```

**手动释放缓存**（一般**不需要**做）：

```bash
$ sync                                  # 先把脏页写盘（必须！）
$ echo 1 | sudo tee /proc/sys/vm/drop_caches    # 1=pagecache, 2=dentries/inodes, 3=两者
$ echo 3 | sudo tee /proc/sys/vm/drop_caches
```

> ⚠️ 生产环境**不要**随便 drop_caches。它会让后续所有文件读取都变慢（缓存没了），而且这只是把 `buff/cache` 挪到 `free`，**并没有解决内存不足**。真正的解法是找出吃内存的进程或扩容。

**OOM killer 的痕迹**：

```bash
$ sudo dmesg -T | grep -i 'killed process'
[Mon Sep 15 03:14:22 2026] Out of memory: Killed process 12345 (java) total-vm:8.2g, anon-rss:7.9g
$ sudo journalctl -k | grep -i oom
```

进程"莫名其妙消失"时，第一件事就是查这个。

</details>

### 题 18 · ⭐ 查看 `nginx` 服务的状态、是否开机自启、以及最近 50 行日志

<details><summary>答案</summary>

```bash
$ systemctl status nginx
● nginx.service - A high performance web server and a reverse proxy server
     Loaded: loaded (/usr/lib/systemd/system/nginx.service; enabled; preset: disabled)
             ↑ enabled 表示开机自启
     Active: active (running) since Mon 2026-09-15 09:00:12 CST; 5h 32min ago
     Docs: man:nginx(8)
  Process: 2045 ExecStartPre=/usr/sbin/nginx -t -q -g 'daemon on; master_process on;' (code=exited, status=0/SUCCESS)
 Main PID: 2050 (nginx)
    Tasks: 5 (limit: 18894)
   Memory: 12.4M
      CPU: 2.341s
   CGroup: /system.slice/nginx.service
           ├─2050 "nginx: master process /usr/sbin/nginx"
           └─2051 "nginx: worker process"

Sep 15 09:00:12 myhost systemd[1]: Starting nginx...
Sep 15 09:00:12 myhost nginx[2045]: nginx: configuration file /etc/nginx/nginx.conf test is successful
Sep 15 09:00:12 myhost systemd[1]: Started nginx.
```

**怎么读这段输出**：

| 字段 | 含义 |
|------|------|
| `Loaded:` | unit 文件路径 + **是否 enabled**（开机自启）。`preset: disabled` 是厂商预设 |
| `Active:` | 当前状态：`active (running)` / `inactive (dead)` / `failed` |
| `Process:` | 每条 `ExecStartPre`/`ExecStartPost` 的执行结果 |
| `Main PID` | 主进程 PID（`Type=forking` 时是真正的守护进程） |
| `CGroup` | 属于这个服务的**所有**进程（含子进程）—— 这就是"服务"的准确定义 |
| 底部日志 | 该服务最近的日志（默认 10 行） |

**状态码的读法**（`Active: failed` 时最关键）：

| 提示 | 含义 |
|------|------|
| `code=exited, status=0/SUCCESS` | 正常 |
| `code=exited, status=1/FAILURE` | 程序自己返回了 1 |
| `code=exited, status=203/EXEC` | **找不到可执行文件**或没有执行权限（路径写错） |
| `code=exited, status=200/CHDIR` | `WorkingDirectory=` 指向的目录不存在 |
| `code=exited, status=217/USER` | `User=` 指定的用户不存在 |
| `code=killed, signal=KILL` | 被 SIGKILL 杀（常见：OOM killer 或手杀） |
| `code=dumped, signal=SEGV` | 段错误崩溃 |

**常用操作**：

```bash
$ systemctl status nginx --no-pager -l     # -l 显示完整（不截断）日志行
$ systemctl is-enabled nginx               # enabled / disabled / static
$ systemctl is-active nginx                # active / inactive / failed
$ systemctl list-units --type=service --state=running     # 所有运行中的服务
$ systemctl list-unit-files --state=enabled               # 所有开机自启的
```

**看日志**：

```bash
$ journalctl -u nginx -n 50 --no-pager              # 最近 50 行
$ journalctl -u nginx -f                            # 实时跟踪（等价 tail -f）
$ journalctl -u nginx --since '1 hour ago'
$ journalctl -u nginx --since '2026-09-15 09:00' --until '2026-09-15 10:00'
$ journalctl -u nginx -p err                        # 只看 error 及以上
$ journalctl -u nginx -b                            # 只看本次启动之后
$ journalctl -u nginx -b -1                         # 只看**上一次**启动的日志（排查崩溃重启）
$ journalctl -u nginx -o json-pretty                # JSON 格式，含 PID/UID 等元数据
```

🔐 **只 `status` 不够，要交叉验证**：

```bash
$ ss -tlnp | grep nginx              # 真的在监听吗
$ systemctl show nginx -p MainPID    # 拿 MainPID
$ ps -p <MainPID> -o pid,user,cmd    # 这个 PID 真的是 nginx 吗（防伪装）
$ ls -l /proc/<MainPID>/exe           # 可执行文件在哪（防替换成后门）
```

</details>

### 题 19 · ⭐ 创建一个每天凌晨 3:30 执行的定时任务

<details><summary>答案</summary>

```bash
$ crontab -e
```

在编辑器里加一行：

```cron
30 3 * * * /home/rivo/scripts/backup.sh >> /home/rivo/logs/backup.log 2>&1
```

**五个字段的含义（顺带记法）**：

```
*  *  *  *  *   命令
│  │  │  │  └── 星期几 (0-7，0 和 7 都是周日)
│  │  │  └───── 月份   (1-12)
│  │  └──────── 日     (1-31)
│  └─────────── 小时   (0-23)
└────────────── 分钟   (0-59)
```

`30 3 * * *` = 每天 3:30。

**常用语法**：

| 写法 | 含义 |
|------|------|
| `*` | 任意值 |
| `5` | 精确值 |
| `1,15` | 列举多个 |
| `1-5` | 范围 |
| `*/10` | 每 10 个单位（步进） |
| `30 3 * * 1-5` | 工作日 3:30 |
| `0 */2 * * *` | 每 2 小时的整点 |

特殊字符串（这些是**非标准扩展**，Vixie cron 系支持）：

```cron
@reboot    /path/to/start.sh
@daily     /path/to/job.sh        # 等价 0 0 * * *
@weekly    /path/to/job.sh
@monthly   /path/to/job.sh
```

**必须重定向输出**：cron 会把命令的输出（stdout+stderr）**邮件**给用户。如果系统没配 MTA，输出会被丢弃，出了问题你看不到任何痕迹。所以要么重定向到日志，要么 `>/dev/null 2>&1`。

**管理命令**：

```bash
$ crontab -l                 # 列出当前用户的
$ crontab -e                 # 编辑（会自动做语法检查）
$ crontab -r                 # ⚠️ 删除**整个** crontab 文件（无确认！）
$ sudo crontab -l -u alice   # 看别人的
$ sudo crontab -e -u alice   # 编别人的
```

> ⚠️ `crontab -r` 和 `crontab -e` 只差一个字母，且 `-r` **没有任何确认提示**，误敲就丢掉全部定时任务。想删某一行请用 `crontab -e` 手工删。

**cron 的环境是"干净"的**（这是 cron 最常见的问题）：

cron 执行任务时**不读取任何 profile/bashrc**，环境里只有一个极小的集合，`PATH` 常常只有 `/usr/bin:/bin`。所以：

| 症状 | 原因 | 修法 |
|------|------|------|
| "手工跑成功，cron 跑失败" | `PATH` 里没有你需要的目录 | 脚本里用**绝对路径**，或在 crontab 里显式设 `PATH=/usr/local/bin:/usr/bin:/bin` |
| 命令找不到 | 见上 | 同上 |
| 变量为空 | cron 不读 `.bashrc` | 在脚本里 `source` 或直接写死 |

排查手段：把环境 dump 出来对比 🔐

```cron
* * * * * env > /tmp/cron_env.txt 2>&1
```

**cron 的日志**：

```bash
$ journalctl -u cron -n 50           # Debian/Ubuntu（服务名 cron）
$ journalctl -u crond -n 50          # RHEL/Arch（服务名 crond）
$ sudo grep CRON /var/log/syslog     # 传统 syslog 方式
```

**cron vs systemd timer**：

| | cron | systemd timer |
|--|------|---------------|
| 语法 | 5 字段，紧凑但表达力弱 | `OnCalendar=`，可读（`Mon *-*-* 03:30:00`） |
| 依赖 | 无 | 可 `After=network-online.target` |
| 错过的任务 | 机器关机就跳过 | `Persistent=true` 可补跑 |
| 环境 | 干净得让人困惑 | 可在 unit 里显式声明 |
| 日志 | 混在 syslog | `journalctl -u xxx.timer` 结构化 |
| 随机延迟 | 需手工加 `sleep $RANDOM` | `RandomizedDelaySec=` |
| 校验语法 | 无 | `systemd-analyze calendar '...'` |

**推荐**：新任务优先用 systemd timer（见 [`../commands/11-系统管理-systemd.md`](../commands/11-系统管理-systemd.md)）。

🔐 **持久化排查**：看有没有攻击者留的定时任务：

```bash
$ for u in $(cut -d: -f1 /etc/passwd); do
    echo "=== $u ==="; sudo crontab -l -u "$u" 2>/dev/null;
  done
$ ls -la /etc/cron.{d,daily,hourly,weekly,monthly}/ /var/spool/cron/ /var/spool/cron/crontabs/ 2>/dev/null
$ sudo cat /etc/crontab /etc/anacrontab 2>/dev/null
```

</details>

### 题 20 · ⭐ 系统开机花了 45 秒，怎么找出是哪个服务拖慢了启动？

<details><summary>答案</summary>

```bash
$ systemd-analyze

Startup finished in 3.214s (firmware) + 2.847s (loader) + 4.123s (kernel) + 35.602s (userspace) = 45.786s
graphical.target reached after 35.421s in userspace.
```

**先看阶段划分**：

| 阶段 | 含义 | 异常时查什么 |
|------|------|--------------|
| `firmware` | UEFI/BIOS 自检 | BIOS 设置、硬件检测、Secure Boot |
| `loader` | GRUB 加载 | 菜单超时（`GRUB_TIMEOUT`）、`initrd` 大小 |
| `kernel` | 内核初始化 | `dmesg` 里的驱动超时、`systemd-analyze` 无细项可看 |
| `userspace` | init 起来之后 | **通常是问题所在** |

**找出最慢的服务**：

```bash
$ systemd-analyze blame | head -15
35.102s NetworkManager-wait-online.service
 2.341s systemd-udev-settle.service
 1.205s docker.service
 0.834s NetworkManager.service
 ...
```

`blame` 按"服务自己花的时间"降序。**注意**：它显示的是**服务处于激活状态的总时长**，长时间等待的服务（比如等网络的）会排在最前，但这不一定意味着它是"原因"——它可能只是**在等别的东西**。

**找出真正的关键路径**：

```bash
$ systemd-analyze critical-chain
graphical.target @35.421s
└─multi-user.target @35.420s
  └─docker.service @34.102s +1.205s
    └─network-online.target @34.080s
      └─NetworkManager-wait-online.service @1.978s +32.100s
        └─NetworkManager.service @1.205s +0.723s
          └─dbus.service @1.100s
            └─basic.target @1.090s
```

**`critical-chain` 的读法**：缩进是"依赖链"，`@X` 是"该服务开始的时间"，`+Y` 是"自己花的时间"。

看 `NetworkManager-wait-online.service @1.978s +32.100s` —— 它从第 2 秒就启动了，但一直等到第 34 秒才完成。**这就是拖慢启动的元凶**（占了一半以上的时间）。

**这条链的含义**：`network-online.target` 在等 `NetworkManager-wait-online`，而 `docker.service` 又 `After=network-online.target`，于是整个启动被这条链卡住。

**常见元凶与处理**：

| 服务 | 为什么会慢 | 处理 |
|------|------------|------|
| `NetworkManager-wait-online.service` | 要等所有网卡拿到 IP，包括那些没插网线的 | 如果不需要"网络就绪才启动服务"，`sudo systemctl disable NetworkManager-wait-online.service` |
| `systemd-udev-settle.service` | 等所有设备探测完成（老式"等 udev 稳定"的遗留做法） | 确认没有依赖它的服务，然后 disable |
| `docker.service` | `After=network-online.target` 导致连带等待 | 通常不用改 |
| `plymouth-*` | 图形启动画面卡住 | 去掉 `splash`/`quiet` 内核参数看真实输出 |
| `fsck` 超时 | 磁盘有问题 | `dmesg` + `tune2fs -l` 看挂载次数与错误 |

**更细的时间线分析**：

```bash
$ systemd-analyze blame --no-pager | head -20         # 全部（不截断）
$ systemd-analyze critical-chain nginx.service        # 只看某个 unit 的链
$ systemd-analyze plot > /tmp/boot.svg                # 生成可视化时间线（用浏览器打开）
$ systemd-analyze dot | dot -Tsvg > /tmp/deps.svg     # 依赖关系图
$ systemd-analyze verify nginx.service                # 校验 unit 文件语法
```

**看内核启动细节**：

```bash
$ dmesg -T | head -50                       # 内核启动日志，带可读时间
$ journalctl -b -o short-monotonic           # 本次启动的日志，用"从启动起算的秒数"显示时间
$ journalctl -b -p warning                   # 只看 warning 及以上
```

`-o short-monotonic` 特别有用：它把时间戳变成"启动后多少秒"，这样能直接看出"第 28 秒发生了什么"：

```
[   28.123456] myhost systemd[1]: Starting Network Manager...
```

> ⚠️ `systemd-analyze security`（评 unit 的安全加固程度）和 `blame` 是两个不同的功能，别混用：
> ```bash
> $ systemd-analyze security nginx.service     # 给这个 unit 打分（越低越好），列出可改进项
> ```

</details>
