> - `chmod -R 777 路径` 是**最危险**的权限操作之一。它会同时给目录、脚本、配置文件、密钥全部放开读写执行；SSH 会直接拒绝工作（`~/.ssh` 权限过宽时 `sshd` 报 `Authentication refused: bad ownership or modes`）。

### 1. 用八进制数字把文件的权限设成 `640` ⭐

**场景**：`secret/readme.txt` 是机密文件，要求「属主可读写、属组只读、其他人完全无权」。

**要求**：用数字模式设置，并验证。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

chmod 640 secret/readme.txt
stat -c '%a %A %n' secret/readme.txt
ls -l secret/readme.txt
```

**预期输出**：

```text
640 -rw-r----- secret/readme.txt
```

**解析**：

权限位的八进制编码（**记住这张表，一切就通了**）：

```text
            属主   属组   其他人
             u      g      o
读  r  = 4   4      4      4
写  w  = 2   2      2      2
执行 x = 1   1      1      1
            ────   ────   ────
chmod 640 =  6      4      0
             4+2    4      0
             rw-    r--    ---
```

| 数字 | 二进制 | 权限 |
|------|--------|------|
| 0 | 000 | `---` |
| 1 | 001 | `--x` |
| 2 | 010 | `-w-` |
| 3 | 011 | `-wx` |
| 4 | 100 | `r--` |
| 5 | 101 | `r-x` |
| 6 | 110 | `rw-` |
| 7 | 111 | `rwx` |

- 数字模式是**覆盖**，不是叠加：`chmod 640` 之后不管你原来是什么，结果就是 640。要「在原有基础上加一点」，用**符号模式**（第 2 题）。
- 常用组合速记：`644` 普通文件、`755` 可执行文件/目录、`600` 私钥、`640` 日志、`700` 私有目录、`1777` 公共可写目录。
- `stat -c '%a'` 输出的是**不含特殊位**的三位数字；带 SUID/SGID/sticky 时会输出四位（第 6 题）。

</details>

### 2. 不改变其它权限，只动一位 ⭐⭐

**场景**：一个脚本需要「给属主加执行权、同时去掉属组和其他人的写权」，但**不要碰**其它位。

**要求**：用符号模式一次完成，并说明符号模式的语法。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

cp data/sales.csv /tmp/sym-demo.sh
chmod 664 /tmp/sym-demo.sh
stat -c '改前: %a %A' /tmp/sym-demo.sh

chmod u+x,g-w,o-w /tmp/sym-demo.sh
stat -c '改后: %a %A' /tmp/sym-demo.sh

# 逗号可以省略（等价写法）
chmod u+x,g-w,o-w /tmp/sym-demo.sh

# 一次性对所有人操作
chmod a-x /tmp/sym-demo.sh          # a = ugo = 全部
chmod a=r /tmp/sym-demo.sh          # 全部设成只读（= 是赋值）

# 只操作 ugo 中的一个
chmod g+r /tmp/sym-demo.sh
chmod o= /tmp/sym-demo.sh           # = 后面留空 = 清空这组全部权限
```

**预期输出**：

```text
改前: 664 -rw-rw-rw-
改后: 740 -rwxr-----
```

**解析**：

符号模式的语法是：

```
[ugoa...] [+-=] [rwxXst...]
     ↑        ↑        ↑
   操作谁    怎么操作   操作什么
```

| 部分 | 可选值 | 含义 |
|------|--------|------|
| 操作对象 | `u` | 属主 user |
| | `g` | 属组 group |
| | `o` | 其他人 others |
| | `a` | 全部（= `ugo`） |
| 操作符 | `+` | **添加**权限 |
| | `-` | **移除**权限 |
| | `=` | **设为**（覆盖，清掉原有其它位） |
| 权限 | `r` `w` `x` | 读/写/执行 |
| | `X` | 仅当「是目录」或「已有执行位」时给 `x` |
| | `s` | SUID/SGID |
| | `t` | Sticky |
| | `-u` `-g` `-o` | 复制属主/属组/其他人的权限位 |

- **省略操作对象时等价于 `a`**：`chmod +x file` = `chmod a+x file`。这在共享目录里容易出事（你只想给属主加 `x`，结果给了所有人）。
- **`=` 是覆盖，不是添加**：`chmod u=r file` 会把属主权限**精确设成** `r--`，原来的 `w` 会被去掉。
- **逗号分隔的多个子句按顺序执行**，所以 `chmod g+w,g-w` 最终是 `g-w` 生效。
- 💡 一条命令里混合复制和加减：`chmod g=u file`（让属组权限和属主一样）、`chmod o=g file`。

</details>

### 3. 目录上的 `r` 和 `x` 到底各管什么 ⭐⭐

**场景**：同事把一个目录设成了 `644`（有 `r` 没 `x`），然后说「我能看见文件但进不去，也打不开」。另一个目录设成 `600`，`ls` 直接报错。

**要求**：用实验证明目录 `r` 和 `x` 的独立作用。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

# 造一个测试目录
mkdir -p /tmp/dirmode && echo hello > /tmp/dirmode/f.txt

echo "=== ① 只有 r（644）：能列名，不能进、不能读文件 ==="
chmod 644 /tmp/dirmode
ls /tmp/dirmode                    # ✅ 能列出 f.txt（读到了目录项）
ls -l /tmp/dirmode/f.txt           # ✅ 能 stat（其实需要 x，见解析）
cat /tmp/dirmode/f.txt             # ❌ Permission denied（无法"穿过"目录到文件）
cd /tmp/dirmode                    # ❌ Permission denied

echo "=== ② 只有 x（111）：能进，但列不出名字 ==="
chmod 111 /tmp/dirmode
cd /tmp/dirmode && pwd             # ✅ 能进去
ls                                 # ❌ Permission denied（读不到目录项列表）
cat /tmp/dirmode/f.txt             # ✅ 能读！前提是你知道文件名字
cd /tmp/linux-practice

echo "=== ③ r + x（555）：正常读取 ==="
chmod 555 /tmp/dirmode
ls /tmp/dirmode && cat /tmp/dirmode/f.txt

echo "=== ④ 只有 w + x（311）：能建/删文件，但看不到有什么 ==="
chmod 311 /tmp/dirmode
echo new > /tmp/dirmode/g.txt      # ✅ 能创建
ls /tmp/dirmode                    # ❌ 列不出来

# 恢复
chmod -R 755 /tmp/dirmode
```

**解析**：

目录上的三个权限**含义和文件完全不同**，这是权限体系最大的认知门槛：

| 目录权限 | 含义 | 通俗解释 |
|---------|------|---------|
| `r` | 允许**读取目录项列表**（文件名清单） | 「知道里面有哪些文件」 |
| `w` | 允许在目录中**创建、删除、重命名**条目 | 「能增删条目」 |
| `x` | 允许**穿过**该目录去访问里面的 inode（进入 / 访问具体文件） | 「能走进去」 |

关键推论（每一条都是高频坑）：

1. **目录的 `x` 位是「访问里面文件」的必要条件**。没有 `x` 时，即使你对文件本身有 `r` 权限，`cat 目录/文件` 也会 `Permission denied`。
2. **目录的 `w` 位决定能不能删里面的文件，而不是文件自己的 `w` 位**。这就是为什么 `/tmp` 里任何人能删自己创建的文件，却删不掉别人的——**靠的是 sticky 位**（第 5 题），而不是文件的权限。
3. **`r` 和 `w` 都需要 `x` 才能生效**（对目录操作而言）。`w` 没 `x` 时，`touch 目录/new` 也会失败。
4. 只要知道**文件名**，`x` 单独存在就能访问该文件（这就是「目录只有 `111` 可以按已知路径读文件」的原理）。

💡 实用推论：「共享目录 `rwx` + 里面文件 `---`」是可行的——只要目录可写，就能删/换里面的文件。反过来「目录 `r-x` + 文件 `rwx`」时你依然改不了文件内容（要改内容需要文件的 `w`）。

</details>

### 4. 大写 `X`：只给目录加执行位，文件不加 ⭐⭐

**场景**：你解压了一个目录树，权限全乱了（目录没有 `x` 所以进不去）。你要「给所有目录补上 `x`，但**不要**给普通文件加 `x`」。

**要求**：用一条 `chmod` 完成。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

# 造一个乱权限的目录树
rm -rf /tmp/xtree && mkdir -p /tmp/xtree/a/b
echo 1 > /tmp/xtree/f1.txt
echo 2 > /tmp/xtree/a/f2.txt
echo 3 > /tmp/xtree/a/b/f3.txt
chmod -R 644 /tmp/xtree              # 全部设成 644：目录也没了 x
ls /tmp/xtree                        # ✅ 能列
ls /tmp/xtree/a                      # ❌ Permission denied（a 目录没有 x）

# ✅ 用大写 X
chmod -R u+X /tmp/xtree
find /tmp/xtree -printf '%M %p\n' | sort

# 让所有人可读（目录 755、文件 644）
chmod -R a+rX /tmp/xtree
find /tmp/xtree -printf '%M %p\n' | sort
```

**预期输出**：

```text
-rw-r--r-- /tmp/xtree/a/b/f3.txt
-rw-r--r-- /tmp/xtree/a/f2.txt
-rw-r--r-- /tmp/xtree/f1.txt
drwxr-xr-x /tmp/xtree
drwxr-xr-x /tmp/xtree/a
drwxr-xr-x /tmp/xtree/a/b
```

**解析**：

- **`X`（大写）的条件性执行位**：只有满足下面任一条件时才给 `x`：
  - 目标是**目录**，或
  - 目标**已经**有至少一个执行位（`u+x` 或 `g+x` 或 `o+x` 中任意一个）。
- 所以 `chmod -R a+rX` 是**恢复目录树权限的标准姿势**：目录全部变成可进入，普通文件只变成可读、不会莫名变成可执行。
- 对比 `chmod -R a+x`：那会给**每个文本文件也加上执行位**，看起来无害，实则是安全隐患——被上传的 PHP/JSP/脚本文件只要落了地就多了一层执行能力。**很多 Web 上传漏洞的利用链里就有这一环**。
- 💡 常见配合：

  ```bash
  # 常见需求：目录 755、文件 644
  find . -type d -exec chmod 755 {} +
  find . -type f -exec chmod 644 {} +
  # 或者一步到位
  chmod -R u=rwX,go=rX .
  ```

- 🔐 排查时：`find . -type f -perm -u+x -name '*.txt'` 能找出「被错误加上执行位的文本文件」，这类文件值得看一眼内容。

</details>

### 5. 🔐 粘滞位：为什么 `/tmp` 是 `1777` ⭐⭐⭐

**场景**：`/tmp` 是所有人可写的。那为什么 A 用户不能删掉 B 用户在 `/tmp` 下的文件？

**要求**：解释粘滞位，并用实验证明「没有 sticky 时能删别人的文件」。

<details><summary>参考答案</summary>

```bash
echo "=== 观察系统上的 sticky 目录 ==="
ls -ld /tmp /var/tmp
stat -c '%a %A %n' /tmp
```

**预期输出**：

```text
drwxrwxrwt  ... /tmp
drwxrwxrwt  ... /var/tmp
1777 drwxrwxrwt /tmp
```

**实验：对比有 / 无 sticky 的公共目录**

```bash
# 需要两个用户才能完整验证；单用户环境下用 sudo -u 或 su 模拟
# 下面用 nobody 作为"另一个用户"演示（需要 root 执行）

# ① 有 sticky 的目录
sudo mkdir -p /tmp/sticky-demo && sudo chmod 1777 /tmp/sticky-demo
sudo -u nobody touch /tmp/sticky-demo/nobody-file
rm /tmp/sticky-demo/nobody-file
# rm: cannot remove '/tmp/sticky-demo/nobody-file': Operation not permitted   ← 被 sticky 拦住

# ② 没有 sticky 的目录
sudo mkdir -p /tmp/nosticky-demo && sudo chmod 777 /tmp/nosticky-demo
sudo -u nobody touch /tmp/nosticky-demo/nobody-file
rm /tmp/nosticky-demo/nobody-file
# 删除成功！                                                            ← 危险

# ③ 属主的文件，属主自己总能删（sticky 不放宽，只是"不额外禁止属主"）
sudo chmod 1777 /tmp/sticky-demo
sudo -u nobody touch /tmp/sticky-demo/mine
sudo -u nobody rm /tmp/sticky-demo/mine        # ✅ 属主删自己的没问题
```

**非 root 的替代验证**（在当前用户下观察行为即可）：

```bash
mkdir -p /tmp/sc-demo && chmod 1777 /tmp/sc-demo
ls -ld /tmp/sc-demo
touch /tmp/sc-demo/a && rm /tmp/sc-demo/a && echo "属主删除成功（sticky 不阻止属主）"

# 用沙盒里的 777 目录对比
ls -ld /tmp/linux-practice/shared      # 777，没有 t
find /tmp/linux-practice -type d -perm -1000   # 找出带 sticky 的目录（沙盒里通常没有）
```

**解析**：

- **粘滞位（Sticky Bit）**：设在目录上时，只有**下列三种身份**可以删除/重命名该目录里的文件：
  1. 目录的属主
  2. 文件本身的属主
  3. `root`

- 八进制表示是**前导 1**：`1777`、`1770`。`ls -l` 里显示为**其他人执行位上的 `t`**：

  | 显示 | 含义 |
  |------|------|
  | `drwxrwxrwt` | 有 sticky，且其他人有 `x` |
  | `drwxrwx--T` | 有 sticky，但其他人**没有** `x`（大写 T） |

- **去掉 sticky**：`chmod -t dir` 或 `chmod 777 dir`（数字模式写三位会清掉特殊位）。
- 粘滞位的**历史**：早期 Unix 用它把可执行程序常驻内存（sticky = 粘在内存里），现代内核只保留它作为目录的「防误删」语义。
- 典型用到的场景：`/tmp`、`/var/tmp`、共享上传目录、GitLab Runner 的构建目录。
- 🔐 **安全视角**：一个**没有 sticky 的 777 目录**是提权友好环境。攻击者可以：
  1. 删掉别人（或服务）正在用的文件，换成自己的版本（TOCTOU 替换攻击）；
  2. 删掉定时任务脚本、`authorized_keys`、`.bashrc` 再重建；
  3. 如果 root 的 cron 会执行该目录里的脚本，直接提权。

  审计命令：

  ```bash
  # 找出所有「全局可写但没有 sticky」的目录 —— 这些是可疑点
  find / -xdev -type d -perm -0002 ! -perm -1000 \
       ! -path '/proc/*' ! -path '/sys/*' 2>/dev/null
  ```

</details>

### 6. SGID 让你做出来一个「团队共享目录」 ⭐⭐

**场景**：研发团队 3 个人要共用一个目录，要求：
- 谁都能在里面创建文件
- 创建出来的文件**自动属于团队组**（而不是创建者的主组）
- 只有文件属主（或 root）能删别人的文件

**要求**：给出这个目录的完整权限，并说明每一位的作用。

<details><summary>参考答案</summary>

```bash
# 需要 root 来建组和改属组；非 root 可用现有组（如 wheel / docker）演示
sudo groupadd -f devteam
sudo mkdir -p /srv/devshared
sudo chgrp devteam /srv/devshared
sudo chmod 2775 /srv/devshared
sudo usermod -aG devteam alice       # 把成员加进组（-a 不能漏，见第 12 题）
sudo usermod -aG devteam bob

ls -ld /srv/devshared
# drwxrwsr-x 2 root devteam ... /srv/devshared
#       ↑ s 在属组执行位 = SGID
```

**各权限位的分工**：

| 权限 | 值 | 作用 |
|------|----|------|
| `2` (SGID) | `s` 在 `g` 的 `x` 位 | 目录里新建的文件/子目录**继承该目录的属组** |
| `7` (u=rwx) | 属主可读写进入 | 管理员维护 |
| `7` (g=rwx) | 属组可读写进入 | **团队成员能创建文件** |
| `5` (o=r-x) | 其他人可读进入 | 不给写，防止外部塞文件 |

**要加 sticky 时的组合**（`3775` = SGID + sticky）：

```bash
sudo chmod 3775 /srv/devshared
# drwxrwsr-t ...  ← 既有 SGID 又有 sticky
```

**非 root 的替代验证**（用你已有的附加组，比如 `wheel` 或 `docker`）：

```bash
# 查看自己属于哪些组
id
# uid=1000(rivo) gid=1000(rivo) groups=1000(rivo),966(docker),998(wheel)

# 用其中一个组做演示
mkdir -p /tmp/teamdir
chgrp docker /tmp/teamdir
chmod 2775 /tmp/teamdir
ls -ld /tmp/teamdir                       # drwxrwsr-x
touch /tmp/teamdir/newfile
ls -l /tmp/teamdir/newfile                # 属组是 docker（继承成功）

# 对比：去掉 SGID 会怎样
chmod 775 /tmp/teamdir && rm -f /tmp/teamdir/newfile && touch /tmp/teamdir/newfile
ls -l /tmp/teamdir/newfile                # 属组变回 rivo（创建者的主组）
```

**解析**：

- **SGID 在目录上 = 「继承属组」**。目录里新建的东西自动带上父目录的属组。这是团队共享目录的核心机制——没有 SGID 时，每个文件会带上**创建者自己的主组**，导致「我建的文件同事看不懂」。
- **SGID 在文件上 = 「以属组身份执行」**（类似 SUID 但换组），语义完全不同。`ls -l` 里都是 `s` 在 `g` 的 `x` 位上，要**看是文件还是目录**来区分。
- SGID 目录下的**子目录**会**同时继承 SGID 位和属组**（所以整棵树都能保持组一致）。这是 GNU/Linux 的默认行为。
- 只继承**属组**，不继承属主。属主永远是创建者。
- ⚠️ **`usermod -aG` 里的 `-a` 绝不能漏**。`usermod -G devteam alice` 会把 alice 从**除 devteam 外的所有组**里踢出来，可能直接导致她失去 `sudo`（如果 `sudo` 是靠 `wheel` 组授权的）。这是极其常见的运维事故。
- 💡 想让共享目录「创建的文件自动可被组内读写」，还需要配合 `umask 002`（或默认 ACL，见第 9 题）：

  ```bash
  # 放在 /etc/profile.d/devteam.sh 里
  umask 002      # 新建文件 664、目录 775，保证组内可写
  ```

</details>

### 7. 🔐 SUID 在 `ls -l` 里长什么样，为什么危险 ⭐⭐⭐

**场景**：你在 `ls -l` 里看到 `-rwsr-xr-x` 和 `-rwSr--r--`，不确定哪个是「真的能提权」。

**要求**：说清 `s` 与 `S` 的区别，并给出沙盒里 SUID 样本的观察。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

ls -l bin/suid-demo
stat -c '%a  %A  %n' bin/suid-demo

# 自己造出各种特殊位组合观察
touch /tmp/sp1 /tmp/sp2 /tmp/sp3 /tmp/sp4
chmod 4755 /tmp/sp1        # SUID + 属主有 x
chmod 4644 /tmp/sp2        # SUID 但属主无 x
chmod 2755 /tmp/sp3        # SGID + 属组有 x
chmod 2754 /tmp/sp4        # SGID 但属组无 x
stat -c '%a  %A  %n' /tmp/sp1 /tmp/sp2 /tmp/sp3 /tmp/sp4

mkdir -p /tmp/spd
chmod 2775 /tmp/spd        # 目录上的 SGID
chmod 1777 /tmp/spd-sticky # 目录上的 sticky
stat -c '%a  %A  %n' /tmp/spd /tmp/spd-sticky
```

**预期输出**：

```text
4755  -rwsr-xr-x  /tmp/sp1     ← 小写 s：SUID 生效（属主有 x）
4644  -rwSr--r--  /tmp/sp2     ← 大写 S：SUID 位置被占了，但属主无 x（通常无效）
2755  -rwxr-sr-x  /tmp/sp3     ← 小写 s：SGID 生效（属组有 x）
2754  -rwxr-sr--  /tmp/sp4     ← 大写 S：SGID 但属组无 x
2775  drwxrwsr-x  /tmp/spd         ← 目录上的 SGID
1777  drwxrwxrwt  /tmp/spd-sticky  ← 目录上的 sticky
```

**精确对照表**：

| 八进制 | `ls -l` 显示 | 位置 | 含义 |
|--------|-------------|------|------|
| 4755 | `-rw**s**r-xr-x` | 属主 `x` 位上的**小写 s** | SUID **且**属主有 `x` → 生效 |
| 4644 | `-rw**S**r--r--` | 属主 `x` 位上的**大写 S** | SUID **但**属主无 `x` → 通常无意义 |
| 2755 | `-rwxr-**s**r-x` | 属组 `x` 位上的**小写 s** | SGID **且**属组有 `x` |
| 2754 | `-rwxr-**S**r--` | 属组 `x` 位上的**大写 S** | SGID **但**属组无 `x` |
| 1777 | `drwxrwxrw**t**` | 其他人 `x` 位上的**小写 t** | Sticky **且**其他人有 `x` |
| 1770 | `drwxrwx--**T**` | 其他人 `x` 位上的**大写 T** | Sticky **但**其他人无 `x` |

**记忆法：小写表示「这个位真的生效」（因为底下的 `x` 在），大写表示「标志设了但 `x` 不在」。**

**解析：SUID 为什么危险**

- SUID（Set User ID）的语义：**执行该程序时，进程的有效用户 ID（EUID）变成文件属主的 UID，而不是执行者的 UID**。
- 系统里合法的 SUID 程序（`/usr/bin/passwd`、`/usr/bin/sudo`、`/usr/bin/mount`）：普通用户执行 `passwd` 时，进程以 `root` 身份运行，所以能写 `/etc/shadow`。**程序内部必须自己做权限校验**（只允许改自己的密码）。
- ⚠️ **危险点**：如果 SUID 程序本身有缺陷，普通用户就能拿到 root。常见缺陷类型：

  | 缺陷类型 | 例子 |
  |---------|------|
  | 调用外部命令但没写绝对路径 | 程序里 `system("ps")` → 改 `PATH` 就能劫持 |
  | 用了不安全的环境变量 | `LD_PRELOAD`、`LD_LIBRARY_PATH`、`PYTHONPATH` |
  | 缓冲区溢出 | C 写的程序没做边界检查 |
  | 校验逻辑写错 | 权限判断用了可绕过的条件 |
  | 本不该 SUID | 比如给 `cp`、`vim`、`find`、`tar`、`nmap` 加了 SUID（这几个都有 `!command` 或 `-exec` 之类的逃逸方式） |

- 🔐 原则：**SUID 是可提权的攻击面，越少越好**。安全基线的建议是「只保留发行版自带的、必要时关闭不必要的」。审计见第 8 题。
- 💡 沙盒里的 `bin/suid-demo` 只是 `echo pwned`，**没有真正的提权能力**，可以安全地练习查找与清点。清除它的 SUID：
  ```bash
  chmod u-s bin/suid-demo        # 或 chmod 755
  ls -l bin/suid-demo            # -rwxr-xr-x
  ```

</details>

### 8. 🔐 清点本机所有 SUID / SGID 文件 ⭐⭐⭐

**场景**：安全基线检查，要输出本机所有 SUID 和 SGID 文件清单，并与「已知合法清单」对比。

**要求**：给出审计命令，并说明 `-perm -4000` 与 `-perm /4000` 的区别。

<details><summary>参考答案</summary>

```bash
# ① 只找 SUID（-xdev 不跨文件系统，避免钻进 /proc /sys 和网络挂载）
find / -xdev -perm -4000 -type f 2>/dev/null | sort

# ② SUID + SGID 一起找
find / -xdev -perm /6000 -type f 2>/dev/null | sort

# ③ 生成带元数据的完整报告（属主、权限、大小、mtime、SHA256）
find / -xdev -perm /6000 -type f -printf '%M %u:%g %10s %TY-%Tm-%Td %p\n' 2>/dev/null | sort -k6

# ④ 计算哈希并保存基线（用于后续比对"有没有被替换"）
find / -xdev -perm /6000 -type f -exec sha256sum {} + 2>/dev/null | sort -k2 > /tmp/suid-baseline.txt
# 之后复查：
sha256sum -c /tmp/suid-baseline.txt 2>/dev/null | grep -v ': OK$'

# ⑤ 只想看"最近被改动过"的 SUID（新出现的 SUID 是最可疑的信号）
find / -xdev -perm /6000 -type f -newermt '7 days ago' 2>/dev/null

# ⑥ 最危险的一类：SUID + 你自己可写
find / -xdev -perm -4000 -type f -writable 2>/dev/null | grep -v "^$HOME"

# ⑦ 沙盒里先练手（范围小，输出确定）
cd /tmp/linux-practice
find . -perm -4000 -type f -printf '%M %u:%g %p\n'
```

**预期输出（⑦）**：

```text
-rwsr-xr-x rivo:rivo ./bin/suid-demo
```

**解析：`-perm -4000` vs `-perm /4000`（最常见的 find 坑）**

| 写法 | 语义 | 结果 |
|------|------|------|
| `-perm 4000` | **精确匹配**权限**恰好等于** 4000 | 几乎什么都匹配不到（因为你还要有读权限位） |
| `-perm -4000` | **全部这些位都必须置位**（AND，超级集） | SUID 位为 1 的**所有**文件（不管其它位） |
| `-perm /4000` | **任意一个这些位置位**（OR） | 只要 SUID 或其它指定位置位 |
| `-perm -2000` | SGID 位必须为 1 | → SUID 文件如果没 SGID 就不会被匹配 |

- **记法**：`-` 是「至少包含」（像「满足这些约束」），`/` 是「至少命中一个」。`-perm -4000` 覆盖了「SUID 位为 1」的全部情况，所以**审计用 `-`**。
- `-perm /6000` = 「SUID 或 SGID 任意一个置位」，正好是「SUID 或 SGID 文件」的清单。
- ⚠️ **`/` 与 `-` 的写法在不同 find 版本上差异**：GNU find 早期用 `+4000` 表示 OR，POSIX 不标准，现代统一用 `/`。老教程里看到的 `-perm +4000` 在 GNU find 4.5.12+ 已废弃。
- **为什么要 `-xdev`**：不加时 `find /` 会钻进 `/proc`（伪装成文件的进程信息）、`/sys`、以及所有挂载的 NFS/容器层，产生海量噪音甚至卡死。`-xdev` 让 find 停留在同一个文件系统上。
- 🔐 **审计方法**：
  1. 先收集一份「干净基线」（新装系统或已知健康时跑 `④`）；
  2. 定期复查，用 `sha256sum -c` 找被替换的；
  3. 用 `⑤` 找新出现的 SUID；
  4. 每一条都要能回答「这个程序属于哪个包」：
     ```bash
     # Debian/Ubuntu
     dpkg -S /usr/bin/passwd
     # RHEL/Fedora
     rpm -qf /usr/bin/passwd
     # Arch
     pacman -Qo /usr/bin/passwd
     ```
     **查不到包归属的 SUID 文件 = 高度可疑**。
  5. 更省事的自动化工具：`lynis`、`chkrootkit --scandns`、`rkhunter --check`、`aide`。见 [`../commands/12-安全与审计.md`](../commands/12-安全与审计.md)。

</details>

### 9. 🔐 找出全局可写的文件和目录 ⭐⭐⭐

**场景**：你需要一份「任何人都能改」的清单。这是提权排查的核心检查项之一。

**要求**：分别找出全局可写的**目录**、**文件**，并区分「有 sticky 保护」与「没有」。

<details><summary>参考答案</summary>

```bash
# ① 全局可写的目录（-0002 表示 "other 的 w 位为 1"）
find / -xdev -type d -perm -0002 \
     ! -path '/proc/*' ! -path '/sys/*' 2>/dev/null | sort

# ② 其中"没有 sticky 保护"的 —— 这些才是真正的风险点
find / -xdev -type d -perm -0002 ! -perm -1000 \
     ! -path '/proc/*' ! -path '/sys/*' 2>/dev/null | sort

# ③ 全局可写的普通文件
find / -xdev -type f -perm -0002 \
     ! -path '/proc/*' ! -path '/sys/*' 2>/dev/null | sort

# ④ 全局可写 + 全局可执行（能被人放进去就跑的脚本）
find / -xdev -type f -perm -0003 2>/dev/null | sort

# ⑤ 沙盒里练手（范围小、结果确定）
cd /tmp/linux-practice
echo "--- 全局可写目录 ---"
find . -type d -perm -0002 -printf '%M %p\n'
echo "--- 全局可写文件 ---"
find . -type f -perm -0002 -printf '%M %p\n'
echo "--- 全局可写但没有 sticky 的目录（高风险）---"
find . -type d -perm -0002 ! -perm -1000 -printf '%M %p\n'
```

**预期输出（⑤）**：

```text
--- 全局可写目录 ---
drwxrwxrwx ./shared
--- 全局可写文件 ---
-rw-rw-rw- ./secret/readme.txt
--- 全局可写但没有 sticky 的目录（高风险）---
drwxrwxrwx ./shared
```

**解析：`-0002` 这种写法的含义**

- 前导 `-` 表示「这些位**全部**置位」（见第 8 题的 `/` vs `-` 区别）。
- 八进制 `0002` 的四位分别是「特殊位、属主、属组、其他人」。所以 `-0002` = 「**其他人**的写位必须为 1」——等价于「全局可写」。
- 同理：
  | 写法 | 含义 |
  |------|------|
  | `-0002` | 其他人可写（全局可写） |
  | `-0003` | 其他人可写且可执行 |
  | `-0020` | 属组可写 |
  | `-0100` | 其他人可执行 |
  | `-1000` | 有 sticky 位 |
  | `-4000` | 有 SUID |
  | `-0022` | 属组可写**且**其他人可写 |

  **每一位对应一列**：从左到右 = 特殊位 / u / g / o，和 `ls -l` 的显示顺序一致。

- **为什么「全局可写目录」比「全局可写文件」更严重**：
  - 全局可写的**文件**：别人能改**内容**。如果这个文件是被 root 执行/读取的，就有提权可能。
  - 全局可写的**目录**：别人能在里面**创建、删除、替换**任意文件。这意味着即使目录里的文件权限很严，攻击者也能先删掉再用自己的版本重建。**权限控制完全失效**。

- 🔐 **典型提权场景**：
  1. `crontab` 或 `systemd timer` 调用的脚本位于一个全局可写目录里 → 替换脚本 → 下次定时执行时以 root 运行。
  2. `/etc/ld.so.preload` 或某个 `.so` 所在目录全局可写 → 替换成恶意库 → 任何程序启动都加载它（`LD_PRELOAD` 持久化）。
  3. `PATH` 包含一个全局可写目录，且有 SUID 程序调用了不带绝对路径的外部命令 → 放一个同名恶意程序劫持。

- **修复方式**（对应三个不同场景）：

  ```bash
  # ① 目录不该全局可写 → 去掉 o+w，必要时加 sticky
  chmod o-w /path/to/dir
  chmod +t  /path/to/dir          # 确实需要共享可写时，至少加 sticky

  # ② 文件不该全局可写
  chmod o-w /path/to/file

  # ③ 用默认 ACL 做"只给特定组"的精细授权，替代"全局可写"
  setfacl -m g:devteam:rwx /path/to/dir
  setfacl -d -m g:devteam:rwx /path/to/dir
  ```

</details>

### 10. `chown` 的两个大坑：`-R` 和软链接 ⭐⭐

**场景**：你要把一个目录树的属主改成别的用户/组。同事做完之后，发现目录里的软链接指向的目标目录也被人改了属主，整个系统盘上另一个位置的文件属主错乱。

**要求**：说清 `chown` 对软链接的默认行为，并给出安全做法。

<details><summary>参考答案</summary>

```bash
cd /tmp/linux-practice

# 先造一个带软链接的目录（在 /tmp 里练）
rm -rf /tmp/owndir && mkdir -p /tmp/owndir/sub
ln -sfn /tmp/linux-practice/data /tmp/owndir/mylink

echo "=== 起始状态 ==="
ls -ld /tmp/owndir/mylink
stat -c '%U:%G  %n' /tmp/linux-practice/data

echo "=== ① 不带 -h：chgrp 会跟随软链接，改的是【目标】 ==="
chgrp rivo /tmp/linux-practice/data      # 先把两边设成不同的组以便观察
chgrp rivo /tmp/owndir/mylink
chgrp docker /tmp/owndir/mylink          # ← 改的是目标！
echo "链接自身: $(stat -c %G /tmp/owndir/mylink)"
echo "链接目标: $(stat -c %G /tmp/linux-practice/data)"

echo "=== ② 带 -h：改的是【链接自身】 ==="
chgrp rivo /tmp/linux-practice/data
chgrp -h docker /tmp/owndir/mylink
echo "链接自身: $(stat -c %G /tmp/owndir/mylink)"
echo "链接目标: $(stat -c %G /tmp/linux-practice/data)"

echo "=== ③ 带 -R：GNU chown 默认【不跟随】遍历中遇到的软链接 ==="
chgrp rivo /tmp/owndir/mylink
chgrp -R docker /tmp/owndir
echo "链接自身: $(stat -c %G /tmp/owndir/mylink)"
echo "链接目标: $(stat -c %G /tmp/linux-practice/data)"   # 没变
```

**预期输出**：

```text
① 不带 -h：链接自身=rivo，链接目标=docker    ← 目标被改了
② 带 -h：  链接自身=docker，链接目标=rivo    ← 只改链接
③ 带 -R：  链接自身=docker，链接目标=rivo    ← 目标未被波及
```

**实战命令模板**：

```bash
# 安全改属主（需要 root；本人操作自己的文件时只能改到这组）
sudo chown -Rh alice:devteam /srv/myapp        # -R 递归 + -h 处理链接自身
sudo chown -Rh --from=olduser:oldgroup alice:devteam /srv/myapp   # 只改匹配的（GNU）

# 先看会改什么，再执行（最重要的一步）
find /srv/myapp -printf '%u:%g %p\n' | sort | uniq -c | sort -rn | head

# 只改属组，不改属主（更安全，且可以不带 root —— 如果目标组是你在的组）
chgrp -Rh devteam /srv/myapp
```

**解析**：

- **`chown` / `chgrp` 不带 `-h` / `-R` 时，对软链接会跟随到目标**（`-h` = `--no-dereference`，只影响链接本身）。这是 POSIX 行为，也是最容易被忽视的。
- **`chown -R` 时 GNU 的默认是 `-P`**（不跟随遍历中遇到的软链接）。所以 `-R` 本身相对安全，但**命令行里直接给出的那个软链接参数会被跟随**，除非加 `-h`。
- **`-H` / `-L` / `-P` 三个参数控制遍历时对软链接的处理**：
  | 参数 | 含义 |
  |------|------|
  | `-P`（默认） | 不跟随任何软链接 |
  | `-H` | 只跟随**命令行参数**里的软链接 |
  | `-L` | 跟随**所有**软链接 |
  ⚠️ `-L` 非常危险：如果遍历到指向 `/` 的软链接，`chown -RL` 会试图改动**整个系统盘**的属主。
- ⚠️ **根本原则：`chown -R` 之前一定要先 `find ... -printf '%u:%g %p\n'` 看清范围，并确认路径里没有软链接或挂载点逃逸。** 属主信息**没有备份可言**（`chown` 不记录原值，`stat` 的 `%u` 只在当前状态下有效），改错了基本无法批量还原。
- ⚠️ **绝不要对系统路径做无意识的 `-R`**：`chown -R user:user /usr`、`chown -R user:user /etc` 会让 `sudo`、`su`、`ssh`、`systemd` 大面积失效（很多程序会拒绝以「属主不对」的权限文件运行）。
- 💡 只想改「属主是 A 的文件」用 `--from`（GNU 扩展），能避免误伤：
  ```bash
  sudo chown -Rh --from=olduser:oldgroup newuser:newgroup /srv/myapp
  ```
- 💡 只改**属组**时如果目标组是你在的组，**不需要 root**：`chgrp devteam file` 就够了。这也是唯一能在非 root 下完整练习 `chown` 语义的方式。

</details>

### 11. `umask` 怎么算：新建的文件为什么不是 666 ⭐⭐

**场景**：你 `touch` 一个新文件，期望是 `666`（人人可写），实际是 `644`。新建目录也不是 `777` 而是 `755`。

**要求**：解释 `umask` 的计算规则，并算出 `umask 022`、`027`、`077`、`002` 各自对应的新建权限。

<details><summary>参考答案</summary>

```bash
# 查看当前 umask
umask            # 0022
umask -S         # u=rwx,g=rx,o=rx    ← 符号形式：表示"要保留的位"

# 实验：不同 umask 下新建文件/目录的权限
for m in 022 027 077 002 000 777; do
  ( umask "$m"
    : > /tmp/um-f; mkdir -p /tmp/um-d
    printf 'umask %-4s → 文件 %s  目录 %s\n' \
      "$m" "$(stat -c %a /tmp/um-f)" "$(stat -c %a /tmp/um-d)"
    rm -f /tmp/um-f; rmdir /tmp/um-d )
done
```

**预期输出**：

```text
umask 022  → 文件 644  目录 755
umask 027  → 文件 640  目录 750
umask 077  → 文件 600  目录 700
umask 002  → 文件 664  目录 775
umask 000  → 文件 666  目录 777
umask 777  → 文件 000  目录 000
```

**解析：计算规则**

```
新建文件的权限 = 666  &  (~umask)     ← 起始基准 666（没有执行位！）
新建目录的权限 = 777  &  (~umask)     ← 起始基准 777
```

- **基准值不是 777**：新建**文件**不会自动带执行位（因为绝大多数文件不是程序），所以基准是 `666`。这就是「文件总比目录少一个 `x`」的根源。
- `~umask` 是**按位取反**，然后与基准做**按位与**。等价说法：**从基准里去掉 umask 中置位的那些权限**。

  逐步算 `umask 027`：

  ```text
  基准（文件）:    666 = 110 110 110
  umask:           027 = 000 010 111
  ~umask:               111 101 000
  ─────────────────────────────────────
  666 & ~027  =   640 = 110 100 000     → rw- r-- ---
  ```

  ```text
  基准（目录）:    777 = 111 111 111
  ~umask:               111 101 000
  ─────────────────────────────────────
  777 & ~027  =   750 = 111 101 000     → rwx r-x ---
  ```

- **`umask -S` 的符号表示是「保留什么」**，与数字形式语义相反，别搞混：
  ```text
  umask 022    → 0600/0644（八进制数，表示"去掉什么"）
  umask -S     → u=rwx,g=rx,o=rx（表示"保留什么"）
  ```
  反推：数字形式里为 1 的位 = 符号形式里**没有**的位。

**各 umask 的适用场景**：

| umask | 文件 | 目录 | 适用场景 |
|-------|------|------|---------|
| `022` | `644` | `755` | **绝大多数发行版默认**。组内只读，其他人可读 |
| `027` | `640` | `750` | 更严格：其他人完全看不到 |
| `077` | `600` | `700` | 私有目录（如 `~/.ssh`）。**多用户共享机器的推荐值** |
| `002` | `664` | `775` | 团队协作目录：组内可写（见第 6 题） |
| `007` | `660` | `770` | 严格限组：其他人无任何权限 |

- **`umask` 只影响「新建」**已存在的文件权限不会被改。
- **`umask` 不影响显式指定权限的命令**：`chmod 777 f` 就是 777，`install -m 755` 就是 755，`mkdir -m 700` 就是 700。因为 `umask` 只在创建时由内核应用，而显式指定的模式会与 `~umask` 做与运算……**注意**：`mkdir -m` 和 `install -m` 会**绕过** umask，而 `touch`（内部用 `open(2)` 的 `mode` 参数）**会**受 umask 影响。这是两者行为差异的来源。
- ⚠️ **不安全的值**：`umask 000` 会让所有新文件全局可写（`666`）。这在多用户机器上等于放弃了文件保护。

</details>

### 12. 临时改 `umask` 而不影响当前 shell ⭐⭐

**场景**：你有一段脚本要创建几个私密文件，需要一个更严格的 `umask`，但**不希望**改完之后当前终端的 `umask` 也变了（否则你后面手敲创建的文件全变成 600）。

**要求**：给出三种隔离方式。

<details><summary>参考答案</summary>

```bash
echo "当前: $(umask)"

# ① 子 shell 隔离（推荐）：( ... ) 里改的东西不影响外面
( umask 077; : > /tmp/private1; mkdir -p /tmp/private-d )
stat -c '%a %n' /tmp/private1 /tmp/private-d
echo "外面还是: $(umask)"        # 0022 ← 没变

# ② 保存 → 修改 → 恢复（同一个 shell 里临时用）
old=$(umask)
umask 077
: > /tmp/private2
umask "$old"                     # 恢复
echo "恢复后: $(umask)"

# ③ 用 trap 保证异常退出也能恢复（最稳）
save=$(umask)
trap 'umask "$save"' EXIT
umask 077
: > /tmp/private3
# ... 这里做你的工作
# 无论正常结束还是 Ctrl+C，都会恢复

# 永久生效（写进启动文件）——注意这时候是"真的改"
# echo 'umask 027' >> ~/.bashrc       # 用户级
# echo 'umask 027' > /etc/profile.d/umask.sh   # 系统级（需 root）
```

**预期输出**：

```text
当前: 0022
600 /tmp/private1
700 /tmp/private-d
外面还是: 0022
恢复后: 0022
```

**解析**：

- **`umask` 是 shell 内建命令**，改的是**当前 shell 进程**的属性。它会**被子进程继承**，但不会往上影响父进程。所以：
  - `bash script.sh`（子进程执行）：脚本里 `umask` 不影响你的终端——**天然隔离**。
  - `source script.sh` / `. script.sh`（当前 shell 执行）：会**污染**你的终端。
- **`( ... )` 子 shell 是最省心的隔离手段**，一行搞定，不用管恢复。
- `trap '...' EXIT` 的价值：如果中间某步出错退出（`exit`）或被 `Ctrl+C` 打断，恢复代码依然会执行。手写的「改回去」语句在这种时候会被跳过。
- 💡 更精确的做法：**不用改 umask，直接指定权限**。
  ```bash
  install -m 600 /dev/null /tmp/private4      # 直接建一个 600 的文件
  ( umask 077; touch /tmp/private5 )          # 只要一个文件时这样也行
  ```
- 💡 系统级默认 umask 的配置位置：
  - `/etc/profile`（登录 shell）
  - `/etc/bashrc`（RHEL）/ `/etc/bash.bashrc`（Debian）
  - `/etc/login.defs` 的 `UMASK`（同时影响用户主目录创建、`useradd` 等）
  - systemd 服务：在 unit 里写 `UMask=0077`

  ⚠️ 对 systemd 服务来说，**`/etc/profile` 的 umask 完全不生效**（服务不是登录 shell 启动的）。这是「手动跑脚本正常、做成服务就权限不对」的经典原因。

</details>

### 13. `setfacl` 给「一个特定用户」开权限，而不动属组 ⭐⭐⭐

**场景**：`/srv/reports` 目录属于 `root:devteam`，权限 `750`。现在要额外允许审计员 `auditor` 只读访问，**但不能**把她加进 `devteam`（她不该有写权限），也**不能**把目录改成全局可读。

**要求**：用 ACL 完成，并验证。

<details><summary>参考答案</summary>

```bash
# 需要 root 才能 chown；非 root 用 /tmp 下的文件练 ACL 语法
sudo mkdir -p /srv/reports && sudo chown root:devteam /srv/reports && sudo chmod 750 /srv/reports

# 给 auditor 这个用户加只读+进入权限
sudo setfacl -m u:auditor:rx /srv/reports

# 查看
sudo getfacl -p /srv/reports
sudo ls -ld /srv/reports
```

**非 root 的等价练习**（在 /tmp 下做，语法与效果完全一致）：

```bash
cd /tmp
rm -f /tmp/acl-file && echo "机密内容" > /tmp/acl-file
chmod 640 /tmp/acl-file

echo "=== 改前 ==="
ls -l /tmp/acl-file

echo "=== 给 nobody 加读权限 ==="
setfacl -m u:nobody:r /tmp/acl-file
ls -l /tmp/acl-file                  # 注意权限串末尾多了个 +
getfacl -p /tmp/acl-file

echo "=== 给 wheel 组加读写 ==="
setfacl -m g:wheel:rw /tmp/acl-file

echo "=== 给所有人加读（等价于 a::r，不是加 ACL，是改 other 位）==="
setfacl -m o::r /tmp/acl-file

echo "=== 删除单条 ACL ==="
setfacl -x u:nobody /tmp/acl-file

echo "=== 清空全部 ACL ==="
setfacl -b /tmp/acl-file
ls -l /tmp/acl-file                  # 末尾的 + 消失
```

**预期输出**：

```text
$ ls -l /tmp/acl-file
-rw-r-----+ 1 rivo rivo 13 ... /tmp/acl-file
          ↑ 这个 + 号 = 有扩展 ACL

$ getfacl -p /tmp/acl-file
# file: /tmp/acl-file
# owner: rivo
# group: rivo
user::rw-              ← 属主权限（u::）
user:nobody:r--        ← 给单个用户 nobody 的权限
group::r--             ← 属组权限（g::）
group:wheel:rw-        ← 给轮组 wheel 的权限
mask::rw-              ← ACL 掩码（决定"有效权限"的上限）
other::---             ← 其他人
```

**解析**：

**ACL 是什么**：传统 rwx 只能表达「属主 / 属组 / 其他人」三类。ACL 允许给**任意多个具体用户和组**分别授权，不需要改变属组、也不需要复制文件。

**`setfacl` 的常用语法**：

| 命令 | 作用 |
|------|------|
| `setfacl -m u:alice:rw file` | 给用户 alice 加读写 |
| `setfacl -m g:dev:rwx dir` | 给组 dev 加读写执行 |
| `setfacl -m o::- file` | 改「其他人」权限（等价 chmod o=） |
| `setfacl -m m::rx file` | 设置 mask（有效权限上限） |
| `setfacl -x u:alice file` | **删除** alice 这一条 |
| `setfacl -b file` | **清空所有** ACL |
| `setfacl -R -m ...` | 递归 |
| `setfacl -d -m ...` | 设置**默认 ACL**，让新文件继承（第 15 题） |
| `setfacl -k dir` | 删除默认 ACL |

**关键点**：

- **`ls -l` 里权限串末尾的 `+`** 是唯一提示「有扩展 ACL」的信号。**看到 `+` 就必须用 `getfacl` 看细节**——`ls -l` 显示的 `rw-r-----` 可能只是 mask，真正的权限分配藏在 ACL 里。这是权限排查里最容易漏的一环。
- **ACL 的权限项顺序比你预期的多**：`user::`（属主）、`user:name:`（具体用户）、`group::`（属组）、`group:name:`（具体组）、`mask::`、`other::`。别名：`u::` = `user::`、`g::` = `group::`、`o::` = `other::`、`m::` = `mask::`。
- 💡 不显示注释头部（便于脚本解析）：`getfacl -cp file`。
- 💡 备份与恢复 ACL：`getfacl -R dir > acl.bak` + `setfacl --restore=acl.bak`。
- ⚠️ **`cp` / `tar` 默认不带 ACL**。要保留用 `cp -a`、`tar --acls`、`rsync -A`。否则「恢复了备份但 ACL 全丢」是常见事故。
- ⚠️ 文件系统必须支持 ACL。ext4 默认支持；`tmpfs` 也支持（沙盒在 `/tmp` 上所以能用）；但 NFS 需要服务端支持，某些容器/精简内核可能编译时关闭。

</details>

### 14. `getfacl` 里的 `mask` 和 `#effective` 是什么 ⭐⭐⭐

**场景**：你给了用户 `nobody` 一个 `rwx` 的 ACL，但 `nobody` 实际只能读。`getfacl` 输出里写着 `user:nobody:rwx  #effective:r--`。

**要求**：解释 `mask` 的机制，并说明为什么「ACL 给了权限但不生效」。

<details><summary>参考答案</summary>

```bash
cd /tmp
rm -f /tmp/mask-demo && echo x > /tmp/mask-demo

# ① 给 nobody 完整 rwx
setfacl -m u:nobody:rwx /tmp/mask-demo
getfacl -p /tmp/mask-demo | grep -E 'nobody|mask|group::|other::'

# ② 现在把 mask 收到只读
setfacl -m m::r /tmp/mask-demo
getfacl -p /tmp/mask-demo | grep -E 'nobody|mask'

# ③ 想真正全放开：把 mask 也放到 rwx
setfacl -m m::rwx /tmp/mask-demo
getfacl -p /tmp/mask-demo | grep -E 'nobody|mask'

# ④ 用符号简写：setfacl -m u:nobody:rw 会自动重算 mask（除非后面显式给 m::）
```

**预期输出**：

```text
①  user:nobody:rwx
    mask::rwx

②  user:nobody:rwx	#effective:r--        ← 注意这个 #effective 注释
    mask::r--                             ← mask 被收到只读

③  user:nobody:rwx
    mask::rwx
```

**解析**：

- **`mask` 是「ACL 条目的有效权限上限」**。它**只约束**这三类条目：
  - 所有**具名用户**条目（`user:alice:`、`user:bob:`）
  - 所有**具名组**条目（`group:dev:`）
  - **属组**条目（`group::`）

  它**不约束** `user::`（属主）和 `other::`（其他人）。

- **实际生效的权限 = 该条目的权限 & mask**，按位与。

  ```text
  user:nobody:rwx   = 111
  mask::r--         = 100
  ─────────────────────────
  有效权限           = 100  → 只有读
  ```

- `getfacl` 在**有效权限与声明权限不一致**时会自动加 `#effective:r--` 注释。**看到 `#effective` 就意味着「你写的权限没完全生效」**，需要检查 mask。
- **mask 为什么存在**：它让「整体权限收紧」变得容易。例如你要临时把整个文件设为只读，只需 `setfacl -m m::r file`，所有具名条目同时被压到只读，之后恢复 `m::rwx` 就全回来了。此外，`chmod` 对带 ACL 的文件操作 `group` 位时，**改的其实就是 mask**——这保证了「`chmod g-w` 之后 ACL 也不会意外给予写权限」的直觉一致性。
- **什么时候 mask 会自动被重算**：用 `setfacl -m` 添加 ACL 条目时，如果不显式指定 `m::`，`setfacl` 会把 mask 更新为「所有 ACL 条目权限的并集」。所以 ① 里 mask 是 `rwx`。但一旦你**显式**给过 `m::`，后续添加条目时 mask 就**不再自动扩大**（只会收缩或保持）——这就是「加了 ACL 却不生效」的最常见原因。
- 💡 诊断流程：

  ```bash
  getfacl -p file | grep -E '^(user|group|mask|other)'   # 看全部条目
  getfacl -p file | grep '#effective'                     # 只看"没完全生效"的条目
  # 修复：把 mask 放开
  setfacl -m m::rwx file
  ```

  💡 让 `getfacl` 直接输出「计算后的有效权限」也可以：
  ```bash
  # 有些版本支持，或直接用 namei 交叉验证
  namei -l /tmp/mask-demo        # 显示路径上每一级的权限（排查"哪一级挡住了"）
  ```

- 🔐 **审计提示**：`#effective` 条目是 ACL 配置出错的重灾区。检查权限问题时如果只看 `ls -l`（显示的是 mask），会完全看不到「具名用户被限制」这件事。

</details>

### 15. 默认 ACL：让目录里新创建的文件自动继承权限 ⭐⭐⭐

**场景**：共享目录 `/srv/shared` 需要让新来的文件**自动**对 `devteam` 组可读写。用 `umask` 会影响全局，用 `chmod -R` 只能处理已有文件、新文件管不到。

**要求**：用默认 ACL 实现「新文件自动继承」。

<details><summary>参考答案</summary>

```bash
# 非 root 的等价练习（在 /tmp 下，语法与效果一致）
mkdir -p /tmp/acl-inherit
chmod 750 /tmp/acl-inherit

# 设置【默认 ACL】：-d 表示这些规则被子目录/新文件继承
setfacl -d -m u:nobody:rwx /tmp/acl-inherit

echo "=== 目录自身的 ACL ==="
getfacl -p /tmp/acl-inherit

echo "=== 在目录里新建文件/子目录 ==="
touch /tmp/acl-inherit/newfile
mkdir -p /tmp/acl-inherit/newdir

echo "=== 新文件继承了什么 ==="
getfacl -cp /tmp/acl-inherit/newfile
echo "=== 新子目录继承了什么（包括默认 ACL） ==="
getfacl -cp /tmp/acl-inherit/newdir
```

**预期输出**：

```text
=== 目录自身的 ACL ===
# file: /tmp/acl-inherit
# owner: rivo
# group: rivo
user::rwx
group::r-x
other::r-x
default:user::rwx              ← 默认 ACL 开始
default:user:nobody:rwx
default:group::r-x
default:mask::rwx
default:other::r-x

=== 新文件 ===
user::rw-
user:nobody:rwx	#effective:rw-     ← 继承到了条目，但文件没有 x 位所以被 mask 削掉
group::r-x	#effective:r--
mask::rw-
other::r--

=== 新子目录 ===
user::rwx
user:nobody:rwx
group::r-x
default:user::rwx                  ← 子目录连"默认 ACL"都继承了
default:user:nobody:rwx
default:group::r-x
default:mask::rwx
default:other::r-x
```

**完整实战：一个自动继承的团队共享目录**

```bash
sudo mkdir -p /srv/shared
sudo chown root:devteam /srv/shared
sudo chmod 2775 /srv/shared                    # SGID：继承属组
sudo setfacl -d -m g:devteam:rwx /srv/shared   # 默认 ACL：组内可读写
sudo setfacl -d -m o::--- /srv/shared          # 默认：其他人无权
sudo setfacl -d -m m::rwx /srv/shared          # 默认 mask 放开（关键！）
sudo setfacl -R -m g:devteam:rwX /srv/shared   # 已有内容也统一一遍

# 验证
sudo -u alice touch /srv/shared/test.txt
ls -l /srv/shared/test.txt
getfacl -cp /srv/shared/test.txt
```

**解析**：

- **默认 ACL（default ACL）**只对**目录**有意义，作用是「这个目录里**将来**创建的东西自动套用这些规则」。
- 默认 ACL 的条目在 `getfacl` 里带 `default:` 前缀。它**不影响目录自身**的权限，所以常见做法是「普通 ACL + 默认 ACL 都设一遍」：
  ```bash
  setfacl -m  g:devteam:rwx /srv/shared        # 目录自己
  setfacl -d -m g:devteam:rwx /srv/shared      # 将来创建的东西
  ```
- **继承规则**（POSIX ACL 标准）：
  | 新建什么 | 继承什么 |
  |---------|---------|
  | 普通文件 | 目录的 `default:` 条目 → 转成普通 ACL；**默认 ACL 条目本身不继承** |
  | 子目录 | 目录的 `default:` 条目 → **既转成普通 ACL，又继续作为自己的默认 ACL**（所以能一直传下去） |
  | 普通文件 | **不会**继承执行位（文件初始权限里没有 `x`，所以 `default:mask::rwx` 里的 `x` 会被削掉 → 出现 `#effective`） |

- **必须显式设 `default:mask::rwx`**（或让 `setfacl -d -m` 自动算）。这是最容易漏的一步：如果 mask 没跟上，继承下来的条目会被压成 `#effective:r--`，然后你会看到「权限配了但同事还是写不了」。
- **`-R` 与 `-d` 组合**：`setfacl -R -d -m ...` 会给整棵子树的所有目录都设默认 ACL。这是「让一个已存在的目录树全面启用继承」的标准做法。
- ⚠️ 注意备份/恢复要带 `--acls`，否则 ACL 全丢（`tar --acls -czf`、`rsync -A`、`cp -a`）。
- ⚠️ 挂载选项可能禁用 ACL：某些 NFS 挂载、`/etc/fstab` 里的 `noacl`、或文件系统编译时未启用 ACL 支持。`setfacl` 报 `Operation not supported` 就是这个原因（此时该用 `mount -o remount,acl`）。

</details>

### 16. 🔐 `sudo` 与 `sudoers`：为什么不能直接编辑 ⭐⭐⭐

**场景**：团队的新同事需要能重启 `nginx` 和查看日志，但**不该**给他完整 root。

**要求**：给出正确的 sudoers 配置方式，并说明「为什么必须用 `visudo`」、「`NOPASSWD` 的风险」。

<details><summary>参考答案</summary>

```bash
# ① 永远用 visudo（会用 $EDITOR 打开 + 保存时做语法检查 + 加锁防止并发编辑）
sudo visudo

# ② 更好的做法：不改 /etc/sudoers，而是加一个 drop-in 文件
sudo visudo -f /etc/sudoers.d/devops
```

在 `visudo` 里写入（**drop-in 文件里不要写 `Defaults` 之外的全局设置**，格式与主文件相同）：

```sudoers
# 语法： 用户  主机=(可切换到的用户:组)  命令
# 「谁能」  「在哪」  「以谁的身份」        「能跑什么」

# 让 alice 能在任何主机上以 root 身份重启/停止/启动 nginx，
# 且不需要输入自己的密码
alice  ALL=(root) NOPASSWD: /usr/bin/systemctl restart nginx, \
                           /usr/bin/systemctl stop nginx, \
                           /usr/bin/systemctl start nginx, \
                           /usr/bin/systemctl status nginx

# 让 devteam 组能查看任何日志（只读）
%devteam  ALL=(root) /usr/bin/journalctl, /usr/bin/tail, /usr/bin/cat

# 拒绝某些命令（注意：sudoers 是"允许清单"模型，deny 规则要小心使用）
# bob ALL=(ALL) ALL, !/usr/bin/su
```

**检查与使用**：

```bash
# 看某用户的 sudo 权限（需要先有权限跑 sudo -l）
sudo -l -U alice

# 自己看自己的
sudo -l

# 语法检查（不进入编辑）
sudo visudo -c
sudo visudo -cf /etc/sudoers.d/devops
```

**预期输出（`sudo -l`）**：

```text
User rivo may run the following commands on omarchy:
    (ALL : ALL) ALL
```

**解析**：

**sudoers 的格式**：

```
用户/组   主机列表 = (可切换到的用户:组)  命令列表
   ↓          ↓            ↓                 ↓
 alice      ALL        (root)          /usr/bin/systemctl restart nginx
 %devteam   ALL        (ALL:ALL)       ALL
```

| 部分 | 说明 |
|------|------|
| 用户/组 | 用户名，组要加 `%` 前缀（`%wheel`、`%sudo`） |
| 主机 | `ALL` 或主机名列表。**本地 sudo 基本都写 `ALL`** |
| `(可切换到的用户:组)` | `-u` 参数能切换到的目标 |
| 命令 | **必须写绝对路径**，可以用逗号分隔多个，反斜杠续行 |
| `NOPASSWD:` | 前缀，表示免密 |
| `Defaults` | 全局选项，如 `Defaults timestamp_timeout=5`（5 分钟后重新要密码）、`Defaults secure_path="..."`、`Defaults logfile="/var/log/sudo.log"` |

**为什么必须用 `visudo`**：

1. **语法校验**：`visudo` 在保存前会跑一遍解析器。**如果 `/etc/sudoers` 有语法错误，sudo 会拒绝任何人使用**（包括 root 用 sudo），这是「一把锁把自己锁在门外」的经典事故。`visudo` 检测到错误会提示你「重新编辑 / 放弃保存」。
2. **加锁**：防止两个管理员同时编辑导致内容交错损坏。
3. **原子写入**：用临时文件 + `rename`，避免写到一半断电导致文件残缺。

- **`/etc/sudoers.d/` drop-in 目录**：比直接改主文件更安全、更好管理（每个服务一个文件、便于审计和回滚）。**注意**：
  - 用 `visudo -f /etc/sudoers.d/xxx` 来编辑（才有语法检查）。
  - 文件名**不能**含 `.` 或以 `~` 结尾，否则会被 `#includedir` 跳过（防止编辑器备份文件被当成配置）。
  - 主 `/etc/sudoers` 里通常已经有一行 `#includedir /etc/sudoers.d`（**注意没有前导 `#` 才是生效**，`#includedir` 是特例：带 `#` 也是有效指令）。

- 🔐 **`NOPASSWD` 的风险**：
  - 它把「知道你的登录密码」这层二次验证去掉了。任何拿到你 shell 的人（比如通过某个 Web 漏洞获得一个低权 shell）都能立刻用这条规则拿 root。
  - 所以 `NOPASSWD` 只应给**极窄的、参数固定的**命令。像 `NOPASSWD: /bin/bash`、`NOPASSWD: /usr/bin/vim`、`NOPASSWD: ALL` 等于直接给了 root。

- 🔐 **sudo 规则的经典绕过**（写规则时必须避免）：
  | 错误规则 | 怎么绕过 |
  |---------|---------|
  | `alice ALL=(root) /usr/bin/systemctl` | `systemctl` 的 `--unit` + 可控 service 文件 → 任意命令。`systemctl edit` 可执行任意二进制 |
  | `alice ALL=(root) /usr/bin/vim` | `:!bash` 逃逸到 shell |
  | `alice ALL=(root) /bin/tar` | `tar --checkpoint-action=exec=sh` |
  | `alice ALL=(root) /usr/bin/find` | `find . -exec /bin/bash \;` |
  | `alice ALL=(root) /usr/bin/less` | `!bash` |
  | `alice ALL=(root) /usr/bin/cat` | 可以读 `/etc/shadow`、`~/.ssh/id_rsa` |
  | `alice ALL=(root) /usr/bin/env` | `env /bin/bash` |
  | `alice ALL=(root) /usr/bin/python3` | `python3 -c 'import os;os.system("sh")'` |
  | 带通配符且通配符能匹配到空格 | `alice ALL=(root) /bin/echo *` → `echo a; bash` |
  | 用相对路径 | 攻击者改 `PATH` 就能劫持 |

  **安全写法的原则**：命令用绝对路径、参数**完全固定**（不用通配符、不让人传参）、不要给「能读任意文件」「能执行任意命令」的工具。

- 💡 审计：
  ```bash
  sudo -l                              # 自己的权限
  sudo -l -U alice                     # 指定用户
  sudo -l -l                           # 详细模式
  grep -r . /etc/sudoers /etc/sudoers.d/   # 全部规则
  journalctl -u sudo -n 50 --no-pager      # sudo 的日志（含"用户执行了什么"）
  sudo grep -r 'sudo' /var/log/auth.log*   # Debian 系
  ```
- ⚠️ 恢复「sudoers 写坏了、sudo 用不了」的流程：
  1. 用 **单用户模式 / 救援模式**（`systemd.unit=rescue.target`），或以 root 直接登录（`su -`）；
  2. `visudo` 修复，或用 `visudo -c` 定位错误行；
  3. 如果是远程服务器且没有 root 直登通道，那就只能进救援模式——这是「改配置前先开第二个 SSH 会话验证」的经典理由。
- 💡 **`sudo -i` vs `sudo su -` vs `sudo -s`**：
  | 命令 | 行为 |
  |------|------|
  | `sudo -i` | 以 root 身份启动**登录 shell**（读 `/etc/profile`、`~/.profile`，`HOME=/root`，`PATH` 变成 root 的） |
  | `sudo -s` | 以 root 身份启动交互式**非登录** shell（保留大部分原环境变量） |
  | `sudo su -` | 先 sudo 再 su，等价 `sudo -i` 但多一层 |
  | `sudo cmd` | 只跑一条命令，环境基本不变 |
  推荐 `sudo -i`。

</details>

### 17. 📦 创建用户、设密码、设有效期 ⭐⭐

**场景**：新同事 `devuser` 入职，需要：主目录 `/home/devuser`、登录 shell 用 bash、加入 `devteam` 组（保留原有组）、首次登录必须改密码、密码 90 天过期。

**要求**：给出完整命令序列。

> 📦 本机无 root 权限，**以下命令未能实测**（`useradd`/`passwd`/`chage` 需要 root）。语法来自 `man` 与 `commands/03-权限与用户.md`，请在容器（`docker run --rm -it debian:stable bash`）或自己的虚拟机里验证。

<details><summary>参考答案</summary>

```bash
# ① 建组（-f = 已存在时不报错）
sudo groupadd -f devteam

# ② 建用户
#    -m  创建主目录（并按 /etc/skel 填充）
#    -s  指定登录 shell
#    -G  附加组（注意是"附加"）
#    -c  注释（通常是姓名）
#    -d  指定主目录路径（默认 /home/<name>）
sudo useradd -m -s /bin/bash -G devteam -c "Dev User" devuser

# ③ 设密码（交互式，会提示输入两次，输入不回显）
sudo passwd devuser

# ④ 强制首次登录改密码
sudo passwd -e devuser                 # -e = expire，让密码立刻过期
# 或用 chage
sudo chage -d 0 devuser                # -d 0 = 上次修改日期设为 1970-01-01 = 立即需改

# ⑤ 密码 90 天过期，过期前 7 天开始提醒
sudo chage -M 90 -W 7 devuser

# ⑥ 查看有效期配置
sudo chage -l devuser
```

**预期输出（`chage -l devuser`）**：

```text
Last password change                                    : password must be changed
Password expires                                        : password must be changed
Password inactive                                       : never
Account expires                                         : never
Minimum number of days between password change          : 0
Maximum number of days between password change          : 90
Number of days of warning before password expires       : 7
```

**解析**：

**核心命令分工**：

| 命令 | 作用 |
|------|------|
| `useradd` | 只创建**账号**（写 `/etc/passwd`、`/etc/shadow`、`/etc/group`）。**不会设密码、不会建主目录**（除非 `-m`） |
| `adduser` | Debian 系的**交互式包装脚本**，自动 `mkdir` + 提示设密码 + 抄 `/etc/skel`。RHEL 系没有 |
| `usermod` | 改属性（组、shell、主目录、锁定） |
| `userdel` | 删账号。`-r` 同时删主目录和邮件池 |
| `passwd` | 改密码 |
| `chage` | 改密码/账号有效期策略 |
| `groupadd`/`groupmod`/`groupdel`/`gpasswd` | 组的增删改与成员管理 |

**必须记住的几个坑**：

- **`-m` 不能漏**。`useradd devuser` 不建主目录，用户登录后会看到 `Could not chdir to home directory`，而且 shell 无法读取 `~/.bashrc`（所以环境变量、别名全没）。
- **`-G` vs `-g`**：
  - `-G`（大写）是**附加组**列表（逗号分隔）。
  - `-g`（小写）是**主组**（只能有一个）。
- 🔐 **`usermod -aG` 里的 `-a` 绝对不能漏**。`usermod -G devteam alice` 会把 alice **从除 devteam 外的所有组里移出**，可能直接让她丢掉 `sudo`（若是靠 `%wheel` 授权）。这是最经典的运维事故。

  ```bash
  # ✅ 追加一个组
  sudo usermod -aG devteam alice
  # ❌ 会覆盖组列表（可能踢掉 wheel/sudo）
  sudo usermod -G devteam alice
  ```
  **`-a` 只在配合 `-G` 时有意义**，单独用 `usermod -a` 会报错。

- **`passwd` 常用参数**：
  | 参数 | 作用 |
  |------|------|
  | `-e` | 立刻让密码过期（强制下次登录改） |
  | `-l` / `-u` | 锁定 / 解锁账号（在 `/etc/shadow` 密码字段前加 `!`） |
  | `-d` | 清空密码（**危险**：变成空密码可登录） |
  | `-S` | 查看状态（`PS` = 已设密码、`L` = 锁定、`NP` = 无密码） |
  | `-n 7` | 密码最少使用 7 天才允许再改（防绕过历史） |
  | `-x 90` | 最长使用 90 天 |
  | `-w 7` | 过期前 7 天提醒 |
  | `-i 30` | 过期后 30 天不登录就锁定账号 |

- **`chage` 的字段**（对应 `/etc/shadow` 的第 3~8 列）：
  | 字段 | 含义 | 对应参数 |
  |------|------|---------|
  | 上次修改日期 | 从 1970-01-01 起的天数 | `-d` |
  | 最小间隔 | 多少天内不许再改 | `-m` |
  | 最大使用期 | 多少天后必须改 | `-M` |
  | 警告期 | 过期前几天提醒 | `-W` |
  | 不活跃期 | 过期后多少天锁定 | `-I` |
  | 账号失效日期 | 账号何时彻底不可用 | `-E` |

- 🔐 **`-d 0`（立即过期）之后，`chage -l` 会显示 `password must be changed`**，用户 `ssh` 登录或 `su` 登录时会被强制改密码。注意：**用 SSH 密钥登录时不会触发这个强制改密流程**（因为没走 PAM 的密码认证路径），这是有意的安全设计，也容易被忽略。
- 🔐 **批量建用户的安全做法**：
  ```bash
  # ⚠️ 不要这样（密码会进 shell 历史、进 ps 输出）
  # echo "devuser:Passw0rd" | chpasswd

  # 更安全：用随机密码 + 强制首登修改
  pw=$(tr -dc 'A-Za-z0-9!@#%^&*' < /dev/urandom | head -c 16)
  echo "devuser:$pw" | chpasswd
  sudo chage -d 0 devuser
  printf '用户 devuser 初始密码: %s（首次登录必须修改）\n' "$pw"
  ```
  ⚠️ `chpasswd` 从 stdin 读 `用户:密码`，**明文**。在共享机器上通过管道传也有被 `ps` 或审计日志捕获的风险（历史版本的 `ps` 能看到命令行；管道内容不会被 `ps` 看到，但 shell 历史会记录整个命令）。
- 💡 批量建用户 + 同名组 + 主目录 + 附加组，用 `useradd` 的默认行为配置 `/etc/login.defs` 和 `/etc/default/useradd`；
- 💡 **用户与组的关键文件**（见 [`../basics/02-权限与用户体系.md`](../basics/02-权限与用户体系.md)）：
  | 文件 | 内容 | 权限 |
  |------|------|------|
  | `/etc/passwd` | `用户名:x:UID:GID:注释:主目录:shell` | `644` 所有人可读 |
  | `/etc/shadow` | 密码哈希 + 有效期 | `640 root:shadow` **仅 root 可读** |
  | `/etc/group` | `组名:x:GID:成员列表` | `644` |
  | `/etc/gshadow` | 组密码（基本废弃） | `640` |
  | `/etc/login.defs` | `useradd`/`passwd` 的默认策略 | `644` |
  | `/etc/skel/` | 新用户主目录的模板 | — |

</details>

### 18. 确认「我现在是谁、属于哪些组」 ⭐

**场景**：你通过 `sudo -i` 切换了身份，需要确认当前的**有效身份**，以及自己到底在哪些组里。

**要求**：输出 UID/GID、所有组、以及某个具体用户的信息。

<details><summary>参考答案</summary>

```bash
# 当前身份
id                                  # 完整：uid/gid/groups
id -u                               # 只看 UID（数字）
id -un                              # 只看用户名
id -g                               # 只看主组 GID
id -Gn                              # 只看全部组名（脚本里最常用）
uid=1000(rivo) gid=1000(rivo) groups=1000(rivo),966(docker),998(wheel)

whoami                              # 等于 id -un
echo "$USER / $LOGNAME"             # 环境变量（可被伪造，不如 id 可靠）

# 查另一个用户（不需要 root）
id nobody
id -Gn root
groups                              # 等于 id -Gn
groups root

# 从系统数据库查（不依赖本地 /etc/passwd，支持 LDAP/SSSD）
getent passwd rivo
getent group wheel
getent passwd | awk -F: '$3>=1000 && $3<65534 {print $1, $3}'

# 当前进程的有效/真实 UID（SUID 场景下会不同！）
cat /proc/self/status | grep -E '^(Uid|Gid):'
# Uid: 1000 1000 1000 1000     ← 真实 / 有效 / 保存的 / 文件系统
```

**解析**：

- **`id` 比 `whoami` 信息更全、更可靠**。`$USER`、`$LOGNAME` 是**环境变量**，可以被 `env USER=root bash` 伪造（很多脚本错误地依赖它做判断）。`id` 走的是系统调用，拿的是真实身份。
- **`id -Gn`** 是最实用的形式：一行拿到所有组名，方便 `grep`：
  ```bash
  id -Gn | tr ' ' '\n' | grep -qx docker && echo "在 docker 组里"
  # 或
  if id -nG | grep -qw docker; then echo yes; fi
  ```
  `grep -qw` 的 `-w`（整词匹配）很重要，否则 `docker` 会误匹配 `dockeradmin`。
- **`getent` vs 直接读 `/etc/passwd`**：`getent` 查询的是**NSS（Name Service Switch）配置的全部后端**——包括 `/etc/passwd`、LDAP、SSSD、NIS、systemd-homed。企业环境里用户可能根本不在 `/etc/passwd` 里。**脚本里应该用 `getent`，不要 `grep /etc/passwd`**。
- **UID 的四元组**（`/proc/PID/status` 的 `Uid:` 行）：真实 UID / 有效 UID / 保存的 setuid UID / 文件系统 UID。**SUID 程序运行时，有效 UID ≠ 真实 UID**，这正是「提权」的原理：
  ```bash
  # 观察 SUID 生效（以 passwd 为例，普通用户运行时 EUID 是 0）
  # （需要借助能查看进程状态的权限）
  sudo cat /proc/$(pgrep -f '/usr/bin/passwd')/status 2>/dev/null | grep Uid
  ```
- **UID 约定**（[`../basics/02-权限与用户体系.md`](../basics/02-权限与用户体系.md)）：
  | 范围 | 用途 |
  |------|------|
  | 0 | root |
  | 1–999 | 系统账号（服务、daemon），登录 shell 通常是 `/usr/sbin/nologin` |
  | 1000+ | 普通用户（Debian 从 1000、RHEL 从 1000、某些发行版从 500） |
  | 65534 | `nobody`（映射失败时的兜底） |

</details>

### 19. 登录审计：谁登录过、谁在线上、谁失败最多 ⭐⭐

**场景**：怀疑服务器被人登过。你要查：当前谁在线、最近登录记录、失败登录次数。

**要求**：给出四条查询，并说明各读的是哪个文件。

<details><summary>参考答案</summary>

```bash
# ① 当前在线用户（读 /var/run/utmp）
who
who -a                 # 全部信息（含运行级别、init 等）
w                      # 更详细：用户在跑什么、负载、空闲时间
w -h                   # 不要表头
users                  # 只列用户名

# ② 登录历史（读 /var/log/wtmp）
last -n 20             # 最近 20 条
last -F                # 带完整时间戳（年月日时分秒）
last rivo              # 只看某用户
last -x                # 包含 shutdown/runlevel 事件
last reboot            # 重启历史

# ③ 失败登录（读 /var/log/btmp，通常需要 root）
sudo lastb -n 20
sudo lastb -F | head -20

# ④ 各用户最后一次登录（读 /var/log/lastlog）
lastlog                # 全部用户（输出很长）
lastlog -u rivo        # 只看一个用户
lastlog -t 7           # 只显示最近 7 天登录过的
# 若提示 command not found，说明 shadow 工具包没装/不完整

# ⑤ systemd 系统的替代路径（比 last 更新更快）
journalctl _COMM=sshd --since '7 days ago' --no-pager | grep -iE 'Accepted|Failed'
journalctl -u sshd -n 100 --no-pager
journalctl _COMM=login -n 20 --no-pager
```

**预期输出（节选）**：

```text
$ w
 18:17:31 up 1 day,  8:25,  2 users,  load average: 8.32, 6.73, 7.11
USER     TTY       LOGIN@   IDLE   JCPU   PCPU  WHAT
rivo     tty1      Mon09   28:26m  0.18s  0.04s systemctl --user start ...

$ last -n 3 -F
rivo  pts/11  wayland-1  Tue Sep 15 18:18:49 2026 - Tue Sep 15 18:19:02 2026  (00:00)
rivo  pts/15  wayland-1  Tue Sep 15 18:10:54 2026   still logged in
wtmp begins Tue Sep  8 09:51:54 2026
```

**解析：四个命令读四个不同的文件**

| 命令 | 数据来源 | 内容 | 谁能读 |
|------|---------|------|--------|
| `who` / `w` / `users` | `/var/run/utmp` | **当前**登录会话 | 所有人 |
| `last` | `/var/log/wtmp` | **历史**登录/注销/重启记录 | 通常所有人 |
| `lastb` | `/var/log/btmp` | **失败**登录尝试 | 通常 root（`640 root:utmp`） |
| `lastlog` | `/var/log/lastlog` | 每个用户**最后一次**登录 | 通常所有人 |

- 这四个都是「**仅追加的二进制记录文件**」，不是文本，**不能用 `cat`/`grep` 读**，必须用 `utmpdump`/专用工具。误用会看到乱码。
  ```bash
  utmpdump /var/log/wtmp | tail -20          # 转成可读文本
  utmpdump /var/run/utmp
  ```
  💡 用 `utmpdump` 还能把文本转回二进制，做「伪造登录记录」的取证实验。
- ⚠️ **这些文件可被篡改**。`wtmp` 的默认权限通常是 `664 root:utmp`，历史上不少系统改成 `660`。有 root 的攻击者常会：
  - 直接改 `wtmp`/`utmp` 抹掉自己的记录；
  - 删掉 `~/.bash_history`；
  - 在 `/var/log` 里做手脚。
  所以**取证时不能只看 `last`**，要交叉验证：
  - `journalctl`（systemd 的 journal 是独立存储，且可配置为只追加 + 远程转发）
  - `auditd` 的日志（`ausearch`）
  - 应用自身日志（`sshd` 的详细日志）
  - 远程日志服务器（最可靠的证据）
- 🔐 常见的审计问法：
  ```bash
  # 失败登录最多的 IP（爆破来源）
  sudo lastb -F | awk '{print $3}' | sort | uniq -c | sort -rn | head

  # 成功登录的 IP 列表
  last -F | grep -v '^$' | awk '{print $3}' | sort | uniq -c | sort -rn | head

  # sshd 上的"Accepted password/publickey"（成功认证）
  journalctl -u sshd --since today --no-pager | grep -E 'Accepted (password|publickey)'

  # 已被 faillock 锁定的账号（见 ../commands/03-权限与用户.md 的 faillock）
  faillock --user rivo
  ```
- 💡 `who` 输出里的 `(:0)` / `(wayland-1)` / `(IP)` 是**来源**——从哪连进来的。远程登录时会显示 IP，这是判断「有没有陌生 IP」的关键列。
- ⚠️ `lastlog` 在本机不可用（`shadow` 包未安装）。替代方案：`sudo lastlog` 装包后可用的等价查询是
  ```bash
  # 用 journal 替代"最后一次登录"
  journalctl _COMM=sshd --no-pager | grep 'Accepted' | tail -20
  ```

### 20. 🔐 权限混乱大排查：一次找出所有可疑点 ⭐⭐⭐

**场景**：接管一台来历不明的服务器。在改动任何东西之前，先做一份权限审计报告。

**要求**：给出一套完整的只读审计命令，覆盖：UID=0 的账号、空密码账号、有登录 shell 的普通账号、SUID/SGID、全局可写目录、无属主的文件、异常 ACL。

<details><summary>参考答案</summary>

```bash
# ============================================================
#  权限审计报告（全部为只读操作，不改动系统）
#  建议：sudo bash -c '...' > /tmp/audit-$(date +%F).txt
# ============================================================

echo "########## 1. UID = 0 的账号（应该只有 root 一个）##########"
awk -F: '$3==0 {print $1, $3, $6, $7}' /etc/passwd
getent passwd | awk -F: '$3==0 {print $1}'

echo
echo "########## 2. 空密码 / 无密码账号（需要 root 读 shadow）##########"
sudo awk -F: '($2=="" ) {print $1 "  ← 空密码！"}' /etc/shadow
sudo awk -F: '($2 ~ /^!?$/) {print $1 "  ← 密码字段为空或仅 !"}' /etc/shadow

echo
echo "########## 3. 有登录 shell 的账号（非 nologin/false）##########"
awk -F: '$7 !~ /(nologin|false|\/bin\/sync)$/ {print $1":"$3":"$7}' /etc/passwd

echo
echo "########## 4. SUID / SGID 文件 ##########"
find / -xdev -perm /6000 -type f \
     -printf '%M %u:%g %10s %TY-%Tm-%Td %p\n' 2>/dev/null | sort -k6

echo
echo "########## 5. 全局可写目录（无 sticky 的最危险）##########"
find / -xdev -type d -perm -0002 ! -perm -1000 \
     ! -path '/proc/*' ! -path '/sys/*' -printf '%M %u:%g %p\n' 2>/dev/null

echo
echo "########## 6. 全局可写文件 ##########"
find / -xdev -type f -perm -0002 \
     ! -path '/proc/*' ! -path '/sys/*' -printf '%M %u:%g %p\n' 2>/dev/null

echo
echo "########## 7. 无属主 / 无属组的文件（可能是残留或攻击痕迹）##########"
find / -xdev \( -nouser -o -nogroup \) -printf '%M %u:%g %p\n' 2>/dev/null

echo
echo "########## 8. 带扩展 ACL 的文件（ls -l 末尾有 +）##########"
find / -xdev -type f -exec getfacl -cp {} \; 2>/dev/null | head -0   # 太慢，换下面按目录抽查
find /etc /srv /home /var/www -type f -exec sh -c \
  'getfacl -cp "$1" 2>/dev/null | grep -qE "^(user|group):[^:]" && echo "$1"' _ {} \; 2>/dev/null

echo
echo "########## 9. 有 immutable/append-only 属性的文件（chattr）##########"
find /etc /usr/bin /usr/sbin -maxdepth 2 -type f -exec lsattr -d {} + 2>/dev/null \
  | grep -E 'i|a' | head -20

echo
echo "########## 10. sudo 配置 ##########"
sudo -l -l 2>/dev/null | head -40
grep -rE '^[^#]' /etc/sudoers /etc/sudoers.d/ 2>/dev/null

echo
echo "########## 11. 组与成员（重点看有没有人混进 root/wheel/sudo/docker）##########"
getent group | awk -F: '$1 ~ /(root|wheel|sudo|adm|docker|disk)$/ {print}'

echo
echo "########## 12. 登录记录概览 ##########"
last -n 15 -F 2>/dev/null
sudo lastb -n 10 -F 2>/dev/null
```

**在沙盒里先练手**（范围受限、结果确定）：

```bash
cd /tmp/linux-practice

echo "=== SUID ==="
find . -perm -4000 -type f -printf '%M %u:%g %p\n'

echo "=== 全局可写目录（高风险：无 sticky）==="
find . -type d -perm -0002 ! -perm -1000 -printf '%M %p\n'

echo "=== 全局可写文件 ==="
find . -type f -perm -0002 -printf '%M %p\n'

echo "=== 有扩展 ACL 的文件 ==="
for f in $(find . -type f); do
  getfacl -cp "$f" 2>/dev/null | grep -qE '^(user|group):[^:]' && echo "$f"
done

echo "=== 断链（可能指向被删掉的持久化文件）==="
find . -xtype l -printf '%p -> %l\n'
```

**预期输出（沙盒）**：

```text
=== SUID ===
-rwsr-xr-x rivo:rivo ./bin/suid-demo

=== 全局可写目录（高风险：无 sticky）===
drwxrwxrwx ./shared

=== 全局可写文件 ===
-rw-rw-rw- ./secret/readme.txt
```

**解析：每一条为什么值得查**

| # | 检查项 | 为什么 |
|---|--------|--------|
| 1 | **UID=0 的账号** | 除 `root` 外任何 UID 为 0 的账号都是**后门**。攻击者常直接把一个普通账号的 UID 改成 0，这样看起来是普通用户、实际是 root |
| 2 | **空密码账号** | 任何人 `su` 上去就拿到该账号的权限。`/etc/shadow` 第 2 字段为空 = 空密码 |
| 3 | **有登录 shell 的账号** | 系统服务账号的 shell 应该是 `/usr/sbin/nologin`。出现 `/bin/bash` 说明有人为了持久登录改过 |
| 4 | **SUID/SGID** | 提权第一入口。**重点是找「不属于任何已安装包」的那些**（用 `pacman -Qo` / `dpkg -S` / `rpm -qf` 核对） |
| 5 | **无 sticky 的全局可写目录** | 能删/换别人的文件。若里面有 root 执行的脚本 → 直接提权 |
| 6 | **全局可写文件** | 能改内容。若被 root 读取（如 `.bashrc`、cron 脚本、配置）→ 提权 |
| 7 | **无属主/无属组文件** | 用户被删了但文件还在（攻击者常「建账号 → 提权 → 删账号」，留下 UID 已不存在的文件）。也常见于手工解压的包 |
| 8 | **扩展 ACL** | ACL 能授予 `ls -l` 看不出的权限，是「隐藏的后门权限」的理想载体 |
| 9 | **`chattr +i` 的文件** | 攻击者用它「保护」自己的后门文件不被删除；也可能是管理员误操作导致配置改不了 |
| 10 | **sudo 配置** | 通配符/危险命令/`NOPASSWD: ALL` 都是提权路径（第 16 题） |
| 11 | **特权组成员** | `docker` 组成员约等于 root（能挂载宿主根目录）；`disk` 组能直接读裸设备；`wheel`/`sudo` 组能给任意人提权 |
| 12 | **登录记录** | 找陌生 IP、异常时间、失败爆破源 |

🔐 **补充的「权限之外的持久化位置」**（权限审计要一起看）：
```bash
# cron
for u in $(cut -d: -f1 /etc/passwd); do crontab -l -u "$u" 2>/dev/null | grep -v '^#'; done
ls -la /etc/cron.{d,daily,hourly,weekly,monthly}/ /etc/crontab /var/spool/cron/ 2>/dev/null
# systemd 的定时与自启
systemctl list-timers --all --no-pager
find /etc/systemd/system /usr/lib/systemd/system -name '*.service' -newermt '30 days ago' 2>/dev/null
# 启动脚本
ls -la /etc/rc.local /etc/profile.d/ ~/.bashrc ~/.bash_profile ~/.config/autostart 2>/dev/null
# 动态库劫持
cat /etc/ld.so.preload 2>/dev/null
```

💡 **审计结果的下一步**：
1. **先隔离**（快照磁盘、断开或限流网络），再做深入分析。**不要在原始环境上"边查边改"**——会破坏证据。
2. 每一条可疑项都要能回答「它属于哪个包 / 谁在什么时候改的」：
   ```bash
   pacman -Qo /usr/bin/pkexec        # Arch
   dpkg -S /usr/bin/pkexec           # Debian
   stat -c '%y %n' /usr/bin/pkexec   # 看 mtime/ctime
   ```
3. 用自动化工具交叉验证（见 [`../commands/12-安全与审计.md`](../commands/12-安全与审计.md)）：
   ```bash
   sudo lynis audit system          # 系统加固审计
   sudo chkrootkit                  # rootkit 扫描
   sudo rkhunter --check --sk       # rootkit + 后门扫描
   sudo aide --check                # 文件完整性
   ```
