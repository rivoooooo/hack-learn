# 综合场景题 · 15 题

真实的运维 / 排障 / 安全场景。每题给出**完整处置流程**：怎么观察 → 怎么定位 → 怎么处置 → 怎么预防。

> **做这组题的方式**：
> 1. 先只看「现象」，自己写下"我会先看什么"。
> 2. 再看「排查路径」，逐步对照 —— 重点看**为什么这样排序**。
> 3. 「处置」里的命令带 `⚠️` 的会改系统，在虚拟机/容器里试。
>
> 这些场景都能在 [`../labs/README.md`](../labs/README.md) 的 Docker 环境里复现。

## 场景 1 · 磁盘满了，`du` 却只算出几十 MB

**现象**

```bash
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        20G   20G     0 100% /

$ sudo du -sh / 2>/dev/null | tail -1
1.2G    /
```

`df` 说用了 20G，`du` 只找到 1.2G。差出来的近 19G 去哪了？

<details><summary>排查路径与处置</summary>

**先建立正确的心智模型**：`df` 报告的是**文件系统层面的已用块数**，`du` 统计的是**目录树里能找到的文件的块数**。两者不一致，说明"有块被占了但目录树里找不到"。

**候选原因（按发生频率排序）**：

| 原因 | 判断方法 |
|------|----------|
| **已删除但仍被进程占用** | `lsof +L1` 有输出 |
| **被覆盖的挂载点**（mount 到了非空目录） | `mount \| grep` 与底层目录内容不一致 |
| **保留块**（ext4 默认给 root 留 5%） | `tune2fs -l` 看 `Reserved block count` |
| **inode 耗尽**（与空间无关，但 `df -i` 会满） | `df -i` |
| 快照 / CoW 占用（btrfs、ZFS、LVM snapshot） | `btrfs filesystem df` / `lvs` |
| 被删除但还有打开的目录（`rm -rf` 半个进程崩了） | 一般会被上面第一条覆盖 |
| 隐藏的巨型文件（`du` 因为权限看不到） | 用 `sudo du` |

**第一步：找"已删除但被占用"的文件（最常见的答案）**

```bash
$ sudo lsof +L1
COMMAND    PID USER   FD   TYPE DEVICE  SIZE/OFF NLINK   NODE NAME
java      2050  app   45u   REG  8,1  18765432100     0  12345 /var/log/app.log (deleted)
                                     ↑ 18.7 GB ！
```

`lsof +L1` 里的 `+L1` 表示"链接数小于 1"，也就是**已经没有目录项指向它了，但进程还开着 fd**。文件内容仍在内核里存着，**磁盘空间不会释放**。

`SIZE/OFF` 会显示这个文件占用的大小，`NAME` 后面带 `(deleted)`。

**不装 `lsof` 时的替代**：

```bash
$ sudo ls -l /proc/*/fd/* 2>/dev/null | grep '(deleted)' | sort -k5 -n | tail
$ sudo find /proc/*/fd -lname '* (deleted)' -ls 2>/dev/null | sort -k7 -n | tail
```

**处置（三种方案，按推荐顺序）**：

**方案 A（最干净）：让进程自己重新打开日志**

```bash
# 先查清是谁
$ sudo lsof +L1 | grep deleted

# 如果是日志文件，让进程重开日志（多数守护进程响应 SIGUSR1 或 SIGHUP）
$ sudo kill -USR1 2050
$ sudo kill -HUP  2050

# 验证空间回来了
$ df -h /
```

**方案 B（激进）：重启这个进程**

```bash
$ sudo systemctl restart <服务>
```

重启后旧 fd 被关闭，空间立即释放。**但这会中断服务**，先评估影响。

**方案 C（不重启进程，把内容"捞"出来再清）**

```bash
# 用 truncate 清空这个 fd 指向的文件（注意是 /proc/<pid>/fd/<n>，不是路径）
$ sudo truncate -s 0 /proc/2050/fd/45
$ df -h /
```

> ⚠️ **`truncate` 这个 fd 会让数据永久丢失**。如果里面可能是你要查的日志（尤其在被入侵的场景下 🔐），**先另存一份**：
> ```bash
> $ sudo cp /proc/2050/fd/45 /var/tmp/recovered_app.log
> $ sudo chmod 600 /var/tmp/recovered_app.log
> ```

**如果是日志文件且反复出现，根治办法是改 logrotate 配置**（让程序在轮转后重新打开文件，而不是继续写旧 inode）：

```
# /etc/logrotate.d/myapp
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    delaycompress
    missingok
    notifempty
    create 0640 app app
    sharedscripts
    postrotate
        systemctl reload myapp > /dev/null 2>&1 || true
    endscript
}
```

关键就是 `postrotate` 段：给程序发信号让它重开日志。**少了这一段，日志轮转后空间永远不释放**——这是本题最常见的原因。

```bash
# 验证 logrotate 配置（不实际操作）
$ sudo logrotate -d /etc/logrotate.conf
# 强制执行一次
$ sudo logrotate -f /etc/logrotate.d/myapp
```

**第二步（如果 lsof 没输出）：检查被覆盖的挂载点**

```bash
# 找一个"被挂载覆盖"的目录：先记录内容摘要
$ sudo du -sx /var/log
# 卸载后看同一目录的内容（临时，⚠️ 会中断服务）
$ sudo umount /var/log && sudo du -sx /var/log && sudo mount /var/log
```

**第三步：`df -i` 看 inode**

```bash
$ df -i /
Filesystem      Inodes  IUsed   IFree IUse% Mounted on
/dev/sda1      1310720 1310720       0  100% /
```

| 症状 | 原因 |
|------|------|
| `df -h` 没满，`df -i` 满了 | inode 耗尽（海量小文件） |
| 报 `No space left on device` 但 `df -h` 和 `df -i` 都不满 | 可能是**保留块**用完（非 root 无法用保留块） |

**找海量小文件的位置**：

```bash
$ sudo find / -xdev -type f | sed 's#/[^/]*$##' | sort | uniq -c | sort -rn | head -20
$ sudo find /var/spool -xdev -type f 2>/dev/null | wc -l
```

典型元凶：`/var/spool/postfix/maildrop`（cron 邮件堆积，因为 cron 输出没重定向）、`/var/lib/php/sessions`（session 文件）、`/tmp`。

**第四步：保留块**

```bash
$ sudo tune2fs -l /dev/sda1 | grep -i 'reserved block'
Reserved block count:     262144
```

ext4 默认给 root 保留 5%，防止用户进程把根分区占满导致系统无法管理。可以用 `tune2fs -m 1` 降到 1%（**只对数据盘建议改，系统盘别动**）。

**预防措施清单**

```bash
# 1. 给关键分区设监控（df -h 和 df -i 都要）
$ df -h && df -i

# 2. 检查 logrotate 的 postrotate 是否都配了
$ grep -L postrotate /etc/logrotate.d/*

# 3. 给日志目录设总量上限（systemd-journald）
$ sudo journalctl --disk-usage
$ sudo systemctl edit systemd-journald
# [Journal]
# SystemMaxUse=1G
```

</details>

## 场景 2 · 服务器 SSH 突然连不上了，但 ping 是通的

**现象**

- `ping server` 正常
- `ssh user@server` 卡住几十秒后报 `Connection timed out`
- 控制台（VNC/IPMI）能登录，本地 `ssh localhost` 也正常

<details><summary>排查路径与处置</summary>

**`ping` 通 + `ssh` 不通 = 网络层没问题，问题在 TCP 层或应用层。** 先用 5 秒缩小范围。

**第一步：在服务端抓包，确定问题在哪一段**

```bash
# 在服务端（用控制台）实时抓 SSH 端口的 SYN
$ sudo tcpdump -i any -nn 'tcp port 22 and tcp[tcpflags] & tcp-syn != 0'
```

| 抓包结果 | 结论 |
|----------|------|
| **完全没有包** | 包在到达主机前被拦（云安全组、网络 ACL、上游设备） |
| 有 SYN，没有 SYN-ACK | 服务端防火墙 DROP，或 sshd 没在监听 |
| 有 SYN，有 RST | 端口没程序在听，或有防火墙 REJECT |
| 有完整握手，然后卡住 | 问题在认证阶段（DNS 反解、PAM、磁盘满、`sshd_config`） |

**第二步：检查 sshd 是否在监听**

```bash
$ sudo ss -tlnp | grep :22
LISTEN 0 128 0.0.0.0:22 0.0.0.0:* users:(("sshd",pid=842,fd=3))
```

如果**没有输出**，sshd 挂了：

```bash
$ sudo systemctl status sshd          # 或 ssh.service（Debian 系）
$ sudo journalctl -u sshd -n 50 --no-pager
$ sudo systemctl restart sshd
```

**第三步：检查防火墙**

```bash
$ sudo nft list ruleset | grep -A5 'chain input'
$ sudo iptables -L INPUT -n -v --line-numbers | head
$ sudo ufw status verbose
```

**第四步（本题最可能的原因）：`fail2ban` 把客户端的 IP 封了** 🔐

```bash
$ sudo fail2ban-client status sshd
Status for the jail: sshd
|- Filter
|  |- Currently failed: 0
|  |- Total failed:     47
|  `- File list:        /var/log/auth.log
`- Actions
   |- Currently banned: 1
   |- Total banned:     3
   `- Banned IP list:   203.0.113.45      # ← 你的 IP 在里面
```

解封：

```bash
$ sudo fail2ban-client set sshd unbanip 203.0.113.45
```

看为什么会被封（`47` 次失败）：

```bash
$ sudo grep 'Failed password' /var/log/auth.log | tail -20
```

> 💡 **如果是自动化脚本反复连 SSH 且带错密码**（比如监控用错密钥），就会触发封禁。修法是给脚本配正确的密钥，或把它的 IP 加进 `ignoreip`。

**第五步：检查"半开连接"打满**

```bash
$ ss -tn state syn-recv | wc -l
$ ss -tn state established '( sport = :22 )' | wc -l
$ cat /proc/sys/net/core/somaxconn
$ cat /proc/sys/net/ipv4/tcp_max_syn_backlog
```

`syn-recv` 状态大量堆积说明有 SYN flood 或扫描。sshd 的 `MaxStartups` 也会限流：

```bash
$ grep -i maxstartups /etc/ssh/sshd_config
MaxStartups 10:30:100
```

含义：未认证连接达到 10 个开始随机丢弃，到 30 个丢弃 30%，到 100 个全丢。

**第六步：认证阶段卡住**

如果能建立 TCP 但卡在认证：

| 原因 | 检查 |
|------|------|
| **DNS 反解超时** | `sshd_config` 里的 `UseDNS yes`（现代默认 `no`）会让服务端反查客户端 IP，DNS 挂了就卡住。改成 `UseDNS no` |
| **`AllowUsers` / `Match` 规则** | `sudo sshd -T \| grep -i allow` |
| **PAM 模块卡住**（如 `pam_systemd` 等 systemd 会话） | `sudo journalctl -u sshd -f` 看实时日志 |
| **磁盘满** | `df -h` —— 磁盘满是 SSH 登录失败的**经典隐藏原因**，因为 sshd 要写审计记录、PAM 要写日志 |
| **`nologin` 文件存在** | `cat /etc/nologin` —— 维护模式会拒绝非 root 登录 |
| **用户被锁定/密码过期** | `sudo passwd -S user`、`sudo chage -l user` |

**第七步：检查 `sshd_config` 是否被改坏**

```bash
$ sudo sshd -t                    # 语法校验（改了配置必跑！）
$ sudo sshd -T | head -40         # 打印生效的完整配置（含默认值）
```

> ⚠️ **改 `sshd_config` 的铁律**：
> 1. 先 `sudo sshd -t` 语法检查
> 2. **不要关闭当前连接**，另开一个 SSH 会话测试新配置能否登录
> 3. 确认能登录后再断开旧会话
> 4. 有控制台（VNC/IPMI）可用时最安全
>
> 直接 `systemctl restart sshd` 然后断开连接，如果配置有错，你就再也连不上了。

**快速恢复通道**（如果已经锁在外面）：

| 手段 | 说明 |
|------|------|
| 云控制台的 VNC / 串口 | 最直接 |
| IPMI / iDRAC / iLO | 裸金属远程管理 |
| 云厂商的 "重置密码" 功能 | 会重启机器并注入密码 |
| 挂载磁盘到另一台机器改配置 | 最保险，不改动运行中的系统 |

**预防**

```bash
# 1. 在 22 端口之外留一个备用 sshd（云端/容器里很常用）
$ sudo /usr/sbin/sshd -p 2222 -o PidFile=/run/sshd2222.pid
# 2. 配 fail2ban 时先加白名单
$ sudo grep -A3 '^\[DEFAULT\]' /etc/fail2ban/jail.local
ignoreip = 127.0.0.1/8 ::1 203.0.113.0/24 10.0.0.0/8
# 3. 用密钥登录，关闭密码认证（减少爆破面）
$ sudo sshd -T | grep -i passwordauthentication
# 4. 监控 sshd 状态与连接数
$ systemctl is-active sshd && ss -tn state established '( sport = :22 )' | wc -l
```

</details>

## 场景 3 · 系统很卡，但 CPU 使用率很低，`load average` 很高

**现象**

```bash
$ uptime
 14:32:05 up 5 days, load average: 42.11, 38.94, 25.30
$ nproc
8
$ top -bn1 | head -5
%Cpu(s):  3.2 us,  1.1 sy,  0.0 ni, 88.4 id,  7.1 wa,  0.0 hi,  0.2 si,  0.0 st
```

load 42 对 8 核来说是 5 倍超载，但 CPU 88% 空闲，`wa`（IO wait）7%。**这不是 CPU 瓶颈。**

<details><summary>排查路径与处置</summary>

**第一步：确认 load 里到底是什么**

load average 统计的是 **R（可运行）+ D（不可中断睡眠）** 状态的进程数。CPU 空闲但 load 高，几乎一定是 **D 状态进程**在堆。

```bash
$ ps -eo stat,pid,user,wchan:32,comm | awk '$1 ~ /^D/'
D     1234 root   rpc_wait_bit_killable   nfs_worker
D     1250 root   nfs_wait_on_request     nfs_worker
D     1263 app    wait_on_page_bit        mysqld
...
```

**第一步就能看出方向**：`wchan` 列直接告诉你进程阻塞在内核的哪个函数。

| `wchan` 关键字 | 指向 |
|----------------|------|
| `nfs_*` / `rpc_*` | NFS 挂载卡住 |
| `wait_on_page_bit` / `blk_*` | 本地磁盘 IO |
| `wait_on_rcu` | 内核 RCU 问题 |
| `cifs_*` | SMB 挂载卡住 |
| `jbd2_*` | ext4 日志提交 |
| `xfs_*` | XFS 文件系统 |

**第二步：看 VM 统计里 blocked 的进程**

```bash
$ vmstat 1 5
procs -----------memory---------- ---swap-- -----io---- -system-- ------cpu-----
 r  b   swpd   free   buff  cache   si   so    bi    bo   in   cs us sy id wa st
 2 38      0 812345 123456 789012    0    0   512  1024  120  340  3  1 88  7  0
   ↑
   b = 38：有 38 个进程处于不可中断睡眠
```

`b` 列持续很大，就是 D 状态的证据。

**第三步：看磁盘 IO 到底多慢**

```bash
$ iostat -xz 1
Device   r/s    w/s   rkB/s  wkB/s  await  r_await  w_await  aqu-sz  %util
sda     45.2  112.3  1234.5 5678.9  892.3    780.2    950.1    12.4   99.8
                                     ↑ 平均等待 892 毫秒！
```

**关键指标（`iostat -xz` 里）**：

| 指标 | 正常 | 异常含义 |
|------|------|----------|
| `r_await` / `w_await` | 机械盘 < 20ms，SSD < 5ms | **超过 100ms 就是严重瓶颈**。这里 780/950ms 是灾难级 |
| `aqu-sz` | 一般 < 1~2 | 平均队列深度。12.4 说明请求大量排队 |
| `%util` | 机械盘接近 100% 是饱和 | **SSD/NVMe 上 `%util` 不可靠**（能并行处理请求，100% 也不代表慢），要结合 `await` |
| `r/s` / `w/s` | 参考值 | IOPS |

**第四步：找出是哪个进程在压磁盘**

```bash
# 需要 root
$ sudo iotop -oP
Total DISK READ: 12.34 M/s | Total DISK WRITE: 156.78 M/s
  PID  PRIO  USER  DISK READ  DISK WRITE  SWAPIN  IO>    COMMAND
 2100 be/4  postgres  0.00 B/s  120.45 M/s   0.00%  95.23% postgres: writer
```

`-o` 只显示有 IO 的，`-P` 显示进程而不是线程。

**没有 `iotop` 时的替代**：

```bash
$ sudo cat /proc/<PID>/io        # read_bytes / write_bytes
$ sudo pidstat -d 1              # 需要 sysstat 包
$ cat /proc/pressure/io          # PSI（Pressure Stall Information）
some avg10=45.23 avg60=32.11 avg300=12.45 total=12345678
↑ some = 至少有一个任务因 IO 停顿的时间占比（45%！）
```

**`/proc/pressure/` 是 Linux 4.20+ 的新特性**，比 load average 精确得多，区分了 `some`（至少一个任务卡）和 `full`（所有任务都卡）：

```bash
$ cat /proc/pressure/io
some avg10=45.23 avg60=32.11 avg300=12.45 total=12345678
full avg10=38.11 avg60=25.44 avg300=9.87 total=9876543
```

`full` 有值说明**所有可运行任务都在等 IO**，系统实质已无进展。

**第五步：按根因处置**

| 根因 | 处置 |
|------|------|
| **申请中的写入过猛**（备份、日志、`fsync` 频繁） | 限速：`rsync --bwlimit`、`ionice -c3`、调 `commit=` 参数 |
| **数据库随机 IO** | 加索引减少全表扫描；把数据放到 SSD；调 `innodb_flush_method` |
| **NFS / CIFS 挂载卡住** | 恢复网络；fstab 加 `soft,timeo=30,retrans=2`；用 `umount -l` 缓解 |
| **磁盘故障（坏道、重试）** | `dmesg -T \| grep -i 'I/O error'`、`smartctl -a`（见场景 13） |
| **内存不足导致换页** | `vmstat` 的 `si`/`so` 非 0；加内存或减少缓存 |
| **RAID 重建/降级** | `cat /proc/mdstat`、`megacli`/`storcli` |

**临时缓解（不是根治）**：

```bash
# 给最重的 IO 进程降优先级（只对"阻塞型"有效，对已被提交的请求无效）
$ sudo ionice -c3 -p 2100
$ sudo renice 19 -p 2100

# ⚠️ 把 dirty page 阈值调小，让写入更平滑（代价是 IOPS 更高）
$ sudo sysctl -w vm.dirty_ratio=10 vm.dirty_background_ratio=3
```

**预防与监控**

```bash
# 关键指标：await、aqu-sz、PSI full
$ iostat -xz 1 5
$ cat /proc/pressure/io

# 让 iostat 常驻采样，出问题时能回看
$ sar -d 1 60 > /tmp/sar_$(date +%s).log
$ sar -b -f /var/log/sa/sa15      # 回看历史某天的 IO
```

> 🔐 **安全相关的同类现象**：挖矿木马会表现为"CPU 打满 + load 高"；而"load 高但 CPU 空闲"更常见于 IO，但**也可能是勒索软件正在批量加密文件**（大量读写）+ 或**正在被批量复制数据**（数据外传）。所以排 IO 的同时顺手看一眼：
> ```bash
> $ sudo ss -tnp state established | grep -v '127.0.0.1'
> $ ps -eo stat,pid,user,comm | awk '$1 ~ /^D/'
> ```

</details>

## 场景 4 · 服务起不来，`systemctl status` 显示 `203/EXEC`

**现象**

```bash
$ sudo systemctl status myapp
× myapp.service - My Application
     Loaded: loaded (/etc/systemd/system/myapp.service; enabled; preset: disabled)
     Active: failed (Result: exit-code) since Tue 2026-09-15 14:00:00 CST; 2min ago
    Process: 3001 ExecStart=/opt/myapp/bin/start.sh (code=exited, status=203/EXEC)
                                                                            ↑↑↑↑↑↑↑↑
```

<details><summary>排查路径与处置</summary>

**先读状态码。`203/EXEC` 的含义是 `EXEC` 失败 —— systemd 无法执行 `ExecStart` 指定的文件。**

常见原因（按频率）：

| 原因 | 怎么验证 |
|------|----------|
| **文件不存在 / 路径写错** | `ls -l /opt/myapp/bin/start.sh` |
| **文件没有执行权限** | `ls -l` 看有没有 `x` |
| **shebang 行有问题**（解释器不存在、`\r\n` 行尾） | `head -1 file \| xxd \| head -2` |
| **解释器路径不存在** | `head -1 file` 拿到的路径 `ls -l` 一下 |
| **SELinux / AppArmor 拒绝** | `sudo ausearch -m avc -ts recent` |
| **`ExecStart` 里有 shell 语法**（管道、重定向、`&&`） | `ExecStart` **不经过 shell**，见下 |
| **文件系统是 `noexec`** | `findmnt -no OPTIONS /opt` |
| **unit 文件里有多余的引号/空格** | `systemctl cat myapp` |

**第一步：核对文件本身**

```bash
$ systemctl cat myapp | grep -i exec
ExecStart=/opt/myapp/bin/start.sh --config /etc/myapp.conf

$ ls -l /opt/myapp/bin/start.sh
-rw-r--r-- 1 root root 1234 Sep 15 10:00 /opt/myapp/bin/start.sh
 ↑ 没有执行位！这就是 203 的原因

$ sudo chmod +x /opt/myapp/bin/start.sh
$ sudo systemctl restart myapp
```

**第二步：检查 shebang**

```bash
$ head -1 /opt/myapp/bin/start.sh | cat -A
#!/bin/bash^M$
           ↑^M 是 Windows 换行的 CR！
```

**`\r\n` 行尾是"脚本在命令行能跑、在 systemd 里 203"的一个隐蔽原因**。因为内核读 shebang 时会把 `\r` 当成解释器路径的一部分，去找一个叫 `/bin/bash\r` 的文件 —— 当然找不到。

```bash
$ sudo sed -i 's/\r$//' /opt/myapp/bin/start.sh
# 或者用 dos2unix
$ sudo dos2unix /opt/myapp/bin/start.sh
```

**验证解释器存在**：

```bash
$ head -1 script.sh
#!/usr/bin/python3.11
$ ls -l /usr/bin/python3.11
ls: cannot access '/usr/bin/python3.11': No such file or directory   # ← 203 的原因
```

**第三步：`ExecStart` 不经过 shell（这是最多人踩的坑）**

```ini
# ❌ 错的：这整行会被当成一个"可执行文件路径"，包含空格和 & 都没有特殊含义
ExecStart=/bin/bash -c "cd /opt/app && ./run.sh > /var/log/app.log 2>&1"

# ⚠️ 上面这行实际上能工作（因为 /bin/bash 存在，-c 是参数）
# 但下面这种一定失败：

# ❌ 绝对不行：systemd 不做 shell 解析，管道和重定向都不是它的语法
ExecStart=/opt/app/run.sh | tee /var/log/app.log

# ❌ 也不行：找不到名为 "cd" 的可执行文件（cd 是 shell 内建命令）
ExecStart=cd /opt/app && ./run.sh

# ✅ 正确：把逻辑写进脚本
ExecStart=/opt/app/run.sh

# ✅ 或者显式调 shell
ExecStart=/bin/bash -c 'cd /opt/app && exec ./run.sh'
```

**systemd 的 `ExecStart` 语法规则**：

- 第一项必须是**绝对路径**（或简单文件名，会在标准目录里找）
- 空格分隔参数，**双引号可以包住含空格的参数**
- **没有** shell 元字符：`|` `>` `<` `&` `;` `$()` `` ` `` 都没有特殊含义
- `%` 开头的说明符会被 systemd 展开（`%i` `%n` `%H` 等）
- 想用 shell 特性必须显式 `ExecStart=/bin/sh -c '...'`

**第四步：看更详细的日志**

```bash
$ sudo journalctl -u myapp -n 100 --no-pager
$ sudo journalctl -u myapp -o verbose | head -40      # 含所有元数据
$ sudo systemd-analyze verify /etc/systemd/system/myapp.service   # 校验 unit 文件
```

**第五步（如果前面都正常）：SELinux / AppArmor**

```bash
# SELinux
$ getenforce
Enforcing
$ sudo ausearch -m avc -ts recent | tail -20
$ ls -Z /opt/myapp/bin/start.sh        # 看文件的 SELinux 标签
$ sudo restorecon -Rv /opt/myapp       # 恢复默认标签

# AppArmor
$ sudo aa-status | head
$ sudo journalctl -k | grep -i apparmor | tail
```

**第六步：`noexec` 挂载**

```bash
$ findmnt -no TARGET,OPTIONS /opt
/opt  rw,noexec,relatime
        ↑ 这个挂载点禁止执行任何文件
```

改成 `rw,exec` 或把程序放到别的分区。

**完整的诊断顺序（可复制）**

```bash
$ U=myapp
$ systemctl cat $U | grep -iE '^(Exec|WorkingDirectory|User|Type)'
$ P=$(systemctl show $U -p ExecStart --value | grep -oP 'path=\K[^ ;]+')
$ echo "ExecStart 路径: $P"
$ ls -l "$P"                       # 存在吗？有 x 吗？
$ head -1 "$P" | cat -A            # shebang 有 \r 吗？
$ file "$P"                        # 是什么类型
$ sudo -u $(systemctl show $U -p User --value) "$P"   # 以服务用户身份试跑
$ sudo journalctl -u $U -n 50 --no-pager
$ sudo ausearch -m avc -ts recent 2>/dev/null | tail
```

> 💡 **最关键的一条**：用 `sudo -u <服务用户> <命令>` **手工以服务的身份跑一次**。这能立刻区分"文件本身有问题"和"权限/环境有问题"。
>
> ⚠️ 服务常见的隐藏问题就是**环境差异**：`EnvironmentFile` 没加载、`PATH` 不同（systemd 的默认 `PATH` 是 `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`，**不含 `/opt/...`**）。所以 `ExecStart` 里的路径要写绝对路径。

</details>

## 场景 5 · 脚本手工运行正常，放进 cron 就失败

**现象**

- `bash /opt/scripts/backup.sh` 手动跑，输出正常
- 加到 crontab 后，日志里什么都没有，或者报 `command not found`

<details><summary>排查路径与处置</summary>

**根因：cron 的环境与交互式 shell 完全不同。** 它**不读取** `~/.bashrc`、`~/.bash_profile`、`/etc/profile`，只带一个极小的环境。

**第一步：把 cron 的实际环境 dump 出来对比** 🔐

```bash
$ crontab -e
```

```cron
*/1 * * * * env > /tmp/cron_env.txt 2>&1
* * * * * echo "PATH=$PATH" >> /tmp/cron_path.txt 2>&1
```

等一两分钟后：

```bash
$ cat /tmp/cron_env.txt
SHELL=/bin/sh
PATH=/usr/bin:/bin
PWD=/home/<你的用户名>
LOGNAME=<你的用户名>
HOME=/home/<你的用户名>
```

> 上面这些是**真实值**，随用户与机器而变（`LOGNAME`、家目录路径都会不同）；
> 重点是看 cron 环境里**缺了什么**，而不是照抄某个具体值。

对比你的交互式 shell：

```bash
$ env | sort > /tmp/shell_env.txt
$ diff <(sort /tmp/cron_env.txt) /tmp/shell_env.txt | head -40
```

**关键差异通常是这几个**：

| 变量 | 交互式 shell | cron | 影响 |
|------|--------------|------|------|
| `PATH` | 含 `/usr/local/bin`、`~/.local/bin`、`/opt/...` | 只有 `/usr/bin:/bin` | **`command not found`** |
| `SHELL` | `/bin/bash` | **`/bin/sh`** | 脚本里的 `[[ ]]`、`${var//x/y}` 等 bash 语法会失败 |
| `HOME` | 有 | 有 | 但 dotfiles 不加载 |
| `LANG` / `LC_*` | 有 | **通常没有** | 输出编码变成 POSIX，中文可能乱码 |
| `TZ` | 有 | 通常没有 | 时间计算会错 |
| 自定义变量 | 有 | **没有** | 脚本读不到 |

**第二步：定位具体失败原因**

```cron
# 把输出和错误都留住（最重要的一步）
*/5 * * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1

# 想更详细，用 bash -x 跟踪
*/5 * * * * bash -x /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

```bash
$ tail -50 /var/log/backup.log
/opt/scripts/backup.sh: line 12: rsync: command not found
/opt/scripts/backup.sh: line 20: [[: not found
```

**第三步：按四种典型问题逐个修**

**问题 A：`command not found`（最常见）**

```cron
# 方案 1：在 crontab 顶部显式设 PATH（推荐）
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
MAILTO=""
0 3 * * * /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

```bash
# 方案 2：脚本内用绝对路径
$ which rsync
/usr/bin/rsync
$ sed -i 's|^rsync |/usr/bin/rsync |' /opt/scripts/backup.sh

# 方案 3：脚本头显式设 PATH（最稳，不依赖 crontab）
#!/usr/bin/env bash
set -euo pipefail
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
```

**问题 B：`[[: not found` / `Syntax error`**

cron 用 `/bin/sh`（在 Debian/Ubuntu 上是 `dash`，不是 bash）执行。**在 crontab 里显式指定解释器**：

```cron
0 3 * * * /bin/bash /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

或者在脚本的 shebang 里写 `#!/usr/bin/env bash`（**并确认 crontab 调的是脚本路径而不是 `sh 脚本`**）。

**问题 C：变量读不到**

```bash
# 脚本里显式 source 需要的文件（注意：这不是 ~/.bashrc，而是专门的配置文件）
#!/usr/bin/env bash
set -euo pipefail
if [[ -r /etc/myapp/myapp.env ]]; then
  set -a                  # 之后所有赋值自动 export
  source /etc/myapp/myapp.env
  set +a
fi
```

> ⚠️ 不要在脚本里 `source ~/.bashrc`。`~/.bashrc` 通常是给**交互式** shell 用的，里面可能有 `return`（非交互时提前退出）、有依赖 `$-` 的判断、或者输出提示信息（污染 cron 的输出）。**用专门的 env 文件。**

**问题 D：时间/时区不对**

```bash
$ timedatectl                      # 看系统时区
$ date
```

```cron
# 在 crontab 里显式设时区（Vixie cron 支持）
CRON_TZ=Asia/Shanghai
0 3 * * * /opt/scripts/backup.sh
```

**第四步：确认 cron 本身在工作**

```bash
$ systemctl status cron           # Debian/Ubuntu
$ systemctl status crond          # RHEL/Arch
$ journalctl -u cron -n 30 --no-pager | tail -20
$ sudo grep CRON /var/log/syslog | tail -20
```

如果日志里**连"执行了"都没有**，说明 cron 没跑这条：

| 现象 | 原因 |
|------|------|
| crontab 里没有这一行 | 编辑没保存（编辑器问题）或编辑了别的用户的 crontab |
| 语法错误 | cron 会拒绝**整份** crontab 并记录日志 |
| 时间字段写错 | 用 `crontab.guru` 之类工具核对 |
| 系统 cron 服务没启动 | `systemctl enable --now cron` |

**第五步（如果 cron 没错但任务是"跑一半"）：检查并发与耗时**

```cron
# 防止上一次还没跑完就再次启动
*/5 * * * * flock -n /var/lock/backup.lock /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

`flock -n` 拿不到锁就立刻退出（`-n` = non-blocking），避免任务堆积。

**预防：一个健壮的 cron 任务模板**

```bash
#!/usr/bin/env bash
# /opt/scripts/backup.sh
set -euo pipefail

# 1. 自己设好环境，不依赖 crontab
export PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
export LC_ALL=C
export TZ=Asia/Shanghai

# 2. 日志带时间戳
log() { printf '%s %s\n' "$(date -Is)" "$*"; }

# 3. 出错时也留下线索
trap 'log "ERROR: 第 $LINENO 行失败，退出码 $?"' ERR

log "备份开始"
rsync -a --delete /data/ /backup/data/
log "备份完成"
```

```cron
PATH=/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin
SHELL=/bin/bash
MAILTO=""
30 3 * * * flock -n /var/lock/backup.lock /opt/scripts/backup.sh >> /var/log/backup.log 2>&1
```

> 💡 **更现代的选择：systemd timer**。它在 unit 文件里能显式声明 `Environment=`、`WorkingDirectory=`、`User=`，日志进 journal（`journalctl -u xxx`），还有 `Persistent=true`（错过的任务重启后补跑）。见 [`../commands/11-系统管理-systemd.md`](../commands/11-系统管理-systemd.md)。
>
> ⚠️ 排查 cron 问题时如果把 `env` 输出到世界可读的 `/tmp`，会泄露环境变量（可能含密钥）🔐。排查完记得删：`rm -f /tmp/cron_env.txt`。

</details>

## 场景 6 · 某进程内存持续增长，最后被 OOM killer 杀掉

**现象**

- 一个 Java/Python 服务每天增长 200MB，几天后被内核杀掉
- `journalctl -u app` 里能看到服务"无故重启"
- `dmesg` 里能找到 OOM killer 的记录

<details><summary>排查路径与处置</summary>

**第一步：确认"被杀"而不是"自己崩"**

```bash
$ sudo dmesg -T | grep -iE 'killed process|out of memory'
[Mon Sep 15 03:14:22 2026] Out of memory: Killed process 12345 (java) total-vm:9234568kB, anon-rss:8154412kB, file-rss:0kB, shmem-rss:0kB
```

**读这条日志的要点**：

| 字段 | 含义 |
|------|------|
| `Killed process 12345 (java)` | 被杀的是谁 |
| `total-vm` | 虚拟内存总量 |
| **`anon-rss`** | **匿名页**（堆、栈、malloc）—— 内存泄漏就长在这里 |
| `file-rss` | 映射的文件页（可回收） |
| `shmem-rss` | 共享内存 |

`anon-rss` 接近内存总量 → 确实是这个进程吃掉了内存。

```bash
$ sudo journalctl -k | grep -i oom | tail -20
$ sudo grep -i 'oom' /var/log/syslog | tail
```

**第二步：确认是内存泄漏，而不是"正常但需要更多内存"**

**泄漏的特征**：内存随时间**单调上升**，且**重启后从低位重新开始**。

```bash
# 建一个采样脚本，长期观察（这是判断"泄漏"的关键证据）
$ cat > /tmp/mem_watch.sh <<'EOF'
#!/bin/bash
PID="$1"
while kill -0 "$PID" 2>/dev/null; do
  printf '%s rss=%s kB\n' "$(date -Is)" "$(awk '/VmRSS/{print $2}' /proc/$PID/status)"
  sleep 60
done
EOF
$ chmod +x /tmp/mem_watch.sh
$ /tmp/mem_watch.sh $(pgrep -x java) >> /tmp/mem_trend.log &
```

看趋势：

```bash
$ cat /tmp/mem_trend.log | awk '{print $1, $2}' | tail -20
```

如果 RSS 每 60 秒稳定涨几 MB 且不回落 → 泄漏（或有缓存没有上限）。

> ⚠️ **"一直涨"不一定是泄漏**。区分两种：
> | 类型 | 特征 | 是否正常 |
> |------|------|----------|
> | 缓存增长 | 涨到某处**平台期**，或内存压力大时会回落 | 正常（如 JVM 堆扩大、页缓存） |
> | 泄漏 | **持续单调上升直到 OOM**，压力下也不释放 | Bug |
>
> **判断方法**：给进程做一次内存压力测试，或在别的进程吃内存时观察它会不会缩。不会缩的就是泄漏。

**第三步：找出泄漏在哪个部分**

**按语言分**：

| 语言 | 工具 | 关键指标 |
|------|------|----------|
| Java | `jcmd <PID> GC.heap_info`、`jmap -histo:live <PID>`、`jstat -gcutil <PID> 1s` | 老年代（Old Gen）是否持续增长 |
| Python | `tracemalloc`、`objgraph`、`memory_profiler` | 对象数量随时间堆叠 |
| Go | `pprof` 的 `heap` profile | `inuse_space` |
| C/C++ | `valgrind --leak-check=full`（离线）、ASan 的 `LeakSanitizer` | `definitely lost` 增长 |
| Node.js | `--inspect` + Chrome DevTools 的 Memory 面板 | 堆快照对比 |

**JVM 的典型排查**：

```bash
$ jcmd <PID> GC.heap_info
garbage-first heap   total 4194304K, used 3987654K
region size 2048K, 1956 young (4005888K), 8 survivors (16384K)
Metaspace       used 89234K, committed 90112K, reserved 1114112K
                    ↑ Metaspace 持续增长 = 类加载器泄漏（热部署常见）

$ jmap -histo:live <PID> | head -20
 num     #instances         #bytes  class name
   1:       2987654      239012320  [C                ← char 数组占了 239MB
   2:        998877       79830160  java.lang.String
```

间隔一段时间做**两次** `jmap -histo:live`，diff 出增长最快的类：

```bash
$ jmap -histo:live <PID> > /tmp/h1.txt
# 等 10 分钟
$ jmap -histo:live <PID> > /tmp/h2.txt
$ diff <(awk '{print $3, $4}' /tmp/h1.txt | sort -k2 -nr | head -30) \
       <(awk '{print $3, $4}' /tmp/h2.txt | sort -k2 -nr | head -30)
```

**第四步：内核视角（与语言无关）**

```bash
$ sudo pmap -x <PID> | tail -5
Address           Kbytes     RSS   Dirty Mode  Mapping
...
total kB         9234568 8154412  8123456

$ sudo pmap -x <PID> | sort -k3 -nr | head -10      # 哪一段占最多
```

```bash
$ cat /proc/<PID>/smaps_rollup
Rss:             8154412 kB
Pss:             4123456 kB       ← Pss 按共享比例分摊，比 Rss 准确
Shared_Clean:    123456 kB
Shared_Dirty:         0 kB
Private_Clean:    12345 kB
Private_Dirty:    2048000 kB      ← 私有脏页 = 进程真正独有的内存
Swap:            512340 kB        ← 已在交换空间里的
```

**`smaps_rollup` 是排查单个进程内存最准确的方式**（`Pss` 比 `Rss` 更接近"该进程实际负担的内存"）。

**第五步：处置**

**短期（止血）**：

```bash
# 1. 给它设个内存上限，让它在超限时被自己约束而不是拖垮系统
$ sudo systemctl edit app
# [Service]
# MemoryMax=4G
# MemoryHigh=3G        # 超过这个值开始回收
# MemorySwapMax=512M
$ sudo systemctl daemon-reload && sudo systemctl restart app
```

`MemoryMax` 达到时，cgroup 会先尝试回收，然后 OOM **只杀这个 cgroup 里的进程**，不会影响系统其他部分 —— 这是比放任全局 OOM 好得多的做法。

```bash
# 2. 看 cgroup 的内存事件（是否真在被限流）
$ cat /sys/fs/cgroup/system.slice/app.service/memory.events
low 0
high 1234            # MemoryHigh 触发次数
max 12               # MemoryMax 触发次数
oom 3                # OOM 次数
oom_kill 3
```

```bash
# 3. 检查有没有 core dump（有些 OOM 会留下）
$ coredumpctl list app
$ coredumpctl info 12345
```

**长期（根治）**：

- 修代码里的泄漏（找到增长的类/对象/缓存，加上限或释放逻辑）
- 给"本来就应该有上限的缓存"设 LRU 上限（无上限的 `dict`/`HashMap` 缓存是最常见的 C++/Java/Python 泄漏源）
- 对 JVM 调 `-Xmx` 和 `-XX:MaxMetaspaceSize`

**预防：把 OOM 变成"可观测事件"**

```bash
# 1. OOM 时打印更多信息
$ sudo sysctl -w vm.oom_dump_tasks=1

# 2. 用 systemd 的 MemoryMax 隔离爆炸半径（推荐做法）
# 3. 监控 RSS 趋势并告警
```

> 🔐 **安全视角**：内存"异常"增长也可能是攻击迹象——比如反序列化漏洞导致的对象膨胀、或者被植入了内存 shell（`memfd` + `execve`）。此时顺手查：
> ```bash
> $ sudo ls -l /proc/<PID>/exe                 # 指向 (deleted) 或 /memfd: 的就是可疑
> $ sudo grep -c . /proc/<PID>/maps
> $ sudo cat /proc/<PID>/maps | grep -i 'memfd\|deleted'
> ```

</details>

## 场景 7 · 🔐 怀疑服务器被入侵，给出取证优先的排查流程

**现象**

- 网络出口监控报警：这台机器在向外网某个 IP 持续发送数据
- `top` 里有个陌生进程占着 CPU
- 可能的入口：暴露在公网的 Redis / 弱口令 SSH / 未打补丁的 Web 应用

> ⚠️ **最重要的原则：先取证，后清理。** 一旦 `kill` 掉进程、`rm` 掉文件、重装系统，**证据就永久消失了**，你无法回答"他是怎么进来的、还留了什么、影响了哪些数据"。
>
> ⚠️ **不要在这台机器上做分析**（攻击者可能装了监控工具）。理想做法：**对磁盘做只读镜像**，在另一台干净的机器/虚拟机上分析。
>
> ⚠️ **全程只做合法授权范围内的调查**。未经授权对他人系统的调查是违法的。

<details><summary>排查路径与处置</summary>

**第 0 步：写保护 + 固定现场（如果机器还能动）**

```bash
# 记录当前时间与系统状态（取证的第一件事是"固定时间线"）
$ date -Is | tee /var/tmp/evidence_$(date +%s)/timeline.txt
$ uptime

# ⚠️ 如果要做磁盘取证，先只读挂载或做镜像（不要继续往这块盘写东西）
$ sudo dd if=/dev/sda of=/mnt/forensics/disk.img bs=4M conv=noerror,sync status=progress
$ # 更好的选择：
$ sudo dcfldd if=/dev/sda of=/mnt/forensics/disk.img hash=sha256 hashwindow=1G
$ sha256sum /mnt/forensics/disk.img | tee /mnt/forensics/disk.img.sha256
```

> 💡 **内存比磁盘更容易消失**，优先级更高。如果可以，先 dump 内存：
> ```bash
> $ sudo dd if=/proc/kcore of=/mnt/forensics/mem.img bs=1M   # 需要内核对 /proc/kcore 的支持
> # 或用 LiME / avml 等专用工具
> ```

**第 1 步：看有哪些"活着的"东西（挥发性数据，最优先）**

```bash
# 1. 进程与完整命令行（注意看路径在 /tmp、/dev/shm 的）
$ ps -eo pid,ppid,user,lstart,stat,cmd --sort=start_time | tail -40

# 2. 进程的可执行文件：指向 (deleted) 或 /memfd: 的高危
$ sudo ls -l /proc/*/exe 2>/dev/null | grep -E 'deleted|memfd'

# 3. 网络连接：找出对外连接
$ sudo ss -tunap state established
$ sudo ss -tunap | grep -vE '127\.0\.0\.1|\[::1\]'

# 4. 监听端口
$ sudo ss -tulnp

# 5. 进程的工作目录（恶意程序常从 /tmp 运行）
$ sudo ls -l /proc/*/cwd 2>/dev/null | grep -vE '/$|/root$|/home/'

# 6. 环境变量（含反弹 shell 的地址）
$ for p in $(ls /proc | grep -E '^[0-9]+$'); do
    echo "--- $p ---"; sudo tr '\0' '\n' < /proc/$p/environ 2>/dev/null | grep -iE 'http|proxy|host|shell';
  done | grep -B1 -iE 'http|shell'
```

**第 2 步：找持久化（攻击者怎么"活下来"）** 🔐

```bash
# cron
$ for u in $(cut -d: -f1 /etc/passwd); do echo "=== $u ==="; sudo crontab -l -u "$u" 2>/dev/null; done
$ ls -la /etc/cron.{d,daily,hourly,weekly,monthly}/ /var/spool/cron/ /var/spool/cron/crontabs/ 2>/dev/null
$ sudo cat /etc/crontab /etc/anacrontab /etc/cron.d/* 2>/dev/null

# systemd（含用户级）
$ systemctl list-units --type=service --all --no-pager | grep -vE '^\s*(UNIT|●)'
$ systemctl list-timers --all --no-pager
$ ls -la /etc/systemd/system/ /usr/lib/systemd/system/ /etc/systemd/user/ ~/.config/systemd/user/ 2>/dev/null
$ sudo find /etc/systemd /usr/lib/systemd -newermt '-30 days' -name '*.service' -o -name '*.timer' 2>/dev/null | head -30
$ systemctl list-unit-files --state=enabled --no-pager

# SSH 授权密钥（最爱的持久化点）
$ sudo find / -xdev -name authorized_keys -o -name '*.pub' 2>/dev/null | head -40
$ sudo cat /root/.ssh/authorized_keys 2>/dev/null
$ sudo find / -xdev -name authorized_keys -exec ls -l {} + 2>/dev/null

# shell 启动文件
$ sudo find / -xdev \( -name '.bashrc' -o -name '.bash_profile' -o -name '.profile' -o -name '.bash_login' \) \
       -newermt '-60 days' -ls 2>/dev/null | head -30

# 动态链接库劫持
$ cat /etc/ld.so.preload 2>/dev/null          # 有内容就是高度可疑 🔐
$ ls -la /etc/ld.so.conf.d/
$ echo "$LD_PRELOAD" "$LD_LIBRARY_PATH"

# 内核模块
$ lsmod | head -40
$ sudo find /lib/modules -newermt '-60 days' -name '*.ko*' 2>/dev/null | head

# PAM 后门（记录所有密码）
$ sudo find /lib*/security /usr/lib*/security -newermt '-60 days' -ls 2>/dev/null | head
$ sudo grep -rn 'pam_' /etc/pam.d/ | grep -vE '^\S+:\s*#' | head -30
```

**第 3 步：找文件层面的痕迹**

```bash
# 最近修改的文件（按时间倒序，排除噪声目录）
$ sudo find / -xdev -type f -newermt '-7 days' \
       -not -path '/proc/*' -not -path '/sys/*' -not -path '/var/log/*' \
       -not -path '/var/lib/docker/*' -printf '%TY-%Tm-%Td %TH:%TM %p\n' 2>/dev/null | sort -r | head -60

# 常见的"藏东西"位置
$ ls -la /tmp /var/tmp /dev/shm /run/shm 2>/dev/null
$ sudo find /tmp /var/tmp /dev/shm /run -type f -newermt '-7 days' -ls 2>/dev/null | head -40

# 隐藏文件与"看起来正常"的名字
$ sudo find / -xdev -name '.*' -type f -newermt '-30 days' 2>/dev/null | head -40
$ sudo find / -xdev -type f -size -4k -newermt '-30 days' -name '*.*' 2>/dev/null | head -40

# 被设了不可变属性的文件（攻击者用它保护自己）
$ sudo lsattr -R /etc /tmp /var/tmp 2>/dev/null | grep -v '^---------------' | head -20

# SUID / SGID
$ sudo find / -xdev -type f -perm -4000 -o -type f -perm -2000 2>/dev/null | sort

# 全局可写的目录（攻击者的落脚点）
$ sudo find / -xdev -type d -perm -0002 -not -path '/tmp' -not -path '/var/tmp' 2>/dev/null | head -30
```

**第 4 步：账号层面的痕迹**

```bash
# 新增/异常的账号
$ awk -F: '$3>=1000 && $3<65534 {print}' /etc/passwd
$ awk -F: '$3==0 {print}' /etc/passwd                    # UID 0 的非 root
$ sudo awk -F: '$2=="" {print $1}' /etc/shadow           # 空密码
$ sudo stat /etc/passwd /etc/shadow /etc/group /etc/sudoers

# 高权限组的成员
$ getent group sudo wheel admin docker | cut -d: -f1,4

# sudoers 被改过吗
$ sudo grep -rE 'NOPASSWD|!authenticate' /etc/sudoers /etc/sudoers.d/ 2>/dev/null
$ sudo find /etc/sudoers.d -newermt '-60 days' -ls 2>/dev/null

# 登录记录（注意：这些文件可能被篡改）
$ last -n 30
$ sudo lastb -n 30                       # 失败登录
$ sudo lastlog | grep -v 'Never'
$ sudo journalctl -u sshd --since '-7 days' | grep -iE 'accepted|failed' | tail -40
$ sudo grep -c 'Failed password' /var/log/auth.log 2>/dev/null
```

> ⚠️ **`/var/log/wtmp`（`last` 的数据源）、`/var/log/btmp`（`lastb`）、`~/.bash_history` 都可能被攻击者清空或伪造** 🔐。检查它们的**文件大小和修改时间**是否异常：
> ```bash
> $ sudo ls -l /var/log/wtmp /var/log/btmp /var/log/lastlog ~/.bash_history
> ```
> 一个"空但 mtime 是最近"的 wtmp 就是被清空的证据。`journalctl` 的日志（如果开了持久化 + 转发到远端）更难篡改。

**第 5 步：日志与审计**

```bash
# systemd 日志（注意看有没有断层 —— 攻击者可能清理过）
$ sudo journalctl --since '-7 days' -p warning --no-pager | tail -60
$ sudo journalctl --list-boots

# auditd 是取证最强的工具
$ sudo ausearch -m EXECVE --start recent | head -40
$ sudo aureport --auth --summary
$ sudo aureport --file --summary | head -30
$ sudo ausearch -ua 1000 --start '-7 days' | head -60     # 按 uid 查
$ sudo aureport --summary --failed

# 检查 sshd 的认证
$ sudo grep -E 'Accepted|Failed|Invalid' /var/log/auth.log 2>/dev/null | tail -50
```

**第 6 步：完整性校验**

```bash
# 如果之前建过基线（强烈建议），直接比对
$ sudo aide --check           # AIDE 基线检查
$ sudo rkhunter --check --sk  # rootkit 扫描
$ sudo chkrootkit | grep -v 'not infected'

# 没有基线时，用包管理器自带的校验
$ sudo pacman -Qkk 2>&1 | grep -v '0 altered files'        # Arch
$ sudo dpkg -V                                              # Debian
$ sudo rpm -Va                                              # RHEL

# 内核与关键二进制是否被替换
$ sudo find /usr/bin /usr/sbin /bin /sbin -type f -newermt '-30 days' -ls 2>/dev/null | head -30
```

> ⚠️ **包管理器的校验依赖本地数据库，如果攻击者同时改了数据库，校验会通过** 🔐。所以最好的做法是**离线保存一份文件哈希清单**：
> ```bash
> $ sudo find /usr/bin /usr/sbin /etc -type f -exec sha256sum {} + > /mnt/offline/baseline.sha256
> ```
> 离线（不可被本机写入的介质）保存的基线才是可信的。

**第 7 步：处置（在完成取证之后）**

按顺序：

| 步骤 | 动作 | 注意 |
|------|------|------|
| 1 | **隔离网络**（不是关机） | 关机会丢内存证据。拔网线或用防火墙隔离 |
| 2 | 保存证据 | 磁盘镜像、内存、日志导出、进程列表 |
| 3 | 评估影响面 | 哪些数据被访问/篡改？横向移动到了哪些机器？ |
| 4 | 修改所有相关凭据 | 所有在这台机器上用过的密码、密钥、token |
| 5 | 修复入口 | 打补丁、改配置、限制暴露面 |
| 6 | **重建而不是清理** | 不做"删掉坏文件"就完事；从干净的镜像重装最可靠 |
| 7 | 恢复业务并加强监控 | 监控同样的入口是否再被利用 |

**加固清单（事后）**

```bash
# 1. 只暴露必要的端口
$ sudo ss -tulnp | grep -E '0\.0\.0\.0|\[::\]'
# 2. SSH 只允许密钥
$ sudo grep -E '^(PasswordAuthentication|PermitRootLogin|PubkeyAuthentication)' /etc/ssh/sshd_config
# 3. 装并启用审计
$ sudo systemctl enable --now auditd
$ sudo auditctl -w /etc/passwd -p wa -k passwd_change
$ sudo auditctl -w /etc/sudoers -p wa -k sudoers_change
# 4. 文件完整性
$ sudo aideinit && sudo cp /var/lib/aide/aide.db.new /var/lib/aide/aide.db
# 5. 日志转发到远端（本机日志会被污染的）
# 6. fail2ban / 端口敲门 / VPN 收口
```

**最关键的三个判断**

| 问题 | 怎么答 |
|------|--------|
| 他是怎么进来的？ | 看入口服务的日志（ssh / web / redis），结合 `lastb`、`auth.log`、应用访问日志 |
| 他做了什么？ | `auditd` 的 EXECVE 记录 + 文件 mtime 分布 + 网络连接历史 |
| 他还留着什么？ | 持久化清单（cron/systemd/ssh keys/ld.so.preload/kernel module）逐项核对 |

</details>

## 场景 8 · 误删了一个正在被进程写入的文件，怎么抢救

**现象**

```bash
$ rm /var/log/mysql/error.log      # 手滑
$ ls /var/log/mysql/error.log
ls: cannot access '/var/log/mysql/error.log': No such file or directory
```

但 MySQL 进程还在跑，日志还在往这个"不存在的文件"里写，磁盘空间也没释放。

<details><summary>排查路径与处置</summary>

**先理解发生了什么**：`rm` 只是删掉了**目录项**（目录里那个名字），文件的 inode 和数据还在，因为进程还持有打开的**文件描述符（fd）**。链接数变成 0，但引用计数不为 0。

**第一步：找到那个 fd**

```bash
$ sudo lsof +L1 | grep mysql
mysqld  1234 mysql  5w  REG  8,1  12345678  0  12345 /var/log/mysql/error.log (deleted)
                                              ↑         ↑
                                        链接数 0   inode 号
```

关键信息：

| 字段 | 值 |
|------|-----|
| `PID` | 1234 |
| `FD` | `5w`（fd 5，`w` 表示以写模式打开） |
| `NLINK` | `0`（这就是 `+L1` 匹配的条件） |
| `NAME` | `/var/log/mysql/error.log (deleted)` |

**不装 `lsof` 的替代**：

```bash
$ sudo ls -l /proc/*/fd/* 2>/dev/null | grep -i 'error.log.*deleted'
l-wx------ 1 mysql mysql 64 Sep 15 14:30 /proc/1234/fd/5 -> /var/log/mysql/error.log (deleted)
```

**第二步：抢救（三种方案）**

**方案 A（最推荐）：直接从 fd 复制出来，然后让进程重开**

```bash
# 1. 把内容恢复到原路径（cp 会创建一个**新**文件，内容来自那个 fd）
$ sudo cp /proc/1234/fd/5 /var/log/mysql/error.log
$ sudo chown mysql:mysql /var/log/mysql/error.log
$ sudo chmod 640 /var/log/mysql/error.log
$ ls -l /var/log/mysql/error.log

# 2. 验证内容对不对
$ sudo tail -20 /var/log/mysql/error.log

# 3. 让进程重新打开日志（不同程序用不同信号）
$ sudo systemctl reload mysql     # 或 kill -HUP 1234 / kill -USR1 1234
```

**注意**：`cp` 之后，进程**仍然在往旧的（已删除的）inode 写**，新的文件暂时不会收到新日志。所以**必须让进程重开日志文件**。重开之后：

```bash
$ sudo lsof +L1 | grep mysql        # 应该没有输出了
$ df -h /                            # 空间释放了
$ sudo tail -f /var/log/mysql/error.log   # 有新的日志进来
```

**方案 B：只清空不恢复（如果内容不重要）**

```bash
$ sudo truncate -s 0 /proc/1234/fd/5
$ df -h /
```

⚠️ 数据永久丢失。适用于"这是个疯狂的日志文件，我只要空间"的场景。

**方案 C：内容很重要，先完整保存再处理**

```bash
# 用 cp 或 cat 完整取出（⚠️ 如果是还在写的大文件，复制过程中会看到"增长的"内容）
$ sudo cat /proc/1234/fd/5 > /mnt/backup/recovered_error.log
$ sudo sha256sum /mnt/backup/recovered_error.log
# 保全之后再做方案 A 或 B
```

> 💡 **如果文件很大，`cp` 时可能因为进程持续写入而一直读不完**。可以用 `dd` 加 `iflag=nonblock`，或者先 `kill -STOP` 暂停进程：
> ```bash
> $ sudo kill -STOP 1234                # 暂停进程
> $ sudo cp /proc/1234/fd/5 /mnt/backup/recovered.log
> $ sudo kill -CONT 1234                # 恢复
> ```

**第三步：验证是否真的恢复**

```bash
$ sudo lsof -p 1234 | grep -i log        # 看它现在打开的是哪个文件
$ df -h /                                 # 空间是否释放
$ sudo ls -li /proc/1234/fd/5 /var/log/mysql/error.log
```

**如果 inode 号不同**，说明进程还开在旧的 inode 上，需要再 reload 一次。

**第四步：如果进程已经死了，但文件还"在"**

如果进程已经退出，`/proc/<PID>` 就没了，fd 也随之消失，**数据无法恢复**。剩下的只有磁盘层面：

```bash
# 立刻卸载或只读挂载这个分区，停止写入
$ sudo mount -o remount,ro /
# 然后在别的机器上用 extundelete / ext4magic / photorec 尝试恢复
$ sudo extundelete /dev/sda1 --restore-file var/log/mysql/error.log
```

> ⚠️ **文件恢复的铁律：发现误删后立即停止对那个分区的写入。** 每一次写入都可能覆盖被删文件的块。所以：
> 1. 立刻 `umount` 或 `remount,ro`
> 2. 用 Live USB 或把磁盘挂到别的机器上做恢复
> 3. 恢复工具的输出**写到另一个盘**，不要写回原分区

**第五步：用 `debugfs` 抢救（ext4，不卸载也能试试）**

```bash
$ sudo debugfs -R 'lsdel' /dev/sda1 | head -30        # ext4 已基本不支持 lsdel
$ sudo debugfs -R 'stat <12345>' /dev/sda1            # 按 inode 号查（如果知道）
$ sudo debugfs -R 'dump <12345> /tmp/recovered' /dev/sda1
```

> 💡 `debugfs` 需要知道 inode 号。如果之前 `lsof` 输出里有 inode（本场景中就是 `12345`），可以试着直接 dumy 出来。但**文件系统一旦重用过这个 inode，数据就没了**。

**预防**

```bash
# 1. 用 alias 给自己加一道刹车（交互式 shell 里）
$ alias rm='rm -I --preserve-root'
$ rm -I
rm: remove 3 arguments recursively? y

# 2. 脚本里用垃圾回收目录代替直接删
$ mkdir -p ~/.trash
$ trash() { mv -- "$@" ~/.trash/; }        # 或装 trash-cli

# 3. 关键日志用 chattr +a（只允许追加，不能删除）
$ sudo chattr +a /var/log/mysql/error.log
$ sudo rm /var/log/mysql/error.log
rm: cannot remove '/var/log/mysql/error.log': Operation not permitted

# 4. 让程序用 logrotate 管理，别手工 rm
# 5. 定期备份 / 用集中式日志（远端 syslog / journald 转发）
```

> 🔐 **安全视角**：`lsof +L1` 也是**攻击者清理痕迹**的重点检查项。攻击者常用 `rm` 删掉恶意程序，但进程还在跑 —— 此时 `/proc/<PID>/exe` 指向 `(deleted)`，你可以直接把它拷出来做样本分析：
> ```bash
> $ sudo ls -l /proc/*/exe | grep deleted
> $ sudo cp /proc/<PID>/exe /var/tmp/sample.bin
> $ sha256sum /var/tmp/sample.bin
> ```

</details>

## 场景 9 · 网站突然大量 403，文件权限看起来"没问题"

**现象**

- Nginx/Apache 日志里大量 `403 Forbidden`
- `ls -l` 看文件是 `-rw-r--r--`，属主 `root:root`
- 之前一直正常，最近有人执行过"批量权限修复"

<details><summary>排查路径与处置</summary>

**403 与 404、500 的区别**：

| 状态码 | 含义 | 排查方向 |
|--------|------|----------|
| 403 | 服务器**能读到文件**但拒绝提供 | 文件/目录权限、SELinux、`nginx.conf` 的 `deny` |
| 404 | 找不到 | 路径错、`root`/`alias` 配错 |
| 500 | 脚本执行出错 | 应用日志，不是权限 |

**403 而文件权限看着正常 → 几乎一定是"目录缺 `x`"或"SELinux"或"应用层的拒绝规则"。**

**第一步：读日志，看 403 的具体原因**

```bash
$ sudo tail -50 /var/log/nginx/error.log
2026/09/15 14:30:11 [error] 2050#2050: *1234 "/var/www/html/index.php" is forbidden (13: Permission denied)
                                                                    ↑ 13 = EACCES
```

`(13: Permission denied)` = `EACCES`，是**权限问题**。

`ngrep`/`grep` 状态码分布：

```bash
$ sudo awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
   4521 200
    892 403          # ← 突然这么多
     12 404
```

**第二步：逐级检查"路径上每一个目录"的 `x`**

**这是本题最关键的一点**：访问 `/var/www/html/a/b/c.php`，需要**路径上每一个目录**都有 `x` 权限给 Web 服务器用户。

```bash
$ sudo -u www-data namei -l /var/www/html/index.php
f: /var/www/html/index.php
drwxr-xr-x root     root     /
drwxr-xr-x root     root     var
drwxr-xr-x root     root     www
drwxr-xr-x root     root     html
-rw-r--r-- root     root     index.php
```

`namei -l` 会列出路径上**每一级**的权限与属主 —— 这是排查 403 最有效的单条命令。

**常见问题**：

| 现象 | 原因 |
|------|------|
| `/var/www/html` 是 `drw-r--r--`（缺 `x`） | `chmod -R 644 /var/www/html` 的错误操作把目录也变成了 644 |
| 某级目录属主是 `root` 且 `700` | Web 服务器用户 `www-data` 进不去 |
| 文件属主是 `root:root` 且 `600` | `www-data` 读不到 |

**第三步：核对"Web 服务器以谁的身份运行"**

```bash
# Nginx
$ ps -o pid,user,group,cmd -C nginx
    PID USER     GROUP    CMD
   2050 root     root     nginx: master process
   2051 www-data www-data nginx: worker process      ← worker 才是实际读文件的
# Apache
$ ps -o pid,user,group,cmd -C apache2 -C httpd
# 配置里显式指定的
$ grep -rE '^\s*(user|User|group|Group)\s' /etc/nginx/nginx.conf /etc/apache2/apache2.conf /etc/httpd/conf/httpd.conf
```

**第四步：快速定位到底哪一级有问题**

```bash
# 以 www-data 的身份实际读一下（最直接的验证）
$ sudo -u www-data cat /var/www/html/index.php > /dev/null && echo "能读" || echo "读不了（这就是 403 的原因）"

# 逐级测试
$ sudo -u www-data test -x /var && echo "/ 可进入"
$ sudo -u www-data test -x /var/www && echo "/var/www 可进入"
$ sudo -u www-data test -x /var/www/html && echo "/var/www/html 可进入"
$ sudo -u www-data test -r /var/www/html/index.php && echo "文件可读"
```

**第五步：修复（正确的方式）**

```bash
# 目录：755（属主读写进入，其他人可进入）
$ sudo find /var/www/html -type d -exec chmod 755 {} +

# 文件：644（属主读写，其他人只读）
$ sudo find /var/www/html -type f -exec chmod 644 {} +

# 或者用符号法（利用 X 的"条件执行位"，一步到位）
$ sudo chmod -R u=rwX,go=rX /var/www/html

# 属主（推荐让 Web 用户拥有，而不是 root）
$ sudo chown -R www-data:www-data /var/www/html

# 只有确实需要写的目录才放宽
$ sudo chmod 775 /var/www/html/uploads
```

**验证**：

```bash
$ sudo -u www-data cat /var/www/html/index.php > /dev/null && echo OK
$ curl -sS -o /dev/null -w '%{http_code}\n' http://localhost/
200
```

**第六步（如果权限都对了还是 403）：SELinux / AppArmor**

```bash
$ getenforce
Enforcing

# 看 SELinux 拒绝日志
$ sudo ausearch -m avc -ts recent | grep -i httpd | tail -20
time->Tue Sep 15 14:30:11 2026
type=AVC msg=audit(...): avc:  denied  { read } for  pid=2050 comm="nginx" name="index.html"
    dev="sda1" ino=12345 scontext=system_u:system_r:httpd_t:s0
    tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file permissive=0
                                    ↑ 文件标签是 user_home_t，不是 httpd_sys_content_t
```

**诊断**：

```bash
$ ls -Z /var/www/html/index.php
unconfined_u:object_r:user_home_t:s0 /var/www/html/index.php
                     ↑ 标签不对（应该是 httpd_sys_content_t）
```

**修复（永久）**：

```bash
# 1. 加一条 fcontext 规则（让 restorecon 知道这类文件该是什么标签）
$ sudo semanage fcontext -a -t httpd_sys_content_t '/var/www/html(/.*)?'
$ sudo restorecon -Rv /var/www/html

# 2. 如果内容需要可写
$ sudo semanage fcontext -a -t httpd_sys_rw_content_t '/var/www/html/uploads(/.*)?'
$ sudo restorecon -Rv /var/www/html/uploads
```

> ⚠️ **不要把 SELinux 设成 `Permissive` 或 `Disabled` 来"解决"问题**。那只是关掉安全检查，会让同类问题在别处继续发生，而且丢失了一层防护。正确做法是修标签。

**AppArmor 的情况**：

```bash
$ sudo aa-status | head -20
$ sudo journalctl -k | grep -i 'apparmor.*denied' | tail -20
$ sudo dmesg | grep -i 'apparmor.*DENIED'
```

修法：编辑 `/etc/apparmor.d/usr.sbin.nginx` 的 `profile`，加上需要的路径规则，然后：

```bash
$ sudo apparmor_parser -r /etc/apparmor.d/usr.sbin.nginx
```

**第七步（如果都不对）：应用层或 Nginx 配置的 deny**

```bash
$ sudo nginx -T | grep -nE 'deny|allow|auth_basic|internal|limit_except'
$ ls -la /var/www/html/.htaccess 2>/dev/null       # Apache 的 .htaccess 可能拒绝
```

常见配置错误：

| 配置 | 效果 |
|------|------|
| `deny all;` 没有配 `allow` | 全部拒绝 |
| `location ~ /\.` 配 `deny all` | 拒绝所有点文件 |
| `internal;` | 该 location 只能被内部重定向访问，直接请求会 403 |
| `auth_basic` 但密码文件不存在 | 也可能是 500 |
| `autoindex off` + 目录 | 目录没有 index 文件 → 403 |

**预防**

```bash
# 1. 建立"权限基线"并定期校验
$ sudo find /var/www -type d -exec chmod 755 {} +
$ sudo find /var/www -type f -exec chmod 644 {} +

# 2. 在 CI / 部署脚本里固化权限，而不是让人手工敲 chmod -R
# 3. 用 namei -l 做"访问某路径"的例行检查
# 4. SELinux 环境下，用 semanage fcontext 而不是 chcon（chcon 不持久）
```

> ⚠️ **`chmod -R 777` 是 403 的常见"后遗症"来源**。有人为了"解决权限问题"执行了它，把目录的 `x` 和各种位的语义搞乱；或者反过来执行了 `chmod -R 644` 导致目录缺 `x`，全站 403。**这类批量操作一定要按 `find -type d` / `-type f` 分开处理。**

</details>

## 场景 10 · 系统时间错乱，导致证书校验失败、定时任务乱跑

**现象**

- `curl https://example.com` 报 `SSL certificate problem: certificate is not yet valid`
- `make` 报 `file has modification time in the future`
- 日志时间戳跳到未来或过去
- cron 任务在不该跑的时间跑

<details><summary>排查路径与处置</summary>

**第一步：确认当前时间与硬件时钟**

```bash
$ date -Is
2026-09-15T14:32:05+08:00

$ timedatectl
               Local time: Tue 2026-09-15 14:32:05 CST
           Universal time: Tue 2026-09-15 06:32:05 UTC
                 RTC time: Tue 2026-09-15 06:32:05
                Time zone: Asia/Shanghai (CST, +0800)
System clock synchronized: yes          # ← 关键：是否已同步
              NTP service: active       # ← NTP 服务状态
          RTC in local TZ: no           # ← RTC 存 UTC 还是本地时间
```

**逐项解读**：

| 字段 | 含义 | 异常判断 |
|------|------|----------|
| `Local time` | 带时区的本地时间 | |
| `Universal time` | UTC 时间 | 与 Local 的差应等于时区偏移 |
| `RTC time` | **硬件时钟（CMOS）** | 与 Universal 应一致（若 RTC 存 UTC） |
| `System clock synchronized` | **时间同步状态** | `no` 说明 NTP 没生效 |
| `NTP service` | 时间同步服务 | `inactive` 要启用 |
| `RTC in local TZ: yes` | **⚠️ 双向启动的经典问题源** | 一般是 `no`（RTC 存 UTC）；Windows 双系统时 Windows 会把它当本地时间 |

**第二步：看时区是否正确**

```bash
$ timedatectl list-timezones | grep -i shanghai
Asia/Shanghai
$ sudo timedatectl set-timezone Asia/Shanghai
$ ls -l /etc/localtime
/etc/localtime -> /usr/share/zoneinfo/Asia/Shanghai
```

**时区错了的表现**：时间本身"对"，但显示的小时数差几小时；日志时间和实际不符；cron 在错误的时间跑。

**第三步：修复时间同步**

**现代方案：chrony 或 systemd-timesyncd**

```bash
# systemd-timesyncd（轻量，桌面/简单服务器）
$ sudo systemctl enable --now systemd-timesyncd
$ timedatectl set-ntp true
$ systemctl status systemd-timesyncd
$ journalctl -u systemd-timesyncd -n 20 --no-pager

# chrony（服务器推荐，收敛快、支持更多源）
$ sudo systemctl enable --now chronyd
$ chronyc sources -v
MS Name/IP address         Stratum Poll Reach LastRx Last sample
^* ntp1.aliyun.com               2   6   377    45    -12us[  -18us] +/-   12ms
^^ ntp2.aliyun.com               2   6   377    47    +15us[  +10us] +/-   15ms
$ chronyc tracking
Reference ID    : 0A0A0A0A (ntp1.aliyun.com)
Stratum         : 3
System time     : 0.000012345 seconds fast of NTP time
Last offset     : +0.000013 seconds
RMS offset      : 0.000045 seconds
Frequency       : 3.245 ppm slow
```

| `chronyc sources` 的标记 | 含义 |
|--------------------------|------|
| `^*` | 当前选中的同步源（**星号 = 已同步**） |
| `^+` | 备选源（可用但未选中） |
| `^-` | 被排除的源 |
| `^?` | 不可达或无响应 |

`Reach` 列是 8 位八进制，表示最近 8 次探测的成功情况。`377` = 全部成功，`0` = 全部失败。

```bash
# 手工立即同步一次（调试用）
$ sudo chronyc makestep
200 OK
```

**为什么不用 `ntpdate`**：`ntpdate` 是"一次性跳变"，会**破坏单调时间**（依赖时间差的应用如数据库、Kerberos 会出问题）。chrony/systemd-timesyncd 会**渐进调整**（slew）而不是跳变。

**第四步：手动设时间（没有 NTP 或时间差太大时）**

```bash
# ⚠️ 关掉 NTP 才能手动设（否则会被同步覆盖）
$ sudo timedatectl set-ntp false
$ sudo timedatectl set-time '2026-09-15 14:32:05'
$ sudo timedatectl set-ntp true

# 或者用 date
$ sudo date -s '2026-09-15 14:32:05'

# 硬件时钟同步
$ sudo hwclock --systohc                 # 系统 → 硬件
$ sudo hwclock --hctosys                 # 硬件 → 系统
$ sudo hwclock --show
```

**第五步：处理"时间跳变"带来的具体问题**

**问题 A：证书校验失败**

```bash
$ curl -v https://example.com 2>&1 | grep -iE 'certificate|expire|not yet'
* Server certificate:
*  start date: Sep  1 00:00:00 2026 GMT
*  expire date: Dec  1 23:59:59 2026 GMT
* SSL certificate problem: certificate has expired
```

检查（需要 `openssl`）：

```bash
$ echo | openssl s_client -connect example.com:443 -servername example.com 2>/dev/null \
    | openssl x509 -noout -dates
notBefore=Sep  1 00:00:00 2026 GMT
notAfter=Dec  1 23:59:59 2026 GMT
```

如果 `notBefore` 是过去、`notAfter` 是未来，但客户端还报错 → **客户端的时间不对**：

```bash
$ date -u                          # 与证书的 GMT 时间对比
$ sudo chronyc makestep            # 立即纠正
$ curl -v https://example.com 2>&1 | grep -i 'SSL certificate problem'   # 应该没有输出了
```

**问题 B：`make` 报时间在未来**

```bash
$ make
make: Warning: File 'foo.o' has modification time 31536000 s in the future
```

这是"构建产物比源文件还新（在未来）"导致的。修好系统时间后：

```bash
$ find . -newermt 'now' -exec touch {} +      # 把所有"未来"的文件时间改成现在
```

**问题 C：cron 任务在错误时间跑**

时间错了，cron 自然在错误的绝对时间触发。**修好时间后，检查有没有任务因为"错过了时间点"而漏跑**：

```bash
$ journalctl -u cron --since '-1 day' | grep -c CRON
```

如果用的是 systemd timer 且设了 `Persistent=true`，重启后会补跑一次。

**问题 D：Kerberos / 集群认证失败**

Kerberos 默认要求客户端与服务端时间差**不超过 5 分钟**，否则票据无效。报错通常是 `Clock skew too great`。

```bash
$ klist
$ sudo chronyc makestep
```

**第六步：处理 RTC 与本地时间的矛盾（双系统）**

```bash
$ timedatectl
          RTC in local TZ: yes        # ← Windows 双系统的典型状态
```

Windows 默认把硬件时钟当**本地时间**，Linux 默认当 **UTC**。双系统切换会导致每次差 8 小时。

两个解法（选一个，不要两边都改）：

```bash
# 解法 1（推荐）：让 Linux 也把 RTC 当本地时间
$ sudo timedatectl set-local-rtc 1 --adjust-system-clock

# 解法 2：改 Windows 的注册表让它用 UTC（更规范，但只影响 Windows）
# 在 Windows 上执行：
# reg add "HKLM\SYSTEM\CurrentControlSet\Control\TimeZoneInformation" /v RealTimeIsUniversal /t REG_DWORD /d 1 /f
```

**完整的诊断顺序**

```bash
$ timedatectl
$ date -u && date
$ ls -l /etc/localtime
$ systemctl status systemd-timesyncd chronyd 2>/dev/null | grep -E 'Active|Loaded'
$ chronyc sources -v 2>/dev/null || timedatectl show-timesync
$ echo | openssl s_client -connect <host>:443 -servername <host> 2>/dev/null | openssl x509 -noout -dates
$ sudo journalctl --since '-1 hour' -p warning | grep -i 'time\|clock\|skew'
$ dmesg -T | grep -i 'clocksource\|tsc\|hpet\|time' | head -20
```

> ⚠️ **虚拟机的时钟漂移**：VM 里如果没装/启动时间同步，时钟会持续漂移（尤其在高负载或快照恢复后）。看 `dmesg` 里的 `clocksource` 选择，以及是否有 `hpet`/`tsc` 不稳定的警告。**虚拟机必须配时间同步**。
>
> 🔐 **安全视角**：时间错乱会让**日志时间线失去意义**，攻击者也常故意改时间来扰乱取证。所以日志时间的一致性很重要 —— 这也是"把日志转发到远端集中存储"的另一个理由。另外，**证书有效期检查依赖系统时间的正确性**，一个被调慢的时钟可能让过期的攻击者证书"看起来有效"。

</details>

## 场景 11 · 一次批量权限操作把系统搞坏了，怎么救

**现象**

有人执行了：

```bash
$ sudo chmod -R 777 /etc          # ⚠️ 灾难
# 或者
$ sudo chown -R alice:alice /     # ⚠️ 更灾难
```

之后：SSH 拒绝登录（`/etc/ssh/ssh_host_*_key` 权限成了 777，sshd 拒绝启动）、`sudo` 报错、`/etc/shadow` 变成世界可读。

<details><summary>排查路径与处置</summary>

**先理解伤害的性质**：`chmod -R` 和 `chown -R` 是**覆盖式**操作，它修改了每个文件的权限/属主。**原始值没有被记录在任何地方**，所以"精确还原"是不可能的 —— 只能靠**恢复默认**或**从备份/重装**。

**第一步：评估范围（不要慌着改回去）**

```bash
$ sudo stat -c '%a %U:%G %n' /etc/passwd /etc/shadow /etc/sudoers /etc/ssh/ssh_host_ed25519_key
777 root:root /etc/passwd           # 应该是 644
777 root:root /etc/shadow           # 应该是 600 或 640（root:shadow）
777 root:root /etc/sudoers          # 应该是 440
777 root:root /etc/ssh/ssh_host_ed25519_key   # 应该是 600
```

**第二步：按"SSH 能登录"优先，先修 SSH**

```bash
# 私钥必须严格受限（sshd 会拒绝权限过宽的私钥）
$ sudo chmod 600 /etc/ssh/ssh_host_rsa_key /etc/ssh/ssh_host_ed25519_key /etc/ssh/ssh_host_ecdsa_key
$ sudo chmod 644 /etc/ssh/ssh_host_*.pub
$ sudo chmod 644 /etc/ssh/ssh_config
$ sudo chmod 600 /etc/ssh/ssh_config.d/* 2>/dev/null
$ sudo chmod 640 /etc/ssh/sshd_config
$ sudo chmod 700 /etc/ssh
$ sudo sshd -t && sudo systemctl restart sshd
```

**第三步：用包管理器"恢复默认权限/属主"**

**这是最可靠的办法** —— 包管理器的数据库里**记录了每个文件的属主、属组、权限**。

**Debian / Ubuntu（`dpkg`）**：

```bash
# 1. 找出所有"权限或属主被改过"的包
$ dpkg -l | awk '/^ii/{print $2}' | while read p; do
    dpkg --verify "$p" 2>/dev/null
  done | grep -vE '^\s*$' | head -40

# 2. 重装所有包以恢复默认（较慢但有效）
$ sudo apt-get install --reinstall $(dpkg -l | awk '/^ii/{print $2}')

# 3. 只重装受影响的包（更精准）
$ sudo apt-get install --reinstall openssh-server sudo passwd libpam0g
```

> 💡 `dpkg` 的数据库在 `/var/lib/dpkg/info/*.md5sums` 里存了哈希，但**权限和属主来自包本身的安装脚本**。所以"重装"是最直接的恢复手段。

**RHEL / CentOS（`rpm`）**：

```bash
# 1. 校验所有包，只看权限/属主不对的（第 2 位是 M=权限，第 5 位是 U=属主）
$ sudo rpm -Va | awk 'substr($0,2,1)=="M" || substr($0,6,1)=="U"' | head -40

# 2. 重装以恢复（rpm 重装会还原权限与属主）
$ sudo rpm -qa | xargs -r sudo rpm --reinstall

# 3. 或用 dnf 的 reinstall 子命令
$ sudo dnf reinstall -y 'openssh*' sudo passwd

# 4. ⭐ 最精准：直接从 rpm 包里提取权限信息与文件重新安装
$ sudo rpm --setperms -a         # 只恢复权限位！
$ sudo rpm --setugids -a         # 只恢复属主与属组！
```

> ⭐ **`rpm --setperms -a` 和 `rpm --setugids -a` 是本题最优解**：它直接按包数据库里记录的元数据**只覆盖权限/属主**，不改内容、不重启服务。这是 RHEL 系恢复批量权限事故的标准手段。

**Arch Linux（`pacman`）**：

```bash
# 1. 校验
$ sudo pacman -Qkk 2>&1 | grep -v '0 altered files'

# 2. Arch 没有等价的 --setperms。可选方案：
#    a) 从包缓存重新解包（注意：不含安装脚本的动作）
$ cd /tmp && pacman -Sw $(pacman -Qqn)        # 下载所有包到缓存
$ sudo pacman -U /var/cache/pacman/pkg/*.pkg.tar.zst --overwrite '*'   # ⚠️ 谨慎

#    b) 更安全的做法：对关键包逐个重装
$ sudo pacman -S --overwrite '*' openssh sudo filesystem
```

**第四步：单独处理"包管理器不管"的文件**

| 文件 | 正确权限 |
|------|----------|
| `/etc/shadow` | `0000` 或 `0640 root:shadow`（发行版不同） |
| `/etc/gshadow` | `0000` 或 `0640 root:shadow` |
| `/etc/passwd` | `0644 root:root` |
| `/etc/group` | `0644 root:root` |
| `/etc/sudoers` | `0440 root:root` |
| `/etc/sudoers.d/*` | `0440 root:root` |
| `~/.ssh/` | `0700` |
| `~/.ssh/id_*`（私钥） | `0600` |
| `~/.ssh/authorized_keys` | `0600` |
| `~/.ssh/config` | `0600` |
| `/root` | `0700`（多数发行版） |
| `/etc/crontab` | `0644 root:root` |
| `/var/spool/cron/crontabs/*` | `0600` 且属主是那个用户 |

```bash
# 🔐 /etc/shadow 被改成 777 是**严重的信息泄露**：任何本地用户都能读到密码哈希
#    修权限之外，还要考虑改密码（哈希可能已被拷走爆破）
$ sudo chmod 0000 /etc/shadow
$ sudo chmod 0000 /etc/gshadow
$ getent group shadow
shadow:x:42:
$ sudo chown root:shadow /etc/shadow /etc/gshadow    # 按发行版实际属组
$ sudo chmod 0640 /etc/shadow /etc/gshadow

# sudoers
$ sudo chmod 440 /etc/sudoers
$ sudo chmod 440 /etc/sudoers.d/*
$ sudo visudo -c                     # 语法校验
```

**第五步（如果 `/` 整个被 `chown -R` 改过）**

这比 `chmod -R` 更难救，因为**几乎所有系统文件都需要 root 属主**。

```bash
# 判断范围
$ sudo find / -xdev -not -user root -not -user nobody 2>/dev/null | head -50
$ sudo find /etc /usr /bin /sbin /var -xdev -not -user root 2>/dev/null | wc -l
```

**处置策略（按可靠性排序）**：

| 策略 | 说明 | 适用 |
|------|------|------|
| **`rpm --setugids -a`** | RHEL 系，一条命令恢复全部包的属主 | ⭐ 首选（RHEL 系） |
| **重装所有包** | `apt-get install --reinstall` 全量 | Debian 系 |
| **从备份恢复** | 有系统备份（`rsync` 快照、LVM snapshot、镜像） | 最好，但要有备份 |
| **重装系统** | 保留 `/home` `/etc`（比对后）重新安装 | 最可靠，代价最大 |
| 手工修 | 对少数关键目录逐个 `chown root:root -R` | 只适合范围很小的情况 |

```bash
# 手工修常见目录（⚠️ 会破坏"本该属于其他用户"的文件，要小心）
$ sudo chown root:root /bin /sbin /lib /lib64 /usr /etc
$ sudo chown -R root:root /etc/systemd /etc/security
# 用户家目录必须保持原属主
$ sudo chown -R alice:alice /home/alice
```

**第六步：验证系统是否恢复正常**

```bash
# 关键检查
$ sudo sshd -t && echo "sshd OK"
$ sudo visudo -c
$ sudo su - nobody -s /bin/sh -c 'id'
$ sudo systemctl daemon-reload
$ sudo systemctl restart sshd sudo cron
$ passwd --status root
$ sudo -l
$ getent passwd root
```

**预防（这才是重点）**

```bash
# 1. 给危险的 rm/chmod/chown 加保护
$ alias chmod='chmod --preserve-root'
$ alias chown='chown --preserve-root'

# 2. 关键文件加不可变属性（防止被意外改）
$ sudo chattr +i /etc/passwd /etc/shadow /etc/sudoers /etc/group
# ⚠️ 但记得：包升级时会因此失败，升级前要 chattr -i

# 3. 用"权限基线"定期校验（cron 每天跑）
$ sudo find /etc /usr/bin /usr/sbin -printf '%m %u:%g %p\n' | sort > /var/lib/baseline_perms.txt
$ # 之后对比：
$ sudo find /etc /usr/bin /usr/sbin -printf '%m %u:%g %p\n' | sort | diff /var/lib/baseline_perms.txt -

# 4. AIDE / Tripwire 做文件完整性（含权限与属主）
$ sudo aide --check | grep -i 'perm\|owner'

# 5. 生产环境禁用直接在 root shell 里跑批量命令；用正式的配置管理（Ansible/Puppet）
#    配置管理的幂等性天然避免了这类事故
```

> ⚠️ **`chmod -R 777 /etc` 会让 `/etc/shadow` 变成世界可读**，等于**本机所有用户的密码哈希暴露**。处置时必须：
> 1. 立即改权限
> 2. **假设哈希已泄露，强制所有用户改密码**
> 3. 检查 `sudoers` 是否被改（777 意味着任何用户都能改它 → 提权）
> 4. 审计这段时间内的登录记录与新建账号

</details>

## 场景 12 · 硬盘出现 I/O 错误，服务卡在 D 状态

**现象**

```bash
$ dmesg -T | tail -30
[Mon Sep 15 14:20:11 2026] blk_update_request: I/O error, dev sda, sector 123456789 op WRITE
[Mon Sep 15 14:20:11 2026] sd 0:0:0:0: [sda] tag#12 FAILED Result: hostbyte=DID_OK driverbyte=DRIVER_SENSE
[Mon Sep 15 14:20:11 2026] critical medium error, dev sda, sector 123456789
[Mon Sep 15 14:20:12 2026] EXT4-fs warning (device sda1): ext4_end_bio:344: I/O error 10 writing to inode 12345
[Mon Sep 15 14:20:13 2026] EXT4-fs (sda1): Remounting filesystem read-only
[Mon Sep 15 14:20:14 2026] Aborting journal on device sda1-8.
```

而业务侧：服务无响应，`ps` 里出现一堆 `D` 状态进程。

<details><summary>排查路径与处置</summary>

**第一步：确认是硬件问题还是软件问题**

```bash
# 1. 内核日志里的关键词
$ sudo dmesg -T | grep -iE 'I/O error|medium error|failed command|ata[0-9]+\.' | tail -40

# 2. SMART 健康状态
$ sudo smartctl -H /dev/sda
SMART overall-health self-assessment test result: FAILED!
                                       ↑ 硬件的自己判断：不行了

# 3. 关键 SMART 属性
$ sudo smartctl -A /dev/sda
ID# ATTRIBUTE_NAME          FLAG     VALUE WORST THRESH TYPE      UPDATED  WHEN_FAILED RAW_VALUE
  5 Reallocated_Sector_Ct   0x0033   100   100   010    Pre-fail  Always       -       120
187 Reported_Uncorrect      0x0032   098   098   000    Old_age   Always       -       45
197 Current_Pending_Sector  0x0012   100   100   000    Old_age   Always       -       88
198 Offline_Uncorrectable   0x0010   100   100   000    Old_age   Offline      -       88
199 UDMA_CRC_Error_Count    0x003e   200   200   000    Old_age   Always       -       0
```

**SMART 属性的危险等级**：

| ID | 属性 | 含义 | 危险信号 |
|----|------|------|----------|
| **5** | Reallocated_Sector_Ct | 已重映射的坏扇区数 | **非 0 且持续增长 = 磁盘在退化** |
| **187** | Reported_Uncorrect | 无法纠正的错误数 | 非 0 → 数据已丢 |
| **197** | Current_Pending_Sector | 待重映射的可疑扇区 | 非 0 → 读取时会失败 |
| **198** | Offline_Uncorrectable | 离线扫描发现的不可纠正扇区 | 非 0 → 严重 |
| **199** | UDMA_CRC_Error_Count | **SATA 线缆/接口**错误 | 非 0 → **先换 SATA 线**（不是盘的错！） |
| 9 | Power_On_Hours | 通电小时数 | 长时间运行参考 |
| 194 | Temperature | 温度 | > 55°C 要注意 |
| 241 | Total_LBAs_Written | 总写入量 | SSD 寿命指标 |

**特别说明 `199 UDMA_CRC_Error_Count`**：它计数的是**传输层**错误，通常是**数据线接触不良或线缆质量问题**，**不是盘坏**。换一根 SATA 线往往就能解决。**别急着换盘。**

**第二步：判断"盘在退化"还是"已经坏了"**

```bash
# 跑一次完整的 SMART 自检（会花较长时间）
$ sudo smartctl -t long /dev/sda
# 等 10 分钟~几小时后看结果
$ sudo smartctl -l selftest /dev/sda
SMART Self-test log structure revision number 1
Num  Test_Description    Status                  Remaining  LifeTime(hours)  LBA_of_first_error
# 1  Extended offline    Completed: read failure       90%      12345         123456789
                                    ↑ 自检读失败 = 有坏道
```

**第三步：确认文件系统状态**

```bash
$ sudo dmesg -T | grep -E 'EXT4-fs|XFS|BTRFS' | tail -30
$ mount | grep -E 'ro,|read-only'
/dev/sda1 on / type ext4 (ro,relatime)      # ← 已被内核强制只读挂载
```

**内核在检测到写入错误后会做两件事**：

1. **把文件系统重新挂载为只读**（防止错误扩散）→ 你的服务立即失去写能力
2. **中止日志（journal abort）** → 这是"不能继续用"的强信号

**第四步：处置（**不要在故障盘上继续做修复操作**）**

**立即做的**：

```bash
# 1. 业务层面：切换到备用节点，把服务摘出去
# 2. 保存现场
$ sudo dmesg -T > /var/log/disk_error_$(date +%s).log 2>/dev/null || \
  sudo dmesg -T > /root/disk_error.log
$ sudo smartctl -a /dev/sda > /root/smart_$(date +%s).txt
$ sudo smartctl -x /dev/sda > /root/smart_extended_$(date +%s).txt

# 3. 立刻备份能读出来的数据（用 ddrescue，比 dd 更适合坏盘）
$ sudo apt install gddrescue           # 或 dnf install ddrescue
$ sudo ddrescue -d -r3 /dev/sda /mnt/backup/sda.img /mnt/backup/sda.mapfile
#      ↑ 直接读  ↑ 重试3次            ↑ 输出镜像          ↑ 进度文件（可续跑）
```

> ⭐ **`ddrescue` 比 `dd` 好在哪里**：
> - 第一遍**只读好区域**（跳过出错的地方），先抢救出 99% 的数据
> - 出错位置记在 `mapfile` 里，可以**中断后续跑**
> - 多轮重试，逐块缩小坏区
> - `dd` 遇到错误会卡住或整体失败，且 `conv=noerror` 会**跳过错误但不记录位置**（镜像里那块是空的，你不知道哪些数据丢了）
>
> 所以**坏盘救援一律用 `ddrescue`，不要用 `dd`**。

**如果是 SSD**：

```bash
# SSD 还有 TRIM、磨损均衡等机制，且坏块处理方式不同
$ sudo smartctl -a /dev/nvme0n1 | grep -iE 'percentage_used|media_errors|available_spare'
Percentage Used:                    92%      # 寿命用了 92%
Media and Data Integrity Errors:    1024     # ← 非 0 就是有数据完整性问题
Available Spare:                    8%       # ← 低于阈值说明备用块快用完
```

**第五步：文件系统层面的修复（只在换盘/恢复后做）**

```bash
# ⚠️ 绝对不能在正在使用的文件系统上做 fsck
# 先卸载，或用 Live USB 启动后对设备做检查
$ sudo umount /dev/sda1
$ sudo fsck -f -y /dev/sda1              # ext4
$ sudo xfs_repair -n /dev/sda1           # XFS：-n 是只检查不改！
$ sudo xfs_repair /dev/sda1              # 确认后再实际修
$ sudo btrfs check --readonly /dev/sda1  # btrfs：只读检查
```

> ⚠️ **XFS 的 `xfs_repair` 在"日志需要重放"时会拒绝运行**，需要先 `xfs_repair -L`（**清空日志**）—— 而这**会丢失最近未落盘的数据**。所以在数据盘上先想清楚能不能接受这个损失。

**第六步：D 状态进程怎么处理**

```bash
# 看它们阻塞在哪
$ ps -eo pid,stat,wchan:32,comm | awk '$2 ~ /^D/'
```

这些进程**杀不掉**（`kill -9` 无效，因为 D 状态屏蔽信号）。它们的 IO 请求在块层排队。

```bash
# 看块层的队列
$ sudo cat /sys/block/sda/inflight
       0        0       # 读写 inflight 数量
$ cat /proc/diskstats | grep sda
```

处理方式：

1. 如果硬件能恢复（换线、重启存储），D 进程会自己完成 IO 并继续。
2. 如果硬件彻底不行，**只能重启机器**（`reboot` 可能也会卡，需要 `reboot -f` 或硬件复位）。
3. ⚠️ 重启前尽量把内存里的数据落盘（虽然已经失败了）。

**第七步：换盘后的恢复**

```bash
# 1. 新盘分区（复制原分区表）
$ sudo sfdisk -d /dev/sda > /root/sda_partition_table.txt
$ sudo sfdisk /dev/sdb < /root/sda_partition_table.txt

# 2. 从 ddrescue 镜像恢复到新盘
$ sudo ddrescue /mnt/backup/sda.img /dev/sdb /mnt/backup/sda_restore.mapfile

# 3. fsck 后挂载验证
$ sudo fsck -f /dev/sdb1
$ sudo mount /dev/sdb1 /mnt/check && sudo ls -la /mnt/check | head

# 4. 如果用了 UUID 挂载（fstab），新盘的 UUID 变了！
$ sudo blkid /dev/sdb1
$ sudo sed -i 's/<旧UUID>/<新UUID>/' /etc/fstab && sudo mount -a
```

**预防**

```bash
# 1. 定期跑 SMART 自检并监控关键属性
$ sudo smartctl -t short /dev/sda     # 每天
$ sudo smartctl -t long  /dev/sda     # 每周
# 2. smartd 常驻监控并告警
$ sudo systemctl enable --now smartd
$ cat /etc/smartd.conf | grep -v '^#'
# 3. 用 RAID 而不是单盘（容忍单盘故障）
$ cat /proc/mdstat
# 4. 监控 dmesg 里的 IO 错误
$ sudo dmesg -T | grep -ci 'I/O error'
# 5. 备份，且定期验证备份**能恢复**（备份不验证等于没有备份）
# 6. 装 UPS，避免意外断电（写入中断是"日志中止"的主因之一）
```

> 🔐 **安全视角**：`smartctl` 也能看到盘的**通电时间、序列号、型号**，这些在取证时用于确认"这块盘是不是原来那块"。另外，磁盘故障也可能是**攻击者故意制造的**（物理接触或恶意固件），在安全事件调查中要保留盘不覆盖。

</details>

## 场景 13 · `journald` 日志占满了磁盘

**现象**

```bash
$ df -h /
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        40G   40G     0 100% /

$ sudo journalctl --disk-usage
Archived and active journals take up 8.5G in the file system.
```

<details><summary>排查路径与处置</summary>

**第一步：看日志占了多少、哪些在涨**

```bash
$ sudo journalctl --disk-usage
Archived and active journals take up 8.5G in the file system.

$ sudo ls -lsh /var/log/journal/*/
total 8.5G
4.0G -rw-r-----+ 1 root systemd-journal 4.0G Sep 15 14:30 system@1234.journal
2.5G -rw-r-----+ 1 root systemd-journal 2.5G Sep 14 03:00 system@1233.journal
1.0G -rw-r-----+ 1 root systemd-journal 1.0G Sep 13 03:00 system@1232.journal
```

**第二步：找出"谁在疯狂打日志"**

```bash
# 按来源统计日志量（找出最吵的服务）
$ sudo journalctl --since '-1 day' -o json | jq -r '.SYSLOG_IDENTIFIER // ._COMM' | sort | uniq -c | sort -rn | head -20
   1289345 nginx
    234567 myapp
     12345 kernel
```

```bash
# 不装 jq 的话，用其它字段
$ sudo journalctl --since '-1 day' --no-pager | awk '{print $5}' | sed 's/\[[0-9]*\]//' | sort | uniq -c | sort -rn | head -20
```

```bash
# 按优先级看错误量
$ sudo journalctl --since '-1 day' -p err --no-pager | wc -l
$ sudo journalctl -p err --since '-1 day' --no-pager | awk '{print $5}' | sort | uniq -c | sort -rn | head
```

**一个服务疯狂打错误日志（比如连接失败重试循环）是日志暴涨最常见的原因** —— 修掉根因比清日志重要。

**第三步：立即释放空间（三选一）**

```bash
# 方案 1（推荐）：把日志裁到指定大小
$ sudo journalctl --vacuum-size=500M
Vacuuming done, freed 8G of archived journals from /var/log/journal.

# 方案 2：按保留时长裁
$ sudo journalctl --vacuum-time=7d
$ sudo journalctl --vacuum-time=2weeks

# 方案 3：按文件数裁
$ sudo journalctl --vacuum-files=5
```

> ⚠️ `--vacuum-*` **只删归档（已轮转）的日志，不删当前正在写的**。所以裁完之后当前那个 `.journal` 文件可能还是很大。
>
> ⚠️ **删日志会丢证据** 🔐。如果这台机器正在做安全调查，先导出再删：
> ```bash
> $ sudo journalctl --since '-30 days' --no-pager > /mnt/backup/journal_export.txt
> $ sudo journalctl -o export --since '-30 days' > /mnt/backup/journal_export.bin
> ```

**第四步：配置上限（防止再次发生）**

```bash
$ sudo systemctl edit systemd-journald
```

```ini
[Journal]
# 日志总上限（所有 journal 文件加起来不超过这个值）
SystemMaxUse=1G

# 单个 journal 文件的上限
SystemMaxFileSize=100M

# 保留的最短/最长时间
MaxRetentionSec=1month

# 内存中的日志（重启就没了，用于缓解磁盘压力）
RuntimeMaxUse=100M

# 日志级别：只保留 info 及以上（不发 debug）
MaxLevelStore=info

# 压缩（默认开）
Compress=yes

# 限制单个服务的日志速率（防止打日志风暴）
RateLimitIntervalSec=30s
RateLimitBurst=10000
```

```bash
$ sudo systemctl restart systemd-journald
$ systemctl show systemd-journald -p SystemMaxUse
```

**重要配置项说明**：

| 配置 | 作用 | 建议值 |
|------|------|--------|
| `SystemMaxUse` | **硬上限**（超过会开始裁旧日志） | 按磁盘大小，一般 1G~4G |
| `SystemMaxFileSize` | 单文件上限，影响轮转粒度 | `SystemMaxUse` 的 1/8 |
| `MaxRetentionSec` | 时间上限 | `1month` |
| `RateLimitIntervalSec` / `RateLimitBurst` | **限制每个服务的日志速率** | 默认 30s/10000，日志风暴时可调小 |
| `Storage` | `persistent`（存盘）/ `volatile`（只存内存）/ `auto` / `none` | 见下 |

**`Storage` 的四种值**：

| 值 | 行为 |
|----|------|
| `volatile` | 只写在 `/run/log/journal`，**重启就丢** |
| `persistent` | 存在 `/var/log/journal`，重启保留 |
| `auto` | 有 `/var/log/journal` 目录就 persistent，否则 volatile |
| `none` | **完全关闭持久化**（只转发给 syslog 或远端） |

🔐 **取证角度**：`Storage=volatile` 意味着**攻击者重启一次就抹掉了所有 journal 证据**。所以有安全要求的机器应设 `persistent`，并**转发到远端**（见下）。

**第五步（如果是容器 / 特殊环境）**

```bash
# 容器里 journald 常不可用，日志走 stdout
$ docker logs --tail 100 <container>
$ docker inspect <container> | jq '.[0].HostConfig.LogConfig'
```

Docker 的日志也可以无限增长（`json-file` driver）：

```bash
# 看容器日志大小
$ sudo du -sh /var/lib/docker/containers/*/*-json.log | sort -h | tail -5

# 配置上限（daemon 级别）
$ sudo cat /etc/docker/daemon.json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "5" }
}
```

**第六步：日志量少但磁盘还是满 → 检查别的**

```bash
$ sudo journalctl --disk-usage
Archived and active journals take up 128M in the file system.     # 不是 journald 的问题

$ sudo du -xh / --max-depth=2 2>/dev/null | sort -h | tail -25
$ sudo lsof +L1                   # 已删除但仍被占用的文件
```

**常见"非 journald"的日志占用**：

| 位置 | 说明 |
|------|------|
| `/var/log/*.log` | 传统 syslog / 应用日志，看 `logrotate` 配置 |
| `/var/log/nginx/*.log` | Web 日志 |
| `/var/lib/docker/` | 镜像、容器层、卷 |
| `/var/cache/` | 包管理器缓存（`apt clean` / `dnf clean all` / `pacman -Sc`） |
| `/var/spool/` | mail、cron 的输出堆积 |
| `/var/crash/` | core dump（`systemd-coredump`） |
| `/tmp`、`/var/tmp` | 临时文件没清理 |

```bash
$ sudo journalctl --disk-usage              # journald
$ sudo du -sh /var/log /var/cache /var/lib/docker /var/crash /tmp /var/tmp 2>/dev/null
$ sudo systemd-tmpfiles --clean --dry-run    # 看 systemd 会清理什么
$ sudo coredumpctl list                       # 有哪些 core dump
$ sudo coredumpctl --vacuum-size=100M         # 限制 coredump 大小
```

**第七步：日志转发到远端（安全与容量双赢）** 🔐

```bash
# 1. systemd-journal-upload（把 journal 发到远端 journald 或 HTTP 端点）
# /etc/systemd/journal-upload.conf
[Upload]
URL=https://logserver.example.com:19532
ServerKeyFile=/etc/ssl/private/journal-upload.key
ServerCertificateFile=/etc/ssl/certs/journal-upload.crt
TrustedCertificateFile=/etc/ssl/certs/ca.crt

$ sudo systemctl enable --now systemd-journal-upload

# 2. rsyslog 转发（传统方式）
# /etc/rsyslog.d/50-remote.conf
*.* @@logserver.example.com:514      # @@ = TCP，@ = UDP
$ sudo systemctl restart rsyslog

# 3. 用 journald 的 ForwardToSyslog
$ sudo systemctl edit systemd-journald
# [Journal]
# ForwardToSyslog=yes
```

**为什么要转发**：攻击者拿到 root 后**第一件事就是清日志**。本地日志不可信，远端（且机器无写权限，最好只写不删）才是可靠的证据源。

**完整的处置与预防清单**

```bash
# 立即
$ sudo journalctl --vacuum-size=500M
$ df -h /

# 找出噪音源
$ sudo journalctl --since '-1 day' --no-pager | awk '{print $5}' | sort | uniq -c | sort -rn | head

# 配上限
$ sudo systemctl edit systemd-journald    # 加 SystemMaxUse/SystemMaxFileSize
$ sudo systemctl restart systemd-journald

# 防再发
$ sudo systemctl enable --now smartd      # 磁盘健康
$ sudo journalctl --disk-usage             # 加进监控
$ # 把日志转发到远端
```

> ⚠️ **不要用 `rm /var/log/journal/*` 删 journal**。systemd-journald 持有这些文件的 fd，`rm` 后空间**不会释放**（变成"已删除但被占用"，见场景 1），而且可能让 journald 行为异常。**正确做法是 `journalctl --vacuum-*`。**

</details>

## 场景 14 · 容器起来就退出，Kubernetes 里是 `CrashLoopBackOff`

**现象**

```bash
$ kubectl get pods
NAME                     READY   STATUS             RESTARTS      AGE
myapp-7d9f8b6c5-abcde    0/1     CrashLoopBackOff   8 (45s ago)   3m12s
```

或者本地 Docker：

```bash
$ docker run myapp:latest
$ docker ps -a
CONTAINER ID   IMAGE          STATUS                     
3f2c8a4e1d5b   myapp:latest   Exited (1) 3 seconds ago
```

<details><summary>排查路径与处置</summary>

**第一步：看容器为什么退出的（退出码是第一条线索）**

**Docker**：

```bash
$ docker ps -a
CONTAINER ID   IMAGE          COMMAND       CREATED          STATUS                     PORTS   NAMES
3f2c8a4e1d5b   myapp:latest   "/entry.sh"   3 seconds ago    Exited (1) 2 seconds ago           myapp

**退出码语义**：

| 退出码 | 含义 | 常见原因 |
|--------|------|----------|
| **0** | 正常退出 | ⚠️ **容器主进程不能"正常退出"**！容器生命周期 = 主进程生命周期。没有前台进程了就退出（见下） |
| 1 | 应用级错误 | 配置错、依赖不可用、崩溃 |
| 2 | 用法错误 | 命令行参数错 |
| **126** | 命令无法执行 | 没执行权限、不是可执行格式 |
| **127** | 命令未找到 | `ENTRYPOINT`/`CMD` 里的命令不在镜像里 |
| **128+N** | 被信号 N 杀死 | 137 = 137−128 = 9 = SIGKILL（**通常是被 OOM killer 杀**） |
| 139 | 段错误（SIGSEGV，128+11） | 程序崩溃 |
| 143 | SIGTERM（128+15） | 被优雅停止 |

**第二步：看日志**

```bash
$ docker logs myapp                  # stdout + stderr
$ docker logs --tail 100 -f myapp
$ docker logs myapp 2>&1 | tail -50
$ docker inspect myapp | jq '.[0].State'
```

```bash
$ kubectl logs myapp-7d9f8b6c5-abcde
$ kubectl logs myapp-7d9f8b6c5-abcde --previous       # ⭐ 看**上一次**崩溃的日志
$ kubectl logs myapp-7d9f8b6c5-abcde -c <容器名>       # 多容器 Pod 指定容器
$ kubectl logs -f myapp-7d9f8b6c5-abcde
$ kubectl logs myapp-7d9f8b6c5-abcde --tail=200
```

> ⭐ **`--previous`（`-p`）是排查 CrashLoopBackOff 的关键**。Pod 反复重启时，`kubectl logs` 看到的是**当前这次**（可能刚起来还没输出），而 `--previous` 是**上一次失败的那一轮**，那里才有报错。

**第三步：按最常见的 5 类原因逐个排除**

**原因 1：容器没有前台进程（退出码 0）**

```dockerfile
# ❌ 错：主进程是 nginx 的启动脚本，它 fork 出守护进程后自己退出 → 容器立即结束
CMD service nginx start

# ❌ 错：nginx 默认配置是 daemon on，会 fork 后父进程退出
CMD nginx

# ✅ 对：让 nginx 在前台运行
CMD ["nginx", "-g", "daemon off;"]

# ✅ 对：如果用 systemd/supervisord，必须让它们在前台
CMD ["/usr/bin/supervisord", "-n", "-c", "/etc/supervisord.conf"]
```

**排查**：

```bash
$ docker inspect myapp --format='{{.Config.Cmd}} {{.Config.Entrypoint}}'
[service nginx start] []
```

**验证方式**：手工跑一个 shell 覆盖 entrypoint，看里面发生了什么：

```bash
$ docker run --rm -it --entrypoint /bin/sh myapp:latest
/ # service nginx start
/ # ps aux        # 看有没有前台进程
/ # exit
```

**原因 2：配置/依赖问题**

```bash
$ docker logs myapp 2>&1 | grep -iE 'error|refused|denied|timeout|not found|no such'
```

| 报错关键词 | 指向 |
|------------|------|
| `Connection refused` | 依赖的服务（DB/Redis）不可达 |
| `Unknown host` / `getaddrinfo` | DNS 解析失败（K8s 里看 Service 名 / CoreDNS） |
| `Access denied` | 凭据错误 |
| `Permission denied` | 文件权限 / 以非 root 运行但需要特权 |
| `exec format error` | **镜像架构与宿主机不匹配**（arm64 镜像跑在 amd64 上） |
| `no space left` | 磁盘满（见场景 1） |

**架构不匹配**（很常见）：

```bash
$ docker inspect myapp:latest --format='{{.Architecture}}/{{.Os}}'
arm64/linux
$ uname -m
x86_64
# ← 不匹配！需要 --platform linux/amd64 或使用 multi-arch 镜像
```

**原因 3：被 OOM 杀掉（退出码 137）**

```bash
$ docker inspect myapp --format='{{.State.OOMKilled}}'
true

$ docker inspect myapp --format='{{.HostConfig.Memory}}'
536870912            # 512MB 上限

$ docker logs myapp | tail
Killed
```

**Kubernetes 里**：

```bash
$ kubectl describe pod myapp-7d9f8b6c5-abcde | grep -iE 'oom|limit|Memory'
$ kubectl get pod myapp-... -o jsonpath='{.spec.containers[*].resources}'
```

修法：调大 limit，或修应用的内存使用。

```bash
$ docker run --memory=1g myapp:latest
```

**原因 4：探针（probe）配置不当 —— 只在 K8s 里**

```yaml
livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 5      # ← 如果应用启动需要 30 秒，5 秒后探针失败 → 被重启 → 永远起不来
  periodSeconds: 10
  failureThreshold: 3
```

**症状**：日志显示应用启动正常，但运行几秒后被重启。

```bash
$ kubectl describe pod myapp-... | grep -A5 -i 'liveness\|readiness'
  Warning  Unhealthy  10s (x3 over 30s)  kubelet  Liveness probe failed: Get "http://10.1.2.3:8080/healthz": dial tcp: connect: connection refused
```

修法：加大 `initialDelaySeconds`，或改用 `startupProbe`（专门给慢启动应用）：

```yaml
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  failureThreshold: 30
  periodSeconds: 10            # 最多给 5 分钟启动时间
```

**原因 5：挂载/权限问题**

```bash
$ docker logs myapp 2>&1 | grep -i 'permission denied'
mkdir: cannot create directory '/data': Permission denied
```

| 场景 | 原因 |
|------|------|
| 挂载了宿主目录，容器内用户 UID 不同 | 宿主目录属主是 UID 1000，容器里是 100 |
| `readOnlyRootFilesystem: true` 但要写文件 | 需要额外的 `emptyDir` 挂载 |
| Secret/ConfigMap 权限 | K8s 挂载的 Secret 默认 `0644`，若要求 `0600` 要设 `defaultMode` |
| SELinux 上下文 | `:Z` 后缀（`-v /data:/data:Z`） |

**第四步：进入"起不来"的容器调试**

容器起来就退，无法 `exec` 进去。三个办法：

```bash
# 办法 1：覆盖 entrypoint，起一个能交互的 shell
$ docker run --rm -it --entrypoint /bin/sh myapp:latest
$ docker run --rm -it --entrypoint /bin/bash myapp:latest    # 如果镜像有 bash

# 办法 2：让它"起但不执行主进程"，用 sleep 撑住
$ docker run -d --name debug --entrypoint sleep myapp:latest 3600
$ docker exec -it debug /bin/sh

# 办法 3（K8s）：临时改 command 为 sleep
$ kubectl run debug --image=myapp:latest --restart=Never --command -- sleep 3600
$ kubectl exec -it debug -- /bin/sh
```

**在调试 shell 里手工复现启动过程**：

```bash
$ docker run --rm -it --entrypoint /bin/sh -v $(pwd)/config:/app/config myapp:latest
/ # cat /app/entrypoint.sh          # 看启动脚本
/ # sh -x /app/entrypoint.sh        # 带 trace 执行，看卡在哪一行
/ # env                             # 看环境变量
/ # ls -la /app
/ # su -s /bin/sh appuser -c '/app/start.sh'    # 以应用用户身份跑
```

**第五步：检查资源与调度（K8s）**

```bash
$ kubectl describe pod myapp-... | grep -A10 'Events:'
$ kubectl get events --sort-by='.lastTimestamp' | tail -30
$ kubectl top pod myapp-...                    # 实际资源使用
$ kubectl describe node <节点名> | grep -A10 'Conditions\|Allocated resources'
```

| Event 消息 | 原因 |
|------------|------|
| `Insufficient memory/cpu` | 节点资源不足，Pod 无法调度 |
| `FailedScheduling` | 亲和性/污点/资源约束不满足 |
| `MountVolume.SetUp failed` | PV/PVC 挂载失败 |
| `ImagePullBackOff` | 镜像拉不下来（名称错、私有仓库凭据缺失、网络） |
| `ImagePullBackOff` + `unauthorized` | 需要 `imagePullSecrets` |

```bash

$ docker inspect myapp --format='{{.State.Pid}}'
$ sudo nsenter -t <PID> -n ss -tlnp        # 进容器的网络命名空间看监听
$ sudo nsenter -t <PID> -n ss -tnp state established
```

**第六步：一个完整的诊断脚本（可复制）**

```bash
#!/bin/bash
# diagnose_container.sh <容器名或ID>
C="${1:?用法: $0 <容器名或ID>}"
echo "=== 1. 基本状态 ==="
docker inspect "$C" --format 'ExitCode={{.State.ExitCode}} OOMKilled={{.State.OOMKilled}} Error={{.State.Error}} Started={{.State.StartedAt}} Finished={{.State.FinishedAt}}'
echo "=== 2. 启动命令 ==="
docker inspect "$C" --format 'Entrypoint={{.Config.Entrypoint}} Cmd={{.Config.Cmd}}'
echo "=== 3. 资源限制 ==="
docker inspect "$C" --format 'Memory={{.HostConfig.Memory}} CpuQuota={{.HostConfig.CpuQuota}}'
echo "=== 4. 挂载 ==="
docker inspect "$C" --format '{{range .Mounts}}{{.Type}} {{.Source}} -> {{.Destination}} (rw={{.RW}}){{"\n"}}{{end}}'
echo "=== 5. 最近 100 行日志 ==="
docker logs --tail 100 "$C" 2>&1 | tail -100
echo "=== 6. 相关内核信息 ==="
sudo dmesg -T | grep -iE "oom|killed process" | tail -5
```

**预防**

```yaml
# 1. 显式声明资源请求与限制（不要不写）
resources:
  requests: { memory: "256Mi", cpu: "250m" }
  limits:   { memory: "512Mi", cpu: "500m" }

# 2. 用 startupProbe 而不是靠大 initialDelaySeconds
# 3. 合理设置 restartPolicy 与 backOffLimit
# 4. 镜像里保留一个 shell（极简镜像如 distroless 无法 exec 调试）

$ kubectl debug -it myapp-... --image=busybox --target=myapp

> 💡 **`kubectl debug` 是排查极简镜像的现代手段**：它给 Pod 注入一个临时的、带工具的容器，且可以共享目标容器的进程/网络命名空间。
>
> 🔐 **安全提示**：排查容器时用 `nsenter -t <PID> -a` 进入容器命名空间，会**继承宿主的 root 权限**。这正是容器逃逸的典型手法（见 [`../commands/14-容器与虚拟化.md`](../commands/14-容器与虚拟化.md)）。只在你有权限的机器上用。

## 场景 15 · 一台机器上的多个服务互相影响（资源争抢）

**现象**

- 机器上跑着 Web、数据库、定时备份、日志采集
- 每天凌晨跑备份时，Web 响应时间从 50ms 涨到 3s
- 白天偶发数据库查询超时
- 各服务单独看都"正常"，整体体验差

<details><summary>排查路径与处置</summary>

这类问题的核心是**资源不是被某一个服务耗尽，而是几个服务在同一时刻竞争同一资源**。所以排查思路是**建立时间线**，找出"谁和谁在同一时间抢什么"。

**第一步：先建立"资源消费时间线"**

```bash
# 采集一整天的高频指标（sar 是 sysstat 包）
$ sar -u 60 1440  > /tmp/sar_cpu_$(date +%F).log     # CPU，每分钟一次，一天
$ sar -r 60 1440  > /tmp/sar_mem_$(date +%F).log     # 内存
$ sar -b 60 1440  > /tmp/sar_io_$(date +%F).log      # IO
$ sar -n DEV 60 1440 > /tmp/sar_net_$(date +%F).log  # 网络
$ sar -d 60 1440  > /tmp/sar_disk_$(date +%F).log    # 每块盘
$ sar -q 60 1440  > /tmp/sar_load_$(date +%F).log    # 负载与运行队列
$ sar -W 60 1440  > /tmp/sar_swap_$(date +%F).log    # 换页
```

**用 history 模式回看（如果 sysstat 已经在收集）**：

```bash
$ sar -u -f /var/log/sa/sa15 -s 02:00:00 -e 05:00:00     # 只看凌晨 2-5 点
$ sar -d -f /var/log/sa/sa15 -s 02:00:00 -e 05:00:00
$ sadf -d /var/log/sa/sa15 -- -u | head -20              # 输出便于画图/awk 处理
```

**对齐时间线**（这是关键动作）：

```bash
$ echo "=== CPU ===" && sar -u -f /var/log/sa/sa15 -s 02:30:00 -e 03:30:00 | tail -20
$ echo "=== IO ===" && sar -b -f /var/log/sa/sa15 -s 02:30:00 -e 03:30:00 | tail -20
$ echo "=== 负载 ===" && sar -q -f /var/log/sa/sa15 -s 02:30:00 -e 03:30:00 | tail -20
```

如果 IO 的 `tps`/`wkB/s` 在 03:00 飙升，而 CPU 的 `%iowait` 同步上升、负载 `ldavg-1` 同步上升 —— **备份任务在 03:00 抢了磁盘**。

**第二步：确认"谁"在抢**

```bash
# 定时任务的时间点
$ ls -la /etc/cron.d/ /etc/cron.daily/ /etc/cron.hourly/
$ for u in $(cut -d: -f1 /etc/passwd); do sudo crontab -l -u "$u" 2>/dev/null | sed "s/^/[$u] /"; done
$ systemctl list-timers --all --no-pager
NEXT                         LEFT     LAST                         PASSED  UNIT
Mon 2026-09-16 03:00:00 CST  12h left Mon 2026-09-15 03:00:12 CST  11h ago backup.timer
```

```bash
# 备份任务在做什么
$ sudo systemctl cat backup.service
$ sudo journalctl -u backup.service --since 'today 02:00' | head -30
```

```bash
# 数据库的慢查询（同时段）
$ sudo tail -1000 /var/log/mysql/slow.log
$ sudo journalctl -u postgresql --since 'today 02:00' | grep -i slow
```

**第三步：量化竞争的程度**

```bash
# 用 cgroup 看每个服务的实际资源消耗（systemd 场景）
$ systemd-cgtop -m -b -n 1 --order=memory
Control Group                                    Tasks   %CPU   Memory  Input/s Output/s
system.slice                                     1234   145.2    9.8G    12.3M/s  45.6M/s
├─backup.service                                    4    12.1    245.6M    2.1M/s  38.2M/s    ← 备份
├─mysqld.service                                   89    98.4    6.2G    8.9M/s   6.1M/s     ← 数据库
└─nginx.service                                    12    22.4    812.3M   1.2M/s   0.9M/s

$ systemd-cgtop -b -n 1 --order=io
```

```bash
# PSI（内核级资源压力，最准确）
$ cat /proc/pressure/cpu /proc/pressure/io /proc/pressure/memory
some avg10=12.34 avg60=8.12 avg300=4.56 total=...
full avg10=5.67 avg60=3.21 avg300=1.23 total=...
```

```bash
# 看按进程的 IO（需 root）
$ sudo iotop -oP -d 5
```

**第四步：处置（三类手段）**

**手段 A：用 cgroup 给服务划资源（最推荐，systemd 直连）**

```bash
# 1. 给备份任务限制 CPU 和 IO 权重
$ sudo systemctl edit backup.service
```

```ini
[Service]
# CPU：最多用 1 个核的 50%（100000/50000 = 50%）
CPUQuota=50%
# CPU 权重（默认 100，越小越让路）
CPUWeight=20

# IO：权重 10（默认 100），让备份在 IO 竞争中处于劣势
IOWeight=10
# 更狠：直接限制带宽
IOReadBandwidthMax=/dev/sda 20M
IOWriteBandwidthMax=/dev/sda 50M

# 内存上限（见场景 6）
MemoryMax=1G

# 进程优先级（让 CPU 调度器也让路）
Nice=19
IOSchedulingClass=idle
```

```bash
$ sudo systemctl daemon-reload
$ sudo systemctl restart backup.service
# 验证
$ systemctl show backup.service -p CPUQuotaPerSecUSec -p IOWeight -p MemoryMax
$ cat /sys/fs/cgroup/system.slice/backup.service/io.weight
```

**手段 B：用 IO 调度器的 cgroup 支持（老内核/非 systemd）**

```bash
# 手工建 cgroup（cgroup v1 风格）
$ sudo cgcreate -g blkio:/backup
$ sudo cgset -r blkio.throttle.write_bps_device="8:0 52428800" /backup     # 8:0 = sda, 50MB/s
$ sudo cgexec -g blkio:/backup /opt/scripts/backup.sh
```

**手段 C：错开时间（最简单，成本最低）**

```bash
# 把备份从 03:00 挪到 04:30，避开数据库的批处理
$ sudo systemctl edit backup.timer
```

```ini
[Timer]
OnCalendar=*-*-* 04:30:00
RandomizedDelaySec=300        # ⭐ 加随机延迟，避免所有机器同一秒开始（雪崩）
Persistent=true
```

> ⭐ **`RandomizedDelaySec` 是集群场景的关键**。如果 100 台机器的定时任务都在 03:00:00 启动，会在同一瞬间把所有后端打爆。加随机延迟能把压力摊平。

**手段 D：应用层优化（治本）**

| 优化 | 效果 |
|------|------|
| 备份改用增量（`rsync` / `restic` / `borg`） | IO 量降一个数量级 |
| 备份加限速（`rsync --bwlimit`、`ionice -c3`） | 不抢占前台 IO |
| 数据库加索引，减少全表扫描 | 减少随机 IO |
| 数据库调 `innodb_io_capacity`（SSD 上调高） | 更好地利用 SSD 并行能力 |
| 用连接池，减少短连接开销 | 降低 TIME-WAIT 和 CPU 开销 |
| 把备份/分析类任务放到**独立的机器** | 物理隔离，最彻底 |

**第五步：验证改善**

```bash
# 在下一个备份周期，同时采集两边的指标
$ sar -b -f /var/log/sa/sa16 -s 04:00:00 -e 05:30:00
$ curl -w 'total=%{time_total}\n' -so /dev/null http://localhost/api/health   # 每 10 秒一次

# 用 PSI 看"IO 造成的停顿"是否下降
$ cat /proc/pressure/io
```

**第六步：建立监控（防止再次失控）**

```bash
# 关键指标（每个服务都要有上限 + 告警）
# CPU: 每个 cgroup 的 CPU 使用 + CPUQuota 触发次数
# 内存: MemoryMax 触发次数、OOM 次数
$ cat /sys/fs/cgroup/system.slice/*.service/memory.events 2>/dev/null | head

# IO: await、%util、PSI full
$ iostat -xz 1 5
$ cat /proc/pressure/io

# 负载与队列
$ sar -q
$ uptime
```

**一个实用的"资源账本"模板**

| 服务 | CPU 需求 | 内存 | IO 模式 | 时间窗 | 优先级 | 限量手段 |
|------|----------|------|---------|--------|--------|----------|
| MySQL | 高（突发） | 6G（固定） | 随机小 IO，频繁 fsync | 全天 | **最高** | 不限制，保证资源 |
| Nginx | 中 | 1G | 少 | 全天 | 高 | `CPUQuota=200%` |
| 备份 | 低 | 512M | **顺序大 IO** | 凌晨 | 低 | `CPUQuota=50%`、`IOWeight=10`、`--bwlimit` |
| 日志采集 | 低 | 256M | 顺序写 | 全天 | 低 | `IOWeight=50` |

规划的原则：**分清"延迟敏感"（数据库、Web）和"吞吐优先"（备份、批处理）**，前者保证资源，后者设上限并在时间上错开。

> 💡 **更彻底的方案是容器化/隔离**：把备份、日志采集放到独立的 Pod/容器，用 K8s 的 `resources.limits` 和 `priorityClass` 强制隔离。物理机上一台机器跑多个"对资源敏感度不同"的服务，本质上是把风险耦合在了一起。
>
> 🔐 **安全视角**：资源争抢也可能被**恶意利用**——攻击者在机器上跑挖矿程序会抢 CPU；跑扫描器会抢网络；做数据打包外传会抢 IO。所以"突然的资源争抢"除了查自己的定时任务，也要看一眼有没有陌生的进程和外连（见场景 3、场景 7）。

</details>

- [ ] `load` 高但 CPU 空闲，说明什么？怎么验证？（D 状态；`vmstat` 的 `b`、`ps` 的 STAT、`/proc/pressure/io`）
- [ ] systemd 报 203/EXEC，我会按什么顺序排查？（文件存在/权限/shebang/解释器/`ExecStart` 无 shell 语义）
- [ ] cron 失败但手工成功，我第一个怀疑什么？（`PATH`，以及 `SHELL=/bin/sh`）
- [ ] 判断"内存泄漏"和"缓存增长"的关键区别是什么？（是否单调上升、压力下是否释放）
- [ ] 怀疑被入侵时，为什么不能先 `kill` 进程？（会丢失内存证据与进程信息）
- [ ] 删除正在被写入的文件后，空间为什么没释放？怎么救？（fd 仍持有 inode；`/proc/PID/fd`）
- [ ] 403 而权限看着正常，用什么命令一次看清路径上每一级？（`namei -l`）
- [ ] 时间错乱会导致哪些具体故障？（证书校验、Kerberos、cron、构建时间戳）
- [ ] 批量 `chmod -R` 事故后，RHEL/Debian/Arch 各自的恢复手段？（`rpm --setperms --setugids` / `dpkg` 重装 / 从包缓存解包）
- [ ] SMART 里 `199 UDMA_CRC_Error_Count` 非 0 先换什么？（SATA 线，不是盘）
- [ ] 坏盘救援为什么用 `ddrescue` 而不是 `dd`？（分轮次、可续跑、记录坏区位置）
- [ ] `journald` 日志满了，为什么不能 `rm`？（fd 仍持有；用 `journalctl --vacuum-*`）
- [ ] CrashLoopBackOff 时为什么必须用 `kubectl logs --previous`？（当前这轮可能还没输出）
- [ ] 多个服务争资源，用什么机制强制隔离？（cgroup v2 / `systemd` 的 `CPUQuota`、`IOWeight`、`MemoryMax`）
